## 논문 선정 배경

최근 개발자들 사이에서 "Cursor / Claude Code 같은 코딩 에이전트가 어디까지 사람을 대체하나"라는 질문이 반복적으로 올라오고 있습니다. 보통 이런 논의는 *생산성 X% 향상* 같은 효율 지표 수준에서 멈추는 경우가 많은데, 이 논문은 한 발 더 나아가 **"소프트웨어를 만드는 행위의 정의 자체가 바뀐다"**는 주장을 first-principles 분석으로 정리하고 있어 흥미로워 읽어봤습니다.

특히 다음 두 가지가 와닿았습니다.

- 요즘 만들어지는 Agent 시스템 다수가 결국 "코드 = LLM이 그때그때 만들고 버리는 도구" 구조에 가까워지고 있다는 점
- 업계 전반에서 "Agent-as-a-Service" 형태의 사업·운영 모델 논의가 빈번해진 만큼, 그 이론적 배경을 한 번 정리해 두고 싶었습니다.

## 1. 패러다임 이분법 — "코드는 무엇인가"의 재정의

논문은 먼저 전통 소프트웨어와 에이전트 시스템을 **공리 수준**에서 다음과 같이 구분합니다.

| 구분 | 전통 소프트웨어 | 에이전트 시스템 |
|---|---|---|
| 코드의 위상 | **의사결정 로직의 영속적 담체** | **LLM 추론 루프가 사용하는 일시적 도구** |
| 의사결정 주체 | 코드 = 인간 설계자의 의도가 박제된 결과 | LLM/에이전트의 동적 추론 |
| 변경 단위 | 릴리즈 / 패치 (영구적) | 호출 / 세션 (즉시 생성·폐기) |
| 핵심 자산 | 코드베이스, 아키텍처 문서 | 모델 가중치, 프롬프트, 메모리, 도구 체인 |
| 품질 보증 | 유닛/통합 테스트, 정적 분석 | 시뮬레이션, 정책 검증, 행동 평가 |

저자는 이 구분이 단순히 "개발 방식이 다르다" 수준이 아니라, **"소프트웨어가 무엇을 가리키는 단어인가"의 정의가 바뀌는 일**이라고 강조합니다. 코드가 더 이상 시스템의 "본체"가 아니라 LLM의 자율 추론을 보조하는 *기구(instrument)*가 되면, 우리가 50년간 다듬어온 "코드 중심의 품질·일정·인력 관리" 프레임이 적용 대상 자체를 잃는다는 논리입니다.

## 2. 역사적 전환 — Licensed SW → SaaS → AaaS

논문은 산업의 변화를 "**복잡성이 누구에게 귀속되는가**"라는 한 축으로 깔끔하게 풀어냅니다.

### 2.1 Licensed Software (1980s~)

- 고객이 패키지를 구매해 **자체 인프라에 설치·운영**
- 설치·업데이트·커스터마이징의 복잡성 대부분이 **사용자 측**(고객 IT)에 귀속
- 코드는 100% "인간이 사전 설계한 결정 로직"

### 2.2 Software-as-a-Service (2000s~)

- 소프트웨어가 클라우드에서 운영되고, 사용자는 브라우저/클라이언트로 접속
- 인프라·버전 관리 복잡성이 **서비스 제공자(벤더)**로 이동
- 사용자는 *구성·사용*에만 집중. 다만 **"코드 중심" 패러다임은 그대로 유지** — 누가 운영하느냐가 바뀐 것뿐.

### 2.3 Agent-as-a-Service (2025~)

- 사용자는 "**목표 / 정책 / 제약 조건**"을 자연어로 정의
- 에이전트가 내부적으로 *언제, 어떤 코드를 생성·실행·폐기할지* 결정. 사용자에게는 그 과정이 투명함.
- 복잡성은 더 이상 사용자가 다루는 정적 SW 스택에 있지 않고, "**에이전트가 동적으로 구성하는 행동·플랜·도구 체인**"에 자리잡음.

> 그래서 저자는 단순히 "새 SaaS 세대가 등장했다"가 아니라, **"코드를 다루던 학문이 정책·목표·평가를 다루는 학문으로 무게중심을 옮긴다"**고 말합니다.

## 3. Complexity Scaling — 왜 인간 중심 SE는 한계에 부딪치는가

논문 4장은 "복잡성을 누가 흡수하느냐"에 대한 first-principles 분석입니다. 핵심 논거를 요약하면:

1. **탐색 공간의 차원성**
   - 전통 SE: \(N\)개의 상호작용하는 변수 → 사람이 손으로 관리해야 할 분기·예외가 최소 \(O(N^2)\) 이상으로 폭증.
   - 에이전트: 탐색 공간은 지수적이지만, **LLM의 추론 메커니즘이 런타임에 압축·우선순위화**하여 도달 가능한 부분 공간만 다룸.
2. **사전 계산 vs 런타임 추론의 비대칭**
   - 전통 SE는 "미리 모든 케이스를 고려해서 코드에 인코딩"하는 *컴파일 타임 무한 책임* 구조.
   - AaaS는 **추론 시점에 필요한 복잡도만 동원**하고, 그 외에는 모델 안의 사전 지식으로 갈음. → 운영비용 곡선이 다른 모양으로 휘어짐.
3. **자기 개선 루프(self-improvement loop)**
   - 전통 코드는 정적이라 "성능이 시간에 따라 *자연 감소*" (요구 변화 ↔ 코드 고착).
   - 에이전트는 피드백·평가 루프를 통해 시간이 지날수록 *자가 개선* 가능.
4. **필요한 만큼의 복잡성(complexity-on-demand)**
   - 인간은 처음부터 모든 엣지 케이스를 모듈로 떼어내려 하지만, 에이전트는 **"이 요청에 필요한 만큼만"** 도구 체인을 조립.
   - 결과적으로 *유지보수 부채*의 성격이 바뀜 — 코드 부채에서 **정책·평가·관측 부채**로.

저자는 이 네 가지 비대칭이 누적되면, **"코드를 잘 짜는 능력"이 시스템 품질의 병목이 아니게 된다**고 결론짓습니다. 병목은 "에이전트가 일하기 좋은 환경(도구·데이터·정책·평가)을 설계하는 능력"으로 옮겨갑니다.

## 4. AaaS 진화 로드맵 (4단계)

논문 6장은 산업이 다음과 같은 4단계를 거쳐 *자기진화 에이전트 생태계*로 수렴한다고 봅니다.

| Phase | 이름 | 코드와 에이전트의 관계 | 인간의 역할 |
|---|---|---|---|
| Phase 1 | **Augmentation (강화)** | 기존 SW에 에이전트가 *보조 모듈*로 추가. 자동완성·테스트 생성 등. | 여전히 코드·아키텍처 주도 |
| Phase 2 | **Substitution (대체)** | 특정 기능 모듈을 에이전트가 *독립적으로* 설계·구현 | 검증·감독 비중 증가 |
| Phase 3 | **Autonomous Systems (자율)** | 요구사항 수집 → 배포까지 에이전트가 일관 수행 | 목표·정책 정의, 예외 대응 |
| Phase 4 | **Self-Evolving Ecosystem (자기진화 생태계)** | 에이전트들이 서로 협업하며 *자체적으로 목표·도구를 갱신* | 거시 거버넌스 (안전·윤리·KPI) |

저자는 현재 산업이 **대략 Phase 1 후반 ~ Phase 2 초입**에 있고, Phase 3로 가는 데 5~10년이 걸릴 것으로 추정합니다. Phase 4는 "방향성 가설" 수준의 비전.

## 5. Agentic Engineering vs Software Engineering

논문 후반부의 가장 실용적인 부분으로, 새 학문 분야로서의 *Agentic Engineering*을 다음과 같이 정의합니다.

| 차원 | 전통 Software Engineering | Agentic Engineering |
|---|---|---|
| **설계 산출물** | 알고리즘·자료구조·아키텍처 문서 | 목표 정의, 정책, 평가 기준, 도구·데이터 카탈로그 |
| **버전 관리 단위** | 코드 (Git 커밋) | 프롬프트·모델 스냅샷·메모리 상태·도구 버전 |
| **테스트 전략** | 유닛/통합 테스트 (결정적) | 시뮬레이션·롤아웃 평가 (확률적) |
| **배포 모델** | 특정 시점의 릴리즈 | 지속 관측 + 동적 업데이트 |
| **에러 처리** | 예측 가능한 예외 | 예측 불가능 상황에 대한 **복원력(resilience)** |
| **인간 역할** | 설계·구현·디버깅 | 목표 정의, 가드레일, 평가 인프라 구축 |
| **핵심 기술** | 언어·프레임워크·아키텍처 패턴 | 프롬프트 공학, 평가 설계, 정책·메모리 관리 |

> 즉, *"소프트웨어 공학 vs 데이터 사이언스"*가 별도 분야로 자리잡았듯, 향후 *Agentic Engineering*이 별도의 정체성을 갖고 분기할 것이라는 예측.

## 6. 시사점

**① 개인 (Practitioners) 관점**

- 코드 작성 역량 자체보다, **문제 정의 · 요구사항 명료화 · 평가 설계** 역량의 중요성이 커진다.
- 디버깅이 "코드 라인 추적"에서 "에이전트 행동·도구 호출 로그 추적"으로 옮겨간다 — Claude Code의 trace나 LangSmith 같은 관측 도구가 유닛테스트만큼 일상이 됨.
- 조직 차원의 의미: AI 활용 가이드(Cursor / Claude Code 등) 같은 자료가 갖는 위상이 더 커진다.

**② 조직 관점**

- 인력 구성: "코드 중심 풀스택 조직"에서 **도메인 전문가 + 에이전트 오케스트레이터 + 평가/거버넌스 엔지니어**의 삼각 구조로 재편될 가능성.
- 비즈니스 모델: "앱/기능 판매" → **"에이전트가 달성한 업무 결과(Outcome)에 과금"**으로 이동. SAP의 *Autonomous Enterprise*, Microsoft·Google의 에이전트 플랫폼 전략과 정확히 같은 방향.
- 인프라 투자: 코드 저장소·CI/CD 만큼이나 **에이전트 평가 환경, 메모리 스토어, 정책 가드레일**에 대한 투자 비중이 커진다.

---

## 7. 정리

- 이 논문은 "AI 에이전트가 소프트웨어 공학을 끝낸다"가 아니라, **"소프트웨어 공학이 다루던 핵심 자산이 코드에서 정책·평가·도구 체인으로 옮겨간다"**는 주장입니다.
- Licensed → SaaS → **AaaS**라는 역사적 흐름과 *Complexity Scaling* 첫 원리 분석을 같이 묶어, 실무자가 자기 일을 설명할 수 있는 새 어휘(*Agentic Engineering*)를 제공한다는 점이 가장 큰 기여.
- 다만 *이론 논문*이라는 한계를 분명히 인지하고, 정량적 의사결정에는 SWE-bench / Tau2 같은 실증 벤치마크와 함께 인용하는 게 안전합니다.
