> 에이전틱 RAG를 *유한 수평 부분관측 마르코프 결정과정(finite-horizon POMDP)*으로 정형화하여, 파편화된 아키텍처·평가·안전성 논의를 하나의 의사결정 이론 틀로 통합한 SoK(Systematization of Knowledge) 논문.

**참고 자료**

- 원문 (arXiv abs): [arxiv.org/abs/2603.07379](https://arxiv.org/abs/2603.07379)
- HTML 버전: [arxiv.org/html/2603.07379v1](https://arxiv.org/html/2603.07379v1)

## 논문 선정 배경

실무에서 문서 QA·검색 파이프라인을 단순 RAG(retrieve→generate)에서 *반복 검색·검증·도구 호출이 결합된 에이전틱 RAG*로 확장하는 흐름이 늘고 있습니다. 실제로 2026년 들어 Agentic RAG가 엔터프라이즈 AI의 지배적 패턴으로 자리잡았다는 보고가 잇따르지만(Gartner: 기업 67%가 agentic 문서 처리 평가 중), 막상 "무엇을 에이전틱 RAG라 부를 것인가", "어떻게 평가할 것인가", "어떤 고유 리스크가 있는가"에 대한 공통 언어가 없는 상황입니다.

이 논문은 개별 시스템(ReAct, Self-RAG, Search-R 계열 등)을 나열하는 데 그치지 않고, 에이전틱 RAG 전체를 **순차적 의사결정 시스템(sequential decision-making system)**으로 보고 POMDP로 형식화합니다. 파이프라인 설계 시 "메모리·검색·도구 호출을 정책(policy)과 상태(state) 관점에서 어떻게 배치할 것인가"를 판단하는 데 직접 참조할 수 있는 이론적 토대라 판단해 선정했습니다.

## 1. 문제 정의 — 왜 "통합 프레임워크"가 필요한가

![one-shot RAG에서 에이전틱 RAG로의 진화](https://arxiv.org/html/2603.07379v1/diagrams/Introduction.png)
*그림 1 — 단발성(one-shot) RAG → 반복 검색 → 에이전틱 RAG로 이어지는 진화. 검색·추론·종료에 대한 명시적 다단계 제어로의 이행을 보여준다.*

RAG가 *자율 아키텍처*로 진화하면서 LLM이 다단계 추론·동적 메모리 관리·반복 검색 전략을 직접 조율하게 됐지만, 연구 지형은 다음 세 가지로 파편화되어 있다는 것이 저자들의 진단입니다.

- **파편화된 아키텍처(fragmented architectures)**: 시스템마다 플래닝·검색·메모리 구조가 제각각이라 비교 기준이 없음
- **일관성 없는 평가(inconsistent evaluation)**: 정적 정답 지표(accuracy, BLEU)로 반복 루프 시스템을 평가하는 한계
- **미해결 신뢰성 리스크(unresolved reliability risks)**: 자율 루프에서만 발생하는 고유 실패 양식이 체계화되지 않음

기존 RAG 서베이들이 컴포넌트 나열에 머문 데 반해, 이 논문은 "에이전틱 RAG를 *순차적 의사결정 시스템*으로 이해한 적이 없다"는 점을 근본 공백으로 지목하고 이를 메우려 합니다.

## 2. 방법론 — POMDP 정형화

![정적 RAG에서 POMDP 정형화로의 진화](https://arxiv.org/html/2603.07379v1/figures/rag_evolution.png)
*그림 2 — 정적 one-shot RAG 파이프라인에서 에이전틱 RAG의 POMDP 정형화로의 아키텍처 진화. 선형 생성 파이프라인이 지속 메모리 상태를 관리하는 순환 제어 정책으로 바뀐다.*

핵심 기여는 에이전틱 검색-생성 루프를 **유한 수평 부분관측 마르코프 결정과정(finite-horizon POMDP)**으로 정의한 것입니다. 시스템을 다음 튜플로 표현합니다.

$$\mathcal{S}_{ARAG} = \langle\mathcal{S}_{env}, \mathcal{A}, \Omega, \mathcal{O}, \pi_\theta, \mathcal{M}, \mathcal{T}\rangle$$

각 구성요소의 의미는 다음과 같습니다.

| 기호 | 구성요소 | 의미 |
|---|---|---|
| $$\mathcal{S}_{env}$$ | 환경 상태 | 코퍼스 $$\mathcal{C}$$ 안의 잠재 지식 상태 (직접 관측 불가) |
| $$\mathcal{A}$$ | 행동 공간 | $$\mathcal{A}_{ret} \cup \mathcal{A}_{reason} \cup \mathcal{A}_{tool} \cup \{STOP\}$$ — 검색·추론·도구·종료 |
| $$\Omega$$ | 관측 공간 | 검색된 텍스트 청크, 도구 출력 등 |
| $$\mathcal{O}(o_t \mid s_t,a_t)$$ | 관측 함수 | 상태·행동에 조건화된 관측을 반환 |
| $$\pi_\theta(a_t \mid \mathcal{M}_t)$$ | 제어 정책 | LLM으로 파라미터화된 확률적 정책 |
| $$\mathcal{M}_t$$ | 작업 메모리 | 믿음 상태(belief state) $$b_t$$ 를 근사 |
| $$\mathcal{T}(s_{t+1} \mid s_t,a_t)$$ | 상태 전이 함수 | 행동에 따른 상태 변화 |

**목적 함수**는 작업 보상을 최대화하되 단계별 비용을 정규화 항 $$\lambda$$ 로 억제합니다.

$$\max_{\pi_\theta} \mathbb{E}_{\tau \sim \pi_\theta}\left[R_{task}(y,y^*) - \lambda\sum_{t=0}^{T-1}C(a_t)\right]$$

이 정식화의 핵심 의도는 "검색을 *행동*으로, 메모리를 *믿음 상태*로, LLM을 *정책*으로" 사상(map)한다는 것입니다. 정적 RAG에서는 검색이 전처리 단계였지만, POMDP 관점에서는 매 스텝의 검색·추론·도구 호출이 모두 정책이 선택하는 행동이 되며, 비용-정확도 트레이드오프가 목적 함수에 명시적으로 들어옵니다.

논문은 에이전틱 RAG가 갖춰야 할 **필수 속성 4가지**도 정의합니다.

- **반복 제어(Iterative Control)**: 확률적 정책 $$\pi_\theta$$ 가 지배하는 피드백 루프
- **동적 검색(Dynamic Retrieval)**: 진화하는 $$\mathcal{M}_t$$ 에 조건화된 런타임 쿼리 생성
- **도구 매개 상호작용(Tool-Mediated Interaction)**: 검색기를 행동 공간 $$\mathcal{A}$$ 의 명시적 행동으로 취급
- **상태 지속성(State Persistence)**: 루프 반복 간 유지되는 에피소딕 작업 메모리

## 3. 분류 체계 (Taxonomy)

![에이전틱 RAG 4축 분류 체계](https://arxiv.org/html/2603.07379v1/figures/section4_taxonomy.png)
*그림 3 — 아키텍처·검색 전략·추론 패러다임·메모리/컨텍스트 관리 4개 축에 걸친 에이전틱 RAG 분류 체계. 직교하는 제어 흐름 결정이 결합해 고유 아키타입을 형성한다.*

2번에서 정의한 POMDP 튜플의 구성요소를 *실제 시스템을 분류하는 축*으로 풀어낸 것이 이 분류 체계입니다. 즉 아키텍처는 정책 $$\pi_\theta$$ 가 어떻게 분산되는가, 검색 전략은 행동 $$\mathcal{A}_{ret}$$ 가 몇 번·어떻게 호출되는가, 추론 패러다임은 정책이 행동을 선택하는 방식, 메모리는 믿음 상태 $$b_t$$ 를 무엇으로 근사하는가에 각각 대응합니다. 저자들이 4개 축을 고른 이유는 이 네 가지가 POMDP 튜플에서 *독립적으로 설계 결정이 갈리는* 지점이기 때문이며, 덕분에 임의의 에이전틱 RAG 시스템을 "(아키텍처, 검색, 추론, 메모리)" 좌표로 위치시킬 수 있게 됩니다.

**① 아키텍처(플래닝 토폴로지)**

| 유형 | 정의 | 특징 |
|---|---|---|
| Single-Agent RAG | 한 에이전트가 플래닝·생성 모두 수행 | 단일 제어 정책, 직접 도구 호출 |
| Planner–Executor | 플래닝/실행 역할 분리 | 역할 간 명시적 인터페이스, 위임 기반 |
| Multi-Agent RAG | 여러 에이전트에 의사결정 분산 | 독립 에이전트 + 협응(coordination) 메커니즘 |

**② 검색 전략**

| 전략 | 정의 | 패턴 |
|---|---|---|
| One-Shot Retrieval | 단일 검색 후 생성 | 베이스라인 RAG, 고정 컨텍스트 |
| Iterative Retrieval | 중간 상태에 의존한 반복 검색 | 이전 결과에 조건화된 후속 쿼리 |
| Self-Refining Retrieval | 검색 + 비평·수정 결합 | 피드백 루프로 쿼리/근거 정제 |

**③ 추론 패러다임**

| 접근 | 메커니즘 |
|---|---|
| Chain-of-Thought & ReAct | 추론 트레이스 + 도구 호출 인터리빙 |
| Reflection-Based | 과거 실패의 에피소딕 메모리로 자기 평가·궤적 비평 |
| Tree-Based Exploration | 다중 후보 분기 + 백트래킹 탐색 |

**④ 메모리·컨텍스트 패러다임** (3계층)

- **단기 메모리**: 진화하는 컨텍스트 윈도우(스크래치패드)
- **에피소딕 메모리**: 행동·피드백의 유한 궤적
- **지속적 장기 메모리**: 벡터 DB 기반 세션 간 정보 보존
- 메커니즘: 동적 컨텍스트 프루닝, 메모리 갱신 전략, 학습형 메모리 컨트롤러

네 축은 서로 직교한다기보다 *결합*되어 하나의 시스템 프로파일을 만듭니다. 예컨대 Self-RAG 계열은 (Single-Agent, Self-Refining, Reflection-Based, 에피소딕) 조합에, 멀티에이전트 검색 루프는 (Multi-Agent, Iterative, ReAct, 장기 메모리) 조합에 가깝습니다. 이 좌표화의 실무적 가치는 "내 파이프라인이 어느 칸에 있는지"를 먼저 박아두면, 같은 칸의 알려진 실패 양식(6번 리스크)과 평가 방법(5번)을 그대로 참조할 수 있다는 점입니다. 단 저자도 8번에서 인정하듯 실제 시스템은 한 칸에 깔끔히 떨어지지 않고 여러 셀에 걸치는 경우가 많아, 분류는 *진단 도구*이지 배타적 범주가 아니라는 점에 유의해야 합니다.

## 4. 설계 패턴 7종

![설계 패턴 제어 흐름 맵](https://arxiv.org/html/2603.07379v1/diagrams/Section-6-top-to-bottom.png)
*그림 6 — 에이전틱 RAG 시스템이 명시적 결정을 통해 설계 패턴을 합성하는 제어 흐름 맵. 과제 분해·검색 시점·반복 정제·오케스트레이션에 걸쳐 선형 파이프라인이 순환 루프로 전환된다.*

3번의 분류가 *시스템을 묘사하는 좌표축*이라면, 7개 설계 패턴은 그 좌표 안에서 실무가 실제로 반복 채택해 온 *검증된 제어 흐름 레시피*입니다. 저자들이 굳이 패턴을 따로 떼어낸 의도는, 추상적 분류만으로는 "그래서 무엇을 만들어야 하나"가 안 나오기 때문 — 패턴은 분류와 구현 사이의 다리 역할을 합니다.

| 패턴 | 제어 흐름 | 적합 사례 |
|---|---|---|
| Plan-Then-Retrieve | 계획 → 단계별 검색 → 답 구성 | 근거를 미리 열거 가능한 멀티홉 QA |
| Retrieve-Reflect-Refine | 검색 → 초안 → 성찰 → 쿼리 정제 → 반복 | 출처가 붙는 장문 생성, 오픈도메인 QA |
| Decomposition-Based | 추론 → 검색 정식화 → 관측 반영 → 반복 | 적응적 탐색, 조사형 태스크 |
| Tool-Augmented Loop | 도구 선택 → 호출 → 상태 갱신 → 루프 | 다양한 도구가 필요한 복합 도메인 |
| Multi-Agent Collaboration | 병렬/순차 에이전트 실행 → 합의 집계 | 분산 지식 작업 |
| Retrieval-Grounded Verification | 제안 → 검색 대조 검증 → 피드백 교정 | 고위험 출처 기반 생성 |
| Human-As-A-Tool (HITL) | 실행 → 에스컬레이션 게이트 → 인간 승인 → 재개 | 안전 핵심 워크플로 |

표를 읽는 핵심은 패턴들이 *비용·신뢰성 축에서 점증*한다는 점입니다. 위에서 아래로 갈수록(Plan-Then-Retrieve → … → HITL) 루프의 자율성과 검증 강도가 올라가는 대신 토큰·지연 비용이 커집니다. 따라서 패턴 선택은 곧 2번 목적 함수의 비용 항 $$\lambda$$ 를 얼마나 크게 잡느냐의 문제로 환원됩니다. 저위험 멀티홉 QA라면 상단의 가벼운 패턴으로 충분하고, 고위험 출처 기반 생성·규제 도메인이라면 Retrieval-Grounded Verification이나 HITL처럼 검증 게이트가 박힌 하단 패턴이 필요합니다.

![PPAR 폐루프와 HITL 에스컬레이션](https://arxiv.org/html/2603.07379v1/diagrams/PPAR_Verification_Loop_with_HITL.png)
*그림 5 — Perception–Planning–Action–Reflection(PPAR) 폐루프와 HITL 에스컬레이션. 해결 불가 실패에 대한 검증 루프·에스컬레이션 경로의 구조적 필요성을 보여준다.*

## 5. 평가 — 3계층 파이프라인

평가를 3계층으로 나눈 *이유*가 이 섹션의 핵심입니다. 정적 RAG는 입력→출력이 한 번이라 최종 답만 채점하면 됐지만, 에이전틱 RAG는 매 스텝이 정책의 행동이므로 *최종 답이 맞아도 중간 궤적이 엉터리*일 수 있고, 반대로 궤적은 합리적인데 비용이 폭발할 수 있습니다. 단일 지표로는 이 다층적 실패를 잡지 못하기 때문에, 컴포넌트→궤적→시스템으로 확대되는 세 렌즈가 필요합니다.

- **Layer 1 — 컴포넌트 수준**: 모듈별 정확성(검색 정밀도, 추론 일관성), 스텝별 입출력 검증
- **Layer 2 — 궤적(trajectory) 수준**: 다단계 추론 일관성, 행동 간 논리 의존성, 인용 충실도·귀속 체인
- **Layer 3 — 시스템 수준**: 엔드투엔드 성능(답 품질), 비용-지연 트레이드오프, 적대적 교란에 대한 강건성

세 계층은 2번 POMDP와도 맞물립니다. Layer 1은 개별 관측 함수 $$\mathcal{O}$$·행동의 정확성, Layer 2는 정책이 생성한 *궤적* $$\tau$$ *전체*의 논리 일관성, Layer 3은 목적 함수(보상 − 비용)의 최종 값을 보는 셈입니다. 특히 Layer 2(궤적 수준)가 기존 RAG 평가에 없던 새 기여인데, 인용 충실도·행동 간 논리 의존성처럼 "답은 맞아도 *어떻게* 도달했는가"를 보는 지표가 여기 들어갑니다.

> 핵심 갭: accuracy·BLEU 같은 정적 정답 지표는 반복 시스템에 불충분하며, *궤적 수준*과 *조합성(compositionality)* 평가가 필요하다.

## 6. 5대 시스템 리스크

자율 루프에서만 증폭되는 고유 실패 양식을 5가지로 정리합니다. 이 부분이 보안·신뢰성 관점에서 가장 실무 가치가 큽니다. 다섯 리스크의 공통 원리는 *피드백 루프가 오류를 소멸시키는 게 아니라 증폭시킨다*는 데 있습니다 — 정적 RAG라면 한 번의 검색 실패로 끝날 일이, 에이전틱 RAG에서는 그 실패가 메모리에 적재돼 다음 스텝의 입력이 되고, 다시 더 나쁜 행동을 유발하는 식으로 전파됩니다.

- **검색 드리프트·쿼리 오정렬**: 초기 임베딩이 질의를 엉뚱한 문서로 매핑, "lost in the middle"로 노이즈 컨텍스트에서 추론 열화, 실패 시 적응적 보정 부재
- **검색에도 불구한 환각**: 근거 부족 시 파라메트릭 메모리로 환각, 검색-생성 단계 격리로 궤적 중간 교정 불가, 초기 실패가 다단계 루프로 전파
- **도구 오용·연쇄 오류**: 잘못된 도구 호출이 스텝 간 누적, 잘못된 API 호출이 하류 관측 오염, 샌드박싱 부재로 실패 무제한 전파
- **반복 검색에서의 프롬프트 인젝션**: 검색 결과 속 적대적 문서가 후속 추론 조작, 다단계 루프가 인젝션 표면적을 증폭, 메모리 포이즈닝으로 에피소딕 버퍼 오염
- **메모리 포이즈닝·리스크 증폭**: 오염된 에피소딕 메모리가 향후 플래닝 열화 → "나쁜 메모리 → 나쁜 검색 → 더 나쁜 메모리"의 피드백 폐루프

주목할 점은 이 5가지가 독립적이지 않고 *연쇄*한다는 것입니다. 검색 드리프트가 잘못된 문서를 끌어오고(①) → 그 문서에 환각이 더해지며(②) → 잘못된 도구 호출로 이어지고(③) → 그 결과가 적대적 컨텍스트를 주입하며(④) → 종국엔 메모리를 오염시켜 폐루프를 완성(⑤)하는 식입니다. 따라서 방어도 단일 지점이 아니라 루프 전체에 걸쳐(샌드박싱·궤적 모니터링·메모리 검증·HITL 게이트) 다층으로 설계해야 한다는 것이 실무적 함의입니다.

## 7. 향후 연구 방향

향후 과제 5가지는 모두 앞 섹션에서 *드러난 공백을 메우는* 방향으로 정렬됩니다 — 5번(평가)·6번(리스크)에서 "문제는 정의했으나 해법은 아직"이라고 남긴 지점들이 그대로 연구 어젠다가 됩니다.

- **플래닝 루프 하 안정적 적응 검색**: 무한 루프 방지, 비용 폭발을 막는 예산 인식(budget-aware) 오케스트레이션
- **에이전틱 추론 품질의 형식적 평가**: 정답 정확도를 넘는 궤적 수준 지표, 조합성·논리 일관성 벤치마크
- **메모리 강건성·포이즈닝 저항**: 오염 전파 차단 격리 메커니즘, 메모리 신선도·일관성 검증
- **비용 인식 자율 오케스트레이션**: 토큰/지연/정확도 트레이드오프를 최적화하는 학습형 정책, 동적 예산 배분
- **신뢰 보정·감독 메커니즘**: 자율-안전 균형을 위한 HITL 에스컬레이션 정책, 자율 트리거 환각을 막는 검증 게이트

## 8. 한계 및 비판적 검토

- **저자가 인정한 한계**: 전통적 *정적* 평가 관행이 자율 시스템에 부적합하다는 점을 핵심 갭으로 명시하나, 제안한 3계층 평가 파이프라인은 *개념적 틀* 수준이며 구체적 지표·벤치마크 구현체나 정량 실험 검증은 제시하지 않음.
- **리뷰어 관점의 약점**: SoK 특성상 새로운 실험·SOTA 수치가 없어 "최초의 통합 프레임워크"라는 기여는 실증보다 *정리·형식화*의 가치에 의존. POMDP 사상은 우아하지만, 실제 LLM 정책이 마르코프 가정·유한 수평 가정을 어느 정도 만족하는지에 대한 경험적 근거는 부족.
- **검증되지 않은 가정**: 작업 메모리 $$\mathcal{M}_t$$ 가 믿음 상태 $$b_t$$ 를 "근사한다"는 전제가 핵심인데, 그 근사 품질·오차 한계는 다루지 않음. 목적 함수의 비용 항 $$\lambda$$ 도 형식적으로만 도입되고 실측 캘리브레이션은 없음.
- **남은 질문**: 분류 체계(아키텍처·검색·추론·메모리)의 축들이 상호 직교적인지, 실제 시스템이 여러 셀에 걸칠 때의 매핑 모호성은 어떻게 해소할지가 열려 있음.

## 시사점

**① (설계 관점)** 에이전틱 RAG 파이프라인을 "검색=행동, 메모리=믿음 상태, LLM=정책"으로 환원해 보면, 실제 과제에서 어디에 *반복 제어*와 *예산 제약*을 넣어야 할지 판단 기준이 생깁니다. 7개 설계 패턴은 PoC 단계에서 아키텍처 후보를 빠르게 좁히는 체크리스트로 쓸 수 있습니다.

**② (안전·운영 관점)** 5대 리스크(특히 메모리 포이즈닝·반복 검색 프롬프트 인젝션)는 단순 RAG에는 없던 *루프 고유* 위협입니다. 프로덕션 배포 전 샌드박싱·HITL 에스컬레이션·궤적 수준 모니터링을 설계 초기에 반영해야 한다는 근거 자료로 활용 가능합니다.

## 정리

- 에이전틱 RAG를 *유한 수평 POMDP*로 정형화 — 검색/추론/도구 호출을 정책이 선택하는 행동으로, 메모리를 믿음 상태로 사상한 최초의 통합 이론 틀.
- 4축 분류(아키텍처·검색·추론·메모리) + 7개 설계 패턴 + 3계층 평가 + 5대 리스크로 파편화된 논의를 한 체계로 묶음.
- 가장 실무적인 기여는 *루프 고유 리스크*의 체계화와 *궤적 수준 평가*의 필요성 제기.
- 한계: 정량 실험·구현체 없는 개념적 정형화 — POMDP 가정의 경험적 타당성과 평가 지표 구현은 후속 과제로 남김.
