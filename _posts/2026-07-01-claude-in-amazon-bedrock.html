Claude 모델 개요

🎬 영상

Claude에는 서로 다른 우선순위에 맞춰 최적화된 세 가지 핵심 모델 계열인 Opus, Sonnet, Haiku가 있으며, 여기에 Claude Opus보다 상위 티어인 새 모델 Claude Fable 5가 더해집니다. 이 모델들은 모두 Claude의 핵심 기능을 공유하며 텍스트 생성, 코딩, 이미지 분석 등 다양한 작업을 처리할 수 있습니다. 핵심적인 차이는 지능, 속도, 비용 사이의 균형을 어떻게 맞추느냐에 있습니다.

Claude Fable 5

Claude Fable 5는 현재까지 가장 강력한 모델입니다. Claude Opus보다 상위에 위치하는 새로운 모델 티어로, 가장 까다로운 과제를 위해 만들어졌습니다. Anthropic은 2026년 6월에 이 새 모델 계열을 출시했습니다 — 자세한 내용은 출시 공지에서 확인할 수 있습니다.

Fable 5는 핵심 모델 계열을 대체하는 것도 아니고, 대부분의 작업에서 기본 선택지가 되는 것도 아닙니다. Opus보다 비용이 훨씬 높기 때문에, 그 추가 성능에 비용을 지불할 가치가 있는 작업에만 쓰는 것이 좋습니다.

Amazon Bedrock에서 Fable 5는 model ID anthropic.claude-fable-5로 사용할 수 있습니다.

Claude Opus

Opus는 Claude의 세 핵심 모델 계열 중 가장 강력한 모델입니다. 정교한 추론과 계획 능력이 필요한 복잡한 상황을 위해 설계되었습니다.

Opus는 복잡한 프로젝트를 장시간에 걸쳐 독립적으로 수행하는 데 뛰어납니다. 사람의 개입 없이도 여러 단계로 이루어진 프로세스를 관리하고 다양한 요구사항을 처리할 수 있습니다. 이 모델은 reasoning을 지원하므로, 간단한 작업에는 빠르게 답하고 더 복잡한 문제에는 시간을 들여 깊이 생각할 수 있습니다.

대신 지연 시간이 다소 있고 비용이 높다는 단점이 있습니다. 더 높은 지능을 얻는 대가로 비용을 더 내고 더 오래 기다리게 됩니다.

Claude Sonnet

Sonnet은 Claude 라인업에서 최적의 균형점에 위치하며, 대부분의 실무 애플리케이션에 잘 맞는 지능, 속도, 비용의 균형을 제공합니다.

Sonnet이 특히 유용한 이유는 강력한 코딩 능력과 빠른 텍스트 생성을 겸비했기 때문입니다. 많은 개발자가 기존 기능을 망가뜨리지 않으면서 복잡한 코드베이스를 정밀하게 수정하는 능력을 높이 평가합니다.

Claude Haiku

Haiku는 Claude에서 가장 빠른 모델로, 응답 시간이 중요한 애플리케이션을 위해 특별히 만들어졌습니다. 최대 지능보다는 속도와 비용 효율에 최적화되어 있습니다.

한 가지 중요한 제약이 있습니다. Haiku는 Opus와 Sonnet이 제공하는 reasoning 기능을 지원하지 않습니다. 그래서 실시간 상호작용이 필요한 사용자 대면 애플리케이션에는 이상적이지만, 복잡한 문제 해결 작업에는 덜 적합합니다.

적합한 모델 고르기

모델 선택은 결국 지능과 비용/속도 사이의 트레이드오프를 이해하는 문제입니다. 다음 기준으로 결정하세요:

  • 가장 까다로운 과제에는 Fable 5를 선택하세요. Opus가 감당할 수 있는 수준을 넘어서고 그 결과가 높은 비용을 정당화한다면, Fable 5가 사용 가능한 가장 강력한 선택지입니다.
  • 강력한 reasoning 능력이 필요한 복잡한 작업에는 Opus를 선택하세요. 핵심 계열 중에서 속도와 비용보다 품질을 택하는 것입니다.
  • 속도가 가장 중요할 때는 Haiku를 선택하세요. 실시간 사용자 상호작용이나 가장 빠른 응답이 필요한 대량 처리에 적합합니다.
  • 균형이 필요할 때는 Sonnet을 선택하세요. 대부분의 애플리케이션은 지능, 속도, 합리적 비용을 겸비한 Sonnet의 조합에서 이점을 얻습니다.

여러 모델 함께 쓰기

많은 팀이 하나의 모델만 고집하지 않습니다. 대신 같은 애플리케이션 안에서도 부분별로 서로 다른 모델을 사용합니다:

  • 속도가 중요한 사용자 대면 상호작용에는 Haiku
  • 핵심 비즈니스 로직에는 Sonnet
  • 더 깊은 reasoning이 필요한 복잡한 작업에는 Opus
  • 추가 성능이 비용을 정당화하는 가장 어려운 문제에는, 선택적으로 Fable 5

이렇게 하면 전체 비용과 성능을 관리하면서도 애플리케이션의 각 부분을 요구사항에 맞게 최적화할 수 있습니다.

API에 접근하기

🎬 영상

AI 모델로 애플리케이션을 만들려면 사용자 입력에서 AI가 생성한 응답까지 데이터가 흐르는 과정을 이해해야 합니다. AWS Bedrock에서 이 과정이 어떻게 동작하는지, 일반적인 채팅 애플리케이션의 이면에서 무슨 일이 일어나는지 살펴보겠습니다.

채팅 애플리케이션의 동작 방식

간단한 채팅 인터페이스를 가진 웹 앱을 만든다고 상상해 보세요. 사용자가 "Define quantum computing"이라고 입력하고 전송을 누릅니다. 그러면 실제로는 다음과 같은 일이 벌어집니다:

사용자에게는 깔끔한 인터페이스만 보이지만, 그 응답을 만들어내기 위해 이면에서는 하나의 완전한 시스템이 작동하고 있습니다.

요청의 흐름

사용자가 텍스트를 전송하면, 그 메시지는 다음과 같은 여정을 거칩니다:

  • 사용자가 웹 인터페이스를 통해 메시지를 전송합니다
  • 서버가 그 텍스트를 담은 요청을 받습니다
  • 서버가 Bedrock client를 사용해 AWS Bedrock에 요청을 보냅니다
  • 요청에는 사용자 메시지와 model ID(예: Claude Haiku, Claude Sonnet)가 포함됩니다
  • 선택된 모델이 요청을 처리하고 텍스트를 생성합니다
  • AWS Bedrock이 생성된 응답을 담은 assistant 메시지를 돌려줍니다
  • 서버가 이 응답을 다시 사용자의 브라우저로 전달합니다

첫 요청 보내기

🎬 영상

AWS Bedrock에 첫 API 요청을 보내려면 세 가지 필수 구성 요소가 필요합니다. 서비스에 연결하는 Bedrock Runtime Client, 실행할 모델을 지정하는 model ID, 그리고 모델에 입력할 텍스트를 담은 사용자 메시지입니다.

Bedrock client 설정하기

먼저 boto3를 사용해 Bedrock runtime 서비스에 연결하는 client를 생성합니다:

import boto3

client = boto3.client("bedrock-runtime", region_name="us-west-2")

model ID와 리전별 제공 여부 이해하기

여기서부터 조금 까다로워집니다. 모든 모델이 모든 AWS 리전에서 제공되는 것은 아닙니다. 선택한 리전에 존재하지 않는 모델을 실행하려고 하면, 모델이 존재하지 않는다는 알기 어려운 오류 메시지가 나타납니다.

예를 들어 Claude Sonnet이 us-west-2에서는 제공되지만 us-east-1에서 요청을 보낸다면, 그 요청은 실패합니다.

inference profile 사용하기

inference profile은 선택한 모델이 실제로 호스팅된 리전으로 요청을 자동으로 라우팅해 주어 리전별 제공 문제를 해결합니다.

어떤 모델이 어떤 리전에 있는지 일일이 추적하는 대신, 해당 모델이 us-west-2, us-east-2 같은 여러 리전에서 제공된다는 것을 이미 알고 있는 inference profile을 사용할 수 있습니다.

inference profile을 사용해 요청을 보내면, 다른 리전에서 연결하더라도 AWS가 모델이 존재하는 올바른 리전으로 자동으로 라우팅합니다.

inference profile ID를 찾으려면 메인 모델 카탈로그 페이지의 model ID를 쓰는 대신, AWS Bedrock 콘솔의 "Cross-region inference" 항목을 확인하세요.

선택한 모델의 inference profile ID를 복사하세요.

사용자 메시지 만들기

사용자 메시지는 처음 보면 지나치게 복잡해 보일 수 있는 특정한 구조를 가지고 있는데, 여기에는 그럴 만한 이유가 있습니다:

user_message = {
"role": "user",
"content": [
{"text": "What's 1+1?"}
]
}

content가 리스트인 이유는 하나의 메시지에 텍스트, 이미지 등 서로 다른 유형의 콘텐츠가 담길 수 있기 때문입니다. 이 구조 덕분에 멀티모달 요청을 보낼 수 있습니다.

요청 보내기

이제 converse 메서드를 사용해 API를 호출할 수 있습니다:

response = client.converse(
modelId=model_id,
messages=[user_message]
)

응답에는 많은 메타데이터가 들어 있지만, 생성된 텍스트만 얻으려면 응답 구조를 따라 들어가야 합니다:

response["output"]["message"]["content"][0]["text"]

메시지 유형 이해하기

다루게 될 주요 메시지 유형은 두 가지입니다:

  • 사용자 메시지 — 모델에 입력하려는 콘텐츠 (role: "user")
  • assistant 메시지 — 모델이 생성한 콘텐츠 (role: "assistant")

두 메시지 유형 모두 role과 content 리스트로 이루어진 동일한 구조를 따릅니다. 이 일관성 덕분에 사용자 메시지와 assistant 메시지를 번갈아 배치하며 대화를 손쉽게 구성할 수 있습니다.

Bedrock에서 돌려받는 assistant 메시지는 role만 다를 뿐 사용자 메시지와 완전히 같은 형식을 따릅니다. 이렇게 표준화된 구조 덕분에 여러 요청을 이어 붙여 긴 대화를 만드는 일이 간단해집니다.

멀티턴 대화

🎬 영상

지금까지 작성한 코드는 Claude와의 아주 단순한 주고받기를 흉내 낸 것입니다. 그런데 대화를 이어가고 싶다면 어떻게 될까요? "What's 1+1?"이라고 물은 뒤 "And 3 more?"처럼 후속 질문을 하면, Claude가 앞선 결과인 2에 3을 더하는 것을 묻는다고 이해하기를 기대할 수 있습니다.

하지만 Bedrock API와 Claude 자체에 대해 반드시 알아야 할 중요한 점이 있습니다.

메시지는 저장되지 않는다

Bedrock과 Claude는 어떤 메시지도 저장하지 않습니다. 여러분이 보내는 메시지도, 돌려받는 응답도 저장되지 않습니다. 각 API 호출은 완전히 독립적입니다.

맥락을 유지하는 여러 메시지로 대화를 이어가려면 다음을 해야 합니다:

  • 코드에서 모든 메시지의 리스트를 직접 관리하기
  • 후속 요청마다 그 전체 메시지 리스트를 함께 전달하기

맥락이 중요한 이유

적절한 맥락 없이 어떤 일이 벌어지는지 살펴봅시다. "And 3 more?"만 단독 메시지로 보내면 Claude는 무엇을 가리키는지 전혀 알 수 없습니다. 최선을 다해 답하려 하겠지만, 이전 대화의 맥락이 없기 때문에 그 답은 말이 되지 않습니다.

후속 질문만 보내면 Claude는 그 고립된 메시지만 보게 되고, 앞선 "What's 1+1?" 주고받기를 모른 채 답하려 합니다.

대화 맥락 구성하기

맥락을 유지하려면 각 요청에 전체 대화 기록을 포함해야 합니다. 방식은 다음과 같습니다:

메시지 리스트에는 이전의 모든 주고받기, 즉 사용자 메시지와 assistant 응답이 모두 담겨야 합니다. 이렇게 완전한 맥락을 보내면 Claude는 "And 3 more?"가 앞선 결과인 2에 3을 더하는 것을 의미한다고 이해할 수 있습니다.

메시지 관리를 위한 헬퍼 함수

대화 관리를 더 쉽게 하기 위해 헬퍼 함수를 만들 수 있습니다:

def add_user_message(messages, text):
user_message = {
"role": "user",
"content": [
{"text": text}
]
}
messages.append(user_message)

def add_assistant_message(messages, text):
assistant_message = {
"role": "assistant", 
"content": [
{"text": text}
]
}
messages.append(assistant_message)

def chat(messages):
response = client.converse(
modelId=model_id,
messages=messages
)
return response["output"]["message"]["content"][0]["text"]

멀티턴 대화 구현하기

대화를 단계별로 구성하는 방법은 다음과 같습니다:

# Make a starting list of messages
messages = []

# Add in the initial user question of "What's 1+1?"
add_user_message(messages, "What's 1+1?")

# Pass the list of messages into chat to get an answer
answer = chat(messages)

# Take the answer and add it as an assistant message into our list
add_assistant_message(messages, answer)

# Add in the user's followup question
add_user_message(messages, "And 3 more added to that?")

# Call chat again with the list of messages to get a final answer
answer = chat(messages)
print(answer)

이 방식은 Claude가 전체 맥락을 갖고 적절히 답할 수 있게 해줍니다: "Starting with the result of 1+1 = 2, if we add 3 more to that, we get: 2 + 3 = 5"

메시지 역할 번갈아 배치하기

메시지 리스트를 구성할 때는 메시지 role이 항상 올바르게 번갈아 나오도록 해야 합니다:

대화는 user → assistant → user → assistant 패턴을 따라야 합니다. 사용자 메시지가 연달아 두 번 나오거나 assistant 메시지가 연달아 두 번 나와서는 안 됩니다. 이렇게 번갈아 나오는 패턴은 API가 요구하는 것이며, 자연스러운 대화 흐름을 반영합니다.

이렇게 메시지를 직접 관리하는 일이 처음에는 번거로워 보일 수 있지만 금세 익숙해집니다. 이 패턴은 Claude와 대화 맥락을 유지해야 하는 모든 애플리케이션을 만드는 데 기본이 됩니다.

시스템 프롬프트

🎬 영상

특정 용도의 AI 챗봇을 만들 때는 AI가 어떻게 응답할지 제어할 방법이 필요합니다. 시스템 프롬프트는 범용 AI를 특정 지침을 따르고 주제에서 벗어나지 않는 전문화된 어시스턴트로 바꿔주는 핵심입니다.

사용자 메시지 수준 지시의 문제점

모든 요구사항을 사용자 메시지 안에 넣는 것이 해결책이라고 생각할 수도 있습니다. 예를 들어 대화마다 AI에게 "AWS 서비스를 언급하라", "경쟁사를 언급하지 말라"고 지시하는 식입니다. 이 방식에는 심각한 한계가 있습니다:

  • 가능한 모든 질문과 예외 상황을 미리 예상해야 합니다
  • 지시 목록이 다루기 힘들 만큼 길고 반복적이 됩니다
  • 사용자에게 모든 내부 지시가 노출되어 대화가 지저분해집니다
  • 요구사항이 질문에 따라 달라집니다

더 나은 방법: 시스템 프롬프트

시스템 프롬프트는 Claude에게 맡을 역할을 부여함으로써 이 문제를 해결합니다. 구체적인 해야 할 일과 하지 말아야 할 일을 나열하는 대신, Claude에게 특정 유형의 전문가처럼 행동하라고 지시합니다. 그러면 AI는 그 사람이 자연스럽게 응답할 법한 방식으로 답합니다.

시스템 프롬프트는 몇 가지 핵심 이점을 제공합니다:

  • Claude가 일관되게 응답하는 방법에 대한 지침을 얻습니다
  • AI가 지정된 역할의 사고방식과 제약을 받아들입니다
  • 응답이 자동으로 주제에 집중되고 브랜드에 부합합니다
  • 가능한 모든 시나리오를 미리 예상할 필요가 없습니다

시스템 프롬프트 구현하기

Claude 대화에 시스템 프롬프트를 추가하려면 converse 함수에 파라미터로 전달합니다:

system_prompt = """
You are an AWS cloud support specialist. Your job is to answer user queries related 
to cloud hosting services on AWS.
"""

response = client.converse(
modelId=model_id, 
messages=messages, 
system=[{"text": system_prompt}]
)

시스템 프롬프트는 "text" 키를 가진 딕셔너리를 담은 리스트 형태로 전달됩니다. 이는 Claude가 사용자 메시지를 보기 전에 어떤 역할을 맡을지 알려줍니다.

유연한 chat 함수 만들기

시스템 프롬프트를 깔끔하게 처리하는 재사용 가능한 chat 함수는 다음과 같습니다:

def chat(messages, system=None):
params = {"modelId": model_id, "messages": messages}

if system:
params["system"] = [{"text": system}]

response = client.converse(**params)

return response["output"]["message"]["content"][0]["text"]

이 방식을 쓰면 시스템 프롬프트를 선택적으로 포함할 수 있습니다. 시스템 프롬프트를 제공하지 않으면 Claude는 기본 상태로 응답하고, 포함하면 그 특정 역할을 맡습니다.

시스템 프롬프트의 실제 효과

같은 질문을 시스템 프롬프트 없이, 그리고 있는 상태로 각각 테스트해 보면 차이가 즉시 드러납니다. 시스템 프롬프트 없이 "How do I host a Postgres database?"라고 물으면, 여러 클라우드 제공업체와 자체 호스팅 방법까지 아우르는 포괄적인 답변을 받게 됩니다.

AWS 지원 전문가 시스템 프롬프트를 적용하면, 응답은 RDS, Aurora, EC2 기반 배포 같은 AWS 솔루션에만 집중됩니다. 경쟁사는 언급되지 않으며, 답변에는 AWS에 특화된 설정 단계가 포함됩니다.

더 인상적인 것은 시스템 프롬프트가 주제를 벗어난 질문을 다루는 방식입니다. AWS 전문가 프롬프트가 활성화된 상태에서 빵 레시피를 요청하면, Claude는 역할을 유지한 채 정중하게 거절합니다:

중요한 기술적 세부사항

시스템 프롬프트를 다룰 때는 다음 요건을 유념하세요:

  • 시스템 프롬프트는 빈 문자열일 수 없으며, 최소 한 글자 이상을 포함해야 합니다
  • system 파라미터는 "text" 키를 가진 딕셔너리의 리스트를 기대합니다
  • 시스템 프롬프트는 대화 내 어떤 사용자 메시지보다 먼저 처리됩니다
  • 시스템 프롬프트는 대화와 대화 사이에는 갱신할 수 있지만, 대화 도중에는 바꿀 수 없습니다

시스템 프롬프트는 복잡한 규칙 시스템 없이도 AI 동작을 강력하게 제어할 수 있게 해줍니다. Claude에게 특정 전문가 역할을 부여하면, 그 역할의 제약과 전문성을 자연스럽게 따르는 일관되고 적절한 응답을 얻을 수 있습니다.

Temperature

🎬 영상

temperature는 Claude의 응답이 얼마나 창의적일지 또는 결정론적일지를 제어하는 강력한 파라미터입니다. 이를 효과적으로 사용하는 법을 이해하면 AI 애플리케이션을 크게 개선할 수 있습니다.

Claude가 텍스트를 생성하는 방식

temperature를 살펴보기 전에 Claude의 텍스트 생성 과정을 이해하면 도움이 됩니다. "What do you think?" 같은 프롬프트를 Claude에 보내면, 세 단계를 거칩니다:

  • tokenization: 입력을 더 작은 조각으로 나눔
  • prediction: 다음에 올 수 있는 토큰들의 확률을 계산함
  • sampling: 그 확률을 바탕으로 하나의 토큰을 선택함

위 도식에서 Claude가 다음에 올 수 있는 토큰들에 서로 다른 확률을 어떻게 부여하는지 볼 수 있습니다. "about"이라는 단어는 30%, "would"는 20% 같은 식입니다. 이 과정은 응답이 완성될 때까지 토큰마다 반복됩니다.

temperature가 하는 일

temperature는 0과 1 사이의 소수값으로, 이 토큰 선택 확률에 직접 영향을 줍니다. 창의성 다이얼이라고 생각하면 됩니다:

  • 낮은 temperature(0에 가까움): 가장 확률이 높은 토큰이 선택될 가능성을 훨씬 더 높입니다
  • 높은 temperature(1에 가까움): 가능한 모든 토큰에 확률을 더 고르게 분산시킵니다

temperature가 0이면 Claude는 결정론적이 되어 항상 가장 확률이 높은 토큰을 선택합니다. temperature가 1이면 확률이 낮은 토큰도 선택될 가능성이 훨씬 커지고, 그 결과 더 창의적이고 다양한 출력이 나옵니다.

temperature 범위와 활용 사례

작업마다 서로 다른 temperature 설정이 필요합니다:

낮은 temperature (0.0 - 0.3)

  • 사실 기반 응답
  • 코딩 지원
  • 데이터 추출
  • 콘텐츠 모더레이션

중간 temperature (0.4 - 0.7)

  • 요약
  • 교육용 콘텐츠
  • 문제 해결
  • 제약이 있는 창작

높은 temperature (0.8 - 1.0)

  • 브레인스토밍
  • 창작
  • 마케팅 콘텐츠
  • 농담 생성

코드에서 temperature 설정하기

기본적으로 Claude의 temperature는 1.0으로 설정되어 있으며, 이는 창의성이 최대라는 뜻입니다. inference configuration에 temperature를 추가해 이 값을 덮어쓸 수 있습니다:

def chat(messages, system=None, temperature=1.0):
params = {
"modelId": model_id,
"messages": messages,
"inferenceConfig": {"temperature": temperature}
}

if system:
params["system"] = [{"text": system}]

response = client.converse(**params)
return response["output"]["message"]["content"][0]["text"]

실제 적용 예시

영화 아이디어 생성을 활용한 실제 예시를 보겠습니다. temperature를 기본값(1.0)으로 두면 다음과 같은 창의적인 응답을 받을 수 있습니다:

"은둔형 종이접기 장인이 자신의 정교한 종이 작품들이 밤이면 살아 움직인다는 사실을 알게 되고, 그들의 존재를 풀어헤쳐 없애려는 정체불명의 그림자 생명체로부터 이 작은 세계를 지키기 위한 마법 같은 여정에 나선다."

그러나 같은 프롬프트에 temperature를 0.0으로 설정하면, 매번 더 예측 가능한 응답을 일관되게 받게 됩니다:

"시간을 여행하는 고고학자가, 고대 유물들의 잊힌 힘을 이용해 종말 장치를 만들려는 IT 억만장자에게 그 유물들을 도둑맞지 않도록 막아야 한다."

낮은 temperature 버전을 여러 번 실행하면 매우 비슷한 응답이 나오며, "시간 여행 역사학자"나 "시간 여행 고고학자" 같은 주제가 반복되곤 합니다.

핵심 정리

temperature는 Claude의 창의성 수준을 직접 제어할 수 있게 해줍니다. 일관되고 사실적인 응답이 필요하면 낮은 temperature를, 창의적이고 다양한 출력을 원하면 높은 temperature를 사용하세요. 기본값 1.0은 창의성을 최대로 끌어올리므로, 정밀함과 일관성이 필요한 작업에서는 값을 낮추는 것을 고려하세요.

스트리밍

🎬 영상

AI 모델로 채팅 인터페이스를 만들 때, 사용자는 완전한 응답을 10~30초씩 기다리기보다 응답이 즉시 나타나기를 기대합니다. converse_stream 함수는 생성되는 대로 텍스트를 스트리밍해 이 문제를 해결하며, 훨씬 나은 사용자 경험을 만들어 줍니다.

스트리밍의 동작 방식

전체 응답이 다 생성될 때까지 기다리는 대신, 스트리밍은 텍스트 조각이 준비되는 즉시 돌려보냅니다. 흐름이 어떻게 달라지는지 살펴봅시다:

converse_stream을 호출하면, stream 객체를 담은 초기 응답을 즉시 돌려받습니다. 이 stream은 모델이 텍스트를 생성하는 동안 이벤트를 하나씩 내보내는 제너레이터입니다. 각 이벤트에는 전체 응답의 작은 조각이 담겨 있습니다.

기본 구현

코드에서 converse_stream을 사용하는 방법은 다음과 같습니다:

messages = []
add_user_message(messages, "Write a 1 sentence description of a fake database")
response = client.converse_stream(messages=messages, modelId=model_id)

for event in response["stream"]:
print(event)

이렇게 하면 도착하는 모든 이벤트가 출력됩니다. 응답이 한 번에 전부가 아니라 조각 단위로 들어오는 것을 볼 수 있습니다.

스트림 이벤트 이해하기

스트림은 각기 다른 목적을 가진 여러 유형의 이벤트를 내보냅니다:

기본적인 텍스트 생성에서는 contentBlockDelta 이벤트만 신경 쓰면 됩니다. 이 이벤트에는 사용자에게 표시하려는 실제 생성 텍스트 조각이 담겨 있습니다.

이벤트는 항상 예측 가능한 순서로 도착합니다. messageStart, 텍스트를 담은 여러 개의 contentBlockDelta 이벤트, 그다음 contentBlockStop, messageStop, 마지막으로 metadata 순입니다.

텍스트 추출하기

각 조각에서 생성된 텍스트만 얻으려면, contentBlockDelta 이벤트만 필터링해 텍스트를 추출합니다:

text = ""
for event in response["stream"]:
if "contentBlockDelta" in event:
chunk = event["contentBlockDelta"]["delta"]["text"]
print(chunk, end="")
text += chunk

print("\n\nTotal Message:\n" + text)

end="" 파라미터는 Python의 print 함수가 자동으로 추가하는 줄바꿈을 제거해, 스트리밍 텍스트가 더 자연스럽게 나타나도록 합니다.

실무 적용

실제 애플리케이션에서는 각 조각을 출력하는 대신 보통 다음과 같이 합니다:

  • WebSockets나 Server-Sent Events를 통해 각 조각을 프론트엔드로 전송하기
  • 점점 길어지는 응답을 실시간으로 표시하도록 UI 업데이트하기
  • 스트리밍이 끝나면 완성된 메시지를 저장하기
  • 스트리밍 도중 발생할 수 있는 오류 처리하기

이 스트리밍 방식은 사용자 경험을 "전송하고 기다리기"에서 "전송하고 응답이 나타나는 것을 지켜보기"로 바꿔주며, AI 기반 애플리케이션을 훨씬 더 반응성 있고 매력적으로 느껴지게 합니다.

모델 출력 제어

🎬 영상

더 나은 프롬프트를 작성하는 것 외에도, Claude의 출력을 제어하는 강력한 기법이 두 가지 있습니다. 바로 prefill된 assistant 메시지와 stop sequence입니다. 이 방법들은 Claude가 어떻게 응답하고 언제 텍스트 생성을 멈출지를 정밀하게 제어할 수 있게 해줍니다.

prefill된 assistant 메시지

메시지 prefilling은 Claude 응답의 첫머리를 여러분이 직접 제공하게 해주며, 이는 답변의 방향에 큰 영향을 줍니다. Claude가 응답을 어떻게 시작할지 스스로 정하게 두는 대신, 대화를 이끄는 특정 도입부를 지정하는 것입니다.

동작 방식은 이렇습니다. 사용자 질문이 담긴 평소의 메시지 리스트를 구성하되, 맨 끝에 원하는 응답의 첫머리를 담은 assistant 메시지를 추가합니다. Claude가 이를 처리할 때 그 assistant 메시지를 보고 "이 질문에 대한 응답을 이미 시작했으니, 멈춘 지점부터 이어서 써야겠다"라고 여깁니다.

예를 들어 "Is tea or coffee better at breakfast?"라고 묻고 "Coffee is better because"로 prefill하면, Claude는 그 지점부터 이어서 커피를 옹호하는 응답을 구성합니다. 핵심은 Claude가 prefill한 텍스트가 끝나는 바로 그 지점부터 이어간다는 점입니다. 여러분이 쓴 내용을 다시 반복하지 않습니다.

실제로 확인해 봅시다:

messages = []
add_user_message(messages, "Is coffee or tea better for breakfast?")
add_assistant_message(messages, "Coffee is better because")

chat(messages)

이렇게 하면 "it has more caffeine." 같은 응답이 돌아옵니다. Claude가 prefill한 텍스트에서 곧바로 이어가므로, 완전한 응답을 얻으려면 두 부분을 합쳐야 합니다: "Coffee is better because it has more caffeine."

prefill 텍스트를 바꾸면 Claude를 어느 방향으로든 이끌 수 있습니다:

  • "Tea is better because" — 차 쪽으로 유도
  • "They are the same because" — 중립적인 응답 유도

stop sequence

stop sequence는 Claude가 특정 텍스트를 생성하는 순간 응답을 즉시 끝내도록 강제합니다. 특정 지점에서 출력을 잘라내거나, Claude가 특정 표지 이후로 이어가지 못하게 막고 싶을 때 유용합니다.

개념은 단순합니다. 문자열 리스트를 제공하면, Claude가 그중 하나를 생성하는 즉시 멈추고 그때까지 생성한 내용을 반환합니다. stop sequence 자체는 응답에 포함되지 않습니다.

stop sequence를 사용하려면 chat 함수가 이를 파라미터로 받도록 수정해야 합니다:

def chat(messages, system=None, temperature=1.0, stop_sequences=[]):
params = {
"modelId": model_id,
"messages": messages,
"inferenceConfig": {
"temperature": temperature,
"stopSequences": stop_sequences
},
}

실제 예시는 다음과 같습니다:

messages = []
add_user_message(messages, "Count from 1 to 10")

chat(messages, stop_sequences=["5"])

이렇게 하면 "1, 2, 3, 4,"를 반환하고 "5"를 포함하기 전에 멈춥니다. 여러 개의 stop sequence를 지정할 수 있으며, Claude는 그중 가장 먼저 만나는 것에서 멈춥니다:

chat(messages, stop_sequences=["5", "3, 4"])

stop sequence는 특히 다음과 같은 경우에 유용합니다:

  • 응답 길이 제어하기
  • 구조화된 출력에서 자연스러운 구분점에 멈추기
  • Claude가 특정 표지나 구분자 이후로 이어가지 못하게 막기

두 기법 모두 Claude의 동작을 세밀하게 제어할 수 있게 해주며, 단순한 프롬프트만으로는 얻을 수 없는 방식으로 응답을 다듬을 수 있게 합니다.

구조화된 데이터

🎬 영상

Claude에게 JSON, Python 코드, 글머리 기호 목록 같은 구조화된 데이터를 생성하게 하려면 흔한 문제에 자주 부딪힙니다. Claude는 도움을 주려는 성향 때문에 콘텐츠 주위에 설명 텍스트, 헤더, 마크다운 서식을 덧붙이려 합니다. 순수한 데이터만 필요할 때는 이런 부가 설명이 사용자 경험을 해칩니다.

AWS EventBridge 규칙을 생성하는 웹 앱을 만든다고 생각해 봅시다. 사용자가 설명을 입력하고 생성 버튼을 누르면, 곧바로 복사해서 쓸 수 있는 깔끔한 JSON을 기대합니다. 그런데 Claude가 JSON을 설명 텍스트와 함께 마크다운 코드 블록으로 감싸서 반환하면, 사용자는 응답 전체를 그대로 복사할 수 없고 JSON 부분만 일일이 선택해야 합니다.

기본 응답의 문제점

기본적으로 Claude는 구조화된 출력을 다음과 같이 서식화하는 경향이 있습니다:

# EventBridge Rule

json { "source": ["aws.ec2"], "detail-type": ["EC2 Instance State-change Notification"], "detail": {"state": ["running"]} }

This rule captures EC2 instance state changes when instances start running or stop.

이는 문서용으로는 훌륭하지만, 프로그램에서 쓸 JSON만 필요할 때는 문제가 됩니다.

해결책: assistant 메시지 prefilling + stop sequence

assistant 메시지 prefilling과 stop sequence를 결합하면 원하는 콘텐츠만 정확히 얻을 수 있습니다. 동작 방식은 다음과 같습니다:

messages = []
add_user_message(messages, "Generate a very short event bridge rule as json")
add_assistant_message(messages, "

json")

text = chat(messages, stop_sequences=["

"])

이 기법은 다음과 같이 동작합니다:

  • assistant 메시지를 마크다운 여는 구분자로 prefill하기
  • Claude가 코드 블록을 닫으려 할 때 생성을 멈추도록 stop sequence 설정하기
  • 이 두 구분자 사이의 콘텐츠만 캡처하기

이면에서의 동작 방식

Claude가 요청을 받으면 prefill된 assistant 메시지를 보고 자신이 이미 JSON 코드 블록을 쓰기 시작했다고 가정합니다. 그래서 자체 헤더와 여는 구분자를 붙이는 대신, 곧바로 실제 JSON 콘텐츠 생성으로 넘어갑니다.

Claude가 JSON을 다 쓰고 마크다운 코드 블록을 자연스럽게 닫으려 할 때

`` , the stop sequence immediately halts generation and returns the response. You get just the JSON content with no extra formatting. 

## Processing the Results

The returned text might contain some newline characters, but you can easily clean this up:

import json

JSON으로 파싱해 검증하고 서식 맞추기

parsed_data = json.loads(text.strip())

또는 다른 데이터 유형이라면 공백만 제거하기

clean_text = text.strip()

## Beyond JSON

This technique isn't limited to JSON generation. You can use it for any structured data where you want just the content without Claude's natural tendency to add explanatory text: 

- Python code snippets 
- Bulleted lists 
- CSV data 
- Configuration files 
- Any format where clean, copyable output matters 

The key is identifying what delimiters Claude would naturally use around your content type, then prefilling the opening delimiter and stopping at the closing one. This gives you precise control over the output format while leveraging Claude's natural formatting instincts.

프롬프트 평가

🎬 영상

Claude를 다룰 때 좋은 프롬프트를 작성하는 것은 시작에 불과합니다. 신뢰할 수 있는 AI 애플리케이션을 만들려면 두 가지 핵심 개념을 이해해야 합니다. 바로 prompt engineering과 prompt evaluation입니다. prompt engineering은 더 나은 프롬프트를 만드는 기법을 제공하고, prompt evaluation은 그 프롬프트가 실제로 얼마나 잘 작동하는지를 측정하도록 도와줍니다.

Prompt Engineering vs Prompt Evaluation

prompt engineering은 프롬프트를 작성하고 개선하기 위한 도구 모음입니다. Claude가 당신이 무엇을 요청하는지, 어떻게 응답하기를 원하는지 정확히 이해하도록 돕는 모범 사례들의 집합이죠. multishot prompting, XML tags를 이용한 구조화 등 앞으로 살펴볼 여러 기법처럼, 프롬프트 작성이라는 하나의 기술이라고 생각하면 됩니다.

반면 prompt evaluation은 측정에 관한 것입니다. 프롬프트가 실제로 효과적인지에 대한 객관적인 지표를 제공하는 자동화된 테스트죠. 프롬프트가 잘 작동하는지 추측하는 대신, evaluation을 통해 다음을 할 수 있습니다.

  • 기대하는 정답과 비교해 테스트
  • 같은 프롬프트의 여러 버전 비교
  • 출력에 오류가 있는지 검토

프롬프트 작성 후의 세 가지 갈림길

프롬프트 초안을 작성하고 나면, 보통 다음에 무엇을 할지에 대해 세 가지 선택지에 직면하게 됩니다.

선택 1: 프롬프트를 한 번 테스트해 보고 충분히 괜찮다고 판단합니다. 사용자가 예상치 못한 입력을 주었을 때 프로덕션에서 망가질 위험이 상당히 큽니다.

선택 2: 프롬프트를 몇 번 테스트하고 한두 가지 예외 케이스를 처리하도록 손봅니다. 선택 1보다는 낫지만, 사용자는 종종 당신이 고려하지 못한 매우 예상 밖의 입력을 주기 때문에 여전히 취약합니다.

선택 3: 프롬프트를 evaluation 파이프라인에 통과시켜 점수를 매긴 뒤, 객관적인 데이터를 바탕으로 프롬프트를 반복 개선합니다. 초기에 더 많은 작업과 비용이 들지만, 프롬프트의 신뢰성에 대해 훨씬 큰 확신을 줍니다.

왜 대부분의 엔지니어는 테스트 함정에 빠질까

선택 1과 2는 저를 포함한 모든 엔지니어가 빠지는 함정입니다. 중요한 애플리케이션을 위한 프롬프트를 작성하면서도 충분히 철저하게 테스트하지 않는 것은 흔한 일이죠. 우리는 스스로에게 당연해 보이는 입력으로 테스트하는 경향이 있지만, 실제 사용자는 전혀 예상하지 못한 방식으로 프롬프트와 상호작용합니다.

해결책은 선택 3, 즉 체계적인 evaluation을 받아들이는 것입니다. 프롬프트를 제대로 된 evaluation 파이프라인에 통과시키면, 다양한 시나리오에서 프롬프트가 얼마나 잘 작동하는지 알려주는 객관적인 점수를 얻게 됩니다. 이 데이터 기반 접근은 자신 있게 반복 개선하고, 문제가 프로덕션에 도달하기 전에 잡아낼 수 있게 해줍니다.

evaluation을 먼저 이해하면, prompt engineering 기법을 적용하면서 개선을 측정할 수 있는 기반이 마련됩니다. 프롬프트의 효과를 신뢰성 있게 측정할 수 있게 되면, 여러 접근을 실험하며 어떤 것이 확실히 더 나은지 판단할 수 있습니다.

전형적인 평가 워크플로

🎬 영상

전형적인 prompt evaluation 워크플로는 프롬프트를 객관적으로 측정하고 개선하기 위한 체계적인 접근을 따릅니다. 이런 워크플로를 구성하는 방법은 여러 가지이고 다양한 오픈소스 및 유료 도구도 있지만, 핵심 프로세스를 이해하면 작게 시작해서 필요에 따라 확장해 나갈 수 있습니다.

1단계: 초기 프롬프트 작성

개선하고 싶은 기본 프롬프트를 작성하는 것부터 시작합니다. 이 예제에서는 간단한 프롬프트 구조를 사용하겠습니다.

prompt = f"""
Please answer the user's question:

{question}
"""

이것으로 작업의 기준선(baseline)이 생깁니다. 어떤 객관적인 방법론으로 evaluation하기 전까지는 이 프롬프트가 효과적인지 알 수 없습니다.

2단계: evaluation dataset 만들기

evaluation dataset에는 프롬프트에 넣을 샘플 입력이 담깁니다. 우리 프롬프트는 입력이 하나(사용자의 질문)뿐이므로, 테스트에 사용할 다양한 질문 모음이 필요합니다.

dataset에는 프롬프트와 병합할 질문들이 담깁니다. 이런 dataset은 직접 손으로 만들 수도 있고 Claude로 생성할 수도 있습니다. 실제 evaluation에서는 수십, 수백, 심지어 수천 개의 서로 다른 레코드를 가질 수 있지만, 이 예제에서는 세 개의 질문만으로 시작하겠습니다.

  • 2+2는 얼마인가요?
  • 오트밀은 어떻게 만드나요?
  • 달은 얼마나 멀리 있나요?

3단계: Claude에 통과시키기

dataset의 각 질문을 프롬프트 템플릿과 병합해 완성된 프롬프트를 만듭니다. 그런 다음 각각을 Claude에 보내고 응답을 수집합니다.

예를 들어 첫 번째 질문은 Claude가 응답할 수 있는 완성된 프롬프트가 됩니다. 이 과정을 dataset의 모든 레코드에 대해 반복하면 "2 + 2 = 4", 자세한 오트밀 조리법, 달까지의 거리 정보 같은 응답을 얻게 됩니다.

4단계: grader에 통과시키기

이제 핵심 단계입니다. 바로 Claude의 응답을 객관적으로 채점하는 것이죠. 각 질문-답변 쌍을 grader에 넣어 Claude 응답의 품질을 평가합니다.

grader는 응답 품질에 따라 점수(보통 1~10)를 부여합니다.

  • 10 = 완벽한 답변, 개선의 여지 없음
  • 4 = 개선의 여지가 분명히 있음
  • 1 = 부실하거나 틀린 응답

우리 예제에서는 응답이 각각 10, 4, 9점을 받을 수 있습니다. 이 점수들을 평균 내면 전체 성능 지표 7.66이 나옵니다.

5단계: 프롬프트 변경 후 반복

기준 점수가 확립되었으니, 이제 프롬프트를 반복 개선할 수 있습니다. Claude의 응답을 유도하기 위해 더 구체적인 지시를 추가해 보세요.

prompt = f"""
Please answer the user's question:

{question}

Answer the question with ample detail
"""

개선한 프롬프트를 전체 evaluation 파이프라인에 다시 통과시킵니다. 점수를 비교해 어느 버전이 더 나은 성능을 내는지 확인하세요.

프롬프트 채점과 반복 개선

이 워크플로의 힘은 각 프롬프트 버전에 대해 객관적인 측정값을 얻는 데 있습니다. 여러 반복(iteration) 간의 점수를 비교해 가장 성능이 좋은 버전을 사용하거나, 더 나은 접근을 찾기 위해 계속 반복 개선할 수 있습니다.

우리 예제에서는 다음과 같습니다.

  • 프롬프트 v1은 7.66점
  • 프롬프트 v2는 8.7점

v2의 더 높은 점수는 "Answer the question with ample detail"을 추가한 것이 테스트 케이스 전반에서 프롬프트 성능을 향상시켰음을 시사합니다.

이런 체계적인 접근은 주관적인 판단에 의존하는 대신 프롬프트 개선을 객관적으로 측정할 수 있는 방법을 제공합니다. 간단한 구현으로 시작해서 필요가 커짐에 따라 점점 더 정교한 평가 기준을 추가해 나갈 수 있습니다.

테스트 데이터셋 생성

🎬 영상

맞춤형 prompt evaluation 워크플로를 만드는 일은 명확한 목표를 세우고 테스트 데이터를 생성하는 것에서 시작합니다. 이 사례에서는 사용자가 AWS 전용 코드(Python 함수, JSON 설정, 또는 정규식)를 부가 설명이나 서식 없이 작성하도록 돕는 프롬프트를 만들어 보겠습니다.

목표 설정

이 프롬프트는 사용자의 작업 설명을 받아 세 가지 출력 유형 중 하나를 반환해야 합니다.

  • Python 코드
  • JSON 설정
  • 정규식(regex)

핵심 요구사항은 응답에 헤더, 푸터, 설명 없이 요청한 코드만 담겨야 한다는 것입니다.

간단한 첫 버전으로 시작하면 관리하기 수월합니다. 초기 프롬프트 템플릿은 단순합니다. "Please provide a solution to the following task: {task}"

evaluation dataset 만들기

evaluation dataset에는 프롬프트에 넣을 입력 예시가 담깁니다. 각 테스트 케이스는 프롬프트와 결합되어 Claude에 전달되며, 이를 통해 다양한 시나리오에서 프롬프트가 얼마나 잘 작동하는지 확인할 수 있습니다.

dataset은 두 가지 방법으로 만들 수 있습니다.

  • 손으로 직접 테스트 케이스 작성
  • Claude를 사용해 자동으로 생성

자동 생성의 경우, 여러 테스트 케이스를 만들어야 하므로 Haiku처럼 더 빠른 모델을 사용하는 것이 합리적입니다.

평가 실행하기

🎬 영상

이제 evaluation dataset이 준비되었으니, 핵심 evaluation 파이프라인을 만들 차례입니다. 이 과정은 각 테스트 케이스를 가져와 프롬프트와 병합하고, Claude에 전달한 뒤, 결과를 채점하는 것으로 이루어집니다.

evaluation 프로세스는 명확한 워크플로를 따릅니다. 테스트 케이스 dataset을 가져와 각각을 프롬프트 템플릿과 결합하고, 처리를 위해 Claude에 보낸 뒤, grader 시스템으로 출력을 평가합니다.

핵심 함수 만들기

evaluation 파이프라인은 각각 고유한 역할을 맡는 세 개의 주요 함수로 구성됩니다. 가장 단순한 것, 즉 개별 프롬프트 실행을 처리하는 함수부터 시작하겠습니다.

run_prompt 함수

이 함수는 테스트 케이스를 받아 프롬프트 템플릿과 병합합니다.

def run_prompt(test_case):
"""Merges the prompt and test case input, then returns the result"""
prompt = f"""
Please solve the following task:

{test_case["task"]}
"""

messages = []
add_user_message(messages, prompt)
output = chat(messages)
return output

지금은 프롬프트를 아주 단순하게 유지하고 있습니다. 서식 관련 지시를 전혀 포함하지 않았기 때문에, Claude는 우리가 필요로 하는 것보다 더 장황한 출력을 반환할 가능성이 큽니다. 이 부분은 나중에 evaluation 프로세스를 반복 개선하면서 다듬을 것입니다.

run_test_case 함수

이 함수는 단일 테스트 케이스를 실행하고 결과를 채점하는 과정을 총괄합니다.

def run_test_case(test_case):
"""Calls run_prompt, then grades the result"""
output = run_prompt(test_case)

# TODO - Grading
score = 10

return {
"output": output,
"test_case": test_case,
"score": score
}

지금은 10점으로 하드코딩된 점수를 사용하고 있습니다. 채점 로직은 이후 섹션에서 상당한 시간을 들여 다룰 부분이지만, 이 임시 값 덕분에 전체 파이프라인 구조를 테스트할 수 있습니다.

run_eval 함수

이것은 전체 dataset을 처리하는 메인 오케스트레이터입니다.

def run_eval(dataset):
"""Loads the dataset and calls run_test_case with each case"""
results = []

for test_case in dataset:
result = run_test_case(test_case)
results.append(result)

return results

이 함수는 dataset의 모든 테스트 케이스를 순회하며 각각을 처리하고, 모든 결과를 하나의 리스트로 모읍니다.

evaluation 실행하기

evaluation 파이프라인을 실행하려면 dataset을 로드하고 메인 함수를 호출합니다.

with open("dataset.json", "r") as f:
dataset = json.load(f)

results = run_eval(dataset)

처음 실행할 때는 시간이 좀 걸린다는 점을 감안하세요. Claude Haiku를 쓰더라도 전체 dataset을 처리하는 데 30초 이상 걸릴 수 있습니다. 최적화 기법은 나중에 다루겠지만, 지금은 인내가 핵심입니다.

결과 살펴보기

evaluation이 완료되면 서식이 적용된 JSON 출력으로 결과를 확인할 수 있습니다.

print(json.dumps(results, indent=2))

결과 구조는 객체 배열을 담고 있으며, 각 객체는 하나의 테스트 케이스 실행을 나타냅니다. 여기서 Claude 출력(서식 제약이 없으면 상당히 장황해지는 경향이 있습니다), 원래의 테스트 케이스 정의, 그리고 점수를 확인할 수 있습니다.

지금까지 이룬 것

이 시점에서 우리는 핵심 evaluation 파이프라인을 성공적으로 구현했습니다. 이제 다음을 할 수 있습니다.

  • dataset에서 테스트 케이스 가져오기
  • 프롬프트 템플릿과 병합하기
  • Claude로부터 응답 받기
  • 모든 결과를 수집하고 정리하기

빠진 조각은 지능적인 채점입니다. 지금은 모든 응답에 고정된 점수를 부여할 뿐이죠. 다음 단계는 Claude의 출력이 실제로 올바른지 평가할 수 있는 grader를 만드는 것이며, 바로 여기서 evaluation 시스템의 진정한 정교함이 발휘됩니다.

모델 기반 채점

🎬 영상

prompt 평가 워크플로우를 구축할 때 grader는 출력 품질에 대한 객관적인 신호를 제공합니다. grader는 모델 출력을 받아 측정 가능한 형태의 피드백을 반환하는데, 보통 1~10 사이의 숫자로 나타내며 10은 높은 품질, 1은 낮은 품질을 의미합니다.

Grader의 종류

모델 출력을 채점하는 방식은 크게 세 가지입니다:

  • Code grader - 직접 작성한 로직으로 출력을 프로그램적으로 평가
  • Model grader - 다른 AI 모델을 사용해 품질을 평가
  • Human grader - 사람이 직접 출력을 검토하고 점수를 매김

Code Grader

Code grader로는 상상할 수 있는 어떤 프로그램적 검사든 구현할 수 있습니다. 대표적인 용도는 다음과 같습니다:

  • 출력 길이 확인
  • 특정 단어의 포함 여부 확인
  • JSON, Python, regex의 구문 검증
  • 가독성 점수

유일한 요구 사항은 코드가 실행될 때 측정 가능한 신호를 반환하는 것뿐입니다.

Model Grader

Model grader는 원본 출력을 평가하기 위해 추가 API 요청을 보냅니다. 이 방식은 다음과 같은 항목을 평가하는 데 엄청난 유연성을 제공합니다:

  • 응답 품질
  • 지시 준수 품질
  • 완결성
  • 유용성
  • 안전성

Human Grader

Human grader는 가장 유연하지만 시간이 많이 들고 번거롭습니다. 다음을 평가할 때 유용합니다:

  • 전반적인 응답 품질
  • 포괄성
  • 깊이
  • 간결성
  • 관련성

평가 기준 정의하기

어떤 grader든 구현하기 전에 명확한 평가 기준이 필요합니다. 코드 생성 prompt라면 다음 항목에 집중할 수 있습니다:

  • 형식 - 설명 없이 Python, JSON, Regex만 반환해야 함
  • 유효한 구문 - 생성된 코드는 유효한 구문을 가져야 함
  • 과제 준수 - 응답은 정확한 코드로 사용자의 과제를 직접적으로 해결해야 함

앞의 두 기준은 code grader로 잘 처리되지만, 과제 준수는 유연성 덕분에 model grader에 더 적합합니다.

Model Grader 구현하기

model grader 함수를 만드는 방법은 다음과 같습니다:

def grade_by_model(test_case, output):
# Create evaluation prompt
eval_prompt = """
You are an expert code reviewer. Evaluate this AI-generated solution.

Task: {task}
Solution: {solution}

Provide your evaluation as a structured JSON object with:
- "strengths": An array of 1-3 key strengths
- "weaknesses": An array of 1-3 key areas for improvement 
- "reasoning": A concise explanation of your assessment
- "score": A number between 1-10
"""

messages = []
add_user_message(messages, eval_prompt)
add_assistant_message(messages, "

json")

eval_text = chat(messages, stop_sequences=["

"])
return json.loads(eval_text)

핵심은 점수와 함께 강점, 약점, 근거를 요청하는 것입니다. 이런 맥락이 없으면 모델은 6점 정도의 어중간한 점수로 수렴하는 경향이 있습니다.

Grader 통합하기

test case 함수가 model grader를 사용하도록 업데이트합니다:

def run_test_case(test_case): output = run_prompt(test_case)

모델 평가 받기

model_grade = grade_by_model(test_case, output) score = model_grade["score"] reasoning = model_grade["reasoning"]

return { "output": output, "test_case": test_case, "score": score, "reasoning": reasoning }

평균 점수 계산하기

전반적인 성능 지표를 얻으려면 모든 test case에 걸친 평균 점수를 계산합니다:

from statistics import mean

def run_eval(dataset): results = []

for test_case in dataset: result = run_test_case(test_case) results.append(result)

average_score = mean([result["score"] for result in results]) print(f"Average score: {average_score}")

return results

이렇게 하면 시간이 지남에 따라 prompt 성능을 추적할 수 있는 구체적이고 객관적인 지표가 생깁니다. model grader가 다소 일관성이 없을 수는 있지만, prompt를 체계적으로 측정하고 개선하기 위한 출발점을 제공합니다.

코드 기반 채점

🎬 영상

코드 기반 채점은 모델 출력이 올바른 형식을 따르고 유효한 구문을 갖추었는지 확인함으로써 prompt 평가에 검증 계층을 하나 더 더합니다. 모델에게 코드, JSON, 정규 표현식을 생성하도록 요청할 때 특히 유용합니다.

코드 채점의 동작 방식

code grader는 크게 두 가지 기준을 평가합니다:

  • 형식 준수 - 출력이 설명 없이 요청된 형식(Python, JSON, regex)만 담고 있는가?
  • 유효한 구문 - 출력이 실제로 파싱되거나 컴파일될 수 있는가?

이 시스템은 형식 유형마다 별도의 검증 함수를 사용합니다. 코드가 성공적으로 파싱되면 만점인 10점을, 파싱이 오류로 실패하면 0점을 받습니다.

검증 함수 설정하기

서로 다른 출력 유형을 검증하려면 세 개의 헬퍼 함수가 필요합니다:

def validate_json(text):
try:
json.loads(text.strip())
return 10
except json.JSONDecodeError:
return 0

def validate_python(text):
try:
ast.parse(text.strip())
return 10
except SyntaxError:
return 0

def validate_regex(text):
try:
re.compile(text.strip())
return 10
except re.error:
return 0

이 함수들은 Python의 내장 파싱 기능을 사용해 구문 유효성을 검사합니다. json.loads()는 JSON을 검증하고, ast.parse()는 Python 추상 구문 트리를 생성하며, re.compile()은 정규 표현식을 검증합니다.

Test Case에 형식 정보 추가하기

test dataset은 각 과제마다 예상 출력 형식을 명시해야 합니다. dataset 생성 prompt에 format 필드를 포함하도록 업데이트하세요:

{
"task": "Description of task",
"format": "python"
}

format 필드에는 해당 과제에서 기대하는 출력 유형에 따라 "json", "python", "regex" 중 하나를 넣습니다.

Prompt 개선하기

code grader에서 더 나은 결과를 얻으려면 prompt 지시를 더 구체적으로 작성하세요:

* Respond only with Python, JSON, or a plain Regex
* Do not add any comments or commentary or explanation

또한 code block과 stop sequence를 활용한 미리 채워진 assistant 메시지를 사용하면 깔끔한 출력 형식을 보장할 수 있습니다.

점수 합치기

마지막 단계는 model grader 점수와 구문 grader 점수를 합치는 것입니다. 간단한 방법은 두 점수의 평균을 내는 것입니다:

model_grade = grade_by_model(test_case, output)
model_score = model_grade["score"]
syntax_score = grade_syntax(output, test_case)

score = (model_score + syntax_score) / 2

이렇게 하면 (model grader가 판단한) 내용 품질과 (code grader가 판단한) 기술적 정확성에 동일한 가중치를 부여합니다. 특정 사용 사례에서 무엇이 더 중요한지에 따라 이 가중치를 조정할 수 있습니다.

결과 해석하기

평가를 실행하면 생성된 코드의 의미적 품질과 기술적 정확성을 모두 반영하는 통합 점수를 얻게 됩니다. 단일 점수만으로는 많은 것을 알 수 없다는 점을 기억하세요. 진짜 가치는 prompt 설계를 반복 개선하며 점수를 비교하는 데서 나옵니다.

이 기준 점수를 활용해 prompt 개선을 테스트하고, 변경 사항이 실제로 더 낫고 안정적인 코드 생성으로 이어지는지 확인하세요.

프롬프트 엔지니어링

🎬 영상

프롬프트 엔지니어링은 작성한 prompt를 개선해 더 안정적이고 높은 품질의 출력을 얻어내는 작업입니다. 이 과정은 초기 prompt를 작성하고, 그 성능을 평가한 뒤, 엔지니어링 기법을 체계적으로 적용해 단계별로 개선하는 흐름으로 이루어집니다.

반복적 개선 과정

이 접근법은 명확한 순환 구조를 따릅니다. 목표를 정하고, 초기 prompt를 작성하고, 평가하고, 프롬프트 엔지니어링 기법을 적용한 뒤, 다시 평가해 성능이 나아졌는지 확인합니다. prompt를 다듬어 가며 이 순환을 반복합니다.

이 튜토리얼 시리즈에서는 실용적인 예제를 다룹니다. 운동선수의 키, 몸무게, 신체 목표, 식이 제한을 바탕으로 하루치 식단을 생성하는 prompt를 만들어 봅니다.

평가 파이프라인 설정하기

이 평가는 앞선 모듈의 파이프라인을 개선한 버전을 사용하며, dataset 생성과 model grading을 처리하는 PromptEvaluator 클래스로 감싸져 있습니다. 이 클래스는 평가 과정을 빠르게 하기 위한 동시 실행을 지원합니다:

evaluator = PromptEvaluator(max_concurrent_tasks=5)

rate limit 오류를 피하려면 낮은 동시 실행 값(예: 3)으로 시작하세요. API 할당량에 따라 조정할 수 있습니다.

테스트 데이터 생성하기

generate_dataset 메서드는 prompt를 위한 test case를 생성합니다. 다음을 지정해야 합니다:

  • prompt가 무엇을 해야 하는지 설명하는 과제 설명
  • prompt가 요구하는 입력의 명세
  • 생성할 test case의 개수

식단 계획 예제의 경우:

dataset = evaluator.generate_dataset(
task_description="Write a compact, concise 1 day meal plan for a single athlete",
prompt_inputs_spec={
"height": "Athlete's height in cm",
"weight": "Athlete's weight in kg", 
"goal": "Goal of the athlete",
"restrictions": "Dietary restrictions of the athlete"
},
num_cases=3
)

초기 Prompt 작성하기

기준선을 잡기 위해 단순하고 소박한 prompt부터 시작합니다. run_prompt 함수는 test case 입력을 받아 모델의 응답을 반환해야 합니다:

def run_prompt(prompt_inputs):
prompt = f"""
What should this person eat?

- Height: {prompt_inputs["height"]}
- Weight: {prompt_inputs["weight"]}
- Goal: {prompt_inputs["goal"]}
- Dietary restrictions: {prompt_inputs["restrictions"]}
"""

messages = []
add_user_message(messages, prompt)
return chat(messages)

평가 실행하기

평가 과정은 prompt의 출력을 기대 기준과 비교합니다. 채점을 안내하기 위한 추가 기준을 더할 수 있습니다:

results = evaluator.run_evaluation(
run_prompt_function=run_prompt,
dataset_file="dataset.json",
extra_criteria="""
The output should include:
- Daily caloric total
- Macronutrient breakdown 
- Meals with exact foods, portions, and timing
"""
)

결과 분석하기

평가를 실행하면 브라우저에서 열 수 있는 output.html 파일이 생성됩니다. 이 리포트는 각 test case의 상세 결과를 보여주며, 점수, 근거, prompt가 실제로 생성한 출력을 포함합니다.

초기 점수가 낮다고 낙담하지 마세요. 원래 그렇습니다! 이 예제의 초기 prompt는 10점 만점에 2.3점밖에 받지 못했지만, 덕분에 개선의 출발점이 되는 명확한 기준선이 생깁니다.

다음 단계

기준선을 잡았으니, 이제 더 구체적으로 쓰기, 출력 형식 요구 사항 추가하기, 구조화된 prompt 사용하기, multishot 예시 적용하기 같은 프롬프트 엔지니어링 기법을 체계적으로 적용할 수 있습니다. 각 기법은 평가 점수를 높여주며, 목표를 향한 측정 가능한 진전을 보여줍니다.

명확하고 직접적으로

🎬 영상

프롬프트의 첫 문장은 요청 전체에서 가장 중요한 부분입니다. 여기서 뒤이어 나올 모든 내용의 무대를 설정하게 되며, 이 첫 문장을 잘 작성하면 결과가 극적으로 좋아집니다.

명확하고 직접적으로 쓰기

이 중요한 첫 문장을 작성할 때는 두 가지 핵심 원칙에 집중해야 합니다. 바로 명확성과 직접성입니다. Claude가 무엇을 해야 하는지에 대해 애매함이 남지 않도록 간결한 표현을 사용한다는 뜻입니다.

명확한 의사 전달

"명확하다"는 것은 다음을 의미합니다.

  • 누구나 이해할 수 있는 간결한 표현을 사용한다
  • 빙빙 돌리지 말고 원하는 바를 정확히 말한다
  • Claude가 해야 할 작업을 직설적으로 먼저 제시한다

"사람들이 지붕에 올려놓는, 태양을 쓰는 그거 있잖아요, 태양광 패널이라고 부르는 것 같은데"처럼 모호하게 쓰는 대신, 직접적으로 "태양광 패널의 작동 원리에 대해 세 문단으로 작성하라"라고 쓰세요.

직접적인 지시

"직접적"이라는 것은 요청을 어떻게 구성하는가에 초점을 맞춥니다.

  • 질문이 아니라 지시문을 사용한다
  • "작성하라", "만들라", "생성하라"처럼 행동을 나타내는 동사로 시작한다

"재생 에너지에 대해 읽고 있는데 지열 에너지가 흥미롭네요. 어떤 나라들이 사용하나요?"라고 묻는 대신, "지열 에너지를 사용하는 국가 세 곳을 찾아라. 각각의 발전량 통계를 포함하라"라고 해보세요.

실제로 적용하기

이 기법을 실제로 살펴봅시다. 단순히 "이 사람은 무엇을 먹어야 하나요?"라고 물었던 약한 프롬프트에서 시작해, 명확하고 직접적인 접근을 적용할 수 있습니다.

개선된 버전은 다음과 같습니다. Generate a one-day meal plan for an athlete that meets their dietary restrictions.

이 수정된 프롬프트는 Claude에게 곧바로 다음을 알려줍니다.

  • 어떤 행동을 할지(생성한다)
  • 무엇을 만들지(식단)
  • 핵심 제약 조건(하루치, 운동선수용, 제약 사항 고려)

결과가 말해준다

이런 간단한 변화만으로도 출력 품질에 큰 차이가 생깁니다. 예시에서 평가 점수는 2.32에서 3.92로 뛰었는데, 첫 문장을 재구성한 것만으로 이룬 상당한 개선입니다.

핵심은, Claude를 원하는 바를 알아서 추측해야 하는 상대가 아니라 명확한 지시가 필요한 유능한 조수처럼 대할 때 가장 잘 반응한다는 점입니다. 행동을 나타내는 동사로 강하게 시작하고 작업을 구체적으로 밝히면, 곧바로 더 나은 결과를 보게 될 것입니다.

구체적으로 지시하기

🎬 영상

Claude를 다룰 때 결과를 개선하는 가장 효과적인 방법 중 하나는 원하는 바를 구체적으로 지시하는 것입니다. 모든 것을 모델의 해석에 맡기는 대신, 명확한 가이드라인이나 단계를 제시해 Claude를 원하는 출력 방향으로 이끌 수 있습니다.

이렇게 생각해보세요. Claude에게 "숨겨진 재능을 발견하는 인물에 대한 단편 소설을 써라"라고 요청하면, 모델은 수많은 방향으로 갈 수 있습니다. 200단어를 쓸 수도, 2,000단어를 쓸 수도 있습니다. 인물 한 명에 집중할 수도, 다섯 명을 등장시킬 수도 있습니다. 이야기 구조도 천차만별일 수 있습니다.

하지만 구체적인 가이드라인을 더하면, 출력을 원하는 바에 훨씬 가깝게 다듬을 수 있습니다.

가이드라인의 두 가지 유형

프롬프트를 구체적으로 만드는 데는 두 가지 주요 접근법이 있으며, 실무 애플리케이션에서는 두 가지를 함께 쓰는 경우가 많습니다.

품질 가이드라인

첫 번째 유형은 출력이 갖춰야 할 품질을 나열하는 데 초점을 둡니다. 이런 가이드라인은 다음과 같은 속성을 제어합니다.

  • 길이 제약(1,000단어 이내로 유지)
  • 구조적 요구사항(인물의 재능이 드러나는 명확한 사건을 포함)
  • 내용 명세(조연 인물을 최소 한 명 포함)

프로세스 단계

두 번째 유형은 모델이 따라야 할 구체적인 단계를 제시합니다. 이 접근법은 Claude가 문제를 체계적으로 사고하도록 만듭니다.

  • 극적 긴장감을 만들어낼 재능 3가지를 브레인스토밍한다
  • 가장 흥미로운 재능을 고른다
  • 그 재능이 드러나는 핵심 장면을 개요로 잡는다
  • 이 발견의 임팩트를 키울 수 있는 조연 유형 3가지를 브레인스토밍한다

품질 가이드라인이 출력의 모습을 제어한다면, 프로세스 단계는 Claude가 그 출력에 이르는 방식을 제어합니다.

실전 테스트

실제로 어떻게 동작하는지 살펴봅시다. 다음은 구체적인 가이드라인을 넣어 식단을 생성하는 프롬프트입니다.

Generate a one-day meal plan for an athlete that meets their dietary restrictions.

- Height: {prompt_inputs["height"]}
- Weight: {prompt_inputs["weight"]}
- Goal: {prompt_inputs["goal"]}
- Dietary restrictions: {prompt_inputs["restrictions"]}

Guidelines:
1. Include accurate daily calorie amount
2. Show protein, fat, and carb amounts
3. Specify when to eat each meal
4. Use only foods that fit restrictions
5. List all portion sizes in grams
6. Keep budget-friendly if mentioned

가이드라인이 없는 기준(baseline) 프롬프트와 비교해 테스트한 결과, 이 접근법은 평가 점수를 3.92에서 7.86으로 끌어올려 품질을 두 배 이상 높였습니다.

프로세스 단계 접근법(Claude에게 먼저 칼로리를 계산하고, 그다음 매크로를 산출하고, 그다음 식사 시간을 계획하라고 지시하는 방식)도 테스트했을 때 7.3점으로 상당한 개선을 보였습니다.

언제 단계를 제시할까

품질 가이드라인은 대부분의 프롬프트에서 잘 작동하지만, 다음과 같은 경우에는 프로세스 단계를 추가하는 것을 고려하세요.

  • 어려운 문제를 해결할 때
  • 의사결정을 할 때
  • 비판적 사고가 필요할 때
  • Claude가 더 "넓은" 관점을 고려하도록 강제하고 싶을 때

예를 들어 지난 분기에 영업팀 실적이 30% 떨어진 이유를 Claude에게 분석하라고 요청한다면, 처음 눈에 띄는 설명으로 성급하게 결론짓지 않도록 여러 관점(시장 상황, 개인 성과, 조직 변화, 고객 피드백)을 반드시 고려하게 하는 단계를 제시하는 것이 좋습니다.

핵심은, 구체적으로 지시하면 모든 것을 운에 맡기는 대신 일관되고 품질 높은 결과를 얻을 수 있다는 점입니다. 품질 가이드라인이든, 프로세스 단계든, 둘 다든, Claude가 작업할 명확한 틀을 제공하는 셈입니다.

XML 태그로 구조화

🎬 영상

많은 내용을 담은 프롬프트를 만들다 보면, Claude가 어떤 텍스트끼리 한 묶음인지, 각 구획이 무엇을 나타내는지 파악하기 어려워하는 경우가 있습니다. XML 태그는 프롬프트에 구조와 명료함을 더하는 간단한 방법으로, 특히 대량의 데이터를 삽입(interpolation)할 때 유용합니다.

구조가 중요한 이유

20페이지 분량의 판매 기록을 분석해야 하는 프롬프트를 생각해봅시다. 명확한 경계가 없으면 Claude는 여러분의 지시와 실제로 분석해야 할 데이터를 구분하기 어려울 수 있습니다.

위 예시는 경계가 불분명하면 Claude가 여러분의 의도를 해석하기 어려워진다는 점을 보여줍니다. 판매 기록을 XML 태그로 감싸면, 프롬프트의 서로 다른 부분들 사이에 명확한 구분이 생깁니다.

명료함을 위해 XML 태그 사용하기

XML 태그는 Claude가 프롬프트의 구조를 이해하도록 돕는 구분자(delimiter) 역할을 합니다. 담긴 내용을 설명하는 사용자 정의 태그 이름을 만들 수 있습니다.

<sales_records>
{sales_records}
</sales_records>

태그 이름은 공식 XML 명세를 따를 필요가 없습니다. sales_records , data , records 처럼 설명적인 이름을 자유롭게 지으면 됩니다. 일반적으로 두루뭉술한 이름보다 구체적인 이름이 더 잘 작동합니다.

실전 예시

XML 태그가 왜 차이를 만드는지 잘 보여주는 예시입니다. "좋지 않은" 버전에서는 어떤 내용이 버그가 있는 코드이고 어떤 것이 문서인지 구분하기 어렵습니다.

개선된 버전은 XML 태그를 사용해 서로 다른 유형의 내용을 명확히 분리합니다.

<my_code>
from datavortex import Pipeline, DataSource

def process_data(input_file, output_file):
pipeline = Pipeline()
source = DataSource.from_csv(input_file)
</my_code>

<docs>
# Creating a data source from data vortex
csv_source = DataSource.from_csv("data.csv")
</docs>

이제 Claude는 디버깅이 필요한 코드와 디버깅 과정을 안내해야 할 문서를 쉽게 구분할 수 있습니다.

내 프롬프트에 구조 적용하기

삽입하는 내용이 방대하지 않을 때도 XML 태그는 명료함을 높여줍니다. 예를 들어 식단을 생성할 때 운동선수 정보를 하나로 묶을 수 있습니다.

<athlete_information>
- Height: {prompt_inputs["height"]}
- Weight: {prompt_inputs["weight"]}
- Goal: {prompt_inputs["goal"]}
- Dietary restrictions: {prompt_inputs["restrictions"]}
</athlete_information>

이렇게 하면 이 블록이 식단 생성에 반영되어야 할 운동선수에 대한 외부 입력이라는 점을 Claude에게 아주 명확하게 알려줄 수 있습니다.

언제 XML 태그를 쓸까

XML 태그는 다음과 같은 경우에 가장 유용합니다.

  • 많은 양의 컨텍스트나 데이터를 포함할 때
  • 프롬프트에 서로 구별되는 여러 유형의 내용이 담겨 있을 때
  • 서로 다른 구획 사이의 경계를 분명히 드러내고 싶을 때
  • 지시와 혼동될 수 있는 내용을 삽입할 때

단순한 프롬프트에서는 극적인 개선이 보이지 않을 수도 있지만, XML 태그는 구분자 역할을 하며 Claude가 여러분의 의도를 더 잘 이해하도록 도와 더 일관되고 정확한 응답으로 이어집니다.

예시 제공하기

🎬 영상

프롬프트에 예시를 제공하는 것은 여러분이 쓰게 될 가장 효과적인 prompt engineering 기법 중 하나입니다. "one-shot" 또는 "multi-shot" 프롬프팅이라 불리는 이 접근법은, Claude에게 샘플 입력/출력 쌍을 주어 응답을 유도하는 방식입니다.

예시가 작동하는 방식

감성 분석 예시를 살펴봅시다. Claude에게 어떤 트윗이 긍정인지 부정인지 분류하게 한다고 해봅시다.

여기서 까다로운 부분은 비꼬는 표현(sarcasm)입니다. "그럼요, 'Plan 9 from Outer Space' 이후로 본 최고의 영화였죠"라는 트윗은 겉보기엔 긍정적이지만, 실제로는 비꼬는 부정적 표현입니다(Plan 9 from Outer Space는 최악의 영화로 유명합니다).

프롬프트에 예시 추가하기

이를 처리하려면, Claude가 정확히 어떻게 응답해야 하는지 보여주는 예시를 추가하면 됩니다.

핵심 요소는 다음과 같습니다.

  • 명확한 도입부: "다음은 이상적인 응답이 함께 있는 예시 입력입니다"
  • 구조를 위한 XML 태그: <sample_input>과 <ideal_output>
  • 원하는 동작을 보여주는 구체적인 예시

코너 케이스 다루기

비꼬는 표현처럼 까다로운 상황에서는 여러 개의 예시를 제공할 수 있습니다(multi-shot 프롬프팅). Claude가 무엇을 주의해야 하는지 짚어주는 맥락을 덧붙이세요.

Be especially careful with tweets that contain sarcasm.
For example:
<sample_input>
Oh yeah, I really needed a flight delay tonight! Excellent!
</sample_input>
<ideal_output>
Negative
</ideal_output>

언제 예시를 쓸까

예시는 특히 다음과 같은 경우에 유용합니다.

  • 코너 케이스나 엣지 시나리오를 포착할 때
  • 복잡한 출력 형식(특정 JSON 구조 등)을 정의할 때
  • "좋은" 출력이 정확히 어떤 모습인지 Claude에게 보여줄 때

평가 결과에서 좋은 예시 찾기

prompt eval을 실행할 때, HTML report에서 가장 높은 점수를 받은 출력을 찾아보세요. 이런 출력은 프롬프트에 넣을 훌륭한 예시가 됩니다.

점수가 잘 나온 응답(가급적 10점, 또는 가장 높은 점수)을 찾아, 그 입력과 출력을 모두 복사해 예시로 사용하세요.

예시에 맥락 더하기

왜 그 예시가 좋은지 설명하면 예시를 한층 더 효과적으로 만들 수 있습니다. 예시 출력 뒤에 짧은 설명을 덧붙이세요.

<ideal_output>
[Your example output here]
</ideal_output>

This example meal plan is well-structured, provides detailed information on food choices and quantities, and aligns with the athlete's goals and restrictions.

이렇게 하면 Claude가 무엇을 만들어야 하는지뿐 아니라, 왜 그 출력이 이상적이라고 여겨지는지까지 이해하는 데 도움이 됩니다.

모범 사례

  • XML 태그로 예시를 명확하게 구조화한다
  • Claude에게 무엇을 보여주는지 분명히 밝힌다
  • 가장 중요한 사용 사례를 아우르는 대표적인 예시를 고른다
  • 모델이 걸려 넘어질 만한 코너 케이스를 포함한다
  • 예시가 좋은 이유가 분명하지 않다면 그 이유를 설명한다

one-shot과 multi-shot 프롬프팅은, 특히 일관되고 형식이 잘 갖춰진 출력이 필요하거나 까다로운 엣지 케이스를 안정적으로 다뤄야 할 때, 여러분의 prompt engineering 도구함에서 곧 필수 도구가 될 것입니다.

도구 사용 소개

🎬 영상

도구(tool)를 사용하면 Claude가 외부 세계의 정보에 접근할 수 있어, Claude의 핵심적인 한계 중 하나를 해결할 수 있습니다. 기본적으로 Claude는 학습된 정보에만 접근할 수 있으므로, 오늘의 날씨나 최신 뉴스 같은 실시간 정보는 제공하지 못합니다.

사용자가 "캘리포니아 샌프란시스코의 날씨는 어때?"라고 물으면 Claude는 보통 "죄송하지만 최신 날씨 정보에는 접근할 수 없습니다."라고 답합니다. 도구는 Claude와 외부 데이터 소스 사이에 다리를 놓아 이 문제를 해결합니다.

tool use의 동작 방식

tool use 과정은 서버와 Claude 사이에서 여러 차례 주고받는 통신을 포함하는 특정한 흐름을 따릅니다:

  • 초기 요청: 추가 데이터를 얻는 방법에 대한 안내와 함께 질문을 Claude에게 보냅니다
  • 도구 요청: Claude가 질문을 분석하고, 필요한 특정 외부 데이터를 요청합니다
  • 데이터 조회: 서버가 코드를 실행해 요청된 정보를 가져옵니다
  • 최종 응답: Claude가 외부 데이터를 활용해 완전하고 근거 있는 답변을 제공합니다

실제 날씨 예시

날씨 질의에 대해 tool use 흐름이 어떻게 동작하는지 살펴보겠습니다:

사용자가 날씨를 물으면, 초기 요청에 현재 날씨 데이터를 가져오는 방법에 대한 상세 정보를 담아 Claude에게 보냅니다. Claude는 현재 날씨 정보가 필요하다는 것을 인식하고 서버에 이를 가져오도록 요청합니다. 서버는 날씨 API를 호출해 실시간 데이터를 조회하고 Claude에게 돌려줍니다. 마지막으로 Claude는 원래 질문과 최신 날씨 데이터를 결합해 정확하고 최신인 응답을 제공합니다.

구현상의 어려움

tool use는 논리적 흐름과 실제 코드를 작성하는 방식 사이에 괴리가 있어 혼란스럽게 느껴질 수 있습니다. 구현 순서가 개념적 단계와 동일하게 진행되지 않기 때문입니다:

실제로는 보통 다음 작업들이 필요합니다:

  • 먼저 도구 함수를 작성한다
  • JSON Schema 명세를 만든다
  • ToolUse와 ToolResult 파트를 처리한다
  • 요청에 스키마를 포함시킨다

구현의 여러 부분을 이렇게 오가야 하기 때문에 tool use가 처음에는 복잡하게 느껴집니다. 핵심은 논리적 흐름의 각 단계마다 특정 코드 구성 요소가 필요하며, 이를 실행 순서와는 다른 순서로 만들게 된다는 점을 이해하는 것입니다.

이어지는 영상들에서는 tool use를 단계별로 구현하며, 지금 어떤 부분을 만들고 있는지 추적하기 위해 이 흐름 다이어그램을 자주 참조하겠습니다.

도구 함수

🎬 영상

Claude를 위한 도구를 만들다 보면 바로 눈에 띄지 않는 여러 문제를 해결해야 합니다. Claude가 미래 날짜에 알림을 설정하도록 하려고 하면, Claude는 현재 날짜는 알지만 정확한 시각은 항상 알지는 못하고, 복잡한 날짜 계산에 서툴며, 실제로 알림을 설정할 내장 수단도 없다는 것을 곧 알게 됩니다.

해결책은 이런 특정 작업을 처리하는 커스텀 도구를 만드는 것입니다. 알림 시스템을 위해서는 세 개의 별도 도구가 필요합니다: 현재 날짜와 시각을 가져오는 도구, 날짜에 기간을 더하는 도구, 그리고 실제로 알림을 설정하는 도구입니다.

왜 어려운가

Claude는 시간 기반 작업에서 몇 가지 한계가 있습니다:

  • Claude는 현재 날짜는 알아도 정확한 시각은 모를 수 있습니다
  • Claude는 시간 덧셈, 특히 여러 날 뒤의 미래를 계산하는 일을 항상 잘 처리하지는 못합니다
  • Claude는 알림을 설정하는 방법을 모릅니다

필요한 도구들

이 문제들을 해결하기 위해 세 개의 전용 도구를 만듭니다:

  • 현재 날짜/시각 가져오기 - Claude는 현재 날짜와 시각을 알아야 합니다
  • 날짜/시각에 기간 더하기 - Claude는 날짜/시각 덧셈이 완벽하지 않습니다
  • 알림 설정하기 - 알림을 설정할 수단이 필요합니다

도구 함수의 동작 방식

도구 시스템은 서버와 Claude 사이에서 특정한 흐름을 따릅니다. 추가 정보가 필요할 때 Claude가 호출할 수 있는 함수를 작성하면, Claude는 그 결과를 받아 응답을 구성하는 데 활용합니다.

이 과정은 여러 단계로 이루어집니다: 도구 함수 작성, JSON Schema 명세 생성, 그 스키마와 함께 Claude 호출, Claude가 요청하면 도구 실행, 그리고 결과를 Claude에게 되돌려주기입니다.

도구 함수 작성하기

도구 함수는 Claude가 사용자를 돕기 위해 추가 정보가 필요하다고 판단할 때 실행되는 평범한 Python 함수입니다. 효과적으로 작성하는 방법은 다음과 같습니다:

모범 사례

  • 잘 짓고 설명적인 인자 이름을 사용하세요 (나중에 중요해집니다)
  • 입력을 검증하고, 검증에 실패하면 에러를 발생시키세요
  • 의미 있는 에러를 반환하세요 - Claude는 에러를 받으면 함수를 한 번 더 호출해 봅니다

첫 번째 도구 만들기

가장 간단한 도구인 현재 날짜와 시각 가져오기부터 시작하겠습니다. 이 함수는 날짜 형식 매개변수를 받아 현재 타임스탬프를 반환합니다:

from datetime import datetime, timedelta

def get_current_datetime(date_format="%Y-%m-%d %H:%M:%S"):
return datetime.now().strftime(date_format)

이 함수는 간단하지만 핵심 원칙을 따릅니다: 설명적인 이름을 가지고, 합리적인 기본값을 갖춘 잘 지어진 매개변수를 받으며, 약속한 것을 정확히 반환합니다.

JSON Schema 명세

함수를 만들었다면, 그것을 Claude에게 설명하는 JSON Schema를 작성해야 합니다. 이 스키마는 함수가 어떤 인자를 필요로 하는지 Claude에게 알려주고, 도구를 언제 어떻게 사용할지 이해하도록 돕습니다.

JSON Schema는 두 가지 목적을 수행합니다: 함수가 어떤 인자를 필요로 하는지 Claude가 이해하도록 돕고, 또한 이는 LLM만의 개념이 아니라 여러 프로그래밍 맥락에서 데이터 검증에 널리 쓰이는 표준입니다. 스키마 생성을 돕는 온라인 도구도 많습니다.

스키마 모범 사례

  • 도구가 무엇을 하고, 언제 쓰며, 무엇을 반환하는지 설명하세요
  • 설명은 3~4문장을 목표로 하세요
  • 매개변수에 대해 상세한 설명을 제공하세요

도구 함수를 작성하고 스키마를 정의했다면, 이제 이를 Claude와 통합해 알림 설정 같은 실제 작업을 처리할 수 있는 더 정교한 AI 상호작용을 만들 준비가 되었습니다.

도구용 JSON 스키마

🎬 영상

도구 함수를 만든 다음 단계는 그것을 설명하는 JSON Schema를 작성하는 것입니다. 이 스키마는 함수가 어떤 인자를 기대하며 어떻게 올바르게 사용하는지를 Claude에게 알려줍니다. 설정이 처음에는 부담스러워 보일 수 있지만, 과정을 이해하고 나면 사실 간단합니다.

JSON Schema 이해하기

JSON Schema는 AI 도구를 위해 만들어진 것이 아니라, 데이터를 검증하는 표준 방식으로 수년간 존재해 왔습니다. 스키마는 두 개의 주요 부분으로 이루어집니다: 상단의 이름과 설명(도구를 언제 사용할지 Claude가 이해하도록 돕는 부분), 그리고 함수의 인자를 설명하는 실제 스키마입니다.

상단 섹션에는 도구의 이름과 설명이 담기며, 이는 Claude가 언제 사용할지 이해하도록 돕습니다. 하단 섹션은 함수의 인자를 상세히 설명하는 실제 스키마입니다.

JSON Schema 만들기: 단계별 안내

어떤 함수든 JSON Schema를 만드는 가장 간단한 방법은 다음과 같습니다:

1단계: 샘플 데이터로 딕셔너리 작성하기

함수를 놓고, 모든 키워드 인자에 샘플 데이터를 채운 딕셔너리를 만듭니다. 예를 들어 다음과 같은 함수가 있다면:

def process_data(ids, profile, primary_id, value):
pass

샘플 값으로 딕셔너리를 만듭니다:

🎬 영상

Claude가 도구 사용 요청으로 응답하면, 서버는 요청된 도구를 실제로 실행하고 결과를 되돌려 보내야 합니다. 이 단계는 Claude 응답에서 도구 사용 파트를 추출하고, 알맞은 함수를 실행하며, 결과를 올바르게 포맷하는 일을 포함합니다.

여러 도구 요청 처리하기

Claude는 한 번의 응답에 여러 개의 도구 사용 파트를 담아 보낼 수 있습니다. 코드는 이 가능성을 방어적으로 처리해야 합니다. assistant 메시지에는 텍스트 파트 뒤에 하나, 둘, 혹은 그 이상의 도구 사용 파트가 이어질 수 있습니다.

tool_result_parts = []

요청된 도구를 실행하는 헬퍼 함수를 만듭니다:

def run_tool(tool_name, tool_input):

else:

여기서 핵심은 **tool_input을 사용해 인자 딕셔너리를 도구 함수에 풀어 넣는(splat) 것입니다. Claude는 인자를 항상 딕셔너리 객체로 반환하므로 이를 제대로 언패킹해야 합니다.

🎬 영상

이제 tool use 워크플로우의 마지막 단계입니다. 도구를 실행해 결과를 얻은 뒤에는, 모든 것을 Claude에게 되돌려 보내 사용자에게 완전한 응답을 제공하도록 해야 합니다.

과정은 간단합니다: 생성한 모든 도구 결과 파트를 user 메시지로 묶고, 전체 대화 이력을 원래 도구 스키마와 함께 Claude에게 되돌려 보냅니다.

Assistant 메시지 추가하기

먼저 대화 이력이 완전한지 확인해야 합니다. 도구 사용 요청이 담긴 Claude의 초기 응답을 받은 뒤, add_assistant_message()를 사용해 그 응답을 메시지 이력에 추가해야 합니다.

이렇게 하면 완전한 대화 흐름을 갖게 됩니다: user 질문 → assistant 도구 요청 → 도구 결과 → 최종 assistant 응답.

도구 실행 및 도구 결과 생성

run_tools() 함수는 Claude 응답의 모든 도구 사용 요청을 처리하고 올바르게 포맷된 도구 결과 파트를 만듭니다. 각 도구 결과에는 다음이 포함됩니다:

  • tool use ID(원래 요청과 일치)
  • 도구 실행으로 얻은 실제 출력
  • 성공 또는 에러를 나타내는 status

이 함수는 성공적인 도구 실행과 에러를 모두 매끄럽게 처리하며, 모든 것을 Claude가 기대하는 올바른 JSON 구조로 감쌉니다.

대화에 도구 결과 추가하기

도구 결과를 얻으면 add_user_message()를 사용해 대화에 추가합니다:

add_user_message(messages, run_tools(parts))

이렇게 하면 모든 도구 결과 파트를 담은 user 메시지가 생성됩니다. 이제 대화에는 Claude가 최종 응답을 제공하는 데 필요한 완전한 왕복 내용이 담깁니다.

Claude에 최종 호출하기

마지막 단계는 모든 것을 Claude에게 되돌려 보내는 것입니다. 여기에는 두 가지 중요한 요소가 필요합니다:

  • 완전한 메시지 이력 (user → assistant → user)
  • 원래 도구 스키마
text, parts = chat(messages, tools=[get_current_datetime_schema])

도구 스키마를 포함하는 것이 매우 중요합니다. 스키마가 없으면 Claude는 대화 이력에 있는 도구 참조를 혼란스러워하며, get_current_datetime이 실제로 무엇을 하는지 이해하지 못합니다.

성공

모든 것이 올바르게 작동하면, Claude는 도구 결과를 받아 완전하고 근거 있는 응답을 제공합니다. 예시에서 Claude는 현재 시각을 성공적으로 조회하고 자연스러운 응답으로 포맷했습니다: "현재 날짜와 시각은 2025-04-03, 12:54:00입니다."

이는 도구 통합이 제대로 작동하고 있음을 보여줍니다. Claude는 현재 날짜는 알지만, 정확한 현재 시각 같은 실시간 정보에는 접근할 수 없는데, 바로 이것이 우리 도구가 제공한 부분입니다.

이제 완전한 tool use 순환이 작동합니다: Claude가 도구를 요청하고, 우리가 실행하며, 결과를 반환하면, Claude가 그 정보를 사용자에게 보내는 최종 응답에 반영합니다.

Stop Reasons

Claude는 여러 이유로 멈출 수 있습니다:

  • "tool_use" - 모델이 도구를 호출하려 함
  • "end_turn" - 모델이 응답 생성을 마침
  • "max_tokens" - 출력 한도에 도달함
  • "stop_sequence" - 제공한 정지 시퀀스를 만남

Chat 함수 개선하기

먼저 chat 함수가 더 많은 정보를 반환하도록 업데이트합니다. 텍스트와 parts를 따로 반환하는 대신, 필요한 모든 것을 담은 딕셔너리를 반환합니다:

def chat(messages, tools=None, system=None, **kwargs):
# ... existing code ...

return {
"parts": parts,
"stop_reason": response["stopReason"],
"text": "\n".join([p["text"] for p in parts if "text" in p])
}

이 방식은 응답 파트에서 모든 텍스트 콘텐츠를 추출하므로, 첫 번째 파트가 항상 텍스트라고 가정하는 것보다 견고합니다.

대화 루프 만들기

전체 대화 흐름을 처리하는 함수를 만듭니다:

def run_conversation(messages):
while True:
result = chat(messages, tools=[get_current_datetime_schema])

add_assistant_message(messages, result["parts"])
print(result["text"])

if result["stop_reason"] != "tool_use":
break

tool_result_parts = run_tools(result["parts"])
add_user_message(messages, tool_result_parts)

return messages

이 루프는 Claude가 도구 사용 이외의 이유로 멈출 때까지 계속됩니다. 각 반복은:

  • 현재 메시지를 Claude에게 보냅니다
  • Claude의 응답을 메시지 이력에 추가합니다
  • Claude가 도구를 사용하려는지 확인합니다
  • 그렇다면 도구를 실행하고 결과를 대화에 다시 추가합니다
  • 아니라면 루프를 빠져나옵니다

구현 테스트하기

이 방식은 도구가 필요한 질문과 간단한 질문을 모두 처리합니다:

# Tool-requiring question
messages = []
add_user_message(messages, "What time is it?")
run_conversation(messages)

# Simple question 
messages = []
add_user_message(messages, "What is 1+1?")
run_conversation(messages)

시간 관련 질문에는 Claude가 datetime 도구를 사용합니다. 수학 질문에는 도구 호출 없이 직접 응답합니다. 대화 루프는 Claude의 stop reason에 따라 자동으로 적응합니다.

이 패턴은 도구를 더 추가해도 잘 확장됩니다. 같은 루프가 도구 사용과 직접 응답의 어떤 조합이든 처리하여, 대화형 AI를 더 견고하고 자연스럽게 만듭니다.

여러 도구 추가

🎬 영상

이제 도구 하나가 작동하니, 프로젝트를 완성하기 위해 나머지 두 도구인 add_duration_to_datetime과 set_reminder를 추가할 차례입니다. 다행히 기반을 갖춰 놓으면 새 도구를 추가하는 일은 간단합니다.

미리 만들어진 함수와 스키마

시간을 아끼기 위해, 두 추가 함수의 구현이 JSON Schema 명세와 함께 이미 제공됩니다. 앞선 코드 셀에서 찾을 수 있습니다:

  • add_duration_to_datetime - 다양한 시간 단위에 대한 날짜 계산을 처리합니다
  • set_reminder - 알림을 생성합니다(현재는 출력만 하지만, 실제 알림 시스템과 통합하도록 확장할 수 있습니다)

각 함수에는 기대되는 매개변수와 그 타입을 정의하는 대응 JSON Schema가 함께 제공됩니다.

대화에 도구 추가하기

첫 단계는 새 도구 스키마를 대화 함수에 포함시키는 것입니다. run_conversation 함수에서 tools 배열에 추가 스키마를 넣습니다:

tools=[
get_current_datetime_schema,
add_duration_to_datetime_schema,
set_reminder_schema
]

도구 함수 연결하기

다음으로, 새 도구 이름을 처리하도록 run_tool 함수를 업데이트해야 합니다. 조건 분기 두 개를 추가합니다:

def run_tool(tool_name, tool_input):
if tool_name == "get_current_datetime":
return get_current_datetime(**tool_input)
elif tool_name == "set_reminder":
return set_reminder(**tool_input)
elif tool_name == "add_duration_to_datetime":
return add_duration_to_datetime(**tool_input)
else:
raise Exception(f"Unknown tool name: {tool_name}")

완성된 시스템 테스트하기

모든 도구를 연결했으니, 이제 여러 도구 호출이 필요한 복잡한 워크플로우를 테스트할 수 있습니다. 예를 들어 Claude에게 "병원 가는 알림을 설정해 줘. 진료는 100일 뒤야"라고 요청하면 일련의 작업이 실행됩니다:

  • get_current_datetime로 오늘 날짜를 가져옵니다
  • add_duration_to_datetime로 그 날짜에 100일을 더합니다
  • set_reminder로 알림을 생성합니다

Claude는 요청을 논리적 단계로 자동 분해하고, 각 도구 호출을 실행하기 전에 계획을 설명합니다. 출력에는 계산된 미래 날짜와 알림 설정 확인을 포함한 전체 워크플로우가 나타납니다.

핵심 정리

기반이 되는 tool use 인프라를 갖춰 놓으면, 새 도구를 추가하는 데는 두 가지 간단한 단계만 필요합니다: tools 배열에 스키마를 포함하고, 라우팅 함수에서 도구 이름을 처리하는 분기를 추가하는 것입니다. 초기 설정은 복잡하게 느껴질 수 있지만, 여러 도구로 확장하는 일은 매우 수월해집니다.

배치 도구 사용

🎬 영상

Claude는 여러 도구를 동시에 네이티브로 실행할 수 있지만, 일부 버전은 이를 기대만큼 충분히 활용하지 않습니다. batch tool을 구현하면 Claude가 한 메시지에서 여러 도구를 호출할 가능성을 크게 높일 수 있습니다.

Claude가 메시지에 도구 사용 파트를 담아 보낼 때, 한 응답에 도구 요청이 두 개 이상 있을 수 있습니다. 예를 들어 "2025년 3월 12일 + 50일은? 그리고 2025년 3월 12일 + 100일은?"이라고 물으면, 이론상 Claude는 각 계산마다 하나씩 두 개의 별도 도구 사용 파트를 보낼 수 있습니다. 이 작업들은 서로 의존하지 않으므로 완전히 병렬화할 수 있습니다.

하지만 Claude는 기대만큼 도구 호출을 항상 병렬화하려고 하지는 않습니다. 두 호출을 동시에 하는 대신 순차적으로 하는 경우가 많은데, 이는 효율이 떨어집니다.

Batch Tool의 동작 방식

batch tool은 다른 도구와 똑같이 구현됩니다. 즉, 도구 명세와 호출 시 처리할 함수가 필요합니다. 핵심 아이디어는 여러 다른 도구를 동시에 호출할 수 있는 도구를 만드는 것입니다.

batch tool 명세의 기본 구조는 다음과 같습니다:

{
"name": "batch_tool",
"description": "Invoke multiple other tool calls simultaneously",
"input_schema": {
"type": "object",
"properties": {
"invocations": {
"type": "array",
"description": "The tool calls to invoke",
"items": {
"type": "object",
"properties": {
"name": {
"type": "string",
"description": "The name of the tool to invoke"
},
"arguments": {
"type": "string", 
"description": "The arguments to the tool, encoded as a JSON string"
}
},
"required": ["name", "arguments"]
}
}
},
"required": ["invocations"]
}
}

이 도구는 invocation 목록을 받으며, 각 invocation에는 호출할 도구의 이름과 인자(JSON 문자열로 인코딩)가 담깁니다.

구현

batch tool 구현은 두 개의 주요 함수로 이루어집니다:

run_batch 함수

def run_batch(tool_input):
batch_output = []
for invocation in tool_input["invocations"]:
tool_name = invocation["name"]
args = json.loads(invocation["arguments"])

tool_output = run_tool(tool_name, args)
batch_output.append({"tool_name": tool_name, "output": tool_output})

return batch_output

이 함수는 각 invocation을 순회하며 도구 이름과 인자를 추출하고, 기존 run_tool 함수로 알맞은 도구를 호출한 뒤 모든 결과를 모읍니다.

run_tool에 추가하기

메인 run_tool 함수에도 분기를 추가해야 합니다:

elif tool_name == "batch_tool":
return run_batch(tool_input)

다른 도구와 달리, batch tool은 원시 입력 구조를 직접 다뤄야 하므로 splat 연산자(**) 없이 tool_input을 그대로 전달한다는 점에 유의하세요.

결과

batch tool을 구현하고 동일한 날짜 계산 질의를 실행하면, 메시지 로그에 두 개의 별도 도구 호출이 아니라 batch tool에 대한 단일 호출이 나타납니다. 이 단일 호출은 두 날짜 계산을 하위 invocation으로 담아 작업을 효과적으로 병렬화합니다.

batch tool은 동시에 실행할 수 있는 독립적인 작업이 여러 개 있을 때 특히 유용합니다. Claude가 이 패턴을 사용하도록 "유도"함으로써 도구 호출 워크플로우의 효율을 크게 개선할 수 있습니다.

도구로 구조화 데이터

🎬 영상

이 강의 앞부분에서 메시지 프리필(pre-fill)과 정지 시퀀스를 사용해 Claude로부터 구조화된 출력을 얻는 방법을 다뤘습니다. 그 방식도 잘 작동하고 설정이 쉽지만, 도구를 사용하면 더 안정적인 출력을 얻을 수 있습니다. 이 방법은 구현이 더 복잡하지만, JSON 같은 구조화된 데이터를 추출할 때 더 나은 일관성을 제공합니다.

왜 두 방식을 모두 배우는가?

도구가 더 안정적이라면 왜 처음부터 도구로 시작하지 않았는지 궁금할 수 있습니다. 답은 간단합니다: 도구는 훨씬 많은 설정과 복잡성이 필요합니다. 두 기법을 모두 갖추면 유연성이 생깁니다. 때로는 빠른 프롬프트 기반 방식을 원하고, 때로는 도구가 제공하는 안정성이 필요할 것입니다.

도구 기반 구조화 출력의 동작 방식

핵심 개념은 간단합니다: Claude에게 응답을 JSON으로 포맷하라고 요청하는 대신, 추출하려는 데이터의 정확한 구조와 일치하는 입력 매개변수를 가진 도구를 만드는 것입니다. 그러면 Claude는 추출한 데이터를 인자로 하여 이 도구를 "호출"합니다.

과정은 다음과 같습니다:

  • 원하는 데이터 구조를 설명하는 JSON Schema를 작성합니다
  • 그 스키마를 입력 명세로 하는 도구를 만듭니다
  • 데이터와 도구 스키마를 Claude에게 보냅니다
  • toolChoice 매개변수로 Claude가 도구를 사용하도록 강제합니다
  • 도구 호출 인자에서 구조화된 데이터를 추출합니다

흐름은 이렇습니다: 서버가 데이터를 분석하고 특정 도구를 호출하라는 프롬프트를 Claude에게 보냅니다. Claude는 추출한 JSON 데이터가 담긴 도구 사용 메시지로 응답합니다. 이 시점에서 데이터를 받아 대화를 끝내면 됩니다. 후속 처리는 필요 없습니다.

도구 사용 제어하기

구조화된 출력에 도구를 사용할 때는 Claude가 반드시 추출 도구를 사용하도록 보장하고 싶을 것입니다. toolChoice 매개변수는 세 가지 옵션을 제공합니다:

  • {"toolChoice": {"auto": {}}} - 모델이 도구 사용 필요 여부를 결정합니다 (기본값)
  • {"toolChoice": {"any": {}}} - 모델은 반드시 도구를 사용하되, 어떤 도구를 쓸지는 선택할 수 있습니다
  • {"toolChoice": {"tool": {"name": "tool-name"}}} - 모델은 반드시 지정된 도구를 사용합니다

구조화된 출력에서는 Claude가 추출 도구를 사용하도록 보장하기 위해 거의 항상 세 번째 옵션을 쓰게 됩니다.

실전 예시

기사에서 제목, 저자, 핵심 주제를 추출하고 싶다고 합시다. 먼저 도구 스키마를 만듭니다:

article_details_schema = {
"toolSpec": {
"name": "article_details",
"description": "Extracts key information from an article",
"inputSchema": {
"json": {
"type": "object",
"properties": {
"title": {
"type": "string",
"description": "The title of the article"
},
"author": {
"type": "string", 
"description": "The author's name"
},
"topics": {
"type": "array",
"items": {"type": "string"},
"description": "List of key topics mentioned"
}
},
"required": ["title", "author", "topics"]
}
}
}
}

그런 다음 데이터와 함께 Claude를 호출하고 도구를 사용하도록 강제합니다:

messages = []

Analyze the article below and extract key data. Then call the article_details tool.

<article_text>
{article_text}
</article_text>

Claude는 지정한 정확한 형식으로 추출된 데이터가 담긴 도구 사용 메시지로 응답합니다. 도구 호출 인자에는 애플리케이션에서 바로 사용할 수 있는 구조화된 JSON 데이터가 담깁니다.

핵심 장점

  • 프롬프트 기반 추출보다 안정적
  • 스키마와 일치하는 구조가 보장됨
  • 메시지 프리필이나 정지 시퀀스가 필요 없음
  • 도구 스키마를 통한 내장 검증

주된 단점은 복잡성입니다. 상세한 스키마를 작성하고 도구 응답을 처리해야 합니다. 하지만 일관되고 안정적인 구조화된 출력이 필요할 때는 도구가 정답입니다.

유연한 도구 추출

🎬 영상

구조화된 데이터 추출을 위해 상세한 JSON Schema를 작성하는 일은 AI 도구를 다룰 때 실질적인 골칫거리가 될 수 있습니다. 복잡한 스키마를 만드는 대신, 원하는 데이터 구조를 프롬프트에 직접 지정하도록 해 주는 영리한 우회책이 있습니다.

유연한 스키마 방식

모든 데이터 추출 작업마다 상세한 스키마를 작성하는 대신, 어떤 객체 구조든 받아들이는 to_json이라는 범용 도구 하나를 만들 수 있습니다. 핵심은 입력 스키마가 추가 속성을 허용하도록 설정한 뒤, 정확한 요구 사항을 프롬프트 자체에 지정하는 것입니다.

이 방식은 큰 JSON Schema를 끊임없이 작성하고 관리해야 하는 주요 골칫거리를 없애 줍니다. 결과가 전용 스키마만큼 좋지는 않지만, 훨씬 적은 설정 작업으로도 여전히 고품질의 JSON 출력을 얻을 수 있습니다.

동작 방식

과정은 간단합니다:

  • 어떤 객체 구조든 받아들이는 하나의 유연한 스키마를 만듭니다
  • 프롬프트에 원하는 데이터 구조를 정확히 지정합니다
  • Claude에게 지정한 구조로 to_json 도구를 호출하라고 지시합니다
  • tool_choice를 사용해 Claude가 도구를 사용하도록 강제합니다

프롬프트 구성하기

{{

}}

손쉬운 구조 변경

진짜 장점은 데이터 구조를 수정해야 할 때 분명해집니다. 스키마 전체를 다시 작성하는 대신, 프롬프트만 업데이트하면 됩니다. 주제 개수를 나타내는 필드를 추가하고 싶다면? 한 줄만 추가하면 됩니다:

"num_topics": int # Number of topics mentioned

이게 전부입니다. 스키마 수정은 필요 없습니다.

각 방식을 언제 사용할까

유연한 스키마 방식은 다음에 적합합니다:

  • 빠른 프로토타이핑과 실험
  • 단순한 데이터 추출 작업
  • 데이터 요구 사항이 자주 바뀌는 상황

다음의 경우에는 전용 스키마를 고수하세요:

  • 중요한 프로덕션 데이터 추출 작업
  • 복잡한 중첩 데이터 구조
  • 가능한 한 높은 정확도가 필요할 때

유연한 방식은 설정 작업의 10%로 품질의 약 90%를 제공하므로, 스키마 관리 부담 없이 구조화된 데이터 추출이 필요한 대부분의 사용 사례에 완벽합니다.

RAG 소개

🎬 영상

RAG(검색 증강 생성, Retrieval Augmented Generation)는 큰 문서를 작은 조각으로 나누고, 각 질문에 대해 가장 관련 있는 chunk만 Claude에 전달함으로써 대용량 문서를 다루도록 도와주는 기법입니다. 800페이지짜리 재무 보고서 전체를 모델에 쏟아붓는 대신, RAG를 사용하면 특정 질문에 답하는 데 필요한 섹션만 뽑아낼 수 있습니다.

대용량 문서의 문제

거대한 문서를 두고 Claude에게 구체적인 질문을 하려고 할 때, 근본적인 어려움에 부딪힙니다. 어떻게 하면 한계에 부딪히거나 성능을 떨어뜨리지 않으면서 적절한 정보를 Claude에 전달할 수 있을까요?

긴 재무 문서를 두고 "이 회사에는 어떤 위험 요인이 있나요?"라고 묻는 상황을 생각해 보세요. 답은 문서 안에 있지만, Claude가 도움을 주려면 관련 내용에 접근할 수 있어야 합니다.

방법 1: 모든 내용을 프롬프트에 넣기

가장 단순한 접근은 문서에서 모든 텍스트를 추출해 하나의 프롬프트에 밀어 넣는 것입니다.

이 방식에는 심각한 한계가 있습니다.

  • 엄격한 토큰 제한 때문에 아주 긴 문서는 아예 들어가지 않습니다
  • 프롬프트가 지나치게 길어지면 Claude의 성능이 떨어집니다
  • 프롬프트가 커질수록 비용이 늘고 처리 시간도 길어집니다
  • 걸러내야 할 정보가 너무 많으면 성능이 저하됩니다

방법 2: 문서를 chunk로 나누기

RAG는 문서를 다루기 좋은 크기로 미리 전처리한 뒤, 각 질문에 관련 있는 chunk만 검색해 오는 더 똑똑한 접근을 취합니다.

동작 방식은 다음과 같습니다.

  • 문서를 더 작은 chunk로 분할합니다(전략 전망, 위험 요인, 대차대조표 등)
  • 사용자가 질문하면 무엇을 찾고 있는지 분석합니다
  • 질문에 가장 관련 있는 chunk를 찾습니다
  • 그 관련 chunk만 Claude 프롬프트에 포함합니다

회사의 위험에 관한 질문이라면, 시스템은 "위험 요인" chunk를 식별해 검색해 오고, 문서 전체 대신 초점이 맞춰진 관련 컨텍스트를 Claude에 제공합니다.

RAG의 장점

  • Claude가 가장 관련 있는 내용에만 집중할 수 있습니다
  • 매우 큰 문서와 여러 문서로 확장됩니다
  • 단일 파일뿐 아니라 문서 모음 전체에 걸쳐 작동합니다
  • 프롬프트가 작아지므로 처리가 빨라지고 비용이 줄어듭니다

RAG의 과제

RAG는 관리해야 할 복잡성을 함께 가져옵니다.

  • 문서를 chunk로 나누는 전처리 단계가 필요합니다
  • 관련 chunk를 찾는 검색 메커니즘이 필요합니다
  • 검색된 chunk에 필요한 컨텍스트가 모두 담겨 있지 않을 수 있습니다
  • 텍스트를 나누는 방법이 아주 다양한데, 어떤 방식이 가장 좋을까요?

문서는 균등한 크기로, 헤더와 섹션 단위로, 의미(semantic) 단위로, 또는 다른 전략으로 나눌 수 있습니다. 각 방식에는 trade-off가 있으며, 자신의 use case에 맞게 평가해야 합니다.

언제 RAG를 사용할까

RAG는 큰 문서나 문서 모음을 다루면서 사용자가 내용의 일부만 필요로 하는 구체적인 질문을 던질 때 빛을 발합니다. 단일 프롬프트에 담기는 한계를 넘어 확장해야 할 때, 더 빠른 응답을 원할 때, 또는 많은 질의에 걸쳐 비용을 관리해야 할 때, 전처리의 복잡성은 그만한 값어치를 합니다.

핵심은 chunking, 검색, 검색 결과 활용을 구현하는 기술적 부담이 자신의 애플리케이션에 합당한지 따져 보는 것입니다. 때로는 "모든 것을 프롬프트에 넣는" 단순한 방식으로 충분하지만, 어떤 경우에는 시스템을 실용적이고 성능 있게 만들기 위해 RAG가 필수가 됩니다.

텍스트 청킹 전략

🎬 영상

텍스트 chunking은 RAG(검색 증강 생성) 파이프라인을 구축할 때 가장 중요한 단계 중 하나입니다. 문서를 어떻게 나누느냐가 전체 시스템의 품질을 직접 좌우합니다. 잘못된 chunking 전략은 관련 없는 컨텍스트가 프롬프트에 삽입되게 만들어, AI가 완전히 틀린 답을 내놓게 할 수 있습니다.

이런 예를 생각해 보세요. 의학 연구와 소프트웨어 엔지니어링 섹션이 있는 문서가 있습니다. chunking이 잘못되면, "올해 엔지니어가 버그를 몇 개나 고쳤나요?"라고 묻는 사용자가 소프트웨어 엔지니어링이 아니라 의학 연구에 관한 정보를 받을 수 있습니다. 단지 의학 섹션이 다른 맥락에서 "bug"라는 단어를 담고 있었다는 이유만으로 말이죠.

이것이 chunking 전략이 그토록 중요한 이유입니다. 목표는 의미적 일관성을 유지하고, 검색되었을 때 유용한 컨텍스트를 제공하는 chunk를 만드는 것입니다.

주요 chunking 전략 세 가지

텍스트를 chunk로 나누는 주요 접근법은 세 가지입니다.

  • 크기 기반: 텍스트를 동일한 길이의 문자열로 나눕니다
  • 구조 기반: 문서 구조(헤더, 문단, 섹션)를 기준으로 나눕니다
  • 의미(semantic) 기반: NLP 기법으로 관련 있는 문장이나 섹션을 묶습니다

크기 기반 chunking

크기 기반 chunking은 가장 단순한 접근입니다. 문서를 대략 비슷한 문자 수 또는 단어 수의 chunk로 나누기만 하면 됩니다. 구현이 쉽고 다양한 문서 유형에서 안정적으로 작동합니다.

다만 이 방식에는 분명한 단점이 있습니다.

  • 문장 중간에서 단어가 잘립니다
  • chunk가 주변 텍스트의 중요한 컨텍스트를 잃습니다
  • 관련 있는 내용이 여러 chunk로 쪼개질 수 있습니다

중첩(overlap) 추가하기

컨텍스트 문제를 해결하려면 overlap 전략을 적용할 수 있습니다. 각 chunk가 이웃한 chunk의 문자 일부를 포함하도록 하여, 추가적인 컨텍스트를 제공하고 chunk 경계에서 중요한 정보가 사라지지 않도록 합니다.

약간의 중복이 생기긴 하지만, 각 chunk가 얻는 컨텍스트 향상을 생각하면 대개 그만한 trade-off의 가치가 있습니다.

구조 기반 chunking

문서에 일관된 서식(예: 명확한 헤더를 가진 markdown)이 있다면, 구조 기반 chunking이 훌륭한 결과를 낼 수 있습니다. 헤더 같은 구조적 요소를 기준으로 나누어, 문서의 자연스러운 구성에 맞는 chunk를 만듭니다.

서식이 잘 갖춰진 문서에서는 아주 훌륭하게 작동하지만, 문서 구조가 보장되어야 합니다. 일반 텍스트 파일이나 서식이 일관되지 않은 문서에서는 안정적으로 작동하지 않습니다.

구현 예시

실제로 구현할 수 있는 chunking 함수 세 가지를 소개합니다.

문자 기반 chunking

def chunk_by_char(text, chunk_size=150, chunk_overlap=20):
chunks = []
start_idx = 0

while start_idx < len(text):
end_idx = min(start_idx + chunk_size, len(text))
chunk_text = text[start_idx:end_idx]
chunks.append(chunk_text)

start_idx = (
end_idx - chunk_overlap if end_idx < len(text) else len(text)
)

return chunks

문장 기반 chunking

def chunk_by_sentence(text, max_sentences_per_chunk=5, overlap_sentences=1):
sentences = re.split(r"(?<=[.!?])\s+", text)
chunks = []
start_idx = 0

while start_idx < len(sentences):
end_idx = min(start_idx + max_sentences_per_chunk, len(sentences))
current_chunk = sentences[start_idx:end_idx]
chunks.append(" ".join(current_chunk))

start_idx += max_sentences_per_chunk - overlap_sentences

if start_idx < 0:
start_idx = 0

return chunks

섹션 기반 chunking

def chunk_by_section(document_text):
pattern = r"\n## "
return re.split(pattern, document_text)

어떤 chunking 전략을 선택할지는 전적으로 use case에 달려 있습니다.

  • 문자 기반: 가장 안정적인 fallback으로, 어떤 문서 유형에도 작동합니다
  • 문장 기반: 산문에 대해 컨텍스트와 의미의 균형이 좋습니다
  • 섹션 기반: 구조화된 문서가 있을 때 훌륭한 결과를 냅니다

서식이 보장되지 않는, 사용자가 업로드한 문서라면 문자 기반 chunking이 가장 안전한 선택인 경우가 많습니다. 잘 구조화된 사내 문서라면 섹션 기반 chunking이 더 나은 결과를 줄 수 있습니다. 문장 기반 chunking은 대부분의 산문에서 잘 작동하지만, 마침표를 예상치 못한 방식으로 사용하는 코드나 기술 문서에서는 어려움을 겪을 수 있습니다.

chunking은 대개 반복적인 과정임을 기억하세요. 단순한 접근으로 시작해 자신의 문서와 use case로 테스트한 뒤, RAG 시스템에서 얻는 결과 품질을 바탕으로 다듬어 나가세요.

텍스트 임베딩

🎬 영상

문서를 chunk로 나눈 뒤, RAG 파이프라인의 다음 단계는 사용자의 질문과 가장 관련 있는 chunk가 무엇인지 찾는 것입니다. 이는 본질적으로 검색 문제입니다. 모든 텍스트 chunk를 살펴보고 사용자가 묻는 내용과 관련된 것을 골라내야 합니다.

관련 chunk 찾기

어려운 점은 어떤 chunk가 사용자의 질문과 "관련 있는지" 판단하는 것입니다. 이는 키워드 매칭처럼 단순하지 않습니다. 질문과 chunk 양쪽의 의미와 맥락을 이해해야 합니다.

가장 일반적인 해법은 semantic search입니다. 정확한 단어 일치를 찾는 대신, text embedding을 사용해 각 텍스트가 실제로 무엇에 관한 것인지 이해합니다.

Text embedding이란?

text embedding은 어떤 텍스트에 담긴 의미를 숫자로 표현한 것입니다. 단어와 문장을 컴퓨터가 수학적으로 다룰 수 있는 형태로 변환하는 것이라고 생각하면 됩니다.

동작 방식은 다음과 같습니다.

  • 텍스트를 embedding 모델에 넣습니다
  • 모델은 긴 숫자 목록을 출력합니다(보통 1024개의 숫자)
  • 각 숫자는 입력 텍스트의 어떤 특성에 대한 "점수"를 나타냅니다
  • 숫자의 범위는 -1에서 +1까지입니다

숫자 이해하기

embedding의 각 숫자는 텍스트의 어떤 측면에 대한 점수와 같습니다. 각 위치가 정확히 무엇을 나타내는지는 알 수 없지만, 서로 다른 특성을 측정한다고 생각하면 도움이 됩니다.

예를 들어 어떤 숫자는 "텍스트가 얼마나 행복한지"를, 다른 숫자는 "텍스트가 바다에 대해 얼마나 이야기하는지"를 나타낼 수 있습니다. 핵심은 각 숫자가 실제로 무엇을 나타내는지 우리가 알지 못한다는 점입니다. embedding 모델은 학습 과정에서 이런 패턴을 익히며, 그 값은 사람이 해석할 수 있는 것이 아닙니다.

코드로 embedding 생성하기

embedding을 만드는 일은 간단합니다. 기본 절차는 다음과 같습니다.

def generate_embedding(
text,
embedding_model_id="amazon.titan-embed-text-v2:0",
dimensions=1024,
normalize=True,
):
request_body = {
"inputText": text,
"dimensions": dimensions,
"normalize": normalize,
}

request_json = json.dumps(request_body)
response = client.invoke_model(
modelId=embedding_model_id,
body=request_json,
accept="application/json",
contentType="application/json",
)

response_body = json.loads(response.get("body").read())
return response_body["embedding"]

이 함수를 텍스트 chunk에 실행하면, 해당 텍스트의 의미를 나타내는 1024개의 숫자 목록을 돌려받습니다.

참고로 AWS Bedrock 콘솔에서 Titan embedding 모델에 대한 접근 권한을 요청해야 할 수 있습니다. 버전 2를 사용할 수 없다면, 학습 목적으로는 버전 1도 똑같이 잘 작동합니다.

embedding이 RAG에서 중요한 이유

비슷한 텍스트는 비슷한 embedding 값을 가진다는 점을 깨달으면 embedding의 위력이 분명해집니다. 즉, 사용자의 질문을 문서 chunk와 수학적으로 비교해, 정확히 같은 단어를 공유하지 않더라도 의미적으로 가장 유사한 것을 찾을 수 있습니다.

이 숫자 표현이 바로 semantic search를 가능하게 하며, RAG 시스템에서 관련 컨텍스트를 찾을 때 단순한 키워드 매칭보다 훨씬 효과적입니다.

전체 RAG 흐름

🎬 영상

이제 RAG의 기초, 텍스트 chunking, embedding을 살펴봤으니, 전체 RAG 파이프라인을 단계별로 짚어 보겠습니다. 이 상세한 예시는 실제 구현에서 모든 조각이 어떻게 맞물리는지를 정확히 보여 줍니다.

1단계: 원본 텍스트를 chunk로 나누기

먼저 원본 문서를 가져와 다루기 좋은 chunk로 나눕니다. 이 예시에서는 간단한 두 개의 텍스트 섹션을 사용합니다.

  • 섹션 1: 의학 연구 - "올해 우리는 이전에 본 적 없는 'bug'인 XDR-47에 대한 이해에서 상당한 진전을 이뤘다."
  • 섹션 2: 소프트웨어 엔지니어링 - "이 부서는 분산 시스템의 다양한 감염 벡터(infection vector)를 연구하는 데 상당한 노력을 기울였다"

2단계: embedding 생성하기

다음으로 각 텍스트 chunk를 숫자 embedding으로 변환합니다. 개념을 명확히 하기 위해, 항상 정확히 두 개의 숫자를 반환하고 각 숫자가 무엇을 의미하는지 우리가 아는 완벽한 embedding 모델이 있다고 상상해 봅시다.

이 가상의 모델에서는 이렇습니다.

  • 첫 번째 숫자: 텍스트가 의학 분야에 대해 얼마나 이야기하는지
  • 두 번째 숫자: 텍스트가 소프트웨어 엔지니어링에 대해 얼마나 이야기하는지

그래서 의학 연구 섹션은 [0.97, 0.34] 라는 embedding을 얻습니다. 매우 의학적이면서, "bug"라는 단어 때문에 소프트웨어와도 다소 관련이 있습니다. 소프트웨어 엔지니어링 섹션은 [0.30, 0.97] 을 얻는데, 매우 소프트웨어 중심이지만 "infection vector"에는 의학적 뉘앙스가 있습니다.

정규화(Normalization)

이 embedding을 저장하기 전에, 각 벡터의 크기를 1.0으로 맞추는 normalize 과정을 거칩니다. 보통 embedding API가 자동으로 처리하지만, 이런 과정이 일어난다는 것을 이해해 두는 것이 중요합니다.

normalize 이후 embedding은 [0.944, 0.331] 과 [0.295, 0.955] 가 됩니다. 이들은 각 점이 정확히 원의 가장자리에 놓이는 단위원 위에 시각화할 수 있습니다.

3단계: vector database에 저장하기

normalize된 embedding은 vector database에 저장됩니다. vector database는 우리의 embedding처럼 긴 숫자 목록을 저장하고, 비교하고, 검색하는 데 최적화된 특수 데이터베이스입니다.

여기서 잠시 멈춥니다. 지금까지의 작업은 모두 사전에 이뤄지는 전처리였습니다. 이제 사용자가 질의를 보내기를 기다립니다.

4단계: 사용자 질의 처리하기

사용자가 "회사가 궁금해요. 특히 소프트웨어 엔지니어링 부서가 올해 무엇을 했나요?" 같은 질문을 하면, 그 질의를 동일한 embedding 모델에 통과시킵니다.

이 질의는 [0.1, 0.89] 로 embedding됩니다. 의학 점수는 낮고 소프트웨어 엔지니어링 점수는 높습니다. normalize 이후에는 [0.112, 0.993] 가 됩니다.

5단계: 유사한 embedding 찾기

이제 vector database에 요청합니다. "이 사용자 질의 embedding에 가장 가까운, 저장된 embedding을 찾아라." 데이터베이스는 가장 유사하기 때문에 소프트웨어 엔지니어링 섹션을 반환합니다.

유사도의 원리: cosine similarity

vector database는 어떤 embedding이 가장 유사한지 판단할 때 cosine similarity를 사용합니다. 이는 두 벡터 사이 각도의 코사인 값을 측정합니다.

cosine similarity의 핵심 사항입니다.

  • 결과 범위는 -1에서 1까지입니다
  • 1에 가까울수록 매우 유사합니다
  • 0에 가까울수록 수직(관련 없음)입니다
  • -1에 가까울수록 완전히 반대입니다

계산에는 내적 공식이 사용됩니다: cos(a) = (A · B) / (||A|| · ||B||)

이 예시에서 사용자 질의는 소프트웨어 엔지니어링 chunk와 0.983의 cosine similarity를, 의학 연구 chunk와는 0.398의 값을 가집니다. 소프트웨어 엔지니어링 chunk가 확실히 더 나은 매치입니다.

Cosine distance

vector database 문서에서 "cosine distance"를 자주 보게 됩니다. 이는 단순히 1 - cosine similarity 로, 해석하기 더 쉬운 값을 줍니다.

  • 0에 가까울수록 유사도가 높습니다
  • 값이 클수록 유사도가 낮습니다

6단계: 최종 프롬프트 구성하기

마지막으로 사용자의 질문과, 찾아낸 가장 관련 있는 텍스트 chunk를 가져와 Claude용 프롬프트로 결합합니다.

이 프롬프트에는 사용자의 질문과 문서에서 가져온 관련 컨텍스트가 함께 담겨, Claude가 우리의 knowledge base에 있는 구체적인 정보를 바탕으로 근거 있는 답을 내놓을 수 있게 합니다.

전체 흐름

처음부터 끝까지 이어지는 RAG 파이프라인 전체입니다.

  • 원본 문서를 chunk로 나눕니다
  • 각 chunk에 대한 embedding을 생성합니다
  • embedding을 vector database에 저장합니다
  • 사용자가 질문하면 그 질의를 embedding합니다
  • cosine similarity로 가장 유사한, 저장된 embedding을 찾습니다
  • 관련 chunk를 사용자의 질문과 함께 프롬프트에 추가합니다
  • 보강된 프롬프트를 Claude에 보내 응답을 받습니다

이 과정과 그 뒤의 수학을 이해하면 vector database를 효과적으로 다루고, RAG 시스템이 기대한 결과를 내놓지 않을 때 문제를 디버깅하는 데 도움이 됩니다.

RAG 흐름 구현

🎬 영상

이 실습에서는 실제 예시를 통해 전체 RAG(검색 증강 생성) 구현을 보여 줍니다. vector database를 처음부터 만들고, 샘플 보고서 문서로 RAG 워크플로의 다섯 단계를 모두 실행해 봅니다.

vector database 준비하기

이 구현은 embedding 저장과 유사도 검색을 처리하는 커스텀 VectorIndex 클래스를 사용합니다. 이 클래스는 vector database 작업에 필요한 핵심 기능을 제공합니다.

다섯 단계 RAG 구현

1단계: 섹션 단위로 텍스트 나누기

먼저 앞서 본 것과 동일한 섹션 기반 chunking 방식으로 원본 문서를 불러와 나눕니다.

with open("./report.md", "r") as f:
text = f.read()

chunks = chunk_by_section(text)

이렇게 하면 보고서가 독립적으로 처리할 수 있는 논리적 섹션으로 나뉩니다.

2단계: 각 chunk에 대한 embedding 생성하기

다음으로 리스트 컴프리헨션을 사용해 모든 chunk에 대한 embedding을 만듭니다.

embeddings = [generate_embedding(chunk) for chunk in chunks]

이 단계는 여러 번의 API 호출을 포함하므로 완료까지 시간이 다소 걸립니다. 각 chunk가 숫자 벡터 표현으로 변환됩니다.

3단계: vector database에 embedding 저장하기

이제 vector store를 만들고 embedding과 그에 연결된 텍스트를 함께 채웁니다.

store = VectorIndex()

for embedding, chunk in zip(embeddings, chunks):
store.add_vector(embedding, {"content": chunk})

여기서 핵심은 embedding과 원본 텍스트를 함께 저장한다는 점입니다. 숫자 목록만 돌려받는 것은 쓸모가 없습니다. 그 embedding에 대응하는 실제 텍스트 내용이 필요합니다. 이 메타데이터 덕분에 나중에 의미 있는 결과를 가져올 수 있습니다.

4단계: 사용자 질의 embedding 생성하기

사용자가 질문하면 이를 동일한 embedding 형식으로 변환합니다.

user_embedding = generate_embedding("What did the software engineering dept do last year?")

이렇게 하면 저장된 embedding과 비교할 수 있는, 사용자 질문의 벡터 표현이 만들어집니다.

5단계: 관련 chunk 검색해 가져오기

마지막으로 vector store를 검색해 가장 유사한 내용을 찾습니다.

results = store.search(user_embedding, 2)

for doc, distance in results:
print(distance, "\n", doc["content"][0:200], "\n")

이는 가장 관련 있는 두 chunk를 cosine distance 점수와 함께 반환합니다. distance가 낮을수록 유사도가 높습니다.

결과 이해하기

검색은 관련도 순으로 정렬된 결과를 반환합니다. 이 예시에서는 소프트웨어 엔지니어링 섹션이 가장 낮은 distance(0.71)를 기록해 가장 관련 있는 매치가 되었습니다. 방법론 섹션이 distance 0.72로 그다음이었습니다.

distance 지표는 시스템이 각 결과의 관련성에 대해 얼마나 확신하는지 파악하는 데 도움이 됩니다. distance가 가까울수록 사용자 질의에 더 잘 맞는 매치입니다.

텍스트를 embedding과 함께 저장하는 이유

중요한 설계 결정은 각 embedding 옆에 원본 텍스트를 함께 저장하는 것입니다. 이것이 없으면 숫자 배열만 돌려받게 되는데, 이는 응답을 생성하는 데 쓸모가 없습니다. 원본 텍스트를 포함하면, 검색된 chunk를 바로 언어 모델의 컨텍스트로 사용할 수 있습니다.

이것으로 핵심 RAG 워크플로가 완성됩니다. 다만 실제 환경에서 성능을 높일 수 있는 추가 최적화와 개선 방법도 있습니다.

BM25 어휘 검색

🎬 영상

RAG 파이프라인을 구축하다 보면, semantic search만으로는 항상 최선의 결과가 나오지 않는다는 사실을 금방 알게 됩니다. 때로는 semantic search가 놓칠 수 있는 정확한 키워드 일치가 필요합니다. 해법은 BM25라는 기법으로 semantic search와 lexical search를 결합하는 것입니다.

semantic search만 쓸 때의 문제

문서에서 "INC-2023-Q4-011" 같은 특정 사건 ID를 검색한다고 해 봅시다. 이 정확한 용어가 관련 섹션에 여러 번 등장하는데도, semantic search는 의미적으로 유사해 보이지만 실제로는 필요한 특정 정보를 담고 있지 않은, 관련 없는 섹션을 반환할 수 있습니다.

이는 semantic search가 정확한 텍스트 일치보다 의미에 집중하기 때문에 일어납니다. 정밀한 키워드 매칭이 필요할 때는 다른 접근이 필요합니다.

하이브리드 검색 전략

해법은 semantic search와 lexical search를 병렬로 실행한 뒤 결과를 병합하는 것입니다. 이렇게 하면 두 방식의 장점을 모두 얻습니다.

  • semantic search - embedding을 사용해 개념적으로 관련 있는 내용을 찾습니다
  • lexical search - 고전적인 텍스트 검색으로 정확한 키워드 일치를 찾습니다
  • 병합된 결과 - 두 방식을 결합해 전반적인 관련성을 높입니다

BM25의 원리

BM25(Best Match 25)는 RAG 파이프라인에서 lexical search에 널리 쓰이는 알고리즘입니다. 검색 질의를 처리하는 방식은 다음과 같습니다.

이 알고리즘은 다음 핵심 단계를 따릅니다.

  • 질의를 토큰화 - 사용자의 질문을 개별 용어로 나눕니다
  • 용어 빈도 계산 - 각 용어가 전체 문서에서 얼마나 자주 나타나는지 봅니다
  • 희소성으로 용어에 가중치 부여 - 덜 자주 쓰이는 용어일수록 더 높은 중요도 점수를 받습니다
  • 문서 점수 매기기 - 가중치가 높은 용어를 더 많이 담은 텍스트 chunk를 찾습니다

핵심은 "INC-2023-Q4-011" 같은 희소한 용어가 "a"나 "the" 같은 흔한 단어보다 검색 관련성에 훨씬 더 중요하다는 점입니다.

BM25 검색 구현하기

BM25 검색 시스템을 설정하는 방법은 다음과 같습니다.

# Create a BM25 store

# Search the store

더 나은 검색 결과

semantic search만으로는 실패했던 동일한 질의를 BM25로 실행하면 훨씬 더 나은 결과를 얻습니다. 이 알고리즘은 정확한 사건 ID를 담은 섹션을 올바르게 우선시하여, 의미적으로는 관련 있어 보이지만 찾는 특정 용어를 담고 있지 않은 섹션보다 높은 순위에 둡니다.

이제 검색 결과는 Financial Analysis 같은 관련 없는 내용을 반환하는 대신, 사건을 실제로 다루는 소프트웨어 엔지니어링 섹션과 사이버보안 섹션을 제대로 드러냅니다.

🎬 영상

semantic search(vector embedding)와 lexical search(BM25)가 각각 독립적으로 동작하게 되면, 다음 단계는 이 둘을 하나의 통합 검색 파이프라인으로 결합하는 것입니다. 이 하이브리드 접근은 두 방식의 강점을 활용해 더 정확한 결과를 제공합니다.

통합 인터페이스 만들기

두 검색 구현은 거의 동일한 API를 공유합니다. 둘 다 add_document() 와 search() 메서드를 갖습니다. 이 일관성 덕분에 두 방식을 조율하는 하나의 Retriever 클래스로 감싸기가 수월합니다.

Retriever는 다음과 같은 조율자 역할을 합니다.

  • 사용자의 질문을 받습니다
  • 이를 VectorIndex와 BM25Index 양쪽에 전달합니다
  • 두 시스템의 결과를 수집합니다
  • 랭킹 알고리즘으로 결과를 병합합니다

Reciprocal Rank Fusion

어려운 점은 서로 다른 검색 방식의 결과를 병합하는 데 있습니다. 각 시스템은 서로 다른 채점 방식으로 결과를 반환하므로, 점수를 그대로 단순히 합칠 수는 없습니다. 대신 Reciprocal Rank Fusion(RRF)이라는 기법을 사용합니다.

실제 예시로 RRF의 동작을 살펴보겠습니다. VectorIndex가 섹션 2, 섹션 7, 섹션 6 순으로 결과를 반환한다고 가정합시다. 한편 BM25Index는 섹션 6, 섹션 2, 섹션 7 순으로 반환합니다.

이 결과를 병합하기 위해, 각 텍스트 chunk가 두 시스템에서 받은 순위를 보여 주는 통합 표를 만듭니다.

RRF 공식은 각 문서에 대한 점수를 계산합니다.

RRF_score(d) = Σ(1 / (k + rank_i(d)))

여기서 k 는 상수이며(보통 60이지만, 결과를 더 뚜렷이 보려면 1도 잘 작동합니다), rank_i(d) 는 i번째 랭킹 시스템에서 문서 d 의 순위입니다.

각 텍스트 chunk에 대해 다음과 같이 계산합니다.

  • 섹션 2: 1.0/(1+1) + 1.0/(1+2) = 0.833
  • 섹션 7: 1.0/(1+2) + 1.0/(1+3) = 0.583
  • 섹션 6: 1.0/(1+3) + 1.0/(1+1) = 0.75

점수로 정렬하면 최종 순위는 섹션 2(1위), 섹션 6(2위), 섹션 7(3위)이 됩니다.

이 설계의 장점은 모듈성입니다. 각 검색 인덱스가 동일한 인터페이스( add_document() 와 search() )를 구현하므로, 새로운 검색 방식을 시스템에 손쉽게 추가할 수 있습니다. 다른 embedding 모델이든, 특정 도메인 전용 검색이든, 그 밖의 어떤 검색 기법이든, 정해진 API만 따르면 하이브리드 파이프라인에 매끄럽게 통합됩니다.

결과 재정렬

🎬 영상

지금까지 만든 하이브리드 검색 방식은 잘 작동하지만, 아직 다듬어지지 않은 부분이 있습니다. 특정 용어를 검색하거나 약어를 사용하면 결과 순서가 완벽하지 않을 수 있습니다. 예를 들어 "What did the eng team do with INC-2023-Q4-011?"이라고 물으면, 그 질의에는 소프트웨어 엔지니어링 섹션이 더 관련 있는데도 사이버보안 섹션이 먼저 나올 수 있습니다.

LLM 기반 reranking

reranking은 vector index와 BM25 index의 결과를 병합한 뒤에 또 하나의 후처리 단계를 추가합니다. 개념은 단순합니다. 검색 결과를 가져와 사용자 질문과의 관련성을 기준으로 다시 정렬해 달라고 Claude에게 요청하는 것입니다.

과정은 다음과 같이 진행됩니다.

  • 평소처럼 하이브리드 검색(vector + BM25)을 실행합니다
  • 이전처럼 결과를 병합합니다
  • 병합된 결과를 reranker 함수에 넘깁니다
  • reranker는 특정 프롬프트와 함께 전체를 Claude에 보냅니다
  • Claude는 가장 관련 있는 문서를 재정렬한 목록을 반환합니다

시스템 프롬프트

reranking 프롬프트는 명확하고 구체적으로 설계됩니다. Claude에게 사용자의 질문과 관련 있어 보이는 모든 문서를 제공한 뒤, 간단한 작업을 요청합니다. 즉, 가장 관련 있는 문서를 관련도가 높은 순으로 반환하라는 것입니다.

전형적인 프롬프트 구조는 다음과 같습니다.

효율성 고려사항

Claude에게 전체 텍스트 chunk를 반환하라고 요청하는 것은 비효율적입니다. Claude가 많은 양의 텍스트를 복사하는 것을 기다려야 하기 때문입니다. 대신 각 텍스트 chunk에 미리 고유 ID를 부여하세요. 그런 다음 Claude에게 그 ID만 올바른 순서로 반환하도록 요청합니다.

컨텍스트 검색

🎬 영상

contextual retrieval은 근본적인 문제를 해결해 RAG 파이프라인의 정확도를 높이는 기법입니다. 문서를 chunk로 나누면 각 chunk는 더 넓은 문서 컨텍스트와의 연결을 잃어버리는데, 바로 이 문제를 다룹니다.

기본 아이디어는 간단합니다. 원본 문서를 chunk로 나눈 뒤, 각 chunk를 retriever 데이터베이스에 저장하기 전에 Claude에게 컨텍스트를 덧붙이도록 요청합니다. 이 전처리 단계는 각 chunk를 더 큰 문서 안에 "자리매김"하도록 돕습니다.

동작 방식

각 텍스트 chunk에 대해, chunk와 원본 문서를 함께 다음과 같은 프롬프트로 Claude에 보냅니다.

Write a short and succinct snippet of text to situate this chunk within the 
overall source document for the purposes of improving search retrieval of the chunk.

Here is the original source document:
<document>
{source_text}
</document>

Here is the chunk we want to situate within the whole document:
<chunk>
{text_chunk}
</chunk>

Answer only with the succinct context and nothing else.

Claude는 이런 컨텍스트를 생성할 수 있습니다. "이 섹션은 여러 분야를 아우르는 그룹에 관한 더 큰 보고서의 일부입니다. 사이버보안 분석 섹션에서도 언급되는 INC-2023-04-011에 대한 언급을 포함합니다."

그런 다음 생성된 컨텍스트를 원본 chunk 텍스트와 결합해 "컨텍스트가 부여된 chunk"를 만들고, 이를 vector index와 BM25 index에 저장합니다.

대용량 문서 다루기

원본 문서가 너무 커서 하나의 프롬프트에 담기지 않는다면, 문서 전체 대신 축소된 컨텍스트를 제공할 수 있습니다.

컨텍스트를 부여하려는 특정 chunk에 대해 다음을 포함하세요.

  • 문서 앞부분의 chunk 몇 개(요약이나 개요를 담고 있는 경우가 많습니다)
  • 대상 chunk 바로 앞에 오는 chunk들(국소적 컨텍스트를 제공합니다)

이 방식은 문서 전체로 프롬프트를 넘치게 하지 않으면서도, Claude가 의미 있는 컨텍스트를 생성하기에 충분한 정보를 제공합니다.

확장 사고(Extended Thinking)

🎬 영상

extended thinking은 최종 응답을 생성하기 전에 모델이 복잡한 문제를 충분히 추론할 시간을 주는 Claude의 고급 기능입니다. Claude의 내부 독백이라고 생각하면 됩니다. Claude가 문제에 어떻게 단계별로 접근하는지 들여다볼 수 있습니다.

Extended Thinking의 동작 방식

extended thinking을 활성화하면 Claude의 응답은 하나가 아니라 두 개의 파트로 구성됩니다.

  • reasoning content 파트 - Claude의 내부 사고 과정
  • text 파트 - 실제로 원했던 최종 응답

reasoning content는 Claude가 문제를 어떻게 분해하고, 무엇을 고려하며, 어떻게 최종 답에 도달하는지를 그대로 보여줍니다. 이러한 투명성은 복잡한 작업을 이해하고 디버깅하는 데 매우 유용합니다.

고려해야 할 트레이드오프

extended thinking에는 명확한 이점과 비용이 함께 따릅니다.

  • 복잡한 작업에서의 정확도 향상
  • 비용 증가 - 모든 thinking 토큰에 대해 비용을 지불
  • 지연 시간 증가 - thinking에는 시간이 걸림

핵심 판단 기준은 단순합니다. 평가(evaluation)를 활용하세요. 이미 프롬프트를 최적화했는데도 필요한 정확도가 나오지 않는다면, 그때가 바로 extended thinking을 고려할 시점입니다.

Signature 시스템

바로 눈에 띄는 중요한 세부 사항 하나는 reasoning content에 첨부되는 암호학적 signature입니다.

이 signature는 thinking 텍스트를 수정할 수 없도록 보장합니다. 후속 대화에 Claude의 이전 reasoning을 포함하려는 경우, signature가 해당 내용이 변조되지 않았음을 검증합니다. 이는 수정된 reasoning 텍스트로 인한 잠재적 안전 문제를 방지합니다.

Redacted Content

때때로 Claude의 thinking이 안전 시스템에 의해 플래그 처리되기도 합니다. 이 경우 읽을 수 있는 thinking 텍스트 대신 redactedContent 필드를 받게 됩니다.

redacted content는 암호화되어 있지만 여전히 기능합니다. 컨텍스트를 잃지 않고 이후 대화에서 Claude에게 다시 전달할 수 있습니다. 다만 개발자 입장에서 읽을 수 없을 뿐입니다.

구현

extended thinking을 활성화하려면 API 호출에 두 개의 파라미터를 추가해야 합니다.

additional_model_fields["thinking"] = {
"type": "enabled",
"budget_tokens": thinking_budget
}

thinking_budget은 Claude가 reasoning에 사용할 수 있는 토큰 수를 제어합니다. 최소값은 1024 토큰이며, 복잡한 문제에는 더 많이 필요할 수 있습니다. Claude의 다른 모든 것과 마찬가지로, 평가(evaluation)를 활용해 자신의 사용 사례에 맞는 적절한 budget을 찾으세요.

업데이트된 chat 함수는 다음과 같습니다.

def chat(
messages,
system=None,
temperature=1.0,
stop_sequences=[],
tools=None,
tool_choice="auto",
text_editor=None,
thinking=False,
thinking_budget=1024
):

구현 테스트

extended thinking을 처리하는 애플리케이션을 만들 때는 일반적인 reasoning content와 redacted content 시나리오를 모두 테스트하는 것이 좋습니다. 실제로 Claude가 redacted content를 반환하도록 강제하는 특수 테스트 문자열이 있어, 코드가 두 경우를 모두 제대로 처리하는지 확인하는 데 유용합니다.

extended thinking에 관한 가장 중요한 핵심은, 사용 여부 결정이 항상 데이터에 기반해야 한다는 점입니다. 먼저 평가(evaluation)를 실행하고 프롬프트를 최적화한 뒤, 복잡한 작업에서 정확도를 한층 더 끌어올려야 할 때에만 extended thinking을 고려하세요.

이미지 지원

🎬 영상

Claude의 vision 기능을 사용하면 메시지에 image를 포함해 Claude에게 분석, 비교, 객체 세기 등 상상할 수 있는 거의 모든 시각 작업을 요청할 수 있습니다. 이를 통해 문서 분석부터 자동 평가에 이르기까지 강력한 애플리케이션 가능성이 열립니다.

이미지 처리 기본

Claude에서 image를 다룰 때는 몇 가지 핵심 제한 사항을 알아 두어야 합니다.

  • 단일 요청의 모든 메시지를 통틀어 최대 20개의 image
  • 최대 크기 3.75MB
  • 최대 높이/너비 8000px
  • 각 image는 일정 수의 토큰으로 계산됨: tokens = (width px × height px) / 750

image를 포함하려면 또 다른 유형의 메시지 파트로 추가하면 됩니다. 보내려는 각 image마다 user 메시지에 하나의 image 파트를 포함합니다. 구조는 다음과 같습니다.

with open("image.png", "rb") as f:
image_bytes = f.read()

add_user_message(messages, [
{
"image": {
"format": "png",
"source": {"bytes": image_bytes}
}
},
{"text": "What do you see in this image?"}
])

여러 이미지

여러 개의 image 파트를 추가하면 단일 메시지에 여러 image를 보낼 수 있습니다. 그러면 Claude는 image 간의 관계를 분석하거나 서로 비교하고, 여러 시각 입력에 대한 이해가 필요한 질문에 답할 수 있습니다.

프롬프팅 기법

Claude의 vision 기능에 관해 가장 중요하게 이해해야 할 점은, 텍스트에 쓰던 프롬프트 엔지니어링 기법이 image에도 그대로 적용된다는 것입니다. 가이드라인이나 분석 단계를 제공하거나 one-shot/multi-shot 예시를 활용하면 Claude의 vision 정확도를 크게 높일 수 있습니다.

예를 들어 단순히 "이 이미지에 구슬이 몇 개 있나요?"라고 묻는 대신, 구조화된 접근 방식을 제공할 수 있습니다.

Analyze this image of marbles and determine the exact count using this methodology:
1. Begin by identifying each unique marble one at a time. Assign each a number as you identify it.
2. Verify your result by counting with a different method. Start from the bottom-left corner and work row by row, from left to right.
What is the exact, verified number of marbles in this image?

또 다른 효과적인 기법은 one-shot 프롬프팅입니다. 대상 image를 분석하도록 요청하기 전에, 올바른 분석이 담긴 예시 image를 먼저 제공하는 방식입니다.

실제 사례: 화재 위험 평가

Claude vision 기능의 실용적인 활용 사례로 보험사를 위한 자동 화재 위험 평가가 있습니다. 각 부동산에 조사원을 파견하는 대신, 고해상도 위성 이미지를 사용해 Claude에게 화재 위험을 평가하도록 요청할 수 있습니다.

이 시스템은 여러 핵심 요소를 분석할 수 있습니다.

  • 주택 근처에 빽빽하게 밀집한 나무
  • 긴급 차량이 진입하기 어려운 접근로
  • 주택 위로 뻗은 나뭇가지
  • 전반적인 나무의 밀도와 간격

이러한 분석은 다음과 같이 구성할 수 있습니다.

with open('./images/prop7.png', 'rb') as f:
image_bytes = f.read()

messages = []

add_user_message(messages, [
{"image": {"format": "png", "source": {"bytes": image_bytes}}},
{"text": prompt}
])

response = chat(messages)

이런 유형의 복잡한 시각 분석에서 성공의 핵심은, 단순한 평가를 요청하는 대신 구체적인 분석 단계를 따라가도록 Claude를 안내하는 상세하고 구조화된 프롬프트를 제공하는 것입니다.

image를 다룰 때는 단순한 프롬프트를 쓰는 함정에 빠지지 마세요. 텍스트 기반 상호작용에서 배운 프롬프트 엔지니어링 기법을 그대로 적용하면 Claude의 시각 분석 정확도를 크게 높일 수 있습니다.

PDF 지원

🎬 영상

Claude는 image를 다루는 것만큼 쉽게 PDF 문서를 읽고 분석할 수 있습니다. 이 기능은 문서 분석, 요약, 질의응답 워크플로에 강력한 가능성을 열어 줍니다.

PDF 처리 설정

PDF를 다루려면 표준 메시지 구조를 몇 가지 핵심적으로 변경해야 합니다. 과정은 image 처리와 유사하지만, document 명세에서 몇 가지 중요한 차이가 있습니다.

먼저 PDF 파일을 바이너리 데이터로 읽습니다.

with open("./earth.pdf", "rb") as f:
file_bytes = f.read()

Document 메시지 구조

PDF의 메시지 구조는 image와 여러 면에서 다릅니다. "image" 객체 대신 다음 필수 필드를 갖는 "document" 객체를 사용합니다.

add_user_message(
messages,
[
{"document": {"format": "pdf", "name": "earth", "source": {"bytes": file_bytes}}},
{"text": "Summarize this document in one sentence"},
],
)

document 구조의 핵심 사항입니다.

  • "image" 대신 "document"를 사용
  • "format": "pdf"로 설정
  • 확장자를 뺀 파일명을 담은 "name" 필드를 포함
  • "source"에는 파일 바이트가 들어감

이 코드를 실행하면 Claude는 PDF 전체 내용을 분석해 종합적인 응답을 제공합니다. 이 경우에는 지구(Earth) 위키백과 문서를 성공적으로 요약하여, 복잡한 레이아웃과 image, 구조화된 정보를 담은 여러 페이지 문서를 처리하는 능력을 보여 주었습니다.

Claude가 PDF로 할 수 있는 일

Claude는 다양한 PDF 처리 작업을 수행할 수 있습니다.

  • 핵심 정보 추출 및 요약
  • 문서 내용에 대한 구체적인 질문에 답변
  • 문서 구조와 서식 분석
  • 여러 페이지 문서를 효율적으로 처리
  • 텍스트와 image가 모두 포함된 PDF 처리

PDF 처리 기능은 citations 같은 다른 기능과 결합하면 더욱 강력해집니다. citations는 Claude가 응답에서 문서의 특정 부분을 참조할 수 있게 해 줍니다. 덕분에 리서치, 문서 분석, 콘텐츠 추출 워크플로에 특히 유용합니다.

인용(Citations)

🎬 영상

Claude에서 PDF를 다룰 때 가장 큰 과제 중 하나는 신뢰입니다. 사용자는 AI가 문서 내용을 올바르게 해석하고 있다고 그저 믿어야 하는 경우가 많습니다. Claude의 citations 기능은 정보가 원본 문서의 어디에서 나왔는지 정확히 보여 줌으로써 이 문제를 직접적으로 해결합니다.

Citations 활성화

PDF 처리에서 citations를 활성화하려면 document 설정에 파라미터 하나만 추가하면 됩니다.

with open("./earth.pdf", "rb") as f:
file_bytes = f.read()

messages = []

add_user_message(
messages,
[
{
"document": {
"format": "pdf",
"name": "earth",
"source": {"bytes": file_bytes},
"citations": {"enabled": True}
}
},
{"text": "How were Earth's atmosphere and oceans formed?"},
]
)

response = chat(messages)

핵심은 document 딕셔너리에 "citations": {"enabled": True}를 추가하는 것입니다. 이는 Claude에게 정보를 어디서 찾았는지 추적하고 응답에 citation 데이터를 포함하도록 지시합니다.

Citation 응답 이해하기

citations가 활성화되면 Claude의 응답 구조가 크게 달라집니다. 단순히 텍스트만 반환하는 대신 여러 파트를 받게 됩니다.

  • text 파트 - 익숙한 일반적인 응답 내용
  • citations content 파트 - 각 진술을 원본 위치에 매핑하는 새로운 구조화된 데이터

citations content에는 Claude가 각 진술의 근거를 어디에서 찾았는지에 대한 상세 정보가 담깁니다. 여기에는 특정 document, 페이지 번호, 나아가 응답에 영향을 준 정확한 텍스트까지 포함됩니다.

Citations가 중요한 이유

citations는 PDF 기반 애플리케이션에 여러 핵심 이점을 제공합니다.

  • 검증 - 사용자가 원본으로 되돌아가 Claude의 작업을 확인할 수 있음
  • 신뢰 - 정보의 출처를 알면 AI 응답에 대한 신뢰가 쌓임
  • 투명성 - AI의 추론 과정이 눈에 보이고 감사 가능해짐
  • 정확성 - citations는 더 신중한 정보 추출을 유도함

이 기능은 정확성과 출처 표기가 중요한 전문, 학술, 리서치 맥락에서 특히 가치가 큽니다. Claude를 블랙박스로 취급하는 대신, citations는 Claude를 자신의 작업 근거를 보여 주는 투명한 리서치 어시스턴트로 바꿔 줍니다.

프롬프트 캐싱

🎬 영상

prompt caching은 이전 요청의 연산 작업을 재사용하여 Claude의 응답 속도를 높이고 텍스트 생성 비용을 줄이는 기능입니다. 작동 방식을 이해하기 위해, 먼저 일반적인 요청에서 Claude 내부에서 무슨 일이 일어나는지 살펴봅시다.

Claude가 요청을 처리하는 일반적인 방식

Claude에 메시지를 보내면, 응답을 받기 전에 뒤에서 많은 일이 일어납니다. Claude는 곧바로 텍스트를 생성하기 시작하는 것이 아니라, 먼저 입력 메시지에 대해 상당한 작업을 수행합니다.

Claude가 메시지에 대해 수행하는 작업은 다음과 같습니다.

  • 프롬프트를 tokenize
  • 각 토큰에 대한 embeddings 생성
  • 주변 텍스트를 바탕으로 컨텍스트 추가
  • 출력 텍스트 생성

이 모든 전처리 작업은 Claude가 실제 응답을 생성하기 전에 이루어집니다. Claude는 요청 처리를 마치고 응답을 돌려보내면, 방금 수행한 모든 연산 작업을 버립니다.

작업을 버릴 때 생기는 문제

이는 Claude와 대화를 나눌 때 비효율을 낳습니다. 앞서 보낸 동일한 메시지에 Claude의 이전 응답, 그리고 대화를 이어 가기 위한 새 메시지를 더한 후속 요청을 보낸다고 가정해 봅시다.

Claude가 그 원본 메시지를 다시 보면, 조금 전에 버렸던 것과 똑같은 연산 작업을 전부 다시 해야 합니다. Claude 입장에서는 본질적으로 이렇게 생각하는 셈입니다. "방금 이 메시지를 처리하고 이 모든 작업을 한 다음 버렸는데, 이제 처음부터 다시 해야 하는구나."

Prompt Caching이 해결하는 방법

prompt caching은 연산 작업을 버리는 대신 저장함으로써 이 비효율을 해결합니다. 작동 방식은 다음과 같습니다.

Claude는 최초 요청을 처리할 때 모든 전처리 작업을 버리는 대신 그 작업을 cache에 저장합니다. cache는 특정 입력 메시지를 그에 대응하는 연산 결과에 매핑하는 룩업 테이블처럼 동작합니다.

동일한 내용을 포함한 후속 요청을 보내면, Claude는 cache를 확인해 처음부터 다시 하는 대신 이전 작업을 재사용할 수 있습니다.

주요 이점과 제약

prompt caching은 여러 이점을 제공합니다.

  • cache된 내용을 사용하는 요청은 더 저렴하고 빠르게 실행됨
  • 최초 요청은 cache에 씀(write)
  • 후속 요청은 cache에서 읽을(read) 수 있음
  • cache는 5분간 유지됨
  • 같은 내용을 반복해서 보낼 때만 유용함(다만 이런 경우가 매우 자주 발생함)

cache의 수명은 5분이므로, 짧은 시간 안에 겹치는 내용으로 여러 요청을 보내는 대화나 워크플로에서 가장 큰 이점을 줍니다. 이 패턴은 실제 애플리케이션에서 매우 흔합니다. 챗봇, 문서 분석 도구, 또는 대화 컨텍스트를 유지하는 모든 시스템을 떠올려 보세요.

많은 AI 애플리케이션이 실제로 같은 내용을 반복해서 보내기 때문에 prompt caching은 특히 가치가 큽니다. system prompt, 대화 이력, 분석 대상 대용량 문서 등 같은 텍스트가 한 세션 내 여러 요청에 걸쳐 반복적으로 등장하는 경우가 많습니다.

프롬프트 캐싱 규칙

🎬 영상

Claude의 prompt caching은 메시지에 대해 수행한 연산 작업을 저장해 후속 요청에서 재사용할 수 있게 하는 방식으로 동작합니다. 이를 통해 이후 요청을 더 저렴하고 빠르게 실행할 수 있지만, 같은 내용을 반복해서 보낼 때에만 그렇습니다.

이 과정은 두 단계 패턴을 따릅니다. 최초 요청은 cache에 쓰고(write), 후속 요청은 cache에서 읽습니다(read). cache는 5분만 유지되므로, 이 기능은 짧은 시간 안에 같은 내용을 반복해서 보낼 때 가장 유용합니다.

Cache Point

prompt caching은 자동으로 활성화되지 않습니다. 무엇을 cache할지 제어하려면 cache point 메시지 파트를 직접 추가해야 합니다. cache point는 메시지에서 해당 지점 이전의 모든 작업을 cache하도록 Claude에게 지시합니다.

user 메시지에 cache point를 추가하는 방법은 다음과 같습니다.

user_message = {
"role": "user",
"content": [
{"text": ""},
{"cachePoint": {"type": "default"}}
]
}

핵심 규칙은 cache point 이전의 모든 작업은 cache되지만, cache point 이후의 것은 cache에 저장되지 않는다는 점입니다.

Cache Point의 동작 방식

cache point가 포함된 최초 요청을 보내면, Claude는 모든 내용을 처리하고 그 cache point까지 수행한 작업을 저장합니다. 후속 요청에서 cache point 이전의 내용이 동일하면, Claude는 이를 다시 처리하는 대신 cache에서 이전에 처리한 작업을 읽습니다.

cache는 cache point 이전의 내용이 완전히 동일할 때에만 사용됩니다. 프롬프트 앞에 "Please"를 붙이는 것 같은 사소한 변경만으로도 cache 사용이 막혀, Claude가 모든 것을 처음부터 다시 처리하게 됩니다.

여러 메시지에 걸친 캐싱

cache point는 여러 메시지에 걸칠 수 있으며 assistant 메시지도 포함할 수 있습니다. 즉, 특정 지점까지의 전체 대화 이력을 cache할 수 있다는 뜻입니다.

예를 들어 user 메시지, assistant 응답, 그리고 또 다른 user 메시지로 이루어진 대화가 있고 그 끝에 cache point를 둘 수 있습니다. 그러면 그 전체 대화 스레드에 대한 모든 처리 작업이 cache되어 재사용될 수 있습니다.

최소 콘텐츠 길이

cache되려면 콘텐츠가 최소 1024 토큰 이상이어야 합니다. 이는 cache point 이전에 cache하려는 모든 메시지와 파트의 합계입니다.

단순한 "Hi there!" 메시지는 1024 토큰 최소 기준을 충족하지 못하므로 아무것도 cache되지 않습니다. 하지만 "Hi there!"를 500번 반복하면 1024 토큰을 초과해 캐싱 대상이 됩니다.

Cache Point 위치

cache point는 user 메시지에만 국한되지 않습니다. system prompt와 tool 정의에도 추가할 수 있으며, 사실 이 두 곳이 가장 흔한 캐싱 기회입니다.

tool 정의의 경우:

tools = [
{"toolSpec": add_duration_to_datetime_schema},
{"toolSpec": get_current_datetime_schema},
{"cachePoint": {"type": "default"}}
]

system prompt의 경우:

system = [
{"text": "You are a senior software..."},
{"cachePoint": {"type": "default"}}
]

system prompt와 tool 목록은 요청 간에 거의 바뀌지 않아 캐싱에 완벽한 후보이므로, 이 두 곳이 가장 가치 있는 캐싱 기회입니다.

MCP 소개

🎬 영상

Model Context Protocol (MCP)은 지루한 통합 코드를 잔뜩 작성하지 않고도 Claude에게 context와 도구를 제공하는 통신 계층입니다. 모든 도구 함수를 직접 만드는 대신, MCP는 그 부담을 무거운 작업을 대신 처리해 주는 전용 서버로 넘깁니다.

MCP를 처음 접하면 기본 아키텍처를 보여주는 도식을 보게 됩니다. MCP client(여러분의 서버)가 도구, prompt, resource를 담고 있는 MCP server에 연결하는 구조입니다. 각 MCP server는 GitHub, AWS, 데이터베이스 같은 외부 서비스에 대한 인터페이스 역할을 합니다.

MCP가 해결하는 문제

사용자가 Claude에게 자신의 GitHub 데이터에 대해 물어볼 수 있는 채팅 인터페이스를 만든다고 해봅시다. 예를 들어 "내 모든 저장소에 걸쳐 열려 있는 pull request는 무엇인가?" 같은 질문입니다. MCP 없이 이를 처리하려면 지원하려는 모든 GitHub 작업에 대한 도구를 직접 만들어야 합니다.

GitHub는 저장소, pull request, 이슈, 프로젝트 등 방대한 기능을 가지고 있습니다. 완전한 GitHub 통합을 구축하려면 엄청나게 많은 도구 스키마와 함수를 작성해야 합니다.

이렇게 되면 직접 작성하고 테스트하고 유지보수해야 할 코드가 많아집니다. 바로 여기서 MCP가 등장합니다.

MCP의 작동 방식

MCP는 도구 정의와 실행의 부담을 여러분의 서버에서 전용 MCP server로 옮깁니다. 그 많은 GitHub 도구를 직접 작성하는 대신, 이미 구현되어 있는 GitHub MCP server에 연결하면 됩니다.

MCP server는 외부 서비스를 감싸는 래퍼 역할을 하며, Claude가 사용할 수 있는 미리 만들어진 도구를 제공합니다. 통합 코드를 전혀 직접 작성하지 않고도 그 모든 GitHub 기능에 접근할 수 있습니다.

자주 묻는 질문

MCP server는 누가 만드나요?

누구나 MCP server 구현체를 만들 수 있습니다. 많은 경우 서비스 제공자가 직접 공식 구현체를 만듭니다. 예를 들어 AWS가 자사의 다양한 서비스용 도구를 담은 공식 MCP server를 배포할 수 있습니다.

API를 직접 호출하는 것과 무엇이 다른가요?

서비스의 API를 직접 호출하면 여전히 도구 스키마와 함수 구현을 직접 작성해야 합니다. MCP server는 그런 도구 스키마와 함수를 이미 정의된 상태로 제공하므로 개발 시간을 절약해 줍니다.

MCP는 그냥 tool use와 똑같은 것 아닌가요?

흔한 오해입니다. MCP server와 tool use는 상호 보완적이지만 서로 다른 개념입니다. tool use는 Claude가 작업을 수행하기 위해 함수를 호출하는 것에 관한 것입니다. MCP는 그 함수를 누가 제공하느냐에 관한 것입니다. 여러분이 직접 작성하는 대신, 누군가가 이미 MCP server에 구현해 둔 것입니다.

핵심은 MCP server가 도구 스키마와 함수를 이미 정의된 상태로 제공하는 반면, 직접 하는 tool use는 모든 것을 여러분이 직접 작성해야 한다는 점입니다. 둘 다 Claude가 도구를 사용하는 것이지만, MCP는 여러분 쪽에서 필요한 개발 작업을 극적으로 줄여줍니다.

MCP 클라이언트

🎬 영상

MCP client는 여러분의 서버와 MCP server 사이의 통신 다리 역할을 합니다. MCP server가 제공하는 모든 도구에 접근하는 진입점이라고 생각하면 됩니다. 외부 기능을 사용해야 할 때, client가 모든 메시지 전달과 프로토콜 세부 사항을 대신 처리해 줍니다.

Transport에 구애받지 않는 통신

MCP의 핵심 강점 중 하나는 transport agnostic이라는 점입니다. 이는 client와 server가 서로 다른 통신 방식으로 대화할 수 있다는 것을 멋지게 표현한 말입니다. 가장 흔한 구성은 MCP client와 server를 같은 머신에서 실행하고 표준 입출력(standard input/output)을 통해 통신하는 것입니다.

하지만 그 방식에만 국한되는 것은 아닙니다. MCP client와 server는 다음을 통해서도 연결할 수 있습니다.

  • HTTP
  • WebSockets
  • 그 밖의 다양한 네트워크 프로토콜

메시지 유형

연결되고 나면 client와 server는 MCP 명세에 정의된 특정 메시지 유형을 주고받습니다. 여러분이 주로 다루게 될 것은 다음과 같습니다.

ListToolsRequest/ListToolsResult: client가 server에게 "어떤 도구를 제공하나요?"라고 묻고, 사용 가능한 기능의 전체 목록을 돌려받습니다.

CallToolRequest/CallToolResult: client가 server에게 "이 인자로 이 특정 도구를 실행하라"고 알리고, 실행 결과를 받습니다.

이 과정은 사용자가 여러분의 서버에 질문을 제출하면서 시작됩니다. 하지만 서버가 Claude에게 도움을 요청하려면, 먼저 어떤 도구를 사용할 수 있는지 알아야 합니다.

여러분의 서버는 MCP client에게 도구 목록을 요청합니다. client는 MCP server에 ListToolsRequest를 보내고, 사용 가능한 모든 도구가 담긴 ListToolsResult를 돌려받습니다.

이제 여러분의 서버는 Claude에게 첫 요청을 보내는 데 필요한 모든 것, 즉 사용자의 질문과 사용 가능한 도구 목록을 갖추게 됩니다.

Claude는 도구를 분석하고 질문에 답하기 위해 그중 하나를 호출해야 한다고 판단합니다. 그리고 tool use 요청으로 응답합니다.

여러분의 서버는 Claude가 도구를 실행하려 한다는 것을 인식하지만, 이제 서버가 도구를 직접 실행하지는 않습니다. 그것은 MCP server의 몫입니다. 그래서 서버는 MCP client에게 Claude가 지정한 인자로 도구를 실행하도록 요청합니다.

MCP client는 MCP server에 CallToolRequest를 보내고, MCP server는 사용자의 저장소를 가져오기 위해 GitHub에 실제 요청을 보냅니다.

GitHub는 저장소 데이터로 응답하고, MCP server는 이를 CallToolResult로 감싸 MCP client에 돌려보냅니다.

MCP client는 도구 결과를 여러분의 서버에 전달하고, 서버는 이를 후속 메시지의 일부로 Claude에게 보냅니다.

마지막으로, Claude는 필요한 모든 정보를 갖추고 "당신의 저장소는..." 같은 응답을 작성하며, 이는 여러분의 서버를 거쳐 사용자에게 전달됩니다.

물론 이 흐름은 여러 단계를 거치지만, 각 구성 요소는 명확한 책임을 가지고 있습니다. MCP client는 server 통신의 복잡성을 추상화해 주므로, 강력한 외부 도구와 서비스에 접근하면서도 여러분은 애플리케이션 로직 구축에 집중할 수 있습니다.

프로젝트 설정

🎬 영상

MCP client와 server가 어떻게 함께 작동하는지 더 잘 이해하기 위해, 직접 CLI 기반 챗봇을 만들어 보겠습니다. 이 실습 프로젝트를 통해 MCP 아키텍처의 양쪽 모두를 실제로 경험해 볼 수 있습니다.

무엇을 만드는가

우리가 만들 챗봇은 사용자가 여러 문서와 대화할 수 있는 커맨드라인 인터페이스입니다. 이 시스템에는 다음이 포함됩니다.

  • CLI 기반 챗봇 인터페이스
  • Claude를 위한 문서 읽기 및 편집 기능
  • @doc_name 문법을 사용한 문서 "mention" 기능
  • /command_name 문법을 사용한 명령 실행
  • 메모리에 저장된 가짜 문서 모음

시스템 아키텍처

이 프로젝트는 함께 작동하는 세 가지 주요 구성 요소로 이루어집니다.

  • MCP client - 사용자 상호작용과 채팅 인터페이스를 담당
  • MCP server - 문서 작업을 위한 도구를 제공
  • 문서 저장소 - 다양한 파일 유형을 담은 인메모리 모음

MCP server는 두 가지 핵심 도구를 구현합니다.

  • 문서 내용을 읽는 도구
  • 문서 내용을 업데이트하는 도구

모든 문서(PDF, 스프레드시트, 텍스트 파일, 마크다운 파일)는 디스크가 아니라 메모리에 저장됩니다. 이렇게 하면 프로젝트를 단순하게 유지하면서 MCP 개념에 집중할 수 있습니다.

중요한 아키텍처 참고 사항

실제 프로젝트에서는 보통 MCP client나 MCP server 중 하나만 구현하지, 둘 다 구현하지는 않습니다. 예를 들면 다음과 같습니다.

  • 다른 개발자에게 서비스를 배포하기 위해 MCP server를 구축
  • 기존 서드파티 MCP server에 연결하는 MCP client를 구축

우리 프로젝트는 순전히 교육 목적으로 두 구성 요소를 하나의 코드베이스에 구현합니다. 그래야 client와 server가 서로 어떻게 상호작용하는지 볼 수 있기 때문입니다.

MCP로 도구 정의

🎬 영상

공식 Python SDK를 사용하면 MCP server를 훨씬 간단하게 구축할 수 있습니다. 도구를 위한 복잡한 JSON 스키마를 직접 작성하는 대신, decorator로 도구를 정의하고 무거운 작업은 SDK에 맡기면 됩니다.

이 예제에서는 문서 작업을 관리하는 MCP server를 만듭니다. server에는 두 가지 주요 도구가 있습니다. 하나는 문서 내용을 읽는 도구이고, 다른 하나는 문서를 업데이트하는 도구입니다. 모든 문서는 키가 문서 ID이고 값이 내용 문자열인 간단한 딕셔너리 형태로 메모리에 존재합니다.

MCP Python SDK의 이점

MCP 프로젝트는 여러 프로그래밍 언어에서 server와 client를 구축할 수 있는 공식 SDK를 제공합니다. Python SDK를 사용하면 다음과 같은 여러 이점이 있습니다.

  • 최소한의 보일러플레이트 코드로 MCP server를 생성
  • Python 함수 시그니처로부터 JSON 스키마를 자동 생성
  • decorator를 통해 도구 정의를 단순화
  • 타입 검증과 에러 처리를 대신 수행

SDK로 도구를 정의하는 것이 얼마나 쉬운지 살펴봅시다. @mcp.tool decorator를 타입 힌트, 필드 설명과 함께 사용하면, Claude가 이해하고 사용할 수 있는 적절한 도구 스키마가 자동으로 생성됩니다.

서버 설정하기

기본적인 서버 설정은 단 몇 줄이면 됩니다.

from mcp.server.fastmcp import FastMCP
from pydantic import Field

mcp = FastMCP("DocumentMCP", log_level="ERROR")

docs = {
"deposition.md": "This deposition covers the testimony of Angela Smith, P.E.",
"report.pdf": "The report details the state of a 20m condenser tower.",
"financials.docx": "These financials outline the project's budget and expenditures",
"outlook.pdf": "This document presents the projected future performance of the system",
"plan.md": "The plan outlines the steps for the project's implementation.",
"spec.txt": "These specifications define the technical requirements for the equipment"
}

읽기 도구 구현하기

첫 번째 도구는 Claude가 문서 ID를 제공하여 문서 내용을 읽을 수 있게 해줍니다.

@mcp.tool(
name="read_doc_contents",
description="Read the contents of a document and return it as a string."
)
def read_document(
doc_id: str = Field(description="Id of the document to read")
):
if doc_id not in docs:
raise ValueError(f"Doc with id {doc_id} not found")

return docs[doc_id]

이 도구 정의에는 다음이 포함됩니다.

  • 동작을 설명하는 명확한 이름
  • 도구가 무엇을 하는지 설명하는 설명(description)
  • 필드 설명이 붙은 타입 지정 파라미터
  • 잘못된 문서 ID에 대한 에러 처리

편집 도구 구현하기

두 번째 도구는 문서 내용에 대해 간단한 찾아 바꾸기 작업을 수행합니다.

@mcp.tool(
name="edit_document",
description="Edit a document by replacing a string in the documents content with a new string."
)
def edit_document(
doc_id: str = Field(description="Id of the document that will be edited"),
old_str: str = Field(description="The text to replace. Must match exactly, including whitespace."),
new_str: str = Field(description="The new text to insert in place of the old text.")
):
if doc_id not in docs:
raise ValueError(f"Doc with id {doc_id} not found")

docs[doc_id] = docs[doc_id].replace(old_str, new_str)

이 도구는 세 개의 파라미터를 받습니다. 문서 ID, 찾을 텍스트, 대체할 텍스트입니다. 구현은 단순하게 Python 내장 문자열 replace() 메서드를 사용합니다.

핵심 구현 세부 사항

MCP SDK로 도구를 정의할 때는 다음 중요한 점들을 기억하세요.

  • 파라미터 설명을 추가하려면 pydantic에서 Field를 import
  • 타입 힌트를 사용해 파라미터 타입을 지정
  • 예외 상황에 대한 에러 처리를 포함
  • 명확하고 설명적인 도구 이름과 설명을 작성
  • SDK가 함수 시그니처를 적절한 JSON 스키마로 자동 변환

MCP Python SDK는 JSON 스키마를 직접 작성하는 것에 비해 도구 생성의 복잡성을 극적으로 줄여줍니다. 예전에는 수십 줄의 스키마 정의가 필요했던 것이 이제는 decorator가 붙은 몇 줄의 Python 함수면 됩니다.

Inspector 인터페이스 사용하기

Tool 테스트 실행하기

  • read_doc_contents tool을 선택합니다
  • 문서 ID를 입력합니다(예: "deposition.md")
  • "Run Tool"을 클릭합니다

inspector가 tool을 실행하고, 성공 여부와 반환된 데이터를 포함한 결과를 보여줍니다.

문서 편집 같은 더 복잡한 tool도 테스트할 수 있습니다:

  • edit_document tool로 전환합니다
  • 문서 ID, 교체할 기존 텍스트, 새 텍스트를 입력합니다
  • tool을 실행해 성공하는지 확인합니다
  • read tool을 다시 사용해 변경 사항이 적용되었는지 검증합니다

개발 워크플로우

inspector는 왼쪽에 tool 호출 이력을 보여주기 때문에, 무엇을 테스트했는지 추적하고 이전 작업을 반복하기 쉽습니다. 이를 통해 다음과 같은 효율적인 개발 루프를 만들 수 있습니다:

  • 서버 코드를 수정합니다
  • inspector를 재시작합니다
  • tool을 곧바로 테스트합니다
  • 결과를 검증합니다

더 복잡한 MCP 서버를 개발할수록 이 inspector는 필수 도구가 됩니다. 기본 기능을 테스트하려고 서버를 전체 애플리케이션에 연결할 필요가 없어져, 개발이 훨씬 빠르고 안정적으로 이루어집니다.

🎬 영상

MCP 서버가 동작하게 되었으니, 이제 클라이언트 쪽을 구현할 차례입니다. 클라이언트는 애플리케이션이 MCP 서버와 통신하고 그 기능에 접근할 수 있게 해주는 요소입니다.

클라이언트 아키텍처 이해하기

코드로 들어가기 전에, MCP 프로젝트에 대해 한 가지 중요한 점을 짚고 넘어가겠습니다. 보통은 MCP client나 MCP server 중 하나만 구현하지, 둘 다 구현하지는 않습니다. 이 프로젝트에서는 둘이 어떻게 함께 동작하는지 보여주기 위해 양쪽을 모두 만들고 있습니다.

MCP client는 함께 동작하는 두 가지 주요 구성 요소로 이루어져 있습니다:

  • MCP Client - session을 더 쉽게 사용하기 위해 우리가 직접 만드는 커스텀 클래스
  • Client Session - 서버와의 실제 연결(MCP Python SDK의 일부)

client session은 저수준 통신을 처리하지만, 프로그램이 종료될 때 리소스를 신중하게 정리해야 합니다. 그래서 이를 우리만의 클래스로 감싸서 정리 작업을 자동으로 관리하는 것입니다.

클라이언트가 애플리케이션에서 하는 역할

앞서 본 애플리케이션 흐름도를 기억하시나요? 클라이언트는 두 가지 핵심 순간에 중요한 역할을 합니다:

우리 CLI 코드는 클라이언트를 사용해 다음을 수행합니다:

  • Claude에게 전달할 사용 가능한 tool 목록을 가져오기
  • Claude가 tool을 요청하면 실행하기

핵심 클라이언트 함수 구현하기

필수 함수 두 가지, list_tools 와 call_tool 를 구현해 보겠습니다.

list_tools 의 경우, session에 연결해 사용 가능한 tool을 요청해야 합니다:

async def list_tools(self) -> list[types.Tool]:
result = await self.session().list_tools()
return result.tools

call_tool 의 경우, tool 이름과 입력 파라미터를 서버로 전달합니다:

async def call_tool(
self, tool_name: str, tool_input: dict
) -> types.CallToolResult | None:
return await self.session().call_tool(tool_name, tool_input)

이게 전부입니다! 복잡한 통신 세부 사항은 session이 모두 알아서 처리해 줍니다.

클라이언트 테스트하기

클라이언트 파일 하단에는 간단한 테스트 하네스가 포함되어 있습니다. 이를 직접 실행해 모든 것이 정상 동작하는지 확인할 수 있습니다:

uv run mcp_client.py

이렇게 하면 MCP 서버에 연결되어 사용 가능한 tool들이 출력됩니다. 이름, 설명, 입력 스키마를 포함한 tool 정의가 출력되는 것을 확인할 수 있습니다.

주의해야 할 스키마 차이

여기 꼭 알아둬야 할 함정이 있습니다: MCP tool 정의는 Claude가 기대하는 형식과 정확히 일치하지 않습니다. MCP 스펙에는 tool 스키마를 위한 고유한 형식이 있으며, 이는 Bedrock이 요구하는 형식과 약간 다릅니다.

리소스 정의

🎬 영상

MCP 서버의 resource는 일반적인 HTTP 서버의 GET 요청 핸들러와 비슷하게, 클라이언트에 데이터를 노출할 수 있게 해줍니다. 동작을 수행하기보다 정보를 가져와야 하는 상황에 안성맞춤입니다.

Resource 이해하기

resource는 문자열, JSON, 바이너리 파일 등 어떤 유형의 데이터든 반환할 수 있는 읽기 전용 엔드포인트라고 생각하면 됩니다. mime_type을 지정하면 어떤 종류의 데이터를 반환하는지 클라이언트에 힌트를 줄 수 있습니다.

resource는 URI(본질적으로는 주소)를 통해 데이터를 노출하는 방식으로 동작합니다. 클라이언트는 데이터가 필요할 때 특정 URI를 담은 ReadResourceRequest를 보내고, 서버는 요청된 정보로 응답합니다.

Resource의 두 가지 유형

만들 수 있는 resource에는 크게 두 가지 유형이 있습니다:

  • Direct Resource - 파라미터를 포함하지 않는 정적 URI를 가짐(예: docs://documents)
  • Templated Resource - URI에 파라미터를 포함함(예: docs://documents/{doc_id})

templated resource의 경우, Python SDK가 URI에서 파라미터를 자동으로 파싱해 함수에 키워드 인자로 전달합니다. URI에 있는 파라미터 이름이 함수의 인자 이름이 됩니다.

Resource 구현하기

@mcp.resource() decorator를 사용하면 resource를 간단하게 만들 수 있습니다. 두 유형을 모두 구현하는 방법은 다음과 같습니다:

@mcp.resource(
"docs://documents",
mime_type="application/json"
)
def list_docs() -> list[str]:
return list(docs.keys())

@mcp.resource(
"docs://documents/{doc_id}",
mime_type="text/plain"
)
def fetch_doc(doc_id: str) -> str:
if doc_id not in docs:
raise ValueError(f"Doc with id {doc_id} not found")
return docs[doc_id]

MCP Python SDK는 여러분이 반환하는 값을 자동으로 직렬화합니다. 데이터를 직접 JSON 문자열로 변환할 필요 없이, 적절한 Python 데이터 구조를 반환하기만 하면 됩니다.

Resource 테스트하기

MCP inspector 도구를 사용해 resource를 테스트할 수 있습니다. uv run mcp dev mcp_server.py 로 서버를 시작한 뒤 웹 인터페이스로 이동하세요.

inspector는 direct resource와 templated resource를 구분해서 보여줍니다. direct resource는 메인 "Resources" 섹션에 나타나고, templated resource는 "Resource Templates" 아래에 표시됩니다. 아무 resource나 클릭해 테스트하고, 서버가 반환하는 정확한 응답 구조를 확인할 수 있습니다.

실전 활용 사례

resource는 다음과 같은 경우에 이상적입니다:

  • 자동 완성 데이터 제공(예: 문서 목록)
  • 파일 내용이나 데이터베이스 레코드 가져오기
  • 설정 데이터 노출
  • 클라이언트에 필요한 읽기 전용 정보 제공

가장 큰 장점은 resource를 통해 클라이언트가 tool이나 복잡한 상호작용에 의존하지 않고도 데이터를 능동적으로 가져올 수 있다는 점입니다. 덕분에 사용자가 언급한 내용을 기반으로 프롬프트에 콘텐츠를 자동으로 삽입하는 문서 멘션 같은 기능에 완벽하게 어울립니다.

MCP의 resource를 사용하면 정보를 얻기 위해 tool을 호출할 필요 없이, 서버가 데이터를 직접 프롬프트에 포함할 수 있도록 노출할 수 있습니다. 덕분에 Claude 같은 AI 모델에 context를 훨씬 효율적으로 제공할 수 있습니다.

리소스 흐름 이해하기

사용자가 애플리케이션에서 "What's in the @..." 같은 입력을 하면, 시스템은 자동완성을 위해 사용 가능한 resource 목록을 가져와야 합니다. MCP client가 서버에 ReadResourceRequest를 보내면, 서버는 참조할 수 있는 문서 이름 목록으로 응답합니다.

리소스 읽기 구현하기

핵심 기능은 MCP client의 read_resource 메서드에서 이루어집니다. 이 메서드는 서버에서 어떤 resource를 가져올지 식별하는 URI 파라미터를 받습니다.

먼저 JSON 파싱과 URL 검증에 필요한 import를 추가합니다:

import json
from pydantic import AnyUrl

주요 구현부는 MCP 서버에 요청을 보내고 응답을 처리합니다:

async def read_resource(self, uri: str) -> Any:
result = await self.session().read_resource(AnyUrl(uri))
resource = result.contents[0]

다양한 콘텐츠 타입 처리하기

Resource는 여러 종류의 콘텐츠를 반환할 수 있으므로, 응답을 적절히 처리하려면 MIME 타입을 확인해야 합니다:

if isinstance(resource, types.TextResourceContents):
if resource.mimeType == "application/json":
return json.loads(resource.text)

return resource.text

이 방식을 사용하면 JSON resource는 제대로 파싱되고, 일반 텍스트 resource는 그대로 반환됩니다.

구현 테스트하기

구현이 끝나면 CLI 애플리케이션을 실행해 resource 기능을 테스트할 수 있습니다. "@"를 입력한 뒤 resource 이름을 입력하면 시스템은 다음을 수행합니다:

  • 사용 가능한 resource를 자동완성 목록으로 표시
  • 방향키와 스페이스로 resource를 선택할 수 있게 함
  • 선택한 resource 콘텐츠를 Claude로 보내는 프롬프트에 직접 포함

즉, Claude는 추가 tool 호출 없이 문서 콘텐츠를 즉시 전달받게 되어 상호작용이 훨씬 효율적입니다.

핵심 이점

정적 정보에 접근할 때 resource는 tool에 비해 여러 장점을 제공합니다:

  • 콘텐츠가 프롬프트에 직접 포함되어 지연 시간 감소
  • 대화 중 추가 API 호출 불필요
  • 자동완성 기능으로 더 나은 사용자 경험
  • 정적 데이터와 동적 작업 간의 깔끔한 분리

Resource는 문서, 리포트, 참고 자료처럼 AI 모델이 쉽게 접근할 수 있게 하고 싶은 비교적 정적인 정보에 가장 적합합니다.

프롬프트 정의

🎬 영상

MCP 서버는 prompt를 정의할 수 있습니다. prompt는 client가 직접 처음부터 작성하는 대신 사용할 수 있는, 미리 작성된 고품질 지시문입니다. 사용자가 직접 작성하는 것보다 더 나은 결과를 내도록 정교하게 다듬어진 템플릿이라고 생각하면 됩니다.

왜 프롬프트를 사용할까?

Claude에게 문서를 markdown으로 다시 포맷팅해 달라고 하고 싶다고 해봅시다. 그냥 "report.pdf를 markdown으로 변환해줘"라고 요청해도 잘 동작합니다. 하지만 엣지 케이스를 다루고 구체적인 포맷팅 지시를 담은, 철저히 테스트된 상세한 prompt를 사용하면 훨씬 더 좋은 결과를 얻을 수 있습니다.

아이디어는 간단합니다. MCP 서버 개발자로서 우리는 정말 좋은 prompt를 만들고 테스트하는 데 시간을 들인 뒤, 서버를 사용하는 누구에게나 제공할 수 있습니다. 사용자는 스스로 프롬프트 엔지니어링 전문가가 되지 않고도 더 나은 결과를 얻게 됩니다.

프롬프트 정의하기

Prompt는 tool, resource와 유사한 decorator 패턴을 사용합니다. 기본 구조는 다음과 같습니다:

@mcp.prompt(
name="format",
description="Rewrites the contents of the document in Markdown format."
)
def format_document(
doc_id: str = Field(description="Id of the document to format")
) -> list[base.Message]:
# Return a list of messages

이 함수는 Claude에 바로 보낼 수 있는 메시지 목록을 반환합니다. 덕분에 필요하다면 여러 개의 user 및 assistant 메시지로 복잡한 prompt를 구성할 수도 있습니다.

포맷 프롬프트 만들기

우리의 문서 서버를 위해 문서를 markdown으로 다시 포맷팅하는 prompt를 만들겠습니다. 이 prompt는 다음을 수행해야 합니다:

  • 문서 ID를 입력으로 받기
  • read_doc_contents tool로 문서 가져오기
  • 올바른 markdown 문법으로 다시 포맷팅하기
  • 변경 사항을 문서에 다시 저장하기

구현은 다음과 같습니다:

def format_document(
doc_id: str = Field(description="Id of the document to format")
) -> list[base.Message]:
prompt = f"""
Your goal is to reformat a document to be written with markdown syntax.

The id of the document you need to reformat is:

{doc_id}

Add in headers, bullet points, tables, etc as necessary. Feel free to add in structure.
Use the 'edit_document' tool to edit the document. After the document has been reformatted...
"""

return [
base.UserMessage(prompt)
]

프롬프트 테스트하기

prompt를 정의했다면 MCP inspector를 사용해 테스트할 수 있습니다. Prompts 탭으로 이동해 prompt를 선택하고 필요한 파라미터를 입력하세요.

inspector는 Claude로 전송될 생성된 메시지를 보여줍니다. 파라미터 보간이 올바르게 동작하는지, prompt에 필요한 지시가 모두 포함되어 있는지 확인할 수 있습니다.

핵심 이점

  • 품질 관리 - 서버 작성자가 사용자에게 노출되기 전에 prompt를 테스트하고 다듬을 수 있습니다
  • 일관성 - 각자 즉흥적으로 작성하는 대신 모두가 동일한 고품질 prompt를 사용합니다
  • 전문화 - prompt를 서버의 특정 도메인과 기능에 맞게 조정할 수 있습니다

클라이언트의 프롬프트

🎬 영상

MCP client 구축의 마지막 단계는 prompt 기능을 구현하는 것입니다. 이를 통해 서버에서 사용 가능한 모든 prompt를 나열하고, 변수가 보간된 특정 prompt를 가져올 수 있습니다.

list_prompts 구현하기

list_prompts 메서드는 간단합니다. session의 list prompts 메서드를 호출하고 그 prompt를 반환합니다:

async def list_prompts(self) -> list[types.Prompt]:
result = await self.session().list_prompts()
return result.prompts

개별 프롬프트 가져오기

get_prompt 메서드는 인자 보간을 처리하기 때문에 좀 더 흥미롭습니다. 특정 prompt를 요청할 때 prompt 함수로 주입되는 인자를 전달합니다. 예를 들어 서버에 doc_id 파라미터를 기대하는 "format" prompt가 있다면, 그 값이 전달되어 실제 prompt 텍스트에 보간됩니다.

async def get_prompt(self, prompt_name, args: dict[str, str]):
result = await self.session().get_prompt(prompt_name, args)
return result.messages

이 메서드는 Claude에 바로 입력할 수 있는 대화 형태의 메시지를 반환합니다.

프롬프트 실제 테스트하기

client를 실행하고 슬래시(/)를 입력하면 사용 가능한 prompt가 커맨드로 표시됩니다. "format" 같은 prompt를 선택하면 사용 가능한 문서 중에서 선택하라는 안내가 나옵니다. 그러면 시스템은 다음을 수행합니다:

  • 문서 ID가 보간된 prompt를 가져옴
  • 그것을 user 메시지로 Claude에 바로 전달
  • Claude는 지시와 문서 ID를 모두 전달받음
  • Claude는 사용 가능한 tool을 사용해 문서 콘텐츠를 가져옴
  • Claude는 다시 포맷팅된 결과로 응답

프롬프트의 동작 방식

Prompt는 client가 사용할 수 있는 user 및 assistant 메시지 집합을 정의합니다. 이러한 prompt는 고품질이고, 잘 테스트되었으며, MCP 서버의 전반적인 목적에 부합해야 합니다.

워크플로는 다음과 같습니다:

  • MCP 서버의 목적에 맞는 prompt를 작성하고 평가
  • @mcp.prompt decorator를 사용해 MCP 서버 안에 prompt 정의
  • client는 언제든지 그 prompt를 요청할 수 있음
  • prompt를 요청할 때 prompt 함수에 키워드 인자로 전달될 인자를 제공
  • 함수는 그 인자를 사용해 prompt 콘텐츠를 맞춤화

이 시스템은 여러 client와 사용 사례에서 공유할 수 있는 재사용 가능하고 파라미터화된 prompt를 만들어, MCP 서버를 더욱 다재다능하고 강력하게 만들어 줍니다.

MCP 리뷰

🎬 영상

이제 MCP 서버를 구축했으니, 세 가지 핵심 서버 primitive를 정리하고 각각 언제 사용해야 하는지 이해해 봅시다. 핵심은 각 primitive가 애플리케이션 스택의 서로 다른 부분에 의해 제어된다는 점입니다.

Tools: 모델이 제어

Tool은 전적으로 Claude가 제어합니다. AI 모델이 이 함수들을 언제 호출할지 결정하고, 그 결과는 Claude가 작업을 완수하는 데 직접 사용됩니다.

Claude에게 추가 기능을 부여하고 싶을 때 tool을 사용하세요. 예를 들어 Claude에게 JavaScript로 3의 제곱근을 계산하라고 요청하면, Claude는 자동으로 JavaScript 실행 tool을 사용하기로 결정해 답을 제공합니다.

tool을 사용하기로 한 결정은 100% 모델이 제어한 것입니다. Claude는 코드를 실행해야 함을 인식하고, 애플리케이션이나 사용자의 어떤 지시도 없이 적절한 tool을 선택했습니다.

Resources: 앱이 제어

Resource는 애플리케이션 코드가 제어합니다. 앱이 언제 resource 데이터를 가져올지, 그리고 그것을 어떻게 사용할지 결정하며, 보통 UI 용도나 대화에 context를 추가하기 위해 사용합니다.

데이터를 앱으로 가져와야 할 때 resource를 사용하세요. 흔한 예시는 다음과 같습니다:

  • UI의 자동완성 옵션 채우기
  • 파일 선택기에 표시할 문서 가져오기
  • Claude에 메시지를 보내기 전에 context 추가하기

Claude 웹 인터페이스의 "Add from Google Drive" 기능이 이를 완벽하게 보여줍니다. 애플리케이션이 사용 가능한 문서 목록을 가져와 UI에 표시하고, 선택된 문서의 콘텐츠를 채팅 context에 주입합니다.

Prompts: 사용자가 제어

Prompt는 사용자가 제어합니다. 사용자는 버튼 클릭, 메뉴 옵션 선택, 슬래시 커맨드 사용 같은 직접적인 행동을 통해 미리 정의된 이 워크플로를 언제 실행할지 결정합니다.

사용자가 쉽게 접근할 수 있는 미리 정의된 워크플로를 구현하고 싶을 때 prompt를 사용하세요. Claude 인터페이스에서는 채팅 입력창 아래에 워크플로 버튼이 있어, 사용자가 글쓰기, 학습, 코딩 같은 흔한 작업을 빠르게 시작할 수 있습니다.

올바른 primitive 선택하기

MCP 서버를 구축할 때는 각 기능을 누가 제어해야 하는지 생각하세요:

  • Claude의 기능을 확장해야 하나요? tool을 사용하세요
  • 데이터를 앱 UI로 가져와야 하나요? resource를 사용하세요
  • 사용자에게 미리 정의된 워크플로를 제공해야 하나요? prompt를 사용하세요

이는 구체적인 사용 사례에 따라 올바른 primitive를 선택하도록 돕는 상위 수준의 가이드라인입니다. 각각은 애플리케이션 스택의 서로 다른 부분을 담당합니다. tool은 모델을, resource는 앱을, prompt는 사용자를 위한 것입니다.

Claude Code 실전

🎬 영상

Claude Code는 단순히 코드를 작성하는 도구가 아니라, 프로젝트 전체 수명 주기 동안 함께하는 코딩 파트너로 설계되었습니다. 초기 설정부터 배포와 유지보수까지, Claude는 소프트웨어 개발의 모든 단계를 도울 수 있습니다.

/init 명령

새 프로젝트를 시작할 때는 /init 명령이 첫 단계입니다. Claude Code가 코드베이스를 스캔하며 프로젝트 구조, 의존성, 명령, 코딩 패턴을 파악합니다. 그 결과는 CLAUDE.md 파일에 요약되며, Claude는 이후 대화에서 이 파일을 자동으로 읽습니다.

범위에 따라 여러 개의 CLAUDE.md 파일을 둘 수 있습니다.

  • Project - git에 커밋되어 엔지니어들끼리 공유하는 파일
  • Local - git에 커밋하지 않는, Claude에게 남기는 개인 메모
  • User - 모든 프로젝트에 걸쳐 사용되는 파일

/init를 실행할 때 Claude가 집중해줬으면 하는 부분에 대한 특별 지시를 추가할 수 있습니다. 또한 # 단축키로 CLAUDE.md 파일에 덧붙일 간단한 메모를 빠르게 추가할 수도 있습니다.

흔히 쓰는 워크플로

Claude는 노력을 배가시키는 도구로 쓸 때 가장 좋습니다. 더 많은 맥락과 구조를 제공할수록 더 나은 결과를 얻습니다. 효과적인 두 가지 접근법을 소개합니다.

계획 우선 워크플로

이 세 단계 접근법은 복잡한 기능에 잘 맞습니다.

  • Claude에 맥락 제공하기 - 기능과 관련된 파일을 찾아 Claude에게 읽게 합니다
  • Claude에게 해결책을 계획하게 하기 - 무엇을 만들고 싶은지 설명하되, 아직 코드는 작성하지 말라고 분명히 지시합니다
  • Claude에게 해결책을 구현하게 하기 - 탄탄한 계획이 마련되면, 이미 확보한 맥락과 계획을 바탕으로 Claude가 코드를 작성합니다

예를 들어 문서 변환 도구를 만든다면, 먼저 Claude에게 기존 도구 예제와 헬퍼 함수를 살펴보게 할 수 있습니다. 그런 다음 구현 단계를 계획하게 하고, 마지막으로 실제 코드 구현을 요청합니다.

test-driven development 워크플로

이 접근법은 초반에 더 많은 노력이 필요하지만 Claude의 효과를 극적으로 높여줍니다.

  • Claude에 맥락 제공하기 - 기능과 관련된 파일을 공유합니다
  • Claude에게 테스트 케이스를 구상하게 하기 - 아직 코드는 전혀 작성하지 말라고 분명히 지시합니다
  • Claude에게 그 테스트들을 구현하게 하기 - 기능과 관련 있어 보이는 테스트만 선별합니다
  • Claude에게 테스트를 통과하는 코드를 작성하게 하기 - Claude가 테스트를 통과할 때까지 해결책을 반복 개선합니다

이 워크플로는 코드를 견고하게 만들고, 처음에는 미처 고려하지 못한 엣지 케이스까지 다루도록 도와줍니다.

실전 팁

Claude는 코드 작성 외에도 일상적인 개발 작업을 처리할 수 있습니다. 다음과 같은 일을 요청할 수 있습니다.

  • 프로젝트 환경 설정 및 의존성 설치
  • 변경 사항을 스테이징하고 설명이 담긴 커밋 메시지로 커밋
  • 테스트 스위트 실행 및 결과 해석
  • /clear로 대화 기록을 지워 맥락 초기화

Claude Code는 CLAUDE.md 파일을 자동으로 읽는다는 점을 기억하세요. 그 파일에 기록한 코딩 표준, 프로젝트별 메모, 아키텍처 결정은 이후 모든 상호작용에 영향을 줍니다. 덕분에 Claude는 프로젝트의 패턴과 요구사항을 더 많이 학습할수록 점점 더 효과적으로 작동합니다.

MCP 서버로 기능 확장

🎬 영상

Claude Code에는 MCP 클라이언트가 내장되어 있어, MCP server를 연결하면 기능을 크게 확장할 수 있습니다. 이를 통해 개발 워크플로를 맞춤화하는 매우 강력한 가능성이 열립니다.

MCP 연동이 작동하는 방식

Model Context Protocol을 통해 Claude Code는 MCP server를 거쳐 외부 서비스에 연결할 수 있습니다. 각 서버는 Claude가 할 수 있는 일을 확장하는 도구, 프롬프트, 리소스를 제공합니다.

이 예제에서는 문서 변환 도구를 제공하는 custom MCP server에 Claude Code를 연결합니다. 이를 통해 Claude가 PDF와 Word 문서를 읽어 markdown 형식으로 변환할 수 있게 됩니다.

Claude Code에 MCP server 추가하기

MCP server 설정은 간단합니다. 먼저 실행 중인 Claude Code 세션을 종료한 뒤, MCP add 명령을 사용합니다.

claude mcp add documents uv run main.py

이 명령은 두 개의 인자를 받습니다.

  • 서버 이름 (원하는 대로 지정 가능 - 여기서는 "documents")
  • MCP server를 시작하는 명령

서버를 추가한 뒤 Claude Code를 재시작하면 자동으로 MCP server에 연결됩니다.

연동 테스트하기

연결이 완료되면 Claude는 MCP server가 제공하는 도구를 사용할 수 있습니다. 이 예제에서는 Claude에게 문서 파일을 markdown 형식으로 변환해달라고 요청하면, 우리가 만든 문서 변환 도구를 자동으로 사용합니다.

이 도구는 문서 내용을 성공적으로 변환하며, MCP server가 Claude Code에 완전히 새로운 기능을 더할 수 있음을 보여줍니다.

개발에 유용한 인기 MCP server

개발 워크플로를 강화해주는 기존 MCP server가 많이 있습니다.

  • sentry-mcp - Sentry에 기록된 버그를 자동으로 찾아 수정
  • playwright-mcp - 테스트와 문제 해결을 위한 브라우저 자동화 기능을 Claude에 제공
  • figma-context-mcp - Figma 디자인을 Claude에 노출
  • mcp-atlassian - Claude가 Confluence와 Jira에 접근하도록 허용
  • firecrawl-mcp-server - 웹 스크래핑 기능을 Claude에 추가
  • slack-mcp - Claude가 메시지를 게시하거나 특정 스레드에 답장하도록 허용

나만의 워크플로 구축하기

진정한 힘은 자신의 개발 요구에 맞는 여러 MCP server를 조합하는 데서 나옵니다. 예를 들어 다음과 같이 구성할 수 있습니다.

  • 프로덕션 오류 상세 정보를 가져오는 Sentry 서버
  • 티켓 요구사항을 읽는 Jira 서버
  • 작업이 완료되면 팀에 알리는 Slack 서버
  • 자신만의 도구와 프로세스를 위한 custom 서버

이러한 유연성 덕분에 Claude Code는 다양한 개발 환경과 워크플로에 놀랍도록 잘 적응합니다. 평소 자주 사용하는 외부 서비스와 도구가 무엇인지 잠시 떠올려 보세요. 그것들을 Claude Code와 연동해주는 MCP server가 이미 존재할 가능성이 높습니다.

Claude Code 병렬화

🎬 영상

Claude Code 인스턴스를 여러 개 병렬로 실행하는 것은 얻을 수 있는 가장 큰 생산성 향상 중 하나입니다. Claude는 가벼워서 손쉽게 여러 개를 띄우고, 각각에 다른 작업을 맡겨 동시에 진행하게 할 수 있습니다. 사실상 프로젝트를 함께 진행하는 가상 소프트웨어 엔지니어 팀을 갖는 셈입니다.

문제: 파일 충돌

병렬 인스턴스의 주된 문제는 같은 파일을 동시에 수정하려 할 수 있다는 점입니다. 각 인스턴스는 다른 인스턴스가 무엇을 하는지 모르기 때문에, 이는 충돌하거나 잘못된 코드로 이어질 수 있습니다.

해결책은 각 Claude 인스턴스에 별도의 작업 공간을 주는 것입니다. 각 인스턴스는 프로젝트의 자체 복사본으로 작업하고, 격리된 상태에서 변경한 뒤, 그 변경 사항을 다시 메인 프로젝트에 병합합니다.

git worktree

git worktree는 이 워크플로에 완벽하게 들어맞습니다. 프로젝트가 이미 Git으로 관리되고 있다면 worktree를 곧바로 사용할 수 있습니다. worktree는 Git 브랜치 기능의 확장으로, 프로젝트의 완전한 복사본을 머신의 별도 디렉터리에 만들 수 있게 해줍니다.

각 git worktree는 별도의 브랜치에 대응합니다. 기능 A를 위한 폴더와 기능 B를 위한 폴더를 각각 둘 수 있고, 각 폴더에는 코드베이스의 완전한 복사본이 들어 있습니다. 그런 다음 각 worktree에서 별도의 Claude Code 인스턴스를 실행하면 완전히 격리된 상태로 작업할 수 있습니다.

각 Claude 인스턴스가 맡은 기능을 끝내면, 일반적인 Git 브랜치를 병합하듯이 작업을 커밋하고 메인 브랜치로 병합합니다.

worktree 생성 자동화하기

관리가 복잡하게 들릴 수 있지만, 전체 워크플로를 Claude Code 자체에 위임할 수 있습니다. 다음과 같은 일을 Claude에게 요청하는 프롬프트를 작성할 수 있습니다.

  • 특정 폴더에 새 git worktree 생성
  • Git이 추적하지 않는 의존성을 심볼릭 링크로 연결
  • 해당 디렉터리에서 새 VS Code 인스턴스 실행

custom command

매번 긴 프롬프트를 복사해 붙여넣는 대신, Claude Code에서 custom command를 만들 수 있습니다. .claude/commands에 .md 파일을 추가하면 custom command가 만들어집니다.

custom command에서는 $ARGUMENTS를 참조할 수 있으며, 이는 명령에 전달한 인자로 치환됩니다. 예를 들어,

  • /project:create_worktree feature_a 는 "feature_a"라는 이름의 worktree를 생성합니다
  • /project:create_worktree develop 는 "develop"이라는 이름의 worktree를 생성합니다

실전 병렬 개발

전체 워크플로가 실제로 어떻게 보이는지 살펴봅니다. 서로 다른 기능을 위해 여러 개의 worktree를 만들 수 있습니다.

각 Claude 인스턴스는 할당된 작업을 수행합니다.

  • 문서 테스트 업데이트
  • 로깅 추가
  • 노트 작성 도구 추가
  • 뺄셈 도구 추가

변경 사항 병합하기

기능이 완성되면 병합 과정도 자동화할 수 있습니다. Claude에게 다음과 같은 일을 지시하는 또 다른 custom command를 만듭니다.

  • worktree 디렉터리로 이동
  • 최신 커밋 확인
  • 루트 디렉터리로 복귀
  • worktree 브랜치 병합
  • 병합 충돌을 자동으로 처리

Claude는 각 브랜치에서 이루어진 변경 사항에 대한 이해를 바탕으로 병합 충돌까지 자동으로 해결할 수 있습니다.

결과

이 접근법은 관리할 수 있는 만큼 병렬 인스턴스를 확장할 수 있습니다. 기능을 순차적으로 작업하는 대신, 여러 Claude 인스턴스가 프로젝트의 서로 다른 부분을 동시에 개발하게 할 수 있습니다. 각자 격리된 환경에서 작업한 뒤 결과를 한데 모으는, 나만의 개발자 팀을 두는 것과 같습니다.

생산성 향상은 상당합니다. 실행하는 병렬 인스턴스 수만큼 개발 역량을 곱하는 셈이기 때문입니다.

자동 디버깅

🎬 영상

Claude는 에디터에서 코드를 작성하는 것에만 쓰이지 않습니다. 프로덕션 애플리케이션을 모니터링하며 오류가 발생하는 대로 자동으로 고칠 수도 있습니다. 이를 통해 사용자에게 영향을 주기 전에 문제를 잡아내고 해결하는 강력한 자동 디버깅 워크플로를 만들 수 있습니다.

문제: 프로덕션에서만 발생하는 오류

가장 답답한 디버깅 상황 중 하나는 애플리케이션이 개발 환경에서는 완벽하게 동작하지만 프로덕션에서는 실패하는 경우입니다. 로컬에서 모든 것을 테스트하고 자신 있게 배포했는데, 정작 실제 환경에서는 특정 기능이 동작하지 않는 것을 뒤늦게 발견할 수 있습니다.

로컬 테스트에서는 완벽하게 동작하는 간단한 챗봇 애플리케이션을 떠올려 봅시다. 질문을 하고, 가짜 데이터로 스프레드시트를 생성하는 등 모든 것이 예상대로 응답합니다. 하지만 동일한 코드를 AWS Amplify에 배포하고 똑같은 테스트를 실행하면, 스프레드시트 생성이 조용히 실패합니다. 요청은 처리되지만 데이터가 나타나지 않습니다.

전통적인 디버깅 방식

보통은 다음과 같은 과정을 거쳐야 합니다.

  • CloudWatch 로그를 뒤져 오류 메시지 찾기
  • 복잡한 오류 상세 정보와 스택 트레이스 분석
  • 코드가 프로덕션에서 왜 다르게 동작하는지 수동으로 디버깅
  • 문제를 고치고 재배포

이 과정은 시간이 오래 걸릴 수 있으며, 방대한 로그 출력에 파묻힌 "The provided model identifier is invalid" 같은 알쏭달쏭한 오류 메시지를 다룰 때 특히 그렇습니다.

자동 오류 탐지 및 수정

수동 디버깅 대신, 매일 자동으로 실행되어 프로덕션 환경을 모니터링하는 GitHub Action을 만들 수 있습니다. 이 워크플로는 전체 디버깅 과정을 Claude에게 위임합니다.

자동화된 워크플로는 다음과 같이 작동합니다.

  • Setup: GitHub Action이 저장소를 체크아웃하고, 의존성을 설치하며, Claude를 설정합니다
  • Log Analysis: AWS CLI로 최근 24시간의 CloudWatch 로그를 가져옵니다
  • Error Processing: Claude가 로그를 분석해 중복을 제거하고 고유한 오류를 식별합니다
  • Fix Implementation: Claude가 해당 코드를 수정해 각 오류를 고치려 시도합니다
  • Pull Request Creation: 수정 사항을 커밋하고 검토용 pull request를 자동으로 엽니다

실제 사례

챗봇 예제에서 Claude는 프로덕션 환경이 잘못된 모델 식별자를 사용하고 있다는 것을 발견했습니다. 이 오류는 프로덕션 설정에서만 참조되던 모델 ID의 오타 때문에 발생했습니다.

Claude는 문제를 식별하고, 올바른 모델 ID 형식을 찾아 설정 파일을 업데이트했습니다. 그런 다음 무엇이 잘못되었고 어떻게 해결했는지 명확히 설명한 커밋으로 수정 사항을 반영했습니다.

자동 디버깅의 이점

  • 선제적 모니터링: 오류의 존재를 인지하기도 전에 잡아냅니다
  • 시간 절약: 수동으로 로그를 뒤지고 디버깅하는 작업을 없앱니다
  • 명확한 문서화: 각 수정에는 상세한 설명이 함께 제공됩니다
  • 검토 절차: pull request를 통해 병합 전에 수정 사항을 확인할 수 있습니다
  • 지속적 개선: 자동으로 실행되어 새로 발생하는 문제를 잡아냅니다

구현 시 고려사항

자동 디버깅 워크플로를 설정할 때는 다음을 유의하세요.

  • CloudWatch 접근을 위한 적절한 AWS 권한 구성
  • 컨텍스트 윈도를 넘지 않도록 처리할 오류 수에 합리적인 제한 설정
  • 유사한 오류를 중복 제거하는 로직 포함
  • pull request 생성을 위해 워크플로에 적절한 저장소 쓰기 권한 부여
  • 사용량이 적은 시간대에 워크플로를 실행하는 방안 고려

이 자동화된 접근법은 디버깅을 사후 대응적이고 수동적인 과정에서, 최소한의 개입으로 애플리케이션을 원활하게 유지하는 선제적이고 자동화된 시스템으로 탈바꿈시킵니다.

Computer Use

Computer Use로 할 수 있는 일

Claude는 무엇을 할지 설명하거나 코드를 생성하는 데 그치지 않고, 다음과 같은 방식으로 실제 작업을 수행할 수 있습니다.

  • screenshot을 찍어 화면 상태 확인
  • 버튼과 링크 클릭
  • 양식과 애플리케이션에 텍스트 입력
  • 여러 애플리케이션과 브라우저 탭 사이를 이동
  • 시각적 피드백이 필요한 여러 단계의 작업 수행

이 덕분에 사용자 인터페이스와 상호작용하며 모든 것이 예상대로 동작하는지 검증해야 하는 품질 보증(QA) 테스트 같은 작업에 특히 유용합니다.

실제 사례: 자동 QA 테스트

Computer Use의 위력을 보여주는 실전 시나리오를 살펴봅니다. 자동완성 기능이 있는 React 컴포넌트를 만들었다고 가정해 봅시다. 사용자는 @를 입력해 파일이나 리소스를 멘션할 수 있습니다. 언뜻 보면 컴포넌트가 잘 동작하는 것 같지만, 엣지 케이스까지 철저히 테스트하고 싶습니다.

모든 시나리오를 직접 수동으로 테스트하는 대신, Computer Use를 갖춘 Claude가 QA 과정을 처리하도록 설정할 수 있습니다. Claude에게 실행할 구체적인 테스트 케이스를 제공합니다.

  • "Did you read @"를 입력하면 자동완성 옵션이 표시되는지 확인
  • Enter를 누르면 텍스트 영역에 멘션이 제대로 추가되는지 테스트
  • 멘션을 추가한 뒤 backspace를 누르면 자동완성 목록이 올바른 위치에 표시되는지 확인

Claude는 각 테스트 케이스를 체계적으로 수행하며 screenshot을 찍고, 인터페이스와 상호작용하고, 결과를 기록합니다. 이 예제에서 Claude는 처음 두 테스트는 통과했지만 세 번째는 실패했다는 것을 발견했습니다. 사용자가 backspace를 누르면 자동완성 드롭다운이 잘못된 위치에 나타났던 것입니다.

테스트 과정이 작동하는 방식

Claude에게 테스트 작업을 맡기면 다음과 같은 구조화된 절차를 따릅니다.

  • 브라우저를 열고 애플리케이션으로 이동
  • 각 테스트 케이스를 단계별로 실행
  • screenshot을 찍어 시각적 동작 확인
  • 테스트 사이에 페이지를 새로고침해 깨끗한 상태 유지
  • 무엇이 통과했고 실패했는지 구체적인 세부 내용과 함께 결과 기록
  • 실행 가능한 발견 사항이 담긴 요약 보고서 제공

핵심 이점은 Claude가 수동 테스트에서 놓치기 쉬운 문제를 잡아낼 수 있고, 코드를 변경할 때마다 동일한 테스트를 일관되게 실행할 수 있다는 점입니다.

Computer Use 설정하기

Computer Use는 보안을 위해 격리된 환경에서 실행됩니다. 일반적인 구성은 다음과 같습니다.

  • 데스크톱 환경을 실행하는 Docker 컨테이너
  • Claude가 제어할 수 있는 브라우저 인스턴스
  • Claude에게 지시를 내리는 채팅 인터페이스
  • 메인 시스템으로부터의 완전한 격리

이 격리는 매우 중요합니다. Claude가 개인 데이터나 시스템 보안에 아무런 위험 없이 애플리케이션과 웹사이트를 다룰 수 있다는 뜻이기 때문입니다.

Computer Use 모범 사례

Computer Use를 사용할 때는 다음 지침을 기억하세요.

  • Claude가 무엇을 테스트하거나 달성하기를 원하는지 구체적으로 지시하기
  • 각 작업에 명확한 성공 기준 제공하기
  • 복잡한 워크플로를 관리 가능한 작은 단계로 쪼개기
  • Computer Use는 항상 격리된 환경에서 실행하기
  • Claude의 발견 사항을 검토하고 중요한 결과는 직접 확인하기

Computer Use는 작업에 대해 텍스트를 생성하는 단계에서 실제로 작업을 수행하는 단계로 나아간, AI 역량의 중요한 진전을 보여줍니다. QA 테스트를 하든, 반복적인 워크플로를 자동화하든, 복잡한 애플리케이션을 탐색하든, 일관되고 문서화된 결과를 제공하면서 상당한 시간을 절약해줍니다.

Computer Use 작동 원리

🎬 영상

Claude의 Computer Use는 일반적인 tool use와 완전히 동일하게 작동합니다. 이미 익숙한 그 기반 위에 만들어졌기 때문입니다. 핵심 차이는 날씨 API나 데이터베이스 함수를 호출하는 대신, Claude가 컴퓨터 인터페이스를 제어하기 위한 요청을 보낸다는 점입니다.

tool use 복습

Computer Use를 살펴보기 전에 표준 tool use가 어떻게 작동하는지 빠르게 되짚어 봅시다. Claude가 도구를 사용하게 하려면, 사용자 메시지와 도구 스키마를 함께 담은 요청을 보냅니다. 도구 스키마는 Claude에 노출하려는 추가 기능을 설명합니다.

일반적인 흐름은 다음과 같습니다.

  • 사용 가능한 도구 스키마와 함께 질문을 Claude에 보냅니다
  • Claude가 요청을 분석해 도구를 사용해야 한다고 판단합니다
  • Claude가 도구 이름과 필요한 입력값을 담은 tool use 요청으로 응답합니다
  • 서버가 도구 함수를 실행하고 결과를 반환합니다
  • 그 도구 결과를 다시 Claude에 보냅니다

예를 들어 샌프란시스코의 날씨를 물어보면, Claude는 위치 파라미터와 함께 get_weather 함수를 호출하고, 서버는 날씨 데이터를 가져오며, 그 결과를 Claude에 반환합니다.

Computer Use: 같은 흐름, 다른 도구

Computer Use는 이와 완전히 동일한 패턴을 따릅니다. 차이는 "도구"가 실제로 하는 일에 있습니다. 날씨 데이터를 가져오는 대신, 마우스 클릭이나 키보드 입력 같은 컴퓨터 상호작용을 시뮬레이션합니다.

Computer Use를 활성화하면, 백그라운드에서 자동으로 확장되는 특별한 도구 스키마를 Claude에 보냅니다. 처음에는 단순한 스키마였던 것이, Claude가 다음과 같은 동작을 수행할 수 있다고 알려주는 포괄적인 인터페이스로 바뀝니다.

  • 마우스 이동 및 클릭
  • 키보드 입력 및 키 조합
  • screenshot 촬영
  • 스크롤 및 기타 인터페이스 상호작용

보내는 도구 스키마는 최소한이지만, Claude에게 필요한 모든 컴퓨터 상호작용 기능을 포함한 상세한 명세로 자동 변환됩니다.

기술적 구현

Computer Use가 작동하려면, Claude가 요청하는 동작을 프로그래밍적으로 실행할 수 있는 컴퓨팅 환경이 필요합니다. 레퍼런스 구현은 Firefox를 실행하는 Docker 컨테이너와, 키 입력 및 마우스 이동을 시뮬레이션할 수 있는 코드를 사용합니다.

Claude가 컴퓨터와 상호작용하기로 결정하면, 다른 도구와 마찬가지로 tool use 요청을 보냅니다. 서버는 이 요청을 받아 컨테이너 환경에서 해당 동작을 실행합니다. 버튼 클릭, 텍스트 입력, screenshot 촬영 등 무엇이든 마찬가지입니다.

중요하게 이해할 점은, Claude가 컴퓨터를 직접 제어하는 것이 아니라는 것입니다. Claude는 도구 요청을 보낼 뿐이고, 여러분의 인프라가 그 요청을 실제 컴퓨터 상호작용으로 옮깁니다.

시작하기

이 인프라를 처음부터 직접 구축할 필요는 없습니다. Anthropic은 복잡한 부분을 모두 처리해주는 레퍼런스 구현을 제공합니다.

Computer Use를 설정하려면 다음이 필요합니다.

  • 시스템에 설치된 Docker 런타임
  • 로컬에 구성된 AWS 프로필 (보통 "default")
  • Anthropic quickstarts 저장소의 레퍼런스 구현

이 준비물을 갖추면 명령 한 줄로 Docker 컨테이너를 시작할 수 있습니다. 이를 통해 시연에서 본 것과 동일한 인터페이스에 접근할 수 있습니다. 왼쪽에는 Claude와 대화하는 채팅 인터페이스가, 오른쪽에는 Claude가 웹 페이지와 애플리케이션을 다룰 수 있는 브라우저 환경이 있습니다.

설정 과정은 간단하며, 전체 설정 가이드는 GitHub의 Anthropic quickstarts 저장소에서 확인할 수 있습니다. 이 레퍼런스 구현은 안전하고 격리된 환경에서 Claude의 Computer Use 기능을 실험하기 시작하는 데 필요한 모든 것을 제공합니다.

에이전트의 특성

🎬 영상

Claude Code와 Computer Use를 살펴본 뒤에는, 무엇이 에이전트를 성공적으로 만드는지 드러내는 핵심 패턴을 짚어낼 수 있습니다. 두 도구 모두 집중된 도구 사용, 환경 인식, 반복 실행에 기반한 체계적인 문제 해결 방식을 보여줍니다.

에이전트가 실제로 작동하는 방식

특정 코너 케이스에 대한 테스트를 추가하라는 요청을 받았을 때, Claude는 명확한 도구 사용 패턴을 따랐습니다. 에이전트는 네 번의 개별 tool call을 했습니다. 두 번은 기존 파일을 읽고, 한 번은 파일을 수정하고, 한 번은 테스트를 실행하는 것이었습니다. 이 구성은 에이전트의 행동에 대해 중요한 점을 드러냅니다.

이 중 세 번의 호출은 순전히 환경에서 정보를 수집하는 것, 즉 변경하기 전에 기존 코드베이스를 이해하는 것이었습니다. 실제로 환경을 수정한 것은 단 한 번의 호출뿐입니다. 이 "먼저 관찰하고, 그다음 행동한다"는 패턴은 Claude Code와 Computer Use 양쪽에서 일관되게 나타납니다.

Computer Use도 웹 애플리케이션을 테스트할 때 같은 방식을 따릅니다. 각 tool call은 screenshot을 반환하여, 인터페이스의 현재 상태에 대한 즉각적인 시각적 피드백을 Claude에 제공합니다. 이 지속적인 피드백 루프 덕분에 에이전트는 무슨 일이 일어나는지 파악하고 그에 맞춰 다음 행동을 조정할 수 있습니다.

에이전트 방식 비교

Claude Code와 Computer Use는 이들을 효과적으로 만드는 몇 가지 근본적인 특성을 공유합니다.

  • 도구 기반 실행: 두 시스템 모두 도구를 적극적으로 사용하며, 성공 기준에 도달하거나 오류가 발생할 때까지 반복 실행합니다
  • 환경적 맥락: 상세한 프롬프트나 RAG 과정에 의존하기보다, 도구 상호작용을 통해 직접 맥락을 수집합니다
  • 집중된 도구 세트: 각 에이전트는 목적이 명확한 소수의 잘 정의된 도구를 갖습니다
  • 가치가 높고 위험이 낮은 작업: 두 도구 모두 실수를 감당할 수 있는 복잡한 문제를 다룹니다
  • 낮은 오류 비용: Computer Use는 오류 비용이 매우 낮고, Claude Code는 낮지만 무시할 수는 없는 수준입니다

효과적인 에이전트의 핵심 특성

이러한 관찰을 바탕으로, 성공적인 에이전트는 네 가지 중요한 특성을 공유합니다.

반복 실행되는 집중된 도구 세트

에이전트는 단순하고 잘 정의된 소수의 도구로 작업할 때 가장 잘 작동합니다. 반복 횟수 제한에 도달하거나, 오류를 만나거나, 성공 기준을 충족할 때까지 이 도구들을 계속 실행합니다. 이러한 반복적 접근은 방향 수정과 개선을 가능하게 합니다.

맥락이 전부다

Claude는 여러분의 특정 환경에 대한 사전 지식이 없습니다. 작업 중인 시스템의 현재 상태를 읽고 이해하려면 도구가 필요합니다. 맥락 수집의 품질은 에이전트 성능에 직접적인 영향을 미칩니다.

오류 비용이 낮은 고가치 작업

에이전트는 실수가 큰 피해를 일으키지 않는, 복잡하고 지식 집약적인 작업에서 탁월합니다. 코드 작성이 완벽한 예입니다. 상당한 전문성이 필요하지만, 오류는 치명적인 결과 없이 잡아내고 고칠 수 있습니다. 오류가 심각한 경제적·안전상의 영향을 줄 수 있는 고위험 의사결정에는 에이전트를 사용하지 마세요.

지속적인 평가

효과적인 에이전트를 만드는 유일하게 믿을 만한 방법은 엄격한 테스트입니다. 평가 기준을 만들고, 실제 시나리오에 대해 에이전트의 성능을 지속적으로 테스트하세요. 이 피드백 루프는 약점을 찾아내고 신뢰성을 높이는 데 필수적입니다.

이러한 패턴을 이해하면 Claude Code와 Computer Use가 왜 그렇게 잘 작동하는지 설명할 수 있습니다. 이들은 효과적인 에이전트 아키텍처의 이 근본 원칙들을 중심으로 설계되었습니다. 직접 에이전트를 만들 때 이 특성들을 염두에 두면, 강력하면서도 신뢰할 수 있는 시스템을 만들 수 있습니다.
