Claude 모델 개요

🎬 영상 + 요약

Claude 모델 라인업 개요 레슨입니다. Anthropic은 용도별로 여러 티어의 모델을 제공하며, Vertex AI에서도 동일한 Claude 모델들을 사용할 수 있습니다.

  • Opus — 가장 유능, 깊은 추론·복잡 분석용
  • Sonnet — 지능·속도·비용의 균형, 대부분의 프로덕션 작업
  • Haiku — 가장 빠르고 저렴, 대량·저복잡 작업(분류·추출)

실무 원칙은 “출시할 만한 출력을 내는 가장 싼 모델”을 고르는 것 — Haiku부터 시도하고 필요할 때만 티어를 올립니다.

API 접근과 요청 흐름

🎬 영상 + 요약

사용자가 메시지를 보낼 때부터 AI 응답이 돌아올 때까지의 전체 요청 라이프사이클을 이해하면 더 나은 아키텍처를 설계하고 디버깅할 수 있습니다.

전체 요청 흐름 — 5단계

사용자 입력 → AI 응답까지는 다섯 단계를 거칩니다: 서버로 요청 → Vertex로 요청 → 모델 처리 → 서버로 응답 → 클라이언트로 응답.

왜 서버가 필요한가

클라이언트 코드에서 직접 API를 호출하면 안 됩니다.

  • API 요청엔 비밀 자격증명이 필요한데, 클라이언트에 노출되면 누구나 볼 수 있음
  • 내가 통제·보호하는 서버를 중개자로 두고 그 서버가 Vertex와 통신

API 요청 만들기

서버는 Anthropic SDK 또는 Google의 공식 Vertex SDK로 통신합니다. Anthropic은 Python·TypeScript·Go·Ruby SDK를 제공합니다.

모든 요청의 핵심 필드: API Key(요청 식별), Model(모델명), Messages(사용자 입력 리스트), Max Tokens(생성 토큰 상한). 사용자 입력은 user 메시지로 감싸 messages 리스트에 넣습니다.

Claude 내부 — 텍스트 생성 4단계

Vertex가 요청을 받으면 토큰화 → 임베딩 → 문맥화 → 생성을 거칩니다.

  • 토큰화 — 입력을 토큰(단어·단어 조각·기호)으로 분할
  • 임베딩 — 각 토큰을 의미를 담은 숫자 리스트로 변환("숫자로 된 정의")

문맥화 (Contextualization)

단어는 여러 의미를 가질 수 있어(예: "quantum") 주변 단어의 문맥으로 올바른 해석을 결정합니다. 각 임베딩이 이웃에 따라 조정됩니다.

생성 (Generation)

문맥화된 임베딩이 출력층을 거쳐 다음 단어의 확률을 만들고, 확률과 무작위성을 섞어 자연스러운 단어를 고른 뒤 시퀀스에 추가하고 반복합니다.

생성이 멈추는 조건

  • Max tokens 도달 — 지정한 한계에 닿음
  • 자연스러운 종료 — end-of-sequence 토큰(보이지 않는 특수 신호) 생성
  • Stop sequence — 미리 정한 정지 문구에 도달

응답

Vertex는 Message(생성 텍스트)·Usage(입력/출력 토큰 수)·Stop Reason(멈춘 이유)을 서버로 돌려주고, 서버는 이를 클라이언트 채팅 UI로 전달합니다.

핵심: 항상 서버를 중개자로 쓰고, 텍스트 생성은 반복적 과정임을 이해하며, 응답 메타데이터로 사용량·모델 동작을 모니터링하라.

첫 요청 보내기

🎬 영상 + 요약

Anthropic Python SDK로 Vertex AI를 통해 Claude에 첫 요청을 보냅니다 — SDK 설치 → 클라이언트 생성 → 호출.

SDK 설치

%pip install "anthropic[vertex]"

[vertex]는 Vertex AI 연결에 필요한 구성요소를 함께 설치합니다.

클라이언트 생성

from anthropic import AnthropicVertex

client = AnthropicVertex(region="global", project_id="your-project-id")
model = "claude-sonnet-4@20250514"

your-project-id는 실제 Google Cloud 프로젝트 ID로 교체. 모델을 변수로 두면 반복 타이핑을 줄입니다.

create 함수 — 세 가지 핵심 파라미터

  • model — 사용할 Claude 모델명
  • max_tokens — 응답 길이 안전 상한(목표가 아니라 상한, 넘지만 않음)
  • messages — Claude에 보내는 대화 기록

max_tokens는 목표가 아니라 예산으로 생각하세요.

메시지 이해

  • User 메시지 — 사람이 작성해 Claude에 넣는 내용
  • Assistant 메시지 — Claude가 생성해 돌려준 내용

첫 요청 구조

message = client.messages.create(
    model=model,
    max_tokens=1000,
    messages=[
        {"role": "user", "content": "What is quantum computing? Answer in one sentence"}
    ]
)

응답에서 텍스트 추출

message.content[0].text

복잡한 응답 객체 전체 대신 생성된 텍스트만 깔끔하게 뽑는 자주 쓰는 패턴입니다.

멀티턴 대화

🎬 영상 + 요약

Claude는 대화 기록을 저장하지 않습니다. 매 요청이 완전히 독립적 — 이전 교환을 기억하지 못합니다.

따라서 멀티턴 대화를 하려면 대화 상태를 직접 관리해야 합니다.

무상태 대화의 문제

"양자컴퓨팅이 뭐야?" 다음에 "한 문장 더 써줘"라고 하면, 기록이 없는 Claude는 무엇을 가리키는지 몰라 엉뚱한 문장을 씁니다.

멀티턴이 동작하는 방식

  • 코드에서 모든 메시지 리스트를 직접 유지
  • 매 요청마다 전체 기록을 함께 전송

흐름: 사용자 메시지 전송 → 응답을 assistant 메시지로 리스트에 추가 → 후속 질문을 user 메시지로 추가 → 전체 기록을 다시 전송.

헬퍼 함수

def add_user_message(messages, text):
    messages.append({"role": "user", "content": text})

def add_assistant_message(messages, text):
    messages.append({"role": "assistant", "content": text})

def chat(messages):
    message = client.messages.create(
        model=model, max_tokens=1000, messages=messages,
    )
    return message.content[0].text

조합해서 사용

messages = []
add_user_message(messages, "Define quantum computing in one sentence")
answer = chat(messages)
add_assistant_message(messages, answer)
add_user_message(messages, "Write another sentence")
final_answer = chat(messages)
기억할 것: 모든 호출은 독립적. 문맥을 유지하려면 메시지를 로컬 저장하고 전체 기록을 매번 전송하며 user/assistant 역할을 올바르게 포맷하라.

시스템 프롬프트

🎬 영상 + 요약

시스템 프롬프트는 Claude의 톤·스타일·접근을 내 용도에 맞게 빚는 강력한 방법입니다.

왜 중요한가 — 수학 튜터 예시

"5x + 2 = 3을 어떻게 풀어?"라는 질문에 정답만 뱉는 대신 진짜 튜터처럼:

  • 정답 대신 힌트를 먼저 주고, 단계별로 인내심 있게 안내
  • 비슷한 문제의 풀이를 예시로 제시

피해야 할 것: 즉시 직접 답 주기, "계산기 쓰라"고 하기.

작동 방식

시스템 프롬프트는 평범한 문자열로 정의해 create 호출의 system에 넘깁니다. 지정한 역할처럼 응답하도록 유도하고 Claude를 과제에 집중시킵니다.

system_prompt = """
You are a patient math tutor.
Do not directly answer a student's questions.
Guide them to a solution step by step.
"""

client.messages.create(
    model=model, messages=messages,
    max_tokens=1000, system=system_prompt
)

유연한 chat 함수

def chat(messages, system=None):
    params = {"model": model, "max_tokens": 1000, "messages": messages}
    if system:
        params["system"] = system
    message = client.messages.create(**params)
    return message.content[0].text
Claude API는 system=None을 받지 않으므로, system 파라미터는 제공될 때만 조건부로 포함하세요.

Temperature

🎬 영상 + 요약

Temperature는 응답의 예측 가능성 vs 창의성을 조절하는 파라미터입니다.

텍스트 생성 3단계

  • 토큰화 → 예측(다음 단어 확률 계산) → 샘플링(확률 기반 선택)

Temperature가 하는 일

0~1 사이 소수값. 낮으면(≈0) 결정적 — 최고 확률 토큰을 거의 항상 선택. 높으면(≈1) 확률을 고르게 퍼뜨려 다양·창의적 출력.

범위별 용도

범위용도
낮음 (0.0–0.3)사실 응답·코딩·데이터 추출·콘텐츠 모더레이션
중간 (0.4–0.7)요약·교육 콘텐츠·문제 해결·제약 있는 창작
높음 (0.8–1.0)브레인스토밍·창작·마케팅·유머 생성

코드로 구현

def chat(messages, system=None, temperature=1.0):
    params = {"model": model, "max_tokens": 1000,
              "messages": messages, "temperature": temperature}
    if system:
        params["system"] = system
    message = client.messages.create(**params)
    return message.content[0].text
Temperature는 다른 출력을 보장하지 않고 확률만 바꿉니다. 일관·사실엔 낮게, 창의·다양성엔 높게 — 과제에 맞춰 조정하세요.

응답 스트리밍

🎬 영상 + 요약

응답 생성엔 10~30초가 걸려 사용자가 스피너만 보게 됩니다. 응답 스트리밍은 텍스트를 조각 단위로 즉시 보여줘 훨씬 반응성 있는 경험을 줍니다.

표준 응답의 문제

전체 응답이 완성될 때까지 클라이언트로 아무것도 안 보내 어색한 지연이 생깁니다.

스트리밍 동작

Claude가 즉시 시작 신호를 보내고, 이후 작은 조각들을 연속 이벤트로 전달 — 모두 단일 요청의 일부입니다.

스트림 이벤트 종류

  • MessageStart · ContentBlockStart · ContentBlockDelta(실제 텍스트 조각) · ContentBlockStop · MessageDelta · MessageStop

ContentBlockDelta에 사용자에게 표시할 실제 텍스트가 담깁니다.

기본 구현

stream = client.messages.create(
    model=model, max_tokens=1000, messages=messages, stream=True
)
for event in stream:
    print(event)

간편 텍스트 스트리밍

with client.messages.stream(
    model=model, max_tokens=1000, messages=messages
) as stream:
    for text in stream.text_stream:
        print(text, end="")

최종 메시지 얻기

with client.messages.stream(...) as stream:
    for text in stream.text_stream:
        pass  # 실제 앱에선 클라이언트로 전송
    final_message = stream.get_final_message()
각 조각은 단어 하나가 아니라 여러 단어/문장일 수 있습니다. 프로덕션에선 WebSocket·SSE로 조각을 즉시 전달하고 서버엔 전체 기록을 유지합니다.

출력 제어

🎬 영상 + 요약

더 나은 프롬프트 외에도 출력을 정밀 제어하는 두 기법: assistant 메시지 프리필과 stop sequence.

Assistant 메시지 프리필

Claude 응답의 시작을 미리 제공하면 그 지점부터 이어 씁니다.

"차와 커피 중 뭐가 나아?"에 프리필 없이 물으면 균형 잡힌 답이 오지만, "Coffee is better because"를 assistant 메시지로 넣으면 커피 옹호로 이어집니다. Claude는 프리필 텍스트를 반복하지 않고 그 뒤부터 완성합니다.

messages = []
add_user_message(messages, "Is tea or coffee better at breakfast?")
add_assistant_message(messages, "Coffee is better because")
answer = chat(messages)

Stop Sequences

지정한 문자열이 생성되면 즉시 멈추고 그때까지의 내용을 반환합니다.

add_user_message(messages, "Count from 1 to 10")
answer = chat(messages, stop_sequences=["5"])
# "1, 2, 3, 4, " (5 직전에서 멈춤)

더 정밀하게 stop_sequences=[", 5"]로 하면 "1, 2, 3, 4"로 깔끔.

프롬프트 평가란?

🎬 영상 + 요약

좋은 프롬프트를 쓰는 것은 시작일 뿐. 신뢰할 앱을 만들려면 프롬프트 엔지니어링(더 나은 프롬프트를 쓰는 기법)과 프롬프트 평가(그게 실제로 잘 동작하는지 측정)를 모두 알아야 합니다.

엔지니어링 vs 평가

구분내용
프롬프트 엔지니어링멀티샷·XML 구조화 등 프롬프트를 쓰고 개선하는 기법 툴킷
프롬프트 평가프롬프트가 실제로 효과적인지 객관적 지표로 재는 자동 테스트

평가로 할 수 있는 것: 기대 답과 비교, 프롬프트 버전 비교, 출력 오류 검토.

프롬프트를 쓴 뒤의 세 갈래

  • 옵션 1 — 한 번 테스트하고 "충분해" (프로덕션에서 깨질 위험 큼)
  • 옵션 2 — 몇 번 테스트 후 코너케이스 한둘 손봄 (예상 못한 입력엔 여전히 실패)
  • 옵션 3 — 평가 파이프라인으로 점수 매기고 데이터 기반으로 반복 (선투자 크지만 신뢰 큼)
옵션 1·2는 모든 엔지니어가 빠지는 함정. 사용자가 어떻게 쓸지 다 예측할 수 없으므로, 진지한 앱엔 객관적 데이터로 반복하는 옵션 3이 정답입니다.

도구 사용 소개

🎬 영상 + 요약

도구(tool)는 Claude가 외부 세계의 정보에 접근하게 해 훈련 데이터 너머로 능력을 확장합니다. 실시간 데이터·외부 시스템에 대한 구조화된 접근 방법입니다.

도구 없을 때의 문제

"샌프란시스코 날씨는?"에 Claude는 "실시간 날씨 정보에 접근할 수 없습니다"라고 답할 수밖에 없습니다.

도구 사용 흐름

  • 초기 요청 — 질문 + 외부 데이터 획득 방법(도구)을 함께 전송
  • 도구 요청 — Claude가 필요를 판단해 어떤 데이터가 필요한지 요청
  • 데이터 획득 — 내 서버가 외부 API/DB에서 정보 조회
  • 최종 응답 — 데이터를 Claude에 돌려주면 완전한 응답 생성

날씨 예시

Claude가 특정 위치의 날씨를 요청 → 서버가 날씨 API 호출 → 결과를 Claude에 전달 → 정확한 최신 응답.

도구 사용은 Claude를 정적 지식 베이스에서 라이브 데이터로 일하는 동적 어시스턴트로 바꿉니다. 도구를 실행하는 건 Claude가 아니라 내 코드입니다.

def get_current_datetime(date_format="%Y-%m-%d %H:%M:%S"):
    if not date_format:
        raise ValueError("date_format cannot be empty")
    return datetime.now().strftime(date_format)
get_current_datetime("%H:%M")       # "14:30"
get_current_datetime("%B %d, %Y")   # "March 15, 2024"

텍스트 청킹 전략

🎬 영상 + 요약

텍스트 청킹은 RAG의 가장 중요한 단계 중 하나 — 잘못하면 엉뚱한 문맥이 들어가 완전히 틀린 답이 나옵니다.

세 가지 전략

  • Size-based — 동일 길이 문자열로 분할
  • Structure-based — 헤더·문단·섹션 등 구조로 분할
  • Semantic-based — NLP로 의미 관련 문장 묶음

Size-based + 오버랩

def chunk_by_char(text, chunk_size=150, chunk_overlap=20):
    chunks = []
    start_idx = 0
    while start_idx < len(text):
        end_idx = min(start_idx + chunk_size, len(text))
        chunks.append(text[start_idx:end_idx])
        start_idx = (end_idx - chunk_overlap if end_idx < len(text) else len(text))
    return chunks

Structure-based

def chunk_by_section(document_text):
    pattern = r'\n## '
    return re.split(pattern, document_text)

Sentence-based (중간 지점)

def chunk_by_sentence(text, max_sentences_per_chunk=5, overlap_sentences=1):
    sentences = re.split(r'(?<=[.!?])\s+', text)
    chunks = []
    start_idx = 0
    while start_idx < len(sentences):
        end_idx = min(start_idx + max_sentences_per_chunk, len(sentences))
        chunks.append(' '.join(sentences[start_idx:end_idx]))
        start_idx += max_sentences_per_chunk - overlap_sentences
    return chunks
일관된 구조 → structure-based, 혼합 유형 → sentence-based, 코드/미지 포맷 → character-based. 청킹은 반복 과정 — 단순하게 시작해 데이터에 맞춰 다듬으세요.

🎬 영상 + 요약

프롬프트 캐싱은 이전 요청의 계산 작업을 재사용해 응답을 빠르고 저렴하게 합니다.

캐싱 규칙

🎬 영상 + 요약

캐싱 규칙을 정리합니다. 초기 요청이 캐시에 쓰고, 후속 요청이 읽습니다(수명 5분).

캐시 브레이크포인트

자동 캐싱이 아니라 수동으로 breakpoint를 블록에 추가. 그 지점까지의 작업이 캐시되고, 그 지점까지 콘텐츠가 동일할 때만 재사용.

// Shorthand - breakpoint 불가
user_message = {"role": "user", "content": "Hi there!"}

// Longhand - breakpoint 필요
user_message = {
    "role": "user",
    "content": [{
        "type": "text", "text": "",
        "cache_control": {"type": "ephemeral"}
    }]
}

브레이크포인트 동작

메시지를 넘나들며 assistant 메시지도 캐시 가능. 콘텐츠가 반드시 동일해야 함.

위치 — 시스템 프롬프트·도구 정의

tools = [
    add_duration_to_datetime_schema,
    get_current_datetime_schema,
    {"name": "set_reminder", "description": "...",
     "input_schema": {...}, "cache_control": {"type": "ephemeral"}}
]
system = [{"type": "text", "text": "You are a senior software...",
           "cache_control": {"type": "ephemeral"}}]

캐시 순서

내부 결합 순서: tools → system → messages. 최대 4개 breakpoint. 마지막 도구에 breakpoint를 두면 그 도구까지만 캐시.

최소 길이

캐시하려는 콘텐츠 합계가 1024토큰 이상이어야 함. "Hi there!"는 미달.

MCP 소개

🎬 영상 + 요약

MCP(Model Context Protocol)는 지루한 통합 코드 없이 Claude에 컨텍스트·도구를 제공하는 통신 계층입니다. 모든 도구 함수를 직접 만드는 대신 전문 서버에 그 부담을 넘깁니다.

기본 구조: MCP Client(내 서버)가 도구·프롬프트·리소스를 담은 MCP Server에 연결. 각 서버는 GitHub·AWS·DB 등 외부 서비스의 인터페이스.

MCP가 푸는 문제

GitHub 데이터를 다루려면 방대한 도구가 필요합니다.

  • get_repos() · list_repos() · search_issues() · create_issue() · create_file() …

MCP가 바꾸는 것

누군가(종종 서비스 제공자)가 GitHub용 MCP Server를 만들어 필요한 도구를 담고, 내 서버는 MCP Client로 그에 연결합니다.

누가 만드나

누구나 만들 수 있고, 공식 구현(예: AWS)도 있습니다. 직접 만들 수도 있습니다.

자주 묻는 질문

  • API 직접 호출과 뭐가 다른가? — MCP는 도구 스키마·함수를 이미 정의해 줌
  • 도구 사용과 같은 건가? — 아님. MCP는 도구 구현을 누가 만들고 유지보수하느냐에 관한 것

리소스 정의

🎬 영상 + 요약

리소스는 클라이언트에 데이터를 노출하는 읽기 전용 엔드포인트(HTTP GET 핸들러와 유사)입니다.

URI를 정의하면 클라이언트가 ReadResourceRequest를 보내고 서버가 ReadResourceResult로 응답. mime_type으로 데이터 유형 힌트.

두 유형

  • Direct — 파라미터 없는 정적 URI("docs://documents")
  • Templated — URI에 파라미터("docs://documents/{doc_id}"). SDK가 파싱해 인자로 전달

구현

@mcp.resource("docs://documents", mime_type="application/json")
def list_docs() -> list[str]:
    return list(docs.keys())

@mcp.resource("docs://documents/{doc_id}", mime_type="text/plain")
def fetch_doc(doc_id: str) -> str:
    if doc_id not in docs:
        raise ValueError(f"Doc with id {doc_id} not found")
    return docs[doc_id]

SDK가 반환값을 자동 직렬화 — JSON 수동 변환 불필요.

테스트

uv run mcp dev mcp_server.py로 인스펙터에서 Resources / Resource Templates 확인.

활용: "@" 멘션 자동완성(direct 리소스로 문서 목록), 멘션된 문서 내용(templated 리소스)을 프롬프트에 선제 주입.

MCP 정리

🎬 영상 + 요약

MCP의 세 핵심 프리미티브를 정리합니다 — 누가 제어하느냐가 핵심.

Tools — 모델 제어

Claude가 언제 호출할지 결정. 능력을 확장할 때 사용(예: JS로 √3 계산).

Resources — 앱 제어

내 앱 코드가 언제 가져올지 결정. 자동완성 옵션, 메시지 문맥 추가, 문서 목록 표시 등 UI·문맥용.

Prompts — 사용자 제어

사용자 액션(버튼·메뉴·슬래시 커맨드)으로 트리거. 대화 시작·작업 템플릿·특화 워크플로우.

실제 예

Claude 공식 UI의 대화 시작 버튼=프롬프트, "Add from Google Drive"=리소스, 계산·코드 실행=도구.

결정 가이드: 능력 확장→Tools, 앱 UI·문맥 데이터→Resources, 미리 정의된 워크플로우→Prompts. 도구는 모델을, 리소스는 앱을, 프롬프트는 사용자를 섬깁니다.

에이전트와 도구

🎬 영상 + 요약

에이전트는 구조화된 워크플로우와 달리, 경로가 불분명할 때 빛납니다. 목표 + 도구를 주고 Claude가 조합 방법을 찾게 합니다.

한 번 만들어 다양한 작업에 배포할 수 있으나, 신뢰성·비용 문제가 따릅니다.

도구가 에이전트를 만든다

  • get_current_datetime · add_duration_to_datetime · set_reminder

"지금 몇 시?"엔 하나, "11일 뒤 무슨 요일?"엔 둘을 체이닝, "다음 수요일 헬스장 리마인더"엔 셋 모두. "90일 보증 언제 끝나?"엔 필요 정보를 사용자에게 되묻고 계산.

도구는 추상적으로
