API 접근 방식

🎬 영상 + 요약

Claude로 애플리케이션을 만들 때 요청의 전체 생명주기를 이해하면 더 나은 아키텍처 결정을 내리고 문제를 효과적으로 디버깅할 수 있습니다. 사용자가 채팅 화면에서 "전송"을 누른 순간부터 Claude의 응답이 화면에 나타나기까지 무슨 일이 일어나는지 따라가 봅니다.

다섯 단계 요청 흐름

Claude와의 모든 상호작용은 다섯 개의 뚜렷한 단계를 따릅니다: 서버로의 요청, Anthropic API로의 요청, 모델 처리, 서버로의 응답, 클라이언트로의 응답.

왜 서버가 필요한가

클라이언트 코드에서 Anthropic API를 직접 호출해서는 절대 안 됩니다. 이유는 다음과 같습니다:

  • API 요청에는 인증을 위한 비밀 API 키가 필요합니다
  • 이 키를 클라이언트 코드에 노출하면 심각한 보안 취약점이 됩니다
  • 누구나 키를 추출해 무단으로 요청을 보낼 수 있습니다

대신 웹/모바일 앱은 자신의 서버로 요청을 보내고, 서버가 안전하게 저장된 키로 Anthropic API와 통신합니다.

API 요청 만들기

서버가 Anthropic API에 접속할 때는 공식 SDK를 쓰거나 일반 HTTP 요청을 보낼 수 있습니다. Anthropic은 Python, TypeScript, JavaScript, Go, Ruby용 SDK를 제공합니다.

모든 요청에는 다음 필수 필드가 포함되어야 합니다:

  • API Key - Anthropic에 요청 주체를 식별시킵니다
  • Model - 사용할 모델 이름 (예: "claude-3-sonnet")
  • Messages - 사용자 입력 텍스트를 담은 리스트
  • Max Tokens - Claude가 생성할 수 있는 토큰 수의 상한

Claude 내부의 처리 과정

Anthropic이 요청을 받으면 Claude는 네 가지 주요 단계로 처리합니다: 토큰화(tokenization), 임베딩(embedding), 문맥화(contextualization), 생성(generation).

토큰화

Claude는 먼저 입력 텍스트를 토큰이라는 작은 조각으로 나눕니다. 토큰은 단어 전체, 단어의 일부, 공백, 기호일 수 있습니다. 단순하게는 단어 하나를 토큰 하나로 생각하면 됩니다.

임베딩

각 토큰은 임베딩으로 변환됩니다. 임베딩은 그 단어가 가질 수 있는 모든 의미를 표현하는 긴 숫자 목록으로, 의미적 관계를 담은 "수치화된 정의"라고 볼 수 있습니다.

단어는 종종 여러 의미를 가집니다. 예를 들어 "quantum"은 다음을 가리킬 수 있습니다:

  • 물리량의 이산적 단위 (물리학)
  • 양자역학 또는 양자물리 개념
  • 극도로 작거나 아원자적인 것
  • 양자 컴퓨팅 응용

문맥화

Claude는 주변 단어를 바탕으로 각 임베딩을 다듬어 문맥상 가장 그럴듯한 의미를 결정합니다. 이 과정에서 수치 표현이 조정되어 적절한 의미가 부각됩니다.

생성

문맥화된 임베딩은 출력 레이어를 거쳐 다음에 올 수 있는 각 단어의 확률을 계산합니다. Claude는 항상 최고 확률 단어만 고르지 않고, 확률과 통제된 무작위성을 섞어 자연스럽고 다양한 응답을 만듭니다.

단어를 하나 고른 뒤에는 그것을 시퀀스에 추가하고, 다음 단어를 위해 전체 과정을 반복합니다.

Claude가 생성을 멈추는 시점

각 토큰 이후 Claude는 계속할지 말지를 결정하기 위해 여러 조건을 확인합니다:

  • Max tokens 도달 - 지정한 상한에 닿았는가?
  • 자연스러운 종료 - 문장 종료(end-of-sequence) 토큰을 생성했는가?
  • Stop sequence - 미리 정의한 정지 문구를 만났는가?

API 응답

생성이 끝나면 API는 구조화된 응답을 돌려줍니다:

  • Message - 생성된 텍스트
  • Usage - 입력·출력 토큰 수
  • Stop Reason - 생성이 끝난 이유

서버는 이 응답을 받아 생성된 텍스트를 클라이언트 앱으로 전달하고, 사용자 화면에 표시됩니다.

핵심 정리

  • API 키를 보호하는 안전한 아키텍처 설계
  • 용도에 맞는 토큰 상한 설정
  • 애플리케이션 로직에서 다양한 stop reason 처리
  • 파이프라인의 어느 지점에서 문제가 생기는지 이해해 디버깅
모든 세부사항을 외울 필요는 없습니다. 목표는 Claude API를 다룰 때 마주칠 용어와 전체 흐름에 익숙해지는 것입니다.

API 키 발급

🎬 영상 + 요약

다음 영상에서 Anthropic API로 요청을 보내려면 비밀 API 키가 필요합니다. 여기서는 키를 만드는 과정을 단계별로 안내합니다.

1단계: Anthropic API 콘솔로 이동

브라우저에서 https://console.anthropic.com/ 로 이동해 Anthropic 계정으로 로그인하면 아래와 같은 페이지가 보입니다.

메인 대시보드 페이지의 오른쪽 상단에서 이 버튼을 찾을 수 있습니다.

3단계: 'Create Key' 버튼 클릭

페이지 오른쪽 상단의 'Create Key' 버튼을 눌러줍니다.

4단계: 워크스페이스와 키 이름 입력

첫 요청 보내기

🎬 영상 + 요약

기본 설정과 구조만 이해하면 Anthropic API로 첫 요청을 보내는 일은 어렵지 않습니다. 여기서는 Python으로 Claude가 프롬프트에 응답하게 하는 핵심 단계를 살펴봅니다.

환경 설정

API 호출 전에 필요한 패키지를 설치하고 API 키를 안전하게 구성해야 합니다. 먼저 Jupyter 노트북에서 의존성을 설치합니다:

%pip install anthropic python-dotenv

다음으로 노트북과 같은 디렉터리에 .env 파일을 만들어 API 키를 안전하게 저장합니다:

ANTHROPIC_API_KEY="your-api-key-here"

이렇게 하면 API 키가 코드 밖에 유지되어 버전 관리에 실수로 커밋되는 일을 막습니다. 항상 .env를 .gitignore에 추가하세요.

환경 변수를 로드하고 API 클라이언트를 생성합니다:

from dotenv import load_dotenv
load_dotenv()

from anthropic import Anthropic

client = Anthropic()
model = "claude-sonnet-4-0"

create 함수

API 요청의 핵심은 client.messages.create() 함수입니다. 이 함수는 세 가지 주요 매개변수를 필요로 합니다:

  • model - 사용할 Claude 모델 이름
  • max_tokens - 응답 길이의 안전 상한 (목표치가 아님)
  • messages - Claude에게 보내는 대화 이력

max_tokens는 안전장치 역할을 합니다. 1000으로 설정하면 Claude는 더 할 말이 있어도 1000 토큰에서 생성을 멈춥니다. Claude는 이 상한에 도달하려 애쓰지 않고, 적절하다고 판단한 만큼만 쓴 뒤 상한에 닿으면 멈춥니다.

Messages 이해하기

Messages는 채팅 앱처럼 사용자와 Claude 사이의 대화를 나타냅니다. 메시지에는 두 가지 유형이 있습니다:

  • User 메시지 - Claude에게 보내려는 내용 (사람이 작성)
  • Assistant 메시지 - Claude가 생성한 응답

각 메시지는 role("user" 또는 "assistant")과 content(실제 텍스트)를 가진 딕셔너리입니다.

첫 요청 만들기

Claude에 요청을 보내는 전체 예시입니다:

message = client.messages.create(
model=model,
max_tokens=1000,
messages=[
{
"role": "user",
"content": "What is quantum computing? Answer in one sentence"
}
]
)

이 코드를 실행하면 Claude가 요청을 처리하고, 생성된 텍스트와 요청 메타데이터를 담은 응답 객체를 반환합니다.

응답 추출하기

응답 객체에는 많은 정보가 있지만 보통 필요한 건 생성된 텍스트뿐입니다. 다음처럼 접근합니다:

message.content[0].text
이 몇 가지 기본기만 갖추면 다양한 프롬프트를 실험하고 Claude와 더 복잡한 상호작용을 만들어 나갈 수 있습니다.

멀티턴 대화

🎬 영상 + 요약

Anthropic API를 다룰 때 반드시 알아야 할 핵심 개념이 있습니다. Claude는 대화 이력을 전혀 저장하지 않습니다. 모든 요청은 완전히 독립적이며 이전 교환에 대한 기억이 없습니다.

따라서 Claude가 앞선 메시지의 문맥을 기억하는 멀티턴 대화를 하려면 대화 상태를 직접 관리해야 합니다.

무상태 대화의 문제

예를 들어 "양자 컴퓨팅이 뭐야?"라고 묻고 좋은 답을 받은 뒤 "한 문장 더 써줘"라고 이어 물으면, Claude는 무엇을 가리키는지 전혀 모릅니다. 양자 컴퓨팅 이야기를 기억하지 못하므로 전혀 엉뚱한 문장을 씁니다.

멀티턴 대화의 작동 원리

대화 문맥을 유지하려면 두 가지를 해야 합니다:

  • 코드에서 모든 메시지 목록을 직접 관리
  • 매 요청마다 전체 메시지 이력을 함께 전송

실제로 작동하는 흐름은 다음과 같습니다:

  1. 초기 user 메시지를 Claude에 전송
  2. Claude의 응답을 assistant 메시지로 메시지 목록에 추가
  3. 후속 질문을 또 다른 user 메시지로 추가
  4. 전체 대화 이력을 Claude에 전송

헬퍼 함수 만들기

대화 관리를 쉽게 하기 위해 세 개의 헬퍼 함수를 만들 수 있습니다:

def add_user_message(messages, text):
user_message = {"role": "user", "content": text}
messages.append(user_message)

def add_assistant_message(messages, text):
assistant_message = {"role": "assistant", "content": text}
messages.append(assistant_message)

def chat(messages):
message = client.messages.create(
model=model,
max_tokens=1000,
messages=messages,
)
return message.content[0].text

모두 합치기

이 함수들로 대화를 유지하는 방법입니다:

# Start with an empty message list
messages = []

# Add the initial user question
add_user_message(messages, "Define quantum computing in one sentence")

# Get Claude's response
answer = chat(messages)

# Add Claude's response to the conversation history
add_assistant_message(messages, answer)

# Add a follow-up question
add_user_message(messages, "Write another sentence")

# Get the follow-up response with full context
final_answer = chat(messages)
전체 대화 문맥을 제공했기 때문에 이제 Claude는 "한 문장 더 써줘"가 양자 컴퓨팅 정의를 확장하라는 뜻임을 이해합니다. 이 헬퍼 함수들은 이후 작업 내내 유용하게 쓰입니다.

시스템 프롬프트

🎬 영상 + 요약

시스템 프롬프트는 Claude가 사용자 입력에 응답하는 방식을 커스터마이즈하는 강력한 방법입니다. 일반적인 답변 대신, 용도에 맞게 Claude의 어조·스타일·접근 방식을 형성할 수 있습니다.

시스템 프롬프트가 중요한 이유

수학 튜터 챗봇을 만든다고 해봅시다. 학생이 "5x + 2 = 3에서 x를 어떻게 풀어?"라고 물으면, Claude가 답만 뱉지 않고 실제 튜터처럼 행동하길 원할 것입니다. 좋은 수학 튜터라면:

  • 완전한 풀이 대신 처음엔 힌트를 준다
  • 단계별로 인내심 있게 안내한다
  • 유사 문제의 풀이를 예시로 보여준다

반대로 원치 않는 행동은:

  • 즉시 직접적인 답을 주는 것
  • 그냥 계산기를 쓰라고 말하는 것

시스템 프롬프트의 작동 방식

시스템 프롬프트는 응답 방식에 대한 지침을 Claude에 제공합니다. 일반 문자열로 정의해 create 함수 호출에 전달합니다. 주요 이점은:

  • 응답 방식에 대한 지침을 Claude에 제공
  • Claude가 지정된 역할의 사람처럼 응답하려고 시도
  • Claude가 과제에서 벗어나지 않도록 유지

기본 구조는 다음과 같습니다:

system_prompt = """
You are a patient math tutor.
Do not directly answer a student's questions.
Guide them to a solution step by step.
"""

client.messages.create(
model=model,
messages=messages,
max_tokens=1000,
system=system_prompt
)

차이 확인하기

시스템 프롬프트가 없으면 Claude는 즉시 완전한 단계별 풀이를 줍니다. 도움이 될 수는 있지만 학생이 스스로 생각하도록 유도하지는 않습니다. 수학 튜터 시스템 프롬프트를 넣으면, Claude는 전체 풀이 대신 "x를 고립시키려면 어떤 첫 단계가 좋을까요? 양변에 어떤 연산을 해야 할지 생각해보세요."처럼 유도하는 질문을 던집니다.

유연한 chat 함수 만들기

시스템 프롬프트를 하드코딩하는 대신 매개변수로 받으면 chat 함수를 더 재사용하기 좋게 만들 수 있습니다:

def chat(messages, system=None):
params = {
"model": model,
"max_tokens": 1000,
"messages": messages,
}

if system:
params["system"] = system

message = client.messages.create(**params)
return message.content[0].text

이 방식은 중요한 세부사항을 처리합니다. Claude API는 system=None을 받지 않으므로, 값이 제공될 때만 조건부로 system 매개변수를 포함해야 합니다. 이제 시스템 프롬프트 유무에 따라 호출할 수 있습니다:

# Without system prompt
answer = chat(messages)

# With system prompt
system = """
You are a patient math tutor.
Do not directly answer a student's questions.
Guide them to a solution step by step.
"""
answer = chat(messages, system=system)
시스템 프롬프트는 일관되고 목적에 맞게 동작하는 AI 애플리케이션을 만드는 데 필수입니다. 일반적인 응답을 역할에 맞는 특화된 상호작용으로 바꿔줍니다.

Temperature

🎬 영상 + 요약

Temperature는 Claude 응답이 얼마나 예측 가능한지 또는 창의적인지를 조절하는 강력한 매개변수입니다. 잘 활용하면 AI 애플리케이션의 품질을 크게 높일 수 있습니다.

Claude의 텍스트 생성 방식

temperature를 다루기 전에 Claude의 생성 과정을 이해하면 도움이 됩니다. "What do you think?" 같은 프롬프트를 보내면 세 단계를 거칩니다:

  • 토큰화 - 입력을 작은 조각으로 분해
  • 예측 - 가능한 다음 단어들의 확률 계산
  • 샘플링 - 그 확률에 근거해 토큰 선택

이 예에서 Claude는 "about"에 30%, "would"에 20%, "of"에 10% 식으로 확률을 부여할 수 있습니다. 그런 다음 토큰 하나를 골라 이 과정을 반복해 완전한 문장을 만듭니다.

Temperature가 하는 일

Temperature는 0과 1 사이의 소수값으로 이 선택 확률에 직접 영향을 줍니다. Claude 응답의 "창의성 다이얼"과 같습니다. 낮은 temperature(0에 가까움)에서는 거의 항상 최고 확률 토큰을 골라 매우 결정적입니다. 높은 temperature(1에 가까움)에서는 확률이 더 고르게 퍼져 다양하고 창의적인 출력이 나옵니다.

인터랙티브 데모

temperature 0.0에서는 "about"이 100% 확률을 받아 완전히 결정적입니다. 1.0에서는 확률이 모든 가능한 토큰에 더 고르게 퍼져 무작위성과 창의성이 생깁니다.

적절한 Temperature 고르기

과제마다 다른 temperature 범위가 어울립니다.

Temperature 범위적합한 용도
낮음 (0.0 – 0.3)사실 응답, 코딩 지원, 데이터 추출, 콘텐츠 검열
중간 (0.4 – 0.7)요약, 교육 콘텐츠, 문제 해결, 제약이 있는 창작
높음 (0.8 – 1.0)브레인스토밍, 창작 글쓰기, 마케팅 콘텐츠, 농담 생성

코드에서 Temperature 구현

기존 chat 함수에 temperature 지원을 추가하는 건 간단합니다:

def chat(messages, system=None, temperature=1.0):
params = {
"model": model,
"max_tokens": 1000,
"messages": messages,
"temperature": temperature
}

if system:
params["system"] = system

message = client.messages.create(**params)
return message.content[0].text

핵심 변경은 temperature=1.0 매개변수를 추가하고 params 딕셔너리에 "temperature": temperature를 포함한 것입니다.

Temperature 효과 테스트

영화 아이디어를 서로 다른 설정으로 생성해 효과를 볼 수 있습니다:

# Low temperature - more predictable
answer = chat(messages, temperature=0.0)

# High temperature - more creative
answer = chat(messages, temperature=1.0)

0.0에서는 "시간여행 고고학자가 고대 유물 도난을 막아야 한다" 같은 응답이 반복적으로 나올 수 있고, 1.0에서는 주제·인물·전개에서 훨씬 다양한 결과를 보게 됩니다.

Temperature는 다른 출력을 보장하지 않고 확률만 바꿉니다. 높은 temperature에서도 비슷한 응답이 나올 수 있습니다. 핵심은 용도에 맞게 temperature를 선택하는 것입니다. 일관·사실적 응답엔 낮게, 창의적 브레인스토밍엔 높게, 그 중간의 일반 과제엔 중간값이 잘 맞습니다.

응답 스트리밍

🎬 영상 + 요약

Claude로 채팅 앱을 만들 때 큰 UX 과제가 있습니다. 응답 생성에 10~30초가 걸려 사용자가 로딩 스피너만 보고 있게 됩니다. 해결책은 응답 스트리밍으로, Claude가 생성하는 대로 텍스트가 조각조각 나타나 훨씬 반응성 있게 느껴집니다.

일반 응답의 문제

일반적인 채팅 구조에서는 서버가 user 메시지를 Claude에 보내고 완전한 응답을 받을 때까지 기다린 뒤에야 클라이언트에 무언가를 보냅니다. 그 사이 사용자는 아무 피드백 없이 어색한 지연을 겪습니다.

스트리밍의 작동 방식

스트리밍을 켜면 Claude는 요청을 받아 생성을 시작한다는 초기 응답을 즉시 보냅니다. 이후 각각 전체 응답의 작은 조각을 담은 이벤트들이 연이어 도착합니다.

서버는 이 텍스트 조각들을 도착하는 대로 클라이언트에 전달해, 사용자가 응답이 단어 단위로 쌓이는 것을 볼 수 있게 합니다. 이 모든 이벤트는 Claude로의 단일 요청에 속합니다.

스트림 이벤트 이해하기

스트리밍을 켜면 Claude는 여러 종류의 이벤트를 보냅니다:

  • MessageStart - 새 메시지 전송 시작
  • ContentBlockStart - 텍스트·도구 사용 등 콘텐츠를 담은 새 블록의 시작
  • ContentBlockDelta - 실제 생성된 텍스트 조각
  • ContentBlockStop - 현재 콘텐츠 블록 완료
  • MessageDelta - 현재 메시지 완료
  • MessageStop - 현재 메시지 정보의 끝

ContentBlockDelta 이벤트가 사용자에게 표시할 실제 생성 텍스트를 담고 있습니다.

기본 스트리밍 구현

스트리밍을 켜려면 messages.create 호출에 stream=True를 추가합니다:

messages = []
add_user_message(messages, "Write a 1 sentence description of a fake database")

stream = client.messages.create(
model=model,
max_tokens=1000,
messages=messages,
stream=True
)

for event in stream:
print(event)

단순화된 텍스트 스트리밍

이벤트를 직접 파싱하는 대신 SDK의 단순화된 스트리밍 인터페이스로 텍스트 콘텐츠만 추출할 수 있습니다:

with client.messages.stream(
model=model,
max_tokens=1000,
messages=messages
) as stream:
for text in stream.text_stream:
print(text, end="")

이 방식은 실제 텍스트 콘텐츠를 제외한 나머지를 자동으로 걸러줍니다. 사용자에게 응답을 표시할 때 대개 이것이면 충분합니다.

완전한 메시지 얻기

조각 스트리밍은 UX에 좋지만, 저장이나 후처리를 위해 완전한 메시지가 필요할 때가 많습니다. 스트리밍이 끝난 뒤 조립된 최종 메시지를 얻을 수 있습니다:

with client.messages.stream(
model=model,
max_tokens=1000,
messages=messages
) as stream:
for text in stream.text_stream:
# Send each chunk to your client
pass

# Get the complete message for database storage
final_message = stream.get_final_message()
이렇게 하면 두 마리 토끼를 다 잡습니다. 사용자에게는 실시간 스트리밍을, 애플리케이션 로직에는 완전한 메시지 객체를 제공합니다.

구조화된 데이터

🎬 영상 + 요약

Claude에게 JSON, Python 코드, 불릿 리스트 같은 구조화된 데이터를 생성하게 하면 흔한 문제에 부딪힙니다. Claude는 도움이 되려고 콘텐츠 주위에 설명 텍스트를 덧붙이려 합니다. 보통은 좋지만, 때로는 다른 것 없이 원본 데이터만 필요할 때가 있습니다.

AWS EventBridge 규칙을 생성하는 웹 앱을 만든다고 해봅시다. 사용자가 설명을 입력하고 생성을 누르면, 바로 복사해 쓸 수 있는 깔끔한 JSON을 기대합니다. Claude가 JSON을 마크다운 코드 블록과 설명 텍스트로 감싸 반환하면, 사용자는 전체 응답을 그대로 복사할 수 없고 JSON 부분만 수동으로 선택해야 합니다.

기본 응답의 문제

기본적으로 Claude에게 JSON을 요청하면 다음과 같은 결과를 받을 수 있습니다:

```json
{
"source": ["aws.ec2"],
"detail-type": ["EC2 Instance State-change Notification"],
"detail": {
"state": ["running"]
}
}
```

This rule captures EC2 instance state changes when instances start running.

JSON은 정확하지만 마크다운 서식으로 감싸여 있고 설명 텍스트가 포함됩니다. 사용자가 원본 JSON을 복사해야 하는 웹 앱에서는 이것이 마찰을 만듭니다.

해결책: assistant 메시지 프리필 + stop sequence

assistant 메시지 프리필(prefilling)과 stop sequence를 결합하면 원하는 콘텐츠만 정확히 얻을 수 있습니다. 방법은 다음과 같습니다:

messages = []

add_user_message(messages, "Generate a very short event bridge rule as json")
add_assistant_message(messages, "```json")

text = chat(messages, stop_sequences=["```"])

이 기법의 원리:

  • user 메시지가 생성할 대상을 Claude에 지시
  • 프리필된 assistant 메시지가 Claude로 하여금 이미 마크다운 코드 블록을 시작했다고 여기게 함
  • Claude가 JSON 콘텐츠만 이어서 작성
  • Claude가 ```로 코드 블록을 닫으려는 순간 stop sequence가 즉시 생성을 종료

그 결과 서식 없는 깔끔한 JSON을 얻습니다:

{
"source": ["aws.ec2"],
"detail-type": ["EC2 Instance State-change Notification"],
"detail": {
"state": ["running"]
}
}

응답 처리하기

응답에 여분의 개행 문자가 있을 수 있는데, 처리하기 쉽습니다:

import json

# Clean up and parse the JSON
clean_json = json.loads(text.strip())

JSON을 넘어서

이 기법은 JSON에만 국한되지 않습니다. 설명 없이 구조화된 데이터가 필요할 때 언제든 쓸 수 있습니다:

  • Python 코드 스니펫
  • 불릿 리스트
  • CSV 데이터
  • 설명이 아닌 콘텐츠만 원하는 모든 서식화된 콘텐츠
핵심은 Claude가 콘텐츠를 자연스럽게 무엇으로 감싸는지 파악해, 그것을 프리필과 stop sequence로 사용하는 것입니다. 코드라면 보통 마크다운 코드 블록입니다. 이 방식은 출력 형식을 정밀하게 제어하게 해줍니다.

프롬프트 평가란?

🎬 영상 + 요약

Claude를 다룰 때 좋은 프롬프트를 쓰는 건 시작일 뿐입니다. 신뢰할 수 있는 AI 애플리케이션을 만들려면 두 가지 핵심 개념을 이해해야 합니다. 프롬프트 엔지니어링은 더 나은 프롬프트를 쓰는 기법이고, 프롬프트 평가는 그 프롬프트가 실제로 얼마나 잘 작동하는지 측정하는 것입니다.

프롬프트 엔지니어링 vs 프롬프트 평가

프롬프트 엔지니어링은 효과적인 프롬프트를 만드는 도구 상자입니다. 다음 같은 기법을 포함합니다:

  • 멀티샷(multishot) 프롬프팅
  • XML 태그로 구조화하기
  • 그 밖의 여러 모범 사례

프롬프트 평가는 다른 접근을 취합니다. 프롬프트를 어떻게 쓰느냐가 아니라, 자동화된 테스트로 효과를 측정하는 것입니다. 이를 통해:

  • 예상 답과 비교해 테스트
  • 같은 프롬프트의 다른 버전을 비교
  • 출력에서 오류를 검토

프롬프트 작성 후 세 갈래 길

프롬프트 초안을 작성한 뒤 보통 세 가지 선택지에 직면합니다:

  1. 한 번 테스트하고 "충분하다"고 결정 — 예상치 못한 입력이 들어오면 프로덕션에서 깨질 위험이 큽니다.
  2. 몇 번 테스트하고 한두 가지 코너 케이스를 처리하도록 손봄 — 1번보다는 낫지만, 사용자는 종종 고려하지 못한 입력을 줍니다.
  3. 프롬프트를 평가 파이프라인에 통과시켜 점수를 매기고, 객관적 지표를 바탕으로 반복 개선 — 더 많은 노력과 비용이 들지만 신뢰도가 훨씬 높습니다.

대부분의 엔지니어가 빠지는 함정

1번과 2번은 모든 엔지니어가 빠지는 흔한 함정입니다. 진지한 애플리케이션의 프롬프트를 충분히 테스트하지 않는 건 자연스러운 일이며, 우리는 실제 사용자가 마주칠 엣지 케이스의 수를 과소평가하는 경향이 있습니다. 프로덕션에 배포하면 사용자는 예상 못 한 방식으로 상호작용하고, 제한적 테스트에서 견고해 보이던 프롬프트가 실세계 입력의 다양성 앞에서 금세 무너질 수 있습니다.

평가 우선 접근법

3번은 더 체계적인 접근입니다. 프롬프트를 평가 파이프라인에 통과시키면 더 넓은 테스트 케이스에 걸친 객관적 지표를 얻습니다. 이 데이터 기반 접근으로:

  • 약점이 프로덕션 문제가 되기 전에 식별
  • 다른 프롬프트 버전을 객관적으로 비교
  • 측정 가능한 개선을 바탕으로 자신 있게 반복
  • 더 신뢰할 수 있는 AI 애플리케이션 구축
평가 우선 접근은 초기 투자(시간·인프라)가 더 들지만, 최종 애플리케이션의 신뢰성과 견고함으로 보답합니다. 목표는 사용자가 문제를 겪기 전, 개발 중에 문제를 잡는 것입니다.

전형적인 eval 워크플로우

🎬 영상 + 요약

전형적인 프롬프트 평가 워크플로우는 다섯 단계로 이루어지며, 객관적 측정을 통해 프롬프트를 체계적으로 개선하도록 돕습니다. 다양한 오픈소스·유료 도구가 있지만, 핵심 과정을 이해하면 작게 시작해 필요에 따라 확장할 수 있습니다.

1단계: 프롬프트 초안 작성

개선하고 싶은 초기 프롬프트를 작성하는 데서 시작합니다. 이 예에서는 간단한 프롬프트를 씁니다:

prompt = f"""
Please answer the user's question:

{question}
"""

이 기본 프롬프트가 테스트·개선의 기준선(baseline)이 됩니다.

2단계: eval 데이터셋 만들기

평가 데이터셋에는 프로덕션에서 다룰 질문·요청 유형을 대표하는 샘플 입력이 들어갑니다. 이 질문들은 프롬프트 템플릿에 끼워 넣어집니다.

이 예의 데이터셋에는 세 질문이 있습니다:

  • "What's 2+2?"
  • "How do I make oatmeal?"
  • "How far away is the Moon?"

실제 평가에서는 수십·수백·수천 개의 레코드가 있을 수 있습니다. 손으로 만들거나 Claude로 생성할 수 있습니다.

3단계: Claude에 통과시키기

데이터셋의 각 질문을 프롬프트 템플릿과 합쳐 완전한 프롬프트를 만든 뒤 Claude에 보내 응답을 받습니다.

예를 들어 첫 질문은 다음이 됩니다:

Please answer the user's question:
What's 2+2?

Claude는 수학 질문에 "2 + 2 = 4", 두 번째엔 오트밀 조리법, 세 번째엔 달까지의 거리를 응답할 수 있습니다.

4단계: 채점기(grader)에 통과시키기

채점기는 원래 질문과 Claude의 답을 함께 살펴 응답 품질을 평가합니다. 보통 1~10 척도로 객관적 점수를 매기며, 10은 완벽한 답, 낮은 점수는 개선 여지를 뜻합니다.

예에서 채점기는 다음처럼 매길 수 있습니다:

  • 수학 질문: 10 (완벽)
  • 오트밀 질문: 4 (개선 필요)
  • 달 질문: 9 (매우 좋음)

전체 평균 점수가 객관적 측정치를 줍니다: (10 + 4 + 9) ÷ 3 = 7.66

5단계: 프롬프트 변경 후 반복

기준 점수를 얻었으니 프롬프트를 수정하고 전체 과정을 다시 돌려 개선 여부를 확인합니다.

예를 들어 프롬프트에 안내를 더 추가할 수 있습니다:

prompt = f"""
Please answer the user's question:

{question}

Answer the question with ample detail
"""

이 개선된 프롬프트를 같은 평가 과정에 돌리면 평균 점수가 8.7로 오를 수 있고, 이는 추가 지시가 더 나은 응답에 도움이 됐음을 나타냅니다.

프롬프트 채점

이 워크플로우의 핵심 이점은 프롬프트 성능의 객관적 측정입니다. 다른 버전을 수치로 비교하고, 최고 점수 버전을 사용하며, 더 나은 접근을 찾아 계속 반복할 수 있습니다.

이 체계적 접근은 프롬프트 엔지니어링에서 추측을 제거하고, 변경이 그저 다른 변형이 아니라 실제 개선이라는 확신을 줍니다.

🎬 영상 + 요약

평가 데이터셋이 준비됐으니 이제 핵심 평가 파이프라인을 만들 차례입니다. 각 테스트 케이스를 프롬프트와 병합하고, Claude에 전달한 뒤 결과를 채점하는 흐름입니다.

평가 프로세스는 명확한 워크플로를 따릅니다. 테스트 케이스 데이터셋을 프롬프트 템플릿과 결합해 Claude로 처리하고, grader 시스템으로 출력을 평가합니다.

핵심 함수 만들기

평가 파이프라인은 각각 하나의 역할을 맡는 세 개의 함수로 구성됩니다. 가장 단순한 것부터 시작합니다.

run_prompt 함수

테스트 케이스를 프롬프트 템플릿과 병합합니다.

def run_prompt(test_case):
"""Merges the prompt and test case input, then returns the result"""
prompt = f"""
Please solve the following task:

{test_case["task"]}
"""

messages = []
add_user_message(messages, prompt)
output = chat(messages)
return output

지금은 프롬프트를 아주 단순하게 유지합니다. 포맷 지시가 없어 Claude가 필요 이상으로 장황하게 출력할 수 있는데, 이후 프롬프트를 다듬으며 개선합니다.

run_test_case 함수

단일 테스트 케이스 실행과 채점을 조율합니다.

def run_test_case(test_case):
"""Calls run_prompt, then grades the result"""
output = run_prompt(test_case)

# TODO - Grading
score = 10

return {
"output": output,
"test_case": test_case,
"score": score

지금은 점수를 10으로 하드코딩합니다. 채점 로직은 이후에 집중적으로 다루지만, 이 플레이스홀더 덕분에 전체 파이프라인을 먼저 테스트할 수 있습니다.

run_eval 함수

전체 평가 과정을 조율합니다.

def run_eval(dataset):
"""Loads the dataset and calls run_test_case with each case"""
results = []

for test_case in dataset:
result = run_test_case(test_case)
results.append(result)

return results

데이터셋의 모든 테스트 케이스를 처리해 결과를 하나의 리스트로 모읍니다.

평가 실행하기

데이터셋을 로드해 함수들에 통과시킵니다.

결과 살펴보기

평가는 각 객체가 하나의 테스트 케이스 결과를 나타내는 구조화된 JSON 배열을 반환합니다.

print(json.dumps(results, indent=2))

각 결과에는 세 가지 핵심 정보가 담깁니다.

  • output: Claude의 전체 응답
  • test_case: 처리된 원본 테스트 케이스
  • score: 평가 점수(현재는 하드코딩)

포맷 지시가 없어 Claude 응답이 꽤 장황한데, 프롬프트를 다듬으며 해결할 문제입니다.

모델 기반 채점

🎬 영상 + 요약

프롬프트 평가 워크플로에서 채점 시스템은 출력 품질에 대한 객관적 신호를 제공합니다. grader는 모델 출력을 받아 측정 가능한 피드백을 반환하는데, 보통 1~10 사이 숫자로 10은 고품질, 1은 저품질을 뜻합니다.

grader의 종류

  • Code graders — 커스텀 로직으로 출력을 프로그래밍적으로 평가
  • Model graders — 다른 AI 모델로 품질을 평가
  • Human graders — 사람이 직접 검토·채점

코드 grader

상상할 수 있는 어떤 프로그래밍적 검사든 구현할 수 있습니다. 흔한 용도는 다음과 같습니다.

  • 출력 길이 확인
  • 특정 단어 포함 여부 검증
  • JSON, Python, regex의 문법 검증
  • 가독성 점수

요구 조건은 코드가 사용 가능한 신호(보통 1~10 숫자)를 반환하는 것뿐입니다.

모델 grader

원본 출력을 또 다른 API 호출에 넣어 평가합니다. 응답 품질, 지시 따르기 품질, 완성도, 유용성, 안전성 등을 유연하게 평가할 수 있습니다.

사람 grader

가장 유연하지만 시간이 많이 들고 번거롭습니다. 전반적 품질, 포괄성, 깊이, 간결성, 관련성 평가에 유용합니다.

평가 기준 정하기

grader를 구현하기 전에 명확한 평가 기준이 필요합니다. 코드 생성 프롬프트라면 다음에 집중할 수 있습니다.

  • Format — 설명 없이 Python/JSON/Regex만 반환
  • Valid Syntax — 생성된 코드의 문법이 유효해야 함
  • Task Following — 정확한 코드로 사용자 작업을 직접 해결

앞의 두 기준은 코드 grader에, 작업 따르기는 유연한 모델 grader에 더 적합합니다.

모델 grader 구현

def grade_by_model(test_case, output):
# Create evaluation prompt
eval_prompt = """

Task: {task}
Solution: {solution}

Provide your evaluation as a structured JSON object with:
- "strengths": An array of 1-3 key strengths
- "weaknesses": An array of 1-3 key areas for improvement
- "reasoning": A concise explanation of your assessment
- "score": A number between 1-10
"""

messages = []
add_user_message(messages, eval_prompt)
add_assistant_message(messages, "```json")

eval_text = chat(messages, stop_sequences=["```"])
return json.loads(eval_text)
핵심은 점수와 함께 강점·약점·근거를 요청하는 것입니다. 이 맥락이 없으면 모델은 6점 언저리의 무난한 점수로 수렴하는 경향이 있습니다.

채점을 워크플로에 통합하려면 테스트 케이스 러너가 grader를 호출하도록 갱신합니다.

def run_test_case(test_case):
output = run_prompt(test_case)

# Grade the output
model_grade = grade_by_model(test_case, output)
score = model_grade["score"]
reasoning = model_grade["reasoning"]

return {
"output": output,
"test_case": test_case,
"score": score,
"reasoning": reasoning
}

마지막으로 모든 테스트 케이스의 평균 점수를 계산합니다.

from statistics import mean

def run_eval(dataset):
results = []

for test_case in dataset:
result = run_test_case(test_case)
results.append(result)

average_score = mean([result["score"] for result in results])
print(f"Average score: {average_score}")

return results

코드 기반 채점

🎬 영상 + 요약

코드를 생성하는 AI를 평가할 때는 응답이 말이 되는지만 보는 것으로는 부족합니다. 생성된 코드가 실제로 유효한 문법인지, 올바른 포맷을 따르는지도 검증해야 합니다. 여기서 코드 기반 채점이 등장합니다.

코드 채점의 동작 방식

  • Format — 설명 없이 요청된 코드 타입(Python/JSON/Regex)만 반환
  • Valid Syntax — 생성된 코드가 해당 언어로 실제 파싱돼야 함
  • Task Following — 요청에 직접 부합하고 정확해야 함

앞의 두 기준은 코드 grader가, 작업 따르기는 모델 grader가 평가합니다. 둘을 합치면 포괄적인 평가가 됩니다.

문법 검증 함수

def validate_json(text):
try:
json.loads(text.strip())
return 10
except json.JSONDecodeError:
return 0

def validate_python(text):
try:
ast.parse(text.strip())
return 10
except SyntaxError:
return 0

def validate_regex(text):
try:
re.compile(text.strip())
return 10
except re.error:
return 0

각 함수는 텍스트를 해당 포맷으로 파싱을 시도합니다. 성공하면 10점, 실패하면 문법이 잘못된 것이므로 0점을 반환합니다.

데이터셋 포맷 요구사항

어떤 검증기를 쓸지 알려면 테스트 케이스가 기대 출력 포맷을 명시해야 합니다.

{
"task": "Create a Python function to validate an AWS IAM username",
"format": "python"
}

데이터셋 생성 프롬프트의 예시 출력 구조에 이 format 필드를 추가하면 자동으로 포함시킬 수 있습니다.

프롬프트 명확성 개선

더 나은 결과를 위해 기대하는 출력 포맷을 구체적으로 지시합니다.

* Respond only with Python, JSON, or a plain Regex
* Do not add any comments or commentary or explanation

미리 채워진 assistant 메시지로 원시 코드만 반환하도록 유도할 수도 있습니다.

add_assistant_message(messages, "```code")

이렇게 하면 Python·JSON·Regex 중 무엇인지 미리 지정하지 않아도 Claude가 코드부터 생성하게 됩니다.

점수 합치기

마지막으로 모델 grader 점수와 코드 grader 점수를 병합합니다. 가장 단순한 방법은 평균입니다.

model_grade = grade_by_model(test_case, output)
model_score = model_grade["score"]
syntax_score = grade_syntax(output, test_case)

score = (model_score + syntax_score) / 2
이 방식은 내용 품질과 기술적 정확성에 동일한 가중치를 줍니다. 사용 사례에서 무엇이 더 중요한지에 따라 가중치를 조정할 수 있습니다.

구현 테스트하기

코드 채점을 구현했다면 평가를 돌려 기준선 점수를 얻으세요. 점수 자체의 좋고 나쁨보다, 프롬프트를 다듬어 그 점수를 개선할 수 있는지가 중요합니다. 주관적 판단 대신 정량적으로 프롬프트 엔지니어링 진척을 측정할 수 있게 됩니다.

프롬프트 엔지니어링

🎬 영상 + 요약

프롬프트 엔지니어링은 이미 작성한 프롬프트를 더 안정적이고 고품질의 출력이 나오도록 개선하는 작업입니다. 기본 프롬프트에서 시작해 성능을 평가하고, 체계적으로 기법을 적용해 개선하는 반복적 과정입니다.

반복 개선 프로세스

  1. 목표 설정 — 프롬프트로 달성하려는 바를 정의
  2. 초기 프롬프트 작성 — 기본적인 첫 시도 작성
  3. 프롬프트 평가 — 기준에 맞춰 테스트
  4. 프롬프트 엔지니어링 기법 적용 — 구체적 방법으로 성능 개선
  5. 재평가 — 변경이 실제로 결과를 개선했는지 검증

마지막 두 단계를 만족할 때까지 반복하며, 매 반복마다 평가 점수가 측정 가능하게 개선돼야 합니다.

평가 파이프라인 설정

이 과정을 보여주기 위해 운동선수용 하루 식단표를 생성하는 프롬프트를 예로 씁니다. 키, 몸무게, 목표, 식이 제한을 고려해 종합적인 식단표를 만들어야 합니다.

평가 설정은 데이터셋 생성과 모델 채점을 처리하는 PromptEvaluator 클래스를 씁니다. 인스턴스 생성 시 max_concurrent_tasks로 동시성을 제어합니다.

evaluator = PromptEvaluator(max_concurrent_tasks=5)

rate limit 오류를 피하려면 3 정도의 낮은 값으로 시작하세요. API 할당량이 허용하면 늘릴 수 있습니다.

테스트 데이터 생성

평가 시스템은 프롬프트 요구사항에 따라 테스트 케이스를 자동 생성할 수 있습니다.

개발 중에는 테스트 케이스 수를 2~3개로 낮게 유지해 반복 속도를 높이고, 최종 검증 때 늘리세요.

명확하고 직접적으로

그 중요한 첫 줄을 쓸 때는 두 가지 원칙, 즉 명확성과 직접성에 집중합니다. Claude가 무엇을 해야 하는지 모호함이 없도록 단순한 언어를 씁니다.

명확한 의사소통

"명확하다"는 것은 다음을 뜻합니다.

  • 누구나 이해할 수 있는 단순한 언어 사용
  • 빙빙 돌리지 않고 원하는 바를 정확히 진술
  • Claude의 작업을 직설적 진술로 시작

"지붕에 올리는 태양광 그거…" 같은 모호한 표현 대신 "태양광 패널의 작동 원리를 세 단락으로 써라"처럼 직접 쓰세요.

직접적인 지시

"직접적"이라는 것은 요청을 구성하는 방식에 관한 것입니다.

  • 질문이 아니라 지시문 사용
  • "Write", "Create", "Generate" 같은 직접적 동사로 시작

"재생에너지 읽다 보니 지열이 흥미롭던데 어떤 나라가 쓰나요?" 대신 "지열 에너지를 쓰는 나라 세 곳을 찾아라. 각 발전 통계를 포함하라"처럼 쓰세요.

실전 적용

"이 사람은 무엇을 먹어야 하나?"라는 약한 프롬프트에 명확·직접 원칙을 적용한 개선 버전은 다음과 같습니다.

Generate a one-day meal plan for an athlete that meets their dietary restrictions.

이 개정본은 Claude에게 즉시 알려줍니다.

  • 어떤 동작을 할지(generate)
  • 무엇을 만들지(식단표)
  • 핵심 제약(하루치, 운동선수용, 식이 제한 충족)

XML 태그로 구조화

🎬 영상 + 요약

많은 내용을 담은 프롬프트에서는 Claude가 어떤 텍스트가 함께 묶이는지, 각 섹션이 무엇을 뜻하는지 헷갈릴 수 있습니다. XML 태그는 특히 대량의 데이터를 삽입할 때 구조와 명확성을 더하는 간단한 방법입니다.

구조가 중요한 이유

20페이지 분량의 영업 기록을 분석해야 하는 프롬프트를 생각해보세요. 명확한 경계가 없으면 Claude는 지시와 실제 데이터를 구분하기 어려워합니다.

실전 예시: 코드와 문서

제공된 문서로 코드를 디버깅시킬 때 모두 섞으면 혼란이 생깁니다. "Not Great" 버전은 코드와 문서를 구분하기 거의 불가능하지만, "Better" 버전은 <my_code>와 <docs> 태그로 명확한 경계를 만듭니다.

커스텀 태그 이름

공식 XML 태그를 쓸 필요는 없습니다. 내용에 맞는 서술적 이름을 만드세요.

  • <sales_records>가 <data>보다 낫다
  • <athlete_information>은 사용자 정보를 명확히 나타낸다
  • <my_code>와 <docs>는 서로 다른 콘텐츠를 분리한다

태그 이름이 구체적이고 서술적일수록 Claude가 각 섹션의 목적을 더 잘 이해합니다.

언제 XML 태그를 쓸까

  • 대량의 맥락이나 데이터를 포함할 때
  • 서로 다른 콘텐츠(코드, 문서, 데이터)를 섞을 때
  • 콘텐츠 경계를 특히 명확히 하고 싶을 때
  • 여러 변수를 삽입하는 복잡한 프롬프트를 다룰 때

실제 적용

<athlete_information>
- Height: 6'2"
- Weight: 180 lbs
- Goal: Build muscle
- Dietary restrictions: Vegetarian
</athlete_information>

Generate a meal plan based on the athlete information above.
단순한 프롬프트에서는 큰 개선이 없을 수 있지만, 프롬프트가 복잡해지고 다양한 콘텐츠가 많아질수록 XML 태그의 가치는 커집니다.

예시 제공하기

🎬 영상 + 요약

프롬프트에 예시를 제공하는 것은 가장 효과적인 프롬프트 엔지니어링 기법 중 하나입니다. "one-shot" 또는 "multi-shot" 프롬프팅이라 불리며, 입력/출력 쌍 예시를 주어 Claude의 응답을 안내합니다.

예시가 작동하는 방식

트윗이 긍정인지 부정인지 분류하는 감성 분석을 예로 들면, 어려운 점은 반어입니다. "역대급 명작이네" 같은 트윗은 표면상 긍정이지만 실제로는 반어적 부정일 수 있습니다.

코너 케이스를 위한 예시 추가

개선된 프롬프트는 다음을 포함합니다.

  • 명확한 긍정 예시: "Great game tonight!" → "Positive"
  • 반어 예시: "Oh yeah, I really needed a flight delay tonight! Excellent!" → "Negative"
  • 반어를 신중히 다뤄야 하는 이유를 설명하는 맥락

예시를 <sample_input>, <ideal_output> 같은 XML 태그로 감싸면 각 부분이 무엇인지 명확해집니다.

언제 예시를 쓸까

  • 코너 케이스나 엣지 시나리오 포착
  • 복잡한 출력 포맷(특정 JSON 구조 등) 정의
  • 원하는 정확한 스타일이나 톤 제시
  • 모호한 입력 처리 방법 시연

One-Shot vs Multi-Shot

  • One-Shot: 패턴을 잡기 위해 예시 하나 제공
  • Multi-Shot: 다양한 시나리오를 다루기 위해 여러 예시 제공

여러 엣지 케이스를 다루거나 다양한 유효 응답을 보여줘야 할 때 multi-shot을 쓰세요.

평가에서 좋은 예시 찾기

예시에 맥락 더하기

입력/출력 쌍만 주지 말고, 그 출력이 왜 좋은지 설명하세요.

This example is well-structured, provides detailed information

goals and restrictions.

  • 항상 XML 태그로 예시를 명확히 구조화

예시는 말로 설명하는 대신 직접 보여주기 때문에 강력합니다. 지시만으로 표현하기 어려운 미묘한 요구사항까지 Claude가 이해하게 해줍니다.

도구 사용 소개

🎬 영상 + 요약

도구(tool)는 Claude가 외부 세계의 정보에 접근하게 해, 학습 데이터를 넘어서는 능력을 갖게 합니다. 기본적으로 Claude는 학습 데이터만 알며 최신 뉴스, 실시간 데이터, 외부 시스템에 접근할 수 없습니다. 도구 사용은 Claude가 새 정보를 요청·수신하는 구조화된 방법을 만들어 이 한계를 해결합니다.

도구가 없을 때의 문제

"샌프란시스코 날씨가 어때?"라고 물으면 Claude는 "최신 날씨 정보에 접근할 수 없다"고 답할 수밖에 없습니다.

Claude가 이론적으로 도울 수 있는 실시간 데이터가 필요할 때, 이는 답답한 경험을 만듭니다.

도구 사용의 동작 방식

도구 사용은 애플리케이션과 Claude 사이의 특정한 주고받기 패턴을 따릅니다.

  1. 초기 요청: 질문과 함께 외부에서 추가 데이터를 얻는 방법을 Claude에 전달
  2. 도구 요청: Claude가 추가 정보가 필요하다고 판단해 어떤 데이터가 필요한지 구체적으로 요청
  3. 데이터 조회: 서버가 코드를 실행해 외부 API나 DB에서 정보를 가져옴
  4. 최종 응답: 가져온 데이터를 Claude에 돌려주면, 원 질문과 새 데이터를 함께 써서 완전한 응답 생성

실전 날씨 예시

사용자가 현재 날씨를 물으면, 프롬프트에 날씨 데이터 조회 방법을 넣습니다. Claude는 최신 정보가 필요함을 인식해 특정 위치의 날씨 데이터를 요청하고, 서버가 날씨 API를 호출해 실시간 상태를 Claude에 돌려주면, Claude가 이를 질문과 결합해 정확한 응답을 제공합니다.

핵심 이점

  • 실시간 정보: 학습 시점에 없던 최신 데이터 접근
  • 외부 시스템 통합: DB, API 등 서비스와 연결
  • 동적 응답: 최신 정보 기반의 답변
  • 구조화된 상호작용: 필요한 정보와 요청 방법을 Claude가 정확히 파악

도구 사용은 Claude를 정적 지식 베이스에서 라이브 데이터로 일하는 동적 어시스턴트로 바꿉니다.

프로젝트 개요

🎬 영상 + 요약

Claude가 미래 날짜에 리마인더를 설정하도록 가르치는 실전 프로젝트를 만듭니다. 단순해 보이지만 커스텀 도구로 풀어야 할 흥미로운 문제들이 드러납니다.

목표는 명확합니다. "다음 주 목요일 진료 예약 리마인더를 설정해줘"라고 말하면 Claude가 "알겠습니다, 알려드릴게요"라고 답하게 하는 것입니다. 이를 위해 Claude의 시간·리마인더 처리 한계를 다뤄야 합니다.

왜 어려운가

Claude는 현재 날짜를 알지만 다음 세 문제를 풀어야 합니다.

  • 제한된 시간 인식: 현재 날짜는 알아도 정확한 시각은 모를 수 있음
  • 날짜 계산 문제: 특히 먼 미래로의 시간 덧셈을 항상 잘 처리하진 못함
  • 리마인더 기능 없음: 리마인더를 설정할 내장 메커니즘이 없음

각 한계는 Claude가 자연히 할 수 있는 것과 우리가 필요로 하는 것 사이의 간극이며, 도구가 이를 메웁니다.

필요한 도구

각 문제를 위해 세 개의 도구를 만듭니다.

  • 현재 날짜·시간 가져오기: 정확한 현재 시각 파악
  • 날짜·시간에 기간 더하기: 신뢰할 수 있는 날짜 덧셈 도구 제공
  • 리마인더 설정하기: 시스템에 실제로 리마인더 등록
핵심 원칙: 모델에 한계가 있을 때 프롬프트로 우회하려 하기보다 도구로 능력을 확장합니다. 가장 단순한 것부터 하나씩 구현합니다.

도구 함수

🎬 영상 + 요약

Claude 앱을 만들 때는 실시간 정보 접근이나 동작 수행 능력을 줘야 할 때가 많습니다. 여기서 도구 함수가 등장합니다. Claude가 추가 데이터가 필요할 때 호출할 수 있는 파이썬 함수입니다.

구현할 세 도구는 현재 날짜·시간 가져오기, 날짜에 기간 더하기, 리마인더 설정입니다. 첫 번째부터 시작합니다.

도구 함수란?

도구 함수는 Claude가 사용자를 돕기 위해 추가 정보가 필요하다고 판단할 때 자동으로 실행되는 평범한 파이썬 함수입니다. 예를 들어 "몇 시야?"라고 물으면 Claude가 날짜·시간 도구를 호출합니다.

도구 함수 모범 사례

  • 서술적 이름 사용: 함수명과 매개변수명이 목적을 명확히 드러내야 함
  • 입력 검증: 필수 매개변수가 비었거나 잘못됐는지 확인하고 오류를 raise
  • 의미 있는 오류 메시지 제공: Claude는 오류를 보고 매개변수를 고쳐 재시도할 수 있음

검증이 특히 중요한 이유는 Claude가 오류로부터 배우기 때문입니다. "Location cannot be empty" 같은 명확한 오류를 내면 Claude가 올바른 값으로 다시 호출할 수 있습니다.

첫 도구 함수 만들기

현재 날짜·시간을 가져오는 함수를 만듭니다. 날짜 포맷 매개변수를 받아 Claude가 다양한 포맷으로 요청할 수 있게 합니다.

def get_current_datetime(date_format="%Y-%m-%d %H:%M:%S"):
if not date_format:
raise ValueError("date_format cannot be empty")
return datetime.now().strftime(date_format)

파이썬 datetime 모듈로 현재 시각을 가져와 포맷 문자열에 맞춰 반환합니다. 기본 포맷은 연-월-일 시:분:초입니다.

# Default format: "2024-01-15 14:30:25"
get_current_datetime()

# Just hour and minute: "14:30"
get_current_datetime("%H:%M")
검증 검사는 빈 문자열을 막습니다. 이 특정 오류는 드물지만, 입력을 검증하고 Claude가 배울 수 있는 유용한 오류 메시지를 제공하는 패턴을 보여줍니다.

도구 스키마

🎬 영상 + 요약

도구 함수를 작성한 뒤에는 함수가 어떤 인자를 기대하고 어떻게 쓰는지 Claude에게 알려주는 JSON 스키마를 만듭니다. 이 스키마는 Claude가 도구를 언제·어떻게 호출할지 이해하기 위해 읽는 문서 역할을 합니다.

JSON 스키마 이해하기

JSON 스키마는 AI나 도구 호출 전용이 아니라 오래전부터 널리 쓰인 데이터 검증 명세입니다. 함수 매개변수를 기술하고 데이터를 검증하기에 편리해 AI 커뮤니티가 채택했습니다.

완전한 도구 명세는 세 부분으로 구성됩니다.

  • name — 명확하고 서술적인 도구 이름("get_weather" 등)
  • description — 도구가 무엇을 하고, 언제 쓰며, 무엇을 반환하는지
  • input_schema — 함수 인자를 기술하는 실제 JSON 스키마

효과적인 설명 작성

  • 도구가 무엇을 하는지 3~4문장으로
  • Claude가 언제 써야 하는지 기술
  • 어떤 데이터를 반환하는지 설명
  • 각 인자에 대한 상세 설명 제공

스키마 생성의 쉬운 방법

스키마를 처음부터 쓰는 대신 Claude에게 생성시킬 수 있습니다.

  • 도구 함수 코드를 복사
  • Claude에게 도구 호출용 JSON 스키마를 써달라고 요청
  • Anthropic 도구 사용 문서를 맥락으로 첨부
  • 모범 사례를 따른 스키마를 생성하게 함

프롬프트는 "이 함수에 대한 도구 호출용 유효 JSON 스키마 명세를 첨부 문서의 모범 사례에 따라 작성하라" 정도면 됩니다.

코드에 스키마 구현

def get_current_datetime(date_format="%Y-%m-%d %H:%M:%S"):
if not date_format:
raise ValueError("date_format cannot be empty")
return datetime.now().strftime(date_format)

get_current_datetime_schema = {
"name": "get_current_datetime",
"description": "Returns the current date and time formatted according to the specified format",
"input_schema": {
"type": "object",
"properties": {
"date_format": {
"type": "string",
"description": "A string specifying the format of the returned datetime. Uses Python's strftime format codes.",
"default": "%Y-%m-%d %H:%M:%S"
}
},
"required": []
}
}
function_name 뒤에 function_name_schema를 붙이는 명명 패턴으로 스키마를 함수와 쉽게 짝지어 관리하세요.

타입 안정성 추가

더 나은 타입 체크를 위해 Anthropic 라이브러리의 ToolParam 타입을 임포트해 씁니다.

from anthropic.types import ToolParam

get_current_datetime_schema = ToolParam({
"name": "get_current_datetime",
"description": "Returns the current date and time formatted according to the specified format",
# ... rest of schema
})

기능상 필수는 아니지만, API에 스키마를 쓸 때 타입 오류를 막아 코드를 더 견고하게 만듭니다.

메시지 블록 처리

🎬 영상 + 요약

Claude의 도구 기능을 다루면 기존 단순 텍스트 응답과는 다른 새로운 응답 구조를 만나게 됩니다. 단일 텍스트 블록 대신, 텍스트와 도구 사용 정보를 함께 담은 멀티 블록 메시지를 반환할 수 있습니다.

도구를 활성화한 API 호출

messages = []

tools 매개변수는 Claude가 호출할 수 있는 함수를 기술하는 JSON 스키마 리스트를 받습니다.

멀티 블록 메시지 이해하기

Claude가 도구를 쓰기로 하면 content 리스트에 여러 블록이 담긴 assistant 메시지를 반환합니다. 이는 기존 텍스트 전용 응답에서 큰 변화입니다.

멀티 블록 메시지는 보통 다음을 포함합니다.

  • Text 블록 — Claude가 무엇을 하는지 설명하는 사람이 읽을 텍스트
  • ToolUse 블록 — 어떤 도구를 어떤 매개변수로 호출할지 알려주는 지시

ToolUse 블록에는 도구 호출 추적용 ID, 호출할 함수 이름(예: "get_current_datetime"), 딕셔너리 형태의 입력 매개변수, "tool_use" 타입 지정이 담깁니다.

멀티 블록 메시지로 대화 기록 관리

Claude는 대화 기록을 저장하지 않으므로 직접 관리해야 합니다. 도구 응답을 다룰 때는 모든 블록을 포함한 전체 content 구조를 보존해야 합니다.

"role": "assistant",
"content": response.content
})
이렇게 텍스트 블록과 tool_use 블록을 모두 보존해야 이후 API 호출에서 대화 맥락이 유지됩니다.

전체 도구 사용 흐름

  1. 도구 스키마와 함께 사용자 메시지를 Claude에 전송
  2. 텍스트 블록과 tool_use 블록이 담긴 assistant 메시지 수신
  3. 도구 정보를 추출해 실제 함수 실행
  4. 전체 대화 기록과 함께 도구 결과를 Claude에 전송

도구 결과 전송

도구 함수 실행하기

Claude가 tool_use 블록으로 응답하면 입력 매개변수를 추출해 함수를 호출합니다.

response.content[1].input

Tool Result 블록

도구 함수를 실행한 뒤 tool result 블록으로 결과를 Claude에 돌려보냅니다. 이 블록은 user 메시지 안에 들어가며, 도구 실행 결과를 Claude에 알립니다. 주요 속성은 다음과 같습니다.

  • tool_use_id — 대응하는 ToolUse 블록의 id와 반드시 일치해야 함
  • content — 도구 실행 출력을 문자열로 직렬화
  • is_error — 오류 발생 시 True

Claude는 한 응답에서 여러 도구 호출을 요청할 수 있습니다. 예를 들어 "10 + 10과 30 + 30은?"이라 물으면 두 개의 ToolUse 블록으로 응답할 수 있습니다.

각 도구 호출에는 고유 ID가 있으며, 결과를 돌려보낼 때 이 ID를 일치시켜야 합니다. 결과가 다른 순서로 도착해도 Claude가 어떤 결과가 어떤 요청에 대응하는지 알 수 있습니다.

🎬 영상 + 요약

여러 도구를 사용하는 애플리케이션에서는 Claude가 하나의 질문에 답하기 위해 여러 도구를 순차적으로 호출해야 하는 상황을 처리해야 합니다. 예를 들어 "오늘부터 103일 뒤는 무슨 요일인가?"라는 질문에는 먼저 현재 날짜를 얻고, 거기에 103일을 더해야 합니다.

멀티턴 도구 패턴

Claude가 여러 도구를 필요로 할 때 내부에서 일어나는 일은 다음과 같습니다.

  1. 사용자가 "오늘부터 103일 뒤는 무슨 요일인가?"라고 질문
  2. Claude가 get_current_datetime을 요청하는 tool use 블록으로 응답
  3. 서버가 함수를 실행하고 결과를 반환
  4. Claude가 정보가 더 필요함을 인지하고 add_duration_to_datetime을 요청
  5. 서버가 그 함수를 실행하고 결과를 반환
  6. 이제 Claude가 최종 답변을 낼 충분한 정보를 확보

대화 루프 구성

이 패턴을 처리하려면 Claude가 더 이상 도구를 요청하지 않을 때까지 반복하는 대화 루프가 필요합니다.

def run_conversation(messages):

헬퍼 함수 리팩터링

대화 루프를 구현하기 전에, 여러 개의 메시지 블록을 제대로 다루도록 헬퍼 함수를 먼저 갱신해야 합니다.

메시지 핸들러 업데이트

기존 add_user_message와 add_assistant_message는 항상 순수 텍스트만 다룬다고 가정합니다. 전체 메시지 객체까지 처리하도록 수정합니다.

from anthropic.types import Message

def add_user_message(messages, message):
user_message = {
"role": "user",
"content": message.content if isinstance(message, Message) else message
}
messages.append(user_message)

이렇게 하면 문자열, 블록 리스트, 완전한 메시지 객체 중 무엇이든 넘길 수 있습니다.

chat 함수 업데이트

chat 함수가 도구 리스트를 받고, 텍스트가 아닌 전체 메시지를 반환하도록 수정합니다.

def chat(messages, system=None, temperature=1.0, stop_sequences=[], tools=None):
params = {
"model": model,
"max_tokens": 1000,
"messages": messages,
"temperature": temperature,
"stop_sequences": stop_sequences,
}

if tools:
params["tools"] = tools

if system:
params["system"] = system

message = client.messages.create(**params)
return message

메시지에서 텍스트 추출

이제 전체 메시지 객체를 반환하므로, 필요할 때 텍스트만 뽑아내는 헬퍼를 만듭니다.

def text_from_message(message):
return "\n".join(
[block.text for block in message.content if block.type == "text"]
)

메시지 안의 모든 text 블록을 찾아 이어 붙이며, 최종 응답을 사용자에게 보여줄 때 유용합니다.

핵심 개선점

  • 유연한 메시지 처리 — 다양한 메시지 형식을 다룰 수 있음
  • chat 함수의 도구 지원 — 도구 스키마를 받아 전달 가능
  • 전체 메시지 반환 — 모든 블록을 보존한 완전한 메시지 확보
  • 텍스트 추출 유틸 — 복잡한 메시지에서 읽을 텍스트를 쉽게 획득

  • 요청이 담긴 user 메시지

세분화된 도구 호출

🎬 영상 + 요약

도구 사용과 스트리밍을 결합하면 AI가 도구 인자를 생성하는 과정을 실시간으로 받아볼 수 있습니다. 더 반응성 높은 경험을 만들지만, 내부 동작에는 알아둘 세부 사항이 있습니다.

기본 도구 스트리밍

스트리밍을 켜면 Claude는 요청을 처리하며 여러 종류의 이벤트를 보냅니다. 일반 텍스트 생성의 ContentBlockDelta는 이미 익숙할 텐데, 도구 사용에서는 InputJsonEvent라는 새 이벤트도 처리해야 합니다.

각 InputJsonEvent에는 두 가지 핵심 속성이 있습니다.

  • partial_json — 도구 인자의 일부를 나타내는 JSON 조각
  • snapshot — 지금까지 받은 조각들을 누적한 JSON
for chunk in stream:
if chunk.type == "input_json":
# Process the partial JSON chunk
print(chunk.partial_json)
# Or use the complete snapshot so far
current_args = chunk.snapshot

JSON 검증 동작 방식

흥미로운 지점입니다. Anthropic API는 Claude가 생성하는 모든 조각을 즉시 보내지 않고, 버퍼링해서 먼저 검증합니다.

API는 최상위 키-값 쌍이 완성될 때까지 기다렸다가 전송합니다. 예를 들어 도구가 다음 구조를 기대한다면:

{
"abstract": "This paper presents a novel...",
"meta": {
"word_count": 847,
"review": "This paper introduces QuanNet..."
}
}

API의 동작은 다음과 같습니다.

  • abstract 값 전체가 완성될 때까지 대기
  • 해당 키-값 쌍을 스키마에 대해 검증
  • 버퍼링한 abstract 조각들을 한꺼번에 전송
  • meta 객체에 대해 같은 과정 반복

이 검증 과정 때문에 스트리밍인데도 지연 후 텍스트가 몰아서 나오는 현상이 생깁니다.

세분화된 도구 호출

더 빠르고 세밀한 스트리밍이 필요하다면 fine-grained tool calling을 켤 수 있습니다.

이 기능의 핵심은 API 측 JSON 검증을 끄는 것입니다.

  • Claude가 생성하자마자 조각을 받음
  • 최상위 키 사이의 버퍼링 지연 없음
  • 보다 전통적인 스트리밍 동작
  • 중요: JSON 검증이 꺼지므로 잘못된 JSON을 코드가 직접 처리해야 함

API 호출에 fine_grained=True를 추가해 활성화합니다.

run_conversation(
messages,
tools=[save_article_schema],
fine_grained=True
)

이렇게 하면 전체 meta 객체가 완성되기를 기다리지 않고 word_count 값을 스트림 초반에 받을 수 있습니다.

잘못된 JSON 처리

fine-grained 사용 시 Claude가 "word_count": undefined 같은 올바르지 않은 JSON을 만들 수 있으므로 우아하게 처리해야 합니다.

try:
parsed_args = json.loads(chunk.snapshot)
except json.JSONDecodeError:
# Handle invalid JSON appropriately
print("Received invalid JSON, continuing...")

이 기능을 끄면 API 검증이 이런 오류를 잡아 문제 값을 문자열로 감쌀 수 있는데, 이는 기대한 스키마와 맞지 않을 수 있습니다.

언제 사용할까

  • 도구 인자 생성 진행 상황을 실시간으로 보여줘야 할 때
  • 부분 도구 결과를 최대한 빨리 처리하고 싶을 때
  • 버퍼링 지연이 사용자 경험을 해칠 때
  • 견고한 JSON 오류 처리를 구현할 수 있을 때

대부분의 애플리케이션에서는 검증이 포함된 기본 동작으로 충분합니다.

텍스트 편집 도구

🎬 영상 + 요약

참고: 모델 버전별 도구 버전 문자열은 공식 문서(text-editor-tool)에서 확인할 수 있습니다. Claude에는 직접 만들 필요 없는 내장 도구가 하나 있는데, 바로 텍스트 편집 도구입니다. 이 도구는 표준 텍스트 편집기처럼 파일과 디렉터리를 다룰 능력을 부여합니다.

텍스트 편집 도구가 하는 일

  • 파일 또는 디렉터리 내용 보기
  • 파일의 특정 라인 범위 보기
  • 파일 내 텍스트 치환
  • 새 파일 생성
  • 특정 라인에 텍스트 삽입
  • 최근 편집 되돌리기

이는 Claude의 능력을 크게 확장해, 사실상 곧바로 소프트웨어 엔지니어처럼 동작하게 합니다.

구현 요구사항 이해

다소 헷갈리는 지점: 도구 스키마는 Claude에 내장돼 있지만 실제 구현은 직접 제공해야 합니다. Claude는 파일 작업을 요청하는 법을 알지만, 그 작업을 실제로 수행하는 코드는 개발자가 작성해야 합니다.

다른 도구는 JSON 스키마와 함수 구현을 모두 작성하지만, 텍스트 편집 도구는 스키마 지식을 Claude가 제공하고 개발자는 파일 생성·읽기·치환 등을 처리하는 함수만 작성하면 됩니다.

스키마 버전

메인 스키마는 내장돼 있지만, 요청 시 작은 스키마 스텁을 포함해야 합니다. 정확한 스키마는 사용하는 Claude 모델에 따라 다릅니다.

def get_text_edit_schema(model):
if model.startswith("claude-3-7-sonnet"):
return {
"type": "text_editor_20250124",
"name": "str_replace_editor",
}
elif model.startswith("claude-3-5-sonnet"):
return {
"type": "text_editor_20241022",
"name": "str_replace_editor",
}

Claude는 이 작은 스키마를 보고 내부에서 전체 텍스트 편집 도구 사양으로 자동 확장합니다.

실전 예시

"./main.py 파일을 열어 내용을 요약해줘"라고 하면 Claude는 도구로 파일을 보고, 내용을 읽고, 요약을 제공합니다. 더 나아가 "./main.py에 파이를 소수점 5자리까지 계산하는 함수를 작성하고, 이를 테스트할 ./test.py를 만들어줘"라고 하면 기존 파일 확인 → 새 구현으로 내용 치환 → 적절한 단위 테스트가 담긴 새 파일 생성을 수행합니다.

왜 사용할까

최신 코드 에디터에 이미 AI가 있는데도 이 도구가 유용한 경우: 파일을 프로그램적으로 편집해야 하는 앱을 만들 때, 완전한 코드 에디터가 없는 환경에서 작업할 때, 파일 편집 기능을 Claude 기반 앱에 직접 통합하고 싶을 때. 즉 나만의 앱 안에 AI 코드 에디터 기능을 재현하고 Claude의 파일 접근을 세밀하게 제어할 수 있습니다.

웹 검색 도구

🎬 영상 + 요약

참고: 사용 전에 조직이 콘솔 설정에서 웹 검색 도구를 활성화해야 합니다(console의 settings/privacy). Claude에는 인터넷을 검색해 최신·전문 정보를 답변에 활용하는 내장 웹 검색 도구가 있습니다. 다른 도구와 달리 구현을 제공할 필요 없이, 간단한 스키마만 넘기면 Claude가 검색 전 과정을 자동으로 처리합니다.

웹 검색 도구 설정

다음 필수 필드로 스키마 객체를 만듭니다.

web_search_schema = {
"type": "web_search_20250305",
"name": "web_search",
"max_uses": 5
}

max_uses는 Claude가 수행할 수 있는 검색 횟수를 제한합니다. 초기 결과를 바탕으로 후속 검색을 할 수 있으므로 과도한 API 호출을 막습니다.

응답 구조

웹 검색 도구를 쓰면 응답에 여러 종류의 블록이 담깁니다.

  • Text 블록 — Claude의 설명
  • ServerToolUseBlock — Claude가 사용한 정확한 검색 쿼리
  • WebSearchToolResultBlock — 검색 결과 모음
  • WebSearchResultBlock — 제목·URL이 포함된 개별 결과
  • Citation 블록 — Claude의 주장을 뒷받침하는 텍스트

이 구조로 Claude가 무엇을 검색했고 어떤 출처를 찾았는지 정확히 확인할 수 있으며, 인용에는 근거 텍스트와 출처 URL이 포함됩니다.

검색 도메인 제한

allowed_domains 필드로 특정 도메인으로 검색을 제한할 수 있습니다. 신뢰할 수 있는 출처가 필요할 때 유용합니다.

web_search_schema = {
"type": "web_search_20250305",
"name": "web_search",
"max_uses": 5,
"allowed_domains": ["nih.gov"]
}

예컨대 의료·운동 조언을 물을 때 PubMed(nih.gov) 같은 도메인으로 제한하면 무작위 블로그 대신 근거 기반 정보를 얻습니다.

검색 결과 렌더링

  • text 블록은 일반 콘텐츠로 렌더링
  • 웹 검색 결과는 상단에 출처 목록으로 표시
  • 인용은 본문 내 인라인으로, 출처 도메인·제목·URL·인용 텍스트와 함께 표시

이 구조는 Claude가 어떻게 답에 도달했는지 사용자에게 투명하게 보여주고 응답에 대한 신뢰를 높입니다.

실전 활용

웹 검색이 잘 맞는 경우: 시사·최신 동향, 학습 데이터에 없는 전문 정보, 사실 확인 및 권위 있는 출처 찾기, 최신 정보가 필요한 조사. 스키마를 tools 배열에 넣기만 하면 Claude가 검색이 도움될 시점을 스스로 판단합니다.

RAG 소개

🎬 영상 + 요약

RAG(Retrieval Augmented Generation)는 하나의 프롬프트에 담기에 너무 큰 문서를 다루기 위한 기법입니다. 모든 것을 거대한 프롬프트에 욱여넣는 대신, 문서를 청크로 나누고 질문에 답할 때 가장 관련 있는 조각만 포함합니다.

큰 문서의 문제

800페이지짜리 재무 문서에 대해 "이 회사의 리스크 요인은?" 같은 질문을 한다고 해봅시다. 관련 정보를 Claude에게 전달해야 하지만, 프롬프트에 넣을 수 있는 텍스트 양에는 한계가 있습니다.

방법 1: 모든 것을 프롬프트에 넣기

가장 단순한 접근은 문서의 모든 텍스트를 추출해 질문과 함께 프롬프트에 넣는 것입니다.

Answer the user's question about the financial document.

<user_question>
{user_question}
</user_question>

<financial_document>
{financial_document}
</financial_document>

이 방식에는 심각한 한계가 있습니다.

  • 프롬프트 길이에 엄격한 제한이 있음 — 문서가 너무 길 수 있음
  • 매우 긴 프롬프트에서는 Claude의 성능이 떨어짐
  • 긴 프롬프트는 비용이 더 큼
  • 긴 프롬프트는 처리 시간이 더 김

방법 2: 문서를 청크로 나누기

RAG는 더 똑똑하게 접근합니다. 전처리 단계에서 문서를 작은 청크로 나눈 뒤, 질문이 들어오면 가장 관련 있는 청크만 찾아 프롬프트에 포함합니다.

"이 회사가 직면한 리스크는?"이라고 물으면 청크들을 검색해 "리스크 요인" 섹션을 찾아 그 청크만 프롬프트에 넣습니다.

RAG의 장점과 과제

장점과제
가장 관련 있는 내용에만 집중문서를 청킹하는 전처리 단계 필요
아주 큰 문서로 확장 가능관련 청크를 찾는 검색 메커니즘 필요
여러 문서와 함께 동작포함된 청크에 필요한 맥락이 모두 없을 수 있음
작은 프롬프트로 비용·속도 개선청킹 방법이 다양해 무엇이 최선인지 판단 필요

언제 RAG를 쓸까

RAG는 단순 프롬프트 스터핑보다 손이 많이 갑니다. 핵심 통찰은 RAG가 단순함을 내주고 확장성과 효율을 얻는다는 점입니다. 아주 큰 문서, 여러 문서, 비용·성능 최적화가 필요할 때 특히 가치 있습니다.

텍스트 청킹 전략

🎬 영상 + 요약

텍스트 청킹은 RAG 파이프라인에서 가장 중요한 단계 중 하나입니다. 문서를 어떻게 나누느냐가 시스템 전체 품질에 직접 영향을 줍니다. 잘못된 청킹은 무관한 맥락을 프롬프트에 넣어 완전히 틀린 답을 유발할 수 있습니다.

예를 들어 의료 연구와 소프트웨어 엔지니어링 섹션이 있는 문서에서 청킹이 나쁘면, "엔지니어가 올해 버그를 몇 개 고쳤나?"라는 질문에 의료 섹션이 다른 맥락의 "bug"라는 단어를 포함했다는 이유로 엉뚱한 정보를 줄 수 있습니다.

크기 기반 청킹

가장 단순한 방식으로, 텍스트를 동일한 길이의 문자열로 나눕니다. 325자 문서를 약 108자씩 세 청크로 나누는 식입니다.

구현이 쉽고 어떤 문서에도 적용되지만 단점이 분명합니다.

  • 단어가 문장 중간에서 잘림
  • 주변 텍스트의 중요한 맥락을 잃음
  • 섹션 헤더가 본문과 분리될 수 있음

이를 완화하려면 청크 사이에 겹침(overlap)을 둡니다. 각 청크가 이웃 청크의 일부 문자를 포함해 맥락과 온전한 문장을 보장합니다.

def chunk_by_char(text, chunk_size=150, chunk_overlap=20):
chunks = []
start_idx = 0

while start_idx < len(text):
end_idx = min(start_idx + chunk_size, len(text))
chunk_text = text[start_idx:end_idx]
chunks.append(chunk_text)

start_idx = (
end_idx - chunk_overlap if end_idx < len(text) else len(text)
)

return chunks

구조 기반 청킹

헤더·문단·섹션 등 문서의 자연스러운 구조로 나눕니다. Markdown처럼 잘 정형화된 문서에서 훌륭히 동작합니다.

def chunk_by_section(document_text):
pattern = r"\n## "
return re.split(pattern, document_text)

각 청크가 완전한 섹션을 나타내 가장 깔끔하고 의미 있는 결과를 주지만, 문서 구조가 보장될 때만 통합니다. 실제 문서 상당수는 구조 마커가 없는 평문이나 PDF입니다.

의미 기반 청킹

가장 정교한 방식입니다. 텍스트를 문장으로 나눈 뒤 NLP로 인접 문장의 관련도를 판단하고, 관련 있는 문장 그룹으로 청크를 구성합니다. 계산 비용이 크지만 가장 관련성 높은 청크를 만듭니다.

문장 기반 청킹

실용적인 중간 지점입니다. 정규식으로 문장을 나눈 뒤 겹침을 두고 그룹화합니다.

def chunk_by_sentence(text, max_sentences_per_chunk=5, overlap_sentences=1):
sentences = re.split(r"(?<=[.!?])\s+", text)

chunks = []
start_idx = 0

while start_idx < len(sentences):
end_idx = min(start_idx + max_sentences_per_chunk, len(sentences))
current_chunk = sentences[start_idx:end_idx]
chunks.append(" ".join(current_chunk))

start_idx += max_sentences_per_chunk - overlap_sentences

if start_idx < 0:
start_idx = 0

return chunks

텍스트 임베딩

🎬 영상 + 요약

문서를 청크로 나눈 다음 RAG 파이프라인의 단계는 어떤 청크가 사용자 질문과 가장 관련 있는지 찾는 것입니다. 본질적으로 검색 문제로, 모든 청크를 훑어 질문과 관련된 것을 골라야 합니다.

의미 검색

관련 청크를 찾는 가장 흔한 방식은 의미 검색(semantic search)입니다. 정확한 단어 일치를 찾는 키워드 검색과 달리, 텍스트 임베딩으로 질문과 각 청크의 의미·맥락을 이해합니다.

텍스트 임베딩

텍스트 임베딩은 텍스트에 담긴 의미의 수치적 표현입니다. 단어와 문장을 컴퓨터가 수학적으로 다룰 수 있는 형태로 변환한 것으로 볼 수 있습니다.

  • 텍스트를 임베딩 모델에 입력
  • 모델이 긴 숫자 리스트(임베딩)를 출력
  • 각 숫자는 -1에서 +1 사이
  • 이 숫자들이 입력 텍스트의 다양한 특성을 나타냄

숫자의 의미

각 숫자는 입력 텍스트의 어떤 특성에 대한 "점수"이지만, 중요한 단서가 있습니다. 각 숫자가 정확히 무엇을 나타내는지는 알 수 없습니다. "텍스트가 얼마나 행복한지"처럼 상상하면 도움이 되지만, 실제 차원의 의미는 학습 중 결정되며 사람이 직접 해석할 수는 없습니다.

임베딩 제공자: VoyageAI

현재 Anthropic은 임베딩 생성을 제공하지 않으므로 VoyageAI가 권장됩니다.

  • 별도 VoyageAI 계정 가입
  • API 키 발급(무료로 시작 가능)
  • 키를 환경 변수에 추가

.env 파일에 추가합니다.

VOYAGE_API_KEY="your_key_here"

구현

먼저 VoyageAI 라이브러리를 설치합니다.

%pip install voyageai

그다음 클라이언트를 설정하고 임베딩 생성 함수를 만듭니다.

from dotenv import load_dotenv

def generate_embedding(text, model="voyage-3-large", input_type="query"):

return result.embeddings[0]

전체 RAG 흐름

🎬 영상 + 요약

RAG·청킹·임베딩 기초를 다뤘으니, 완전한 RAG 파이프라인을 단계별로 살펴봅니다. 각 요소가 어떻게 맞물려 관련 정보를 검색하고 응답을 생성하는지 보여줍니다.

1단계: 원문 청킹

원본 문서를 다루기 쉬운 청크로 나눕니다. 예시로 두 섹션을 사용합니다.

  • 섹션 1 의료 연구 — "올해 처음 보는 'bug'인 XDR-47 이해에 큰 진전이 있었다."
  • 섹션 2 소프트웨어 엔지니어링 — "분산 시스템의 다양한 감염 벡터(infection vectors) 연구에 상당한 노력을 기울였다."

2단계: 임베딩 생성

각 청크를 임베딩으로 변환합니다. 이해를 돕기 위해 항상 두 개의 숫자를 반환하고 그 의미를 우리가 아는 이상적 모델을 가정합니다.

  • 첫 번째 숫자: 텍스트가 의료 분야를 다루는 정도
  • 두 번째 숫자: 텍스트가 소프트웨어 엔지니어링을 다루는 정도

의료 섹션은 "bug" 때문에 소프트웨어 요소가 약간 섞여 [0.97, 0.34], 소프트웨어 섹션은 "infection vectors" 때문에 의료 뉘앙스가 있어 [0.30, 0.97] 정도가 될 수 있습니다.

정규화

임베딩 API는 각 벡터의 크기를 1.0으로 스케일링하는 정규화를 수행합니다. 수학은 자동 처리되며, 위 값은 [0.944, 0.331], [0.295, 0.955] 같은 정규화 벡터가 됩니다.

이 임베딩을 단위원(unit circle) 위에 시각화할 수 있고, 각 점이 하나의 청크를 나타냅니다.

3단계: 벡터 DB에 저장

이 임베딩을 벡터 데이터베이스(긴 숫자 리스트의 저장·비교·검색에 최적화된 특수 DB)에 저장합니다.

여기까지는 사전에 이뤄지는 전처리이며, 이제 사용자 질의를 기다립니다.

4단계: 사용자 질의 처리

"소프트웨어 엔지니어링 부서가 올해 무엇을 했나?" 같은 질문이 들어오면 동일한 임베딩 모델로 질의를 임베딩합니다.

질의는 의료 점수는 낮고 소프트웨어 점수가 높은 [0.1, 0.89]로, 정규화하면 [0.112, 0.993]이 됩니다.

5단계: 유사 임베딩 찾기

질의 임베딩을 벡터 DB에 보내 가장 유사한 저장 임베딩을 찾도록 요청합니다.

DB는 질문과 가장 가까운 소프트웨어 엔지니어링 섹션을 반환합니다.

유사도 계산: 코사인 유사도

벡터 DB는 코사인 유사도로 어떤 임베딩이 가장 유사한지 판단합니다. 두 벡터 사이 각도의 코사인을 측정합니다.

  • 결과 범위는 -1에서 1
  • 1에 가까우면 높은 유사도
  • -1에 가까우면 매우 다름
  • 0은 수직(관계 없음)

예시에서 질의와 소프트웨어 청크의 코사인 유사도는 0.983으로 매우 높고, 의료 청크와는 0.398로 훨씬 낮습니다.

코사인 거리

벡터 DB 문서에서 자주 보이는 "코사인 거리"는 단순히 (1 - 코사인 유사도)입니다. 0에 가까우면 높은 유사도, 값이 클수록 유사도가 낮습니다.

6단계: 최종 프롬프트 구성

질문과 찾은 관련 청크를 결합해 프롬프트로 만들고 Claude에 보냅니다.

Answer the user's question about the financial document.

<user_question>
How many bugs did engineers fix this year?
</user_question>

<report>
## Section 2: Software Engineering
This division dedicated significant effort to studying various infection vectors in our distributed systems
</report>
이것이 완전한 RAG 파이프라인입니다. 의미 유사도를 기반으로 가장 관련 있는 정보를 검색해 맥락으로 제공하고 정확한 응답을 생성합니다.

RAG 흐름 구현

개념을 이해했으니 RAG 흐름을 단계별로 구현합니다. 텍스트 청킹, 임베딩 생성, 벡터 DB 저장, 유사도 검색을 한 예제로 다룹니다.

다섯 단계 RAG 구현

  1. 섹션별로 텍스트 청킹
  2. 각 청크의 임베딩 생성
  3. 벡터 스토어를 만들고 각 임베딩 추가
  4. 사용자 질문의 임베딩 생성
  5. 스토어를 검색해 가장 관련 있는 청크 찾기

1단계: 텍스트 청킹

with open("./report.md", "r") as f:
text = f.read()

chunks[2] # Test to see the table of contents

앞서 쓴 chunk_by_section으로 문서를 논리적 섹션으로 나눕니다.

2단계: 임베딩 생성

embeddings = generate_embedding(chunks)

임베딩 함수는 단일 문자열과 문자열 리스트를 모두 처리하도록 갱신돼 배치 처리에 효율적입니다.

3단계: 벡터 DB에 저장

store = VectorIndex()

for embedding, chunk in zip(embeddings, chunks):
store.add_vector(embedding, {"content": chunk})

임베딩과 원문 텍스트를 함께 저장합니다. 나중에 검색할 때 숫자가 아닌 실제 텍스트를 반환해야 하므로 중요합니다.

원문을 함께 저장하는 이유

질의 시 임베딩 숫자만 돌려받으면 쓸모가 없습니다. 임베딩을 만든 실제 텍스트가 필요하므로 각 임베딩과 함께 원문 청크(또는 참조)를 담아둡니다.

4단계: 사용자 질의 처리

user_embedding = generate_embedding("What did the software engineering dept do last year?")

5단계: 관련 콘텐츠 찾기

results = store.search(user_embedding, 2)

for doc, distance in results:
print(distance, "\n", doc["content"][0:200], "\n")

가장 유사한 두 청크와 유사도 점수(코사인 거리)를 반환합니다.

결과 이해

  • 섹션 2 소프트웨어 엔지니어링 — 거리 0.71 (가장 가까움)
  • Methodology 섹션 — 거리 0.72 (두 번째)

거리 값이 낮을수록 유사하므로 섹션 2가 가장 관련 있습니다.

RAG의 핵심은 텍스트를 숫자(임베딩)로 바꾸고, 효율적으로 저장한 뒤, 수학적 유사도로 관련 콘텐츠를 찾는 것입니다. 기본 사례는 잘 동작하지만 개선이 필요한 시나리오가 남아 있습니다.

BM25 렉시컬 검색

🎬 영상 + 요약

RAG 파이프라인을 만들다 보면 의미 검색만으로는 최선의 결과가 나오지 않을 때가 있음을 알게 됩니다. 의미 검색이 놓치는 정확한 용어 일치가 필요할 때가 있는데, 이럴 때 BM25라는 렉시컬 검색을 결합합니다.

의미 검색만의 문제

"INC-2023-Q4-011" 같은 특정 사건 ID를 검색한다고 합시다. 의미 검색은 맥락 파악에 뛰어나지만, 정작 찾는 정확한 용어가 없는데 의미상 관련된 섹션을 반환할 수 있습니다.

위 예에서 의미 검색은 사건 ID를 포함한 사이버보안 섹션과 함께, ID를 전혀 언급하지 않는 재무 분석 섹션까지 반환했습니다. 개념적 유사성에 집중하기 때문입니다.

하이브리드 검색 전략

해법은 의미 검색과 렉시컬 검색을 병렬로 돌린 뒤 결과를 병합하는 것입니다.

  • 의미 검색: 임베딩으로 개념적 관련 콘텐츠를 찾음
  • 렉시컬 검색: 고전 텍스트 검색으로 정확한 용어 일치를 찾음
  • 병합 결과: 두 방식을 합쳐 정확도 향상

BM25 동작 방식

BM25(Best Match 25)는 RAG의 렉시컬 검색에 널리 쓰이는 알고리즘입니다.

  1. 쿼리 토큰화 — 질문을 개별 용어로 분리. "a INC-2023-Q4-011"은 ["a", "INC-2023-Q4-011"]이 됨
  2. 용어 빈도 계산 — 각 용어가 전체 문서에 얼마나 자주 나오는지 확인
  3. 중요도 가중 — 덜 등장하는 용어일수록 높은 점수. "a"는 낮고 "INC-2023-Q4-011"은 높음
  4. 최적 매치 찾기 — 가중치 높은 용어를 더 많이 포함한 문서를 반환

BM25 검색 구현

# 1. Chunk your text by sections
chunks = chunk_by_section(text)

# 2. Create a BM25 store and add documents
store = BM25Index()
for chunk in chunks:
store.add_document({"content": chunk})

# 3. Search the store
results = store.search("What happened with INC-2023-Q4-011?", 3)

# Print results
for doc, distance in results:
print(distance, "\n", doc["content"][:200], "\n----\n")

이 검색은 의미 검색만 쓸 때보다 훨씬 나은 결과를 줍니다. 사건 ID 같은 희귀 용어를 실제로 포함한 섹션을 우선합니다.

왜 더 잘 동작할까

  • 희귀하고 구체적인 용어에 높은 가중치 부여
  • 검색 가치가 없는 흔한 단어 무시
  • 의미가 아닌 용어 빈도에 집중
  • 기술 용어·ID·특정 문구에 특히 강함

두 검색은 상호 보완적입니다. 의미 검색은 맥락을 이해하고, 렉시컬 검색은 정확한 용어를 놓치지 않게 합니다.

다중 인덱스 아키텍처

VectorIndex와 BM25Index는 add_document()와 search()라는 거의 동일한 API를 공유합니다. 이 일관성 덕분에 둘을 Retriever라는 새 클래스로 함께 감싸기 쉽습니다.

Retriever는 질의를 두 인덱스에 전달하고 결과를 모아 상호 순위 융합(reciprocal rank fusion)으로 병합하는 코디네이터입니다.

상호 순위 융합(RRF) 이해

서로 다른 검색 결과를 병합하는 것은 단순 연결이 아닙니다. 방식마다 점수 체계가 달라 순위를 공정하게 정규화·결합해야 합니다.

"INC-2023-Q4-011"을 검색해 다음 결과를 얻었다고 합시다.

  • VectorIndex: 섹션 2(1위), 섹션 7(2위), 섹션 6(3위)
  • BM25Index: 섹션 6(1위), 섹션 2(2위), 섹션 7(3위)

각 청크의 양쪽 순위를 한 표로 모아 RRF 공식을 적용합니다.

RRF_score(d) = Σ(1 / (k + rank_i(d)))

여기서 k는 상수(보통 60이지만 여기선 결과를 명확히 보려고 1 사용), rank_i(d)는 i번째 랭킹에서 문서 d의 순위입니다.

  • 섹션 2: 1.0/(1+1) + 1.0/(1+2) = 0.833
  • 섹션 7: 1.0/(1+2) + 1.0/(1+3) = 0.583
  • 섹션 6: 1.0/(1+3) + 1.0/(1+1) = 0.75

최종 순위는 섹션 2(0.833), 섹션 6(0.75), 섹션 7(0.583)입니다. 양쪽에서 잘한 섹션 2가 위로 올라오는 것이 직관적입니다.

인용(Citations)

🎬 영상 + 요약

Claude가 제공한 문서를 기반으로 답변할 때, 사용자는 그것이 학습 데이터에서 나온 것인지 문서에서 나온 것인지 알기 어렵습니다. 인용(Citations)은 Claude가 원본 문서의 특정 부분을 참조하고, 각 정보가 정확히 어디에서 왔는지 보여주는 강력한 기능입니다.

인용이 중요한 이유

인용이 없으면 사용자는 답변을 검증하거나 Claude가 실제로 제공된 문서를 참조하고 있는지 확인할 수 없습니다. 인용은 Claude의 응답에서 원본 자료로 이어지는 명확한 경로를 만들어 이 투명성 문제를 해결합니다.

인용 활성화하기

인용을 켜려면 document 메시지 구조를 수정해야 합니다. document 블록에 두 개의 필드를 추가합니다.

{
"type": "document",
"source": {
"type": "base64",
"media_type": "application/pdf",
"data": file_bytes,
},
"title": "earth.pdf",
"citations": { "enabled": True }
}

title 필드는 문서에 읽기 쉬운 이름을 부여하고, citations: {"enabled": True}는 Claude에게 정보의 출처를 추적하도록 지시합니다.

인용 구조 이해하기

인용이 켜지면 Claude의 응답은 단순 텍스트가 아니라 각 주장에 대한 인용 정보를 포함한 구조화된 데이터가 됩니다.

각 인용은 다음과 같은 핵심 정보를 담습니다.

  • cited_text - Claude의 진술을 뒷받침하는 문서 내 정확한 텍스트
  • document_index - 참조 중인 문서(여러 문서를 제공할 때 유용)
  • document_title - 문서에 부여한 제목
  • start_page_number - 인용 텍스트가 시작되는 위치
  • end_page_number - 인용 텍스트가 끝나는 위치

인용을 활용한 UI 구축

인용의 진정한 힘은 이 정보를 사용자가 접근할 수 있는 UI를 만드는 데서 나옵니다. 인용 마커에 마우스를 올리면 정보의 출처를 보여주는 인터랙티브 요소를 만들 수 있습니다.

이를 통해 사용자는 다음을 할 수 있는 투명한 경험을 얻습니다.

  • Claude의 답변이 실제 원본 자료에 근거함을 확인
  • 원본 문서를 확인하여 정보를 검증
  • 인용된 각 정보의 맥락을 이해

  • 주변 텍스트를 기반으로 맥락 추가
  • 그 후에야 실제 출력 텍스트 생성

응답을 보낸 뒤 Claude는 이 모든 연산 작업(토큰화, embedding, 맥락 분석)을 버립니다.

작업을 버리는 것의 문제

같은 내용을 포함한 후속 요청을 보낼 때 비효율이 발생합니다. 예를 들어 같은 긴 텍스트의 요약을 반복해서 다듬는 대화에서는,

Claude는 방금 분석한 내용에 대해 동일한 전처리를 반복해야 합니다. "방금 처리하고 버린 작업을 재사용할 수 있었을 텐데"라고 생각할 수 있는 상황입니다.

프롬프트 캐싱의 해결 방식

프롬프트 캐싱은 전처리 작업을 버리는 대신 저장하여 이 워크플로우를 바꿉니다.

최초 요청 시 Claude는 평소대로 전처리를 하되 결과를 버리지 않고 캐시에 저장합니다. 캐시는 "이 메시지를 다시 보면 이미 한 작업을 재사용하겠다"는 조회 테이블처럼 작동합니다.

핵심 이점과 한계

  • 더 빠른 응답 · 캐시된 내용을 사용하는 요청은 더 빠르게 실행
  • 더 낮은 비용 · 캐시된 부분에 대해 더 적게 지불
  • 자동 최적화 · 최초 요청은 캐시에 쓰고, 후속 요청은 캐시에서 읽음

다만 유의할 한계가 있습니다.

  • 캐시 지속 시간: 캐시된 내용은 1시간만 유지됨
  • 제한된 활용처: 같은 내용을 반복해서 보낼 때만 유용
  • 높은 빈도 요구: 같은 내용이 매우 자주 등장할 때 가장 효과적

같은 대형 문서에 여러 질문을 던지는 문서 분석 워크플로우나, 기반 내용은 고정된 채 세부만 다듬는 반복 편집 작업에 가장 적합합니다.

프롬프트 캐싱 규칙

🎬 영상 + 요약

프롬프트 캐싱은 메시지에 대해 수행한 연산 작업을 저장해 후속 요청에서 재사용하는 방식으로 동작합니다. 이렇게 하면 후속 요청이 더 빠르고 저렴해지지만, 동일한 내용을 반복해서 보낼 때만 효과가 있습니다.

과정은 단순합니다. 최초 요청이 처리 작업을 캐시에 쓰고, 후속 요청은 같은 내용을 재처리하는 대신 캐시에서 읽습니다. 캐시는 1시간만 유지되므로 그 시간 안에 같은 내용을 반복해 보낼 때만 유용합니다.

캐시 브레이크포인트

캐싱은 자동으로 켜지지 않습니다. 메시지의 특정 블록에 캐시 브레이크포인트를 수동으로 추가해야 합니다.

  • 메시지에 대한 작업은 자동 캐시되지 않음
  • 블록에 'cache breakpoint'를 수동으로 추가해야 함
  • 브레이크포인트 이전의 모든 작업이 캐시됨
  • 브레이크포인트까지의 내용이 동일할 때만 후속 요청에서 캐시가 사용됨

캐시 브레이크포인트를 추가하려면 텍스트 블록을 축약형(shorthand)이 아니라 확장형(longhand)으로 작성해야 합니다.

축약형에는 cache control 필드를 넣을 자리가 없으므로, cache_control 필드를 {"type": "ephemeral"}로 설정한 확장 형식을 써야 합니다.

캐시 브레이크포인트의 동작

브레이크포인트를 두면 그 지점까지의 모든 처리 작업이 캐시되고, 이후 내용은 캐시 없이 정상 처리됩니다.

후속 요청에서 캐시가 유용하려면 브레이크포인트까지 내용이 동일해야 합니다. "please" 한 단어를 추가하는 작은 변경조차 캐시를 무효화하고 전체를 재처리하게 만듭니다.

메시지 간 캐싱

캐시 브레이크포인트는 여러 메시지와 메시지 타입에 걸칠 수 있습니다. 뒤쪽 메시지에 브레이크포인트를 두면 이전의 모든 메시지(user, assistant 등)가 캐시 대상에 포함됩니다.

특정 지점까지의 전체 맥락을 캐시하고 싶은 대화에서 특히 유용합니다.

시스템 프롬프트와 도구

텍스트 블록에만 국한되지 않고, 캐시 브레이크포인트는 다음에도 추가할 수 있습니다.

  • 시스템 프롬프트
  • 도구 정의(tool definitions)
  • 이미지 블록
  • tool use 및 tool result 블록

시스템 프롬프트와 도구 정의는 요청 간에 거의 바뀌지 않으므로 캐싱의 훌륭한 후보입니다. 프롬프트 캐싱의 이점을 가장 크게 얻는 부분입니다.

캐시 순서

Claude는 요청 구성 요소를 도구 → 시스템 프롬프트 → 메시지 순으로 처리합니다. 이 순서를 이해하면 브레이크포인트를 효과적으로 배치할 수 있습니다.

브레이크포인트는 총 4개까지 추가할 수 있습니다. 예를 들어 도구를 캐시하고, 대화 기록 중간에 또 하나의 브레이크포인트를 둘 수 있습니다. 요청의 각 부분이 다르게 바뀔 때 유연성을 줍니다.

최소 콘텐츠 길이

캐싱에는 최소 임계값이 있습니다. 캐시하려는 내용은 최소 1024 token 이상이어야 합니다. 이는 개별 블록이 아니라 캐시 대상 모든 메시지와 블록의 합입니다.

주의 · 단순한 "Hi there!" 메시지는 임계값을 못 넘깁니다. 하지만 이를 500번 복제하거나 실제로 긴 프롬프트라면 1024 token을 넘겨 캐싱 대상이 됩니다. 여러 호출에 걸쳐 일관되게 유지되는 부분을 찾아 브레이크포인트를 전략적으로 배치하는 것이 핵심입니다.

프롬프트 캐싱 실전

🎬 영상 + 요약

프롬프트 캐싱은 같은 내용을 Claude에 반복해서 보낼 때 API 요청을 더 빠르고 저렴하게 만드는 강력한 최적화 기능입니다. 실제 애플리케이션에서 효과적으로 구현하는 방법을 살펴봅니다.

프롬프트 캐싱의 동작

캐싱을 켜면 최초 요청이 1시간 유지되는 캐시에 내용을 씁니다. 후속 요청은 같은 내용을 다시 처리하지 않고 캐시에서 읽습니다. 특히 다음을 보낼 때 유용합니다.

  • 큰 시스템 프롬프트(예: 6K token짜리 코딩 어시스턴트 프롬프트)
  • 복잡한 도구 스키마(여러 도구에 약 1.7K token)
  • 반복되는 메시지 내용

핵심은 동일한 내용을 반복해 보낼 때만 캐싱이 도움이 된다는 점인데, 많은 애플리케이션에서 이런 상황이 매우 자주 발생합니다.

도구 스키마 캐싱 설정

도구 스키마를 캐시하려면 도구 목록의 마지막 도구에 cache control 필드를 추가합니다. 원본 정의를 건드리지 않고 처리하는 올바른 방법은 다음과 같습니다.

if tools:
tools_clone = tools.copy()
last_tool = tools_clone[-1].copy()
last_tool["cache_control"] = {"type": "ephemeral"}
tools_clone[-1] = last_tool
params["tools"] = tools_clone

이 방식은 도구 목록과 마지막 도구 스키마의 복사본을 만든 뒤 cache control 필드를 추가합니다. tools[-1]["cache_control"]를 직접 수정할 수도 있지만, 복사 방식은 이후 도구 순서를 바꿔도 문제가 생기지 않게 해줍니다.

시스템 프롬프트 캐싱

시스템 프롬프트는 cache control이 붙은 텍스트 블록 형태로 구조화해야 합니다.

if system:
params["system"] = [
{
"type": "text",
"text": system,
"cache_control": {"type": "ephemeral"}
}
]

이렇게 하면 단순 문자열이던 시스템 프롬프트가 캐싱을 지원하는 구조화된 형식으로 바뀝니다.

캐시 동작 이해하기

캐싱을 켜고 요청을 실행하면 응답에서 서로 다른 usage 패턴을 볼 수 있습니다.

  • 첫 요청: cache_creation_input_tokens=1772 — Claude가 캐시에 씀
  • 후속 요청: cache_read_input_tokens=1772 — Claude가 캐시에서 읽음
  • 내용 변경 시: 새로운 cache creation token이 나타남

캐시는 매우 민감해서, 도구나 시스템 프롬프트에서 문자 하나만 바뀌어도 해당 구성 요소의 전체 캐시가 무효화됩니다.

캐시 순서와 브레이크포인트

한 요청에 여러 캐시 브레이크포인트를 설정할 수 있으며 순서가 중요합니다.

  • 도구(제공된 경우)
  • 시스템 프롬프트(제공된 경우)
  • 메시지

시스템 프롬프트를 바꾸고 도구는 그대로 두면, (도구에 대한) 부분 캐시 읽기와 (새 시스템 프롬프트에 대한) 캐시 쓰기가 함께 나타납니다. 이런 세분화된 캐싱 덕분에 실제로 바뀐 부분에 대한 처리 비용만 지불합니다.

실무 고려 사항

  • 요청 간 일관된 도구 스키마
  • 안정적인 시스템 프롬프트
  • 유사한 맥락으로 여러 요청을 보내는 애플리케이션

캐시는 1시간만 유지되므로, 장기 저장이 아니라 비교적 잦은 API 사용을 하는 애플리케이션을 위한 것임을 기억하세요.

코드 실행과 Files API

🎬 영상 + 요약

Anthropic API는 함께 쓰면 특히 강력한 두 기능, Files API와 Code Execution을 제공합니다. 별개로 보이지만 결합하면 복잡한 작업을 Claude에게 위임할 수 있는 흥미로운 가능성이 열립니다.

Files API

Files API는 파일 업로드를 처리하는 대안입니다. 이미지나 PDF를 메시지에 base64로 직접 인코딩하는 대신, 미리 파일을 업로드하고 나중에 참조할 수 있습니다.

동작 방식은 다음과 같습니다.

  • 별도 API 호출로 파일(이미지, PDF, 텍스트 등)을 Claude에 업로드
  • 고유한 file ID가 담긴 파일 메타데이터 객체를 수신
  • 이후 메시지에서 원본 파일 데이터 대신 file ID를 참조

같은 파일을 여러 번 참조하거나, 매 요청에 넣기 번거로운 큰 파일을 다룰 때 특히 유용합니다.

코드 실행 도구

Code Execution은 구현을 직접 제공할 필요가 없는 서버 기반 도구입니다. 미리 정의된 도구 스키마를 요청에 포함하기만 하면, Claude가 격리된 Docker 컨테이너에서 Python 코드를 선택적으로 실행할 수 있습니다.

코드 실행 환경의 주요 특징:

  • 격리된 Docker 컨테이너에서 실행
  • 네트워크 접근 불가(외부 API 호출 불가)
  • 한 대화 중 Claude가 코드를 여러 번 실행 가능
  • 결과가 캡처되어 최종 응답을 위해 Claude가 해석

Files API와 Code Execution 결합

진짜 힘은 두 기능을 함께 쓸 때 나옵니다. Docker 컨테이너에 네트워크 접근이 없으므로, Files API가 실행 환경에 데이터를 넣고 빼는 주된 방법이 됩니다.

전형적인 워크플로우:

  1. Files API로 데이터 파일(예: CSV) 업로드
  2. 메시지에 file ID를 담은 container upload 블록 포함
  3. Claude에게 데이터 분석 요청
  4. Claude가 파일을 처리하는 코드를 작성·실행
  5. Claude가 다운로드 가능한 출력물(예: 그래프) 생성

실전 예제

스트리밍 서비스 데이터를 사용한 예제를 봅니다. CSV에는 구독 등급, 시청 습관, 이탈(구독 취소) 여부 등 사용자 정보가 담겨 있습니다.

먼저 헬퍼 함수로 파일을 업로드합니다.

file_metadata = upload('streaming.csv')

그런 다음 업로드한 파일과 분석 요청을 함께 담은 메시지를 만듭니다.

messages = []
add_user_message(
messages,
[
{
"type": "text",
"text": """Run a detailed analysis to determine major drivers of churn.
Your final output should include at least one detailed plot summarizing your findings."""
},
{"type": "container_upload", "file_id": file_metadata.id},
],
)

chat(
messages,
tools=[{"type": "code_execution_20250522", "name": "code_execution"}]
)

응답 이해하기

Claude가 코드 실행을 사용하면 응답에 여러 종류의 블록이 담깁니다.

  • Text 블록 - Claude의 분석과 설명
  • Server tool use 블록 - Claude가 실행하기로 한 실제 코드
  • Code execution tool result 블록 - 코드 실행 출력

Claude는 한 응답 안에서 코드를 여러 번 실행하며 반복적으로 분석을 쌓아갈 수 있습니다. 각 실행 주기에는 코드와 그 결과가 포함됩니다.

생성된 파일 다운로드

가장 강력한 기능 중 하나는 Claude가 파일(그래프, 리포트 등)을 생성해 다운로드할 수 있게 하는 것입니다. Claude가 시각화를 만들면 컨테이너에 저장되고, Files API로 다운로드할 수 있습니다.

응답에서 type: "code_execution_output"인 블록을 찾으세요. 생성된 콘텐츠의 file ID가 담겨 있습니다.

download_file("file_id_from_response")

결과는 수동으로 짜려면 상당한 코딩이 필요했을 전문적인 시각화가 포함된 종합 분석입니다.

데이터 분석을 넘어서

데이터 분석이 자연스러운 활용처지만, Files API와 코드 실행의 결합은 다양한 가능성을 엽니다.

  • 이미지 처리와 변환
  • 문서 파싱과 변환
  • 수학적 계산과 모델링
  • 맞춤 형식의 리포트 생성
핵심은 Files API로 입출력을 통제하면서, 복잡한 연산 작업을 Claude에게 위임할 수 있다는 점입니다. Claude가 실제로 코드를 실행하고 반복 개선하는 코딩 어시스턴트가 됩니다.

MCP 소개

🎬 영상 + 요약

MCP(Model Context Protocol)는 지루한 통합 코드를 직접 작성하지 않고도 Claude에게 맥락과 도구를 제공하는 통신 계층입니다. 도구 정의와 실행의 부담을 여러분의 서버에서 전문화된 MCP 서버로 옮기는 방법이라고 생각하면 됩니다.

MCP를 처음 접하면 기본 아키텍처 도식을 보게 됩니다. MCP Client(여러분의 서버)가 도구·프롬프트·리소스를 담은 MCP Server에 연결되는 구조입니다. 각 MCP 서버는 외부 서비스로의 인터페이스 역할을 합니다.

실제 예제로 이해하는 MCP

사용자가 자신의 GitHub 데이터에 대해 Claude에게 물어보는 채팅 인터페이스를 만든다고 합시다. "내 모든 저장소에 열려 있는 PR이 뭐야?"라고 물으면, Claude는 GitHub API에 접근할 도구가 필요합니다.

MCP가 없다면 GitHub 통합 도구를 전부 직접 만들어야 합니다. 지원하려는 모든 GitHub 기능에 대해 스키마와 함수를 작성해야 한다는 뜻입니다.

도구 함수 문제

GitHub는 저장소, PR, 이슈, 프로젝트 등 방대한 기능을 가집니다. 완전한 GitHub 챗봇을 만들려면 엄청난 수의 도구를 작성해야 합니다.

각 도구는 스키마 정의와 함수 구현이 모두 필요합니다. 개발자가 작성·테스트·유지보수해야 하는 코드가 많다는 의미입니다.

MCP의 해결 방식

MCP는 도구 정의와 실행의 부담을 여러분의 서버에서 MCP 서버로 옮깁니다. GitHub 도구를 직접 작성하는 대신, 전용 MCP 서버 안에서 그것들이 작성·실행됩니다.

MCP 서버는 GitHub 기능을 감싸는 래퍼 역할을 하며, 직접 구현하지 않고도 쓸 수 있는 사전 제작된 도구를 제공합니다.

MCP 서버는 외부 서비스가 구현한 데이터나 기능에 대한 접근을 제공합니다. 복잡한 통합을 어떤 애플리케이션이든 연결할 수 있는 재사용 가능한 컴포넌트로 패키징합니다.

MCP에 대한 흔한 질문

  • 누가 MCP 서버를 만드나? 누구나 만들 수 있습니다. 종종 서비스 제공자가 직접 공식 구현을 내놓습니다. 예를 들어 AWS가 자사 서비스용 공식 MCP 서버를 배포할 수 있습니다.
  • 직접 API 호출과 무엇이 다른가? MCP 서버는 도구 스키마와 함수를 이미 정의해 제공합니다. API를 직접 호출하면 그 정의를 직접 작성해야 합니다. MCP는 그 구현 작업을 덜어줍니다.
  • MCP는 그냥 tool use 아닌가? 흔한 오해입니다. 둘은 상호 보완적이지만 다릅니다. MCP의 핵심은 도구를 만들고 유지하는 "작업의 주체"에 관한 것으로, 이미 누군가가 함수와 스키마를 작성해 MCP 서버 안에 패키징해 둔 것입니다.
핵심 통찰: MCP 서버는 이미 정의된 도구 스키마와 함수를 제공하여, 복잡한 통합을 직접 만들고 유지보수할 필요를 없애줍니다.

MCP 클라이언트

🎬 영상 + 요약

MCP 클라이언트는 여러분의 서버와 MCP 서버 사이의 통신 다리 역할을 합니다. MCP 서버가 제공하는 모든 도구에 접근하는 창구라고 보면 됩니다. 외부 도구나 서비스를 써야 할 때, 클라이언트가 메시지 전달과 프로토콜 세부사항을 대신 처리합니다.

전송 방식에 구애받지 않는 통신

MCP의 강점 중 하나는 전송 방식에 구애받지 않는(transport agnostic) 점입니다. 클라이언트와 서버가 서로 다른 통신 방법으로 대화할 수 있다는 뜻입니다. 가장 흔한 구성은 클라이언트와 서버를 같은 머신에서 실행하며 표준 입출력(standard input/output)으로 통신하는 것입니다.

이 방식에만 국한되지 않고, 다음으로도 연결할 수 있습니다.

  • HTTP
  • WebSockets
  • 기타 다양한 네트워크 프로토콜

메시지 타입

연결되면 클라이언트와 서버는 MCP 명세에 정의된 메시지 타입을 교환합니다. 주로 다루는 메시지 타입은 다음과 같습니다.

ListToolsRequest / ListToolsResult: 클라이언트가 서버에게 "어떤 도구를 제공하나?"라고 묻고 사용 가능한 도구 목록을 받습니다.

CallToolRequest / CallToolResult: 클라이언트가 특정 도구를 인자와 함께 실행하도록 요청하고 결과를 받습니다.

전체 흐름 예제

사용자가 "내 저장소가 뭐가 있어?"라고 물을 때의 전체 통신 흐름입니다.

사용자가 서버에 질의를 제출하면서 시작합니다. 서버는 요청 전에 Claude에게 사용 가능한 도구 목록을 제공해야 함을 인지합니다.

서버가 MCP 클라이언트에 도구를 요청하면, 클라이언트는 ListToolsRequest를 MCP 서버로 보내고 ListToolsResult를 받습니다.

이제 서버는 사용자 질문과 사용 가능한 도구를 모두 갖추어 Claude에 최초 요청을 보낼 수 있습니다.

Claude가 도구를 살펴보고 답변에 도구 호출이 필요하다고 판단해 tool use 요청으로 응답합니다.

서버가 MCP 클라이언트에 Claude가 요청한 도구 실행을 맡기면, 클라이언트는 CallToolRequest를 MCP 서버로 보내고, 서버는 실제로 GitHub에 요청합니다.

GitHub가 저장소 데이터를 반환하면 CallToolResult로 MCP 서버 → MCP 클라이언트 → 여러분의 서버로 흘러갑니다.

서버가 도구 결과를 후속 메시지로 Claude에 다시 보내면, Claude는 완전한 응답을 만들 정보를 모두 갖게 됩니다.

마지막으로 Claude가 정리된 답변으로 응답하고, 서버가 이를 사용자에게 전달합니다.

단계는 많지만 각 컴포넌트의 책임은 명확합니다. MCP 클라이언트는 서버 통신의 복잡성을 추상화하여, 여러분은 애플리케이션 로직에만 집중할 수 있습니다.

MCP로 도구 정의

🎬 영상 + 요약

공식 Python SDK를 쓰면 MCP 서버 구축이 훨씬 간단해집니다. 복잡한 도구용 JSON 스키마를 직접 작성하는 대신, SDK가 데코레이터와 타입 힌트로 그 복잡성을 처리해 줍니다.

이 예제에서는 메모리에 저장된 문서를 관리하는 MCP 서버를 만듭니다. 서버는 문서 내용을 읽는 도구와 find-and-replace로 갱신하는 도구, 두 가지를 제공합니다.

MCP 서버 설정

Python MCP SDK는 서버 생성을 매우 간단하게 만듭니다. 한 줄로 완전한 MCP 서버를 초기화할 수 있습니다.

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("DocumentMCP", log_level="ERROR")

이 구현에서는 문서를 단순한 Python 딕셔너리에 저장합니다. 키는 문서 ID, 값은 문서 내용입니다.

docs = {
"deposition.md": "This deposition covers the testimony of Angela Smith, P.E.",
"report.pdf": "The report details the state of a 20m condenser tower.",
"financials.docx": "These financials outline the project's budget and expenditure",
"outlook.pdf": "This document presents the projected future performance of the",
"plan.md": "The plan outlines the steps for the project's implementation.",
"spec.txt": "These specifications define the technical requirements for the equipment"
}

데코레이터로 도구 정의

SDK는 장황한 도구 생성 과정을 깔끔하고 읽기 쉬운 방식으로 바꿉니다. 긴 JSON 스키마 대신 Python 데코레이터와 타입 힌트를 씁니다.

문서 읽기 도구 만들기

첫 번째 도구는 Claude가 ID로 문서를 읽게 합니다.

@mcp.tool(
name="read_doc_contents",
description="Read the contents of a document and return it as a string."
)
def read_document(
doc_id: str = Field(description="Id of the document to read")
):
if doc_id not in docs:
raise ValueError(f"Doc with id {doc_id} not found")

return docs[doc_id]

@mcp.tool 데코레이터가 Claude에 필요한 JSON 스키마를 자동 생성합니다. Pydantic의 Field 클래스는 각 인자가 무엇을 기대하는지 Claude가 이해하도록 파라미터 설명을 제공합니다.

문서 편집 도구 만들기

두 번째 도구는 문서에 대해 단순 find-and-replace를 수행합니다.

@mcp.tool(
name="edit_document",
description="Edit a document by replacing a string in the documents content with a new string."
)
def edit_document(
doc_id: str = Field(description="Id of the document that will be edited"),
old_str: str = Field(description="The text to replace. Must match exactly, including whitespace."),
new_str: str = Field(description="The new text to insert in place of the old text.")
):
if doc_id not in docs:
raise ValueError(f"Doc with id {doc_id} not found")

docs[doc_id] = docs[doc_id].replace(old_str, new_str)

이 도구는 문서 ID, 찾을 텍스트, 대체 텍스트 세 파라미터를 받으며, 구현은 Python 내장 문자열 replace() 메서드를 씁니다.

에러 처리

두 도구 모두 Claude가 존재하지 않는 문서를 요청하는 경우를 대비한 기본 에러 처리를 포함합니다. 잘못된 문서 ID가 주어지면, Claude가 이해하고 대응할 수 있는 설명 메시지와 함께 ValueError를 발생시킵니다.

SDK 방식의 핵심 이점

  • Python 타입 힌트로부터 JSON 스키마 자동 생성
  • 유지보수하기 쉬운 깔끔하고 읽기 쉬운 코드
  • Pydantic을 통한 내장 파라미터 검증
  • 수동 스키마 작성 대비 줄어든 보일러플레이트
  • 개발 시 타입 안전성과 IDE 지원

MCP Python SDK는 복잡했던 도구 정의 과정을 Python 개발자에게 자연스러운 작업으로 바꿉니다. 여러분은 비즈니스 로직에 집중하고, SDK가 프로토콜 세부사항을 처리합니다.

서버 인스펙터

🎬 영상 + 요약

MCP 서버를 만들 때 전체 애플리케이션에 연결하지 않고도 기능을 테스트할 방법이 필요합니다. Python MCP SDK에는 브라우저 기반 인스펙터가 내장되어 있어, 서버를 실시간으로 디버깅하고 테스트할 수 있습니다.

인스펙터 시작하기

먼저 Python 환경이 활성화되어 있는지 확인하고(정확한 명령은 프로젝트 README 참고), 다음으로 인스펙터를 실행합니다.

mcp dev mcp_server.py

이 명령은 6277 포트에서 개발 서버를 시작하고 브라우저에서 열 로컬 URL을 제공합니다. 인스펙터 인터페이스가 로드되며 MCP Inspector 대시보드가 표시됩니다.

인터페이스에 대한 참고

MCP 인스펙터는 활발히 개발 중이라 화면이 스크린샷과 다를 수 있습니다. 다만 도구·리소스·프롬프트를 테스트하는 핵심 기능은 유사하게 유지됩니다.

연결과 도구 테스트

왼쪽의 "Connect" 버튼을 눌러 MCP 서버를 시작합니다. 연결되면 Resources, Prompts, Tools 등의 섹션이 있는 내비게이션 바가 보입니다.

도구를 테스트하려면:

  1. Tools 섹션으로 이동
  2. "List Tools"를 눌러 사용 가능한 모든 도구 확인
  3. 도구를 선택해 테스트 인터페이스 열기
  4. 필요한 파라미터 입력
  5. "Run Tool"을 눌러 실행하고 결과 확인

문서 작업 테스트

예를 들어 문서 읽기 도구를 테스트하려면 문서 ID(예: "deposition.md")를 입력하고 실행합니다. 인스펙터는 반환된 내용이나 성공 메시지를 포함한 결과를 보여줍니다.

작업을 연결해 기능을 검증할 수 있습니다. 예를 들어 텍스트를 대체해 문서를 편집한 뒤 곧바로 읽기 도구를 다시 실행해 변경이 제대로 적용됐는지 확인할 수 있습니다.

개발 워크플로우

  • MCP 서버 코드 변경
  • 인스펙터로 개별 도구 테스트
  • 전체 애플리케이션 설정 없이 결과 검증
  • 문제를 격리해 디버깅

복잡한 MCP 서버를 만들수록 이 도구는 필수가 됩니다. 기본 기능 테스트를 위해 서버를 Claude나 다른 앱에 연결할 필요를 없애, 개발을 훨씬 빠르고 집중적으로 만듭니다.

클라이언트 구현

🎬 영상 + 요약

MCP 서버가 동작하니 이제 클라이언트 측을 만들 차례입니다. 클라이언트는 애플리케이션이 MCP 서버와 통신하고 그 기능에 접근할 수 있게 해줍니다.

클라이언트 아키텍처 이해

대부분의 실제 프로젝트에서는 MCP 클라이언트 또는 서버 중 하나만 구현합니다. 이 프로젝트에서 둘 다 만드는 건 함께 작동하는 방식을 보기 위함입니다.

MCP 클라이언트는 두 주요 컴포넌트로 구성됩니다.

  • MCP Client - 세션 사용을 쉽게 만드는 커스텀 클래스
  • Client Session - 서버로의 실제 연결(MCP Python SDK의 일부)

클라이언트 세션은 사용을 마치면 적절한 리소스 정리가 필요합니다. 그래서 이를 커스텀 MCP Client 클래스로 감싸 정리를 자동으로 처리합니다.

클라이언트가 애플리케이션에 들어맞는 방식

애플리케이션 흐름을 떠올려 보면, CLI 코드는 MCP 서버로 두 가지를 해야 합니다.

  • Claude에 보낼 사용 가능한 도구 목록 가져오기
  • Claude가 요청할 때 도구 실행하기

MCP 클라이언트는 애플리케이션 코드가 쓸 수 있는 간단한 메서드 호출로 이 기능을 제공합니다.

핵심 메서드 구현

클라이언트에 list_tools()와 call_tool() 두 메서드를 구현합니다.

List Tools 메서드

서버에서 사용 가능한 모든 도구를 가져옵니다.

async def list_tools(self) -> list[types.Tool]:
result = await self.session().list_tools()
return result.tools

간단합니다. 세션(서버 연결)에 접근해 내장 list_tools()를 호출하고 결과의 도구를 반환합니다.

Call Tool 메서드

서버에서 특정 도구를 실행합니다.

async def call_tool(
self, tool_name: str, tool_input: dict
) -> types.CallToolResult | None:
return await self.session().call_tool(tool_name, tool_input)

Claude가 제공한 도구 이름과 입력 파라미터를 서버에 전달하고 결과를 반환합니다.

클라이언트 테스트

구현을 테스트하려면 클라이언트를 직접 실행합니다. 파일에는 MCP 서버에 연결해 메서드를 호출하는 테스트 하네스가 포함되어 있습니다.

async with MCPClient(
command="uv", args=["run", "mcp_server.py"]
) as client:
result = await client.list_tools()
print(result)

이 테스트를 실행하면 앞서 만든 read_doc_contents와 edit_document 도구를 포함한 도구 정의가 출력됩니다.

전체 조합

이제 클라이언트가 도구를 나열하고 호출할 수 있으니 전체 흐름을 테스트할 수 있습니다. 메인 앱을 실행하고 문서에 대해 Claude에게 물으면:

  1. 코드가 클라이언트로 사용 가능한 도구를 가져옴
  2. 도구와 사용자 질문을 함께 Claude에 전송
  3. Claude가 read_doc_contents 도구 사용을 결정
  4. 코드가 클라이언트로 해당 도구를 실행
  5. 결과를 Claude에 다시 보내면 Claude가 사용자에게 응답

예를 들어 "What is the contents of the report.pdf document?"라고 물으면 Claude가 문서 읽기 도구를 사용하고, 서버에 설정한 20m 응축탑 문서에 대한 정보를 받습니다.

클라이언트는 애플리케이션 로직과 MCP 서버 사이의 다리 역할을 하여, 하부 연결 세부사항을 신경 쓰지 않고도 서버 기능에 쉽게 접근하게 해줍니다.

리소스 정의

🎬 영상 + 요약

MCP 서버의 리소스(Resources)는 HTTP 서버의 GET 핸들러처럼 클라이언트에 데이터를 노출합니다. 동작을 수행하기보다 정보를 가져와야 하는 상황에 적합합니다.

예제로 이해하는 리소스

사용자가 @document_name을 입력해 파일을 참조하는 문서 멘션 기능을 만든다고 합시다. 두 작업이 필요합니다.

  • 사용 가능한 모든 문서 목록 가져오기(자동완성용)
  • 특정 문서의 내용 가져오기(멘션 시)

사용자가 @를 입력하면 사용 가능한 문서를 보여주고, 멘션이 담긴 메시지를 제출하면 해당 문서 내용을 Claude에 보낼 프롬프트에 자동으로 주입합니다.

리소스의 동작

리소스는 요청-응답 패턴을 따릅니다. 클라이언트가 URI와 함께 ReadResourceRequest를 보내면, MCP 서버가 데이터로 응답합니다. URI는 접근하려는 리소스의 주소 역할을 합니다.

리소스의 종류

  • Direct Resources: 변하지 않는 정적 URI(예: docs://documents)
  • Templated Resources: 파라미터가 있는 URI(예: docs://documents/{doc_id})

템플릿 리소스의 경우, Python SDK가 URI에서 파라미터를 자동 파싱해 함수에 키워드 인자로 전달합니다.

리소스 구현

리소스는 @mcp.resource() 데코레이터로 정의합니다. 두 종류를 만드는 방법입니다.

Direct Resource (문서 목록)

@mcp.resource(
"docs://documents",
mime_type="application/json"
)
def list_docs() -> list[str]:
return list(docs.keys())

Templated Resource (문서 가져오기)

@mcp.resource(
"docs://documents/{doc_id}",
mime_type="text/plain"
)
def fetch_doc(doc_id: str) -> str:
if doc_id not in docs:
raise ValueError(f"Doc with id {doc_id} not found")
return docs[doc_id]

MIME 타입

리소스는 문자열, JSON, 바이너리 등 어떤 데이터든 반환할 수 있습니다. mime_type 파라미터는 어떤 종류의 데이터인지 클라이언트에 힌트를 줍니다.

  • application/json - 구조화된 JSON 데이터
  • text/plain - 일반 텍스트 콘텐츠
  • 기타 다양한 데이터 형식을 위한 유효한 MIME 타입

MCP Python SDK가 반환값을 자동으로 직렬화하므로 JSON 문자열로 수동 변환할 필요가 없습니다.

리소스 테스트

MCP Inspector로 리소스를 테스트할 수 있습니다. 다음으로 서버를 실행합니다.

uv run mcp dev mcp_server.py

브라우저에서 인스펙터에 연결하면 다음이 보입니다.

  • Resources: 직접/정적 리소스 목록
  • Resource Templates: 파라미터를 받는 템플릿 리소스

리소스를 클릭해 테스트하면 클라이언트가 받게 될 정확한 응답 구조를 볼 수 있습니다.

핵심 정리

  • 리소스는 데이터를 노출하고, 도구는 동작을 수행
  • 정적 데이터엔 direct, 파라미터 쿼리엔 templated 리소스 사용
  • MIME 타입은 클라이언트가 응답 형식을 이해하도록 도움
  • SDK가 직렬화를 자동 처리
  • 템플릿 URI의 파라미터명이 함수 인자가 됨

리소스 접근

🎬 영상 + 요약

MCP의 리소스는 도구 호출 없이도 서버 데이터를 프롬프트에 직접 포함할 수 있게 해줍니다. Claude 같은 모델에 맥락을 제공하는 더 효율적인 방법입니다.

리소스 요청 이해하기

MCP 서버에 리소스를 정의했다면, 클라이언트는 이를 요청하고 사용할 방법이 필요합니다. 클라이언트는 애플리케이션과 MCP 서버 사이의 다리로서, 통신과 데이터 파싱을 자동으로 처리합니다.

흐름은 단순합니다. 사용자가 문서를 참조하려 하면(예: "@report.pdf" 입력), 애플리케이션이 MCP 클라이언트로 그 리소스를 서버에서 가져와 Claude에 보낼 프롬프트에 내용을 직접 포함합니다.

리소스 읽기 구현

핵심 기능은 MCP 클라이언트의 read_resource 함수입니다. 어떤 리소스를 가져올지 식별하는 URI 파라미터를 받습니다.

async def read_resource(self, uri: str) -> Any:
result = await self.session().read_resource(AnyUrl(uri))
resource = result.contents[0]

MCP 서버의 응답에는 contents 리스트가 담깁니다. 보통 첫 번째 요소만 필요하며, 여기에 실제 리소스 데이터와 MIME 타입 같은 메타데이터가 들어 있습니다.

다양한 콘텐츠 타입 처리

리소스는 서로 다른 타입의 콘텐츠를 반환할 수 있어 클라이언트가 적절히 파싱해야 합니다. MIME 타입이 처리 방법을 알려줍니다.

if isinstance(resource, types.TextResourceContents):
if resource.mimeType == "application/json":
return json.loads(resource.text)

return resource.text

이 방식은 JSON 리소스를 Python 객체로 올바르게 파싱하고, 일반 텍스트 리소스는 문자열로 반환합니다. MIME 타입이 올바른 파싱 전략을 결정하는 힌트 역할을 합니다.

필요한 임포트

이를 위해 MCP 클라이언트에 다음 임포트가 필요합니다.

import json
from pydantic import AnyUrl

json 모듈은 JSON 응답 파싱을, AnyUrl은 URI 파라미터의 올바른 타입 처리를 담당합니다.

리소스 접근 테스트

구현 후 CLI 앱으로 테스트할 수 있습니다. "What's in the @report.pdf document?"처럼 입력하면 시스템은 다음을 해야 합니다.

  • 자동완성 목록에 사용 가능한 리소스 표시
  • 리소스 선택 허용
  • 리소스 내용을 자동으로 가져오기
  • 그 내용을 Claude 프롬프트에 포함
핵심 이점은 Claude가 문서 내용을 프롬프트에서 바로 받아, 정보 접근을 위한 도구 호출이 필요 없다는 점입니다. 상호작용이 더 빠르고 효율적이 됩니다.

애플리케이션 통합

여러분이 작성한 MCP 클라이언트 코드는 앱의 다른 부분에서 사용됩니다. read_resource 함수는 다른 컴포넌트가 문서 내용을 가져오거나, 리소스를 나열하거나, 리소스 데이터를 프롬프트에 통합하는 데 쓰는 기본 요소가 됩니다. 이런 관심사 분리로 코드가 깔끔하게 유지됩니다.

프롬프트 정의

🎬 영상 + 요약

MCP 서버의 프롬프트(Prompts)는 클라이언트가 직접 프롬프트를 짜는 대신 사용할 수 있는, 사전 제작된 고품질 지시문을 정의하게 해줍니다. 사용자가 직접 만드는 것보다 더 좋은 결과를 내는, 신중히 다듬어진 템플릿이라고 보면 됩니다.

왜 프롬프트를 쓰나

Claude에게 문서를 markdown으로 재구성하게 한다고 합시다. 사용자가 "convert report.pdf to markdown"이라고만 입력해도 동작하지만, 형식·구조·출력 요구사항에 대한 구체적 지시를 담은 철저히 테스트된 프롬프트를 쓰면 훨씬 나은 결과를 얻습니다.

핵심은, 사용자가 스스로 해낼 수는 있어도 MCP 서버 작성자가 신중히 개발·테스트한 프롬프트를 쓰면 더 일관되고 높은 품질의 결과를 얻는다는 점입니다.

프롬프트의 동작

프롬프트는 클라이언트가 바로 쓸 수 있는 user·assistant 메시지 집합을 정의합니다. 클라이언트가 프롬프트를 요청하면, 서버는 Claude에 바로 보낼 수 있는 메시지 목록을 반환합니다.

기본 구조는 다음과 같습니다.

  • @mcp.prompt() 데코레이터로 프롬프트 정의
  • 각 프롬프트에 이름과 설명 추가
  • 완전한 프롬프트를 이루는 메시지 목록 반환
  • 고품질이고 잘 테스트되었으며 서버 목적에 부합해야 함

Format 커맨드 만들기

문서 포매팅 프롬프트를 구현하는 방법입니다. 먼저 base 메시지 타입을 임포트합니다.

from mcp.server.fastmcp import base

그런 다음 프롬프트 함수를 정의합니다.

@mcp.prompt(
name="format",
description="Rewrites the contents of the document in Markdown format."
)
def format_document(
doc_id: str = Field(description="Id of the document to format")
) -> list[base.Message]:
prompt = f"""
Your goal is to reformat a document to be written with markdown syntax.

The id of the document you need to reformat is:

{doc_id}

Add in headers, bullet points, tables, etc as necessary. Feel free to add in extra formatting.
Use the 'edit_document' tool to edit the document. After the document has been reformatted...
"""

return [
base.UserMessage(prompt)
]

프롬프트 테스트

MCP Inspector로 프롬프트를 테스트할 수 있습니다. Prompts 섹션으로 이동해 프롬프트를 선택하고 필요한 파라미터를 제공하면, 인스펙터가 Claude에 보낼 생성된 메시지를 보여줍니다.

실제 앱에서 쓰기 전에 프롬프트가 변수를 올바르게 보간하고 기대한 메시지 구조를 만드는지 검증할 수 있습니다.

모범 사례

  • 서버 목적에 핵심적인 작업에 집중
  • 모호한 요청보다 상세하고 구체적인 지시 작성
  • 다양한 입력으로 철저히 테스트
  • 각 프롬프트가 무엇을 하는지 명확한 설명 포함
  • 서버의 도구·리소스와 어떻게 작동할지 고려

클라이언트의 프롬프트

🎬 영상 + 요약

MCP의 프롬프트는 클라이언트가 사용할 수 있는 user·assistant 메시지 집합을 정의합니다. 이 프롬프트는 고품질이고 잘 테스트되었으며 MCP 서버의 전체 목적에 부합해야 합니다.

List Prompts 구현

첫 단계는 MCP 클라이언트에 list_prompts 메서드를 구현하는 것입니다. 서버에서 사용 가능한 모든 프롬프트를 가져옵니다.

async def list_prompts(self) -> list[types.Prompt]:
result = await self.session().list_prompts()
return result.prompts

세션의 list_prompts 메서드를 호출하고 결과의 프롬프트 배열을 반환하는 단순한 구현입니다.

개별 프롬프트 가져오기

get_prompt 메서드는 인자가 보간된 특정 프롬프트를 가져옵니다. 프롬프트를 요청할 때 제공하는 인자는 프롬프트 함수에 키워드 인자로 전달됩니다.

async def get_prompt(self, prompt_name, args: dict[str, str]):
result = await self.session().get_prompt(prompt_name, args)
return result.messages

이 메서드는 결과의 메시지를 반환하며, 이는 Claude에 바로 넣을 수 있는 대화를 이룹니다.

프롬프트 인자의 동작

서버 측에서 프롬프트 함수를 정의할 때 파라미터를 받을 수 있습니다. 예를 들어 문서 포매팅 프롬프트는 doc_id 파라미터를 기대할 수 있습니다.

def format_document(doc_id: str):
# The doc_id gets interpolated into the prompt

클라이언트가 get_prompt를 호출할 때 인자 딕셔너리에 기대되는 키가 담겨야 합니다. MCP 서버는 이를 프롬프트 함수에 키워드 인자로 전달해, 프롬프트 템플릿에 동적 내용을 삽입할 수 있게 합니다.

CLI에서 프롬프트 테스트

구현 후 CLI로 프롬프트를 테스트할 수 있습니다. 슬래시(/)를 입력하면 사용 가능한 프롬프트가 커맨드로 나타납니다. 프롬프트를 선택하면 옵션(예: 문서 ID)을 고르게 하고, 완성된 프롬프트가 Claude에 전송됩니다.

워크플로우는 다음과 같습니다.

  1. 사용자가 프롬프트 선택(예: "format")
  2. 시스템이 필요한 인자를 물음(예: 포매팅할 문서)
  3. 보간된 값과 함께 프롬프트가 Claude에 전송
  4. Claude가 도구로 추가 데이터를 가져와 작업 완료

프롬프트 모범 사례

  • 서버 목적에 부합하게 만들기
  • 배포 전 철저히 테스트
  • 명확하고 구체적인 지시 사용
  • 사용 가능한 도구와 잘 작동하도록 설계
  • 사용자가 제공할 인자를 고려

프롬프트는 사전 정의된 기능과 동적인 사용자 요구 사이의 간극을 메워, 파라미터화를 통한 유연성을 유지하면서 복잡한 작업의 구조화된 출발점을 Claude에 제공합니다.

Claude Code 설정

🎬 영상 + 요약

Claude Code는 명령줄에서 바로 실행되는 터미널 기반 코딩 어시스턴트입니다. 작업 중인 어떤 코딩 태스크든 도와줄 Claude를 터미널에 두는 셈입니다.

Claude Code가 할 수 있는 일

Claude Code는 개발 워크플로우를 돕는 포괄적인 도구 세트를 갖추고 있습니다.

  • 파일 조작 - 프로젝트 내 파일 검색·읽기·편집
  • 터미널 접근 - 대화 중에 바로 명령 실행
  • 웹 접근 - 문서 검색, 코드 예제 가져오기 등
  • MCP 서버 지원 - MCP 서버를 연결해 도구 추가

MCP 통합은 특히 강력합니다. 데이터베이스, API 등 자신이 다루는 서비스에 맞는 전용 도구를 추가해 Claude Code의 능력을 확장할 수 있기 때문입니다. Claude Code는 macOS, Windows WSL, Linux에서 모두 동작하므로 개발 환경에 상관없이 사용할 수 있습니다.

설치

설치는 단 세 단계입니다.

  1. nodejs.org/en/download 에서 Node.js 설치 (터미널에서 npm help 를 실행해 이미 설치돼 있는지 확인)
  2. npm install -g @anthropic-ai/claude-code 명령으로 Claude Code 설치
  3. 터미널에서 claude 를 실행해 시작 및 로그인

claude 명령을 처음 실행하면 Anthropic 계정 로그인을 요청합니다. 더 자세한 안내가 필요하면 docs.anthropic.com 의 전체 설치 가이드를 참고하세요.

설치가 끝나면 터미널에 바로 Claude가 상주하며 어떤 코딩 프로젝트든 도와줄 준비가 됩니다.

Claude Code 실전

🎬 영상 + 요약

Claude Code는 단순히 코드를 짜 주는 도구가 아니라, 소프트웨어 프로젝트의 모든 단계에서 함께 일하도록 설계됐습니다. 초기 설정부터 배포·유지보수까지 처리할 수 있는 또 한 명의 팀 엔지니어라고 생각하면 됩니다.

/init 명령

프로젝트에서 Claude Code로 작업을 시작할 때 가장 먼저 할 일은 /init 명령 실행입니다. 이 명령은 Claude에게 전체 코드베이스를 스캔해 프로젝트 구조, 의존성, 코딩 스타일, 아키텍처를 파악하게 합니다.

Claude는 파악한 내용을 CLAUDE.md 라는 특별한 파일로 정리합니다. 이 파일은 이후 모든 대화에 자동으로 컨텍스트로 포함되어, Claude가 프로젝트의 중요한 세부 사항을 기억합니다.

범위별로 여러 개의 CLAUDE.md 파일을 둘 수 있습니다.

  • Project - 프로젝트에 참여하는 모든 엔지니어가 공유
  • Local - git에 커밋되지 않는 개인 메모
  • User - 내 모든 프로젝트에 걸쳐 사용

/init 실행 시 Claude가 집중했으면 하는 영역에 대한 지시를 추가할 수 있습니다. 생성된 파일에는 빌드 명령, 코딩 가이드라인, 프로젝트별 패턴이 담깁니다.

# 명령으로 CLAUDE.md에 빠르게 메모를 추가할 수도 있습니다. 예를 들어 # Always use descriptive variable names 라고 입력하면 이 가이드라인을 project·local·user 메모리 중 어디에 추가할지 물어봅니다.

주요 워크플로우

Claude는 노력을 배가시키는 도구로 접근할 때 가장 잘 작동합니다. 더 많은 컨텍스트와 구조를 제공할수록 결과가 좋아집니다. 가장 효과적인 워크플로우는 다음과 같습니다.

1단계: Claude에 컨텍스트 제공

무언가를 만들라고 요청하기 전에, 만들려는 기능과 관련된 파일을 코드베이스에서 찾아 Claude에게 먼저 읽고 분석하게 하세요. 이렇게 하면 Claude가 여러분의 코딩 패턴과 기존 기능을 참고해 그 위에 작업할 수 있습니다.

2단계: 해결책을 계획하게 하기

곧바로 구현으로 넘어가지 말고, 문제를 깊이 생각해 계획을 세우게 하세요. 아직 코드는 작성하지 말고 접근 방식과 필요한 단계에만 집중하라고 명확히 지시합니다.

3단계: 구현 요청

탄탄한 계획이 마련되면 구현을 요청합니다. Claude는 함께 쌓아 온 컨텍스트와 계획을 바탕으로 코드를 작성합니다.

테스트 주도 개발(TDD) 워크플로우

더 나은 결과를 위해 테스트 주도 방식을 쓸 수 있습니다.

  • 컨텍스트 제공 - 앞서와 마찬가지로 관련 파일을 보여 줌
  • 테스트 케이스 구상 요청 - 새 기능을 검증할 테스트를 브레인스토밍
  • 테스트 구현 요청 - 가장 관련성 높은 테스트를 선택해 작성
  • 테스트를 통과하는 코드 작성 요청 - 모든 테스트가 통과할 때까지 구현을 반복

Claude가 명확한 성공 기준을 향해 작업하므로 더 견고한 코드가 나오는 경우가 많습니다.

실제 예시

이 워크플로우가 실제로 어떻게 보이는지 예를 들어 봅니다. 기존 프로젝트에 문서 변환 도구를 추가한다고 가정합니다.

// First, ask Claude to read relevant files
> Read the math.py and document.py files

// Then ask for planning (not implementation)
> Plan to implement document_path_to_markdown tool:
1. Create a function that:
- Takes a file path parameter
- Validates the file exists
- Determines file type from extension
- Reads binary data from file
- Leverages existing binary_document_to_markdown function
- Returns markdown string
2. Add appropriate documentation
3. Register the tool with MCP server
4. Add tests

// Finally, ask for implementation
> Implement the plan

그러면 Claude는 함수를 만들고, 필요한 파일을 수정하고, 테스트를 작성한 뒤 테스트 스위트까지 실행해 정상 동작을 검증합니다.

추가 명령

  • /clear - 대화 기록을 지우고 컨텍스트 초기화
  • /init - 코드베이스를 스캔해 CLAUDE.md 문서 생성
  • # - CLAUDE.md에 메모 추가

Claude는 git 스테이징·커밋, 테스트 실행, 의존성 관리 같은 일상적인 개발 작업도 처리할 수 있습니다. 에디터와 터미널을 오가는 대신 이런 작업을 Claude에게 맡기고 큰 그림에 집중하면 됩니다.

핵심은 Claude Code가 단순한 코드 생성기가 아니라 협업 파트너로 설계됐다는 점입니다. 컨텍스트와 구조를 많이 줄수록 더 효과적으로 도와줍니다.

MCP 서버로 확장

🎬 영상 + 요약

Claude Code에는 MCP 클라이언트가 내장돼 있어 MCP 서버를 연결하면 Claude가 할 수 있는 일을 크게 확장할 수 있습니다. 개발 워크플로우를 맞춤화할 강력한 가능성이 열립니다.

MCP가 Claude를 확장하는 방식

MCP(Model Context Protocol)는 Claude Code가 MCP 서버를 통해 외부 서비스·도구에 연결하게 해 줍니다. Claude 내장 기능에만 의존하는 대신, 특정 도구·리소스·통합을 제공하는 서버를 연결해 맞춤 기능을 추가할 수 있습니다.

각 MCP 서버는 세 가지 주요 구성 요소를 통해 서로 다른 기능을 Claude에 노출합니다. Tools(행동 수행), Prompts(템플릿), Resources(데이터 접근)입니다.

MCP 서버 설정하기

Claude Code에 MCP 서버를 추가하는 일은 간단합니다. 명령줄로 서버를 등록합니다.

claude mcp add [server-name] [command-to-start-server]

예를 들어 uv run main.py 로 시작하는 문서 처리 서버가 있다면 다음과 같이 실행합니다.

claude mcp add documents uv run main.py

한 번 등록하면 Claude Code가 시작할 때 자동으로 해당 서버에 연결합니다.

예시: 문서 처리

실용적인 예로, Claude가 PDF와 Word 문서를 읽게 하는 도구를 만드는 것을 들 수 있습니다. "document_path_to_markdown" 도구를 갖춘 MCP 서버를 만들면 문서 내용을 마크다운으로 변환하도록 요청할 수 있습니다.

"tests/fixtures/mcp_docs.docx 파일을 마크다운으로 변환해 줘"라고 요청하면 Claude가 자동으로 사용자 정의 도구를 사용해 문서를 읽고 변환된 내용을 반환합니다.

인기 있는 MCP 통합

MCP 생태계에는 여러 개발 도구·서비스를 위한 서버가 있습니다.

  • sentry-mcp - Sentry에 기록된 버그를 자동으로 발견·수정
  • playwright-mcp - 테스트·문제 해결용 브라우저 자동화 기능 제공
  • figma-context-mcp - Figma 디자인을 Claude에 노출
  • mcp-atlassian - Confluence와 Jira 접근 허용
  • firecrawl-mcp-server - 웹 스크래핑 기능 추가
  • slack-mcp - 메시지 게시나 특정 스레드 답장 허용

나만의 개발 워크플로우 구축

진짜 강력함은 자신의 개발 프로세스에 맞는 여러 MCP 서버를 조합할 때 나옵니다. 예를 들어 다음과 같이 구성할 수 있습니다.

  • 운영 환경 오류 상세를 가져오는 Sentry 서버
  • 티켓 요구사항을 읽는 Jira 서버

  • 내부 도구·API를 위한 커스텀 서버
여러 MCP 서버를 조합하면 Claude가 이미 사용 중인 모든 도구·서비스와 매끄럽게 연동되어, 워크플로우에 딱 맞는 훨씬 강력한 코딩 어시스턴트가 됩니다.

에이전트와 워크플로우

🎬 영상 + 요약

워크플로우와 에이전트는 Claude가 단일 요청으로 완료할 수 없는 사용자 작업을 처리하기 위한 전략입니다. 사실 이 강의 내내 둘 다 만들어 왔습니다. 도구를 사용하고 Claude가 작업 완료 방법을 스스로 알아내게 했다면 그것이 바로 에이전트입니다.

워크플로우 vs 에이전트, 언제 쓸까

선택은 작업을 얼마나 잘 이해하고 있느냐에 달려 있습니다.

워크플로우에이전트
Claude가 거쳐야 할 정확한 흐름·단계를 그릴 수 있거나, 앱 UX가 사용자를 정해진 작업으로 제한할 때Claude에게 어떤 작업·파라미터를 줄지 정확히 알 수 없을 때
특정 문제를 미리 정해진 단계로 푸는 일련의 Claude 호출목표와 도구를 주고, Claude가 그 도구로 목표 달성 방법을 스스로 찾게 함

예시: 이미지 → CAD 워크플로우

사용자가 금속 부품 이미지를 드래그 앤 드롭하면 그로부터 STEP 파일(3D 모델 산업 표준)을 만드는 웹 앱을 상상해 봅니다. 이미지가 주어졌을 때 무엇을 해야 할지 명확히 알고 있고 미리 정해진 단계로 코드화할 수 있으므로, 워크플로우에 딱 맞는 후보입니다.

워크플로우는 다음처럼 나뉩니다.

  • 이미지를 Claude에 넣어 객체를 설명하게 함
  • 그 설명을 바탕으로 CadQuery 라이브러리로 객체를 모델링하게 함
  • 렌더링 생성
  • 렌더링을 원본 이미지와 비교·채점하고, 문제가 있으면 수정

Evaluator-Optimizer 패턴

이 모델링 워크플로우는 evaluator-optimizer 패턴의 예입니다.

  • Producer: 입력을 받아 출력을 생성 (CadQuery로 부품을 모델링하고 렌더링 생성)
  • Grader: 출력을 특정 기준에 따라 평가
  • Feedback loop: Grader가 출력을 받아들이지 않으면 피드백을 Producer로 되돌려 개선
  • Iteration: Grader가 출력을 수락할 때까지 반복

워크플로우 패턴을 배우는 이유

여러 워크플로우를 파악하는 목적은 여러분의 기능을 구현할 때 재사용 가능한 레시피 모음을 갖추기 위해서입니다. Evaluator-Optimizer는 많은 엔지니어에게 효과가 입증된 패턴 중 하나이니 여러분의 앱에도 활용해 보세요. 다만 패턴을 파악하는 것만으로 저절로 되는 것은 없고, 실제 구현 코드는 직접 작성해야 합니다.

병렬화 워크플로우

🎬 영상 + 요약

AI 애플리케이션을 만들다 보면 겉보기엔 단순하지만 효과적으로 구현하려면 복잡해지는 작업을 자주 만납니다. 복잡한 작업을 다루기 쉬운 초점화된 조각으로 나누는 강력한 패턴, 병렬화 워크플로우를 살펴봅니다.

복잡한 단일 프롬프트의 문제

사용자가 부품 이미지를 올리면 최적 소재를 추천하는 소재 설계 앱을 만든다고 해 봅니다. 처음엔 이미지를 Claude에 보내 금속·폴리머·세라믹·복합재·엘라스토머·목재 중 하나를 고르라고 단순히 요청하고 싶을 것입니다.

이 방식도 동작은 하지만, 단일 요청에서 Claude에게 너무 많은 부담을 지웁니다. 소재별 구체적 기준이 없으면 결과의 신뢰도가 떨어집니다. 그렇다고 각 소재의 상세 기준을 하나의 거대한 프롬프트에 몰아넣으면, Claude가 모든 고려사항을 동시에 저글링해야 해서 혼란과 부실한 결과로 이어집니다.

더 나은 접근: 병렬화

모든 것을 한 요청에 몰아넣는 대신, 작업을 여러 병렬 요청으로 분할합니다. 각 요청은 특화된 기준으로 하나의 소재만 평가하는 데 집중합니다.

작동 방식은 다음과 같습니다.

  • 같은 이미지를 Claude에 동시에 여러 번 전송
  • 각 요청에 소재 하나의 특화 기준 포함 (금속 기준, 폴리머 기준, 세라믹 기준 등)
  • Claude가 각 소재 적합성을 독립적으로 평가
  • 모든 분석 결과를 모아 최종 집계 단계에 투입

마지막 단계에서는 개별 분석 결과를 모두 Claude에 다시 보내 비교하고 최종 소재를 추천하게 합니다.

병렬화 워크플로우의 구조

  • 단일 작업을 여러 하위 작업으로 분할 - 복잡한 결정을 초점화된 특화 평가로 쪼갬
  • 하위 작업을 병렬 실행 - 모든 평가를 동시에 수행해 처리 속도 향상
  • 결과를 집계 - 특화 분석들을 종합해 최종 결정
  • 병렬 하위 작업은 동일할 필요 없음 - 각기 다른 프롬프트·도구·평가 기준 가능

이 방식의 장점

  • 초점 집중: 한 번에 한 측면에 집중해 각 소재를 더 철저하고 정확하게 분석
  • 쉬운 최적화: 각 소재 평가 프롬프트를 독립적으로 개선·테스트 (금속 분석만 다듬어도 다른 것에 영향 없음)
  • 확장성: 새 소재 추가는 병렬 요청 하나를 더하는 것으로 간단
  • 신뢰성 향상: 복잡한 작업을 쪼개 모델의 인지 부하를 줄이고 일관된 결과 확보

언제 병렬화를 쓸까

복잡한 결정을 독립적인 평가들로 나눌 수 있을 때 잘 맞습니다. 여러 기준을 고려하거나, 여러 선택지를 비교하거나, 서로 다른 전문 영역이 얽힌 결정을 내려야 하는 상황을 찾아보세요. 핵심은 의미 있게 분리 가능한 작업을 식별하는 것으로, 각 병렬 하위 작업이 독립적으로 동작하며 최종 결정에 별개의 분석을 기여해야 합니다.

체이닝 워크플로우

🎬 영상 + 요약

체이닝 워크플로우는 처음엔 당연해 보이지만, Claude를 다룰 때 만나는 가장 유용한 패턴 중 하나입니다. 복잡한 작업이나, Claude가 일관되게 처리하기 어려워하는 긴 프롬프트를 다룰 때 특히 가치가 큽니다.

워크플로우 체이닝이란

체이닝 워크플로우는 크고 복잡한 작업을 더 작은 순차적 하위 작업으로 나눕니다. Claude에게 모든 것을 한 번에 시키는 대신, 서로 이어지는 초점화된 단계로 분할합니다.

실용적 예로, 동영상을 자동으로 만들고 게시하는 소셜 미디어 마케팅 도구를 상상해 봅니다. 하나의 거대한 프롬프트로 전부 처리하는 대신 다음처럼 나눌 수 있습니다.

  • Twitter에서 관련 트렌드 주제 찾기
  • 가장 흥미로운 주제 선택 (Claude 사용)
  • 주제 조사 (Claude 사용)
  • 숏폼 동영상 대본 작성 (Claude 사용)
  • AI 아바타와 TTS로 동영상 생성
  • 소셜 미디어에 동영상 게시

왜 하나의 큰 프롬프트 대신 체이닝인가

모든 Claude 작업을 단일 프롬프트로 합치지 않는 이유는 초점 때문입니다. 한 번에 하나의 구체적 작업을 주면 여러 요구사항을 저글링하지 않고 그 작업을 잘 해내는 데 집중할 수 있습니다.

  • 큰 작업을 병렬화 불가능한 작은 하위 작업으로 분할
  • 각 작업 사이에 선택적으로 LLM 외 처리 수행
  • Claude가 전체 작업의 한 측면에 집중하도록 유지

긴 프롬프트 문제

체이닝이 진가를 발휘하는 지점입니다. 많은 구체적 제약과 함께 콘텐츠를 작성하게 해야 하는 상황이 자주 생깁니다. 예를 들어 기술 기사를 쓰되 다음을 지키라고 지정했다고 합시다.

  • AI가 작성했다고 언급하지 않기
  • 이모지 사용 금지
  • 진부하거나 지나치게 캐주얼한 표현 배제
  • 전문적·기술적 어조로 작성

이 제약을 모두 명확히 밝혀도 Claude가 일부 규칙을 어기는 결과를 낼 수 있습니다. 여전히 이모지를 쓰거나, AI 저작을 언급하거나, 비전문적으로 들리는 기사를 돌려줄 수 있습니다.

체이닝 해법

하나의 거대한 프롬프트와 씨름하는 대신 2단계 체이닝을 씁니다.

1단계: 초기 프롬프트를 보내고 첫 결과가 완벽하지 않을 수 있음을 받아들입니다. Claude가 기사를 생성하지만 일부 제약을 어길 수 있습니다.

2단계: 문제 수정에 특화된 후속 요청을 보냅니다. 방금 작성한 기사를 제공하고 타깃 수정 지시를 줍니다.

Revise the article provided below. Follow these steps to rewrite the article: 1. Identify any location where the text identifies the author as an AI and remove them 2. Find and remove all emojis 3. Locate any cringey writing and replace it with text that would be written by a technical writer

이 방식이 통하는 이유는 Claude가 콘텐츠 생성과 제약 준수를 동시에 저울질하지 않고 수정 작업에만 온전히 집중할 수 있기 때문입니다.

언제 체이닝을 쓸까

  • 여러 요구사항이 있는 복잡한 작업
  • Claude가 긴 프롬프트에서 일부 제약을 계속 무시할 때
  • 단계 사이에서 출력을 처리·검증해야 할 때
  • 각 상호작용을 초점화하고 관리 가능하게 유지하고 싶을 때
체이닝은 추가 작업처럼 보여도, 모든 것을 한 프롬프트에 욱여넣는 것보다 더 나은 결과를 내는 경우가 많습니다. 핵심은 작업이 언제 충분히 복잡해서 초점화된 순차 단계로 나눌 만한지 인식하는 것입니다.

라우팅 워크플로우

🎬 영상 + 요약

라우팅 워크플로우는 AI 애플리케이션의 흔한 문제를 해결합니다. 서로 다른 유형의 요청은 서로 다른 처리 방식이 필요하다는 점입니다. 만능 프롬프트를 쓰는 대신, 들어오는 요청을 분류해 특화된 처리 파이프라인으로 라우팅합니다.

일반 프롬프트의 문제

사용자 주제로 동영상 대본을 생성하는 소셜 미디어 마케팅 도구를 생각해 봅니다. 사용자가 "programming"이나 "surfing"을 주제로 입력할 수 있는데, 이 둘은 매우 다른 유형의 콘텐츠를 만들어야 합니다.

프로그래밍 주제는 명확한 설명과 정의가 있는 교육 콘텐츠가 필요하고, 서핑 주제는 흥분과 시각적 매력을 강조한 엔터테인먼트 대본이 더 잘 맞습니다. 단일 일반 프롬프트로는 둘 다 효과적으로 다룰 수 없습니다.

콘텐츠 카테고리 설정

첫 단계는 앱이 생성할 콘텐츠 유형을 정의하는 것입니다. 요청을 다음과 같은 장르로 분류할 수 있습니다.

  • Entertainment - 고에너지, 문화적으로 시의적절하고 트렌디한 언어의 콘텐츠
  • Educational - 명확하고 흥미로운 설명, 공감 가는 예시
  • Comedy - 날카롭고 예상 밖의 콘텐츠, 재치 있는 관찰과 타이밍
  • Personal vlog - 진솔하고 친밀한, 대화체 스토리텔링
  • Reviews - 결단력 있고 경험 기반의, 장단점 부각 콘텐츠
  • Storytelling - 생생한 디테일과 감정적 연결을 쓰는 몰입형 콘텐츠

각 카테고리는 자기만의 특화 프롬프트 템플릿을 갖습니다. 예를 들어 교육용 프롬프트는 "복잡한 정보를 공감 가는 예시와 생각을 자극하는 질문으로 소화 가능한 통찰로 바꾸는 명확하고 흥미로운 대본을 만들라"고 요청할 수 있습니다.

라우팅의 실제 동작

라우팅은 두 단계로 이뤄집니다.

  • 분류(Categorization) - 사용자 주제를 Claude에 보내 미리 정의한 장르 중 하나로 분류 요청
  • 특화 처리(Specialized Processing) - 분류 결과로 적절한 프롬프트 템플릿을 선택해 콘텐츠 생성

예를 들어 사용자가 "Python functions"를 주제로 입력하면 먼저 Claude에 분류를 요청합니다.

  • 사용자 입력이 먼저 라우터 컴포넌트로 감
  • 라우터가 초기 Claude 호출로 요청을 분류

핵심은 사용자 입력이 모든 파이프라인이 아니라 하나의 특화 파이프라인으로만 간다는 점입니다. 덕분에 각 파이프라인을 특정 용도에 고도로 최적화할 수 있습니다.

언제 라우팅을 쓸까

  • 용도를 아우르는 카테고리를 명확히 정의할 수 있을 때
  • 분류 단계를 Claude가 안정적으로 처리할 수 있을 때

에이전트와 도구

🎬 영상 + 요약

에이전트는 지금까지 다룬 구조화된 워크플로우에서의 전환을 의미합니다. 워크플로우가 필요한 단계를 정확히 알 때 완벽하다면, 에이전트는 그 단계가 무엇이어야 할지 확신할 수 없을 때 빛납니다. 경직된 순서를 정의하는 대신, Claude에게 목표와 도구 세트를 주고 그 도구들을 조합해 목적을 달성할 방법을 스스로 찾게 합니다.

이 유연성 덕분에 에이전트는 다양하고 예측 불가한 작업을 다루는 앱에 매력적입니다. 에이전트를 한 번 만들어 어느 정도 잘 동작하게 하면 폭넓은 문제를 풀도록 배포할 수 있습니다. 다만 이 유연성에는 신뢰성·비용 측면의 트레이드오프가 따르며, 이는 뒤에서 다룹니다.

도구가 에이전트를 만든다

에이전트의 진짜 힘은 단순한 도구들을 예상 밖의 방식으로 조합하는 능력에 있습니다. 기본적인 datetime 도구 세트를 생각해 봅니다.

  • get_current_datetime - 현재 날짜·시간 가져오기
  • add_duration_to_datetime - 주어진 날짜에 시간 더하기
  • set_reminder - 특정 시간에 알림 생성

개별로는 단순해 보이지만, Claude는 이들을 엮어 놀랍도록 복잡한 요청을 처리합니다.

"지금 몇 시야?"에는 get_current_datetime 만 호출합니다. 하지만 "11일 뒤는 무슨 요일이야?"에는 get_current_datetime 뒤에 add_duration_to_datetime 을 연쇄합니다. 다음 주 수요일 헬스장 알림 설정에는 세 도구를 순서대로 쓸 수도 있습니다. Claude는 정보가 더 필요한 순간도 인식합니다. "내 90일 보증은 언제 만료돼?"라고 물으면 만료일 계산 전에 구매 시점을 먼저 물어봐야 함을 압니다.

도구는 추상적이어야 한다

효과적인 에이전트를 만드는 핵심 통찰은 초특화된 도구가 아니라 적당히 추상적인 도구를 제공하는 것입니다. Claude Code가 이 원칙을 완벽하게 보여 줍니다.

Claude Code는 다음처럼 범용적이고 유연한 도구에 접근합니다.

  • bash - 임의의 명령 실행
  • read - 임의의 파일 읽기
  • write - 임의의 파일 생성
  • edit - 파일 수정
  • glob - 파일 찾기
  • grep - 파일 내용 검색

"코드 리팩터링"이나 "의존성 설치" 같은 특화 도구는 없다는 점이 특징입니다. 대신 Claude가 기본 도구로 이런 복잡한 작업을 해내는 방법을 스스로 찾습니다. 이 추상화 덕분에 개발자가 명시적으로 계획하지 않은 수많은 프로그래밍 시나리오를 다룰 수 있습니다.

모범 사례: 조합 가능한 도구

에이전트를 설계할 때는 Claude가 창의적으로 조합할 수 있는 도구를 제공하세요. 예를 들어 소셜 미디어 동영상 에이전트는 다음을 포함할 수 있습니다.

  • bash - 동영상 처리를 위한 FFMPEG 접근
  • generate_image - 프롬프트로 이미지 생성
  • text_to_speech - 텍스트를 오디오로 변환
  • post_media - 소셜 플랫폼에 콘텐츠 업로드

이 도구 세트는 단순 워크플로우(동영상 생성·게시)뿐 아니라, 에이전트가 먼저 샘플 이미지를 만들어 사용자 승인을 받은 뒤 동영상 제작으로 넘어가는 더 상호작용적인 경험도 가능하게 합니다.

에이전트는 사용자 피드백과 선호에 따라 접근을 조정할 수 있는데, 이는 경직된 워크플로우로는 달성하기 어렵습니다. 이 유연성이 동적이고 사용자 반응형 앱을 만드는 데 에이전트를 강력하게 만듭니다.

환경 점검

🎬 영상 + 요약

AI 에이전트를 만들 때 자주 간과되는 중요한 개념이 하나 있습니다. 바로 환경 점검(environment inspection)입니다. Claude는 눈이 가려진 채 동작하므로, 효과적으로 일하려면 자기 행동의 결과를 관찰하고 이해할 수 있어야 합니다.

환경 점검이 중요한 이유

Claude가 컴퓨터를 사용하는 방식을 생각해 봅니다. 텍스트 입력이나 버튼 클릭 같은 행동을 할 때마다 Claude는 무슨 일이 일어났는지 이해하기 위해 즉시 스크린샷을 받습니다. 이것은 있으면 좋은 기능이 아니라 필수입니다.

Claude 관점에서 버튼 클릭은 새 페이지로 이동시키거나, 메뉴를 열거나, 온갖 변화를 일으킬 수 있습니다. 결과를 볼 수 없다면 행동이 성공했는지, 환경의 새 상태가 어떤지 알 방법이 없습니다.

쓰기 전에 읽기

같은 원칙이 파일 작업에도 적용됩니다. Claude가 파일을 수정하기 전에는 현재 내용을 이해해야 합니다. 당연해 보여도 에이전트를 만들 때 항상 따라야 할 패턴입니다.

위 예시에서 Python 파일에 새 라우트를 추가하라고 하면, Claude는 먼저 기존 코드를 읽어 현재 구조를 파악합니다. 그래야 기존 기능을 깨뜨리지 않고 안전하게 변경할 수 있습니다.

환경 점검을 위한 시스템 프롬프트

시스템 프롬프트로 Claude가 환경을 점검하도록 유도할 수 있습니다. 동영상 생성처럼 복잡한 작업에서는 특히 중요합니다.

다음이 필요한 동영상 제작 에이전트를 생각해 봅니다.

  • FFmpeg 같은 도구로 동영상 콘텐츠 생성
  • 오디오 대사가 올바르게 배치됐는지 검증
  • 시각 요소가 예상대로 나타나는지 확인

다음과 같은 시스템 프롬프트 지시를 포함할 수 있습니다.

  • bash 도구로 whisper.cpp를 실행해 타임스탬프가 있는 캡션 파일을 생성하고 대사 배치를 검증
  • FFmpeg로 일정 간격마다 동영상에서 스크린샷을 추출해 출력을 시각적으로 점검
  • 생성된 콘텐츠를 원래 요구사항과 비교

환경 점검의 이점

  • 진행 상황 추적 향상 - 작업 완료에 얼마나 가까운지 가늠 가능
  • 오류 처리 - 예상 밖 결과를 감지·수정
  • 품질 보증 - 작업 완료로 간주하기 전에 출력 검증
  • 적응적 행동 - 관찰한 바에 따라 접근 조정

실전 구현

에이전트를 설계할 때 항상 이렇게 물으세요. "이 행동이 제대로 됐는지 Claude가 어떻게 알까?" 파일, API, 사용자 인터페이스 무엇을 다루든 Claude가 행동 결과를 관찰할 수 있는 도구와 지시를 제공하세요. 이는 다음을 의미할 수 있습니다.

  • 수정 전 파일 내용 읽기
  • UI 상호작용 후 스크린샷 촬영
  • API 응답에서 기대 데이터 확인
  • 생성된 콘텐츠를 요구사항과 대조 검증

워크플로우 vs 에이전트

🎬 영상 + 요약

AI 애플리케이션을 만들 때는 두 가지 아키텍처 접근, 즉 워크플로우와 에이전트 사이에서 선택해야 하는 경우가 많습니다. 각각 뚜렷한 장점과 트레이드오프가 있어 서로 다른 시나리오에 적합합니다.

워크플로우란

워크플로우는 알려진 문제를 풀기 위해 미리 정의된 일련의 Claude 호출입니다. 작업 완료에 필요한 정확한 순서를 미리 그릴 수 있을 때 사용합니다. 큰 작업을 훨씬 작고 구체적인 하위 작업으로 나누는 것으로 생각하면 됩니다. 각 단계가 하나의 영역에 집중하므로 Claude가 더 정밀하게 일할 수 있습니다.

에이전트란

에이전트는 Claude에게 기본 도구 세트를 주고, 그 도구로 작업을 완수할 계획을 스스로 세우게 합니다. 워크플로우와 달리 어떤 작업이 주어질지 정확히 알 수 없으므로 시스템이 더 적응적이어야 합니다. 에이전트는 도구를 예상 밖의 방식으로 조합해 다양한 난제를 창의적으로 해결할 수 있습니다.

일반적 권장은 가능한 한 항상 워크플로우를 우선 구현하고, 정말 필요할 때만 에이전트를 쓰는 것입니다. 워크플로우는 대부분의 프로덕션 앱이 필요로 하는 신뢰성·예측 가능성을 제공하고, 에이전트는 요구사항을 미리 정할 수 없는 시나리오에 유연성을 제공합니다.
