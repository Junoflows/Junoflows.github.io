Understanding Skills · 레슨 01

Skills란 무엇인가?

🎬 영상 + 아티클

팀의 코딩 표준을 설명할 때마다, PR 리뷰 방식을 다시 설명할 때마다, 선호하는 커밋 메시지 형식을 상기시킬 때마다 — 당신은 같은 말을 반복하고 있습니다. Skill은 이 문제를 해결합니다.

Skill은 Claude에게 무언가를 하는 법을 한 번 가르치는 마크다운 파일입니다. 이후 Claude는 관련 상황이 오면 그 지식을 자동으로 적용합니다.

Skill의 정체

Skill은 Claude Code가 발견해서 사용하는 지침·자료 폴더입니다. 각 Skill은 SKILL.md 파일에 담기며, 그 frontmatter에 name과 description이 들어갑니다.

description이 곧 매칭 기준입니다. 요청을 보내면 Claude는 그 메시지를 사용 가능한 모든 Skill의 description과 비교해, 맞는 것을 골라 활성화합니다.

---
name: pr-review
description: Reviews pull requests for code quality. Use when reviewing PRs or checking code changes.
---

frontmatter 아래에는 실제 지침 — 리뷰 체크리스트, 형식 선호, Claude가 그 작업에 알아야 할 내용 — 을 씁니다.

Skill이 사는 곳

위치범위
Personal · ~/.claude/skills홈 디렉터리 — 모든 프로젝트에 나를 따라다님(커밋 스타일·문서 형식·설명 방식). Windows는 C:/Users/<user>/.claude/skills.
Project · .claude/skills레포 루트에 위치 — 클론하는 누구나 자동으로 공유받음. 팀 표준(브랜드 가이드·폰트·색상)이 사는 곳. 버전 관리에 함께 커밋됩니다.

Skills vs. CLAUDE.md vs. 슬래시 커맨드

Skill이 특별한 이유는 자동이면서 작업별이기 때문입니다.

  • CLAUDE.md — 모든 대화에 로드됨. "항상 TypeScript strict 모드 사용" 같은 건 여기에.
  • Skills — 요청과 매칭될 때 온디맨드로 로드. 처음엔 name·description만 읽어 컨텍스트 윈도우를 채우지 않음. 디버깅 중엔 PR 리뷰 체크리스트가 필요 없으니, 실제로 리뷰를 요청할 때 로드.
  • 슬래시 커맨드 — 직접 타이핑해야 함. Skill은 상황을 인식하면 스스로 적용.

Skill을 쓸 때

  • 팀이 따르는 코드 리뷰 표준
  • 선호하는 커밋 메시지 형식
  • 조직의 브랜드 가이드라인
  • 특정 문서 유형의 템플릿
  • 특정 프레임워크의 디버깅 체크리스트
경험칙 · Claude에게 같은 것을 반복해서 설명하고 있다면, 그건 아직 쓰이지 않은 Skill입니다.

Understanding Skills · 레슨 02

첫 Skill 만들기

🎬 영상 + 아티클

모든 프로젝트에서 쓸 수 있는 개인 PR 설명 Skill을 밑바닥부터 만들어 봅니다. 개인 Skill이므로 홈 디렉터리에 놓입니다.

Skill 생성 — 디렉터리 + SKILL.md

먼저 Skill 이름과 같은 디렉터리를 만들고, 그 안에 SKILL.md를 둡니다.

mkdir -p ~/.claude/skills/pr-description
---
name: pr-description
description: Writes pull request descriptions. Use when creating a PR, writing a PR, or when the user asks to summarize changes for a pull request.
---

When writing a PR description:

1. Run `git diff main...HEAD` to see all changes on this branch
2. Write a description following this format:

## What
One sentence explaining what this PR does.

## Why
Brief context on why this change is needed

## Changes
- Bullet points of specific changes made
- Group related changes together
- Mention any files deleted or renamed

name은 Skill을 식별하고, description은 언제 쓸지(매칭 기준)를 알려주며, 두 번째 대시 이후의 모든 것이 활성화 시 Claude가 따르는 지침입니다.

테스트

Claude Code는 시작 시 Skill을 로드하므로, 만든 뒤 세션을 재시작해야 합니다. 사용 가능한 Skill 목록에서 확인한 뒤, 브랜치에 변경을 만들고 "내 변경사항에 대한 PR 설명을 써줘"라고 말하면 — Claude가 해당 Skill을 쓴다고 표시하고 diff를 확인해 템플릿대로 매번 같은 형식으로 작성합니다.

매칭이 작동하는 방식

시작 시 Claude Code는 네 위치를 스캔하되 name과 description만 로드합니다(전체 내용 아님). 요청을 보내면 그 메시지를 모든 Skill의 description과 비교 — 예: "이 함수가 뭐 하는지 설명해줘"는 의도가 겹치므로 "explain code with visual diagrams" Skill과 매칭됩니다.

매칭되면 Claude는 로드해도 되는지 확인을 요청합니다. 이 확인 단계가 어떤 컨텍스트가 들어오는지 인지하게 해줍니다. 승인 후 전체 SKILL.md를 읽고 지침을 따릅니다.

Skill 우선순위 (이름 충돌 시)

우선순위설명
1. Enterprise관리형 설정 — 최고 우선순위
2. Personal홈 디렉터리(~/.claude/skills)
3. Project레포의 .claude/skills
4. Plugins설치된 플러그인 — 최저 우선순위

조직은 enterprise Skill로 표준을 강제하고, 개인은 여전히 커스터마이즈할 수 있습니다. 회사의 enterprise "code-review"와 내 personal "code-review"가 같은 이름이면 enterprise가 이깁니다.

충돌 회피 · 그냥 "review" 대신 frontend-review·backend-review처럼 서술적인 이름을 쓰세요.

업데이트와 삭제

업데이트하려면 SKILL.md를 편집, 제거하려면 디렉터리를 삭제 — 어느 경우든 변경을 적용하려면 Claude Code를 재시작합니다.

Building Skills · 레슨 03

구성과 멀티파일 Skill

🎬 영상 + 아티클

기본 Skill은 name·description만으로 동작하지만, 몇 가지 고급 기법이 Skill을 훨씬 강력하게 만듭니다.

메타데이터 필드

agent skills 오픈 표준은 여러 frontmatter 필드를 지원합니다 — 두 개는 필수, 나머지는 선택.

필드역할
name (필수)Skill 식별. 소문자·숫자·하이픈만, 최대 64자, 디렉터리명과 일치.
description (필수)언제 쓸지 명시. 최대 1,024자. 매칭에 쓰이는 가장 중요한 필드.
allowed-tools (선택)Skill 활성 시 Claude가 쓸 수 있는 도구를 제한.
model (선택)Skill에 사용할 Claude 모델 지정.

효과적인 description 쓰기

명시적으로 쓰세요. 누가 "네 일은 문서를 돕는 거야"라고만 하면 뭘 해야 할지 모르듯, Claude도 마찬가지입니다. 좋은 description은 두 질문에 답합니다.

  • 이 Skill은 무엇을 하는가?
  • Claude는 언제 이걸 써야 하는가?

기대할 때 트리거되지 않으면, 실제로 요청을 표현하는 방식의 키워드를 더 추가하세요.

allowed-tools로 도구 제한

파일을 읽기만 하고 수정은 못 하게 하고 싶을 때 — 보안 민감 워크플로우, 읽기 전용 작업, 가드레일이 필요한 상황에 유용합니다.

---
name: codebase-onboarding
description: Helps new developers understand the system works.
allowed-tools: Read, Grep, Glob, Bash
model: sonnet
---

이 Skill이 활성일 때 Claude는 나열된 도구만 쓸 수 있고 편집·쓰기는 못 합니다. allowed-tools를 아예 생략하면 아무 제한도 없고 일반 권한 모델을 씁니다.

점진적 공개 (Progressive disclosure)

Skill은 대화와 컨텍스트 윈도우를 공유합니다. 활성화되면 SKILL.md 내용이 컨텍스트에 로드됩니다. 하지만 참조·예시·유틸 스크립트가 필요할 때, 2,000줄짜리 파일 하나에 다 넣으면 컨텍스트를 잡아먹고 유지보수도 괴롭습니다.

해법은 핵심 지침만 SKILL.md에 두고, 상세 참조는 별도 파일로 빼서 필요할 때만 Claude가 읽게 하는 것. 컨텍스트 안에 문서 전체가 아니라 목차를 두는 셈입니다.

오픈 표준이 제안하는 디렉터리 구성:

디렉터리내용
scripts/실행 가능한 코드
references/추가 문서
assets/이미지·템플릿·기타 데이터 파일

SKILL.md에서 언제 로드할지 명확한 지침과 함께 링크합니다 — 예: 시스템 설계를 물을 때만 architecture-guide.md를 읽고, 컴포넌트 추가 위치를 물으면 그 파일은 로드되지 않습니다.

경험칙 · SKILL.md는 500줄 이하로 유지. 초과하면 별도 참조 파일로 분리를 고려하세요.

스크립트 효율적으로 쓰기

Skill 디렉터리의 스크립트는 내용을 컨텍스트에 로드하지 않고 실행됩니다 — 출력만 토큰을 소비합니다. 핵심은 SKILL.md에 "스크립트를 읽지 말고 실행하라"고 지시하는 것. 환경 검증, 일관성이 필요한 데이터 변환, 생성 코드보다 테스트된 코드가 더 안정적인 작업에 특히 유용합니다.

Skills vs. 다른 Claude Code 기능

🎬 영상 + 아티클

Claude Code는 여러 커스터마이즈 옵션을 제공합니다 — Skills · CLAUDE.md · 서브에이전트 · 훅 · MCP 서버. 각기 다른 문제를 풀며, 언제 뭘 쓸지 알면 엉뚱한 걸 만드는 걸 막습니다.

CLAUDE.md vs Skills

CLAUDE.md는 항상 모든 대화에 로드됩니다(예: TypeScript strict 모드). Skills는 온디맨드 — 요청이 매칭될 때 지침이 대화에 합류합니다.

CLAUDE.md를 쓸 때Skills를 쓸 때
항상 적용되는 프로젝트 전역 표준, "DB 스키마 절대 수정 금지" 같은 제약, 프레임워크·코딩 스타일작업별 전문 지식, 가끔만 관련되는 지식, 매 대화를 어지럽힐 상세 절차

Skills vs 서브에이전트

Skills는 현재 대화에 지식을 더합니다(기존 컨텍스트에 합류). 서브에이전트는 별도 컨텍스트에서 작업을 받아 독립적으로 처리하고 결과만 돌려줍니다(격리됨).

서브에이전트를 쓸 때Skills를 쓸 때
별도 실행 컨텍스트로 위임, 다른 도구 접근이 필요, 위임 작업과 메인 컨텍스트를 격리현재 작업의 지식을 강화, 그 전문성이 대화 전반에 적용

Skills vs 훅

훅은 이벤트에 발화합니다 — 파일 저장 시 린터 실행, 특정 도구 호출 전 검증(이벤트 구동). Skills는 요청 구동 — 무엇을 요청하는지에 따라 활성화됩니다.

훅을 쓸 때Skills를 쓸 때
매 파일 저장마다 실행할 작업, 특정 도구 호출 전 검증, Claude 행동의 자동 부수효과요청 처리 방식을 알려주는 지식, Claude의 추론에 영향을 주는 가이드라인

종합

전형적 셋업: CLAUDE.md(항상 켜진 표준) + Skills(온디맨드 작업 전문성) + 훅(이벤트 기반 자동화) + 서브에이전트(격리 위임) + MCP 서버(외부 도구·통합). 각자 전문 영역을 맡으니 하나에 다 몰아넣지 말고 조합하세요 — 여러 개를 동시에 쓸 수 있습니다.

Sharing & Scaling · 레슨 05

Skills 공유하기

🎬 영상 + 아티클

Skill은 공유될 때 훨씬 가치가 커집니다. 나만 쓰는 PR 리뷰 Skill도 도움되지만, 팀 전체가 공유하면 코드 리뷰가 표준화되고 조직 전반에 일관된 경험이 생깁니다.

1. 레포에 커밋 (가장 간단)

.claude/skills에 두면 클론하는 누구나 추가 설치 없이 자동으로 얻습니다. 푸시하면 다음 pull에서 모두가 받습니다. 팀 코딩 표준·프로젝트 워크플로우·코드베이스 구조를 참조하는 Skill에 적합합니다.

.claude 디렉터리는 agents·hooks·skills·settings를 담으며 — 전부 버전 관리되어 일반 Git 흐름으로 팀과 공유됩니다.

2. 플러그인으로 배포

플러그인은 Claude Code를 팀·프로젝트를 넘어 공유하도록 설계된 확장 방식입니다. 플러그인 프로젝트에 skills 디렉터리를 만들어 .claude와 유사한 구조로 각 Skill을 폴더+SKILL.md로 둡니다. 마켓플레이스에 배포하면 다른 사용자가 발견·설치할 수 있습니다. 프로젝트 특정성이 낮고 커뮤니티에 유용할 때 적합합니다.

3. 엔터프라이즈 관리형 설정

관리자는 관리형 설정으로 Skill을 조직 전체에 배포합니다. Enterprise Skill은 최고 우선순위 — 같은 이름의 personal·project·plugin Skill을 덮어씁니다. strictKnownMarketplaces로 플러그인 설치처를 제어할 수 있습니다.

"strictKnownMarketplaces": [
  {
    "source": "github",
    "repo": "acme-corp/approved-plugins"
  },
  {
    "source": "npm",
    "package": "@acme-corp/compliance-plugins"
  }
]

필수 표준·보안 요건·컴플라이언스·조직 전반에 일관돼야 하는 관행에 적합합니다 — 키워드는 "반드시(must)".

Skills와 서브에이전트 (중요한 함정)

주의 · 서브에이전트는 Skill을 자동으로 보지 못합니다. 위임하면 깨끗한 새 컨텍스트로 시작합니다.
  • 내장 에이전트(Explorer·Plan·Verify)는 Skill에 전혀 접근 불가.
  • 커스텀 서브에이전트는 명시적으로 나열할 때만 Skill 사용 가능.
  • Skill은 서브에이전트 시작 시 로드됩니다(메인 대화처럼 온디맨드가 아님).

.claude/agents에 에이전트 마크다운을 추가(또는 /agents 커맨드로 대화식 생성)하고, frontmatter의 skills 필드에 로드할 Skill을 나열합니다.

---
name: frontend-security-accessibility-reviewer
description: "Use this agent when you need to review frontend code for accessibility..."
tools: Bash, Glob, Grep, Read, WebFetch, WebSearch, Skill...
model: sonnet
color: blue
skills: accessibility-audit, performance-check
---

Skill 문제 해결

🎬 영상 + 아티클

Skill이 기대대로 안 될 때, 문제는 대개 몇 가지 예측 가능한 범주로 나뉩니다 — 트리거 안 됨 · 로드 안 됨 · 충돌 · 런타임 실패. 다행히 대부분의 수정은 간단합니다.

먼저 Skills Validator

가장 먼저 agent skills verifier 커맨드를 실행하세요. 설치는 OS마다 다르지만 uv가 가장 빠릅니다. 설치 후 Skill 디렉터리로 이동하거나 어디서든 실행하면 — 구조적 문제를 먼저 잡아 헛디버깅을 막아줍니다.

트리거 안 됨

존재하고 검증도 통과하는데 Claude가 안 쓴다면 — 원인은 거의 항상 description입니다. Claude는 의미 기반 매칭을 쓰므로 요청과 description의 의미가 겹쳐야 합니다.

  • 실제로 요청을 표현하는 방식과 description을 대조
  • 사용자가 실제로 말할 트리거 문구를 추가
  • "help me profile this", "why is this slow?", "make this faster" 같은 변형으로 테스트 — 실패하는 변형의 키워드를 description에 추가

로드 안 됨

"어떤 Skill이 있어?"에 안 뜨면 구조 요건을 확인하세요.

  • SKILL.md는 이름 있는 디렉터리 안에 있어야 함(skills 루트가 아님)
  • 파일명은 정확히 SKILL.md — "SKILL" 대문자, "md" 소문자

claude --debug를 실행해 로딩 에러를 보고 Skill 이름이 언급된 메시지를 찾으면 종종 곧장 문제로 안내됩니다.

엉뚱한 Skill이 쓰임

Claude가 잘못된 Skill을 쓰거나 헷갈려하면 description이 너무 비슷한 것입니다. 최대한 구체적으로 만들어 구별하세요 — 이는 언제 쓸지 판단을 도울 뿐 아니라 유사 Skill과의 충돌도 막습니다.

우선순위 충돌 / 플러그인 Skill 미표시

  • personal Skill이 무시되면 같은 이름의 enterprise 등 상위 Skill이 있을 수 있음 → 이름을 더 구별되게 바꾸거나 관리자와 상의.
  • 플러그인을 설치했는데 Skill이 안 보이면 캐시를 지우고 재시작·재설치. 그래도 안 되면 플러그인 구조가 잘못된 것 — validator가 진가를 발휘.

런타임 에러

원인대처
의존성 누락외부 패키지는 설치돼 있어야 함. Claude가 알도록 description에 의존성 정보를 추가.
권한 문제스크립트엔 실행 권한 필요 — 참조하는 스크립트에 chmod +x.
경로 구분자Windows에서도 슬래시(/)를 일관되게 사용.

빠른 체크리스트

  • 트리거 안 됨? → description 개선 + 트리거 문구 추가
  • 로드 안 됨? → 경로·파일명·YAML 문법 확인
  • 엉뚱한 Skill? → description을 서로 더 구별되게
  • 가려짐(shadowed)? → 우선순위 확인 후 이름 변경
  • 플러그인 Skill 없음? → 캐시 지우고 재설치
  • 런타임 실패? → 의존성·권한·경로 확인
