Introduction · 레슨 02

MCP 소개

🎬 영상

Model Context Protocol(MCP)은 지루한 통합 코드를 잔뜩 짜지 않고도 Claude에게 컨텍스트와 도구를 제공하는 통신 계층입니다. 핵심 아이디어는 도구 정의와 실행의 부담을 내 서버에서 전문화된 MCP 서버로 넘기는 것입니다.

MCP를 처음 접하면 기본 아키텍처 도식을 보게 됩니다 — MCP 클라이언트(내 서버)가 도구·프롬프트·리소스를 담은 MCP 서버들에 연결됩니다. 각 MCP 서버는 외부 서비스로의 인터페이스 역할을 합니다.

MCP가 푸는 문제

사용자가 Claude에게 자신의 GitHub 데이터를 묻는 채팅 인터페이스를 만든다고 해봅시다. "내 모든 레포에 열려 있는 PR이 뭐가 있지?" 같은 질문에 답하려면 Claude가 GitHub API에 접근할 도구가 필요합니다.

GitHub는 레포·PR·이슈·프로젝트 등 엄청난 기능을 가지고 있습니다. MCP가 없다면 이 모든 기능을 감당하기 위해 수많은 도구 스키마와 함수를 직접 만들어야 합니다.

즉, 그 통합 코드를 전부 직접 작성·테스트·유지보수해야 한다는 뜻입니다. 상당한 노력과 지속적인 유지보수 부담이 따릅니다.

MCP는 어떻게 동작하나

MCP는 도구 정의와 실행을 내 서버에서 전용 MCP 서버로 옮겨 이 부담을 덜어 줍니다. 내가 GitHub 도구를 전부 작성하는 대신, GitHub용 MCP 서버가 그 일을 처리합니다.

MCP 서버는 GitHub의 방대한 기능을 감싸 표준화된 도구 세트로 노출합니다. 내 애플리케이션은 모든 것을 처음부터 구현하는 대신 이 MCP 서버에 연결하기만 하면 됩니다.

MCP 서버란

MCP 서버는 외부 서비스가 구현한 데이터·기능에 접근하게 해 주는 전문화된 인터페이스입니다. 도구·프롬프트·리소스를 표준화된 방식으로 노출합니다.

GitHub 예시에서 GitHub용 MCP 서버는 get_repos() 같은 도구를 담고 GitHub API에 직접 연결됩니다. 내 서버는 MCP 서버와 통신하고, MCP 서버가 GitHub 관련 구현 세부를 모두 처리합니다.

자주 묻는 질문

질문답
누가 MCP 서버를 만드나?누구나 만들 수 있습니다. 흔히 서비스 제공자 스스로 공식 MCP 구현을 내놓습니다(예: AWS가 자사 서비스용 공식 MCP 서버 배포).
API를 직접 호출하는 것과 뭐가 다른가?MCP 서버는 도구 스키마·함수를 이미 정의해 제공합니다. API를 직접 호출하면 그 도구 정의를 직접 작성해야 합니다 — MCP는 그 구현 작업을 아껴 줍니다.
MCP는 그냥 tool use 아닌가?흔한 오해입니다. 둘은 상호 보완적이지만 다릅니다. MCP 서버는 도구를 미리 정의해 제공하고, tool use는 Claude가 그 도구를 실제로 호출하는 방식입니다. 차이는 "누가 그 일을 하느냐" — MCP에서는 누군가 이미 도구를 구현해 둔 것입니다.
이점은 분명합니다 — 복잡한 통합을 직접 유지보수하는 대신, 외부 서비스 연결의 무거운 짐을 대신 져 주는 MCP 서버를 활용할 수 있습니다.

Introduction · 레슨 03

MCP 클라이언트

🎬 영상

MCP 클라이언트는 내 서버와 MCP 서버 사이의 통신 다리입니다. MCP 서버가 제공하는 모든 도구로의 접근점이며, 메시지 교환과 프로토콜 세부를 대신 처리해 내 애플리케이션이 신경 쓸 필요가 없게 합니다.

전송 방식에 구애받지 않는 통신

MCP의 핵심 강점 중 하나는 transport agnostic(전송 방식 불문) — 클라이언트와 서버가 설정에 따라 서로 다른 프로토콜로 통신할 수 있다는 뜻입니다.

가장 흔한 설정은 클라이언트와 서버를 같은 머신에서 돌리고 표준 입출력(stdin/stdout)으로 통신하는 것입니다. 하지만 다음으로도 연결할 수 있습니다:

  • HTTP
  • WebSockets
  • 기타 다양한 네트워크 프로토콜

MCP 메시지 타입

연결되면 클라이언트와 서버는 MCP 명세에 정의된 메시지 타입을 주고받습니다. 주로 다루게 될 것은:

ListToolsRequest / ListToolsResult: 클라이언트가 서버에 "어떤 도구를 제공하나?"를 묻고, 사용 가능한 도구 목록을 받습니다.

CallToolRequest / CallToolResult: 클라이언트가 특정 도구를 주어진 인자로 실행해 달라 요청하고 결과를 받습니다.

전체가 함께 동작하는 방식

사용자 질문이 시스템 전체를 통과하는 완전한 예시입니다 — 내 서버에서 MCP 클라이언트를 거쳐 GitHub 같은 외부 서비스로, 다시 Claude로. "내 레포가 뭐가 있지?"라는 질문의 단계별 흐름:

  • 사용자 질문: 사용자가 내 서버에 질문 제출
  • 도구 탐색: 내 서버는 Claude에 보낼 사용 가능한 도구를 알아야 함
  • List Tools 교환: 내 서버가 MCP 클라이언트에 사용 가능한 도구를 요청
  • MCP 통신: 클라이언트가 서버에 ListToolsRequest를 보내고 ListToolsResult를 받음
  • Claude 요청: 내 서버가 사용자 질문 + 도구 목록을 Claude에 전송
  • 도구 사용 판단: Claude가 답을 위해 도구가 필요하다고 결정
  • 도구 실행 요청: 내 서버가 Claude가 지정한 도구를 실행하라고 클라이언트에 요청
  • 외부 API 호출: 클라이언트가 CallToolRequest를 서버에 보내고, 서버가 실제 GitHub API 호출 수행
  • 결과 역류: GitHub가 레포 데이터로 응답, MCP 서버를 통해 CallToolResult로 돌아옴
  • 도구 결과를 Claude로: 내 서버가 도구 결과를 Claude에 전달
  • 최종 응답: Claude가 레포 데이터로 최종 답 작성
  • 사용자에게 답 전달: 내 서버가 Claude의 응답을 사용자에게 전달
단계가 많아 보이지만 각 컴포넌트의 책임은 명확합니다. MCP 클라이언트가 서버 통신의 복잡성을 추상화해 주므로, 나는 애플리케이션 로직에 집중하면서도 강력한 외부 도구·데이터에 접근할 수 있습니다. 이 흐름을 이해해 두면 이후 클라이언트·서버를 직접 만들 때 이 조각들이 모두 눈에 들어옵니다.

MCP로 도구 정의하기

🎬 영상

공식 Python SDK를 쓰면 MCP 서버 구축이 훨씬 단순해집니다. 복잡한 JSON 스키마를 손으로 작성하는 대신, 데코레이터로 도구를 정의하고 무거운 작업은 SDK에 맡깁니다.

이 예시에서는 문서 두 개를 다루는 관리 서버를 만듭니다 — 문서를 읽는 도구와 수정하는 도구. 모든 문서는 문서 ID를 키로, 내용을 값으로 하는 단순한 딕셔너리로 메모리에 존재합니다.

MCP 서버 세팅

Python MCP SDK는 서버 생성을 간단하게 만듭니다. 한 줄로 서버를 초기화할 수 있습니다:

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("DocumentMCP", log_level="ERROR")

문서는 단순한 딕셔너리 구조로 저장할 수 있습니다:

docs = {
"deposition.md": "This deposition covers the testimony of Angela Smith, P.E.",
"report.pdf": "The report details the state of a 20m condenser tower.",
"financials.docx": "These financials outline the project's budget and expenditures",
"outlook.pdf": "This document presents the projected future performance of the system",
"plan.md": "The plan outlines the steps for the project's implementation.",
"spec.txt": "These specifications define the technical requirements for the equipment"
}

데코레이터로 도구 정의

SDK는 데코레이터로 도구를 정의합니다. JSON 스키마를 손으로 쓰는 대신 Python 타입 힌트와 필드 설명을 쓰면, SDK가 Claude가 이해할 수 있는 적절한 스키마를 자동 생성합니다.

문서 읽기 도구 만들기

첫 번째 도구는 ID로 문서 내용을 읽습니다:

@mcp.tool(
name="read_doc_contents",
description="Read the contents of a document and return it as a string."
)
def read_document(
doc_id: str = Field(description="Id of the document to read")
):
if doc_id not in docs:
raise ValueError(f"Doc with id {doc_id} not found")

return docs[doc_id]

데코레이터는 도구 이름과 설명을 지정하고, 함수 파라미터가 필요한 인자를 정의합니다. Pydantic의 Field 클래스가 제공하는 인자 설명은 각 파라미터가 무엇을 기대하는지 Claude가 이해하도록 돕습니다.

문서 편집 도구 만들기

두 번째 도구는 문서에서 단순 찾기-바꾸기를 수행합니다:

@mcp.tool(
name="edit_document",
description="Edit a document by replacing a string in the documents content with a new string."
)
def edit_document(
doc_id: str = Field(description="Id of the document that will be edited"),
old_str: str = Field(description="The text to replace. Must match exactly, including whitespace."),
new_str: str = Field(description="The new text to insert in place of the old text.")
):
if doc_id not in docs:
raise ValueError(f"Doc with id {doc_id} not found")

docs[doc_id] = docs[doc_id].replace(old_str, new_str)

세 파라미터(문서 ID, 찾을 텍스트, 바꿀 텍스트)를 받으며, 없는 문서에 대한 에러 처리와 단순 문자열 치환을 포함합니다.

SDK 방식의 핵심 이점
  • 수동 JSON 스키마 작성 불필요
  • 타입 힌트가 자동 검증 제공
  • 명확한 파라미터 설명이 Claude의 도구 사용 이해를 도움
  • 에러 처리가 Python 예외와 자연스럽게 통합
  • 데코레이터로 도구 등록이 자동으로 이뤄짐

Building the server · 레슨 06

서버 인스펙터

🎬 영상

MCP 서버를 만들 때 전체 애플리케이션에 연결하지 않고도 기능을 테스트할 방법이 필요합니다. Python MCP SDK에는 브라우저 기반 인스펙터가 내장돼 있어 서버를 실시간으로 디버깅·테스트할 수 있습니다.

인스펙터 실행

먼저 Python 환경이 활성화됐는지 확인한 뒤(정확한 명령은 프로젝트 README 참고), 다음으로 인스펙터를 실행합니다:

mcp dev mcp_server.py

개발 서버가 뜨면서 http://127.0.0.1:6274 같은 로컬 URL을 줍니다. 이 URL을 브라우저에서 열면 MCP 인스펙터에 접속됩니다.

인스펙터 인터페이스 사용

인스펙터 UI는 활발히 개발 중이라 볼 때마다 다를 수 있지만, 핵심 기능은 일관됩니다. 다음 요소를 찾으세요:

  • MCP 서버를 시작하는 Connect 버튼
  • Resources · Tools · Prompts 등 기능별 네비게이션 탭
  • 도구 목록·테스트 패널

먼저 Connect 버튼을 눌러 서버를 초기화하면 상태가 "Disconnected"에서 "Connected"로 바뀝니다.

도구 테스트

Tools 섹션으로 가서 "List Tools"를 누르면 서버가 제공하는 모든 도구가 보입니다. 도구를 선택하면 오른쪽 패널에 세부와 입력 필드가 나타납니다.

예를 들어 문서 읽기 도구를 테스트하려면:

  • read_doc_contents 도구 선택
  • 문서 ID 입력(예: "deposition.md")
  • "Run Tool" 클릭
  • 성공 여부와 기대 출력 확인

인스펙터는 성공 상태와 실제 반환 데이터를 함께 보여 줘 도구가 올바르게 동작하는지 쉽게 검증할 수 있습니다.

도구 상호작용 테스트

여러 도구를 순서대로 테스트해 복잡한 워크플로우를 검증할 수 있습니다. 예컨대 편집 도구로 문서를 수정한 뒤 곧바로 읽기 도구로 변경이 적용됐는지 확인합니다. 인스펙터는 도구 호출 사이 서버 상태를 유지하므로 편집이 지속되고 전체 기능을 검증할 수 있습니다.

개발 워크플로우
  • 도구 구현을 빠르게 반복
  • 엣지 케이스·에러 조건 테스트
  • 도구 상호작용·상태 관리 검증
  • 실시간 디버깅
이 즉각적 피드백 루프 덕분에 별도 테스트 스크립트나 전체 앱 연결 없이도 MCP 서버 개발이 훨씬 효율적이고, 문제를 초기에 잡을 수 있습니다.

클라이언트 구현하기

🎬 영상

서버가 동작하니 이제 클라이언트 쪽을 만들 차례입니다. 클라이언트는 애플리케이션 코드가 MCP 서버와 통신하고 그 기능에 접근하게 해 줍니다.

클라이언트 아키텍처 이해

대부분의 실제 프로젝트에서는 MCP 클라이언트 또는 서버 중 하나만 구현합니다 — 둘 다는 아닙니다. 이 프로젝트에서는 둘의 협동을 보기 위해 둘 다 만듭니다.

MCP 클라이언트는 두 주요 컴포넌트로 구성됩니다:

  • MCP Client — 세션 사용을 편하게 하려고 우리가 만든 커스텀 클래스
  • Client Session — 서버와의 실제 연결(MCP Python SDK의 일부)

클라이언트 세션은 리소스 관리가 중요합니다 — 끝나면 연결을 제대로 정리해야 합니다. 그래서 정리를 자동으로 처리하는 우리 클래스로 감쌉니다.

클라이언트가 애플리케이션에 들어가는 위치

애플리케이션 흐름도를 기억하나요? 클라이언트는 코드가 MCP 서버와 상호작용하는 두 지점을 가능하게 합니다:

  • Claude에 보낼 사용 가능한 도구 목록 가져오기
  • Claude가 요청할 때 도구 실행하기

핵심 클라이언트 함수 구현

두 필수 함수 list_tools()와 call_tool()을 구현합니다.

List Tools 함수 — MCP 서버에서 모든 도구를 가져옵니다:

async def list_tools(self) -> list[types.Tool]:
result = await self.session().list_tools()
return result.tools

세션(서버 연결)에 접근해 내장 list_tools() 메서드를 호출하고 결과의 도구들을 반환하는, 단순한 구조입니다.

Call Tool 함수 — 서버에서 특정 도구를 실행합니다:

async def call_tool(
self, tool_name: str, tool_input: dict
) -> types.CallToolResult | None:
return await self.session().call_tool(tool_name, tool_input)

Claude가 준 도구 이름과 입력 파라미터를 서버에 넘기고 결과를 반환합니다.

클라이언트 테스트

클라이언트 파일 하단에는 간단한 테스트 하네스가 있어 직접 실행해 검증할 수 있습니다:

uv run mcp_client.py

이렇게 하면 MCP 서버에 연결해 사용 가능한 도구를 출력합니다 — 설명·입력 스키마를 포함한 도구 정의가 보여야 합니다.

모두 합쳐 보기

클라이언트 함수가 구현되면 메인 애플리케이션을 실행해 전체 흐름을 테스트합니다:

uv run main.py

"What is the contents of the report.pdf document?"라고 물어보세요. 뒤에서 벌어지는 일:

  • 애플리케이션이 클라이언트로 사용 가능한 도구를 가져옴
  • 도구와 질문이 함께 Claude에 전달됨
  • Claude가 read_doc_contents 도구 사용을 결정
  • 애플리케이션이 클라이언트로 그 도구를 실행
  • 결과가 Claude에 반환되고 Claude가 응답
클라이언트는 애플리케이션 로직과 MCP 서버 기능 사이의 다리 역할을 하며, 강력한 도구를 AI 워크플로우에 쉽게 통합하게 해 줍니다.

리소스 정의하기

🎬 영상

MCP 서버의 리소스(Resource)는 HTTP 서버의 GET 핸들러처럼 클라이언트에 데이터를 노출합니다. 행동을 수행하기보다 정보를 가져와야 하는 상황에 알맞습니다.

예시로 이해하는 리소스

사용자가 @document_name을 입력해 파일을 참조하는 문서 멘션 기능을 만든다고 해봅시다. 두 가지 작업이 필요합니다:

  • 사용 가능한 모든 문서 목록 가져오기(자동완성용)
  • 특정 문서의 내용 가져오기(멘션될 때)

사용자가 문서를 멘션하면 시스템이 그 내용을 Claude에 보내는 프롬프트에 자동 주입해, Claude가 도구로 정보를 가져올 필요가 없어집니다.

리소스 동작 방식

리소스는 요청-응답 패턴을 따릅니다. 데이터가 필요하면 클라이언트가 어떤 리소스인지 식별하는 URI를 담아 ReadResourceRequest를 보냅니다. 서버가 처리해 ReadResourceResult로 데이터를 반환합니다.

흐름은 이렇습니다 — 내 코드가 MCP 클라이언트에 리소스를 요청하면, 클라이언트가 이를 서버로 전달하고, 서버가 URI를 처리해 적절한 함수를 실행한 뒤 결과를 반환합니다.

리소스의 두 종류

Direct(직접) 리소스 — 절대 바뀌지 않는 정적 URI. 파라미터가 필요 없는 작업에 알맞습니다:

@mcp.resource(
"docs://documents",
mime_type="application/json"
)
def list_docs() -> list[str]:
return list(docs.keys())

Templated(템플릿) 리소스 — URI에 파라미터를 포함합니다. Python SDK가 파라미터를 자동 파싱해 함수에 키워드 인자로 전달합니다:

@mcp.resource(
"docs://documents/{doc_id}",
mime_type="text/plain"
)
def fetch_doc(doc_id: str) -> str:
if doc_id not in docs:
raise ValueError(f"Doc with id {doc_id} not found")
return docs[doc_id]

구현 세부

리소스는 문자열·JSON·바이너리 등 어떤 데이터든 반환할 수 있습니다. mime_type으로 클라이언트에 데이터 종류를 힌트로 줍니다:

  • "application/json" — 구조화된 데이터
  • "text/plain" — 일반 텍스트
  • "application/pdf" — 바이너리 파일

MCP Python SDK가 반환값을 자동 직렬화합니다 — 객체를 JSON 문자열로 직접 변환할 필요 없이 데이터 구조를 그대로 반환하면 됩니다.

리소스 테스트

MCP 인스펙터로 리소스를 테스트할 수 있습니다. 서버를 실행합니다:

uv run mcp dev mcp_server.py

브라우저에서 인스펙터에 연결하면 두 섹션이 보입니다:

  • Resources — 직접/정적 리소스 목록
  • Resource Templates — 템플릿 리소스 목록
아무 리소스나 클릭해 테스트할 수 있으며, 템플릿 리소스는 파라미터 값을 넣어야 합니다. 인스펙터는 클라이언트가 받을 정확한 응답 구조(MIME 타입·직렬화 데이터 포함)를 보여 줍니다. 리소스는 도구 호출의 복잡함 없이 읽기 전용 데이터를 깔끔하게 노출하는 방법입니다.

리소스 접근하기

🎬 영상

MCP의 리소스는 도구 호출 없이도 서버 정보를 프롬프트에 직접 포함할 수 있게 해, AI 모델에 컨텍스트를 더 효율적으로 제공합니다.

위 도식은 리소스 동작을 보여 줍니다 — 사용자가 "What's in the @..."처럼 입력하면 코드가 이를 리소스 요청으로 인식해 ReadResourceRequest를 서버에 보내고, 실제 내용이 담긴 ReadResourceResult를 받습니다.

리소스 읽기 구현

클라이언트에서 리소스 접근을 활성화하려면 read_resource 함수를 구현합니다. 먼저 필요한 임포트:

import json
from pydantic import AnyUrl

핵심 함수는 MCP 서버에 요청을 보내고 응답의 MIME 타입에 따라 처리합니다:

async def read_resource(self, uri: str) -> Any:
result = await self.session().read_resource(AnyUrl(uri))
resource = result.contents[0]

if isinstance(resource, types.TextResourceContents):
if resource.mimeType == "application/json":
return json.loads(resource.text)

return resource.text

응답 구조 이해

리소스를 요청하면 서버는 contents 리스트를 담은 결과를 반환합니다. 보통 리소스가 하나면 되므로 첫 요소에 접근합니다. 응답에는:

  • 실제 내용(텍스트 또는 데이터)
  • 내용 파싱 방법을 알려 주는 MIME 타입
  • 기타 메타데이터

콘텐츠 타입 처리

  • application/json이면 텍스트를 JSON으로 파싱해 파싱된 객체를 반환
  • 그 외에는 원시 텍스트 내용을 반환

이 방식으로 구조화된 데이터(JSON)와 일반 텍스트를 모두 매끄럽게 다룹니다.

리소스 접근 테스트

구현 후 CLI 애플리케이션에서 테스트할 수 있습니다. "@" 뒤에 리소스 이름을 입력하면 시스템이:

  • 자동완성 목록에 사용 가능한 리소스 표시
  • 화살표·스페이스로 리소스 선택
  • 리소스 내용을 프롬프트에 직접 포함
  • 추가 도구 호출 없이 모든 것을 AI 모델에 전송
AI 모델이 문서 내용을 얻으려 별도 도구 호출을 하는 것보다 훨씬 매끄러운 경험입니다. 리소스 내용이 초기 컨텍스트의 일부가 되어 데이터에 대한 즉각적 응답이 가능합니다.

프롬프트 정의하기

🎬 영상

MCP 서버의 프롬프트(Prompt)는 클라이언트가 직접 프롬프트를 쓰는 대신 사용할 수 있는 미리 만들어진 고품질 지침입니다. 사용자가 스스로 떠올릴 법한 것보다 더 나은 결과를 주는, 정성껏 다듬은 템플릿이라 생각하면 됩니다.

왜 프롬프트를 쓰나

핵심 통찰: 사용자는 이미 대부분의 작업을 Claude에게 직접 요청할 수 있습니다. 예컨대 "reformat the report.pdf in markdown"이라 입력하면 괜찮은 결과가 나옵니다. 하지만 엣지 케이스를 처리하고 모범 사례를 따르는, 철저히 테스트된 전문 프롬프트를 제공하면 훨씬 나은 결과를 얻습니다.

MCP 서버 작성자로서 여러 시나리오에서 일관되게 동작하는 프롬프트를 만들고·테스트하고·평가하는 데 시간을 쏟을 수 있습니다. 사용자는 프롬프트 엔지니어링 전문가가 되지 않고도 그 전문성의 혜택을 봅니다.

Format 명령 만들기

문서를 마크다운으로 변환하는 format 명령을 구현해 봅시다. 사용자가 /format doc_id를 입력하면 전문적으로 포맷된 마크다운 버전을 돌려받습니다. 흐름:

  • 사용자가 /를 입력해 사용 가능한 명령 확인
  • format을 선택하고 문서 ID 지정
  • Claude가 미리 만든 프롬프트로 문서를 읽고 재포맷
  • 헤더·리스트·포맷이 갖춰진 깔끔한 마크다운 결과

프롬프트 정의

프롬프트는 도구·리소스와 비슷한 데코레이터 패턴을 씁니다:

@mcp.prompt(
name="format",
description="Rewrites the contents of the document in Markdown format."
)
def format_document(
doc_id: str = Field(description="Id of the document to format")
) -> list[base.Message]:
prompt = f"""
Your goal is to reformat a document to be written with markdown syntax.

The id of the document you need to reformat is:
<document_id>
{doc_id}
</document_id>

Add in headers, bullet points, tables, etc as necessary. Feel free to add in structure.
Use the 'edit_document' tool to edit the document. After the document has been reformatted...
"""

return [
base.UserMessage(prompt)
]

함수는 Claude에 바로 전송되는 메시지 리스트를 반환합니다. 여러 user·assistant 메시지를 넣어 더 복잡한 대화 흐름을 만들 수도 있습니다.

프롬프트 테스트

배포 전 MCP 인스펙터로 테스트하세요:

인스펙터는 변수가 프롬프트 템플릿에 어떻게 보간되는지를 포함해, Claude에 전송될 정확한 메시지를 보여 줍니다. 사용자가 의존하기 전에 프롬프트가 올바른지 검증할 수 있습니다.

핵심 이점
  • 일관성 — 사용자가 매번 신뢰할 수 있는 결과
  • 전문성 — 도메인 지식을 프롬프트에 인코딩
  • 재사용성 — 여러 클라이언트가 같은 프롬프트 사용
  • 유지보수 — 한곳에서 갱신하면 모든 클라이언트 개선
프롬프트는 MCP 서버의 도메인에 특화될 때 가장 강력합니다. 목표는, 사용자가 직접 지침을 쓰기보다 이 프롬프트를 선호할 만큼 잘 만들고 테스트하는 것입니다.

클라이언트의 프롬프트

🎬 영상

MCP 클라이언트 구축의 마지막 단계는 프롬프트 기능 구현입니다. 서버의 모든 프롬프트를 나열하고, 변수가 채워진 특정 프롬프트를 가져올 수 있게 합니다.

List Prompts 구현

list_prompts 메서드는 세션의 list prompts를 호출해 프롬프트를 반환하는, 단순한 구조입니다:

async def list_prompts(self) -> list[types.Prompt]:
result = await self.session().list_prompts()
return result.prompts

개별 프롬프트 가져오기

get_prompt 메서드는 변수 보간을 다루므로 더 흥미롭습니다. 프롬프트를 요청할 때 넘긴 인자가 프롬프트 함수에 키워드 인자로 전달됩니다:

async def get_prompt(self, prompt_name, args: dict[str, str]):
result = await self.session().get_prompt(prompt_name, args)
return result.messages

예를 들어 서버에 doc_id를 기대하는 format_document 프롬프트가 있다면, 인자 딕셔너리는 {"doc_id": "plan.md"}가 되고 이 값이 프롬프트 템플릿에 보간됩니다.

실제로 프롬프트 테스트

구현 후 CLI에서 테스트할 수 있습니다. 슬래시(/)를 입력하면 사용 가능한 프롬프트가 명령으로 나타납니다. "format" 같은 프롬프트를 고르면 사용 가능한 문서 중에서 선택하게 됩니다.

문서를 선택하면 시스템이 완성된 프롬프트를 Claude에 보냅니다. Claude는 포맷 지침과 문서 ID를 받아, 사용 가능한 도구로 내용을 가져와 처리합니다.

프롬프트 동작 방식

프롬프트는 클라이언트가 쓸 수 있는 user·assistant 메시지 세트를 정의합니다. 고품질·테스트 완료·서버 목적에 부합해야 합니다. 워크플로우는:

  • 서버 기능에 맞는 프롬프트를 작성·평가
  • @mcp.prompt 데코레이터로 서버에 정의
  • 클라이언트가 언제든 프롬프트 요청 가능
  • 클라이언트가 제공한 인자가 프롬프트 함수의 키워드 인자가 됨
  • 함수가 AI 모델용 포맷된 메시지를 반환
이 시스템은 변수로 커스터마이즈하면서도 일관성을 유지하는, 재사용 가능한 파라미터화 프롬프트를 만듭니다. AI가 매번 제대로 구조화된 지침을 받아야 하는 복잡한 워크플로우에 특히 유용합니다.

MCP 리뷰

🎬 영상

MCP 서버를 다 만들었으니 세 가지 핵심 서버 프리미티브와 각각을 언제 쓸지 정리합시다. 핵심 통찰은 각 프리미티브가 애플리케이션 스택의 서로 다른 부분에 의해 제어된다는 것입니다.

프리미티브제어 주체설명
Tools모델(Claude)Claude가 언제 호출할지 결정하고 결과를 직접 사용. 자율적으로 쓸 새 역량을 줄 때 알맞음(예: "JS로 3의 제곱근 계산").
Resources애플리케이션내 앱 코드가 언제 데이터를 가져와 어떻게 쓸지 결정 — UI 요소나 대화 컨텍스트 보강용(예: 자동완성 채우기, 프롬프트에 내용 주입, "Google Drive에서 추가").
Prompts사용자사용자가 버튼·메뉴·슬래시 명령으로 실행하는 미리 정의된 최적화 워크플로우(예: 채팅 입력 아래 워크플로우 버튼).
어떤 프리미티브를 고를까
  • Claude에 새 역량을 주고 싶다 → Tools
  • UI·컨텍스트용 데이터를 앱에 넣고 싶다 → Resources
  • 사용자용 미리 정의된 워크플로우를 만들고 싶다 → Prompts
이 셋은 Claude 공식 인터페이스에서 모두 확인할 수 있습니다 — 워크플로우 버튼은 프롬프트, Google Drive 통합은 리소스, 코드 실행·계산은 도구입니다. 각각이 스택의 다른 부분을 담당합니다: 도구는 모델을, 리소스는 앱을, 프롬프트는 사용자를 위해.
