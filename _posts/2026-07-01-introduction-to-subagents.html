서브에이전트 개념 · 레슨 01

서브에이전트란?

🎬 영상 + 아티클

서브에이전트(subagent)는 Claude Code가 작업을 위임(delegate)할 수 있는 특화된 도우미입니다. 각 서브에이전트는 자기만의 대화 컨텍스트 윈도우에서 일하고, 작업이 끝나면 요약만 메인 스레드로 돌려줍니다. 파일 읽기·검색·도구 호출 같은 중간 단계는 격리된 채 남아 메인 대화를 어지럽히지 않습니다.

왜 서브에이전트가 중요한가

Claude Code와 대화할 때마다 메인 컨텍스트 윈도우가 채워집니다. 모든 도구 호출·파일 읽기·검색 결과가 거기 쌓이는데, 그 공간은 유한하며 가득 차면 Claude가 앞부분 내용을 놓치기 시작합니다.

서브에이전트는 별도의 컨텍스트 윈도우를 띄워 이 문제를 해결합니다. 서브에이전트가 받는 것은 두 가지입니다.

  • 설정 파일에 정의된 커스텀 시스템 프롬프트 — 서브에이전트의 역할과 행동을 규정
  • 부모 에이전트가 요청 내용을 바탕으로 작성한 작업 설명(task description)

서브에이전트는 스스로 파일을 읽고 검색하고 코드를 수정하며 일합니다. 끝나면 요약만 메인 대화로 돌아오고, 서브에이전트의 전체 대화는 폐기됩니다. 덕분에 메인 컨텍스트는 깨끗하게 유지됩니다. 다만 서브에이전트가 어떻게 결론에 이르렀는지에 대한 가시성은 잃는다는 트레이드오프가 있습니다.

실전 예시 — 환불 처리 서비스 찾기

낯선 코드베이스에서 "어느 서비스가 환불을 처리하지?"를 알고 싶다고 합시다.

  • 서브에이전트 없이 — Claude가 15개 파일을 읽고 여러 검색을 돌리고 함수 호출을 추적합니다. 필요한 건 사실 하나뿐인데 이 모든 게 컨텍스트를 채웁니다.
  • 서브에이전트로 — 질문하면 Explore 서브에이전트가 자기 컨텍스트에서 파헤치고 초점 맞춘 답만 건넵니다. 메인 컨텍스트엔 질문과 요약만 기록되고, 읽은 15개 파일은 남지 않습니다.

내장 서브에이전트

Claude Code에는 바로 쓸 수 있는 내장 서브에이전트가 몇 가지 있습니다.

내장 서브에이전트용도
General purpose탐색과 실행이 모두 필요한 다단계 작업.
Explore코드베이스를 빠르게 검색·탐색.
Plan플랜 모드에서 계획 제시 전 코드베이스 리서치·분석.

커스텀 서브에이전트도 만들 수 있습니다. 커스텀 시스템 프롬프트와 도구 접근 권한으로 코드 리뷰어·테스트 작성기·문서 생성기 등 워크플로우 맞춤형 에이전트를 정의합니다.

핵심 정리

서브에이전트의 세 가지 이점: ① 작업을 초점 잡힌 조각으로 나눠 각자 한 가지에 집중하게 함, ② 중간 작업을 격리해 메인 컨텍스트를 깨끗하게 유지, ③ 필요한 정보만 간결한 요약으로 회수. 메인 컨텍스트의 잡음이 적을수록 더 길고 효과적으로 작업할 수 있습니다.

서브에이전트 만들기 · 레슨 02

서브에이전트 만들기

🎬 영상 + 아티클

커스텀 서브에이전트는 코드 리뷰·테스트 작성·문서 확인 같은 특정 작업에 특화됩니다. YAML frontmatter가 붙은 마크다운 파일로 정의되며, 이 파일이 Claude에게 언제 이 서브에이전트를 쓸지와 어떻게 행동할지를 알려줍니다.

만드는 법 — /agents

가장 쉬운 방법은 /agents 슬래시 명령입니다. 서브에이전트 관리 메인 인터페이스가 열리면 Create new agent를 선택합니다. 먼저 스코프(scope)를 고릅니다.

  • Project-level — 현재 프로젝트에서만 사용 가능
  • User-level — 내 머신의 모든 프로젝트에서 공유

이어서 만드는 방식을 선택합니다. 설정을 직접 작성할 수도 있지만, 권장 방식은 Claude가 대신 생성하게 하는 것입니다. 원하는 동작을 설명하면 Claude가 name·description·시스템 프롬프트를 만들어 줍니다.

도구 커스터마이징

생성 중에 서브에이전트가 접근할 도구를 고를 수 있습니다. 카테고리는 다음과 같습니다.

  • Read-only tools (읽기 전용)
  • Edit tools (수정)
  • Execution tools (실행)
  • MCP tools
  • Other tools
서브에이전트가 실제로 필요한 것만 생각하세요. 코드 리뷰어는 코드를 읽고 분석할 뿐 바꾸지 않으니 Edit 도구는 대개 불필요합니다. 다만 대기 중인 변경을 쉽게 파악하도록 실행 도구는 켜 둘 수 있습니다.

모델과 색상 고르기

모델용도
Haiku빠르고 가벼운 작업에 최적
Sonnet속도와 깊이의 좋은 중간 지점
Opus복잡한 분석에 최적
Inherit메인 대화가 쓰는 모델을 그대로 사용

마지막으로 색상을 고릅니다. UI에 표시되어 여러 서브에이전트가 돌 때 어느 것이 활성인지 빠르게 구분하게 해 줍니다.

설정 파일의 구조

생성이 끝나면 설정 파일이 프로젝트에 저장됩니다 — 보통 .claude/agents/your-agent-name.md. 전형적인 형태는 다음과 같습니다.

---
name: code-quality-reviewer
description: Use this agent when you need to review recently written or modified code for quality, security, and best practice compliance.
tools: Bash, Glob, Grep, Read, WebFetch, WebSearch
model: sonnet
color: purple
---

You are an expert code reviewer specializing in quality assurance, security best
practices, and adherence to project standards. Your role is to thoroughly examine
recently written or modified code and identify issues that could impact reliability,
security, maintainability, or performance.
필드역할
name서브에이전트의 고유 식별자. @agent code-quality-reviewer처럼 참조.
descriptionClaude가 언제 이 서브에이전트를 쓸지 결정하는 근거. 한 줄이어야 함(줄바꿈이 필요하면 \n). 예시 대화를 넣어도 됨.
tools접근 가능한 도구 목록. 생성 시 선택한 것과 일치하되 여기서 언제든 수정 가능.
modelsonnet · opus · haiku · inherit 중 하나.
color서브에이전트 식별용 UI 색상.

시스템 프롬프트

YAML frontmatter 아래의 본문 전체가 시스템 프롬프트입니다. 여기서 무엇에 집중하고, 어떻게 분석하며, 결과를 메인 에이전트에 어떻게 보고할지 지시합니다. 잘 쓴 시스템 프롬프트가 쓸모 있는 서브에이전트와 헛도는 서브에이전트를 가릅니다.

자동으로 위임하게 만들기

명시적으로 요청하지 않아도 Claude가 알아서 위임하게 하려면 description에 "proactively"라는 단어를 넣으세요. 예: description: Proactively suggest running this agent after major code changes... 구체적인 예시 대화를 더할수록 Claude가 언제 위임할지 잘 판단합니다.

서브에이전트를 만든 뒤엔 코드를 조금 바꾸고 리뷰를 요청해 테스트하세요. 기대한 대로 쓰이지 않으면 description을 다시 점검하고, 더 구체적인 예시와 트리거 시나리오를 추가합니다.

설계 원칙 · 레슨 03

효과적인 서브에이전트 설계

🎬 영상 + 아티클

설정이 부실한 서브에이전트는 헤매고, 너무 오래 돌고, 메인 에이전트가 못 쓰는 출력을 냅니다. 해법은 네 가지로 좁혀집니다 — 좋은 description 쓰기, 출력 형식 정의, 장애물 보고, 도구 접근 제한.

설정 데이터가 어떻게 쓰이나

메인 컨텍스트 윈도우 에이전트에 메시지를 보내면, 사용 가능한 모든 서브에이전트의 name과 description이 시스템 프롬프트에 포함됩니다. 메인 에이전트는 이걸 보고 어떤 서브에이전트를 언제 띄울지 결정합니다.

description은 두 번째 역할도 합니다. 메인 에이전트가 서브에이전트를 띄울 때 작업을 시작할 입력 프롬프트(input prompt)를 작성하는데, 이때 description을 지침으로 삼습니다. 즉 description은 언제 실행할지뿐 아니라 무엇을 지시할지도 좌우합니다.

입력 프롬프트를 빚는 description 쓰기

코드 리뷰 서브에이전트를 예로 들면:

  • 모호한 description → 메인 에이전트가 "use get diff to find the current changes" 같은 막연한 입력 프롬프트를 씀. 어떤 파일이 중요한지 서브에이전트가 스스로 알아내야 함.
  • description에 "You must tell the agent precisely which files you want it to review"를 넣으면 → 메인 에이전트가 실제 리뷰할 파일을 나열한 훨씬 구체적인 입력 프롬프트를 씀.

같은 기법이 다른 유형에도 통합니다. 웹 검색 서브에이전트에 "return sources that can be cited"를 넣으면 위임 시 그 지시가 함께 전달됩니다.

출력 형식 정의 — 가장 중요한 개선

시스템 프롬프트에 출력 형식(output format)을 정의하는 것이 서브에이전트에 할 수 있는 가장 중요한 개선입니다. 두 가지 효과가 있습니다.

  • 자연스러운 종료 지점을 만듭니다 — 각 섹션을 다 채우면 끝났음을 앎.
  • 과도한 실행을 막습니다 — 출력이 정의돼 있지 않으면 언제 충분히 조사했는지 판단하지 못해 필요 이상으로 오래 돕니다.

코드 리뷰 서브에이전트의 구조화된 출력 형식 예시:

Provide your review in a structured format:

1. Summary: Brief overview of what you reviewed and overall assessment
2. Critical Issues: Any security vulnerabilities, data integrity risks,
   or logic errors that must be fixed immediately
3. Major Issues: Quality problems, architecture misalignment, or
   significant performance concerns
4. Minor Issues: Style inconsistencies, documentation gaps, or
   minor optimizations
5. Recommendations: Suggestions for improvement, refactoring
   opportunities, or best practices to apply
6. Approval Status: Clear statement of whether the code is ready
   to merge/deploy or requires changes

이 형식은 서브에이전트에 명확한 체크리스트를 줍니다. 모든 섹션이 채워지면 멈춰도 된다는 걸 압니다.

장애물 보고

서브에이전트가 작업 중 우회책(workaround)을 발견하면 — 의존성 문제를 풀거나 특정 명령에 특별한 플래그가 필요하다는 걸 알아냈다면 — 그 내용이 반환 요약에 담겨야 합니다. 그렇지 않으면 메인 스레드가 같은 해법을 다시 발견해야 해 시간과 토큰을 낭비합니다.

표면화할 것: 셋업 이슈·환경 특성, 발견한 우회책, 특별한 플래그·설정이 필요한 명령, 문제를 일으킨 의존성·임포트. 이를 얻는 방법은 출력 형식에 명시적으로 요청하는 것 — "Obstacles Encountered" 섹션을 추가합니다.

7. Obstacles Encountered: Report any obstacles encountered during the
   review process. This can be: setup issues, workarounds discovered or
   environment quirks. Report commands that needed a special flag or
   configuration. Report dependencies or imports that caused problems.

도구 접근 제한

모든 서브에이전트가 모든 도구를 필요로 하진 않습니다. 필요한 도구만 주면 의도치 않은 부작용을 막고, 여러 개가 있을 때 각자의 역할이 명확해집니다.

서브에이전트 유형필요한 도구
리서치 / 읽기 전용Glob · Grep · Read만. 파일을 실수로 수정할 수 없음.
코드 리뷰어git diff 실행용 Bash는 필요하나 Edit·Write는 여전히 불필요.
스타일링 / 코드 수정실제로 코드를 바꾸는 게 일이므로 Edit·Write를 부여.

종합 — 효과적인 서브에이전트의 네 가지 특징

① 구체적인 description — 언제 띄울지와 어떤 지시를 받을지를 모두 조종. ② 구조화된 출력 — 언제 끝났는지 알고 메인 스레드가 쓸 정보를 반환. ③ 장애물 보고 — 우회책·특성·문제를 섹션으로 표면화. ④ 제한된 도구 접근 — 실제 필요한 도구만. 각각은 단순하지만, 합치면 서브에이전트가 제때 끝내고 명확히 보고하는 예측 가능한 일꾼이 됩니다.

활용 판단 · 레슨 04

서브에이전트 잘 쓰기

🎬 영상 + 아티클

언제 서브에이전트가 실제로 도움이 되고, 언제 방해가 될까? 차이는 하나로 귀결됩니다 — 중간 작업이 메인 스레드에 중요한가.

서브에이전트가 빛날 때

서브에이전트는 탐색과 실행이 분리될 때 가장 잘 작동합니다. 각 단계가 이전 단계의 발견에 의존한다면 그 작업은 메인 스레드에 두어야 합니다. 하지만 답만 필요하고 과정은 상관없다면 위임하세요.

  • 과정의 중계가 아니라 결과가 필요할 때
  • 탐색 작업이 메인 스레드의 컨텍스트를 어지럽힐 때
  • 신선한 관점이나 커스텀 시스템 프롬프트가 도움이 될 때

① 리서치 작업 — 전형적 사례

낯선 코드베이스에서 인증(authentication)이 어떻게 동작하는지 조사한다고 합시다. 메인 스레드는 JWT가 어디서 검증되는지는 알아야 하지만, 그 과정에서 검색된 모든 파일을 볼 필요는 없습니다. 리서치 서브에이전트가 수십 개 파일을 읽고 함수 호출을 추적한 뒤, 깔끔한 요약만 돌려줍니다.

JWT validation happens in middleware/auth.js line 42,
called from the Express router in route/api.js

② 코드 리뷰

Claude는 코드가 다른 사람이 작성한 것으로 제시될 때 더 효과적으로 리뷰합니다. 메인 스레드와 여러 턴에 걸쳐 기능을 만든 뒤 같은 스레드에 리뷰를 시키면, Claude가 그 코드 작성에 관여했기에 신선한 눈으로 보기 어려워 약한 피드백이 나옵니다.

리뷰어 서브에이전트는 별도 컨텍스트에서 변경을 봅니다. git diff를 돌리고 수정된 파일을 읽어, 코드가 어떻게 쓰였는지의 이력 없이 리뷰 기준을 적용합니다. 시스템 프롬프트에 프로젝트별 리뷰 표준을 넣어 팀 전체에 일관된 기준을 강제할 수도 있습니다.

③ 커스텀 시스템 프롬프트

Claude Code의 기본 시스템 프롬프트는 간결하고 코드 중심의 응답을 강조합니다. 코딩엔 훌륭하지만 모든 것에 맞진 않습니다. 커스텀 프롬프트가 서브에이전트를 메인 스레드보다 정말 낫게 만드는 두 사례:

서브에이전트커스텀 프롬프트의 가치
카피라이팅톤·독자·스타일 지침을 부여. 기본 프롬프트의 간결한 기술 문체는 랜딩 페이지·이메일 캠페인에 안 맞음.
스타일링디자인 시스템 파일을 가리켜 둠. 실행 시 그 파일이 자동 로드되어 컬러 변수·간격 규칙·컴포넌트 패턴을 CSS 작성 전에 이미 앎.

서브에이전트가 해가 될 때 — 안티패턴

서브에이전트를 띄우는 오버헤드(가시성 상실 + 발견 압축)는 메인 스레드가 할 수 없는 일을 할 때만 값어치를 합니다. 흔한 안티패턴 셋:

안티패턴왜 문제인가
전문가 페르소나"당신은 Python 전문가" 같은 프롬프트는 무가치. Claude가 이미 그 지식을 가짐 — 메인 스레드가 직접 못 할 게 없음.
순차 파이프라인재현→디버그→수정처럼 단계가 이전 발견에 의존하는 흐름은 핸드오프에서 정보가 유실됨. 파이프라인은 작업이 진짜 독립적일 때만 통함.
테스트 러너필요한 정보를 숨김. 테스트 실패 시 전체 출력이 필요한데 "tests failed"만 돌려주면 디버그 스크립트를 또 만들어야 함. 테스트상 모든 구성 중 가장 나쁜 성능.

결정 규칙

"중간 작업이 중요한가?" 하나만 물으세요. 아니오(최종 결과만 필요) → 서브에이전트에 위임. 예(과정을 보고 반응해야) → 메인 스레드에 유지.

쓸 것: 리서치·탐색, 코드 리뷰, 커스텀 시스템 프롬프트가 필요한 작업. 피할 것: 실제 역량을 더하지 못하는 "전문가" 페르소나, 각 단계가 이전에 의존하는 다단계 파이프라인, 전체 출력이 필요한 테스트 실행.
