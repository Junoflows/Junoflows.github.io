Getting started · 레슨 01

시작하기

🎬 영상

이 코스는 MCP(Model Context Protocol)의 고급 주제를 다룹니다. 기본 도구·리소스·프롬프트를 넘어, 서버가 클라이언트의 능력을 빌려 쓰는 샘플링(sampling), 오래 걸리는 작업의 로그·진행 알림(notifications), 로컬 파일 접근을 통제하는 루트(roots), 그리고 이 모든 것을 실어 나르는 전송 계층(transport)(STDIO·StreamableHTTP)까지 파고듭니다.

  • Sampling — 서버가 클라이언트를 통해 Claude를 호출
  • Notifications — 진행 상황·로그를 실시간으로 전달
  • Roots — 허용된 폴더로 파일 접근 범위를 제한
  • Transports — JSON 메시지가 오가는 통로(STDIO / StreamableHTTP)
각 개념 레슨 뒤에는 실제 예제 프로젝트를 단계별로 훑는 walkthrough가 이어집니다. 코드를 실행하기보다 구조를 이해하는 데 목적이 있습니다.

Sampling · 레슨 02

Sampling

🎬 영상

Sampling은 서버가 연결된 MCP 클라이언트를 통해 Claude 같은 언어 모델에 접근하게 합니다. 서버가 Claude를 직접 호출하는 대신, 클라이언트에게 대신 호출해 달라고 요청합니다. 이렇게 하면 텍스트 생성의 책임과 비용이 서버에서 클라이언트로 이동합니다.

Sampling이 해결하는 문제

위키피디아에서 정보를 가져오는 리서치 도구가 있는 MCP 서버를 상상해 보세요. 데이터를 모은 뒤 그것을 하나의 리포트로 요약해야 합니다. 두 가지 선택지가 있습니다.

옵션 1 — MCP 서버에 Claude를 직접 붙입니다. 서버가 자체 API 키를 갖고, 인증을 처리하고, 비용을 관리하고, Claude 통합 코드를 모두 구현해야 합니다. 동작은 하지만 복잡도가 크게 늘어납니다.

옵션 2 — Sampling을 씁니다. 서버는 프롬프트를 만들고 클라이언트에게 "Claude를 대신 불러줄 수 있어?"라고 묻습니다. 이미 Claude와 연결된 클라이언트가 호출하고 결과를 돌려줍니다.

동작 방식

흐름은 단순합니다.

  • 서버가 자기 일을 마침(예: 위키피디아 아티클 가져오기)
  • 서버가 텍스트 생성을 요청하는 프롬프트를 만듦
  • 서버가 클라이언트에 sampling 요청을 보냄
  • 클라이언트가 제공된 프롬프트로 Claude를 호출
  • 클라이언트가 생성된 텍스트를 서버로 반환
  • 서버가 그 텍스트를 자신의 응답에 사용

Sampling의 이점

  • 서버 복잡도 감소 — 서버가 언어 모델과 직접 통합할 필요가 없음
  • 비용 부담 이동 — 토큰 비용은 서버가 아니라 클라이언트가 냄
  • API 키 불필요 — 서버가 Claude 자격 증명을 가질 필요 없음
  • 공개 서버에 최적 — 공개 서버가 모든 사용자의 AI 비용을 떠안게 두고 싶지 않음

구현 — 서버 측

도구 함수 안에서 create_message로 텍스트 생성을 요청합니다.

@mcp.tool()
async def summarize(text_to_summarize: str, ctx: Context):
prompt = f"""
Please summarize the following text:
{text_to_summarize}
"""

result = await ctx.session.create_message(
messages=[
SamplingMessage(
role="user",
content=TextContent(
type="text",
text=prompt
)
)
],
max_tokens=4000,
system_prompt="You are a helpful research assistant",
)

if result.content.type == "text":
return result.content.text
else:
raise ValueError("Sampling failed")

구현 — 클라이언트 측

서버의 요청을 처리할 sampling 콜백을 만듭니다.

async def sampling_callback(
context: RequestContext, params: CreateMessageRequestParams
):
# Call Claude using the Anthropic SDK
text = await chat(params.messages)

return CreateMessageResult(
role="assistant",
model=model,
content=TextContent(type="text", text=text),
)

그리고 클라이언트 세션을 초기화할 때 이 콜백을 넘깁니다.

async with ClientSession(
read,
write,
sampling_callback=sampling_callback
) as session:
await session.initialize()

언제 쓰나

Sampling은 공개 접근 가능한 MCP 서버를 만들 때 가장 유용합니다. 임의의 사용자가 내 비용으로 무제한 텍스트를 생성하는 걸 원치 않기 때문입니다. Sampling을 쓰면 각 클라이언트가 자신의 AI 사용료를 내면서도 서버의 기능은 그대로 누립니다.

이 기법은 본질적으로 AI 통합의 복잡성을 서버에서 클라이언트로 옮깁니다 — 클라이언트는 이미 필요한 연결과 자격 증명을 갖고 있는 경우가 많습니다.

Sampling · 레슨 03

Sampling 예제 훑어보기

실제 예제 프로젝트(server.py · client.py)를 열어 sampling이 어떻게 조립되는지 단계별로 살펴보는 인터랙티브 walkthrough입니다. 코드를 실행하지 않고 구조만 이해하는 게 목적입니다.

  1. Sampling 시작 — 서버의 도구 호출 중 create_message()를 실행해, 언어 모델에 보내고 싶은 메시지들을 전달합니다.
  2. Sampling 콜백 — 클라이언트에는 sampling 콜백을 구현해야 하며, 서버가 준 메시지 목록을 받습니다.
  3. 메시지 포맷 — 서버가 준 메시지는 MCP 통신용으로 포맷되어 있어, 사용 중인 LLM SDK와 반드시 호환되진 않습니다. 예를 들어 Anthropic SDK를 쓴다면 MCP 메시지를 Anthropic SDK 포맷으로 바꾸는 변환 로직을 조금 작성해야 합니다.
  4. 생성된 텍스트 반환 — LLM으로 텍스트를 생성한 뒤 CreateMessageResult(생성된 텍스트 포함)를 반환합니다.
  5. 콜백 연결 — 클라이언트의 콜백은 ClientSession 호출에 반드시 넘겨줘야 합니다.
  6. 결과 받기 — 클라이언트가 생성·반환한 텍스트가 서버로 전달되면, 이를 도구 워크플로우에 쓰거나 / 또 다른 sampling 호출을 하거나 / 그대로 반환할 수 있습니다.
핵심 · 클라이언트의 chat()은 MCP SamplingMessage 목록을 순회하며 role·text를 Anthropic SDK가 이해하는 {"role", "content"} 형태로 변환한 뒤 anthropic_client.messages.create(...)를 호출합니다.

Notifications · 레슨 04

로그와 진행 알림

🎬 영상

로그와 진행 알림(logging & progress notifications)은 구현은 간단하지만 MCP 서버의 사용자 경험을 크게 개선합니다. 오래 걸리는 작업 동안 "혹시 멈춘 건 아닌가" 하는 불안 없이, 지금 무슨 일이 일어나는지 알 수 있게 해줍니다.

Claude가 리서치나 데이터 처리처럼 시간이 걸리는 도구를 호출하면, 보통 사용자는 작업이 끝날 때까지 아무것도 보지 못합니다. 알림을 켜면 진행 바·상태 메시지·상세 로그를 실시간으로 볼 수 있습니다.

동작 방식

Python MCP SDK에서 로그·진행 알림은 도구 함수에 자동 제공되는 Context 인자를 통해 동작합니다. 이 컨텍스트 객체가 실행 중 클라이언트로 다시 소통할 메서드를 제공합니다.

@mcp.tool(
name="research",
description="Research a given topic"
)
async def research(
topic: str = Field(description="Topic to research"),
*,
context: Context
):
await context.info("About to do research...")
await context.report_progress(20, 100)
sources = await do_research(topic)

await context.info("Writing report...")
await context.report_progress(70, 100)
results = await generate_report(sources)

return results
  • context.info() — 클라이언트에 로그 메시지 전송
  • context.report_progress() — 현재값/전체값으로 진행 상황 갱신

클라이언트 측 구현

클라이언트에서는 이 알림들을 처리할 콜백을 설정합니다. 서버는 메시지를 방출하고, 어떻게 사용자에게 보여줄지는 클라이언트가 결정합니다.

async def logging_callback(params: LoggingMessageNotificationParams):
print(params.data)

async def print_progress_callback(
progress: float, total: float | None, message: str | None
):
if total is not None:
percentage = (progress / total) * 100
print(f"Progress: {progress}/{total} ({percentage:.1f}%)")
else:
print(f"Progress: {progress}")

async def run():
async with stdio_client(server_params) as (read, write):
async with ClientSession(
read,
write,
logging_callback=logging_callback
) as session:
await session.initialize()

await session.call_tool(
name="add",
arguments={"a": 1, "b": 3},
progress_callback=print_progress_callback,
)

로그 콜백은 세션 생성 시, 진행 콜백은 개별 도구 호출 시 넘깁니다. 덕분에 알림 종류별로 다르게 처리할 유연성이 생깁니다.

표현 방식

  • CLI 앱 — 메시지와 진행을 터미널에 그냥 출력
  • 웹 앱 — WebSocket·SSE·폴링으로 브라우저에 푸시
  • 데스크톱 앱 — UI의 진행 바·상태 표시 갱신
이 알림 구현은 전적으로 선택 사항입니다. 완전히 무시하거나, 일부만 보여주거나, 앱에 맞게 마음대로 표현해도 됩니다 — 순수하게 UX 향상용입니다.

Roots · 레슨 06

Roots

🎬 영상

Roots는 MCP 서버에게 로컬 머신의 특정 파일·폴더 접근을 허용하는 방법입니다. "이 파일들엔 접근해도 돼"라고 말해주는 권한 시스템이라고 생각하면 되지만, 단순한 권한 부여 이상의 역할을 합니다.

Roots가 해결하는 문제

Roots가 없으면 흔한 문제에 부딪힙니다. MP4를 MOV로 변환하는, 파일 경로를 받는 영상 변환 도구가 달린 MCP 서버를 상상해 보세요.

사용자가 Claude에게 "biking.mp4를 mov로 변환해줘"라고 하면, Claude는 파일명만으로 도구를 호출합니다. 그런데 문제는 — Claude가 파일 시스템 전체를 뒤져 그 파일이 실제로 어디 있는지 찾을 방법이 없다는 것입니다.

파일 시스템은 여러 디렉터리에 파일이 흩어진 복잡한 구조일 수 있습니다. 사용자는 biking.mp4가 Movies 폴더에 있다는 걸 알지만 Claude는 그 맥락이 없습니다. 매번 전체 경로를 입력하게 하면 되지만, 아무도 그러고 싶어 하지 않습니다.

Roots가 있을 때의 흐름

  • 사용자가 영상 파일 변환을 요청
  • Claude가 list_roots로 접근 가능한 디렉터리를 확인
  • Claude가 read_dir로 접근 가능한 디렉터리에서 파일을 탐색
  • 찾으면 전체 경로로 변환 도구를 호출

이 과정이 자동으로 일어나므로, 사용자는 여전히 "biking.mp4 변환해줘"라고만 하면 됩니다.

보안과 경계

Roots는 접근을 제한해 보안도 제공합니다. Desktop 폴더만 허용하면 MCP 서버는 Documents·Downloads 같은 다른 위치의 파일에 접근할 수 없습니다. 승인된 roots 밖의 파일에 접근을 시도하면 오류가 나고, 서버는 현재 구성에서 그 파일에 접근할 수 없음을 사용자에게 알릴 수 있습니다.

구현 세부

MCP SDK는 root 제한을 자동으로 강제하지 않습니다 — 직접 구현해야 합니다. 전형적인 패턴은 is_path_allowed() 같은 헬퍼 함수를 만드는 것입니다.

  • 요청된 파일 경로를 받음
  • 승인된 roots 목록을 가져옴
  • 요청 경로가 그중 하나에 속하는지 확인
  • 접근 허용 여부를 true/false로 반환

파일·디렉터리에 접근하는 모든 도구에서, 실제 파일 작업 전에 이 함수를 호출합니다.

핵심 이점

  • 사용자 친화적 — 전체 경로를 입력할 필요 없음
  • 탐색 집중 — 승인된 디렉터리만 보므로 파일 검색이 빠름
  • 보안 — 승인 영역 밖 민감 파일 접근을 방지
  • 유연성 — roots를 도구로 제공하거나 프롬프트에 직접 주입 가능

JSON 메시지 타입

🎬 영상

MCP는 클라이언트와 서버 사이의 통신을 JSON 메시지로 처리합니다. 이 메시지 타입들을 이해하는 건 MCP 작업에 필수이며, 특히 StreamableHTTP 같은 서로 다른 전송 방식을 다룰 때 중요합니다.

메시지 포맷

모든 MCP 통신은 JSON 메시지로 일어납니다. 각 타입은 도구 호출, 리소스 목록 조회, 시스템 이벤트 알림 등 특정 목적을 갖습니다.

전형적인 예: Claude가 MCP 서버가 제공하는 도구를 호출해야 하면, 클라이언트가 "Call Tool Request" 메시지를 보냅니다. 서버가 처리·실행 후 결과를 담은 "Call Tool Result" 메시지로 응답합니다.

MCP 명세

전체 메시지 타입 목록은 GitHub의 공식 MCP 명세 저장소에 정의돼 있습니다. 이 명세는 각종 SDK 저장소(Python·TypeScript 등)와 별개이며, MCP가 어떻게 동작해야 하는지에 대한 권위 있는 출처입니다. 메시지 타입은 편의상 TypeScript로 쓰여 있는데 — 실행되는 코드라서가 아니라, TypeScript가 데이터 구조와 타입을 명확히 기술하기 때문입니다.

메시지 두 범주

범주설명
Request-Result항상 쌍으로 옴 — 요청을 보내고 결과를 기대. Call Tool, List Prompts, Read Resource, Initialize 등.
Notification응답이 필요 없는 단방향 메시지 — Progress, Logging Message, Tool List Changed, Resource Updated 등.

클라이언트 vs 서버 메시지

명세는 누가 보내느냐로 메시지를 나눕니다. 클라이언트 메시지는 클라이언트가 서버에 보내는 요청(도구 호출 등)과 알림이고, 서버 메시지는 서버가 클라이언트에 보내는 요청과 서버가 방송하는 알림입니다.

핵심 통찰: MCP는 양방향 프로토콜이라 클라이언트와 서버 모두 통신을 개시할 수 있습니다. 서버가 클라이언트에 메시지를 보낼 수 있다는 점은, 일부 전송 방식(예: StreamableHTTP)이 어떤 방향의 메시지를 제한하는지 고를 때 특히 중요해집니다.

STDIO 전송

🎬 영상

MCP 클라이언트와 서버는 JSON 메시지를 주고받지만, 이 메시지가 실제로 어떻게 전달될까요? 통신 채널을 전송(transport)이라 하며, HTTP 요청부터 WebSocket까지(심지어 엽서에 JSON을 적는 것까지 — 프로덕션엔 비추천) 여러 방식이 있습니다.

STDIO 전송

MCP 서버·클라이언트를 처음 개발할 때 가장 흔히 쓰는 건 STDIO 전송입니다. 클라이언트가 MCP 서버를 서브프로세스로 띄우고, 표준 입력·출력 스트림으로 통신합니다.

  • 클라이언트는 서버의 stdin으로 메시지를 보냄
  • 서버는 stdout에 써서 응답
  • 서버든 클라이언트든 언제든 메시지를 보낼 수 있음
  • 같은 머신에서 실행될 때만 동작

터미널에서 직접 보기

별도 클라이언트를 짜지 않고 터미널에서 MCP 서버를 직접 테스트할 수 있습니다. uv run server.py로 실행하면 서버가 stdin을 듣고 stdout에 씁니다. 즉, JSON 메시지를 터미널에 붙여넣고 서버 응답을 즉시 볼 수 있습니다.

MCP 연결 시퀀스

모든 MCP 연결은 세 메시지 핸드셰이크로 시작해야 합니다.

  • Initialize Request — 클라이언트가 먼저 보냄
  • Initialize Result — 서버가 자기 능력(capabilities)으로 응답
  • Initialized Notification — 클라이언트가 확인(응답 불필요)

이 핸드셰이크 이후에야 도구 호출·프롬프트 목록 같은 다른 요청을 보낼 수 있습니다.

메시지 흐름

어떤 메시지는 응답을 요구하고(요청 → 결과), 어떤 건 아닙니다(알림). 클라이언트와 서버 모두 언제든 통신을 개시할 수 있습니다.

네 가지 통신 시나리오

  • 클라이언트 → 서버 요청: 클라이언트가 stdin에 씀
  • 서버 → 클라이언트 응답: 서버가 stdout에 씀
  • 서버 → 클라이언트 요청: 서버가 stdout에 씀
  • 클라이언트 → 서버 응답: 클라이언트가 stdin에 씀
STDIO의 아름다움은 단순함입니다 — 두 채널만으로 어느 쪽이든 언제든 통신을 개시할 수 있어, 완전한 양방향 통신의 "이상적" 기준이 됩니다. HTTP로 옮겨가면 서버가 항상 클라이언트에 요청을 개시할 수 없는 제약을 만납니다. 개발·테스트엔 STDIO가 완벽하지만, 서로 다른 머신에서 돌려야 하는 프로덕션엔 다른 전송을 고려해야 합니다.

StreamableHTTP 전송

🎬 영상

StreamableHTTP 전송은 MCP 클라이언트가 원격 호스팅된 서버에 HTTP로 연결하게 합니다. 클라이언트·서버가 같은 머신에 있어야 하는 STDIO와 달리, 누구나 접근할 수 있는 공개 MCP 서버의 가능성을 엽니다.

다만 중요한 함정이 있습니다. 일부 설정이 서버 기능을 크게 제한할 수 있습니다. 로컬 STDIO에선 완벽하던 앱이 HTTP 전송으로 배포하자 깨진다면, 이 설정이 원인일 가능성이 높습니다.

중요한 설정 두 가지

  • stateless_http — 연결 상태 관리를 제어
  • json_response — 응답 포맷 처리를 제어

기본값은 둘 다 false지만, 특정 배포 시나리오는 true로 강제할 수 있습니다. 켜지면 진행 알림·로깅·서버 개시 요청 같은 핵심 기능이 깨질 수 있습니다.

HTTP 통신의 난제

  • 클라이언트는 서버에 쉽게 요청을 개시할 수 있음(서버 URL이 알려져 있음)
  • 서버는 그 요청에 쉽게 응답할 수 있음
  • 서버가 클라이언트에 요청을 개시하긴 어려움(클라이언트 URL이 없음)
  • 클라이언트에서 서버로 돌아가는 응답 패턴이 까다로워짐

영향받는 MCP 메시지 타입

  • 서버 개시 요청: Create Message 요청, List Roots 요청
  • 알림: Progress, Logging, Initialized, Cancelled 알림

제한적 HTTP 설정을 켜면 바로 이 기능들이 깨집니다 — 진행 바가 사라지고, 로깅이 멈추고, 서버 개시 sampling 요청이 실패합니다.

StreamableHTTP의 해법

StreamableHTTP는 HTTP의 한계를 우회하는 영리한 해법을 제공하지만 트레이드오프가 따릅니다. stateless_http=True나 json_response=True로 강제되면, 우회하는 대신 HTTP의 제약 안에서 동작하라고 전송에 지시하는 셈입니다.

서버 개시 요청이나 실시간 알림에 크게 의존한다면, 전송 선택을 다시 고민하거나 대체 통신 패턴을 구현해야 할 수 있습니다. 핵심은 이 제약이 존재함을 알고 아키텍처를 그에 맞게 설계하는 것입니다.

StreamableHTTP 심화

🎬 영상

StreamableHTTP는 MCP의 근본 문제 — 일부 기능은 서버가 클라이언트에 요청을 보내야 하는데 HTTP는 이를 어렵게 만든다 — 에 대한 해법입니다. 이 우회가 어떻게 동작하고, 언제 그 우회를 깨야 하는지 살펴봅니다.

핵심 문제

sampling·알림·로깅 같은 기능은 서버가 클라이언트에 요청을 개시하는 데 의존합니다. 그러나 HTTP는 클라이언트가 서버에 요청하도록 설계돼 그 반대가 아닙니다. StreamableHTTP는 Server-Sent Events(SSE)를 이용한 영리한 우회로 이를 해결합니다.

초기 연결 설정

  • 클라이언트가 Initialize Request를 보냄
  • 서버가 특별한 mcp-session-id 헤더를 포함한 Initialize Result로 응답
  • 클라이언트가 세션 ID를 담아 Initialized Notification을 보냄

이 세션 ID는 클라이언트를 유일하게 식별하며, 이후 모든 요청에 포함돼야 합니다.

SSE 우회

초기화 후 클라이언트는 GET 요청으로 SSE 연결을 맺습니다. 이는 장수하는 HTTP 응답을 만들어, 서버가 언제든 메시지를 스트리밍해 돌려보낼 수 있게 합니다. 이 SSE 연결이 서버→클라이언트 통신의 핵심입니다.

도구 호출과 이중 SSE 연결

  • 주 SSE 연결 — 서버 개시 요청용, 무기한 열려 있음
  • 도구별 SSE 연결 — 각 도구 호출마다 생성, 도구 결과 전송 시 자동 종료

메시지 라우팅

  • 진행 알림 — 주 SSE 연결로 전송
  • 로그 메시지·도구 결과 — 도구별 SSE 연결로 전송

우회를 깨는 설정 플래그

stateless_http와 json_response를 True로 두면 SSE 우회 메커니즘이 깨질 수 있습니다. 특정 시나리오에선 켜고 싶을 수 있지만, 서버→클라이언트 통신에 의존하는 완전한 MCP 기능이 제한됩니다.

StreamableHTTP는 HTTP의 한계를 우회해야 하므로 다른 전송보다 복잡합니다. 초기화 이후 모든 요청에 세션 ID가 필요하고, 시스템이 여러 SSE 연결을 자동 관리한다는 점 — 이 이중 연결 모델을 이해하는 것이 디버깅·최적화의 핵심입니다.

State와 StreamableHTTP

🎬 영상

MCP 서버의 stateless_http·json_response 플래그는 서버 동작의 근본을 제어합니다. 언제·왜 쓰는지 이해하는 건, 특히 서버를 스케일링하거나 프로덕션에 배포할 계획이라면 매우 중요합니다.

Stateless HTTP가 필요해지는 때

MCP 서버가 인기를 얻는다고 상상해 보세요. 처음엔 단일 서버 인스턴스에 몇몇 클라이언트만 붙습니다.

수천 클라이언트가 연결을 시도하면 단일 인스턴스로는 감당이 안 됩니다.

전형적 해법은 수평 확장 — 로드 밸런서 뒤에 여러 서버 인스턴스를 두는 것입니다.

여기서 복잡해집니다. MCP 클라이언트는 두 개의 연결이 필요합니다.

  • 서버→클라이언트 요청을 받는 GET SSE 연결
  • 도구 호출·응답을 위한 POST 요청

로드 밸런서에선 이 요청들이 서로 다른 인스턴스로 라우팅될 수 있습니다. 도구가 sampling으로 Claude를 써야 하면, POST를 처리하는 서버가 GET SSE를 처리하는 서버와 조율해야 하는 복잡한 문제가 생깁니다.

Stateless HTTP가 해결하는 방식

stateless_http=True는 이 조율 문제를 없애지만 큰 대가가 따릅니다.

  • 클라이언트가 세션 ID를 못 받음 — 서버가 개별 클라이언트를 추적 못 함
  • 서버→클라이언트 요청 불가 — GET SSE 경로가 사라짐
  • sampling 불가 — Claude 등 AI 모델을 못 씀
  • 진행 보고 불가 — 긴 작업 중 진행 업데이트 못 보냄
  • 구독 불가 — 리소스 갱신 알림 못 보냄

다만 한 가지 이점: 클라이언트 초기화가 더 이상 필요 없습니다. 초기 핸드셰이크 없이 바로 요청할 수 있습니다.

JSON Response 이해하기

json_response=True는 더 단순합니다 — POST 응답의 스트리밍을 끕니다. 도구 실행 중 여러 SSE 메시지를 받는 대신, 최종 결과만 평범한 JSON으로 받습니다(중간 진행 메시지·실행 중 로그 없음).

언제 쓰나

stateless HTTPjson response

개발 vs 프로덕션 · 로컬에선 STDIO로 개발하더라도 배포에 쓸 전송으로 테스트하세요. stateful/stateless 모드의 동작 차이는 클 수 있어, 배포 후가 아니라 개발 중에 문제를 잡는 편이 낫습니다.

Wrapping up · 레슨 13

마무리

🎬 영상

이 코스에서는 MCP의 고급 패턴을 두루 살펴봤습니다. 서버가 클라이언트를 통해 Claude를 호출하는 sampling, 오래 걸리는 작업의 로그·진행 알림, 파일 접근을 통제하는 roots, MCP 통신의 언어인 JSON 메시지 타입, 그리고 그것을 실어 나르는 두 전송(STDIO·StreamableHTTP)까지 다뤘습니다.

  • Sampling · 비용·복잡성을 클라이언트로 이동
  • Notifications · 진행·로그로 UX 개선(선택 사항)
  • Roots · 사용자 친화성과 보안을 동시에
  • Transports · STDIO는 이상적 양방향, StreamableHTTP는 SSE로 우회 — 단 stateless_http·json_response가 기능을 제한
가장 중요한 교훈: 서버 개시 통신이 필요한 기능(sampling·알림)은 전송과 설정에 민감합니다. 배포 환경과 스케일링 요구를 먼저 정하고, 그에 맞춰 전송·플래그를 선택하세요.
