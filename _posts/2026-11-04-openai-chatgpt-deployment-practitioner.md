### 통합 최종 정리 — ChatGPT 배포 실무 전문가

#### 요약
ChatGPT 배포 실무 전문가는 "라이선스는 샀는데 이제 무엇을 하지?"라는 상황을 하나의 워크플로, 하나의 첫 코호트, 근거로 판단하는 결정 시점으로 바꾸는 과정이다. 영업 인계를 증거와 가정으로 나눠 배포 개요서를 쓰고(1강), KPI와 30일 출시 계획을 갖춘 성공 계획으로 만든다(2강).

계획을 워크스페이스 요구 사항으로 옮겨 항목마다 준비 상태와 담당자를 붙이고(3강), 후보 워크플로를 품질 기준과 우선순위 점수로 골라 활성화 계획을 세운다(4강). 이어 대상별 역량 강화와 챔피언, 지원 체계로 사용자가 실제 업무에서 워크플로를 반복하게 만든다(5강).

활성화 증거를 계획과 비교해 계속, 조정, 확장, 일시 중지 중 하나를 권고하고(6강), 확장 기준과 거버넌스, 위험 완화를 갖춘 조직 확장 전략을 제안한다(7강). 마지막으로 Kestrel Manufacturing 역할극에서 이 흐름을 고객 대화로 연습한다(8강).

#### 과정 전체 흐름
```
[1강] 영업 인계 → 증거 3구분 → 시작 조치 → 배포 개요서
   │
   └─▶ [2강] 비전·범위 → 출시 책임 → KPI → 30일 계획
          │
          ├─▶ [3강] 구성 종속성 → 소유권 → 준비 상태 4종
          └─▶ [4강] 후보 평가 → 우선순위 점수 → 활성화 계획
                 │
                 └─▶ [5강] 대상별 역량 강화 → 커뮤니케이션 → 챔피언·지원
                        │
                        └─▶ [6강] 도입·성공 신호 → 근본 원인 → 다음 단계 권고
                               │
                               └─▶ [7강] 확장 기준 → 소유권·거버넌스 → 위험 완화
                                      │
[8강] Kestrel 역할극: 첫 워크플로·코호트 → 준비 격차 → 확장 조건
```

#### 강의별 핵심
- **1강 기회 → 배포 계획:** 인계를 확인된 증거, 합리적 가정, 알 수 없는 사항으로 나누고, 증거에 맞는 시작 조치를 고른다.
- **2강 성공을 위한 계획:** 비전과 범위, 책임, KPI 7범주, 30일 계획을 잇고, 기준선이 없어도 방향성 증거로 진행한다.
- **3강 워크스페이스 설정:** "사용자 확인됨 ≠ 접근 준비됨". 항목마다 준비됨, 검증 필요, 차단됨, 보류와 담당자를 붙인다.
- **4강 활성화용 사용 사례:** 기능이 아닌 워크플로로 정의해 품질 6기준과 점수로 고르되, 차단 요인은 평균으로 덮지 않는다.
- **5강 역량 강화·도입 촉진:** 대상별 학습 요건과 커뮤니케이션 4목표, 챔피언과 지원 체계로 역할별 승인 워크플로를 정착시킨다.
- **6강 활성화·측정·확장:** 도입 신호와 성공 신호를 구분하고, 장벽을 근본 원인으로 나눠 계속, 조정, 확장, 일시 중지를 고른다.
- **7강 조직 확장:** 확장 기준 6가지와 소유권, 거버넌스, 지원 경로를 갖추고, 위험마다 조치와 책임자, 검토 증거를 붙인다.
- **8강 실습(역할극):** Kestrel COO와 세 번 대화하며 운영 팀의 지식 검색·절차 요약 하나로 시작하고, 에이전트 자동 게시는 보류한다.

#### 강의를 잇는 연결 고리

| 개념 | 계획(1–2강) | 준비(3–4강) | 도입(5강) | 측정·확장(6–7강) | 역할극(8강) |
|---|---|---|---|---|---|
| 출발점 | 증거 3구분, 배포 문제 정의 | 승인된 성공 계획 | 승인된 활성화 워크플로 | 활성화 증거 vs 계획 | "이제 뭘 하지" |
| 범위 | 범위 경계, 첫 코호트 | 준비 상태 4종 | 활성화 대상 그룹 | 다음 확장 영역 | 워크플로 1개, 코호트 1개 |
| 책임 | 이해관계자, 출시 팀 | 소유권 8역할 | 관리자, 챔피언, L&D | 소유권 6요소 | Dana 출처·접근, Robert 검토 |
| 증거 | KPI 7범주, 증거 맵 | 품질 6기준, 우선순위 점수 | 도입 신호, 피드백 경로 | 도입·성공 신호, 초기 가치 | 도입, 품질, 가치, 리스크 |
| 거버넌스 | 거버넌스 가정과 격차 | 데이터 범위, 사람 검토 | 허용 사용 교육 | 거버넌스 작동 증거 | 에이전트 쓰기 작업 보류 |
| 산출물 | 배포 개요서, 성공 계획 | 준비 체크리스트, 활성화 계획 | 역량 강화·도입 계획 | 활성화 검토, 확장 전략 | 집중된 배포 권고안 |

#### 실무 체크리스트
- ☐ 인계 내용을 확인된 증거, 합리적 가정, 알 수 없는 사항으로 나눴는가
- ☐ 첫 워크플로, 첫 코호트, 결과 책임자, 제외 범위를 한 문장으로 말할 수 있는가
- ☐ KPI마다 근거와 책임자, 검토 시점이 있고 30일 검토의 결정이 정해져 있는가
- ☐ 워크스페이스 항목마다 준비 상태와 담당자를 붙였는가 (책임자 없으면 '준비됨' 아님)
- ☐ 사용 사례를 기능이 아니라 누가 무엇을 만들고 누가 검토하는지로 정의했는가
- ☐ 높은 점수에 가려진 차단 요인을 따로 다뤘는가
- ☐ 교육과 시연이 일반 기능이 아니라 승인된 워크플로 중심인가
- ☐ 사용률만이 아니라 산출물 품질, 검토 행동, 출처 준수를 함께 보았는가
- ☐ 장벽을 근본 원인으로 나누고 조치, 책임자, 다음 증거를 적었는가
- ☐ 확장 전에 같은 워크플로와 검토 모델이 다른 대상에서도 성립하는지와 지원 역량을 확인했는가

> **한 줄 요약:** 영업 인계를 증거와 가정으로 나눠 배포 문제, 범위, 책임자를 정하고, 증거에 맞는 시작 조치를 배포 개요서로 묶는다.

### 핵심 내용
#### 배포 시작점과 인계 점검
- 검증된 기회라도 자동으로 배포 계획 단계로 넘어가지 않는다. 배포 팀은 출시 계획 전에 인계 내용을 검토한다.
- 배포는 접근 권한 부여가 아니라, 맥락과 책임, 검토로 실제 워크플로 안에서 AI를 쓰게 돕는 일이다.
- **배포 준비 원칙:** 조치를 실행하기 전에 근거를 확인한다. 관심과 긴급성은 추진력이지 준비 완료의 증거가 아니다.
- 인계 자료에는 확인된 증거, 합리적 가정, 알 수 없는 사항이 섞여 있다. 고객에게 약속하기 전에 분리한다.
- **ABC 습관:** 아무것도 가정하지 말고, 믿지 말고, 모든 것을 확인한다. 영업 불신이 아니라 약속의 근거를 찾는 것이다.

#### 문제·워크플로·성공 기준으로 전환
- 배포 문제 정의는 현재 마찰, ChatGPT 지원 워크플로, 개선할 성과를 연결한다. 최종 솔루션을 과약속하지 않는다.
- "고객 성공팀 업무 시간 단축" 같은 판매자 수준 문장에는 워크플로, 사용자, 책임자, 성공 증거가 빠져 있다.
- 첫 워크플로는 실행 가능할 만큼 구체적이고, 책임 팀이 있고, 측정 가능하며, 통제된 시작이 될 만큼 좁아야 한다.
- 성공 기준은 최종 ROI 약속이 아니라, 첫 조치 후 진행이나 범위 재조정을 결정하게 돕는 계획 목표다.
- 일반 생산성 주장, 근거 없는 ROI, 의사 결정 완전 자동화 약속 같은 표현은 피한다.

#### 이해관계자·범위·거버넌스 확인
- 후원자가 있는 것만으로는 부족하다. 시범 운영 검토 같은 중요한 결정 시점에 실제로 참여하는지 확인한다.
- 개요서에는 결정권자, 필요한 결정, 결정 시점, 결정에 쓸 근거를 담는다.
- 저위험의 좁은 워크플로는 거버넌스 참여를 낮출 수 있지만, 규제나 정책에 민감한 워크플로는 더 깊은 검토가 필요하다.
- 핵심은 **가시성**이다. 미해결 책임은 숨기지 말고 격차나 종속성으로 적는다.
- 과도한 범위의 신호는 기능 과다, 광범위한 사용자 그룹, 미확인 소스 접근, 소유자 없는 워크스페이스 등이다.

#### 시작 조치 선택과 배포 개요서
- 첫 조치는 배울 수 있을 만큼 좁고, 의미 있을 만큼 신뢰할 수 있어야 한다.
- 제약은 지금 다 풀지 않는다. 이미 해결, 계획 중 관리 가능, 집중 검증 필요, 범위 재조정 필요 중 어디인지 판정한다.
- "준비 상태 결정"과 "실행 구조"를 혼동하지 않는다. 진행이 확정된 뒤에만 시범 운영 같은 구조를 정한다.
- **배포 개요서**는 전체 롤아웃 계획이 아니라 아는 것, 검증할 것, 권장 조치, 다음 단계를 알려 주는 시작 문서다.
- 상세 워크스페이스 설정, 전체 활성화 계획, 입증되지 않은 가치 주장은 개요서에서 뺀다.
- 테스트: 배포 담당자가 영업 내역을 다시 읽지 않고 다음 고객 상담을 계획할 수 있는가?

### 기억할 개념·프레임워크

| 증거 구분 | 의미 |
|---|---|
| 확인된 증거 | 고객이 명시, 동의, 문서화, 할당한 것 |
| 합리적 가정 | 타당하나 미검증 (초기 사용자, 예상 소스, 접근 경로 등) |
| 알 수 없는 사항 | 누락 이해관계자, 불분명한 소스 접근, 규제 요건 등 |

| 단계 | 선택지 | 사용 시점 |
|---|---|---|
| 준비 결정 | 진행 | 확인된 증거, 책임, 거버넌스 준비가 충분 |
| | 집중 검증 | 유망하나 한두 가지 구체 가정의 검증이 필요 |
| | 범위 재조정 | 너무 넓거나 책임이 불분명 |
| | 중단·연기 | 후원, 결정 시점, 승인 소스 같은 필수 조건 누락 |
| 실행 구조 | 시범 운영 | 워크플로는 명확하나 확대 전 증거 필요 |
| | 단계적 도입 | 코호트, 기능, 지역별로 순차 확대 |
| | 광범위한 배포 계획 | 워크플로, 책임, 범위가 모두 구체적 |

- **인계 품질 점검 6질문:** 어떤 업무가 바뀌나? 누가 먼저 쓰나? 결과 책임자는? 성공 모습은? 출시 전 무엇을 검증하나? 다음 단계는?
- **배포 문제 정의 5요소:** 워크플로 마찰점, 영향받는 사용자 그룹, 운영상 영향, 목표 워크플로, 비즈니스 성과.
- **범위 경계**는 포함과 제외를 함께 적는다.
  - 범위 내: 기업 CSM 갱신 브리프, 10~15명 CSM 코호트
  - 제외: 고객 PHI, 미승인 소스, 고객 대상 자동 커뮤니케이션
  - 보류: 자동 위험 점수, CRM 반영, 전사 확대
- **격차 4유형:** 책임 소재, 의사 결정, 범위, 거버넌스·소스 접근.

### 실무 적용 예시
- "CS팀 갱신 준비를 빠르게" → CSM이 흩어진 정보로 브리핑에 몇 시간을 쓰는 문제로 다시 정의한다.
  - 첫 워크플로는 승인된 계정 맥락으로 사람이 검토할 갱신 브리프 초안을 작성하는 것이다.
- 워크플로, 책임자, 소규모 코호트는 명확하나 소스 접근이 미해결 → 진행이 아니라 **집중 검증**을 고른다.
  - 승인 소스와 검토 기대가 확정되면 첫 계정 관리자 그룹으로 소규모 파일럿을 한다.
- "모든 계정 기획에 ChatGPT" → 아직 초기 사용 사례가 아니다. 워크플로, 사용자 그룹, 책임자를 하나씩으로 좁힌다.

### 지식 점검 포인트
- 경영진 관심만으로 빠른 출시를 원하는 고객 → **인계 자료로 사실과 가정, 검증 필요 사항을 확인한 뒤 시작 방안 제안**.
- "모든 지식 근로자 대상"이고 워크플로와 담당자가 미정인 인계 → **'사양 불충분'으로 표시하고 확인할 항목 파악**.
- 가장 배포 준비된 문제 정의 → **사용자, 마찰, 승인 맥락, 사람 검토가 모두 드러난 갱신 브리프 초안 워크플로**.
  - "생산성 향상"이나 "갱신 계획 자동화"는 너무 막연하다.
- 후원자는 있으나 첫 사용자 그룹, 관리자, 결정 시점이 불명 → **진행 전 해결하거나 드러낼 이해관계자·범위 격차**.
- 유망하나 사용자 그룹, 소스 접근, 가치 지표가 미정 → **파일럿 결정 전 집중 검증**.
- 성과 책임자, 범위 경계, 다음 결정 시점이 없는 개요서 → **계획으로 넘어갈 배포 준비 정보가 누락**.

> **한 줄 요약:** 배포 준비된 기회를 비전, 출시 범위, 책임, KPI, 거버넌스 가정, 30일 계획을 갖춘 배포 성공 계획으로 바꾼다.

### 핵심 내용
#### 성공 계획의 틀
- 배포 준비가 된 기회는 좋은 출발점이지만 아직 성공 계획은 아니다.
- **계획 원칙:** 모든 출시 조치를 워크플로, 담당자, KPI, 다음 결정 등 하나 이상과 연결한다.
- 체크리스트는 무슨 작업이 있는지만 말한다. 성공 계획은 왜 중요하고, 누가 하고, 어떤 결정을 돕는지 말한다.
- 어떤 질문과도 연결되지 않는 조치는 실행 계획 범위 밖이거나 이후 업무 흐름에 속한다.
- 계획이 끝나면 팀은 무엇을 먼저 출시하고, 누가 맡고, 30일 후 무엇을 결정할지 알아야 한다.

#### 배포 비전과 출시 범위
- **배포 비전**은 왜 배포하는지, 업무의 어디를 지원하는지, 첫 출시로 무엇을 입증할지를 간결하게 말한다.
  - 약함: "법무팀에 ChatGPT 출시"
  - 강함: 법무 운영팀의 계약 접수 요약을 사람이 검토하게 지원하고, 30일간 품질과 신뢰 증거를 수집
- 광범위한 AI 비전은 초기엔 자연스럽지만, 실행하고 측정하고 관리할 수 있는 워크플로로 구체화해야 한다.
- 출시 범위는 활성화할 만큼 좁되 가치를 입증할 만큼 의미 있어야 한다. 너무 넓으면 소유권과 통제를 잃는다.
- **범위 이탈**은 계획이 안정되기 전에 범위가 커지는 것이다. 야심차 보여도 측정과 지원이 어려워진다.

#### 출시 팀과 운영 리듬
- 소규모 배포에서는 한 사람이 여러 역할을 맡아도 되지만, 모든 핵심 책임에는 담당자가 있어야 한다.
- 흔한 실수는 이해관계자 이름만 나열하는 것이다. 역할마다 무엇을 결정, 검증, 에스컬레이션하는지 적는다.
  - 예: 워크스페이스 관리자는 접근 준비와 승인 소스 검증, 규정 준수 담당자는 민감 데이터 요건 검증.
- **운영 리듬**은 불필요한 프로젝트 관리 없이 책임을 드러내는 가벼운 주기다.

#### 성공 기준을 KPI로
- KPI는 "ChatGPT 사용량 증가"가 아니라, 정의된 사용자가 워크플로에서 실제로 도움을 받는지 테스트한다.
- **3단계 KPI 프로세스:** 가치 창출 요인 파악 → 기준선 설정 → 개선 측정 계획.
- 기준선이 없어도 계획은 멈추지 않는다. 검토자 추정, 샘플 결과 검토, 간단한 피드백으로 방향성 증거를 모은다.
- 고객이 관찰할 수 없는 KPI는 피한다. KPI마다 정의, 출처, 책임자, 검토 시점, 한계를 붙인다.
- 워크스페이스 분석은 도입과 참여의 증거일 뿐, 품질이나 인과적 ROI의 증거가 아니다.

#### 준비·거버넌스 가정과 30일 계획
- 거버넌스 기대는 보편 규칙이 아니라 **검증할 가정**으로 쓰고, 확인할 고객 측 담당자를 지정한다.
- ChatGPT Work나 Workspace Agent에 의존하면 가용성과 권한도 확인된 기능이 아니라 검증 대상으로 본다.
- 에스컬레이션은 막연한 불확실성이 아니라 구체적 장애 요인에 근거하고, 유발 요인과 담당자, 예상 대응을 적는다.
- 접근 설정 자체를 규정 준수로 간주하지 않는다. 규정 준수는 고객 담당자와 검증할 전제 조건이다.
- 30일 계획은 업무 목록이 아니라 준비 → 실행 → 피드백 → 다음 결정으로 나아가는 흐름이다.
- 4주차는 "결과 검토"로 끝내지 않는다. 누가 어떤 증거로 무엇을 결정하는지 적는다.
- **인계 메모**는 다음 팀이 계획을 다시 짜지 않고 바로 움직이게 한다. 관련 없는 요소를 억지로 넣지 않는다.

### 기억할 개념·프레임워크

| KPI 범주 | 확인 질문 |
|---|---|
| 도입률 | 대상 사용자가 시도하나 |
| 참여도 | 첫 노출 후에도 계속 쓰나 |
| 워크플로 산출물 | 의도한 초안, 요약, 분석이 나오나 |
| 품질 | 완전하고 유용하며 적절히 검토됐나 |
| 효율성 | 더 빠르거나 덜 부담스러운가 |
| 신뢰도·인식 | 계속 쓸 만큼 믿나 |
| 거버넌스 신호 | 검토, 출처, 공유 절차를 따르나 |

| 주차 | 중점 | 핵심 내용 |
|---|---|---|
| 1주차 | 전략 연계·준비 확인 | 목표, 범위, 책임자, 지표, 거버넌스 검증 필요 확인 |
| 2주차 | 워크스페이스·접근 준비 | 설정 종속성, 관리자 권한, 소스와 앱 경로 검증 |
| 3주차 | 사용자 준비·활성화 | 교육, 허용 사용 안내, 사람 검토 기대 확인 |
| 4주차 | 강화·피드백 검토·결정 | 품질과 문제를 검토해 계속, 조정, 확대, 일시 중지 결정 |

- **선행 vs 후행 지표:** 둘 다 담아야 한다.
  - 선행(출시가 순조로운가): 코호트 합류, 온보딩 완료, 워크플로 시도
  - 후행(계속할 가치가 있나): 소요 시간 단축, 수정 주기 감소, 30일 도입률
- **출시 운영 리듬:** 킥오프 → 설정 준비 점검 → 활성화 점검 → 초기 피드백 검토 → 거버넌스·문제 검토 → 30일 검토.
- **KPI 증거 맵** 예: 요약 품질은 샘플 검토와 관리자 체크리스트로 4주차에 본다. 사용량으로 품질을 판단하지 않는다.
- **범위 이탈 패턴** 예: 인접 워크플로 모두 추가, 전 직원을 첫 사용자로, 워크플로와 무관한 사용량 측정.
- **성공 계획 품질 7기준:** 워크플로 특화, 책임자 명시, 측정 가능, 명확한 가정, 준비 조건 연계, 시간 제한, 30일 내 현실적.

### 실무 적용 예시
- "법무팀에 ChatGPT 도입, 요약 교육" → 선정 코호트가 승인 자료로 공급업체 계약 접수 요약을 쓰고 사람이 검토하는 30일 테스트로 바꾼다.
  - 시작 범위는 워크플로 1개, 사용자 그룹 1개, 고객과 파트너 담당 각 1명, 소수 지표다.
- 모든 계약 유형의 현재 검토 시간을 모름 → 계획을 멈추지 않고 검토자 추정과 샘플 검토로 방향성 증거를 모은다.
- 승인된 원본 자료 확인 → 1주차 활성화 전에 수행하고, 소스 승인이 불분명하면 법무·준법으로 에스컬레이션한다.

### 지식 점검 포인트
- 30일 계획에서 먼저 의문을 제기할 조치 → **일반 AI 뉴스레터 제작**. 워크플로, 담당자, 결정과 연결되지 않는다.
- 가장 타당한 출시 범위 → **정의된 법무 운영 코호트, 지정 책임자, 품질과 신뢰 근거, 결과 기반의 30일 후 결정**.
- 후원자와 파트너 책임자만 있고 핵심 책임 담당자가 없음 → **책임마다 담당자를 지정하고 에스컬레이션 경로 문서화**.
- 계약 요약 첫 출시의 핵심 KPI → **코호트의 워크플로 사용, 검토자의 유용성 평가, 사용자 신뢰, 원본·검토 문제 기록**.
  - 로그인 빈도, 프롬프트 수, 경영진 관심은 핵심 KPI가 아니다.
- 실행 가능한 거버넌스 체크포인트 → **거버넌스 이해관계자가 10일차까지 원본·검토 규칙을 검증하고 그 결과로 가동 승인**.
- 가장 효과적인 30일 순서 → **준비 → 활성화 → 증거 검토 → 다음 결정**.
- 가장 효과적인 인계 → **워크플로, 코호트, 소스 가정, 검토 기대, KPI 근거, 결정 시점을 담은 메모**.

  <h1 class="lesson-title">작업 공간 설정하기</h1>

> **한 줄 요약:** 승인된 성공 계획을 워크스페이스 요구 사항으로 바꾸고, 항목마다 준비 상태와 담당자를 붙인 준비 체크리스트를 만든다.

### 핵심 내용
#### 성공 계획을 워크스페이스 요구 사항으로
- 워크스페이스 설정은 콘솔 클릭이 아니라, 승인된 워크플로를 지원하기 위한 계획 기반 관리자 검토다.
- 출발점은 제품 선호가 아니라 승인된 배포 계획이다. 대상 워크플로, 사용자 그룹, 필요한 ChatGPT 경험을 확인한다.
- "법무 운영 코호트"는 사용자 목록이 아니라 접근 경로, 프로비저닝, 역할·그룹 결정을 뜻한다.
- **구성 종속성**을 지금 모두 해결할 필요는 없다. 파악하고, 담당자를 정하고, 활성화 전 필수인지 판단한다.
- 가용성과 통제 정보는 특정 시점의 상태다. 준비됨으로 표시하기 전에 고객의 요금제, 워크스페이스, 지역 기준으로 검증한다.

#### 소유권과 관리 책임
- 접근, 설정, 소스 준비, 에스컬레이션 담당자가 없으면 잘 짜인 계획도 지연된다.
- 한 사람이 여러 역할을 맡아도 체크리스트에는 책임 범위를 각각 드러낸다.
- 관리 책임을 암묵적으로 두지 않는다. 비즈니스 소유자가 워크플로만 승인하고 소스 접근은 승인하지 않는다면 명시한다.
- 에스컬레이션 담당자를 미리 정해 두면 작은 장애가 출시 지연으로 번지는 것을 막는다.

#### 접근과 거버넌스 요구 사항
- **"사용자 확인됨" ≠ "접근 준비됨".** 프로비저닝돼도 인터페이스나 앱, 에이전트 권한이 없을 수 있다.
- GPT-6 Astra는 ChatGPT Work 접근과 모델 접근을 따로 확인한다. 이전 'Early Model Access' 설정은 사용 가능성을 보장하지 않는다.
  - 관리자는 제품 가용성, 명시적 모델 활성화, 할당된 모든 역할의 유효 권한을 확인한다.
- 고객 환경에서 확인된 통제만 쓴다. 지역·상주 요구 사항은 기억이 아니라 고객 담당자와 최신 공식 문서로 검증한다.
- 규정 준수 증거와 도입 분석은 별개다. 그 자체로 출력 품질이나 인과적 ROI를 입증하지 않는다.
- 초안 작성 권한이 제출 권한을 주지 않는다. 별도 승인이 없으면 계약 시스템 쓰기 작업은 첫 활성화에서 '보류'로 둔다.

#### 지식·앱·에이전트 요구 사항
- 흔한 실수는 존재한다는 이유로 소스가 준비됐다고 보거나, 나중에 쓸지 몰라 앱을 켜야 한다고 보는 것이다.
- 첫 워크플로가 의존하지 않는 앱, 플러그인, 에이전트는 장애 요인이 되어선 안 된다.
- 클라우드 작업은 데스크톱 파일이나 브라우저 세션을 자동 상속하지 않는다. 선택한 실행 환경을 기록한다.
- 로컬 도구 실행은 오프라인 추론이 아니다. 컨텍스트가 클라우드 모델로 전송될 수 있다.

#### 준비 상태 체크리스트 작성
- 검토 순서: 책임 소재 → 접근·거버넌스 → 지식·앱·에이전트 → 미해결 설정 조치 → 준비 상태 지정.
- 책임자 없는 항목은 '준비됨'이 아니다. 활성화를 막는지에 따라 '검증 필요'나 '차단됨'으로 둔다.
- **미해결 설정 조치**는 "거버넌스 확인"처럼 모호하게 쓰지 않고, 누가 언제 무엇을 확인하는지 적는다.
  - 예: 법무 운영 담당자와 규정 준수 담당자가 활성화 전 사람 검토 기대 사항을 확인.

### 기억할 개념·프레임워크

| 상태 | 의미 | 사용 시점 |
|---|---|---|
| 준비됨 | 활성화할 만큼 충분히 확인됨 | 소유자, 요구 사항, 다음 단계가 명확 |
| 검증 필요 | 쓸 수 있을 수 있으나 확인 필요 | 승인, 소스, 접근 경로 등이 미해결 |
| 차단됨 | 해결 전 활성화 불가 | 필수 소유자, 승인, 소스 등이 누락 |
| 보류 | 첫 활성화에 불필요 | 나중엔 유용하나 첫 범위 밖 |

- '차단됨'은 영원히 불가가 아니라 해결 전까지 활성화하지 말라는 뜻이다. '보류'도 중요하지 않다는 뜻이 아니다.

| 소유권 역할 | 핵심 책임 |
|---|---|
| 비즈니스 소유자 | 워크플로 결과와 우선순위 |
| 배포 책임자 | 출시 준비 조정, 미해결 항목 추적 |
| 워크스페이스 관리자 | 구성, 인터페이스 활성화, 에이전트 통제 |
| 접근 제어 담당자 | 역할·그룹과 RBAC 할당 |
| 앱·에이전트 소유자 | 연결 모델, 게시, 허용 작업, 승인 설정 |
| IT·ID 소유자 | 도메인, SSO, SCIM, 프로비저닝 |
| 보안·법무·규정 준수 소유자 | 민감 데이터 경계, 정책, 보존·상주 |
| 소스 소유자 | 콘텐츠의 최신성, 접근성, 워크플로 적합성 |

- **용어**
  - 앱: ChatGPT를 외부 도구, 정보, 작업과 연결한다.
  - 플러그인: 특정 워크플로용 스킬과 함께 하나 이상의 앱을 묶는다.
  - 워크스페이스 에이전트: 지시, 파일, 도구 등을 결합해 반복 작업을 수행한다.
- **지식 소스 준비 5문:** 이용 가능한가? 최신인가? 승인됐나? 소유자가 있나? 대상 워크플로에 적합한가?
- **앱·에이전트 준비 4문:** 필요한가? 사용 가능하고 활성화됐나? 연결 모델이 승인됐나? 작업과 권한이 제한됐나?

### 실무 적용 예시
- 계약 접수 템플릿 → **검증 필요**. 법무 운영 소스 소유자가 활성화 전 최신성과 승인, 접근을 확인한다.
- 계약 시스템을 업데이트하는 에이전트 → 첫 활성화에 필수가 아니므로 **보류**. 연결 소유권과 쓰기 승인이 검증될 때까지 연기한다.
- 활성화에 필요한데 소유자가 확인되지 않은 정책 지침 → **차단됨**. 해결되지 않으면 중지하거나 범위를 재조정한다.

### 지식 점검 포인트
- 법무 운영 코호트 계획의 가장 큰 워크스페이스 영향 → **가동 전 코호트 접근, 소스 소유권, 사용 범위, 검토 기대 확인**.
- 비즈니스 소유자만 있는 계획 → **소유권 공백으로 접근과 설정 결정이 지연될 수 있음**. 비즈니스 소유자가 설정을 대신하지 못한다.
- 공유 앱 연결로 레코드를 업데이트하려는 Workspace Agent, 권한과 승인 미확인 → **'검증 필요'**.
  - 소유자, 연결 모델, 허용 작업, 승인 설정을 확인한다.
- 구식이고 소유자가 미확정인 정책 문서 → **'검증 필요'**. 소유자와 최신성을 확인한 뒤 활성화 전 필요 여부를 정한다.
- 소스는 승인됐으나 GPT-6 Astra 접근 근거가 이전 설정뿐 → **'검증 필요'**. 대상 환경에서 모델 활성화와 유효 권한을 확인한다.

  <div class="eyebrow">레슨 04 · Design Use Cases for Activation</div>
  <h1 class="lesson-title">활성화를 위한 사용 사례 설계</h1>
</div>

> **한 줄 요약:** 후보 워크플로를 품질 기준으로 평가하고 가치와 준비도, 위험으로 순서를 정해 성공 신호와 시작 요건을 담은 활성화 계획을 만든다.

### 핵심 내용
#### 후보 워크플로 평가
- **사용 사례 활성화**는 정의된 사용자 그룹이 특정 워크플로에서 ChatGPT를 실제 업무에 적용하고 검토하게 하는 것이다.
- 이 연결이 없으면 "접근은 생겼지만 무엇을 해야 할지 모르는" 기능 출시로 끝난다.
- 제품 기능이 아니라 작업의 순간에서 출발한다. "요약" 같은 기능 명칭은 워크플로 정의가 아니다.
  - 약함: "재무 생산성 향상"
  - 강함: 재무 관리자가 승인된 보고 자료로 사람이 검토할 월별 편차 해설 초안 작성
- 협업형과 위임형·실행형은 결과가 비슷해도 활성화 요건이 다르다. 해당 없는 항목은 "해당 없음"으로 적는다.
- "모든 직원용 법률 Q&A"는 "법무 운영 전문가가 승인 자료로 접수 요약 작성"처럼 범위를 좁힌다.
- 고객 대상 응답은 가치가 높아도 검토 기준과 소스 소유권이 미해결이면 첫 활성화에서 연기한다.

#### 우선순위 정하기
- 유망한 워크플로를 한꺼번에 켜면 혼란과 지원 부담이 커지고, 성공 여부를 파악하기 어렵다.
- 비즈니스 가치는 최종 ROI가 아니라 잠재적 영향, 빈도, 사용자 관련성으로 본 방향성 가치다.
- **가치 중간 + 준비 탄탄**한 워크플로가 미해결 종속성이 있는 고가치 워크플로보다 먼저일 수 있다.
- 점수는 판단을 돕되 대체하지 않는다. 차단 요소는 총점이 높아도 평균으로 지우지 않는다.

#### 성공 신호 정의
- **성공 신호**는 장기 ROI 입증이 아니라 계속, 조정, 일시 중지, 확대를 결정하는 데 쓰는 증거다.
- 신호 하나에 의존하지 않는다. 사용량은 승인 워크플로 적용을, 피드백은 결과물 품질을 증명하지 못한다.
- "사용자들이 ChatGPT를 좋아함" 대신 참여와 산출물, 검토, 피드백이 드러나게 쓴다.
  - 예: 첫 기간에 대상 사용자 최소 20명이 갱신 브리프 워크플로를 완료하고, 소유자가 샘플을 검토한다.
- 사람 검토가 필요하면 검토 방식과 담당자를, 에스컬레이션이 필요하면 문제 처리 경로를 명시한다.

#### 선별된 사용 사례 준비
- 가치가 있다고 준비된 것이 아니다. 사용자, 맥락, 검토 기대, 종속성, 책임자가 파악돼야 준비된 것이다.
- 모델 접근만으로 필요한 도구나 파일 접근이 보장되지 않는다.
- **종속성**은 담당자와 조치, 일정이 있으면 관리 가능하고, 없으면 해결 전까지 보류한다.
- 연기는 실패가 아니라, 너무 넓거나 지원되지 않는 워크플로를 켜는 것을 막는 장치다.

### 기억할 개념·프레임워크

| 우선순위 요인 | 1점 | 3점 |
|---|---|---|
| 비즈니스 가치 | 낮거나 불분명 | 배포 목표와 밀접한 높은 가치 |
| 활성화 준비 | 의문점 많음 | 준비 완료 또는 거의 완료 |
| 종속성 위험 | 높거나 차단 위험 | 낮거나 명확히 완화됨 |
| 첫 순서 적합성 | 너무 넓거나 목표와 불일치 | 첫 활성화에 매우 적합 |

| 성공 신호 | 확인 질문 | 예 |
|---|---|---|
| 도입 | 대상 사용자가 시도하나 | 기간 내 첫 사용 완료 |
| 워크플로 | 예상 산출물을 내나 | 승인 구조를 따르고 검토 준비됨 |
| 결과 | 의도한 개선이 보이나 | 초안 노력 감소 보고 |
| 검토·모니터링 | 산출물과 문제가 드러나나 | 합의된 절차로 문제 파악 |

- **사용 사례 품질 6기준:** 워크플로 구체성, 사용자 특정, 결과 연계, 맥락 지원, 반복 가능, 측정 가능.
- **협업형 vs 위임형·실행형**
  - 협업형: 사용자가 단계별로 참여하고, 출력 사용 시점을 직접 정한다.
  - 위임형·실행형: 다단계 결과를 에이전트나 앱에 맡기므로 소유자, 인증, 읽기·쓰기 범위를 정한다.
- **4대 활성화 준비 결정:** 활성화 준비 완료, 한두 가지 요건 확인 후 활성화, 활성화 전 범위 축소, 준비 개선 시까지 연기.
- **종속성 6유형:** 워크스페이스·접근, 지식 소스·앱, 신원·권한·작업, 승인·거버넌스, 워크플로 소유자, 사용자 준비·지원.

### 실무 적용 예시
- **Northstar Home 우선순위**는 가치, 준비, 위험, 적합성 점수로 정한다.
  - 지원 응답 지침(3, 3, 2, 3점) → 사람 검토와 에스컬레이션 기준을 명시하고 먼저 시작
  - 갱신 브리핑(3, 2, 2, 2점) → 가치는 높지만 승인 소스와 검토 책임자 확정 후 다음 순서
  - 전 직원 일반 생산성(1, 1, 1, 1점) → 대상과 지표가 너무 넓어 당분간 보류
- "고객 지원에 활용" → 팀 리더가 승인된 에스컬레이션 정책으로 복잡 사례 응답 지침 초안을 쓰는 워크플로로 좁힌다.
- 바이오제약 규제 답변 요약 초안 → 접근 경로와 소스 소유자 확인이 남아 **한두 가지 요건 확인 후 활성화**를 고른다.
  - 규제 당국 응답 자동 전송은 대외 조치라 더 엄격한 승인이 필요해 당분간 진행하지 않는다.

### 지식 점검 포인트
- 반복 내부 운영 업무에 가장 준비된 후보 → **운영 관리자가 승인 절차 문서로 사람 검토용 교대 인수인계 요약 작성**.
- 첫 활성화 여부에 가장 큰 영향 → **구체성, 가치, 지원 준비, 관리 가능한 종속성**. 경영진 관심이나 사용자 규모는 아니다.
- 가장 유용한 초기 성공 신호 세트 → **승인 워크플로 완료, 결과물 검토, 사용자 피드백, 합의된 경로로 문제 파악**.
- 지금 진행하지 말아야 할 가장 분명한 이유 → **민감한 원본에 의존하는데 소스 소유자나 검토 경로가 미확인**.
  - 좁은 범위나 단순한 첫 사용 절차는 진행 불가 사유가 아니다.

> **한 줄 요약:** 승인된 워크플로를 출발점으로 역량 강화, 커뮤니케이션, 챔피언과 지원 체계를 엮어 사용자가 실제 업무에서 쓰게 하는 도입 계획을 세운다.

### 핵심 내용
#### 역량 강화 요건 정의
- 역량 강화는 제품 기능이 아니라 **승인된 워크플로**에서 시작한다. "프롬프트 세션이 필요하다"로 시작하는 것은 흔한 실수다.
- 승인된 워크플로 하나하나가 도입 워크스트림이 된다. 누가 쓰고, 누가 행동을 강화하고, 어디서 지원받는지 정한다.
- 지원 방식은 상호작용 패턴에 맞춘다.
  - Chat: 사용자가 맥락을 주고, 중간 결과를 검토하고, 결과를 다듬는다.
  - ChatGPT Work: 결과와 검토 기준을 정의하고, 진행을 모니터링하고, 중요한 조치를 승인한다.
  - 활성화 계획에서 경험이 확인되지 않았다면 가정하지 말고 미해결 사항으로 적는다.
- 목표는 "ChatGPT가 무엇을 할 수 있나"가 아니라 "**내 업무에서 무엇을 해야 하나**"를 아는 것이다.

#### 역량 강화 활동 설계
- 큰 교육 행사 하나보다 **소수의 다양한 활동 조합**이 효과적이다.
  - 활성화 전에는 왜 중요한지 설명하고, 활성화 중에는 시연과 실습을 한다.
  - 활성화 후에는 지원하고, 피드백을 모으고, 행동을 강화한다.
- 역할별 사례가 "ChatGPT가 있다는 건 안다"와 "업무에 어떻게 쓰는지 안다" 사이의 간극을 좁힌다.
- 실습은 현실적이되 민감하거나 미승인된 정보는 쓰지 않고, 승인·가공된 입력과 검토 단계를 넣는다.
- 실시간 접속이 안 되면 예시 출력물로 대체하되 표시한다. 대체 활동은 실사용 준비를 입증하지 못한다.

#### 도입 커뮤니케이션
- 커뮤니케이션은 사용자가 무엇을 해야 하고 왜 중요한지 설명할 때만 추진력을 만든다.
- 워크플로 진행에 맞춘 **적시 메시지** 몇 개가 수많은 일반 알림보다 낫다.
- 함정: 이용 권한만 공지하기, 실적 없이 생산성 약속하기, 첫 교육 후 소통 멈추기.

#### 챔피언과 지원 체계
- 챔피언은 단순한 열성 사용자가 아니라 동료가 **승인된 행동을 반복하도록 돕는 사람**이다.
- 챔피언은 유일한 지원 체계가 아니며 정책 결정 권한도 없다. 과도한 부담을 주지 않는다.
- 지원은 질문 답변을 넘어 워크플로를 개선하는 **학습 루프**여야 한다.
- 강화는 구체적이어야 한다. "더 많이 쓰라"가 아니라 "사건 종결 시 요약 체크리스트를 쓰라"가 실행 가능하다.

#### 사용자 역량 강화 및 도입 계획 수립
- 각 섹션은 선정된 워크플로와 연결돼야 한다. 교육, 커뮤니케이션, 상담 시간을 나열만 하면 불완전하다.
- **도입 워크스트림 요약표**로 계획이 일반 교육으로 흐트러지지 않았는지 점검한다.
- 도입은 행동 변화 과제다. 플랫폼 접근은 문을 열 뿐이고, 워크플로 기반 지원이 그 문을 지나가게 한다.

### 기억할 개념·프레임워크

| 대상 | 필요한 것 |
|---|---|
| 주 사용자 | 승인된 워크플로에서의 사용법과 출력 검토법 |
| 관리자·워크플로 소유자 | 행동 강화, 품질 검토, 도입 장애 대응 |
| 챔피언 | 실제 사례 제시, 동료 FAQ 답변, 장애 파악 |
| 이네이블먼트·L&D | 워크플로 가이드, 데모 스크립트, 실습 문제 |
| IT·보안·법무 등 | 출처 사용, 민감 정보, 에스컬레이션 준수 기대 |
| 경영진·후원자 | 정착 여부를 보여 주는 도입 행동과 초기 신호 |

- 커뮤니케이션은 **인지** → 이해 → 참여 → 강화 순서로 목표를 잡는다.
- 핵심 메시지는 왜 쓰는지, 무엇을 다르게 하는지, 어떤 출처를 쓰는지, 어떻게 검토하는지, 어디로 묻는지에 답한다.
- 챔피언 선정 기준: 워크플로와 밀접함, 동료 신뢰, 기대 행동의 모범, 피드백 공유 의지, 관리자의 시간 지원.
- 대표 도입 장벽: 언제 쓸지 모름, 관리자가 장려하지 않음, 승인 출처 불확실, 초안 과신으로 검토 생략.

### 실무 적용 예시
- Rowan Retail에 "전 사용자 교육과 상담 시간"을 제안 → 너무 포괄적이다.
  - 사례 해결 요약 초안 워크플로에 맞춘 데모, 가이드, 관리자 지원, 첫 2주 상담 시간으로 묶는다.
- 사례 요약 출시 공지 → "이제 ChatGPT를 쓸 수 있습니다"는 약하다. 승인 출처, 검토 책임, 질문 채널을 함께 알린다.
- 특정 사례 유형을 요약해도 되는지 반복 질문 → 교육 문제가 아니라 정책 소유자에게 보낼 거버넌스 질문으로 다룬다.

### 지식 점검 포인트
- 역량 강화 요건을 가장 잘 정의하는 방법 → **대상 그룹별로 이해·연습·검토할 사항과 에스컬레이션 정의**.
- 승인된 워크플로 도입을 가장 잘 뒷받침하는 지원 → **역할 기반 데모, 안내형 실습, 간단한 워크플로 가이드**.
- 사례 요약 도입에 가장 도움 되는 메시지 → **승인 출처로 작성하고, 사용 전 검토하고, 문제는 도입 지원 경로로**.
- 워크플로 기반 도입에서 챔피언의 역할 → **승인된 워크플로 시연과 동료 질문 답변**.
- Rowan Retail에 가장 적합한 계획 → **지원 담당자, 검토 행동, 실습, 지원, 피드백, 위험을 연결한 워크플로 도입 계획**.
  - 교육, 커뮤니케이션, 지원 계획만 단독으로는 불완전하다.

  <h1 class="lesson-title">활성화, 측정, 확장</h1>
</div>

> **한 줄 요약:** 활성화 증거를 계획과 비교해 도입 신호, 초기 가치, 장벽을 가려내고 계속, 조정, 확장, 일시 중지 중 하나를 권고한다.

### 핵심 내용
#### 활성화 결과 평가
- 승인됐다고 의도대로 쓰였다고 가정하지 않는다. 가치와 확장을 따지기 전에 **실제로 일어난 일**부터 확인한다.
- 로그인 여부를 넘어, 의도된 사용자가 승인된 맥락으로 쓰고 검토 지침을 따랐는지 본다.
- 계획된 활동과 관찰된 활동을 구분하는 것이 다음 결정의 사실 기반이 된다.
- 사용량이 많다고 성공도, 적다고 실패도 아니다. 관찰 활동이 의도된 워크플로의 유용한 증거인지가 핵심이다.
- 좋은 관찰은 구체적이다. "사용자들이 혼란스러워한다"보다 "일부가 승인 SOP를 몰라 확대 전 지침 정리가 필요하다"가 강하다.

#### 도입 현황과 초기 가치 신호
- 도입은 접근과 다르다. 한 번 로그인한 사용자보다 승인된 업무에 **반복 사용**하는 사용자가 강한 신호다.
- 가장 중요한 신호는 의도된 워크플로 단계에서의 활용이다. 일반 질문만 쓴다면 워크플로는 아직 도입되지 않은 것이다.
- 정량 지표와 정성 지표를 함께 본다.
  - 정량: 참여, 반복 사용, 완료율.
  - 정성: 자신감, 혼란, 유용성, 워크플로 적합성.
- ChatGPT Work처럼 위임 기능이 있으면 합의된 완료 상태 도달, 필수 승인 준수, 실패 작업 보고까지 확인한다.
- **초기 가치 증거**는 대개 불완전하다. "2주간 관리자 검토 12건 표본이므로 방향성 증거"처럼 한계를 밝힌다.

#### 장벽과 개선 기회 파악
- 장벽은 관찰 가능한 증상이고, **근본 원인**은 그 장벽의 가장 유력한 이유다.
- 같은 낮은 반복 사용도 관리자 지원 미흡, 지침 불명확, 출처 품질 등 원인이 다를 수 있다.
- 모든 문제를 교육 문제로 보지 않는다.
  - 관심은 있으나 혼란스러움 → 지침과 예시를 보강한다.
  - 출처가 낡아 품질 저하 → 승인 소스 세트를 갱신하고 소유권을 확인한다.
  - 산출물을 아무도 검토하지 않음 → 도입이 아니라 검토 책임 문제다.
- 결과가 혼재돼도 워크플로가 실패한 것은 아니다. 다만 다음 단계가 확장이 아닐 수 있다.

#### 확장 판단과 계획 수립
- 확장은 열의가 아닌 **증거와 준비 상태**에 기반한다. 지금 확장하면 가치가 커지는지, 미해결 문제가 커지는지 묻는다.
- 가장 안전한 후보는 성공한 워크플로와 유사한 것이다. 같은 SOP 구조를 쓰는 다른 운영 지역이 그 예다.
- 고객 대면 사고 대응처럼 새 데이터 경계와 검토 요건이 생기는 워크플로는 위험도가 높다.
- 계획은 활성화 결과, 배포 결과, 확장 권고의 3단으로 쓰고, 확인된 사실과 방향성 수준을 구분한다.
- 권고에는 **책임 소재**와 검토 시점을 명시한다. 경영진 보고서는 후원자가 모든 데이터 없이 결정을 이해하게 쓴다.

### 기억할 개념·프레임워크

| 결정 | 사용 시점 |
|---|---|
| 계속 | 유망하며 근거를 더 모으는 동안 계속 실행 |
| 조정 | 잠재력은 있으나 확대 전 구체적 문제 해결 필요 |
| 확장 | 도입, 초기 가치, 준비 상태가 충분하고 남은 위험이 관리 가능 |
| 일시 중지 | 차단 요인, 취약한 근거, 책임 불명확으로 계속이 무책임 |

| 장벽 | 개선 조치 |
|---|---|
| ChatGPT는 알지만 승인 워크플로는 모름 | 더 명확한 워크플로 안내 |
| 적용 자신감 부족 | 목표에 맞춘 역량 강화 조정 |
| 여러 채널에 질문 분산 | 지원 경로 명확화 |
| 관리자가 검토 기준을 강조하지 않음 | 챔피언과 관리자 지원 |
| 소스 자료가 낡거나 불명확 | 확장 전 원본 담당자 확인, 승인 세트 갱신 |

- 근본 원인은 **역량 격차**, 워크플로 문제, 지원 한계의 세 범주로 나눈다.
- 개선 권고 5요소: 장벽, 추정 근본 원인, 권장 조치, 책임자, 다음에 검토할 증거.
- 확장 준비 요인: 도입 지표, 초기 가치, 지원 역량, 운영 가시성, 거버넌스 작동 증거 등.

### 실무 적용 예시
- Churchill Manufacturing에서 교육 52명, 1회 완료 39명 → 계획(교육 45명, 완료 35명 이상)을 넘은 참여다.
  - 다만 승인 SOP 반복 질문과 비공개 메시지 문의가 있어 출처 지침과 지원 경로를 보강한다.
- HR 정책 요약에서 어떤 정책을 참조할지 반복 질문 → 관심 부족이 아니라 출처 지침 문제다. 승인 출처 목록부터 정리한다.
- 후원자가 다음 분기 전 두 번째 지역 확장을 원함 → 압박이 아닌 증거로 결정한다.
  - 시간 기준치 부재, 지원 문의 증가, 미교육 지역에 대한 조치와 책임자를 확장 전에 정한다.

### 지식 점검 포인트
- 활성화가 예상대로 진행됨을 보여 주는 지표 → **대상 사용자가 승인된 워크플로에서 ChatGPT를 활용 중**.
- 도입 지표와 초기 가치 증거의 차이 → **도입은 승인 워크플로 활용 여부, 가치는 유용한 결과 창출 여부**.
  - 둘 다 정량과 정성으로 볼 수 있고, 최종 ROI로 과장하지 않는다.
- HR 정책 참조에 대한 반복 질문 → **승인 출처 목록 명확화, 지침 갱신, 출처 소유자 확인**.
- 확장 권고에 가장 큰 영향을 주는 요인 → **첫 코호트 증거가 확장을 정당화할 만큼 충분한가**.
- 활성화 검토 및 확장 계획의 주요 구성 → **경영진 보고, 활성화 성과, 도입과 가치 증거, 장애 요인, 위험, 다음 조치**.

  <div class="eyebrow">레슨 07 · Scaling ChatGPT Across the Organization</div>
  <h1 class="lesson-title">조직 전반에 걸쳐 ChatGPT 확대 적용하기</h1>
</div>

> **한 줄 요약:** 활성화 증거로 다음 확장 영역의 우선순위를 정하고, 책임과 거버넌스, 지원, 위험을 담은 조직 확장 전략을 제안한다.

### 핵심 내용
#### 조직 확장 우선순위 정의
- 확장은 사용자 수를 늘리는 일이 아니라, **이전 활성화의 증거**로 다음에 어디까지 넓힐지 정하는 일이다.
- 사례 기업 미들턴 제조는 SOP 기반 절차 요약 워크플로를 1차 도입해 높은 참여와 반복 사용을 확인했다.
  - 다만 검토 기준 미확정, 지원 문의 증가, 다음 분기 전 성과 요구가 남아 있다.
- 모든 문제가 해결될 필요는 없다. 책임감 있는 결정을 내릴 만큼 근거가 있으면 된다.
- 가장 안전한 후보는 **이미 성과를 낸 워크플로와 유사한 경우**다. 같은 SOP 구조를 쓰는 다른 운영 지역이 그 예다.
- "첫 코호트가 좋아했으니 확대"는 약하다. 왜 이 대상이 적합하고 확대 전 무엇이 준비돼야 하는지 설명한다.

#### 소유권과 거버넌스 정의
- 도입이 커지면 비공식 소유권으로는 부족하다. "고객이 책임질 것" 대신 업무마다 **담당 역할**을 명시한다.
- 한 집단에서 관리 가능했던 워크플로도 여러 팀이 제각각 쓰면 일관성을 잃는다.
- 제품 통제를 누가 관리하는지도 확인한다. SCIM 그룹 접근, 워크스페이스 에이전트 게시, 작업 승인 등이 대상이다.
  - 실제 가용성과 제어 방식은 플랜과 워크스페이스 구성에 따라 다르다.
- **분석과 규정 준수 기록은 분리한다.** Task Insights는 도입 패턴을, 규정 준수 기록은 감사와 조사를 지원한다.
- 분석만으로는 산출물 품질, 규정 준수, 비즈니스 가치를 입증할 수 없다.

#### 확장 지원 및 역량 강화
- 소규모 그룹에 통하던 실시간 세션과 비공식 코칭 대신 **반복 가능한 지원**을 마련한다.
- 확장은 일회성 출시가 아니다. 첫 주 이후, 첫 검토 이후, 워크플로 변경 시 재교육이 필요할 수 있다.
- 미들턴 1차 코호트가 승인 SOP를 반복 문의했으므로, 2차 지역 전에 지침을 갱신해 같은 혼란을 막는다.
- 챔피언 한 명이 교육, 답변, 에스컬레이션을 모두 떠안으면 피로가 쌓여 확장이 취약해진다.
- 근본 원인, 책임 공백, 거버넌스 문제는 챔피언이 해결하지 않고 적절한 담당자에게 넘긴다.

#### 위험·의존성과 확장 전략
- 소규모에서 관리 가능했던 문제가 확장 시 드러난다. 원본 품질 문제 확산과 지원 채널 과부하가 그 예다.
- 위험은 확장 결정과 연결해 쓴다.
  - 약함: "거버넌스가 문제가 될 수 있다."
  - 강함: "2차 지역 관리자에게 검토 기준이 전달되지 않으면 검토 관행이 어긋날 수 있다."
- **의존성**은 확장 전에 준비돼야 할 요소다. 일부는 출시 전 해결하고, 일부는 단계적 출시 중 모니터링한다.
- 확장 위험이 곧 중단 사유는 아니다. 고객이 지원하고 모니터링할 수 있는 속도로 확장하면 된다.
- 전략은 선택한 확장안이 왜 타당한지와 함께 **아직 진행하지 말아야 할 영역**도 밝힌다.

### 기억할 개념·프레임워크

| 확장 기준 | 확인할 것 |
|---|---|
| 비즈니스 관련성 | 중요 우선순위와 연결되는가 |
| 조직·환경 준비 상태 | 맥락, 자료, 지침, 이해관계자 지원 |
| 운영적 타당성 | 인력, 일정, 챔피언과 검토 역량 |
| 예상 영향 | 노력, 품질, 일관성 개선 근거 |
| 거버넌스·검토 준비 | 허용 사용, 소스 범위, 에스컬레이션 명확성 |
| 가시성 | 활동, 피드백, 문제를 볼 수 있는가 |

| 확장 방식 | 사용 시점 |
|---|---|
| 단계적 확장 | 인접 팀이나 지역을 하나씩 넓히고 매 단계 점검 |
| 반복 및 확장 | 성공 워크플로를 유사 환경에 복제한 뒤 관련 워크플로로 |
| 확장 전 조정 | 원본 지침, 검토 책임 등 구체적 장애를 먼저 해결 |
| 확장 보류 | 증거, 준비, 책임, 지원이 너무 약할 때 |

- 소유권은 경영진 후원자, 영역별 비즈니스 책임자, 운영 배포 책임자, 챔피언 리더, 에스컬레이션 책임자 등으로 나눈다.
- 질문은 유형별로 보낸다.
  - 워크플로는 챔피언 채널, 소스는 소스 소유자, 검토는 관리자에게 보낸다.
  - 접근은 워크스페이스 관리자와 IT, 거버넌스는 거버넌스 소유자에게 보낸다.
- 좋은 **완화 조치**는 위험, 조치, 책임자, 시기, 검토할 증거를 함께 담는다.

### 실무 적용 예시
- 두 번째 운영 지역 → 같은 워크플로와 SOP 구조, 비슷한 검토 기대를 공유하므로 우선순위 '높음'이다.
  - 단, 2차 지역 준비와 챔피언 커버리지, 관리자 검토 역량 확인이 전제다.
- 1차 활성화 중 지원 문의 증가 → 챔피언 리더가 주간 상담 시간을 늘리고 승인 출처 FAQ를 갱신한다.
  - 문의가 계속 늘면 배포 책임자가 지원 역량이 나아질 때까지 확장 속도를 늦춘다.
- 최종 권고 → 운영 지역 하나만 단계적으로 추가하고, 안전 사고 요약과 고객 대응 초안은 아직 보류한다.
  - 2주 후 점검에서 분석, 관리자 검토 샘플, 지원 문의를 보고, 감사·보존 사안은 규정 준수 기록으로 따로 본다.

### 지식 점검 포인트
- 가장 강력한 첫 확장 우선순위 → **비즈니스 관련성이 명확한 유사 워크플로나 인접 팀**.
- 여러 팀으로 확대할 때의 소유권 모델 → **확장 영역마다 비즈니스 책임자, 도입 조정, 챔피언 리더십을 명확히 둔다**.
- 팀이 늘어날 때 도입을 유지하는 지원 → **반복 가능한 지침, 셀프 서비스 리소스, 명확한 에스컬레이션 경로**.
- 빠른 확대 요구 속 문의 증가와 검토 기준 불일치 → **대규모 확장 전에 지원, 검토, 피드백 위험을 해결**.
- 확장 전략의 주요 구성 → **확장 목표, 우선순위, 출시 접근 방식, 다음 조치**.

### 핵심 내용
#### 시나리오와 진행 방식
- 가상 제조 기업 **Kestrel Manufacturing**의 COO Evan Brooks와 ChatGPT Enterprise 배포 상담을 연습한다.
- 중심 워크플로는 운영 팀을 위한 내부 지식 검색 및 절차 요약이다. 기술 구현이 아니라 안내에 따른 적용 실습이다.
- 모든 문제를 한 번에 풀지 않는다. 우려를 경청하고 대화를 첫 워크플로 진입점에 집중시킨다.
- 세 대화는 이어진다. 마지막에 Evan이 권장 배포 경로를 요청하면 별도 서면 과제가 아니라 역할극 안에서 답한다.

#### 활동별 과제
- 활동 1: 첫 워크플로 진입점, 첫 사용자 그룹, 성공 지표, 검증 질문을 명확히 한다.
- 활동 2: 첫 활성화를 책임 있게 시작하는 데 **가장 큰 영향을 주는 격차**를 찾는다.
  - Evan이 전하는 우려로, Dana Reyes는 워크스페이스 준비와 승인 출처를, Robert King은 거버넌스와 검토 기대를 짚는다.
  - 한 팀이 공개하려는 워크스페이스 에이전트는 연결 방식, 쓰기 작업, 승인 시점이 합의되지 않았다.
- 활동 3: 사용자 지원, 성공 신호 측정, 확장 전 조건, 개선 책임자를 권고한다.

### 기억할 개념·프레임워크
- **핵심 배포 패턴:** 배포 과제 → 첫 워크플로 진입점 → 첫 사용자 그룹 → 준비·거버넌스 격차 → 도입 지원 → 성공 신호 → 확장 조건 → 다음 단계

| 활동 | 강한 답변의 산출물 |
|---|---|
| 1 | 워크플로 진입점과 첫 코호트, 성공 지표와 검증 질문 구분 |
| 2 | 가장 중요한 격차, 진행·축소·보류 판단, 책임자와 다음 단계 |
| 3 | 사용과 검토 안내, 성공 신호 측정, 확장 조건, 개선 책임자 |

### 실무 적용 예시 (직접 진행한 역할극)
- 활동 1 → 한 사업장의 교대 관리자와 현장 감독자를 첫 코호트로, 범위를 절차 요약 하나로 좁혔다.
- 활동 2 → 워크스페이스 에이전트를 보류하고, 사람이 검토하는 요약으로 좁힌 조건부 진행을 제안했다.
- 활동 3 → 한 페이지 가이드, 교대별 챔피언, 30일 검토 기반의 확장 조건을 제시했다.
- 세 활동 모두 "잘했어요!" 평가를 받았다. 정량 목표, 부서별 책임, 30일 이후 결정 과정은 보완점으로 남았다.

### 롤플레이 과제
- 세 활동은 채점되지 않는 연습이며 지식 점검 문항은 없다.
- 좋은 답변의 조건은 다음과 같다.
  - 고객의 압박은 인정하되 하나의 워크플로와 코호트로 범위를 좁힌다.
  - 새 이해관계자 우려는 별도 과제가 아니라 같은 결정을 다듬는 재료로 쓴다.
  - 에이전트 쓰기 작업처럼 합의되지 않은 항목은 보류해 첫 활성화를 지킨다.
  - 성공 신호, 확장 조건, 책임자를 명시한 채 끝맺는다.
- 가장 강력한 권고는 가장 넓은 도입 계획이 아니라 **가장 명확한 다음 배포 결정**이다.
