### 통합 최종 정리 — OpenAI 기초 지식

#### 한 문단 요약
기초 지식 과정은 PartnerU 파트너가 OpenAI를 고객에게 **과장 없이, 워크플로 중심으로** 설명하는 공통 기반을 다진다. 1~2강에서 OpenAI의 미션과 파트너 역할, 학습 경로와 배지 체계를 익힌다.

3~4강은 안전 우려를 인식 → 책임 구분 → 검증 순서로 다루는 법과 AI 가치를 4가지 패턴으로 설명하는 법을 다룬다. 5~8강은 AI 용어, 응용 패턴과 RAG, 인프라 신호, 에이전트 구성 요소를 배운다.

9강은 포트폴리오를 세 계층으로 나누고, 10~12강은 ChatGPT, Codex, API의 쓰임을 구분한다. 13강은 고객 문제에서 솔루션 패턴과 측정 가능한 성과까지 잇는 방법으로 마무리한다.

#### 과정 전체 흐름
```
[1~2강] 오리엔테이션: 미션·파트너 역할, 학습 경로·배지
   │
[3~4강] 대화 원칙: 안전(인식 → 책임 → 검증), 가치 4패턴
   │
[5~8강] 개념 기초: 용어 → 응용·RAG → 인프라 → 에이전트
   │
[9강] 포트폴리오 3계층: 표면 · 기능 · 배포
   │
   ├─▶ [10강] ChatGPT: Chat(협업), Work(위임)
   ├─▶ [11강] Codex: 소프트웨어 전달
   └─▶ [12강] API: 제품·시스템에 AI 내장
   │
[13강] 고객 문제 → 워크플로 → 솔루션 패턴 → 성과
```

#### 강의별 핵심
- **1강 OpenAI 소개:** OpenAI는 "연구 조직이자 배포 회사"다. 미션을 성과 약속 근거로 쓰지 않고, 모르면 확인 후 답한다.
- **2강 배지 프로그램:** 공통 기초, 8가지 실무자 경로, 배지, 실시간 학습으로 구성된다. 배지가 실시간 학습 참여를 보장하진 않는다.
- **3강 AI 안전:** 안전 대화는 인식 → 책임 구분 → 검증 순서다. "안전하다" 대신 감소·관리·검증 표현을 쓴다.
- **4강 비즈니스 혁신:** 효율성, 의사결정 품질, 대규모 개인화, 새로운 역량 창출로 가치를 설명하고 워크플로로 좁힌다.
- **5강 AI·ML 기초:** LLM은 AI의 일부일 뿐이다. 모델은 고객 데이터를 자동으로 모르며, 기능을 먼저 말한다.
- **6강 응용 분야:** 응용 패턴 6가지와 RAG를 익히고, 인터페이스와 기능, 배포 결정을 분리한다.
- **7강 인프라·구현:** 앱 위치, 추론 위치, 운영 책임, 데이터 이동을 나눠 묻고 훈련과 추론을 구분한다.
- **8강 에이전트:** 여러 단계와 도구, 사람 감독이 필요할 때 적합하다. "완전 자율"이나 "항상 정확"은 오해다.
- **9강 제품 포트폴리오:** Chat은 협업, Work는 위임, API는 내장, Codex는 엔지니어링이다. 에이전트는 별도 제품이 아닌 기능이다.
- **10강 ChatGPT 에센셜:** 프롬프트는 작업 + 맥락 + 기대치다. 요금제와 기능은 최신 공식 출처로 확인한다.
- **11강 Codex 에센셜:** 소프트웨어 전달을 돕는 코딩 에이전트다. 방향, 판단, 승인 등은 사람이 맡는다.
- **12강 API의 핵심:** 고객 제품과 시스템에 AI를 내장하는 경로다. 권한, 로깅, 사람 감독 등 안전 장치를 챙긴다.
- **13강 현장의 OpenAI 솔루션:** 고객 문제에서 워크플로와 솔루션 패턴을 거쳐 측정 가능한 성과까지 잇는다.

#### 강의를 잇는 연결 고리

| 개념 | 처음 등장 | 이어지는 강의 |
|---|---|---|
| 워크플로 우선 | 1강 고객 목표 먼저 | 4강, 9강, 13강 솔루션 사고 순서 |
| 세 가지 결정 계층 | 1강 생태계 3층위 | 6강, 8강, 9강, 13강 솔루션 설계 |
| 엔터프라이즈 AI 4요소 | 1강 컨텍스트, 런타임 등 | 3강 운영 질문, 7강, 9강 운영 개념 |
| 표면 구분 | 1강 제품 표면 예시 | 6강 인터페이스 신호, 9강, 10~12강 |
| 과장 없는 표현과 검증 | 1강 신뢰 원칙 | 3강 안전, 4강 AI 전환, 8강 에이전트 |
| 사람 검토와 승인 | 3강 공동 책임 | 8강 가드레일, 11강, 12강 안전 장치 |

#### 실무 체크리스트
- ☐ 제품 이름보다 고객 문제와 워크플로를 먼저 물었는가
- ☐ 제품 표면, 기능, 배포를 따로 판단했는가
- ☐ Chat, Work, Codex, API 중 어떤 신호인지 구분했는가
- ☐ AI에 필요한 정보의 출처와 접근 권한을 확인했는가
- ☐ 앱 위치, 추론 위치, 운영 책임, 데이터 이동을 나눠 파악했는가
- ☐ 다단계 에이전트가 정말 필요한지, 단일 응답으로 충분한지 따져 봤는가
- ☐ "안전하다" 대신 감소·관리·검증 표현을 썼는가
- ☐ 사람의 검토 지점과 성과 측정 방법을 정했는가
- ☐ 요금제, 기능, 모델 이름을 약속 전에 최신 공식 문서로 확인했는가

> **한 줄 요약:** OpenAI의 미션과 운영 방식, 생태계 내 역할을 정확히 설명하고 과장 없이 고객 대화를 이끄는 기본기를 익힙니다.

### 핵심 내용
#### 미션과 파트너의 역할
- 미션은 "AGI가 인류 전체에 이익이 되도록 하는 것"입니다. AGI는 현재 제품의 능력이 아니라 장기 방향입니다.
- 미션을 고객 성과를 약속하는 근거로 쓰면 안 됩니다. 가치는 사용 사례, 워크플로, 거버넌스 등에 따라 달라집니다.
- 파트너는 OpenAI 역량을 고객 맥락으로 **번역**합니다. 대상 문제, 인정받을 성과, 먼저 검증할 것을 묻습니다.
- 제안한 경로를 고객이 인정하는 성과와 잇지 못하면 아직 대화를 깊게 진행할 단계가 아닙니다.

#### 발전 과정과 운영 방식
- 가장 정확한 설명은 "연구 조직이자 배포 회사"입니다. 연구는 가능성을 넓히고, 배포는 실제 사용 방식을 드러냅니다.
- 운영은 연구, 배포, 안전, 피드백의 네 활동이 균형을 이루는 구조입니다. 안전 작업이 연구와 배포를 잇습니다.
- 초기 대화에서는 "연구와 실제 배포를 결합해 개선된다" 정도의 설명이면 충분합니다.

#### 생태계에서의 역할과 고객 목표
- 조직은 생산성, 정보 접근성, 고객 경험 등을 위해 AI에 투자합니다. 개인 생산성에서 시스템 내장으로 확장됩니다.
- 제품보다 고객 목표가 먼저입니다. "ChatGPT를 쓰고 싶다"는 출발점일 뿐이니 문제와 성공 기준부터 묻습니다.
- 많은 고객은 AI를 "알고는" 있지만 "준비된" 상태는 아닙니다. 파트너는 기회 발굴과 책임 있는 도입을 돕습니다.

#### 신뢰와 커뮤니케이션 원칙
- 신뢰는 명확성, 관련성, 정직성에서 나옵니다. 모를 때는 "확인 후 답하겠다"가 추측보다 신뢰를 높입니다.
- 검증된 사실은 확신 있게, 맥락에 따라 다른 것은 조건을 붙여, 깊은 검토가 필요한 것은 에스컬레이션으로 말합니다.
- 흔한 과장은 ROI 보장, 컴플라이언스 자동 충족, 위험의 완전 제거 등입니다. 위험은 줄이고 관리하는 대상입니다.
- 확인 후 약속하기: 질문을 인정하고, 아는 범위만 설명한 뒤, 공식 문서나 전문가 확인을 약속합니다.

### 기억할 개념·프레임워크

| 생태계 층위 | 질문 | 예시 |
|---|---|---|
| 제품 표면·경험 | 사람과 워크플로가 어디서 일하나? | ChatGPT Chat, ChatGPT Work, API, Codex |
| 기능·아키텍처 | 시스템이 무엇을 해야 하나? | 에이전트, 멀티모달 |
| 배포·운영 모델 | 어디서 어떻게 실행하고 통제하나? | 호스팅, 권한과 승인, 오픈 웨이트 모델 |

- **엔터프라이즈 AI 4요소:** 컨텍스트, 런타임, 관측성, 거버넌스. 관측성은 증거를 줄 뿐 거버넌스를 대체하지 않습니다.
- **초기 대화 흐름:** 미션 → 고객 문제 → 워크플로 맥락 → 책임 있는 탐색 → 가능한 OpenAI 경로.
- **파트너가 만드는 전환:** 호기심에서 실질적 탐색으로, 가정에서 검증으로, 개별 사용에서 책임 있는 도입으로.

### 실무 적용 예시
- "OpenAI로 지식 관리가 되나요?" → 제품보다 어느 팀이 무엇을 찾느라 느린지, 접근 규칙은 무엇인지부터 묻습니다.
  - 첫 검증은 권한 있는 문서로 출처가 달린 브리프를 만들고 리드가 원문과 대조하는 방식입니다.
- "AI가 이 프로세스를 완전히 대체하나요?" → "가능하다" 대신 사람의 판단과 승인이 필요한 지점부터 파악하자고 답합니다.
- "생산성을 자동으로 높이고 위험을 없앤다" → 적합한 워크플로와 통제가 갖춰질 때 도움이 될 수 있다고 고쳐 말합니다.

### 지식 점검 포인트
- 미션과 고객 관련성을 잇는 설명 → **OpenAI 역량이 실제 비즈니스 요구를 책임 있게 지원할지 고객과 함께 탐색**합니다.
- AI 능력을 넓히는 활동 → **연구**. 실제 사용에서 배워 제품과 가이드를 개선하는 활동은 배포입니다.
- 위임형 다단계 지식 업무에 맞는 표면 → **ChatGPT Work**. API는 제품과 시스템에 내장하는 AI입니다.
- 초기 대화에서 신뢰를 쌓는 행동 → **고객 목표를 묻고, 쉬운 말로 설명하고, 약속 전에 확인**하기.
- 가장 정확한 표현 → **"워크플로 개선을 도울 수 있지만, 효과는 사용 사례와 구현, 거버넌스에 따라 달라진다"**.

  <h1 class="lesson-title">배지 프로그램 이해하기</h1>
</div>

> **한 줄 요약:** PartnerU 프로그램이 공통 기초, 8가지 실무자 경로, 배지 검증, 실시간 학습을 어떻게 엮는지 이해하고 다음 학습을 계획함.

### 핵심 내용
#### 프로그램 운영 방식
- 단일 과정이 아니라 서로 연결된 학습 여정이며, 모두가 같은 고정 순서를 따르지 않음.
- 구성 요소는 공통 기초 커리큘럼, 실무자 경로, 배지 인증, 실시간 학습 기회의 4가지.
- Foundation은 권장 기준일 뿐 필수 선행 조건이 아님. 공식 선행 요건은 현행 지침에 명시된 경우만 적용.
- 배지는 과정 수료가 아니라 **실무 능력 검증**을 위한 것. 정확한 명칭과 수여 규칙은 최신 PartnerU 지침에서 확인.

#### Foundation과 경로 선택
- Foundation은 OpenAI 입문자나 다음 경로가 불확실한 사람에게 권장되는 출발점.
- 목표는 모든 기능 숙달이 아니라, 다음 경로를 고르고 다른 역할과 협업할 만큼의 이해.
- Foundation 수료만으로 실무자 배지가 자동 부여되지 않음.
- 경로는 직함이 아니라 **실제 수행 업무**를 기준으로 고름. 책임이 넓어지면 경로를 추가해 나감.

#### 배지와 평가
- 과정 수료는 콘텐츠를 마쳤다는 뜻이고, 배지는 정의된 영역에서 준비됐음을 입증했다는 뜻.
- 배지가 입증하는 것은 개념의 실제 적용, 역할에 맞는 의사결정, OpenAI 역량과 고객 성과의 연결 등.
- 평가는 지식과 판단력의 적용을 확인하고, 검증은 배지 요건 충족을 확인하는 포괄적 절차임.
- 실습이나 과정 이수만으로는 배지 요건을 채울 수 없음(지침에 명시된 경우 제외).

#### 실시간 학습
- 웨비나, 부트캠프, 구현 워크숍, 해커톤 같은 전문가 주도 학습이 포함됨.
- 배지 획득 순서와 별개이며 자격, 초청, 수용 인원 등 별도 요건이 적용될 수 있음.
- 배지 소지가 참여 권한을 자동으로 열어주지 않음. 일정과 자격은 PartnerU나 파트너 포털에서 확인.

### 기억할 개념·프레임워크
- **배지 진행 4단계:** 학습 → 실습 → 평가 또는 검증 → 배지 인정. 실시간 학습은 이 순서와 별개임.

| 실무자 경로 | 언제 선택하나 |
|---|---|
| OpenAI 컨설팅 솔루션 | 폭넓은 기회 발굴, 가치 평가, 솔루션 안내 |
| ChatGPT 솔루션, Codex 솔루션 | 제품별 포지셔닝과 기회 추진 |
| ChatGPT 배포, Codex 배포, API 배포 | 제품별 배포와 구현 업무 |
| OpenAI 기술 | 아키텍처, 보안 등 제품 간 기술 판단 |
| OpenAI 사이버 | 방어적 사이버 보안과 Daybreak 워크플로 |

- **학습 계획 템플릿(약 5분):** 역할, 관련 경로, 습득할 역량, 다음 학습 단계 등을 적고 내 업무와 맞는지 자문함.

### 실무 적용 예시
- 고객 요구 파악과 가치 설명, 폭넓은 솔루션 안내가 주 업무 → OpenAI 컨설팅 솔루션 실무자 경로 선택.
- OpenAI가 처음이거나 다음 경로가 불확실 → Foundation으로 공통 기준을 쌓은 뒤 자가 질문으로 경로를 고름.
- 배지를 땄으니 부트캠프에 자동 참여할 수 있다고 생각 → 별도 자격과 초청 요건이 있으므로 따로 확인.

### 지식 점검 포인트
- Foundation 트랙의 목적 → **전문 트랙 선택 전에 공통 OpenAI 기초 지식 제공**.
- 기회 평가와 가치 설명, 솔루션 안내가 주 책임인 학습자 → **OpenAI 컨설팅 솔루션 실무자**.
- 배지가 나타내는 것 → **경로별 학습과 검증 요건으로 입증된 적용 능력**. 단순 참여나 자동 접근 권한이 아님.
- 제품 간 기술적 의사결정 → **OpenAI 기술 실무자**.
- API 솔루션 설계 및 제공 → **API 배포 실무자**.

  <h1 class="lesson-title">AI 안전 및 책임 있는 AI</h1>
</div>

> **한 줄 요약:** 고객의 AI 안전 우려를 유형별로 파악하고, 책임을 구분해 과장 없이 검증 가능한 표현으로 안전을 논의함.

### 핵심 내용
#### 파트너의 역할과 안전의 의미
- 책임 있는 AI는 고객 가치와 분리되지 않음. 단순한 관심을 신뢰할 수 있는 도입으로 바꿔 줌.
- 파트너가 안전이나 법률 전문가일 필요는 없음. 우려를 일찍 파악하고 언제 전문가 확인이 필요한지 아는 것이 역할.
- 안전은 켜고 끄는 옵션이 아니라 도입 라이프사이클 전반의 원칙. 안전 문제는 곧 신뢰와 평판 같은 비즈니스 문제.
- 하면 안 되는 일: 정확성이나 성과 보장, 법률 조언, 위험 제거 주장, 기억에 의존한 약속.

#### 일반적인 우려 사항
- 우려 유형마다 다음 조치가 다르므로 먼저 **어떤 우려인지 명명**해야 함.
- 편향: 완전히 편향 없는 AI는 없음. 결정이 민감하고 영향이 직접적일수록 인간 검토를 더 신중히.
- 환각: 그럴듯하지만 틀린 출력. 평가와 감소는 가능하나 완전 제거는 불가.
- 민감 분야의 중대한 의사결정은 현행 사용 정책상 자격 있는 사람의 검토 없는 자동화가 금지됨.
- 비즈니스 데이터는 고객 동의 없이는 기본적으로 모델 훈련에 쓰이지 않음. 계약 진술 전엔 요금제와 설정 대조 필수.

#### OpenAI의 안전 접근과 참고 자료
- 안전은 훈련, 테스트, 공유, 학습으로 이어지는 지속적 작업. "OpenAI가 이미 해결했다"는 표현은 피함.
- 참고 자료는 외우는 것이 아니라 상황에 맞게, 기억이 아닌 최신 출처로 안내함.
- 자료는 신뢰를 뒷받침할 뿐 고객 검토를 생략하는 수단이 아님. 범위를 넘으면 법무, 보안 등 전문가를 참여시킴.

#### 공동 책임
- OpenAI는 모델과 플랫폼 안전 작업, 공개 자료와 시스템 카드, 제품 수준 제어를 제공함.
- 그렇다고 모든 고객 사용 사례가 자동으로 적절하거나 규정을 준수하는 것은 아님.
- 파트너와 고객은 작업 적합성, 데이터 출처와 검토자, 내부 정책 정합성, 사용자의 한계 인식을 책임짐.
- 고객의 확신은 절대적 약속이 아니라 명확한 책임, 안전장치, 최신 출처, 현실적 기대에서 나와야 함.

### 기억할 개념·프레임워크
- **안전 대화 3단계:** 인식하기 → 책임 구분하기 → 확인(검증)하기.
  - 인식 예: "믿어도 되나요?"는 정확성, "누가 최종 승인하나요?"는 거버넌스 문제.
  - 확인: 큰 틀은 명확히 말하고, 구체적 약속은 현재 문서와 고객 요건을 확인한 뒤에 함.

| 고객 질문 | 안내할 자료 |
|---|---|
| OpenAI는 안전을 어떻게 보나? | OpenAI 안전 리소스 |
| 이 사용이 허용되나? | 이용 정책(Usage Policies) |
| 특정 모델의 기능과 한계는? | 배포 안전 허브, 시스템 카드 |
| 첨단 AI 위험은 어떻게 관리하나? | 대비 프레임워크(Preparedness Framework) |
| 데이터 훈련 사용과 개인정보 약속은? | 기업 개인정보 보호 자료 |

| 피할 표현 | 바꿀 방향 |
|---|---|
| "이 제품은 안전합니다" | 안전 투자 + 고객 워크플로와 거버넌스 고려 |
| "환각을 생성하지 않습니다" | 발생 가능, 출처 검증과 인간 검토로 감소·관리 |
| "규정 준수를 자동 충족" | 적용 여부는 고객 법무·보안 팀이 확인 |

### 실무 적용 예시
- 상담원 응답 속도를 원하면서 부정확한 답변 전달을 우려 → 출처 자료와 검토, 품질 모니터링 방식을 먼저 정하자고 제안함.
- 의료 기관이 "잘못된 지침을 따르면 누가 책임지나?" → 정책 출처와 검증자, 모니터링은 조직이 정해야 한다고 답함.
- "절대 틀리지 않는다고 보장하나요?" → 오류 없는 AI는 없다고 밝히고, 근거 정보와 사람 검토 지점을 확인함.

### 지식 점검 포인트
- 과장 없이 안전 우려를 해소하는 답 → **"AI 안전성은 사용 사례, 워크플로, 데이터, 감독 모델에 따라 달라진다"**.
- 특정 모델의 기능과 한계, 안전 정보를 볼 곳 → **배포 안전 허브 또는 관련 시스템 카드**.
- 내부 정책, 법적 검토, 규정 준수와의 조율 → **고객** 책임.
- "안전과 무편향을 보장하나요?" → **OpenAI는 안전 연구와 지침을 제공하지만, 귀사 적용은 직접 확인해야 한다**.

  <h1 class="lesson-title">AI가 비즈니스 혁신을 주도하는 방식</h1>
</div>

> **한 줄 요약:** AI의 비즈니스 가치를 4가지 패턴으로 설명하고, 기능과 산업을 넘어 구체적 워크플로에 연결해 과장 없이 이야기함.

### 핵심 내용
#### AI가 업무에 미치는 영향
- 많은 조직이 실험과 파일럿에서 일상 프로세스와 고객 접점에 AI를 쓰는 단계로 이동 중.
- 기존 소프트웨어는 정해진 경로를 따르게 하지만, AI는 필요를 설명하면 유용한 출발점을 만들어 줌.
- 같은 AI 기능도 워크플로, 인력, 거버넌스에 따라 결과가 크게 다름. 혁신은 자동으로 일어나지 않음.
- "AI로 생산성을 높이겠다"는 부족함. 구체적 워크플로와 사용자 그룹, 비즈니스 성과가 더 확실한 출발점.

#### 가치 창출 4가지 패턴
- 4패턴은 점수 모델이나 ROI 프레임워크가 아니라 **핵심 가치 스토리**를 파악하는 실용적 방법.
- 패턴은 자주 겹침. 예: 답변 초안 시간 단축(효율성)과 반복 문의 주제 도출.
- 효율성만이 가치는 아님. 주간 보고서 시간 절약의 더 큰 가치는 경영진이 빨리 우선순위를 정하는 것.
- 의사결정 품질은 인간 책임을 대체하지 않음. 계약 조항 요약을 받아도 최종 해석은 법무팀 몫.
- 대규모 개인화는 마케팅에 국한되지 않으며, 개인정보와 브랜드 정책과의 균형이 필요함.
- 새로운 역량 창출도 책임 있는 설계와 거버넌스가 필요. 중요한 워크플로일수록 사람 책임 지점을 명확히.

#### 기능과 산업 전반의 활용
- 기능은 영업이나 재무 같은 영역, 워크플로는 그 안의 구체적 업무. **워크플로가 가장 중요**함.
- 이 단계 목표는 솔루션 추천이나 ROI 산출이 아니라 예상 가치 패턴을 실무 언어로 설명하는 것.
- 산업마다 규제, 데이터 민감도 등 제약이 다름. 산업 사례는 설명용일 뿐 업계 전체에 대한 주장이 아님.
- "AI가 의료를 바꾼다" 대신 지식 접근, 문서 분석 같은 공통 워크플로 패턴 언어로 말함.

#### 과장 없이 말하기
- 피할 과장: 보편적 전환, 보장된 가치, 입증되지 않은 고객 사례, 마찰 없는 도입 등.
- 자가 점검: 워크플로 맥락을 밝혔나, 확언을 피했나, 다음에 검증할 것을 말했나?

### 기억할 개념·프레임워크

| 패턴 | 초점 | 예 |
|---|---|---|
| 효율성 | 수작업 부담 감소, 더 빠르게 | 회의 요약, 초안 작성 |
| 의사결정 품질 | 정보를 더 잘 활용 | 문서 비교, 위험 도출 |
| 대규모 개인화 | 대상별 맞춤 출력과 지원 | 맞춤 지원 응답, 현지화 |
| 새로운 역량 창출 | 이전에 불가능하던 업무 | 비기술자의 데이터 분석 |

- **기능 → 워크플로 질문:** 어떤 업무를 누가 하나, 어디서 오래 걸리거나 위험한가, 어떤 가치 패턴이 맞나 등 5가지.
- **재작성 템플릿:** "AI는 [워크플로]를 지원해 [기능]을 뒷받침할 수 있다. 다만 [검증할 사항]이 필요하다."
- **설명 흐름:** 고객 상황 → 가치 패턴 → 워크플로 영향 → 다음 탐구 사항.

### 실무 적용 예시
- "영업에 AI를 쓰고 싶다" → 분기 회의 전 임원용 계정 브리핑 준비로 좁히고, 효율성과 의사결정 품질로 설명함.
- "AI가 재무팀을 자동으로 혁신한다" → 기획 자료 요약과 월간 해설 초안을 돕되, 원자료와 검토 절차를 먼저 검증하자고 재작성.
- "ChatGPT가 이 팀에 맞는다"처럼 제품부터 말함 → "주간 보고 워크플로에 AI 지원이 필요할 수 있다"처럼 업무부터 말함.

### 지식 점검 포인트
- AI 주도 혁신의 설득력 있는 설명 → **AI는 실제 업무의 일부가 되지만, 영향은 워크플로와 거버넌스 등에 따라 달라진다**.
- 문서 비교와 검토 전 위험 파악 → **의사결정 품질**.
- 비기술 사용자가 전문가 도움 없이 데이터 분석 → **새로운 역량 창출**.
- 업종 일반화를 피한 문장 → **"금융에서 AI는 문서 검토 같은 워크플로를 지원할 수 있지만, 활용 사례와 통제는 검증돼야 한다"**.

  <h1 class="lesson-title">AI 및 머신러닝 핵심 기초</h1>
</div>

> **한 줄 요약:** AI 핵심 용어의 관계, "모델"의 두 의미, 모델 용어와 학습 방식을 익히고 "기능 먼저, 모델 이름은 필요할 때 확인" 습관을 기름.

### 핵심 내용
#### 핵심 AI 용어의 관계
- AI가 가장 넓은 범주. ML은 고정 규칙 대신 데이터에서 패턴을 학습하는 AI의 하위 개념.
- 딥러닝은 다층 신경망으로 복잡한 패턴을 학습하는 ML의 하위 분야. 현대 AI 기능 다수가 의존함.
- LLM은 언어를 처리하고 생성하는 딥러닝 모델의 한 유형일 뿐 **AI의 전부가 아님**.
- 고객이 "이미 AI를 쓴다"고 하면 바로잡으려 하지 말고 무엇을 뜻하는지 확인 질문을 함.

#### "모델"의 의미와 컨텍스트
- "모델"은 입력을 출력에 매핑하는 훈련된 시스템이자, 제품이나 API에서 고르는 명명된 옵션이기도 함.
- "어떤 모델을 써야 하나요?"는 여러 뜻일 수 있으므로 먼저 의미를 확인함.
- 모델은 고객의 비공개 문서나 내부 정책을 **자동으로 알지 못함**. 설정, 승인된 연결, 검색으로 제공돼야 함.
- "모델이 이미 귀사 비즈니스를 안다"는 접근 범위를 과장하므로 쓰지 않음.
- 모델, 제품, API 표면은 서로 다름. 같은 제품이나 API가 여러 모델을 지원할 수 있음.

#### 모델 용어와 기능 우선 습관
- 트랜스포머는 아키텍처일 뿐 제품이나 모델 이름이 아님. 이것만으로 사용 사례 적합성을 판단할 수 없음.
- 파운데이션 모델은 범용성을 뜻할 뿐, OpenAI를 뜻하거나 그 자체로 바로 쓸 솔루션이 되는 것은 아님.
- 프론티어 모델은 새 모델이 나오면 바뀌는 "특정 시점" 라벨. 고객 약속 전에 최신 공식 출처로 확인.
- 모델 이름과 가격, 가용성은 계속 바뀜. 먼저 필요한 기능을 말하고 정확한 이름은 확정 전에 확인함.
- 정확한 이름이 필요한 때: 코드와 구성, 가격 논의, 고객 약속, 공식 솔루션 권장 등.

#### 시스템이 학습하는 방식
- 인식 수준의 이해만 필요하며 훈련 파이프라인 설계는 다루지 않음.
- 실제 시스템은 여러 접근을 결합하기도 하므로 억지로 한 범주에 넣지 않음.

### 기억할 개념·프레임워크
- **계층 구조:** AI ⊃ 머신러닝 ⊃ 딥러닝. 신경망은 딥러닝에서 흔히 쓰는 구조.

| 용어 | 답하는 질문 |
|---|---|
| 트랜스포머 | 모델이 어떻게 구축되나(아키텍처) |
| 파운데이션 모델 | 얼마나 폭넓게 적용되나(범위) |
| 프론티어 모델 | 특정 시점에 얼마나 고성능인가(현재 수준) |

| 학습 방식 | 핵심 | 확인 질문 |
|---|---|---|
| 지도 학습 | 정답이 알려진 예시로 학습 | 레이블 있는 예시로 배우나? |
| 비지도 학습 | 정답 없이 구조 발견 | 레이블 없이 패턴을 찾나? |
| 강화 학습 | 피드백으로 행동 개선 | 피드백으로 점점 개선되나? |
| 혼합 시스템 | 여러 접근 결합 | 주요 학습 개념이 무엇인가? |

### 실무 적용 예시
- "이미 사기 탐지에 AI를 써요" → "고정 규칙인가요, 학습 모델인가요, 생성형 AI 워크플로인가요?"로 의미를 확인.
- "직원들이 ChatGPT에서 어떤 모델을 쓰나요?" → AI 시스템, 모델 옵션, 제품 경험 중 무엇을 묻는지 먼저 구분.
- "가장 저렴한 모델이면 돼요" → 품질 요건을 충족하는 비용 최적화 옵션을 찾고, 권고 전에 정확한 모델을 확인하자고 재작성.

### 지식 점검 포인트
- AI 용어의 정확한 관계 → **AI ⊃ ML ⊃ 딥러닝, 신경망은 딥러닝의 흔한 구조**. LLM이 AI 밖에 있다는 보기는 오답.
- 트랜스포머, 파운데이션, 프론티어의 의미 → **구축 방식, 활용 범위, 특정 시점의 성능 수준**.
- 기능 우선 표현의 좋은 예 → **"대량 데이터를 신뢰성 있게 요약해야 하므로, 정확한 모델 옵션을 확인해야 한다"**.
- 정답 없이 패턴을 찾는 방식 → **비지도 학습**.

  <h1 class="lesson-title">AI 응용 분야 및 기술</h1>
</div>

> **한 줄 요약:** 고객이 원하는 결과를 응용 패턴으로 해석하고, RAG와 에이전틱 AI를 과장 없이 설명하며, 세 가지 결정을 분리한다.

### 핵심 내용
#### 생성형 AI와 응용 패턴
- 고객은 AI 범주가 아니라 결과로 요청을 말한다. 이를 **응용 패턴**으로 번역하는 것이 목표다.
- 생성형 AI는 입력을 바탕으로 새 콘텐츠를 만든다. DB에서 정해진 답을 꺼내는 것과 다르다.
- 맥락이 빠지거나 정보가 낡아도 그럴듯한 결과가 나올 수 있다. 쓸 정보와 검토자를 묻는 계기로 삼는다.
- 한 워크플로에 여러 패턴이 섞인다. 지원 어시스턴트는 검색 기반 답변, 텍스트 생성, 분류, 요약을 함께 쓴다.
- 담당자 '전달'은 워크플로의 다음 단계일 뿐 AI 활동 유형이 아니다.

#### 개념 수준의 RAG
- RAG(검색 증강 생성)는 승인된 출처에서 관련 정보를 찾고, 그 정보로 답변을 만드는 방식이다.
- "RAG가 필요하다"는 대개 "우리 정보에 근거한 답변이 필요하다"는 뜻이다.
- 쓰는 이유는 고객별 지식, 최신 정보, 근거 확보, 투명성 지원이다. 임베딩 같은 구현 주제는 다루지 않는다.
- RAG는 **정확성을 보장하지 않는다**. 잘못된 검색이나 낡은 출처가 답변 품질을 떨어뜨릴 수 있다.
- 고위험, 규제, 고객 대면 워크플로에는 평가와 사람 검토가 여전히 필요하다.

#### 응용 패턴에서 솔루션 결정까지
- 응용 패턴은 AI가 '무엇을' 하는지만 알려준다. 인터페이스, 기능, 배포는 따로 결정한다.
- 고객 클라우드에서 앱이 돌아가도 모델 추론은 OpenAI 호스팅일 수 있다.
- 고객 직접 운영은 지원되는 오픈 웨이트 모델에만 해당한다. 독점 모델의 자체 호스팅을 가정하지 않는다.
- 상세 아키텍처, 가격, 구현 계획은 범위 밖이다. 검증할 사항을 정리해 전문가를 참여시킨다.

#### 에이전틱 AI와 AGI
- 에이전틱 AI는 단계 계획과 도구 사용으로 목표를 향해 진행하는 시스템이다. '고급 AI'의 동의어가 아니다.
- AGI는 장기 연구 목표로만 다룬다. 현재 제품을 AGI라 부르거나 AGI 기능을 약속하지 않는다.

### 기억할 개념·프레임워크

| 응용 패턴 | 예시 |
|---|---|
| 텍스트 생성 | 대상별 제품 발표 초안 3종 |
| 요약 | 갱신 회의 전 계정 이력을 위험과 조치로 요약 |
| 분류 | 티켓을 청구, 기술, 계정 접근 등으로 분류 |
| 이미지 생성 | 크리에이티브 브리프 기반 캠페인 비주얼 |
| 코드 생성 | 테스트 케이스 생성, 실패 원인 설명 |
| 검색 기반 답변 | 승인된 정책 문서 기반 출장 경비 정책 답변 |

| 결정 계층 | 질문 | 선택지 예 |
|---|---|---|
| 사용자·제품 인터페이스 | 사용자가 주로 어디서 일하나? | ChatGPT 채팅, ChatGPT Work, Codex, API 앱 |
| 기능·아키텍처 | 시스템이 무엇을 해야 하나? | 생성, 검색, 도구, 에이전트, 구조화된 출력 |
| 배포·운영 | 누가 어디서 운영하고 데이터는 어디로 가나? | 권한, 승인, 보존, 로깅, 사람 검토 |

- **배포 구성 4가지**
  - OpenAI 호스팅 추론(ChatGPT, API)
  - 고객 클라우드 앱 + OpenAI 호스팅 추론
  - 타사 호스팅 서비스: 제공업체별 약관과 데이터 경로를 확인한다.
  - 고객 직접 운영 오픈 웨이트 모델

### 실무 적용 예시
- "지원 팀이 더 빨리 대응하게" → 정보 검색, 답변 초안, 요청 분류, 요약으로 재기술하고 검토가 필요한 답변을 묻는다.
- 재무 월말 보고서 같은 위임형 지식 업무 → 패턴은 검색 기반 답변, 요약, 텍스트 생성이고 인터페이스는 ChatGPT Work다.
- HR 정책 Q&A → 승인된 내부 정책 문서가 근거여야 하므로 검색 기반 답변이 필요할 가능성이 높다.

### 지식 점검 포인트
- 티켓을 요청 유형별로 나누기 → **분류**. 각 티켓에 카테고리를 할당하기 때문이다.
- 자주 바뀌는 정책 문서 기반 답변 → **RAG는 승인된 출처로 답변을 뒷받침하지만 검토는 여전히 중요하다**.
- 자체 클라우드 앱이 OpenAI API로 응답 생성 → **앱 호스팅과 모델 추론은 별개의 결정**이다.

  <div class="eyebrow">레슨 07</div>
  <h1 class="lesson-title">AI 인프라 및 구현</h1>
</div>

> **한 줄 요약:** 아키텍처를 설계하지 않고도 앱·추론 위치, 데이터 이동, 실현 가능성 제약을 일찍 알아보고 전문가 참여 시점을 판단한다.

### 핵심 내용
#### AI 시스템이 구동되는 곳
- 하나의 솔루션이 여러 장소의 구성 요소를 결합할 수 있다. 예: 고객 클라우드 앱과 OpenAI 호스팅 추론.
- 고객 클라우드에서 앱이 돈다고 고객이 **모델을 운영**한다고 가정하지 않는다.
- 고객이 운영하는 구성 요소가 많을수록 업데이트, 모니터링, 사고 대응 같은 운영 책임도 커진다.
- 상충 관계는 환경 레이블 하나가 아니라 앱 위치, 추론 위치, 데이터 이동, 운영 책임의 조합에서 생긴다.
- 하드웨어는 의미만 알면 된다. GPU는 훈련과 대규모 추론에, NPU는 기기 내 로컬 AI 처리에 흔히 쓰인다.

#### 훈련과 추론
- **훈련**은 모델이 데이터에서 패턴을 학습하거나 조정되는 단계로, 대개 큰 연산과 방대한 데이터가 필요하다.
- **추론**은 훈련된 모델로 입력에서 출력을 만드는 단계다. 사용자가 접하는 대부분의 AI 경험은 추론이다.
- 추론에서는 응답 시간, 네트워크 경로, 규모, 비용이 중요하다.
- "모델을 훈련해야 한다"가 실제로는 비즈니스 맥락 이해를 뜻할 수 있다. 목표를 물으면 검색이나 컨텍스트가 답일 수 있다.

#### 실현 가능성 제약
- **지연 시간**: 음성 비서나 라이브 채팅은 빠른 응답이 필요하고, 예약 요약은 느려도 된다.
- **처리량**: 사용자 수, 사용 빈도, 입출력 크기로 정해지며 비용과 용량, 신뢰성에 영향을 준다.
- **데이터·개인정보**: 보존이나 거주지 같은 세부 사항은 추측하지 않고 승인된 출처로 확인한 뒤 약속한다.
- 제약은 대개 함께 나타난다. 고객 대상 어시스턴트는 빠른 응답, 대규모 사용자, 민감 데이터를 동시에 요구한다.

#### 인프라가 구현 타당성에 미치는 영향
- 인프라 결정은 선호 기술이 아니라 **워크로드** 이해에서 시작한다.
- 같은 요약 기능도 소규모 내부 팀용과 규제 대상 대고객 프로세스용은 고려 사항이 다르다.
- "AI 어시스턴트가 필요하다"만으로는 판단할 수 없다. 역할, 데이터 이동, 응답 속도, 사용자 수 등을 파악한다.

### 기억할 개념·프레임워크

| 배포 질문 | 핵심 | 주의점 |
|---|---|---|
| 애플리케이션 위치 | 사용자 대면 앱이 어디서 실행되나 | 이것만으로 추론 위치를 알 수 없음 |
| 모델 추론 위치 | 모델이 어디서 입력을 처리하나 | 고객 클라우드 앱 ≠ 고객이 모델 운영 |
| 운영 책임 | 누가 설정, 모니터링, 지원하나 | 고객 운영 요소가 많을수록 책임 증가 |
| 데이터 이동 | 무엇이 이동하고 어떤 권한이 적용되나 | 앱·추론 위치와 별도로 파악 |

- **배포 구성 사례:** OpenAI 호스팅 작업 공간, 고객 클라우드 앱과 호스팅 추론, 고객 운영 추론, 엣지 분할 처리. 서로 배타적이지 않다.
- **기업 운영 관점:** 컨텍스트는 AI가 알아야 할 것, 런타임은 실행 위치와 데이터 이동, 가시성은 모니터링과 개선이다.

### 실무 적용 예시
- 소매업체 지원 앱은 자체 클라우드, 추론은 OpenAI 호스팅 → 데이터 경로와 양측 운영 책임을 따로 파악한다.
- 어시스턴트를 승인된 정책 문서와 연동하려는 요청 → 새 훈련이 아니라 맥락, 출처, 권한 부여가 핵심이다.
- 연결이 불안정한 현장에서 앱과 추론을 기기에서 실행 → 기술 팀이 설계 전 명확히 할 배포 세부 사항을 정리한다.

### 지식 점검 포인트
- 소매업체 클라우드 앱이 OpenAI 호스팅 모델로 요청을 보냄 → **앱은 고객 클라우드, 추론은 OpenAI 호스팅**.
- 정책 문서 요약 요청에 훈련된 모델이 응답 생성 → **추론**.
- 워크로드별 핵심 제약:
  - 사용자가 말하는 동안 응답하는 음성 비서 → **지연 시간**
  - 수백만 건 요청을 받는 고객 대상 앱 → **처리량**
  - 민감한 고객 기록을 쓰는 워크플로 → **데이터·개인정보 보호**
- 빠른 응답, 많은 사용자, 고객 데이터가 모두 필요한 어시스턴트 → **여러 제약을 동시에 고려**.

  <h1 class="lesson-title">에이전트 및 에이전트 기반 워크플로우</h1>
</div>

> **한 줄 요약:** 에이전트를 업무 완수를 돕는 시스템으로 보고, 구성 요소와 적합 신호, 결정 계층, 과장 없는 표현법을 익힌다.

### 핵심 내용
#### 에이전트란 무엇이며 왜 중요한가
- **AI 에이전트**는 무엇을 할지 추론하고, 맥락을 활용하며, 도구로 조치를 취해 목표를 달성하는 시스템이다.
- 에이전시는 연속체다. 단일 프롬프트 응답은 낮고, 정보 수집부터 사람 검토까지 이어지는 워크플로는 높다.
- 단계가 늘어도 사람의 지시, 권한, 검토가 시스템이 할 수 있는 범위를 정한다.
- 가치는 첨단처럼 들려서가 아니라 실제 워크플로의 마찰을 줄일 때 생긴다.

#### 에이전틱 워크플로의 구성 요소
- 유능한 모델만으로는 부족하다. 목표, 지침, 맥락, 도구, 인계, 사람 점검이 함께 운영 방식을 정한다.
- **목표**는 구체적이어야 한다. "좋은 호텔 찾아줘"보다 비교 기준과 예약 전 승인 요청까지 담는다.
- 도구 접근 권한은 구매 승인이 아니다. 서비스 접근, 작업 수행 권한, 특정 구매 승인은 별개다.
- **인계**는 무슨 일이 있었고, 무엇이 남았으며, 다음은 누가 할지 알게 해 준다.
- 승인과 검증은 다르다. 승인은 조치를 허용하고, 검증은 결과가 승인된 결정과 맞는지 확인한다.

#### 에이전틱 워크플로가 필요한 경우
- 모든 AI 워크플로가 에이전틱일 필요는 없다. 단순 답변, 초안, 분류로 충분한 경우가 많다.
- "문서 요약"은 단순하고, "요약 후 현재 정책과 비교해 상충을 표시하고 법무팀에 전달"은 다단계다.
- 에이전틱 워크플로는 도구 접근, 상태 추적, 권한, 모니터링 같은 복잡성을 더한다.

#### 기술 경로와 표현
- 인터페이스, 기능, 운영 모델은 따로 결정한다.
- 일회성 다단계 보고서는 **ChatGPT Work**, 같은 프로세스를 반복·공유·일정 실행하면 워크스페이스 에이전트가 맞다.
- 제품 내장이 필요하면 API 기반 경로다. 고객이 UI와 통합을 제어하는 만큼 기술·운영 책임도 커진다.
- 소프트웨어 제공은 별도 인터페이스가 아니라 워크로드다. Codex, API 앱, 또는 그 조합을 쓴다.
- 신뢰할 수 있는 논의는 정의된 업무, 명확한 경계, 적절한 감독, 검증할 사항에 초점을 둔다.

### 기억할 개념·프레임워크

| 구성 요소 | 핵심 질문 |
|---|---|
| 목표 | 어떤 결과를 향해 일하나? |
| 지침 | 어떤 규칙과 경계가 이끄나? |
| 맥락 | 어떤 정보를 쓸 수 있나? |
| 도구·앱 | 어떤 시스템과 기능에 접근하나? |
| 작업(조치) | 어떤 행동을 할 수 있나? |
| 상태·메모리·인계 | 어디까지 왔고, 다음은 누가 하나? |
| 가드레일·인적 점검 | 무엇을 하면 안 되고, 누가 승인하나? |

- **적합 신호:** 여러 단계, 목표 지향 과정, 도구와 시스템 상호작용, 변화하는 상황, 사람 감독 필요.
- **불필요할 수 있는 경우:** 단일 턴 응답, 단순 생성, 가치 낮은 자동화, 감독 미흡한 고위험 자동화.
- **세 결정 계층:** 사용자·제품 인터페이스, 기능·아키텍처, 배포·운영. 통합 솔루션도 계층별로 평가한다.
- **흔한 오해:** 완전 자율, 항상 정확, 자동으로 안전, 사람 개입 불필요, 에이전트 = AGI. 모두 틀리다.

### 실무 적용 예시
- 계정 메모 검토부터 업데이트 초안, 검토 필요 항목 표시까지 하는 주간 계정 업데이트 → 다단계라 에이전틱이다.
- ChatGPT Work로 출장 호텔 예약 → 일정에 영향을 주는 절충은 구매 전 승인받고, 여행자가 실제 내역과 대조한다.
- "사람 개입 없이 올바른 호텔을 예약한다" → "허용된 도구 범위에서 비교하고 구매 전 승인을 받는다"로 고쳐 쓴다.

### 지식 점검 포인트
- 에이전시가 가장 분명한 예 → **계정 메모 검토, 활동 확인, 초안 작성, 검토 항목 표시**.
- 계속하기 전 누가 검토하고 승인하나 → **인적 점검 단계**.
- 분류, 승인 정보 검색, 답변 초안, 복잡 사례 전달을 원하는 고객 → **에이전틱 워크플로를 시사**.
- 관리자가 역할, 권한, 승인, 로깅을 정의 → **배포 및 운영 계층**.
- 과장 없는 설명 → **승인된 도구 접근, 검토 단계, 모니터링 범위 안에서 분류하고 초안을 쓰고 전달한다**.

  <h1 class="lesson-title">OpenAI 제품 포트폴리오 개요</h1>
</div>

> **한 줄 요약:** 포트폴리오를 세 개의 독립된 결정 계층으로 나누고, 워크플로 단서와 다섯 솔루션 패턴으로 '워크플로 우선' 매핑을 한다.

### 핵심 내용
#### OpenAI 포트폴리오 이해하기
- 질문을 "어떤 제품을 써야 하나?"에서 개선할 워크플로, 필요한 기능, 실행과 제어 방식으로 옮긴다.
- 도입이 성숙할수록 가치는 개인 생산성을 넘어 워크플로와 운영 모델에 지능을 내재화하는 데로 넓어진다.
- 표면마다 역할이 다르다.
  - ChatGPT Chat: 함께 탐구하고 다듬는 협업 방식.
  - ChatGPT Work: 결과와 범위를 정하고 맡기는 위임 방식.
  - API 앱: 조직이 관리하는 제품과 시스템에 지능을 내장.
  - Codex: 소프트웨어 계획부터 유지 관리까지 전용 플랫폼.
- 에이전트적 행동은 별도 제품 경로가 아니라 ChatGPT Work나 API 프로세스 안에서 나타나는 **기능**이다.
- 오픈 웨이트 모델은 모든 제어 요건의 기본 해법이 아니라 검증할 하나의 배포 옵션이다.
- 모델 선택은 포트폴리오 결정과 별개다. GPT-6 Astra는 모델일 뿐 별도 인터페이스가 아니다.

#### 기술의 적용 분야 파악하기
- 직원이 주 사용자이고 생산성이 목표면 ChatGPT다. 메모 요약은 Chat, 다단계 브리핑 위임은 Work.
- AI가 기존 제품이나 포털에 내장되고 맞춤형 UX가 필요하면 API 앱이다.
- 엔지니어링 팀이 주 사용자이고 소프트웨어 전달이 핵심이면 Codex를 먼저 검토한다.
- 다단계, 도구, 승인이 보이면 에이전트 기능이지만, 이것만으로 인터페이스나 배포 모델이 정해지지 않는다.
- "우리가 제어하는 환경이어야 한다"는 결론이 아니다. 앱 위치, 추론 위치, 운영 주체, 데이터 이동을 구분한다.

#### 워크플로 중심 접근법
- 하나의 비즈니스 문제도 여러 워크플로를 포함한다. 한 제품을 전체에 일률 적용하지 않는다.
- 모든 사용자가 같은 인터페이스를 필요로 한다고 가정하지 않는다.
- 이 단계의 목표는 최종 권고가 아니라 **1차 지도**와 검증 필요 항목이다.

### 기억할 개념·프레임워크

| 계층 | 핵심 질문 | 예시 |
|---|---|---|
| 사용자·제품 표면 | 주로 어디서 운영되나? | ChatGPT Chat, ChatGPT Work, Codex, API 앱 |
| 기능·아키텍처 | 시스템이 무엇을 해야 하나? | 앱과 도구, 워크스페이스 에이전트, 검색 |
| 배포·운영 | 어디서 어떻게 실행, 제어되나? | 호스팅 또는 임베디드, 권한, 로깅 |

| 솔루션 패턴 | 잠재 표면과 기능 |
|---|---|
| 직원 생산성·지식 업무 | ChatGPT Chat·Work, 앱, 심층 연구 |
| 고객 경험 | API 앱, 에이전트 기능, 검색 |
| 소프트웨어 제공·엔지니어링 가속화 | Codex, 필요 시 API 통합 |
| 워크플로 자동화·에이전트 업무 | 워크스페이스 에이전트, 도구, 사람 승인 |
| 유연한 배포 요구 | 호스팅 추론, 고객 클라우드 앱, 오픈 웨이트 |

- **네 가지 운영 개념:** 컨텍스트, 런타임, 가시성, 거버넌스. 모니터링과 정책 통제를 구분한다.
- **워크플로 우선 순서:** 고객 문제 → 사용자·제품 표면 → 기능·아키텍처 → 배포·운영.

### 실무 적용 예시
- 지역 보험사의 "AI를 쓰고 싶다" → 고객 서비스는 ChatGPT, 레거시 유지보수는 Codex, 디지털 채널은 API 앱으로 나눈다.
  - 표면은 달라도 운영과 거버넌스는 일관되게 적용할 수 있다.
- 금융 서비스 기업의 여러 요구 → 직원 생산성, 고객 경험, 자동화, 배포 요구 패턴을 먼저 찾고 세 계층에 매핑한다.

### 지식 점검 포인트
- 고객 운영 오픈 웨이트 모델 → **배포·운영 계층에서 검증할 옵션**.
- 음성, 이미지 생성, 심층 연구 → **사용 범위를 확장하는 기능과 인터페이스**.
- 직원 보고서, 제품 내 고객 도움, 플랫폼 현대화를 동시에 원함 → **워크플로로 나눠 각각 세 계층에 매핑**.
- 기존 포털에서 복잡한 계정 업데이트를 돕는 AI → **API 기반 앱, 다단계면 에이전트 기능 활용**.
  - 개인정보, 신원, 로깅 같은 운영 요구는 별도로 평가한다.

  <h1 class="lesson-title">ChatGPT 에센셜</h1>
</div>

> **한 줄 요약:** ChatGPT의 역할과 API·Codex와의 차이, 요금제와 거버넌스, '작업 + 맥락 + 기대치' 프롬프트와 대표 워크플로를 익힌다.

### 핵심 내용
#### ChatGPT란 무엇이며 왜 중요한가
- ChatGPT는 협업적 사고와 창작, 가능한 경우 위임된 지식 업무를 위한 OpenAI의 **최종 사용자용 AI 제품**이다.
- Chat은 질문, 초안, 요약, 분석을 후속 프롬프트로 다듬는 협업형 작업이다.
- **Work**는 다단계 지식 업무를 위임하는 방식이다. 사용자는 결과를 정의하고 중요한 조치를 승인한다.
- ChatGPT는 제품이고, GPT-6 Astra 같은 모델이 그 안에서 기반 지능을 제공할 수 있다.
- 정확성 확인, 민감 정보 보호, 최종 결정의 책임은 항상 사용자에게 있다.

#### 요금제 및 업무 환경 고려 사항
- 개인 계정을 각자 쓰면 조직은 사용 현황과 정책 준수를 파악하기 어렵다. 관리형 작업 공간이 이를 해소한다.
- 플랜은 조직 규모만이 아니라 워크플로, 거버넌스 요구, 데이터 위치, 필요한 제어로 고른다.
- Business와 Enterprise의 입출력은 기본적으로 **모델 훈련에 쓰이지 않는다**. 최신 내용은 공식 채널로 확인한다.
- 요금제 이름, 기능, 모델 제공 여부는 바뀔 수 있으니 약속 전 승인된 출처로 확인한다.

#### 더 나은 출력을 위한 프롬프트 기본
- 실용 패턴은 **작업 + 맥락 + 기대치**다. 매번 다 쓸 필요는 없고, 필요한 정보를 떠올리게 하는 사고 도구다.
- 예: "이 보고서를 고위 경영진 대상으로, 핵심 위험 3가지 중심, 글머리 5개 이하로 요약".
- 진짜 기술은 첫 응답에 반응하며 다듬는 반복이다. "더 짧게", "어떤 가정을 하고 있나요?" 같은 후속 지시를 쓴다.
- Work 같은 위임형 작업에서는 제약, 승인 범위, 검토 기준 정의가 초기 지시만큼 중요하다.

#### 워크플로와 자신감 있는 사용
- 사용자는 기능이 아니라 완료할 업무에서 출발하므로 워크플로 관점으로 설명한다.
- 분석에서는 중요한 조건을 명시한다. 예: 유지율 표의 미래 빈 칸은 0이 아니라 아직 관측되지 않은 값이다.
- 맥락과 위임이 늘수록 권한, 승인 범위, 출처 검증의 중요성도 커진다.
- 좋은 첫 워크플로는 실용적이고 검토하기 쉬운 것이다. 작게 시작하고, 맥락을 주고, 출력을 검토한다.

### 기억할 개념·프레임워크

| 구분 | ChatGPT Chat | ChatGPT Work | OpenAI API | Codex |
|---|---|---|---|---|
| 주요 사용자 | 직원 | 지식 근로자 | 개발자 | 엔지니어링 팀 |
| 상호작용 | 협업 | 위임 | 구축·통합 | 엔지니어링 업무 위임 |
| 적합 영역 | 사고·창작 | 다단계 지식 업무 | 임베디드·맞춤형 AI | 소프트웨어 공학 |

| 기능 | 쓰는 때 |
|---|---|
| 프로젝트 | 관련 채팅, 파일, 지침을 한곳에 모을 때 |
| 맞춤형 GPT | 특정 작업용 재사용 어시스턴트가 필요할 때 |
| 앱(예전 명칭 커넥터) | 승인된 외부 도구와 정보에 연결할 때 |
| 심층 연구 | 여러 출처를 깊이 조사할 때 |
| 워크스페이스 에이전트 | 반복 작업을 공유하고 예약 실행할 때 |

- **5대 워크플로:** 학습·탐구, 검색·연구 지원, 작성·협업, 분석·해석, 간단한 반복 지원.
- **사용자 자신감 4요소:** 명확한 예시, 안전한 사용 지침, 시작용 프롬프트, 실습 기회.

### 실무 적용 예시
- 경비 승인 공지문 작성 → 대상, 어조, 200단어 제한을 담아 요청하고 "더 짧게" 같은 후속 지시로 다듬는다.
- 직원은 개인 계정을 쓰고 리더는 가시성이 없음 → 관리형 작업 공간으로 옮기고 검토 기준을 합의한다.
- 고객 미팅 준비가 반복됨 → 큰 브리핑은 Work에, 반복 준비는 Workspace Agent에 맡기되 공유 전 출처를 검토한다.

### 지식 점검 포인트
- 개인 계정을 쓰는 팀의 리더가 감독과 지침을 원함 → **관리형 작업 공간**.
- 채팅, 파일, 지침을 한곳에 모으고 싶음 → **프로젝트**.
- 다단계 지식 업무를 맡기고 결과를 검토 → **ChatGPT Work**.
- 정확도가 걱정되는 신규 사용자의 첫 단계 → **저위험 워크플로와 안전 사용 지침**.
  - 결과 검토의 필요성도 함께 상기시킨다.

> **한 줄 요약:** Codex를 소프트웨어 개발용 코딩 에이전트로 이해하고, 코딩 지원과의 차이와 에이전트 기반 소프트웨어 전달 개념을 익힌다.

### 핵심 내용
#### Codex란 무엇이며 왜 중요한가
- Codex는 OpenAI의 **코딩 에이전트**다. 코드 스니펫을 넘어 소프트웨어 작업 자체를 지원한다.
- ChatGPT 데스크톱 앱, Codex CLI, IDE 확장, Codex 클라우드, GitHub 워크플로로 쓴다(요금제와 구성에 따라 다름).
- 엔지니어링 과제의 상당수는 코딩이 아니라 **워크플로 과제**다. 시스템 파악, 결함 조사, 테스트, 문서화에 시간이 든다.
- 엔지니어링 요구를 일반 생산성이나 API 구축으로 기본 취급하지 말고, 소프트웨어 전달 업무인지 먼저 본다.
- 방향 설정, 검토, 승인, 최종 결정의 책임은 여전히 사람에게 있다.

#### Codex의 차별점
- "날짜 포맷 함수 작성"은 좁은 코딩 작업, "결제 실패 원인 조사 후 해결안 제안"은 소프트웨어 전달 작업이다.
- **프롬프트**는 응답을 요청하고, 위임은 목표와 달성에 충분한 맥락을 준다.
- 경계 밖 작업, 네트워크 사용, 높은 권한이 필요한 작업은 승인이 필요할 수 있다.
- 코드에 드러나지 않는 비즈니스 규칙과 판단이 있어, 에이전트 기반 전달은 대체가 아니라 협업이다.

#### 일반적인 소프트웨어 전달 워크플로
- 구체적 목표가 실행과 검토 모두 쉽다. "양식 개선"보다 "필수 입력 누락 시 오류를 보여 주는 검사 추가"가 낫다.
- 공개 API 변경 금지처럼 바꾸면 안 되는 제약은 팀이 정의한다.
- GitHub 워크플로로 PR 검토를 구성할 수 있지만, 발견 사항 처리와 진행 여부는 엔지니어가 정한다.

#### 에이전트 기반 소프트웨어 전달
- AI 개발 지원은 코드 완성, 코딩 지원, **에이전트 기반 소프트웨어 전달** 순으로 진화했다. 제안에서 위임으로의 전환이다.
- 장시간 비동기 작업은 "설정하고 방치"가 아니라 다른 협업 리듬이다. 사람은 진행을 검토하고 방향을 승인한다.
- Codex가 확인 없이 할 구현과 검증 단계를 미리 합의하고, 병합과 배포는 사람이 결정한다.
- 진행 메시지나 소요 시간은 완료의 증거가 아니다. 변경에 맞는 의미 있는 검증이 필요하다.
- 올바른 질문은 "코드를 생성할 수 있나?"가 아니라 "어디에 지원이 필요하고, 무엇을 위임할 만큼 명확한가?"다.

### 기억할 개념·프레임워크

| 경로 | 지원 대상 | 기억법 |
|---|---|---|
| ChatGPT | 최종 사용자의 협업·위임 지식 업무 | 사람이 작업 공간에서 협업하거나 위임 |
| OpenAI API | 제품, 앱, 워크플로에 AI 통합 | 개발자가 AI를 통합 |
| Codex | 엔지니어링 팀의 소프트웨어 전달 | 엔지니어링 팀이 전달 업무에 활용 |

- **4대 워크플로:** 시스템 이해·문제 조사, 구축·개선, 테스트·검증·검토, 문서화·유지보수.
- **위임 과제 5요소:** 목표, 맥락, 제약, 예상 결과, 검토 기대.
- **사람이 제공하는 5가지:** 방향성, 맥락, 판단, 승인, 책임.
- **조직이 기대하는 성과:** 출시 속도와 품질 향상, 엔지니어링 역량 확대, 반복 업무 감소.

### 실무 적용 예시
- 백로그 팀이 "코드를 더 빨리 쓰려면?"을 물음 → 실제 시간은 조사, 테스트, 문서에 쓰이므로 전달 업무 전반으로 질문을 넓힌다.
- Blossom Airlines 예약 실패 수정을 위임 → 테스트로 정상 동작을 확인했어도 증거의 충분성은 엔지니어가 판단한다.
  - 검사는 UI가 아닌 예약 로직만, 재테스트는 'Blossom One' 운임만 다뤘다.
- 중복 이메일 CSV 가져오기 실패 → "DB 스키마는 바꾸지 말고 최소 수정과 실행할 테스트를 요약하라"처럼 위임한다.

### 지식 점검 포인트
- Codex를 가장 잘 설명하는 것 → **소프트웨어 개발과 엔지니어링 워크플로를 위한 OpenAI의 코딩 에이전트**.
- 코딩 지원과 에이전트 기반 전달의 차이 → 코딩 지원은 산출물을, 에이전트 기반 전달은 **사람 검토 아래 전달 성과**를 돕는다.
- 에이전트 기반 전달의 가장 명확한 예 → **실패 재현, 범위 내 수정, 검사 실행, 병합 전 사람 검토용 결과 제출**.
  - 테스트 결과는 검토 근거일 뿐 릴리스를 자동 승인하지 않는다.
- 엔지니어가 레거시 이해와 테스트, 문서에 시간을 많이 씀 → **전달 라이프사이클 전반의 워크플로 문제**로, Codex가 해법이 될 수 있다.

  <h1 class="lesson-title">API의 핵심</h1>
</div>

> **한 줄 요약:** OpenAI API를 고객이 제어하는 제품과 워크플로에 AI를 내장하는 통합 경로로 이해하고, 통합 패턴과 안전 장치를 익힌다.

### 핵심 내용
#### API란 무엇이며 왜 중요한가
- **API**는 한 소프트웨어 시스템이 다른 시스템과 통신하도록 정의된 규칙의 집합이다.
- 기본 흐름은 요청과 응답이다. 날씨 앱은 기상 서비스가 데이터를 어떻게 모으는지 몰라도 API로 받아 쓴다.
- API가 없으면 AI는 별도 제품으로만 쓸 수 있다. 많은 조직은 포털, 내부 앱, 제품 안에 AI가 들어가길 원한다.

#### OpenAI API란?
- OpenAI API는 OpenAI 모델과 기능으로 애플리케이션을 구축하는 **개발자 플랫폼**이다.
- 새 맞춤형 프로젝트는 **Responses API**로 시작하길 권장한다. 추론, 도구 사용, 다단계 작업에 가장 적합하다.
- GPT-6 Astra는 API로 쓸 수 있는 모델이다. 도구, 권한, 승인 제어는 주변 애플리케이션이 정한다.
- 핵심 질문은 "고객이 자신이 제어하는 소프트웨어 안에 내장된 경험이 필요한가"이다.

#### 일반적인 API 사용 사례와 통합 패턴
- 고객은 기능 이름이 아니라 "제품에 AI 어시스턴트를 넣고 싶다" 같은 요구로 말한다.
- 내장형 어시스턴트는 사용자가 별도 작업 공간으로 이동하지 않는다는 점이 ChatGPT 직접 사용과 다르다.
- 후속 시스템에 신뢰할 계약이 필요하면 **JSON 스키마 기반 구조화된 출력**으로 응답 형식을 정한다.
- 도구 사용 시 모델은 조회를 요청할 뿐, 도구를 실행하고 결과를 돌려주는 것은 애플리케이션이다.
- 턴 도중 방향 전환(mid-turn steering)은 응답 방향을 바꾸지만, 시작된 작업을 되돌리거나 도구 호출을 취소하지는 않는다.

#### 어떤 상황에서 API 솔루션이 필요한지 파악하기
- 가장 확실한 단서는 AI를 고객이 관리하는 제품에 내장하고, 사용자가 그 제품을 떠나지 않아야 하는 경우다.
- 모델 선택은 별개 결정이다. 설계 확정 전 기술 팀이 모델 접근성과 기능 지원을 확인한다.
- 예: 턴 도중 방향 전환은 현재 Responses API의 WebSocket 연결과 GPT-6 Astra가 필요하다.

### 기억할 개념·프레임워크

| 경로 | 가장 적합한 경우 |
|---|---|
| ChatGPT | 바로 쓰는 AI 작업 공간이 필요할 때 |
| OpenAI API | 기존 제품, 포털, 내부 도구에 AI를 통합할 때 |
| Codex | 코드 작성, 검토, 테스트 등 소프트웨어 전달 |

| API 패턴 | 예 |
|---|---|
| 내장형 어시스턴트 | 기존 지원 포털 안의 질문 응대 |
| 검색·지식 접근 | 승인된 내부 문서로 답변 |
| 구조화된 추출 | 이메일 필드를 뽑아 검토용 기록으로 |
| 도구 사용 | 내부 시스템에서 주문 상태 확인 |
| 실시간·다중 모달 | 음성으로 묻고 실시간 음성 응답 |

- **API 안전 장치 체크리스트**
  - 출력: 검토와 안전 점검, JSON 스키마 기반 구조화.
  - 조치: 도구 사용 범위와 승인, 중대한 결정의 사람 감독.
  - 접근: 권한 경계, 인증과 키 관리(API 키는 기밀).
  - 운영: 로깅과 모니터링, 요청 제한, 데이터 보존.

### 실무 적용 예시
- 로그인한 고객이 포털을 떠나지 않고 승인된 콘텐츠로 답을 받길 원함 → API로 포털에 AI를 내장한다.
- 주문 변경 이메일 수백 통 → 주문 번호, 변경 요청, 긴급도를 추출해 검토용 구조화 기록으로 바꾼다.
- ChatGPT로 메모를 쓰는 직원과 정책 답변을 내는 HR 포털 → 전자는 작업 공간, 후자는 API 기반 솔루션이다.

### 지식 점검 포인트
- API의 기능 → **정의된 규칙으로 한 시스템이 다른 시스템과 통신하게 함**.
- 자체 제어하는 환경으로 기존 고객 포털에 AI 구현 → **OpenAI API**.
- 기존 HR 포털에서 승인된 정책 답변을 일관된 형식으로 → **OpenAI API**.
  - 기존 포털 내 경험, 승인된 컨텍스트, 시스템용 출력 형식이 API 신호다.

> **한 줄 요약:** 고객 문제에서 워크플로를 파악하고, 솔루션 패턴을 세 계층으로 나눠 설계하며, 산업 맥락에 맞춰 측정 가능한 성과와 잇는다.

### 핵심 내용
#### 고객 문제에서 솔루션 패턴으로
- 고객은 제품 이름이 아니라 마찰을 말한다. 예: "정보 찾는 데 시간이 너무 든다", "배포가 느리다".
- 문제부터 파악하면 성급한 제품 추천을 피한다. ChatGPT를 묻는 고객도 더 넓은 워크플로 솔루션이 필요할 수 있다.
- **워크플로**는 사람, 작업, 의사결정, 정보 흐름, 결과의 순서다. 이를 보면 AI의 기여 지점이 드러난다.
- 솔루션 패턴은 흔한 문제를 해결하는 재사용 가능한 방법이며 제품과 다르다.

#### 기술을 결합해 완전한 솔루션 구축하기
- **단일 제품 솔루션**은 주요 인터페이스 하나로 주된 워크플로가 해결되고 필요한 제어가 명확할 때 맞다.
- 다중 제품 솔루션은 직원용 ChatGPT와 고객용 API처럼 여러 인터페이스를 쓰되, 결정은 계층별로 분리한다.
- 제품 내장, 신뢰할 지식, 다단계 완료는 서로 대체하는 경로가 아니라 **서로 관련된 결정**이다.
- 가장 효과적인 솔루션이 가장 복잡한 것은 아니다. 워크플로와 위험 수준에 맞는 조합이 최선이다.

#### 산업별 솔루션 사례
- 같은 패턴도 산업마다 맥락, 위험, 이해관계자가 달라 적용 방식이 바뀐다.
- 금융 서비스의 성과는 검색 속도 향상을 넘어 규정을 준수하는 시기적절한 고객 서비스다.
- 의료·생명과학은 정확성, 출처 품질, 개인정보, 전문가 검토가 책임 있는 도입의 핵심이다.
- 산업 라벨로 제품을 자동 선택하지 말고, 산업 맥락으로 **패턴을 조정**한다.

### 기억할 개념·프레임워크
- **솔루션 사고 순서:** 고객 문제 → 워크플로 → 제품 인터페이스 → 기능 → 배포·운영 → 솔루션 패턴 → 결과.
- **워크플로 점검 4요소:** 사람, 결정, 정보 흐름, 결과.

| 패턴 | 주 인터페이스 | 성과와 유의점 |
|---|---|---|
| 지식·정보 접근 | 직원용 ChatGPT, 내장형은 API 앱 | 검색 시간 단축, 셀프 서비스 향상 |
| 콘텐츠·커뮤니케이션 | 반복 초안은 Chat, 다단계 제작은 Work | 거친 의도를 검토된 소통으로 빠르게 |
| 소프트웨어 전달·엔지니어링 | Codex | 개발 주기 단축, 테스트와 리뷰 강화 |
| 연구·분석 | 연구자용 ChatGPT 또는 내장형 API | 판단과 최종 결론은 사람 몫 |

- **업계 공통 교훈:** 워크플로부터 시작하고, 결정을 분리하고, 시간 절감이나 재작업 감소 같은 영향을 측정한다.
- **솔루션 패턴 스냅샷**은 구현 계획이나 최종 제품 추천이 아니라 패턴 수준에 머문다.

### 실무 적용 예시
- 방대한 지식베이스 검색에 시간을 쓰는 금융 자문가 → 자문가용 ChatGPT에 승인된 지식 검색과 전문가 검토를 더한다.
- 거친 회의록을 내부 업데이트로 정리하는 소규모 운영 팀 → 다른 시스템 통합이 필요 없어 ChatGPT Chat만으로 충분하다.
- 직원 답변 검색, 포털 내 고객 지원, 일부 시스템 조치를 원하는 지원 조직 → 직원용 ChatGPT와 고객용 API 포털을 결합한다.

### 지식 점검 포인트
- 내부 문서 검색에 시간이 많이 듦 → **지식 지원**.
- 사례 요약과 답변 초안 → **고객 서비스 강화**.
- 검증된 지식, 도구 사용, 사람 승인이 필요함 → **선택한 인터페이스 위에 얹는 기능과 운영 요구**.
- 산업 맥락의 활용법 → **패턴을 정하기 전에 워크플로와 위험, 이해관계자를 이해하고 패턴을 조정**.
  - 산업 라벨로 제품을 고르지 않는다.
