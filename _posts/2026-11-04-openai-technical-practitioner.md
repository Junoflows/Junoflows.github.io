### 통합 최종 정리 — OpenAI 기술 실무자

#### 한 문단 요약
기술 실무자는 모델이나 제품 이름부터 꺼내지 않는다. **워크플로우에서 출발해** 인터페이스 / 기능·아키텍처 / 배포·운영이라는 세 결정을 분리하고(1강), 코드 이전에 구현 라이프사이클과 책임 소재를 짚으며(2강), 작업 형태로 모델 클래스와 솔루션 패턴을 고르고(3강), 꼭 필요한 최소 역량 세트만 조합해(4강), 재사용 가능한 패턴을 간결한 1차 청사진으로 옮긴다(5강). 이 모든 단계에 데이터·권한·조치 위험·통제를 처음부터 넣어 거버넌스를 신뢰 수단으로 삼는다(6강). 결과물은 언제나 "확정 설계"가 아니라 **가정과 검증 필요 사항, 에스컬레이션 대상이 드러난 예비 권고**다.

#### 과정 전체 흐름
```
[1강] 워크플로우 → 3축 라우팅(인터페이스 / 기능·아키텍처 / 배포·운영) + 4대 탐색 계층
   │
   ├─▶ [2강] 구현 라이프사이클 · Responses API 요청-응답 · 환경/접근/책임 · 평가·안전장치 → 구현 준비 스냅샷
   ├─▶ [3강] 작업 형태 → 모델 클래스·의사결정 요인 → 솔루션 경로·패턴 → 평가 근거 (4단계 결정 구조)
   ├─▶ [4강] 기능 역할 7가지 → 읽기 전용/실행형 도구 경계 → 최소 실행 가능 역량 세트 (4단계 결정 구조)
   └─▶ [5강] 아키텍처 패턴 → 1차 청사진 → (전문가) 최종 기술 설계
                │
[6강] 데이터 범주·소유권 → 조치-위험 단계·승인 게이트 → 평가·가드레일·모더레이션·가시성·감사 가능성 → 준비도 권고안
```

#### 강의별 핵심
- **1강 기술적 유창성:** 3축 라우팅(ChatGPT Chat / ChatGPT Work / Codex / API 앱·프로세스는 *인터페이스*, 에이전트·자동화는 *기능·아키텍처*, 오픈 웨이트는 *모델·배포* 결정). 4대 탐색 계층(사용자·워크플로우 / 맥락·데이터 / 런타임·도구 / 거버넌스·가시성). 권고 신뢰도 레벨 1(예비) → 2(검증된 아키텍처) → 3(배포 준비)
- **2강 기술 구현의 기초:** 라이프사이클은 일직선이 아닌 루프(워크플로 정의 → 종속성 확인 → 안전한 입력으로 프로토타입 → 안전장치·평가 → 테스트·반복 → 출시·모니터링·개선). 맞춤형 API는 Responses API에서 시작, 입력·상태·출력 계약·추적으로 사고. 개발·테스트·스테이징·프로덕션별로 데이터·접근·소유자·모니터링·롤백 가정이 다름
- **3강 모델 선정:** 작업 형태 진술문(작업·입력·결과·사용자·검토 요건) → 지속적인 모델 클래스(추론 중심·범용·효율적·멀티모달·오디오/실시간·임베딩 + 모더레이션·도구·검색 기능) → 의사결정 요인(추론 깊이·지연·비용·규모·맥락·구조화 출력·도구·위험·평가) → 대표 평가 사례로 검증, 실패 사례는 라우팅 근거
- **4강 플랫폼 기능:** 기능 역할 7가지(상호작용·컨텍스트·조치·오케스트레이션·평가·개발자 워크플로·거버넌스/가시성). 기능마다 종속성과 통제가 따라옴. 읽기 전용 도구와 실행형 도구를 분리하고, 실행형에는 승인·제한·추적·책임을 추가. 실시간·멀티모달·에이전트·Codex는 필요할 때만
- **5강 아키텍처 패턴·청사진:** 패턴(일반 해법 형태) → 1차 청사진(이 워크플로 적용 + 검증할 것) → 최종 기술 설계(전문가 주도). 9가지 패턴 계열과 수정자(고객 전달 → 사람 검토, 스캔 양식 → 멀티모달, 레코드 업데이트 → 기업 시스템 연동, 검색+도구+승인 → 하이브리드)
- **6강 보안·거버넌스·데이터:** 거버넌스 = 소유자·범위·검토 시점·근거·에스컬레이션을 정해 *더 빠르게* 움직이게 하는 장치. 데이터 범주·출처·소유권·접근을 매핑하고, 조치-위험 단계(읽기 전용 → 초안 → 권장 → 승인 후 실행 → 제한)에 맞춰 승인 게이트와 통제 수단을 배치. 준비도 권고안은 "알려진 것 / 가정 / 검증할 것 / 다음 단계 담당자"

#### 강의를 잇는 연결 고리
| 개념 | 라우팅(1강) | 구현(2강) | 모델·기능(3·4강) | 청사진(5강) | 거버넌스(6강) |
|---|---|---|---|---|---|
| 출발점 | 워크플로우 우선, 제품명 금지 | 무엇을 구현하나(스냅샷 Q1) | 작업 형태 / 워크플로우 요구 사항 | 패턴보다 워크플로 | 워크플로우 소유자 |
| 데이터·맥락 | 맥락·데이터 계층 | 데이터 흐름·환경별 데이터 | 검색·임베딩, 승인된 컨텍스트 | 승인 소스·소스 소유자 | 데이터 범주·출처·소유권 |
| 도구·조치 | 런타임·도구 계층 | 도구 범위·프롬프트 주입 경계 | 읽기 전용 vs 실행형 | 런타임·도구 가정 | 조치-위험 단계·승인 게이트 |
| 검증 | 평가·가드레일 조기 고려 | 초기 평가 세트·안전장치 10범주 | 대표 평가 사례·실패 사례 | 평가가 성공 지표와 연계 | 평가·감사 가능성을 증거로 |
| 사람의 역할 | 전문가 참여 신호 | 출력 검토자·출시 후 책임자 | 사람 검토 기능 | 사람 검토 수정자 | 검증 역할·승인자 |
| 산출물 | 기술 유창성 내비게이터 | 구현 준비 스냅샷 | 4단계 결정 구조(모델/역량) | 1차 OpenAI 솔루션 청사진 | 준비도 권고안 |

#### 실무 체크리스트
- ☐ 고객 요청을 워크플로우(누가, 어떤 업무, 어떤 결과)로 다시 말할 수 있는가
- ☐ 인터페이스 / 기능·아키텍처 / 배포·운영 결정을 섞지 않고 분리했는가
- ☐ 데이터 출처·소유자·민감도·접근 권한·이동·보존을 확인했는가
- ☐ 모델 이름이 아니라 작업 형태와 의사결정 요인으로 모델 클래스 가설을 세웠는가
- ☐ 1차 버전에 꼭 필요한 최소 역량만 골랐고, 미룰 것을 구분했는가
- ☐ 읽기 전용과 실행형(쓰기·전송·트리거) 경계를 나누고, 실행 전 사람 승인을 두었는가
- ☐ 대표·극한·실패·모호·정책 사례로 된 초기 평가 세트와 성공 기준이 있는가
- ☐ 출시 후 모니터링·롤백 경로와 운영 책임자가 정해졌는가
- ☐ 권고안에 가정·검증 필요 사항·에스컬레이션 대상(전문가)을 드러냈고, 확정 설계처럼 과장하지 않았는가

  <div class="eyebrow">레슨 01 · Technical Fluency Orientation</div>
  <h1 class="lesson-title">기술적 유창성 오리엔테이션</h1>
</div>

**한 줄 요약:** 제품 이름부터 꺼내지 않고 워크플로우에서 출발해 사용자·제품 인터페이스 / 기능·아키텍처 / 배포·운영이라는 세 결정을 분리하고, 네 가지 탐색 계층으로 증거를 모아, 과장 없이 예비 경로를 제안·검증하며 필요할 때 전문가를 참여시키는 법을 배운다.

### 핵심 내용
#### 환영합니다 (도입)
- 기술적 유창성은 고객 워크플로우를 신뢰할 수 있는 솔루션 경로와 연결하고, 더 나은 구현 질문을 던지고, 상충 관계를 조기에 파악하며, 전문가 검증 없이는 진행할 수 없는 시점을 알아차리게 한다.
- 제품 심층 과정이 아니며 수료가 모든 제품·모델·아키텍처·거버넌스 전문가를 뜻하지 않는다. 목표는 더 나은 질문, 신뢰할 수 있는 초기 경로, 과도한 주장 회피다.
- 핵심 질문: 과도한 설계·과장된 주장·잘못된 팀으로의 인계 전에 기술적 기회를 어떻게 책임감 있게 계획할 것인가?
- 선택 산출물: 고객 대화·솔루션 검토·구현 인계 전에 쓰는 역할별 '기술적 유창성 내비게이터'.

#### 기술 솔루션 현황 파악
- 고객 대화는 "운영팀용 AI 어시스턴트", "이 워크플로 자동화 가능?", "ChatGPT에 넣을까, API로 구축할까?" 같은 포괄적 요청으로 시작되기 쉽다.
- 제품 이해 중심 응답은 곧바로 기능·모델 이름으로 가지만, 기술적으로 유창한 응답은 멈춰서 워크플로우·데이터·사용자·제약·위험·성공 기준을 파악한다.
  - 제품 이해도 = 제품 명칭·일반 기능을 아는 것 / 실무적 기술 판단력 = 적합성을 가르는 질문, 중요한 절충점, 권고 전 검증할 것을 아는 것 / 계산적 사고 = 문제를 단계별로 나눠 필요한 정보·접근 가능한 데이터를 파악하고 대안을 비교하는 것.
- **제품이 아닌 워크플로우부터:** 같은 성과가 ChatGPT·Codex·API 애플리케이션, 여러 기능, 운영 모델의 조합으로 달성된다. 통합 솔루션은 각 축 결정의 결과이지 별개의 동등한 경로가 아니며, 기능·배포 제약·운영 통제·성공 기준이 명확해질 때까지는 초기 가설로 다룬다.
- 초기 적합성 신호는 출발점 단서일 뿐 최종 권고가 아니다. 처음 몇 분에 아키텍처를 풀려 하지 말고 작업 위치, 시스템 역할, 경로를 바꿀 운영 제약을 경청한다.
- 라우팅 실수는 대개 워크플로를 이해하기 전에 "ChatGPT 써라 / API로 구축하라 / 에이전트로 만들라 / Codex 써 봐라"를 기본값으로 쓸 때 생긴다.

#### 기본 기술적 사고 모델 구축하기
- 네 가지 탐색 계층은 제품 경로 목록을 대체하지 않고 3축 라우팅 안에서 증거를 모으는 데 쓴다. 철저한 탐색은 증거 수집과 경로 설정을 구분한다.
- **API·애플리케이션·워크플로우:** 애플리케이션이 요청(정보·지시·매개변수)을 보내면 서비스가 응답을 돌려주고, 이를 표시·저장·라우팅·전달한다. 많은 AI 기회는 직원용 채팅 공간이 아니라 기존 제품·프로세스·고객 경험에 AI를 내장하는 것이며, 사용자가 AI 관여를 모를 수도 있다. API 설계는 필요 없고 내장이 필요한 시점만 알아보면 된다.
  - 핵심 질문: "사용자가 AI와 직접 상호작용하나, 다른 시스템이 더 큰 워크플로우의 일부로 AI를 쓰나?" → ChatGPT·API·조합 중 시작점 결정.
- **맥락이 품질을 좌우:** 맥락 = 사용자 제공 정보, 검색된 지식, 연동 시스템, 파일·문서, 구조화된 데이터, 도구 출력, 정책·운영 규칙, 권한·접근 경계. 강력한 모델도 맥락이 틀리면 그럴듯하지만 부정확하거나 오래된 답을 낸다(예: 최신 HR 정책이 없는 HR 어시스턴트). 목표는 더 많은 정보가 아니라 올바른 출처의 올바른 정보를 올바른 사용자에게 주는 것.
- **평가·가드레일은 초기에:** 한 번 작동한 데모와 배포 가능한 시스템의 차이는 "양호함"과 "일관성"을 미리 정의했는지에 있다. 첫 실패 후 뒤늦게 붙이면 안 된다.
  - 워크플로우와 기대 결과를 반영한 대표적·라벨링된 예제로 평가를 시작한다. 라벨은 목표 주석일 뿐 데이터 정제도의 척도가 아니며, 학습·미세 조정 결정에는 별도의 데이터 전략과 전문가 검증이 필요하다.
  - 타당한 경로, 안전한 테스트 가능성, 출시 전 필요한 신뢰도, 심층 설계 전 필요한 증거, 파일럿 이후 확장 준비 여부에 영향을 준다.

#### 기술적 판단으로 경로 설정·검증·에스컬레이션
- **권장과 검증 구분:** 모든 세부를 알기 전에 의견을 내는 것은 정상이지만 증거보다 확신에 찬 어조가 위험하다. 초기 상담은 대부분 레벨 1(예비 해결 방안)에 집중해, 유력한 시작 경로와 그 이유, 아직 검증할 것을 함께 말한다.
  - 예: "직원용 지식 워크플로우로 보여 ChatGPT가 합리적 첫 방향이지만, 확정 전 정보 저장 위치·현재 접근 방식·보안·승인 요건을 파악해야 한다."
- **상충 관계:** 한쪽을 개선하면 다른 쪽이 어려워지거나 비싸진다. 예: ChatGPT로 빠르게 시작 vs 지원 플랫폼과 깊은 통합(원활하지만 추가 기술 작업·통합 계획·지속 지원 필요). 정답은 고객 우선순위에 달려 있으며, 경로를 바꿀 상충과 검증할 사항만 명확히 하면 된다.
  - "확실히 올바른 해결책입니다" 대신 "합리적인 첫 단계로 보이지만 통합 요구와 승인 절차를 검증해야 합니다."
- **전문가 참여:** 모든 질문에 직접 답할 필요는 없다. 상당한 불확실성·기술적 복잡성·전문 검토가 필요한 요구가 생기면 적절한 인력을 참여시킨다.
- 강한 초기 권고는 ① 예상 사용자·제품 인터페이스 ② 필요한 기능·아키텍처 ③ 검증할 배포·운영 가정을 모두 담아, "너무 모호함"과 "증거 이상의 확신"이라는 두 실수를 피한다.

#### 기술 유창성 내비게이터 구축하기
- 내비게이터는 어떤 대화를 준비하나, 어떤 인터페이스가 타당한가, 어떤 기능·아키텍처가 필요한가, 어떤 배포·운영 가정과 에스컬레이션 신호가 중요한가에 답하는 사고 도구다. 최종 권고안·아키텍처 문서·구현 계획이 아니다.
- 역할별 필요 시점: 기술 프리세일즈(예상 인터페이스·기능·배포 옵션 설명, 적합성 신호 파악) / 솔루션 컨설턴트(워크플로우 과제 → 기술 탐색 질문) / 솔루션 아키텍트(제약·가정·위험·검증 요구 파악) / 구현 실무자(준비도·구현 계획·인계) / 개발자·FDE 빌더(플랫폼 기능·패턴을 구현 접근에 접목).
- 도울 대화 유형 1–2개를 고르고, 4개 역량(인터페이스 구분, 기능 파악, 배포·운영 질문, 상충·전문가 판단)의 자신감을 낮음/중간/높음으로 표시해 낮음·중간부터 강화한다. 가볍게 유지하고 경험에 따라 업데이트한다.

#### 정리
- 기술적 유창성은 암기가 아니라 더 나은 질문, 중요한 상충 파악, 추가 검증 시점 인지다. 가장 깊은 기술 전문가일 필요는 없다.
- 다음 대화 전 자문: 고객이 해결하려는 문제는? 관련 정보·시스템·도구는? 아직 검증할 구현 세부는? 누가 남은 질문을 도와야 하나?

### 기억할 개념·프레임워크
- 3축 라우팅 모델

| 결정 축 | 올바른 질문 | 방향성 예시 |
|---|---|---|
| 사용자·제품 인터페이스 | 사용자·워크플로가 주로 어디서 운영되나? | ChatGPT Chat(대화형 협업) / ChatGPT Work(위임된 지식 업무) / Codex(소프트웨어 엔지니어링) / API 앱·프로세스(임베디드·맞춤 경험) |
| 기능·아키텍처 | 시스템이 무엇을 해야 하나? | 앱·도구, 워크스페이스 에이전트, 정보 검색, 구조화된 출력, 코드 실행, 자동화 |
| 배포·운영 | 어디서·어떻게 실행·제어되나? | 온프레미스/클라우드, 호스팅/임베디드, 신원, 권한, 승인, 보존, 로깅, 사람 검토, 해당 시 고객 운영 오픈 웨이트 모델 평가 |

- 인터페이스 적합성 신호: Chat = 대화형 탐색·초안·비평·수정 / Work = 위임 업무의 결과·맥락·제약·승인 범위·검토 기준을 정의 가능 / Codex = 리포지토리·테스트·검토·디버깅·문서화 / API = 지능을 제품·시스템·워크플로우에 내장. 오픈 웨이트 모델은 데이터가 민감해서가 아니라 특정 배포 요구 때문에 고려한다.
- 흔한 라우팅 실수: 모든 경로를 동등한 목록으로 취급 / Chat·Work 미구분 / 에이전트·자동화를 인터페이스로 취급(실제는 기능·아키텍처) / 오픈 웨이트를 인터페이스로 취급(실제는 모델·배포 결정) / 맥락·도구·조치·출력 정의 전 인터페이스 선택 / 권한·승인·로깅·사람 검토·소유권을 마지막까지 무시 / 축별 근거 없이 "하이브리드"로 명명.
- 4대 탐색 계층

| 계층 | 핵심 질문 |
|---|---|
| 사용자·워크플로우 | 누가, 어떤 업무·산출물? 구체적 비즈니스 문제? 반복 vs 일회성? |
| 맥락·데이터 | 무엇을 알고·검색·접근해야? 대표적·최신·활용 가능한 데이터인가? |
| 런타임·도구 | 작업은 어디서? 어떤 시스템·도구? 어떤 작업이 허용되나? |
| 거버넌스·가시성 | 어떻게 모니터링·제어·평가·개선하나? |

- 맥락 4질문: 정보 출처? 최신 유지 방법? 접근 권한자? 산출물 검토·검증 방법?
- 평가 = 예상대로 작동하는지 체계적 테스트(완전성, 형식, 올바른 출처, 근거 없는 주장 회피, 경계 사례) / 가드레일 = 할 수 있는 것·안 되는 것·출력 형태와 거부·에스컬레이션·사람 검토 시점을 정하는 제어.
- 권고 신뢰도 3단계: 레벨 1 예비 해결 방안(현재 정보 기반 유력 방향) / 레벨 2 검증된 아키텍처(주요 기술 가정 검증) / 레벨 3 배포 준비 구현 계획(요구·승인·통합·운영 세부 정의).
- 상충 관계: 경험 측면 = 속도 vs 통제, 품질 vs 비용·지연, 자동화 vs 감독, 단순성 vs 통합 깊이 / 책임 운영 측면 = 데이터 접근·보안, 거버넌스·신뢰성, 유지 관리·소유권, 구현 성숙도.
- 전문가 참여 신호: 데이터·규정 준수(민감·규제 데이터, 데이터 보관지, 개인정보, 불분명한 소유권) / 시스템·조치(기록 업데이트, 작업 실행, 고객 직접 메시지, 중요한 결정) / 보안·권한(신원, 접근 제어, 승인 규칙, 감사, 도구 경계) / 아키텍처·통합(복잡한 통합, 검색 시스템, 에이전트 워크플로우, 불분명한 구현 책임) / 제품·정책(동작, 가용성, 로드맵, 보안·규정 준수의 공식 확인).
- 내비게이터 4섹션: ① 나의 역할·대화 초점 ② 3축 라우팅 단서 ③ 재사용 탐색 질문(워크플로우·결과 1개 + 축별 1개) ④ 상충 관계·에스컬레이션 신호. 마무리 문구: "예상 표면은 ___, 워크플로에는 ___가 필요할 수 있고, 권장 전 배포·운영에서 ___를 검증해야 한다."

### 실무 적용 예시
- **"운영팀용 AI 어시스턴트":** "ChatGPT 쓰세요/에이전트 만드세요"는 성급하다. 워크플로우, 사용자, 필요한 정보, 답변만 vs 조치까지, 관련 시스템, 검토·승인 대상, 데이터·보안·거버넌스 요구를 묻는다. 상호작용형 탐색·요약·초안이면 Chat, 위임 업무의 기준을 정의할 수 있으면 Work, 운영 플랫폼 내장이면 API 앱이 타당하며, 검색·도구·승인·자동화는 기능 결정이고 배포·운영 통제는 여전히 검증 대상이다.
- **API 내장 패턴:** 지원 티켓 생성 → 티켓·계정·지식 기반을 백엔드로 전송 → 응답 초안·문제 범주·다음 조치 생성 → 담당자 검토 후 발송. 온보딩 계획, 계약서 정보 추출, CRM 계정 요약, 규정 준수 예외 표시도 같은 패턴.
- **에이전트형 요청:** 고객 정보 검색 + 여러 시스템 기록 업데이트 + 후속 이메일 자동 발송 → 에이전트 워크플로우로 보되 권한·승인·시스템 접근·감사·운영 통제는 전문가와 검증.
- **워크플로별 필요 맥락:** 정책 보조자(승인된 정책 문서·사용자 권한·민감 질문 검토 절차) / 영업 준비(CRM·통화 메모·계정 계획·갱신 내역) / 계약 검토(승인된 템플릿·법률 지침·관련 계약 문서).

### 지식 점검 포인트
- 고객 요구 → 예비 라우팅 단서 매칭 → 고객용 제품 내 AI 생성 결과물: API 앱·프로세스 / 밀접히 참여하는 대화형 정책 Q&A·초안: ChatGPT Chat / 테스트·문서화·PR 지원: Codex / 승인된 출처 기반 검토 가능한 정책 개요서 위임 작성: ChatGPT Work / 검색·구조화된 출력·도구 사용·자동화: 기능·아키텍처 결정 / 권한·승인·로깅·보존·사람 검토: 배포·운영 결정.
- 질문 → 탐색 계층·라우팅 축 매칭 → "누가 사용?": 사용자·워크플로우 계층 / "어떤 레코드에 접근?": 맥락·데이터 계층 / "티켓을 업데이트할 수 있나?": 런타임·도구 계층 / "오류는 어떻게 모니터링?": 거버넌스·가시성 계층 / "담당자·워크플로가 주로 어디서 운영?": 인터페이스 결정 / "시스템은 무엇을 해야?": 기능·아키텍처 결정 / "어디서·어떻게 실행·제어?": 배포·운영 결정.
- "공급업체 위험 정보를 검토하고 조달 기록을 자동 업데이트" → 인터페이스·기능/아키텍처·배포/운영 결정을 분리하고 데이터 접근·권한·검토·감사 가능성·에스컬레이션을 검증한다(인터페이스, 자동화, 민감 정보, 시스템 write-back이 얽혀 있음). 즉시 ChatGPT Work, "agentic"을 제품 경로로 보고 바로 자동화 설계, 민감 데이터라 오픈 웨이트 선택은 오답.
- "AI 자동화"를 원하나 워크플로·데이터·사용자·승인 미설명 → 워크플로우를 먼저 명확히 한 뒤 라우팅 전에 세 결정을 분리한다. 빠르니 ChatGPT, 자동화=에이전트, 원하는 모델부터 질문은 오답.
- 선택 실습 1(신호 분류, 5분): 5개 고객 신호마다 인터페이스·기능 1개·배포 질문 1개를 적고 미지 사항은 기록한다.
- 선택 실습 2(가정 찾기, 6–8분): "현장 팀의 고객 미팅 준비를 빠르게" 요청을 4계층으로 점검해 가장 불명확한 계층과 다음 질문을 정한다.
- 선택 실습 3(과장 없이 권고, 5–7분): 고객 성공팀의 갱신 위험·계정 요약·후속 조치·CRM 메모 업데이트 요청에 3–4문장 레벨 1 권고를 쓴다.
- 선택 실습 4(1페이지 내비게이터, 5–7분): 4섹션 구조로 역할별 내비게이터를 작성한다.

**한 줄 요약:** 구현은 코드 이전에 시작되는 라이프사이클이다. 워크플로우·요청-응답 흐름(Responses API)·환경과 접근·책임 소재·평가와 안전 장치를 짚어 "구현 준비 스냅샷"으로 정리하고, 다음 기술 단계를 책임 있게 고르는 법을 배운다.

### 핵심 내용
#### 환영합니다 (도입)
- 기술적 구현은 코드를 쓰기 전부터 시작된다. 시스템 간 통신, 실행 위치, 데이터 이동, 품질 테스트, 다음 단계 담당자 등 구현 논의의 기초를 다룬다.
- 학습 목표: 구현 라이프사이클 설명, 새 맞춤형 OpenAI API 구현의 기본 구성 요소로 Responses API가 권장되는 이유, 환경·접근·데이터·통합 고려 사항, 평가(evals)·안전 장치(safeguards)가 준비 과정에 포함되는 이유, 기술 인계 질문 준비.
- 결과물: 워크플로우, AI 상호작용, 데이터·접근 가정, 준비 미비점, 테스트 요구, 안전 장치, 에스컬레이션 지점을 담는 간단한 **구현 준비 스냅샷**(선택).

#### 구현 파트너의 관점에서 생각하라
- 구현은 단일 빌드 단계가 아니라 의사결정·종속성·테스트·안전 장치·책임자·증거가 얽힌 **라이프사이클**이다. 핵심 질문: "이 워크플로우는 책임 있는 구현 계획을 세울 만큼 명확한가?"
- "수작업 감소·품질 개선" 같은 목표는 출발점일 뿐이다. 워크플로우가 일회성인지 반복 가능한지가 필요한 노력·테스트·책임·자동화 수준을 가른다.
- 라이프사이클은 순서가 고정되지 않는다. 테스트 중 데이터 소스가 불완전함이 드러나거나 안전 장치 논의로 기능 범위가 바뀌어 이전 결정으로 돌아가는 일이 흔하다.
- **구현 준비 완료**란 모든 세부가 해결된 상태가 아니라, 미지 사항이 드러나고 가정이 명시되고 다음 단계 범위가 정해진 상태다. 확인 질문: "피할 수 있는 위험이나 재작업 없이 다음 기술 단계를 진행할 만큼 알고 있는가?" 답이 '아니오'여도 기회 자체는 유망할 수 있다.
- 다음 단계 예: 탐색 계속, 안전한 프로토타입, 데이터 접근 검토/검증, 워크플로우 명확화 회의, 평가 설계 논의, 전문가 인계.
- **구현 격차:** 좋은 사용 사례라도 구축·테스트·배포·지원을 어렵게 만드는 누락 사항이 남는다. 일부는 데모에서 프로토타입이 작동한 뒤, 실제 사용자·데이터·권한·운영 책임 하의 동작을 설명하지 못할 때 늦게 드러난다. 격차는 기회가 약하다는 뜻이 아니라 남은 확인 사항을 보여 줄 뿐이다.

#### API를 통합의 기반으로 이해하기
- API는 한 소프트웨어 시스템이 다른 시스템과 소통하는 방식이다(항공편 조회, 잔액 조회, 일기 예보 등). AI도 채팅창 대신 애플리케이션이 요청을 보내고 응답을 받아 워크플로우에 쓰는 방식으로 제품·내부 도구에 내장된다.
- 기본 패턴: 애플리케이션이 요청 → AI가 응답 → 애플리케이션이 다음 단계를 결정. Responses API에서는 모델 출력, 내장/사용자 정의 도구 호출과 결과, 턴을 넘는 상태가 포함될 수 있지만 다음 단계 결정은 여전히 애플리케이션 몫이다.
- 새 맞춤형 OpenAI API 프로젝트는 **Responses API부터 시작**한 뒤 입력, 지시사항, 승인된 컨텍스트, 도구, 상태, 출력 계약, 사람 검토, 추적, 평가 증거, 릴리스/롤백 결정을 정의한다.
- 요청에는 사용자 질문 외에 시스템 지시, 승인된 컨텍스트, 파일·구조화 데이터, 도구(검색 포함), 출력 계약(하류 시스템이 신뢰할 결과가 필요하면 JSON 스키마 기반 구조화된 출력), 상태/이전 응답 정보, 신원·권한이 포함될 수 있다.
- 응답도 텍스트 이상이다: 초안, 구조화된 출력, 분류·권장, 도구 호출/결과, 상태·후속 조치·승인 요청, 거부나 상급자 보고.
- 다단계·도구 사용 작업은 릴리스 전에 사람 검토와 **추적(trace)** 을 정의해 모델 출력·도구 호출·승인·조치를 검토할 수 있어야 한다. 정확한 추적·저장·접근 설계는 구현·보안 검증이 필요하다.
- 핵심 질문: "AI에 무엇이 전송되고, 무엇이 반환되며, 그다음 무슨 일이 일어나는가?" 이를 설명 못 하면 워크플로우 정의가 더 필요하다.
- **인증**은 연결 권한의 입증, **접근 제어**는 연결 후 할 수 있는 일의 결정이다. API 키·토큰 등 비밀 정보는 프롬프트·공유 문서·데모·회의록에 붙여 넣지 않는다. 테스트와 프로덕션은 자격 증명·권한을 분리할 수 있다.
- 출력을 받는 시스템이 요구하는 구조·필드 형식·인계 단계를 확인하고, 호환성·소유권·모니터링·지원 기대치를 검증한 뒤에 통합 완료로 본다.
- **프롬프트 주입 경계:** 검색된 콘텐츠·사용자 파일·도구 결과는 데이터로 취급하고, 시스템 지시·권한·승인 규칙을 바꾸는 권한으로 보지 않는다. 도구는 최소한으로 제한하고 입출력을 검증하며, 외부 쓰기·파괴적 작업 전에는 사람 승인을 받는다. 경계가 불분명하면 보안·구현 검토로 넘긴다.

#### 환경, 데이터 흐름, 접근 권한 및 소유권 계획
- 핵심 질문: "어디에서 실행되고, 무엇에 접근하며, 출시 후 누가 소유하는가?" 데모가 설득력 있어도 실제 사용자 대상 준비와는 다르다.
- 솔루션은 개발 → 테스트 → 스테이징 → 프로덕션 환경을 거치며 더 높은 기대치·통제·신뢰도를 요구받는다. 개발에서 잘 되던 것도 프로덕션 전에 추가 테스트·보안 통제·모니터링·승인·운영 책임 배정이 필요하다.
- **배포 경계**는 솔루션이 실행되는 위치와 접근 대상을 정한다. ChatGPT 작업 공간의 어시스턴트와 고객 대상 제품에 내장된 기능은 다르며, 내부 앱·고객 제품·백엔드 서비스·에이전트 런타임·클라우드/고객 관리형 인프라·타사 워크플로 도구 등이 있다. 붙여넣기 기반 프로토타입이 업무 시스템에서 데이터를 가져오고 다시 기록하게 되면 접근·권한·로깅·검토·소유권의 중요도가 크게 오른다.
- **운영 책임:** 책임자 없는 솔루션은 지원되지 않는 시제품으로 전락한다. 워크플로우, 애플리케이션·통합, 데이터 접근, 변경 승인, 오류 검토, 사용·품질 모니터링, 프롬프트·도구·평가·지침 업데이트마다 소유자가 다를 수 있다.
- **릴리스·롤백:** 릴리스는 실제 사용자·데이터·시스템·운영 기대치가 적용되기 시작하는 시점이다. 제한된 파일럿이나 통제된 데이터 소스로 작게 시작한다. 롤백/비활성화 경로에는 기능 비활성화, 통합 일시 중지, 수동 프로세스 복귀, 접근 제한, 전 출력의 사람 검토 전환 등이 있다. 고객 대상·규제 대상·조치 수행 시스템에서 특히 중요하다.

#### 평가(eval)와 안전 장치로 릴리스 신뢰도 높이기
- 핵심 질문: "어떤 근거가 출시·모니터링·개선에 대한 확신을 주는가?"
- **평가**는 AI 시스템이 예상대로 작동하는지 확인하는 체계적 테스트다. 데모가 한 예시의 성공을 보여 준다면, 평가는 일반 입력·경계 사례·고위험 상황 전반의 안정성을 확인한다. AI 출력은 불완전해도 자신 있게 들릴 수 있기 때문이다.
- 평가로 프롬프트·모델·도구·검색 방식을 비교하고, 품질을 측정하며, 회귀를 잡고, 개선을 추적한다. 출시 전 최종 점검만이 아니라 변경 때마다 쓰는 도구이며, 사람의 판단과 전문가 검증이 여전히 필요하다.
- **초기 평가 세트**는 완벽한 벤치마크가 아니라 초기 안전망이다. 각 사례는 워크플로우의 의도된 결과와 위험 수준에 연결한다.
- **안전 장치**는 마지막에 붙이는 기능이 아니라 워크플로우 설계의 일부다. 시스템이 쓸 정보, 할 수 있는 작업, 출력 형태, 사람 검토·승인 시점을 정하며 구체적 위험에 맞춘다(민감 데이터 → 접근 제어·검토 규칙 / 타 시스템 업데이트 → 승인·로깅 / 의사결정에 활용 → 품질 검사·출처 참조·에스컬레이션).
- **추적·로그·모니터링·개선 루프:** 추적은 모델 출력·도구 호출·승인·조치의 순서를 재구성하고, 로그는 특정 이벤트(입력·컨텍스트·출력·후속 조치)를 조사하며, 모니터링은 사용량·오류·품질 신호·지연 시간·비용·에스컬레이션 비율 등 시간에 따른 패턴을 본다. 개선 루프는 그 증거로 프롬프트·도구·검색 소스·평가 사례·안전 장치·워크플로우를 고치거나 릴리스 범위를 좁힌다. 가시성은 사후가 아닌 설계 단계 고려 사항이다.

#### 구현 준비 스냅샷 정리하기
- 상세 계획이나 기술 설계가 아니라 사전 파악 통화, 프로토타입 계획, 솔루션 검토, 인계, 준비 상태 논의 전에 쓰는 짧은 대화 보조 메모다. 목표는 모든 답이 아니라 가정·검증 필요 사항·에스컬레이션 시점·다음 단계를 명확히 하는 것이다.
- 스냅샷의 일부를 채우기 어렵다면 그것도 정보다. 더 많은 조사·검증·전문가 의견이 필요하다는 신호다.
- 역할별 활용: 기술 프리세일즈(인계 전 준비 질문) / 솔루션 컨설턴트(디스커버리 구조화) / 솔루션 아키텍트(제약·종속성·위험·심층 설계 영역) / 구현 담당자(준비 검토·인계·파일럿·책임 논의) / 개발자(빌드 가정·상호작용 흐름·테스트 요구로 구체화). 목적은 모두 같다: 빌드·파일럿·릴리스·인계 전에 불명확한 가정을 드러내는 것.

#### 정리
- "AI가 이걸 할 수 있을까?"에서 곧장 "만들어 봅시다"로 가지 말고, 무엇을 명확히 하고 테스트하고 통제하고 책임져야 하는지로 대화를 돌리는 것이 구현 파트너의 역할이다.

### 기억할 개념·프레임워크
- 탄탄한 구현 계획이 밝힐 7가지: 수행 기능 / 사용자 / 연동 시스템 / 필요 데이터 / 산출물 검증 방법 / 통제할 위험 / 출시·개선 책임자
- 구현 준비 확인 8문항: 사용자, 적용 업무 범위, 입력 데이터, 출력, 데이터 소스·시스템, 요구 품질, 통제할 위험, 출력 검토자·출시 후 책임자
- 흔한 구현 격차 10가지: 모호한 워크플로우 범위 / 신뢰할 데이터 소스 부재 / 불분명한 권한 / 테스트 케이스 부재 / 품질 기준치 부재 / 대체 동작 미비 / 수동 검토 경로 부재 / 운영 책임자 불분명 / 데모 결과 과신 / 제품 가용성·동작에 대한 근거 없는 가정
- 환경별 구현 가정

| 고려 사항 | 개발 | 테스트 | 스테이징 | 프로덕션 |
|---|---|---|---|---|
| 데이터 소스 | 안전한 샘플 | 테스트 데이터 | 운영과 유사한 데이터 | 실시간 비즈니스 데이터 |
| 관련 시스템 | 로컬·수동 | 테스트 시스템 | 통합 시스템 | 실시간 시스템 |
| 접근 권한 | 팀 제한 접근 | 역할 기반 | 승인된 접근 | 통제된 접근 |

- 책임 소재 7문항: 워크플로우 / 애플리케이션·통합 / 데이터 접근 / 변경 승인 / 오류 검토 / 사용·품질 모니터링 / 프롬프트·도구·평가·지침 업데이트의 책임자는 누구인가
- 릴리스·롤백 7문항: 첫 파일럿 대상 / 제외할 사용자·워크플로·데이터·작업 / 필요한 승인 단계 / 충족할 테스트 기준 / 필요한 로깅·모니터링 / 일시 중지·비활성화·롤백 방법 / 변화·문제 발생 시 통보 대상
- 초기 평가 세트 구성: 전형적 성공 사례 / 극한 사례 / 실패 사례 / 모호한 입력 / 안전·정책 관련 사례 / (해당 시) 도구·검색·상태·프롬프트 주입 사례
- 안전 장치 10범주: 입력 필터링, 출력 검사, 구조화된 출력, 도구 범위 지정, 프롬프트 주입 경계, 사람 승인, 접근 제한, 모니터링, 로깅, 에스컬레이션 규칙
- 구현 준비 스냅샷 4문항

| 질문 | 담을 내용 |
|---|---|
| 1. 무엇을 구현하나? | 워크플로우·비즈니스 프로세스, 사용자 그룹, 기대 결과, 다음 단계 |
| 2. AI 상호작용은? | 시작 기본 요소(맞춤형 API는 Responses API), 입력·시스템 지시·승인된 컨텍스트, 도구·상태·출력 계약, 출력 후 사람 검토·조치 |
| 3. 무엇이 준비돼야 하나? | 첫 실행 위치, 관련 데이터·시스템, 접근 주체, 검토·유지·모니터링 담당 |
| 4. 무엇을 테스트·검토·에스컬레이션하나? | 시작 평가 사례 1~2건, 안전 장치·프롬프트 주입 경계·검토 지점, 추적·모니터링 신호, 릴리스/롤백 기준과 전문가 검증 질문 |

### 실무 적용 예시
- **지원 티켓 요약:** "티켓 요약 AI가 필요하다"에 "요약 도구를 만들 수 있다"로 바로 답하면 약한 대응. 대상 티켓 유형, 독자, 제외할 정보, 저장 위치, 티켓팅 플랫폼 재기록 여부, 정확도 기준, 부실 요약 감지, 출시 후 담당자를 묻는다. 내부 리더용인지 고객 노출용인지, 플랫폼에 회신하는지, 민감 정보가 있는지에 따라 검토·접근 제어·에스컬레이션 기대치가 달라진다. 질문을 "AI가 할 수 있나?"에서 "도입할 만큼 신뢰하려면 무엇이 필요한가?"로 바꾼다.
- **정책 답변 도우미(요청-응답 추적):** 요청 = 직원 질문 + 역할·권한 + 승인된 정책 문서 + "승인된 출처로만 답하고 근거 정책을 인용하라"는 지시. 응답 = 답변 + 출처 + 불확실성 인정·이관 판단. 다음 단계 = 법무·규정 준수·인사 등 민감 주제는 담당 팀으로 전달하고, 확신 없는 질문은 기록해 정책 담당자가 문서를 개선.
- **재무 정책 어시스턴트:** 사내용·정보 제공용이라도 민감 주제·구식 자료 위험이 있어 소규모 테스트 그룹, 승인된 정책 문서, 읽기 전용 접근, 추적 가능한 피드백, 정책 업데이트 책임자, 불확실·민감 질문 에스컬레이션으로 시작. 출처에 없거나 문서가 상충하거나 민감한 예외면 답을 지어내지 말고 이관. 확대 전에 접근 제어 확인, 평가 사례 확대, 모니터링 신호 정의, 불확실 답변 처리 합의, 원본 문서·피드백 책임자 지정이 필요.
- **관리자 정책 답변 초안:** 초안만 쓰더라도 직원 경험·규정 준수에 영향. 초기 평가는 정답이 명확한 질문, 맥락 누락(위치·역할·지역 불명 시 추가 정보 요청), 민감 개인 정보, 거절·이관이 필요한 질문, 인용 필요 질문을 테스트. 안전 장치는 승인된 출처만 사용, 근거 미확인 시 답변 금지, 고위험 주제 사람 검토, 민감 데이터 출력 점검, 미답변·이관 질문 로그.

### 지식 점검 포인트
- 확실한 사용 사례와 경영진 지원으로 다음 달 출시를 원하지만 사용자 그룹·데이터 소스·검토 절차·출시 후 책임자가 불명 → 구현 준비로 보기 전에 **사용자, 데이터, 검토 절차, 책임 소재를 명확히** 해야 한다(비즈니스 가치와 실행 준비도는 별개. 즉시 출시, 데모 한 번 더, 운영 계획 완성까지 전면 중지는 오답).
- 요청-응답 사고방식 역할 매칭 → 새 맞춤형 OpenAI API 구현: Responses API부터 시작 / 회의록 발췌·작업 기록: 입력 및 승인된 컨텍스트 / JSON 스키마의 위험·담당자·마감일 필드: 출력 계약 / 다음 차례에 필요한 이전 응답 정보: 상태 / 모델 출력·도구 호출·승인·조치 기록: 추적.
- 샘플 데이터로 잘 작동하는 프로토타입을 전 직원 대상 프로덕션으로 전환하려 함 → "릴리스 전에 **어떤 운영 데이터, 접근 제어, 모니터링 신호, 운영 책임자, 롤백 경로**가 필요한가?"(프로덕션 전환은 위험 프로필이 달라짐).
- 구현 위험 → 첫 대응책 매칭 → 출력이 정해진 형식을 따라야 함: 구조화된 출력 확인 / 구식 정책 기반 답변: 검색·출처 품질 평가 / 민감한 직원 정보 포함: 인적 검토 또는 민감 정보 보호 조치 / 도구가 기록을 잘못 업데이트: 승인 절차 및 도구 사용 테스트 / 오류 발생 시 조사 필요: 로그 기록 및 모니터링.
- 명확한 워크플로우·작동하는 프로토타입이 있지만 출시 후 오류 모니터링 담당자 미지정 → **출시 전 스냅샷을 업데이트해 책임 소재와 모니터링을 명시**(그대로 진행, 더 견고한 모델 선택, UI 문구 우선은 오답).
- 선택 실습(공통 예시: 회의록·업무 추적 기록으로 주간 프로젝트 보고서 초안을 쓰는 내부 비서)
  - 명확/불명확/준비 부족 확인(5~7분): 워크플로우·명확한 점·불명확한 점·최대 준비 부족·다음 조치를 4~5개 요점으로 작성.
  - 요청과 응답 추적(6~8분): 입력·도구/상태·출력 계약과 검토자를 3개 요점으로 쓰고 "구현 전에 검증할 것"으로 마무리.
  - 프로토타입 너머 생각하기(5~6분): 실행 위치·접근 데이터·관리 주체·문제 시 대응을 4개 요점으로 쓰고 "운영 전에 검증할 것"으로 마무리.
  - 출시 전 신뢰도 확보(4~6분): 첫 테스트(정상·모호·실패 사례), 안전 장치·검토 단계, 모니터링·이관 신호를 3개 요점으로 정리.
  - 나만의 구현 준비 스냅샷(6~8분): 4문항에 답해 4문장 스냅샷을 쓰고 "다음으로 취할 책임 있는 조치는…"으로 마무리.

**한 줄 요약:** "어떤 모델을 써야 하나?"라는 질문에 모델 이름이 아닌 작업 형태(task shape)로 답을 시작해, 모델 클래스·의사결정 요인·솔루션 경로와 패턴·평가 근거를 거쳐 전달/검증/에스컬레이션 중 다음 기술적 조치를 정하는 법을 배운다.

### 핵심 내용
#### 환영합니다 (도입)
- 가장 좋은 답은 대개 모델 이름이 아니라 워크플로우에서 시작한다. AI가 할 작업, 실행 빈도, 필요한 출력, 위험·검토 요건, 권장안을 믿게 할 근거를 먼저 본다.
- 목표: API 기반 기회에 대해 과제·출력·맥락·위험·상충 관계·검증 근거를 종합해 실용적인 모델 클래스·솔루션 경로·패턴을 제안하고, 초기 권고를 전달·검증·상급 이관할 시점을 판단하는 것.

#### 모델 이름이 아닌 작업 형태부터 시작하기
- "계약서 검토", "청구 검토", "지원 트리아지", "조달 접수" 같은 워크플로 라벨은 출발점일 뿐, 그 안에 여러 서로 다른 작업이 섞여 있다.
- **작업 형태**: 시스템이 하는 작업, 필요한 정보, 생성할 결과물, 결과물을 다음에 쓰는 대상(사람·하류 시스템), 적용되는 위험·검토 수준. 그래서 모델 선택은 "가장 최신·강력한 모델"이 아니라 작업·데이터·위험·성공 기준·운영 맥락에서 시작한다.
  - 약함: "지원 티켓 분류가 필요하다" / 강함: "접수 티켓을 읽고 문제 유형·긴급도를 분류하고, 필요 시 승인된 해결 방법·정책을 검색하며, 모호·민감·고우선 사례는 간략한 사유와 함께 담당자 대기열로 보낸다" → 분류·검색·에스컬레이션·검토 기준이 드러난다.
- 하나의 워크플로우에 여러 작업 패턴이 들어 있으면, 추천 전에 패턴을 분리한다. 목표는 완벽한 분류가 아니라 더 나은 질문이다.
- **출력 요구사항**: "분석"이 실제로는 요약, 구조화된 표, 분류 레이블, 의사결정 메모, 인용 답변, 도구 호출, 파일, 음성, 코드 변경, 에스컬레이션을 동반한 안전한 거절 등일 수 있다. 출력이 사람에게 정보만 주면 자연어로 충분하지만, 워크플로를 주도하거나 시스템을 업데이트하거나 조치를 유발하면 더 많은 구조화·검증·검토가 필요하다.
- **위험과 검토**: 고위험 워크플로는 "더 뛰어난 모델"이 아니라 더 강한 검증, 명확한 인간 검토, 안전한 에스컬레이션, 신중한 책임 소재가 필요하다. 고객 직접 노출, 규제·민감 데이터, 대량 처리, 법률·재무·의료·보안·고용 결정, 시스템 동작 유발·데이터 기록, 제한된 인간 검토일 때 위험이 커진다.

#### 모델 클래스와 의사결정 요인 이해하기
- 요구사항은 모델 클래스 용어로 정의하고, 선정된 후보를 테스트한다. 모델 클래스는 최종 답이 아닌 출발 가설이다.
- 과정은 현재 모델이 비교 기준에 어떻게 들어맞는지 보여주려 GPT-6 Astra를 예로 들지만, 즉시 추천하라는 뜻은 아니다. 기능·지원 설정·가격·접근성은 여전히 확인해야 한다.
- 모델 클래스(모델 범주)와 기능·아키텍처(검색·순위·도구 사용·에이전트 오케스트레이션), 운영 선택(호스팅·신원·권한·승인·보존·로깅)은 서로 영향을 주지만 하나의 동등한 목록으로 섞지 않는다.
- **추론 깊이**: 단순 요약·재작성·서식·안정적 분류는 범용/효율적 모델로 충분할 수 있다. 불완전 입력, 상충 제약, 정책 해석, 다단계 계획, 에스컬레이션 판단, 순차적 도구 사용이 있으면 심층 추론이 중요해진다. 질문은 "더 강한 모델이 할 수 있나?"가 아니라 "이 워크플로의 과제·위험·증거가 더 깊은 추론을 정당화하나?"이다.
- **지연 시간·비용·규모**: 빈번·사용자 대면·운영 통합 워크플로에서 특히 중요하다. 명목상 토큰 가격이 아니라 성공 작업당 총비용(모델·추론 사용량, 도구 비용, 재시도, 수작업 수정, 하류 재작업)을 비교하고, 재현을 위해 가격 책정 날짜와 처리 모드도 기록한다.
  - 절감 수단: 효율적 모델, 짧은 입력, JSON 스키마 기반 구조화 출력, 쉬운/어려운 사례 분리 라우팅, 반복 결과 캐싱, 어려운 사례만 심층 추론하도록 재설계.
- **맥락·지식**: 모델이 프롬프트 밖의 최신·비공개·승인 정보가 필요하면 모델 선택만으로는 해결되지 않는다. "모델이 프롬프트에서 처리할 수 있는 것 vs 고객이 승인된 컨텍스트·검색·도구·연결 시스템으로 제공해야 하는 것"을 구분해, 실제 문제가 컨텍스트 부족인데 "더 나은 모델"을 추천하는 실수를 피한다.
- **구조화 출력·도구 사용·위험**: 구조화 출력은 추출·분류·라우팅·양식·보고·자동화에 유용하다. 도구 사용은 가치와 함께 책임도 키우므로 권한 범위, 승인 규칙, 오류 처리, 가시성, 평가, 에스컬레이션 계획이 권장안에 반영되어야 한다.
- 좋은 초기 권고안: 가장 타당한 모델 클래스, 비교할 대안, 핵심 상충 관계, 권고를 뒷받침할 증거를 설명한다. 목표는 최종 모델 선정이 아니라 타당한 후보 목록과 검증 항목, 상급 보고 시점을 정하는 것이다.

#### 솔루션 경로와 패턴 비교하기
- API 모델 선택은 고객이 맞춤형 UX, 제품 통합, 백엔드 자동화, 구조화 출력, 도구 사용, 시스템 작업, 프로덕션 규모 동작이 필요할 때 적절한 다음 단계다. 이때 모델은 더 큰 시스템의 일부이고, 주변 애플리케이션이 상호작용·컨텍스트·출력 형식·도구·후처리를 제어한다.
- 새 맞춤형 API 프로젝트는 Responses API를 기본 출발점으로 쓰고, 입력·컨텍스트·도구·출력 계약·상태·검토·평가 근거를 현재 API 문서 기준으로 검증한다. 구현·평가·모니터링·개선의 책임 소재를 조기에 파악한다.
- 솔루션 경로는 **세 가지 결정을 분리**해 판단한다(아래 프레임워크). "에이전트", "오픈 모델", "하이브리드"는 동등한 사용자 인터페이스가 아니라 후속 결정(기능·배포) 범위다.
- **솔루션 패턴**은 최종 아키텍처가 아니라 AI가 워크플로를 지원하는 반복 가능한 방식이며, 패턴에 이름을 붙이는 이유는 설계 전에 함의를 드러내기 위해서다.
- **패턴 조합**: 기능 나열이 아니라 워크플로 순서로 설명한다. 각 단계마다 산출물, 필요한 맥락·도구, 실패 가능성, 검증 근거, 인간 검토·에스컬레이션 지점을 묻는다.

#### 평가 증거로 권고 검증하기
- 데모는 가능성을 보여줄 뿐이다. 직관, 선호, 한 번의 인상적 답변, "더 뛰어난 모델이 항상 최적"이라는 가정에 의존하지 않는다.
- 모델 선택 단계의 경량 eval은 완전한 평가 프로그램이 아니라, 초기 권고를 뒷받침·수정·상급 보고할 근거를 확보하는 것이 목적이다.
- **성공 기준 2–3개**: 작업 형태·출력·위험·활용 방식에 근거해 고른다(조달 접수 → 분류 정확도·형식 준수·에스컬레이션 / 검색 기반 정책 답변 → 근거 타당성·완전성·인용 / 음성 → 지연 시간·대화 진행 품질). 기준이 너무 많으면 실제 결정을 가린다.
- **소규모 시드 세트**: 일반 사례와 어려운 사례(모호성, 정보 누락, 민감 입력, 고위험 예외, 필수 형식, 검색·도구 요구)를 포함한다. 대표성 있는 소규모 세트가 모호한 대규모 세트보다 유용하며, 소규모 비교로 보편적 모델 순위를 정할 수는 없다.
- 공정 비교: 기존 방식과 후보(예: GPT-6 Astra)에 동일한 사례·승인 입력·프롬프트·도구 권한을 적용하고, 모델 ID·추론 설정·불가피한 구성 차이를 기록하며, 같은 품질 기준으로 채점하고 종단 간 지연·수정 노력·사용량을 기록한다.
- **결과 해석 기준을 미리 정한다**: 뒷받침(일반 사례 일관 처리, 형식 준수, 고위험 사례 올바른 이관) / 약화(쉬운 예제만 잘하고 모호 사례 실패, 근거 없는 정보 사용, 필수 필드 누락, 비일관 에스컬레이션) / 상급 보고. 다음 단계는 추천, 예시 추가 수집, 다른 클래스 테스트, 패턴 수정, 인간 검토 추가, 전문가 이관 중 하나다.

#### 모델 선택 결정 논리 적용하기
- 핵심 질문: "지금 책임감 있게 권고할 수 있는 것은 무엇이고, 무엇이 아직 검증이 필요한가?" → 경로 제시 / 검증 / 상급 보고 중 선택.
- 이해관계자가 고객 요구에서 모델 이름으로 너무 빨리 넘어갈 때 4단계 구조로 논의를 정리한다(예: "공급업체 온보딩에 어떤 모델?" → 수집 정보, 승인 정책 출처, 시스템 읽기/쓰기 여부, 필요한 사람 승인, 신뢰를 입증할 평가 근거부터 확인).
- **초기 권고의 경계 명시**: "설명된 워크플로우 기준으로 검증할 초기 모델 클래스·솔루션 패턴이며 최종 구현 권고가 아니다"처럼 말한다. 확정 아키텍처, 실전 구현 계획, 보안·규정 준수 승인, 가격·가용성 확약, 정확한 모델 선정, 벤치마크 결과, 전체 평가 계획, 상세 API·통합 설계, 고객용 구현 사양처럼 들리게 하지 않는다.

### 기억할 개념·프레임워크
- 작업 형태 진술문 구성: 작업 / 입력·맥락 / 예상 결과 / 사용자·하류 시스템 / 검토·성공 요건
- 일반 작업 패턴 11가지: 요약·종합 / 분류·라우팅 / 추출·구조화 / 초안·재작성 / 추론·분석 / 검색 기반 답변 / 도구 활용 워크플로 지원 / 멀티모달 이해 / 음성·실시간 상호작용 / 코드·개발자 워크플로 지원 / 검토·안전 필터링
- 출력 초기 질문 3가지: 다음 사람·시스템이 출력을 어떻게 쓰나? 어떤 형식이어야 하나? 얼마나 자주·반복 가능하게 요청되나?
- 지속적인 모델 클래스와 관련 기능

| 범주 | 유용한 경우 |

| 범용 모델 | 문서 작성, 요약, 재작성, 분류, 일상 업무 지원 등 광범위한 언어 작업 |

- 의사결정 요인: 추론 깊이 / 지연 시간 / 비용 / 규모 / 맥락 / 구조화 출력 / 도구 사용 / 위험 / 평가 요구
- 솔루션 경로 3계층: ① 사용자·제품 인터페이스(ChatGPT Chat: 협업적 사고·초안·분석 / ChatGPT Work: 결과·맥락·제약·검토 기준을 정의한 위임형 다단계 지식 업무 / Codex: 위임형 소프트웨어 엔지니어링 / API로 구축한 애플리케이션·프로세스: 내장형·맞춤형 AI 경험) ② 기능·아키텍처(검색, 구조화 출력, 도구 활용, 에이전트 조율·자동화, 멀티모달·실시간) ③ 배포·운영(호스팅·임베딩, 신원, 권한, 승인, 인간 검토, 보존, 로깅, 모델 호스팅 제약)
- API 솔루션 패턴: 텍스트 생성, 구조화 추출, 분류·라우팅, 검색 기반 응답, 요약·합성, 멀티모달 이해, 음성·실시간, 도구 사용 워크플로, 검토·안전 필터링, Human-in-the-Loop 검토
  - 함의: 구조화 추출 → 예측 가능한 필드·형식 검증 / 검색 기반 답변 → 승인 출처·근거 검증 테스트 / 도구 활용 → 권한 경계·오류 처리 / 인간 검토 → 승인·거부·보고 기준
- 4단계 모델 선정 의사결정 구조

| 결정 영역 | 명확히 하는 내용 | 지침 질문 |
|---|---|---|
| 작업 형태 및 산출물 요구사항 | 워크플로 라벨, 작업 패턴, 필수 산출물, 맥락 요구, 위험 신호, 검토 필요, 누락 질문, 성공 기준 | AI에게 어떤 작업을 요청하나? |
| 모델 클래스 및 의사결정 요인 | 예상 모델 클래스, 대안, 추론 깊이·지연·비용·맥락·구조화 출력·도구·위험·평가 요구 | 어떤 클래스가 타당한 초기 가설이고, 어떤 상충 관계가 가장 중요한가? |
| 솔루션 경로 및 패턴 | 주 인터페이스, 기능·아키텍처, 배포·운영 제약, 패턴(조합), 적합 이유, 검증 항목 | 어디서 운영되고, 무엇을 하며, 어떻게 실행·제어되나? |
| 평가 근거 및 에스컬레이션 | 성공 기준, 대표 시드 사례, 지원·취약점·에스컬레이션 신호 | 고객 공개·실행 전 어떤 증거가 필요한가? |

- 다음 조치 3가지: 경로(워크플로 충분히 명확 → 시작 클래스·경로·패턴 제시) / 검증(증거·요구사항 누락 → 권고 전 확인) / 상급 보고(제품·보안·데이터·규정 준수·아키텍처·구현에 전문가 필요)

### 실무 적용 예시
- **계약 검토 요청:** "계약 검토용 모델이 필요하다"는 아직 워크플로 명칭이다. 상업 조건 요약, 의무·갱신일·지급 조건 추출, 플레이북 대비 조항 비교, 특이 조항 표시, 협상 메모 작성, 위험도별 검토 대기열 배정 중 무엇인지 먼저 확인한다(추출 → 구조화 출력, 정책 비교 → 승인 출처·검색, 라우팅 → 분류·에스컬레이션 규칙, 협상 메모 → 사용 전 신중한 수동 검토).
- **대량 지원 메시지 분류:** 분류가 명확하고 입력이 짧으며 출력이 단순 레이블이면 효율적 모델이 출발점(일관성·지연·비용·규모 중시). 모호·다중 이슈·계정 맥락·현행 정책 의존이면 추론 중심 모델, 검색, 도구 접근, 에스컬레이션 로직이 필요할 수 있다. 대표 사례로 검증해 긴급·민감 사례를 놓치면 클래스·라우팅·검토 단계를 바꾼다.
- **갱신 청구서 조정:** 서명된 수정 계약으로 요율·갱신일이 바뀌었지만 기록·청구 일정은 옛 약관 그대로인 상황에서, 승인 기록을 대조해 유효 약관을 확인하고 재무팀 검토용 초안만 작성(발행 아님). 품질 기준은 정확한 날짜·금액, 변경 조건별 추적 가능 근거, 기록 충돌·증거 누락 시 상급 보고. 권한은 모델이 아닌 애플리케이션이 부여한다. 요구사항이 명확해진 뒤 기존 방식과 Astra를 같은 기록·도구로 비교하고, 품질 기준을 허용 비용 내에서 충족하면 더 단순한 쪽을 채택한다. 시드 세트에는 일치 기록, 상충 수정안, 증거 누락, 조회 도구 불가 사례를 넣고 기대 결과는 허위 발행이 아닌 정직한 중단·검토 이관이다.
- **조달 접수 개선:** 시스템 연결·구조화 출력·승인 정책 컨텍스트·예외 인간 검토가 필요하면 주 인터페이스는 API로 구축한 애플리케이션·프로세스이고, 분류 + 구조화 추출 + 승인 지침 검색 + 공급업체·승인 데이터 도구 활용 + 예외 인간 검토를 조합한다. 권고 전 대상 시스템, 승인 정책 출처, 읽기 전용인지 업데이트까지인지, 사람 승인이 필요한 예외를 확인한다. 과도한 약속 없이 방향·이유·검증 항목을 제시하는 답변이다.
- **지원 티켓 분류 eval:** 효율적 vs 추론 중심 클래스를 간단·모호·정보 누락·긴급·에스컬레이션 필요 티켓으로 비교한다. 효율적 모델이 대표 세트를 충분히 처리하면 운영상 더 나은 권고가 되고, 모호·고위험 사례에서 실패하면 추론 모델·라우팅·검토 강화가 필요하다.

### 지식 점검 포인트
- "클레임 검토에 어떤 모델을 써야 하나?"에 업무 절차 중심을 유지하는 질문은? → "청구 심사에서는 무엇을 수행해야 합니까?"(승인된 모델명, 최신 모델 사용 여부, 회의 참석 인원은 오답).
- 워크플로 요구 → 모델 클래스·기능 매칭 → 문서 이미지 이해: 멀티모달 모델 / 승인된 내부 문서 전반 검색: 임베딩 또는 검색 지원 기능 / 모호한 정책 해석: 추론 중심 모델 / 검토 전 안전성 필터링: 모더레이션·안전 중심 기능 / 대량 단순 분류: 효율적인 모델.
- 보험 청구 앱(유형 분류·필드 추출·약관 규칙 조회·예외 담당자 검토)의 초기 패턴 권장은? → API로 분류·구조화 추출·검색·사람 검토를 갖춘 애플리케이션/프로세스 구축(ChatGPT Chat 단독, Codex 주 인터페이스, 이른 오픈 모델 배포 결정은 오답).
- 쉬운 예제는 잘하지만 모호한 요청·고위험 예외를 놓치면? → 실패 사례를 라우팅 근거로 삼아 증거 추가 수집·대안 테스트·안전장치·상급 보고를 진행한다(평균 결과로 추천, 고위험 사례 제거, 멀티모달 전환은 오답).
- 항목 → 결정 영역 매칭 → 워크플로 레이블·작업 패턴·필수 산출물·상황적 요구·위험 신호: 작업 형태 및 산출물 요구사항 / 타당한 모델 클래스·대안·의사결정 동인·상충 관계: 모델 클래스 및 의사결정 동인 / 주 사용자·제품 표면, 기능·아키텍처, 배포·운영, 패턴 조합: 솔루션 경로 및 패턴 / 성공 기준·시드 케이스·지원·취약점·에스컬레이션 신호: 평가 근거 및 에스컬레이션.
- 선택 실습 1(작업 유형 분해, 2–3분): "보험금 청구 심사에 AI 지원 필요" 요청을 작업 패턴·출력·맥락·위험 신호·누락 질문을 담은 작업 형태 메모로 정리.
- 선택 실습 2(모델 클래스 후보 선정, 2–3분): 대량 지원 메시지 분류에 유력 클래스(조합)·대안·핵심 요인 2–3개·검증할 상충 관계·필요 증거를 담은 상충 관계 메모 작성.
- 선택 실습 3(워크플로 3단계 구성, 2–3분): 청구 처리 앱에 주 인터페이스·패턴 조합·적합 이유·배포/운영 질문을 담은 라우팅·패턴 메모 작성.
- 선택 실습 4(평가 근거 정의, 3–4분): 지원 트리아지에서 기존 방식 vs GPT-6 Astra 매칭 비교 설계(고정 요소, 설정 차이, 성공 기준 2개, 시드 사례 3–5개, 뒷받침·약화·상급 보고 결과 유형). 실행 전 결과는 "미실행"으로 기록.
- 선택 실습 5(라우팅·검증·에스컬레이션, 3–5분): 미확정 사항이 많은 공급업체 온보딩 자동화 요청에 대응 방안·이유·다음 기술 질문을 담은 결정 메모 작성.

**한 줄 요약:** 기능 목록이 아니라 워크플로우 요구 사항에서 출발해 각 기능이 맡는 역할·종속성·통제·검증 사항을 따지고, 첫 번째 책임 있는 버전에 필요한 최소 실행 가능 역량 세트를 고르는 법을 배운다.

### 핵심 내용
#### 환영합니다 (도입)
- 플랫폼 기능은 AI 아이디어를 실제 제품·워크플로우·개발자 경험으로 구현하는 빌딩 블록이다. 이 과정은 기능 목록이 아닌 워크플로우 요구 사항으로 기능을 고르는 연습을 한다.
- 목표: 역할(상호작용·컨텍스트·액션·오케스트레이션·평가·개발자 워크플로우)로 기능 구분, 새 사용자 지정 API 프로젝트는 Responses API로 시작, 구조화된 출력·파일 검색·도구 호출·Agents SDK·MCP·평가·오디오/실시간·Codex가 언제 관련되는지 파악, 상충 관계·종속성·통제·에스컬레이션 신호 식별.

#### 기능 목록이 아니라 역량에 초점 맞추기
- 플랫폼 기능은 업무의 한 부분을 수행하는 재사용 가능한 기술 빌딩 블록이며, 명확한 워크플로우 요구와 연결될 때 유용하다.
- 좋은 권고는 네 가지를 설명한다: 구성 요소의 역할 / 왜 지금 필요한지 / 어떤 종속성·통제·상충 관계를 낳는지 / 권고 전에 무엇을 검증해야 하는지.
- OpenAI 기능의 업무상 역할: API(제품·운영·고객 접점에 지능을 접목하는 구축·통합 경로), ChatGPT 경험(Chat은 협업적 사고·창작, Work는 사용 가능·활성화 시 위임된 지식 업무), Codex·개발자 도구(소프트웨어 배포·엔지니어링), 에이전트(컨텍스트·도구·안전장치·승인을 활용해 업무 수행).
- "검색이 필요해요", "에이전트가 필요해요", "Codex를 쓰고 싶어요" 같은 기능 이름은 워크플로우 요구를 설명하지 못한다. 기능 우선 제안은 사용자 요구·소스·출력 형식·작업 범위·위험을 확인하기 전에 복잡성을 키워 과잉 구축, 검증·라우팅·인계 곤란을 낳는다.
- 기능 추가 전 질문: 어떤 역할을 하나? 어떤 종속성·통제를 도입하나? 1차 버전에서 빼면 어떻게 되나? 권고 전 무엇을 검증해야 하나?
- **최소 실행 가능 기능 세트:** 워크플로우 성공에 필요한 가장 작은 *책임 있는* 조합. 가장 작은 데모가 아니라 사용자 요구 충족, 위험 관리 통제, 다음 기술 결정을 뒷받침할 근거를 갖춘 최소 버전이다. 지금 필요한 것 / 나중에 추가할 것 / 위험·비용·운영 부담을 키우는 것 / 데이터·권한·소스 품질·시스템 준비에 좌우되는 것 / 전문가 검증이 필요한 것을 구분한다.

#### 상호작용 및 컨텍스트 기능 선택
- **상호작용 계층:** 애플리케이션·워크플로우가 AI에 작업을 요청하고 출력을 받는 부분이자 워크플로우의 인계 지점. 흐름: 요청 → 지침 → 입력 → 컨텍스트 → 출력 → 검토 또는 조치.
- **Responses API:** 새 사용자 지정 API 프로젝트(맞춤 앱·제품 기능·시스템 간 프로세스)의 기본 시작점. 주변 애플리케이션이 모델 호출 방식, 사용 가능한 정보·도구, 결과 처리를 제어한다.
  - 모델이 도구 실행을 *요청*했다고 실제 실행된 것은 아니다. 애플리케이션이 실행·추적하고 결과를 확인할 책임을 진다.
  - 지원 시 비동기 도구 호출(도구 실행 중 모델이 독립 작업 계속, 백그라운드 생성과는 다름), Responses WebSocket의 턴 도중 제어(요구 추가·변경은 가능하나 이미 시작된 작업·도구 호출은 취소 불가)는 필요할 때만 쓴다.
  - 적합성 신호: 맞춤 앱 경험, 텍스트·이미지·파일 입력, 음성·실시간 오디오, 구조화된 출력, 도구 사용, 다단계 상호작용, 검색·근거, 시스템 간 워크플로우, API 수준 제어 필요.
  - 모든 AI 워크플로우에 사용자 정의 API가 필요한 것은 아니다. ChatGPT 환경(Work 포함)으로 충분하면 그쪽이 더 나은 출발점이다. 상세 주장 전에는 공식 문서로 현재 기능을 확인한다.
- **후속 사용을 위한 출력 설계:** "무엇을 생성할까"가 아니라 "워크플로우 안에서 이 산출물이 어떤 형태여야 하나"를 묻는다. 후속 시스템에 신뢰할 수 있는 계약이 필요하면 JSON 스키마 기반 구조화된 출력을 쓴다.
  - 일관 형식 → 구조화된 출력 / 출처 참조 → 검색·인용 / 공개 전 검토 → 검토·평가 / CRM 업데이트 트리거 → 도구 범위·승인 설계.
  - 영업 담당자용 브리프(승인된 요약·출처·위험·다음 단계)와 운영자용 실행 기록(호출·결과 ID, 검증 실패, 승인, 상태)을 분리한다. 형식이 맞아도 비즈니스 의미가 뒷받침되는지 확인한다.
- **컨텍스트 계층:** AI가 비즈니스에 대해 아는 정보. 사용자가 직접 충분한 컨텍스트를 줄 수도, 승인된 소스에서 검색해야 할 수도, 구조화된 지식·권한 로직·전문가 입력이 필요할 수도 있다. 핵심 결정은 "검색을 추가할까?"가 아니라 "어떤 승인된 컨텍스트가 필요하고, 신뢰할 결과를 뒷받침할 준비가 됐나?"이다.
- **검색 준비도 = 콘텐츠 준비 + 접근 준비.** 신뢰할 출처, 소유·관리자, 최신성·완전성, 사용자 그룹별 권한 차이, 인용 필요 여부, 누락·상충 시 처리, 검색 품질 검증 방법을 확인한다. 예: 사용자가 회의록을 직접 주는 앱은 검색 불필요, 사내 IT 정책 어시스턴트는 검색·최신성·권한 검증·상충 지침 검토가 필요하다.

#### 도구, MCP 방식 통합, 경계로 시스템 연결
- 워크플로우가 "답을 돕는" 단계에서 "다른 시스템에 영향을 주는" 단계로 넘어가면 권한·승인·로깅·오류 처리·테스트·소유권·에스컬레이션 요구가 강해진다.
- 도구는 출력이 프롬프트·검색 문서·정적 컨텍스트 밖의 요소에 의존할 때 필요하다(레코드 검색, 상태 확인, 계산, 초안, 필드 업데이트, 워크플로우 트리거, 내부 API 호출).
- 직접 도구 호출: 모델이 도구 선택·결과 검토·다음 단계 결정을 해야 할 때. 프로그래밍 방식 도구 호출: 대량 검색·조인·집계·변환처럼 예측 가능하고 범위가 제한돼 모델이 중간 결과를 볼 필요가 없을 때만.
- **MCP 방식 연결:** 여러 도구·시스템, 재사용 가능한 연결, 에이전트 워크플로우, 개발자·플랫폼 팀 참여, 도구 접근 거버넌스가 필요할 때 검토할 가치가 있다. CRM 필드 하나 확인은 단순 도구 호출로 충분하다. 선별적으로 쓰고, 권한·시스템 접근·에이전트 행동·거버넌스에 영향을 주면 전문가를 참여시킨다.
- **애플리케이션 소유 경계로 정립:** 승인된 작업에 대해 완전하고 검증된 호출만 보내고 부분 스트리밍된 인수는 실행하지 않는다. 보류·완료·실패·차단 상태를 추적해 원래 호출과 매칭한다. 조회 실패는 빈 레코드가 아니며, 승인 누락은 진행 허가가 아니다.

#### 필요할 때만 실시간·다중 모드·에이전트·개발자 워크플로 도구 선택
- **상호작용 형태**(비동기, 채팅, 제품 내, 음성, 실시간 지원, 이미지·문서 이해, 다중 모드)가 기능 세트를 좌우한다. 워크플로우를 지원하는 가장 단순한 형태를 고른다. 비동기·텍스트로 충분하면 검증·운영이 더 쉽다.
- 실시간·다중 모드 검증 질문: 입력·응답 모달리티, 필요한 응답 속도와 지연 허용, 수집·저장 데이터, 동의·개인정보·접근성, 잘못 듣거나 읽을 때의 처리, 품질 평가 방법.
- **에이전트 기반 툴링:** 컨텍스트 추적, 시스템 간 도구 사용, 상태, 승인 단계, 재사용 지침, 인계, 테스트·추적, 운영 모니터링 등 조율된 다단계가 필요할 때 적합. 맞춤 앱에 관리형 오케스트레이션·인계·가드레일·추적이 필요하면 Agents SDK, 단일 경계 호출이면 더 단순한 패턴을 쓴다.
- **평가·가시성은 선택 시 고려 사항:** 기능마다 품질 질문이 생긴다(검색 → 관련성·근거, 구조화 출력 → 형식 준수, 도구 → 정확성·권한·오류·승인, 에이전트 → 단계 순서·인계·추적).
  - 평가 대상: 출력 품질, 형식 준수, 검색 품질, 도구 사용 정확성, 에스컬레이션, 안전 행동, 변경 후 회귀. 조회 도구 장애, 결과-요청 매칭 실패, 중간 중단 같은 실패 경로도 테스트하고, 미완성 브리프를 사용 준비로 표시하지 않는다.
  - 가시성: 실행 단계, 사용 도구, 포함된 컨텍스트, 오류, 승인 요청·부여, 문제 지점, 조사용 정보. 모니터링은 테스트·사람 검토를 대체하지 못한다(경고는 틀리거나 놓칠 수 있고, 중지해도 완료된 작업은 되돌려지지 않는다).
- **Codex·개발자 워크플로 도구:** 고객 요구가 소프트웨어 전달 과정 안에 있을 때(코드베이스 이해, 코드 변경, 테스트, 디버깅, PR 검토, 문서화, 릴리스·유지보수, 엔지니어링 위임, 개발 생산성 병목). 계정 브리핑 보조 도구 자체에는 불필요하고, 그 도구를 구현·테스트·유지하는 개발 업무로 넘어갈 때 관련된다. 저장소 접근, 환경·샌드박스, 승인·검토, 테스트 요구, 전문가 검증을 함께 밝힌다.

#### 가장 작은 책임 있는 역량 세트 선택
- 고객이 "계정 개요를 쓰는 에이전트"를 요청해도 가능한 기능을 나열하지 말고, 결과·컨텍스트·출력 형식·도구·검토·평가·가시성 요구와 미해결 검증 사항부터 명확히 한다.
- 4단계 의사결정 구조로 판단을 정리하되, 근거 없는 제품·가격·규정 준수·보안·아키텍처·구현·가용성 주장에 쓰지 않는다.
- **경계 설정 언어:** "설명된 워크플로우로 볼 때 최종 설계가 아니라 검증해야 할 1차 버전 기능 세트" 식으로 말한다. 확정 아키텍처, 실전 구현 계획, 보안·규정 준수 승인, 출시 약속, 가격 권고, 상세 API·SDK·MCP·Codex·평가·가시성 설계, 고객 적용 준비 사양처럼 들리게 하지 않는다.

#### 정리
- 핵심 원칙: 워크플로우에서 출발 → 필요한 기능만 선택 → 제품·보안·데이터·통합·거버넌스·구현 질문은 전문가에게 에스컬레이션. 기능을 추천하기 전에 올바른 질문부터 던진다.

### 기억할 개념·프레임워크
- 기능 역할 7가지

| 역할 | 의미 | 계정 브리프 예 |
|---|---|---|
| 상호작용 | 사용자·시스템이 솔루션과 상호작용하는 방식 | 내부 앱·워크스페이스에서 브리프 요청 |
| 컨텍스트 | 필요한 정보에 접근하는 방식 | 승인된 계정 메모·기회·통화 요약·정책 문서 |
| 조치(액션) | 도구 사용·다른 시스템에 영향 | CRM 상태 확인, 계산, 후속 작업 생성, 승인용 업데이트 준비 |
| 오케스트레이션 | 다단계 작업 조정 | 요청 수집 → 컨텍스트 → 누락 필드 확인 → 작성 → 검토 요청 |
| 평가 | 품질·신뢰성 테스트 | 완전성, 승인 출처 근거, 형식, 유용성 |
| 개발자 워크플로우 | 솔루션 생성·테스트·검토·유지 | Codex로 구현·테스트 추가·코드 리뷰·통합 유지 |
| 거버넌스·가시성 | 활동 제어·모니터링·개선 | 권한, 승인 단계, 로그, 사용 신호, 품질 검사, 에스컬레이션 경로 |

- 기능별 종속성: 검색 → 승인·최신·접근 가능한 소스 / 구조화된 출력 → 정의된 형식 / 도구 → 시스템 접근·권한·오류 처리·소유권 / 평가 → 성공 기준·대표 테스트 케이스 / 사람 검토 → 사용 방식과 위험.
- 읽기 전용 vs 실행형 도구

| 구분 | 하는 일 | 필요한 통제 |
|---|---|---|
| 읽기 전용 | 조회·검색·검사·계산(레코드 변경·후속 트리거 없음) | 접근 권한, 소스 검증, 로깅, 검색 품질 테스트 |
| 실행형 | 생성·업데이트·삭제·전송·승인·예약·트리거 | 위에 더해 승인 단계, 제한된 작업, 로그·추적, 오류 처리, 명확한 책임, 테스트 |

- 도구 경계 질문: 어떤 도구가 필요한가 / 읽기 전용·실행형 구분 / 허용·제한 작업 / 사람 승인 시점 / 실패 시 처리 / 기록 대상 / 통합 책임자 / 테스트 대상 / 에스컬레이션 대상. 경계가 명확해진 후에만 조회에서 실행으로 넘어간다("제어 전환" 관점).
- 4단계 역량 결정 구조

| 결정 영역 | 명확히 하는 사항 | 지침 질문 |
|---|---|---|
| 워크플로우 요구 사항 및 필수 역량 역할 | 수행할 작업, 결과물 사용자, 필요한 역할 | 솔루션이 어떤 업무를 지원해야 하나? |
| 최소 실행 가능 역량 세트 | 1차 버전 핵심 기능(추후 개선과 구분) | 지금 필수인 것과 미룰 것은? |
| 주요 종속성, 통제 수단 및 상충 관계 | 승인 소스, 권한, 도구 경계, 승인 단계, 평가, 로깅, 소유권, 운영 복잡성 | 각 기능이 무엇을 도입하고 무엇에 의존하나? |
| 검증 및 에스컬레이션 질문 | 제품 세부, 소스 준비, 시스템 접근, 보안, 데이터 권한, 통합 소유권, 구현 타당성, 거버넌스 | 무엇이 검증·전문가 검토가 필요한가? |

### 실무 적용 예시
- **계정 브리프 보조 도구:** "영업팀 계정 개요 작성 어시스턴트" 요청 → 상호작용 계층(내부 앱·워크스페이스), 승인 소스 검색, 구조화된 출력(개요·우선순위·진행 기회·위험·다음 단계), 필요 시 CRM 조회 도구, 평가, 고객 사용 전 사람 검토로 구성. 실시간·다중 모드·MCP·Codex·에이전트 툴링은 특별히 요구되지 않으면 불필요. 검증 질문: 승인 소스와 위치, 사용자별 접근 차이, CRM 접근 필요 여부(사용자가 맥락 제공 가능한가), 브리프 형식, 검토자.
- **Responses API 인계 흐름:** 모델이 CRM 조회 요청 → 애플리케이션이 요청과 허용 계정 검증 → 작업자가 조회 실행 → 결과를 원래 호출로 반환 → 모델이 영업 담당자 검토용 브리핑 준비.
- **조달 공급업체 상태 확인:** 읽기 전용 버전은 공급업체 기록·정책 상태·계약 메타데이터를 조회해 검토용 요약 반환(승인 여부, 계약 유효성, 정책 메모). 실행형 버전은 티켓 생성·기록 업데이트·승인 요청 전송까지 하므로 승인 게이트·제한 작업·로깅·소유권·테스트·오류 처리·에스컬레이션이 추가로 필요. 차이는 시스템이 아니라 "조회만 하나, 변경할 수 있나"에 있다.
- **에이전트형 확장:** 승인 메모로 브리프 초안만 쓰면 검색·구조화 출력·평가·검토로 충분하다. 여러 시스템에서 컨텍스트 수집 → 누락 필드 확인 → 사용자에게 질문 → 초안 → 후속 조치 준비 → CRM 업데이트 전 승인 요청 → 단계 기록까지 하면 에이전트 툴링이 타당해진다.

### 지식 점검 포인트
- 내부 계정 브리핑 보조 도구 1차 버전에서 가장 뛰어난 기능 판단은? → **워크플로 역할(사용자 요청, 승인된 컨텍스트, 일관된 출력, 검토, 검증)부터 시작**한다(모든 주요 기능 선포함, 에이전트 패턴부터, CRM write-back부터는 오답).
- 승인된 계정 메모 기반 브리핑 앱, 일관 형식 + 출처 참조, 사용자별 접근 권한 상이 → **구조화된 출력, 승인된 검색, 접근 권한 검증, 검토/평가**(실시간, Codex, "권한은 출시 후 처리"는 오답).
- CRM 기회 상태 조회 + 예측 필드 업데이트 → **경계를 분리: 상태 조회는 읽기 전용, write-back 전에는 승인**(둘 다 읽기 전용 취급, MCP 자동 사용, 도구 사용 회피는 오답).
- 음성·이미지·코드베이스·자율 업데이트가 불필요한 1차 계정 브리핑 도구에서 과도한 기능을 피하는 선택 → **승인된 컨텍스트, 구조화된 출력, 검토, 평가, 기본 가시성부터 시작하고 CRM 조회는 별도 검증**(실시간·다중 모드·Codex·에이전트 선추가, Codex, CRM 쓰기 선추가는 오답).
- 의사결정 영역 매칭 → 워크플로우 결과·사용자 그룹·필수 역량 역할: 워크플로우 요구 사항 및 필수 역량 역할 / 첫 번째 책임 버전에 필요한 역량: 최소 실행 가능 역량 세트 / 승인된 소스·권한·도구 경계·승인 단계: 주요 종속성, 통제 수단 및 상충 관계 / 제품·보안·데이터·통합·구현 질문: 검증 및 상신(에스컬레이션) 질문.
- 선택 실습(역량 역할 파악, 2–3분): 계정 브리핑 요청에 대해 워크플로우 결과·사용자 그룹·필수/선택 역할·선정 전 질문을 메모한다.
- 선택 실습(상호작용·맥락 요구 결정, 3–4분): 상호작용 경로, 승인 컨텍스트 소스, 검색 필요성, 소스 품질·권한 검증, 구조화 출력 여부를 정리하고 영업용 브리프와 운영자 기록을 구분한다.
- 선택 실습(도구 사용 경계 설정, 3–4분): 조달 공급업체 사례에서 읽기 전용·실행형 부분, 승인·제한, 실패 처리, 기록·책임·에스컬레이션 대상을 메모한다.
- 선택 실습(조건부 기능 분류, 3–4분): 상호작용 계층부터 Codex까지 11개 기능을 현재 필수 / 검증 필요 / 나중에 선택 / 이 버전에 불필요로 분류한다.
- 선택 실습(가장 작은 책임 기능 집합 선택, 4–5분): 초안 기능 13개 중 1차 버전 필수, 연기·제거, 검증 필요, 전문가 검토 대상을 정리한다.

**한 줄 요약:** 고객 워크플로우에 맞는 재사용 가능한 아키텍처 패턴을 먼저 고르고, 이를 사용자·컨텍스트·도구·검토·평가·위험·검증 필요 사항을 드러내는 간결한 1차 청사진으로 옮기되, 최종 설계로 과장하지 않는 법을 배운다.

### 핵심 내용
#### 환영합니다 (도입)
- 아키텍처 패턴은 "무엇을 구축할까?"를 최종 설계로 건너뛰지 않고 워크플로우·사용자·맥락·도구·검토·위험·미해결 문제에 대한 기술 대화로 바꿔 주는 공통 언어다.
- 학습 목표: 일반 패턴 식별, RAG·에이전트 오케스트레이션·인간 검토·멀티모달·음성·엔터프라이즈 통합이 언제 맞는지(그리고 순위 지정/재순위 지정이 언제 검색 맥락의 관련성을 높이는지) 구별, 청사진이 요구·데이터·컨텍스트·도구·런타임·거버넌스·성과 지표를 잇는 방식 설명, 가정·위험·검증 필요 사항 파악.
- 선택 산출물: 4개 섹션으로 된 간소화 청사진. 논의를 쉽게 하되 모든 설계 문제가 해결된 것처럼 보여서는 안 된다.

#### 설계도보다 패턴을 먼저 생각하라
- 고객이 기회를 설명하면 도구·통합·모델로 바로 뛰어들기 쉽다. 먼저 "어떤 솔루션 형태인가?"를 묻는다(신뢰 지식 기반 답변? 다중 도구 단계 조율? 실행 전 사람 검토? 멀티모달 입력? 기업 시스템 통합?).
- 패턴은 누가 쓰는지, 필요한 정보, AI의 역할, 관여 도구·시스템, 사람 검토·승인 지점, 성공 평가 방식, 모니터링·에스컬레이션 대상을 설명하게 해 준다. 모든 해법을 일회성 맞춤형으로 다루거나 성급히 기술 선택으로 넘어가는 것을 막는다.
- 패턴 계열은 엄격한 범주가 아니며 실제로는 자주 겹친다(검색 → 관련성 순위 → 구조화 → 사람 검토 → 타 시스템 업데이트). 목록 암기보다 워크플로우를 가장 잘 설명하는 패턴을 고르는 것이 중요하다.
- 좋은 1차 청사진은 "모호해서 쓸모없는" 상태와 "가정 검증 전에 지나치게 세부적인" 상태라는 두 실수를 피한다.
- 실제 사례(HR 정책 어시스턴트): 주 패턴은 RAG + 정책 문구 재순위 지정 + 담당자 에스컬레이션. 일관된 후속 조치 초안이 필요하면 구조화 출력이 보조 패턴. 티켓 생성·권한·승인·로깅이 검증될 때까지 도구 사용은 가정하지 않고, 1차 버전에서는 티켓 생성을 추후 검증 항목으로 둔다. 주제 빈도 분석·클러스터링·이상치 탐지는 별도 분석 작업이다.

#### 블루프린트 지식 및 오케스트레이션 패턴
- 혼동하기 쉬운 두 패턴: **검증된 지식 활용(RAG)** vs **다단계 작업 오케스트레이션**. 에이전트 용어는 워크플로우가 요구하기 전에 불필요한 복잡성을 더할 수 있다.
- **RAG가 맞는 경우:** 내부 문서·정책·기록·지식 기반에 의존, 답변이 출처에 근거해야 함, 참고 자료·증거가 필요, 원본 콘텐츠 통제 필요, 근거 없는 답변을 피해야 함.
- 검색은 후보 문단을 만들고, 순위 지정/재순위 지정은 관련성 순으로 정렬해 가장 유용한 승인 맥락이 먼저 오게 한다(키워드 빈도로 문의를 묶는 것과 다름).
- RAG도 판단을 없애지 않는다. 유창한 답변도 불완전·근거 부족·잘못된 출처일 수 있으므로 검토, 근거성·완전성 평가, 민감·미지원 사례 에스컬레이션이 필요하다. 출처로 뒷받침되지 않으면 명확화 요청·제한 표시·검토자 전달·에스컬레이션 같은 안전한 대응을 정의한다.
- API 논의의 핵심은 "연결 가능한가"가 아니라 앱이 무엇을 보내고, AI가 무엇을 반환하며, 어떤 시스템이 결과를 쓰고, 어떤 접근·형식·검토·오류 처리 가정을 검증해야 하는가다.
- **에이전트 오케스트레이션이 맞는 경우:** 다단계 목표, 시스템 간 도구 사용, 상태·인계·워크플로 컨텍스트, 사람 승인, 완료 기준, 오류 처리, 로깅·추적·모니터링, 결과 달성까지 반복. 단일 답변·요약·분류·구조화 출력이면 더 단순한 패턴이 낫다.
- 일반 위험: 불충분·노후 원본, 접근·권한 로직 누락, 미지원 출력 형식, 도구 오용·예상 밖 동작, 불명확한 검토 책임, 미흡한 성공 기준, 평가·가시성 부족, 미검증 통합 가정. 목표는 위험 제거가 아니라 가장 중요한 위험을 명명해 적임자가 평가하게 하는 것이다.

#### 블루프린트 검토, 멀티모달, 음성 및 통합 패턴
- 검토·모달리티·통합 결정은 책임 소재, 상호작용 방식, 관련 시스템, 검증 대상을 드러내 청사진을 더 명확하게 만들어야 한다.
- **사람 검토가 필요한 경우:** 고객 대상 결과물, 고위험·판단 중심 결정, 민감 데이터, 규정 준수 콘텐츠, 조치 수행 도구, 저신뢰 출력, 예외·모호 사례. 저위험 내부 초안은 사용자 확인으로 충분할 수 있다.
- "human in the loop"만으론 부족하다. 검토 대상, 검토자, 트리거, 기준, 변경 가능 범위, 불합격 시 처리(수정·반송·전문가 에스컬레이션·지원 불가 표시·조치 차단), 기록 항목, 피드백 반영, 에스컬레이션 대상을 명시한다.
  - 나쁜 예: "위험 사례는 인간 개입 필요" / 좋은 예: "환불·계정 해지·법적 문구·미해결 고객 이슈가 포함된 권고는 발송 전 지원 관리자가 정책 준수·근거·어조·고객 영향을 확인하고, 근거 부족 시 지원 팀장에게 상신".
- 검토자 수정·거부 결과·상신 사례·반복 실패는 프롬프트·소스·평가 사례·안전장치 개선으로 이어지는 선순환이 된다. 검토는 병목 없이 위험을 실질적으로 줄이는 곳에 둔다.
- **멀티모달·음성이 맞는 경우:** 이미지·스크린샷·양식·스캔 문서, 오디오 입출력, 핸즈프리·현장 업무, 실시간 안내, 고객 지원 전화, 접근성, 실시간 번역. 핵심 질문은 모달리티가 가치나 실현 가능성을 바꾸는지이며, 텍스트·비동기 방식으로 같은 결과가 나오면 불필요하다.
- 모달리티 청사진은 입출력 모달리티, 사용자 환경, 지연 시간, 동의·개인정보·접근성, 수집·저장, 검토, 오인식·오청취·저신뢰 시 오류 처리, 모달리티별 평가 사례를 담는다(예: 현장 음성 안내는 배경 소음·응답 속도, 스크린샷 지원은 이미지 품질·민감 정보).
- **엔터프라이즈 통합:** 관련 시스템, 데이터 이동, 접근·권한, 도구·통합 담당, 승인 단계, 가시성, 검증 질문, 인계·에스컬레이션 경로를 드러낸다. "고객 시스템에 연결한다"로 끝내지 않는다. 상세 통합 아키텍처·보안·데이터 처리·배포는 전문가나 이후 설계 단계로 넘긴다.
- 하이브리드 사례(정책 조회 → 양식 필드 추출 → 자격 규칙 확인 → 권고 작성 → 관리자 승인 → 레코드 업데이트): 핵심이 전 과정 조율이면 주 패턴은 에이전트 오케스트레이션이고, 검색(근거)·추출(접수 구조화)·검토(책임)·통합(기존 시스템 연결)이 지원한다.

#### OpenAI 솔루션 청사진 구축 및 압력 테스트
- 청사진 4개 섹션: ① 워크플로·사용자 그룹·선택 패턴 ② 컨텍스트·데이터·런타임·도구·통합 가정 ③ 인적 검토·에스컬레이션·평가·성공 지표 ④ 위험·검증 필요 사항·권장 다음 기술 단계.
- 좋은 청사진의 세 역할: 워크플로 용어로 해법 형태 설명, 검증이 필요한 가정 표시, 책임감 있는 다음 기술 단계 제시.
- 간결하게 유지: 전체 아키텍처 다이어그램, 클라우드 배포 계획, 상세 통합 맵, 보안·거버넌스 설계, 제품 구성 가이드, 최종 평가·가시성 사양이 되면 안 된다. 예: "1차 버전은 승인된 운영 기록 사용, 시스템 write-back 없음, 소스 소유권·접근 범위 검증 필요."
- 미해결 질문이 남아도 논의 준비가 된 것일 수 있다. 오히려 그것을 드러내는 것이 1차 청사진의 핵심이다.
- 정리: 워크플로우에서 출발 → 작동 방식을 가장 잘 설명하는 패턴 선택 → 가정을 드러냄 → 제품·보안·데이터·통합·구현 세부는 전문가 검증으로 상신.

### 기억할 개념·프레임워크
- 세부 수준 3단계

| 수준 | 핵심 질문 | 내용 |
|---|---|---|
| 아키텍처 패턴 | 이 워크플로에 맞는 일반적 해법 형태는? | 재사용 가능한 틀(RAG, 인간 검토, 에이전트 오케스트레이션, 엔터프라이즈 통합 등) |
| 1차 청사진 | 그 형태가 여기에 어떻게 적용되며 아직 무엇을 검증해야 하나? | 사용자·워크플로·맥락·도구·검토·평가·위험·가정·검증 요구 |
| 최종 기술 설계 | 검증된 해법을 어떻게 구현·운영·보안·확장·지원하나? | 전문가 주도: 아키텍처, 배포, 인증, 데이터 처리, 로깅, 모니터링, 보안 통제, 통합·구현 사양 |

- 패턴 계열 9가지: 검색 기반 생성 / 구조화된 추출·변환 / 에이전트 워크플로 조정 / 검색 순위 지정·재순위 지정 / 인간 개입형 검토 / 멀티모달 / 음성·실시간 상호작용 / 엔터프라이즈 통합 / 하이브리드
- 용어: **컨텍스트**(AI가 써야 할 승인 문서·기록·정책·비즈니스 규칙·사용자 입력) / **런타임**(업무가 어디서 어떻게 실행·조정되는지; 구성은 불필요, 트리거·조정·승인·모니터링·완료 의존 여부만 파악) / **가시성**(출력·오류·승인·에스컬레이션·반복 실패·품질 신호 등 모니터링·통제·개선 대상)
- 패턴별 청사진 구성 요소

| 패턴 | 청사진에 담을 것 |
|---|---|
| RAG | 사용자 질문·과제, 승인 소스, 소스 소유자, 접근·권한 가정, 검색·컨텍스트 메커니즘, 출력 형식, 출처 참조 요건, 민감 주제 검토·에스컬레이션, 근거성·완전성·무근거 답변 평가, 소스 업데이트 절차 |
| 에이전트 오케스트레이션 | 트리거, 사용자 목표·완료 기준, 주요 단계, 관련 도구·시스템, 사람 승인·검토, 실패·대체 조치, 책임·에스컬레이션, 평가·추적·가시성·성공 신호, 규모 확대 시 일관성 위한 안전장치 |

- 청사진 수정자(modifier): 출력이 고객에게 전달 → 사람 검토 / 스캔 양식 입력 → 멀티모달 / 시스템 레코드 업데이트 → 기업 시스템 연동 / 검색·도구·승인 결합 → 하이브리드 / 실시간 음성 지원 → 음성·실시간 상호작용
- 검증 질문 9가지: 워크플로 명확? 패턴이 워크플로에 부합? 컨텍스트·데이터 가정 명확? 런타임·도구·통합 가정 명확? 중요한 곳에 사람 검토? 평가가 성공 지표와 연계? 위험·가정 드러남? 에스컬레이션 기준 명확? 논의하기에 충분히 간단?
- 신중한 표현 예: "타당한 시작 경로로 보이지만, 권장 사항으로 보기 전에 소스·접근·런타임·도구·검토·평가·거버넌스 가정을 검증해야 한다."

### 실무 적용 예시
- **HR 정책 어시스턴트 1차 청사진:** 워크플로(직원 정책 질문 + 후속 조치 초안) / 사용자(직원, 인사 운영 검토자, 에스컬레이션 시 관리자) / 주 패턴 RAG / 지원 요소(정책 문구 재순위 지정, 민감·근거 부족·모호 사례 수동 검토, 후속 조치용 구조화 출력) / 데이터(승인 HR 정책, 소유권·업데이트 절차·역할 기반 접근 가정) / 도구(1차 버전 티켓 생성 제외) / 평가(근거성, 완전성, 출처 인용 정확도, 무근거 답변 처리, 에스컬레이션 정확도) / 검증(출처 소유권, 접근 권한, 정책 최신성, 민감 주제 규칙, 검토 기준, 향후 티켓 생성 승인).
- **월별 예외 보고서:** 1차 버전은 승인 기록·이전 보고서로 초안 작성 + 관리자 검토, 시스템 업데이트 없음 → RAG + 인간 검토. AI가 초안을 쓴다고 에이전트형이 아니다. 이후 시스템 간 기록 확인·승인 요청·운영 도구 업데이트·지속 모니터링이 생기면 에이전트/하이브리드로 전환. 검증 항목: 승인 기록 범위, 기록 소유자, 필수 포함 내용, 권고 형식, 검토 관리자, 평가 항목, 기록 누락·상충 처리, 미검증 도구·통합 가정.
- **경비 정책 어시스턴트 비교:** A(승인 정책 기반 답변 + 예외 시 재무 문의 안내, RAG) vs B(경비 내역 확인·예외 판단·티켓 생성·시스템 업데이트, 에이전트). 1차 버전은 단순한 A를 택하고, 조율된 조치가 실제로 요구될 때 패턴을 바꾼다.

### 지식 점검 포인트
- 항목 → 수준 매칭: "구조화된 추출 및 예외 사항 수동 검토" → 아키텍처 패턴/패턴 조합 / "세부 인증·보존·로깅·배포·통합·지원 설계" → 최종 기술 설계 / "검색 기반 생성 및 인간 검토" → 아키텍처 패턴 / "승인 HR 문서 사용, 출처 참조 표시, 민감 질문 에스컬레이션, 티켓 생성은 검증 항목인 정책 어시스턴트" → 1차 청사진.
- 승인된 정책 출처, 인용된 답변, 정책 누락 시 이관 절차가 필요한 워크플로의 패턴은? → **검색 기반 생성(RAG)**(기본값 에이전트 오케스트레이션, 음성·실시간, write-back 통합은 오답).
- 워크플로 신호 → 청사진 수정자: 실시간 음성 지원 → 음성·실시간 상호작용 / 시스템 레코드 업데이트 → 기업 시스템 연동 / 검색·도구 사용·승인 결합 → 하이브리드 패턴 / 출력물이 고객에게 전달 → 사람 검토 / 스캔 양식 입력 → 멀티모달 워크플로우.
- 1차 논의에 가장 효과적인 청사진 노트는? → **승인된 인사 정책 활용, 출처 인용, 민감 사안 상급자 보고, 접근 권한 검증**(강력한 모델·빠른 응답·전사 확대, 도입·시간 절감 지표 추적, 최종 인프라·보존·인증·모니터링 설계 포함은 오답).
- 선택 실습 1(세부 수준 분류, 8–10분): HR 어시스턴트 관련 문장을 패턴/초기 논의/최종 설계로 분류하고, 검증 전 최종으로 보면 위험한 문장을 성찰한다.
- 선택 실습 2(더 간단한 패턴 선택, 4–5분): 경비 정책 어시스턴트의 RAG안과 에이전트안을 비교해 1차 버전 패턴과 추가 복잡성을 정리한다.
- 선택 실습 3(추가 복잡성 정당화, 4–5분): 접수 양식 어시스턴트의 검토·멀티모달·음성·통합·하이브리드 각각을 "지금 필요/나중에/아직 불필요"로 판단한다.
- 선택 실습 4(1차 청사진 작성, 5–7분): 월별 예외 보고서 개요로 4개 섹션 청사진을 섹션당 1–2문장으로 작성한다.

**한 줄 요약:** 거버넌스를 걸림돌이 아닌 신뢰 수단으로 보고, 데이터·권한·조치 위험·통제 수단을 점검해 "알려진 것 / 가정한 것 / 검증할 것 / 누가 다음 단계를 맡는가"를 담은 보안·거버넌스·데이터 준비도 권고안을 쓰는 법을 배운다.

### 핵심 내용
#### 환영합니다 (도입)
- 보안·거버넌스·데이터 결정은 AI 솔루션이 신뢰받고, 도입·확장되고, 책임 있게 운영될 수 있는지를 좌우한다.
- 실무 위험 신호 인식, 거버넌스 요구 정리, 전문가 검증이 필요한 시점 파악에 초점을 둔다.
- 산출물은 4개 섹션의 간결한 '보안, 거버넌스 및 데이터 준비도 권고안'. 규정 준수 검토·법률 자문·보안 아키텍처·개인정보 평가가 아니라, 현재 아는 것·가정한 것·검증할 것·담당자를 정리하는 실무 문서다.

#### 거버넌스를 신뢰 구축의 수단으로 삼기
- 신뢰할 수 있는 AI 작업에는 좋은 프롬프트 이상으로 운영 모델(워크플로우 운영 방식, 책임자, AI가 할 수 있는 일)이 필요하다.
- 거버넌스 = AI 기반 업무가 통제·검토·모니터링·개선되는 방식. 소유권, 권한, 데이터·도구 경계, 승인 규칙, 검토 기준, 평가, 가드레일, 로그, 감사 가능성, 에스컬레이션 경로, 운영 모니터링을 포함한다.
- 거버넌스는 관료주의가 아니다. 책임자·경계·검토·에스컬레이션이 미리 정해지면 나중의 모호성 해소 비용이 줄어 오히려 빨라진다. 약한 거버넌스는 시범 운영 지연, 피할 수 있는 위험, 후기 재작업을 낳는다.
- 이 과정에서의 역할은 통제를 직접 구성하는 것이 아니라, 언제 중요한지 알아보고 질문하며 전문가 검증 시점을 파악하는 것이다.
- 솔루션 유형(ChatGPT 워크스페이스, API 앱, 에이전트·도구, Codex, 오픈 모델·자체 호스팅)에 따라 통제는 달라지지만 습관은 같다: AI가 무엇에 접근·수행하는지, 누가 검토하는지, 어떻게 모니터링하는지, 개선 책임은 누구인지 묻는다.
- Codex는 모든 편집·명령에 승인이 필요하다고 가정하지 않는다. 활성 샌드박스와 정책이 허용 경계를 정한다. 오픈 모델·자체 호스팅은 인프라·패치·모니터링·운영 책임 검토가 필요하다.

#### 데이터의 민감도, 접근, 소유권 및 이동 매핑
- 데이터 준비는 "시스템이 접근할 수 있는 것"과 "고객이 사용을 승인한 것"을 구분하는 데서 시작한다. **사용 가능한 데이터가 곧 승인된 데이터는 아니다.**
- 민감도가 높을수록 더 강한 접근 제어·검토·로깅·전문가 검증이 필요하다. 권고안에 "데이터 사용 가능"이라고만 쓰지 말고 유형·민감도·출처·소유자·접근 경계·필요 검증을 적는다.
- 접근 제어는 검색·도구·에이전트·연결 시스템이 관여할 때 특히 중요하다. 접근 경계를 지키지 않으면 볼 권한이 없는 사용자에게 정보가 노출될 수 있다.
- 데이터 흐름을 처음부터 끝까지 매핑한다(유입, 모델·API 전송, 연결 시스템 조회, 출력 저장 위치, 로그 보관, 재사용 금지 데이터, 고객 보존 정책). 하나의 보존·삭제 설정이 모든 제품 표면·엔드포인트·도구·로그를 포괄한다고 가정하지 않는다.
- API 워크플로우는 저장·보존 통제를 검증하고, Zero Data Retention 요구가 사용할 수 있는 엔드포인트·도구·기능 선택을 바꾸는지 확인한다.
- 데이터 메모는 검증 질문으로 전환한다(데이터 메모 → 검증 질문 → 위험 영역 → 검증 담당자 → 다음 책임 단계). 불확실성을 확신으로 오인하지 않는다.

#### 권한, 역할, 도구 위험 및 승인 범위 정의
- 권한과 역할은 데이터 경계를 운영 규칙으로 바꾼다: 누가 조회·수정·승인·전송·실행·무시할 수 있고 어디서 사람 검토가 필요한가.
- 역할이 불분명하면 위험하다. 초안은 AI가 써도 검토 기준·에스컬레이션 범주·최종 발송 권한, 원본 콘텐츠 업데이트, 접근 제어·로깅은 각각 담당자가 필요하다.
- 조치-위험 단계로 "AI가 도울 수 있다"에서 "AI가 행동할 수 있다"로 너무 빨리 넘어가는 것을 막는다. 같은 워크플로우도 시간이 지나며 단계가 올라갈 수 있다.
- 도구·에이전트 권한은 위험 프로필을 바꾼다. 승인 설정·작업 제약은 도구 사용 범위를 제한할 뿐, 연결 시스템 자체의 권한을 대체하거나 반환 콘텐츠의 안전성을 보장하지 않는다. 외부·검색 콘텐츠는 숨은 명령이 있을 수 있으므로 신뢰하지 않는다.
- 승인 게이트는 "사람의 개입"처럼 막연히 쓰지 말고 검토자, 검토 트리거, 적용 기준, 승인·거부·상신 후 다음 조치를 구체적으로 적는다.

#### 평가, 가드레일, 가시성, 감사 가능성으로 동작 제어·개선
- 유망한 데모만으로는 준비 완료가 아니다. 평가는 동작을 테스트하고, 가드레일은 경계를 정하고, 가시성은 실제 사용 상황을 보여주고, 감사 가능성은 사후 재구성을 돕는다.
- 평가는 정확성, 근거성, 완전성, 형식 준수, 거부·도구 사용·에스컬레이션 행동, 안전 민감 사례, 변경 후 회귀를 테스트한다. 고위험 워크플로우에서는 선택이 아니라 준비도의 일부다.
- 구조화된 출력은 하류 시스템의 모호성을 줄이지만 정확성을 보장하지 않으므로 여전히 평가가 필요하다.
- 가시성은 대시보드가 아니라 운영 질문이다: 잘 작동하는가, 어디서 실패하는가, 개선 책임은 누구인가. 적절한 지표는 워크플로우와 위험 수준에 따라 다르다.
- 개선 루프(실패 사례 검토, 지침·원본 콘텐츠·검색·가드레일 개선, 평가 세트 확장, 에스컬레이션 규칙 수정, 사용자 교육, 드리프트 모니터링)에는 담당자를 명시한다. 책임 소재가 없으면 문제를 찾아도 고칠 수 없다.
- 통제 수단은 단독으로 충분하지 않으며 서로 연계될 때 가장 효과적이다.

#### 검증 필요 사항 파악 및 준비도 권고안 작성
- 검증 필요성을 파악하는 것과 답을 주는 것은 다르다. 법률·규정 준수·개인정보·데이터 소재지·보안·제품 가용성·구현 준비에 대해 근거 없는 주장을 하지 않는다.
- 신중한 표현: "타당한 출발점으로 보이지만, 권고로 채택하기 전에 데이터·출처·접근·검토·평가·거버넌스 가정을 검증해야 한다." 이는 회피가 아니라 책임 있는 태도다.
- 검증 함정(트립와이어)이 있다고 작업이 자동 중단되지는 않는다. 불확실성을 확신으로 포장하지 말고 책임 있게 다루라는 신호다.

### 기억할 개념·프레임워크
- 실용적 거버넌스 질문: 워크플로우·데이터·AI 산출물의 소유자는? 데이터 출처와 이 워크플로우 사용 승인 여부는? 변경 승인자·고위험 산출물 검토자는? 제한 조치·기록 대상·에스컬레이션 사항은? 확장 전 필요한 증거와 검증 담당자는?
- 검증 역할: 워크플로우 소유자(프로세스·사용자·검토 단계) / 데이터 담당자(품질·승인 용도·접근·유지) / 보안 책임자(접근 제어·도구 권한·로깅·감사·사고) / 개인정보·법무 검토자(개인·규제 데이터, 보존, 지역, 계약) / 구현 책임자(환경·릴리스·모니터링·롤백) / 파트너 기술 책임자(가정 파악, 다음 단계 설정, 전문가 연결)
- 데이터 범주: 공개 / 내부 비즈니스 / 기밀 기업 정보 / 고객 데이터 / 개인정보 / 규제 대상 / 인증 정보·비밀·키 / 소스 코드·독점 기술 / 재무·법률·건강·고용·보안 민감 데이터
- 출처·소유권 질문: 저장 위치, 소유자·관리자, 접근자, 최신성, 워크플로우 사용 승인, AI 처리 가능 여부, 출력에 포함·노출 가능 여부
- 접근 제어 기본 질문: 접근이 필요한/제외할 사용자, 역할 기반 여부, 원본 시스템 권한 상속, 사용자별 컨텍스트 필요, 출력의 경계 초과 노출 가능성, 접근 변경 승인자

|---|---|
| 읽기 전용 | 정보 검색·요약 |
| 초안 | 사람이 검토할 콘텐츠 생성 |

- 승인 게이트가 필요한 곳: 민감 결과물, 대외 커뮤니케이션, 시스템 쓰기, 영향이 큰 결정, 부작용 있는 도구 사용, 프로덕션 변경, 보안 민감 조치, 예외, 저신뢰 결과
- 통제 수단

| 모더레이션(검토 점검) | 안전하지 않거나 정책상 민감한 콘텐츠 식별 |

- 권고안 품질 점검: 데이터 민감도 명시, 소스·소유자·접근 가정 명시, 읽기 전용과 실행 동작 구분, 검토·승인 단계, 평가·가드레일, 가시성·감사 신호, 근거 없는 규정 준수·보안 주장 회피, 검증 항목 식별, 다음 조치 명시

### 실무 적용 예시
- **고객 대응 초안 작성:** 승인된 지원 문서·최근 사례 메모·템플릿을 쓰는 초안 어시스턴트. 단순 텍스트 초안이라도 고객에게 영향을 주므로 승인 자료, 사례 메모 사용 가능 여부, 발송 전 검토자, 에스컬레이션 주제(환불·해지·법적 민원·미해결 사건·민감 영향), 거부·회피 사항, 기록 대상, 콘텐츠·규칙 업데이트 책임자를 명확히 한다. 거버넌스는 마지막 체크리스트가 아니라 설계의 일부이며, 파트너는 보안·법률 질문을 직접 승인하는 척하지 않는다.
- **사용 가능 vs 승인된 데이터:** 지원 플랫폼에 지원 문서·사례 메모·환불 결정·계정 내역·내부 에스컬레이션 코멘트가 있음. 지원 문서는 안전할 수 있지만 사례 메모는 개인정보·내부 메모 포함 가능, 환불·법적 불만은 더 엄격한 검토 필요, 내부 코멘트는 고객 응답에 부적절할 수 있다. 파트너는 승인 여부를 단독 판단하지 않고 출처별 민감도·소유자·노출 위험·검증 필요 사항을 권고안에 적는다.
- **공급업체 위험 정보 업데이트:** 조달팀이 요약·위험 표시·다음 단계 추천·최종적으로 시스템 업데이트를 원함. 읽기 전용 / 분석가 검토용 초안 / 승인이 필요한 권고 / 레코드 변경 쓰기 작업 / 자동화 금지 조치를 구분한다. 실제 조치에 가까울수록 더 강한 승인·감사·오류 처리·책임 소재가 필요하다.
- **불만 분류:** 일반·긴급·모호·안전하지 않음·에스컬레이션 필요 사례를 평가하고, 구조화된 범주·검토 점검·제한 주제·사람 검토를 가드레일로 둔다. 가시성 지표는 에스컬레이션 빈도·검토자 재승인·오류 패턴·저신뢰 사례, 감사 정보는 불만 내용·할당 범주·권고·검토자·후속 조치.
- **권고안 예시 결정:** 초안 전용이지만 고객 데이터와 민감 사례 유형을 다루고 추후 티켓 자동 업데이트 가능성이 있는 워크플로우 → "시범 운영 전 전문가 검증 필요". 데이터 사용 승인, 접근 범위, 수동 검토, 에스컬레이션, 로깅, 감사 가능성, 향후 쓰기 작업 통제 강화 여부를 검증한다.

- 강력한 거버넌스를 가장 잘 반영하는 문장은? → 거버넌스는 소유자·범위·검토 시점·근거·에스컬레이션 절차를 정의해 팀이 신뢰를 바탕으로 더 빠르게 움직이게 한다(파일럿 후 결정, 모든 자동화에 '아니오', 법적 기능일 뿐은 오답).

- 플랫폼-통제 영역 매칭 → ChatGPT 워크스페이스: 관리자 지원, 역할·그룹 액세스, 승인된 앱·플러그인·Workspace 에이전트, 작업 권한·검토 / API 앱: 인증, 데이터 흐름, 로깅, 저장·보존, Zero Data Retention의 엔드포인트·도구·기능 선택 시사점 / 에이전트·도구: 연결 신원, 최소 권한, 읽기/쓰기 경계, 승인·작업 제한 / Codex: 리포지토리 신뢰, 샌드박스·작업 공간 경계, 네트워크 접근, 승인 정책, 검토, 감사 가능성.
- 선택 실습(거버넌스 격차 찾기, 3~4분): 지원 응답 초안 워크플로우의 책임자·경계·검토/에스컬레이션 대상을 3개 요점으로 적는다.
- 선택 실습(사용 가능 vs 승인 데이터 구분, 3~4분): 가장 안전한 출처, 먼저 검증할 출처, 노출 위험을 정리한다.
- 선택 실습('도움'과 '행동'의 경계, 3~4분): 요약·초안·에스컬레이션 권장·티켓 상태 변경·이메일/크레딧 발송을 저위험 / 승인 필요 / 제한으로 나눈다.
- 선택 실습(첫 번째 통제 수단 선택, 4~5분): 불만 분류 워크플로우에 평가·가드레일·가시성 지표·감사 질문을 하나씩 고른다.
