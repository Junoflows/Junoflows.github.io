### 통합 최종 정리 — OpenAI 기술 실무자

#### 요약
기술 실무자는 모델이나 제품 이름부터 꺼내지 않고 **워크플로우에서 출발**한다. 인터페이스, 기능·아키텍처, 배포·운영이라는 세 결정을 분리하고(1강), 코드 이전에 구현 라이프사이클과 책임 소재를 짚는다(2강).

설계 단계에서는 작업 형태로 모델 클래스와 솔루션 패턴을 고르고(3강), 꼭 필요한 최소 역량만 조합해(4강) 재사용 가능한 패턴을 간결한 1차 청사진으로 옮긴다(5강).

모든 단계에 데이터, 권한, 조치 위험, 통제를 처음부터 넣어 거버넌스를 신뢰 수단으로 삼는다(6강). 결과물은 확정 설계가 아니라 **가정과 검증 필요 사항이 드러난 예비 권고**다.

#### 과정 전체 흐름
```
[1강] 워크플로우 → 3축 라우팅 + 4대 탐색 계층
   │
   ├─▶ [2강] 구현 라이프사이클 → 환경·책임 → 구현 준비 스냅샷
   ├─▶ [3강] 작업 형태 → 모델 클래스 → 솔루션 패턴 → 평가 근거
   ├─▶ [4강] 기능 역할 → 도구 경계 → 최소 실행 가능 역량 세트
   └─▶ [5강] 아키텍처 패턴 → 1차 청사진 → (전문가) 최종 설계
                │
[6강] 데이터·소유권 → 조치-위험 단계·승인 게이트 → 준비도 권고안
```

#### 강의별 핵심
- **1강 기술적 유창성:** 인터페이스, 기능·아키텍처, 배포·운영을 분리하고 4대 탐색 계층으로 증거를 모은다.
- **2강 기술 구현의 기초:** 구현은 루프형 라이프사이클이다. 맞춤형 API는 Responses API에서 시작하고 환경별 가정을 구분한다.
- **3강 모델 선정:** 작업 형태로 모델 클래스 가설을 세우고 대표 평가 사례로 검증하며, 실패 사례는 라우팅 근거로 쓴다.
- **4강 플랫폼 기능:** 기능 역할 7가지로 필요한 것만 고르고, 읽기 전용과 실행형 도구를 나눠 실행형에 통제를 더한다.
- **5강 아키텍처 패턴·청사진:** 재사용 패턴을 1차 청사진으로 옮기고, 최종 기술 설계는 전문가가 주도한다.
- **6강 보안·거버넌스·데이터:** 거버넌스는 더 빠르게 움직이게 하는 장치다. 조치-위험 단계에 맞춰 승인 게이트를 둔다.

#### 강의를 잇는 연결 고리

| 개념 | 라우팅(1강) | 구현(2강) | 모델·기능(3·4강) | 청사진(5강) | 거버넌스(6강) |
|---|---|---|---|---|---|
| 출발점 | 워크플로우 우선 | 무엇을 구현하나 | 작업 형태 | 패턴보다 워크플로 | 워크플로우 소유자 |
| 데이터·맥락 | 맥락·데이터 계층 | 환경별 데이터 흐름 | 검색, 승인된 컨텍스트 | 승인 소스와 소유자 | 데이터 범주와 소유권 |
| 도구·조치 | 런타임·도구 계층 | 프롬프트 주입 경계 | 읽기 전용 vs 실행형 | 런타임·도구 가정 | 조치-위험 단계 |
| 검증 | 평가 조기 고려 | 초기 평가 세트 | 대표 평가 사례 | 성공 지표와 연계 | 평가와 감사 가능성 |
| 사람의 역할 | 전문가 참여 신호 | 출시 후 책임자 | 사람 검토 기능 | 사람 검토 수정자 | 검증 역할과 승인자 |
| 산출물 | 기술 유창성 내비게이터 | 구현 준비 스냅샷 | 4단계 결정 구조 | 1차 솔루션 청사진 | 준비도 권고안 |

#### 실무 체크리스트
- ☐ 고객 요청을 워크플로우(누가, 어떤 업무, 어떤 결과)로 다시 말할 수 있는가
- ☐ 인터페이스, 기능·아키텍처, 배포·운영 결정을 섞지 않고 분리했는가
- ☐ 데이터 출처, 소유자, 민감도, 접근 권한을 확인했는가
- ☐ 모델 이름이 아니라 작업 형태와 의사결정 요인으로 모델 클래스 가설을 세웠는가
- ☐ 1차 버전에 꼭 필요한 최소 역량만 골랐고, 미룰 것을 구분했는가
- ☐ 읽기 전용과 실행형 도구의 경계를 나누고, 실행 전 사람 승인을 두었는가
- ☐ 대표, 극한, 실패, 모호 사례로 된 초기 평가 세트와 성공 기준이 있는가
- ☐ 출시 후 모니터링과 롤백 경로, 운영 책임자가 정해졌는가
- ☐ 가정과 에스컬레이션 대상을 드러내고, 확정 설계처럼 과장하지 않았는가

> **한 줄 요약:** 제품 이름이 아닌 워크플로우에서 출발해 세 결정을 분리하고, 네 계층으로 증거를 모아 과장 없이 예비 경로를 제안한다.

### 핵심 내용
#### 기술적 유창성이란
- 기술적 유창성은 고객 워크플로우를 신뢰할 수 있는 솔루션 경로와 잇고, 상충 관계와 검증 시점을 일찍 알아차리는 능력이다.
- 목표는 모든 제품의 전문가가 되는 것이 아니라 더 나은 질문, 신뢰할 수 있는 초기 경로, **과도한 주장 회피**다.
- 제품 이해도는 제품 이름과 기능을 아는 것이다. 실무적 기술 판단력은 적합성을 가르는 질문과 권고 전 검증할 것을 아는 것이다.

#### 제품이 아닌 워크플로우부터
- "운영팀용 AI 어시스턴트" 같은 포괄적 요청에 곧바로 기능이나 모델 이름으로 답하지 않는다.
- 먼저 워크플로우, 데이터, 사용자, 제약, 위험, 성공 기준을 파악한다.
- 같은 성과도 ChatGPT, Codex, API 애플리케이션의 조합으로 달성될 수 있다. 통합 솔루션은 각 축 결정의 결과이지 별개 경로가 아니다.
- 라우팅 실수는 워크플로우를 이해하기 전에 "ChatGPT 써라", "에이전트로 만들라"를 기본값으로 쓸 때 생긴다.
- 초기 적합성 신호는 출발점 단서일 뿐 최종 권고가 아니다.

#### 기본 기술적 사고 모델
- 핵심 질문은 "사용자가 AI와 직접 상호작용하나, 다른 시스템이 워크플로우의 일부로 AI를 쓰나?"이다.
- 많은 AI 기회는 직원용 채팅이 아니라 기존 제품이나 프로세스에 **AI를 내장**하는 것이다.
- 강력한 모델도 맥락이 틀리면 그럴듯하지만 오래된 답을 낸다(예: 최신 HR 정책이 없는 HR 어시스턴트).
- 목표는 더 많은 정보가 아니라 올바른 출처의 올바른 정보를 올바른 사용자에게 주는 것이다.
- **평가와 가드레일**은 첫 실패 후 붙이지 않고 초기에 정한다. 대표적이고 라벨링된 예제로 평가를 시작한다.

#### 경로 설정·검증·에스컬레이션
- 세부를 다 알기 전에 의견을 내는 건 정상이다. 위험한 것은 **증거보다 확신에 찬 어조**다.
- 초기 상담은 대부분 레벨 1(예비 해결 방안)이다. 유력한 경로와 이유, 아직 검증할 것을 함께 말한다.
- "확실히 올바른 해결책입니다" 대신 "합리적인 첫 단계지만 통합 요구와 승인 절차를 검증해야 합니다"라고 말한다.
- 상당한 불확실성이나 전문 검토가 필요한 요구가 생기면 적절한 전문가를 참여시킨다.
- 강한 초기 권고는 예상 인터페이스, 필요한 기능·아키텍처, 검증할 배포·운영 가정을 모두 담는다.

#### 기술 유창성 내비게이터
- 내비게이터는 대화 준비용 사고 도구다. 최종 권고안이나 아키텍처 문서, 구현 계획이 아니다.
- 도울 대화 유형 1~2개를 고르고, 4개 역량의 자신감을 표시해 낮은 것부터 강화한다.

### 기억할 개념·프레임워크

| 결정 축 | 올바른 질문 | 방향성 예시 |
|---|---|---|
| 사용자·제품 인터페이스 | 워크플로가 주로 어디서 운영되나? | ChatGPT Chat, ChatGPT Work, Codex, API 앱 |
| 기능·아키텍처 | 시스템이 무엇을 해야 하나? | 검색, 구조화된 출력, 코드 실행, 자동화 |
| 배포·운영 | 어디서 어떻게 실행·제어되나? | 신원, 권한, 승인, 로깅, 사람 검토 |

- **인터페이스 적합성 신호**
  - Chat: 대화형 탐색, 초안, 비평
  - Work: 결과와 승인 범위를 정의할 수 있는 위임 업무
  - Codex: 리포지토리, 테스트, 디버깅
  - API: 지능을 제품이나 시스템에 내장
- 에이전트와 자동화는 인터페이스가 아니라 **기능·아키텍처** 결정이고, 오픈 웨이트는 모델·배포 결정이다.
- 오픈 웨이트 모델은 데이터가 민감해서가 아니라 특정 배포 요구 때문에 고려한다.

| 탐색 계층 | 핵심 질문 |
|---|---|
| 사용자·워크플로우 | 누가 어떤 업무와 산출물을 다루나? |
| 맥락·데이터 | 무엇을 알고 검색·접근해야 하나? |
| 런타임·도구 | 어떤 시스템에서 어떤 작업이 허용되나? |
| 거버넌스·가시성 | 어떻게 모니터링하고 개선하나? |

- **권고 신뢰도:** 레벨 1 예비 해결 방안 → 레벨 2 검증된 아키텍처 → 레벨 3 배포 준비 구현 계획.
- **전문가 참여 신호:** 민감·규제 데이터, 기록 업데이트 같은 시스템 조치, 접근 제어와 감사, 복잡한 통합 등.

### 실무 적용 예시
- "운영팀용 AI 어시스턴트" 요청 → 워크플로우, 필요한 정보, 조치 여부, 승인 대상을 먼저 묻는다.
  - 탐색과 초안이면 Chat, 위임 업무면 Work, 운영 플랫폼 내장이면 API 앱이 타당하다.
- 지원 티켓이 생기면 백엔드가 응답 초안과 다음 조치를 만들고 담당자가 검토 후 발송 → 전형적인 **API 내장 패턴**이다.
- 고객 정보 검색, 여러 시스템 기록 업데이트, 후속 이메일 자동 발송 → 에이전트 워크플로우로 보되 권한과 감사는 전문가와 검증한다.

### 지식 점검 포인트
- 고객용 제품 안의 AI 생성 결과물 → **API 앱·프로세스**. 테스트와 PR 지원은 Codex, 승인된 출처 기반 위임 작성은 Work다.
- "티켓을 업데이트할 수 있나?"라는 질문 → **런타임·도구 계층**. "오류는 어떻게 모니터링?"은 거버넌스·가시성 계층이다.
- 공급업체 위험을 검토하고 조달 기록을 자동 업데이트 → **세 결정을 분리하고 접근, 권한, 감사 가능성을 검증**한다.
  - 즉시 Work를 고르거나, 민감 데이터라서 오픈 웨이트를 고르는 것은 오답이다.
- 워크플로 설명 없이 "AI 자동화"만 원함 → **워크플로우를 먼저 명확히 한 뒤 세 결정을 분리**한다.

  <h1 class="lesson-title">기술 구현의 기초</h1>

> **한 줄 요약:** 구현은 코드 이전에 시작되는 라이프사이클이다. 요청-응답 흐름, 환경과 책임, 평가와 안전 장치를 짚어 다음 단계를 고른다.

### 핵심 내용
#### 구현 파트너의 관점
- 구현은 단일 빌드 단계가 아니라 결정, 종속성, 테스트, 책임자가 얽힌 **라이프사이클**이다.
- 라이프사이클은 일직선이 아니다. 테스트 중 데이터 소스가 불완전하다고 드러나 이전 결정으로 돌아가는 일이 흔하다.
- **구현 준비 완료**는 모든 세부가 해결된 상태가 아니라, 미지 사항과 가정이 드러나고 다음 단계 범위가 정해진 상태다.
- 확인 질문은 "피할 수 있는 위험이나 재작업 없이 다음 단계를 진행할 만큼 아는가?"이다. 답이 '아니오'여도 기회는 유망할 수 있다.
- 구현 격차는 기회가 약하다는 뜻이 아니라 남은 확인 사항을 보여 줄 뿐이다. 데모 성공 뒤에 늦게 드러나기도 한다.

#### API와 Responses API
- 기본 패턴은 애플리케이션이 요청하고, AI가 응답하고, 애플리케이션이 다음 단계를 결정하는 흐름이다.
- 새 맞춤형 OpenAI API 프로젝트는 **Responses API부터 시작**한다. 그다음 입력, 도구, 상태, 출력 계약, 추적을 정의한다.
- 하류 시스템이 신뢰할 결과가 필요하면 JSON 스키마 기반 구조화된 출력을 쓴다.
- 핵심 질문은 "AI에 무엇이 전송되고, 무엇이 반환되며, 그다음 무슨 일이 일어나는가?"이다. 답하지 못하면 워크플로우 정의가 더 필요하다.
- **인증**은 연결 권한의 입증이고, 접근 제어는 연결 후 할 수 있는 일을 정한다.
- API 키 같은 비밀 정보는 프롬프트, 공유 문서, 데모에 붙여 넣지 않는다.
- **프롬프트 주입 경계:** 검색된 콘텐츠와 도구 결과는 데이터로 다루고, 지시나 권한을 바꾸는 명령으로 보지 않는다.
- 외부 쓰기나 파괴적 작업 전에는 사람 승인을 받는다.

#### 환경, 접근 권한, 소유권
- 핵심 질문은 "어디에서 실행되고, 무엇에 접근하며, 출시 후 누가 소유하는가?"이다.
- 개발에서 잘 되던 것도 프로덕션 전에 추가 테스트, 보안 통제, 모니터링, 운영 책임 배정이 필요하다.
- 붙여넣기 기반 프로토타입이 업무 시스템에 다시 기록하게 되면 접근, 권한, 로깅의 중요도가 크게 오른다.
- **책임자 없는 솔루션**은 지원되지 않는 시제품으로 전락한다.
- 릴리스는 제한된 파일럿으로 작게 시작한다. 롤백 경로에는 기능 비활성화, 수동 프로세스 복귀, 전 출력 사람 검토 전환 등이 있다.

#### 평가와 안전 장치
- 데모는 한 예시의 성공을 보여 줄 뿐이다. **평가**는 일반 입력, 경계 사례, 고위험 상황 전반의 안정성을 확인한다.
- 평가는 출시 전 최종 점검만이 아니라, 프롬프트나 모델, 도구를 바꿀 때마다 회귀를 잡는 도구다.
- 초기 평가 세트는 완벽한 벤치마크가 아니라 초기 안전망이다.
- **안전 장치**는 마지막에 붙이는 기능이 아니라 워크플로우 설계의 일부다. 구체적 위험에 맞춘다.
  - 민감 데이터: 접근 제어와 검토 규칙
  - 타 시스템 업데이트: 승인과 로깅
  - 의사결정 활용: 품질 검사, 출처 참조, 에스컬레이션
- 추적은 모델 출력과 도구 호출의 순서를 재구성하고, 모니터링은 시간에 따른 패턴을 본다. 가시성은 설계 단계에서 고려한다.

### 기억할 개념·프레임워크

| 고려 사항 | 개발 | 테스트 | 스테이징 | 프로덕션 |
|---|---|---|---|---|
| 데이터 소스 | 안전한 샘플 | 테스트 데이터 | 운영과 유사한 데이터 | 실시간 비즈니스 데이터 |
| 접근 권한 | 팀 제한 접근 | 역할 기반 | 승인된 접근 | 통제된 접근 |
| 소유자 | 빌더 주도 | 팀 간 공동 | 지정된 책임자 | 책임 있는 소유자 |
| 모니터링 | 기본 점검 | 테스트 로깅 | 경고와 검토 | 실시간 모니터링 |
| 롤백 질문 | 다시 시작 가능? | 이전 버전 복원? | 릴리스 롤백? | 정의된 롤백 계획? |

- **흔한 구현 격차:** 모호한 범위, 신뢰할 데이터 소스 부재, 품질 기준치 부재, 운영 책임자 불분명, 데모 결과 과신 등.
- **초기 평가 세트:** 전형적 성공, 극한, 실패, 모호한 입력, 안전·정책 사례. 해당하면 도구와 프롬프트 주입 사례도 넣는다.
- **안전 장치 10범주:** 입력 필터링, 출력 검사, 구조화된 출력, 도구 범위 지정, 사람 승인, 에스컬레이션 규칙 등.

| 4. 무엇을 테스트·검토·에스컬레이션하나? | 평가 사례, 안전 장치, 모니터링 신호, 롤백 기준 |

### 실무 적용 예시
- "티켓 요약 AI가 필요하다"에 "만들 수 있다"로 바로 답함 → 약한 대응이다. 대상 티켓, 독자, 재기록 여부, 정확도 기준, 출시 후 담당자를 묻는다.
- 정책 답변 도우미의 요청-응답 추적 → 승인된 정책 문서와 출처 인용 지시를 보내고, 답변과 출처를 받으며, 민감 주제는 담당 팀으로 넘긴다.
- 사내용 재무 정책 어시스턴트 → 소규모 테스트 그룹, 승인된 문서, 읽기 전용 접근으로 시작한다.
  - 출처에 없거나 문서가 상충하면 답을 지어내지 말고 이관한다.

### 지식 점검 포인트
- 경영진 지원으로 다음 달 출시를 원하지만 사용자와 데이터, 검토 절차가 불명 → **사용자, 데이터, 검토 절차, 책임 소재를 먼저 명확히** 한다.
  - 비즈니스 가치와 실행 준비도는 별개다.
- 다음 차례에 필요한 이전 응답 정보 → **상태**. JSON 스키마의 담당자 필드는 출력 계약, 도구 호출과 승인 기록은 추적이다.
- 샘플 데이터 프로토타입을 전 직원 프로덕션으로 전환 → **운영 데이터, 접근 제어, 모니터링, 운영 책임자, 롤백 경로**를 먼저 정한다.
- 도구가 기록을 잘못 업데이트하는 위험의 첫 대응 → **승인 절차와 도구 사용 테스트**.
- 프로토타입은 작동하지만 출시 후 오류 모니터링 담당자가 없음 → **스냅샷을 업데이트해 책임 소재와 모니터링을 명시**한다.

  <div class="eyebrow">레슨 03 · Model Selection and Solution Patterns</div>
  <h1 class="lesson-title">모델 선정 및 솔루션 패턴</h1>
</div>

> **한 줄 요약:** 모델 이름이 아닌 작업 형태로 시작해 모델 클래스와 솔루션 패턴을 가설로 세우고, 평가 근거로 다음 조치를 정한다.

### 핵심 내용
#### 작업 형태부터 시작하기
- "계약서 검토", "지원 트리아지" 같은 워크플로 라벨은 출발점일 뿐, 그 안에 여러 작업이 섞여 있다.
- **작업 형태**는 시스템이 할 작업, 필요한 정보, 결과물, 그 결과물을 쓰는 대상, 위험과 검토 수준을 말한다.
- 약한 진술은 "지원 티켓 분류가 필요하다"이다. 강한 진술은 분류, 검색, 에스컬레이션 기준까지 드러낸다.
  - 예: "긴급도를 분류하고, 필요하면 승인된 정책을 검색하며, 모호하거나 민감한 사례는 사유와 함께 담당자에게 보낸다."
- 출력이 정보만 주면 자연어로 충분하다. 워크플로를 주도하거나 시스템을 업데이트하면 더 많은 구조화와 검증이 필요하다.
- 고위험 워크플로에는 "더 뛰어난 모델"이 아니라 **더 강한 검증과 명확한 사람 검토**가 필요하다.

#### 모델 클래스와 의사결정 요인
- 모델 클래스는 최종 답이 아니라 **출발 가설**이다. 요구사항을 클래스 용어로 정의하고 후보를 테스트한다.
- 과정은 GPT-6 Astra를 예로 들지만 즉시 추천하라는 뜻은 아니다. 기능, 가격, 접근성은 따로 확인한다.
- 단순 요약이나 안정적 분류는 범용 또는 효율적 모델로 충분할 수 있다. 정책 해석과 다단계 계획에는 심층 추론이 중요하다.
- 비용은 명목 토큰 가격이 아니라 **성공 작업당 총비용**으로 비교한다. 재시도, 수작업 수정, 하류 재작업까지 포함한다.
- 최신·비공개 정보가 필요하면 모델 선택만으로 풀리지 않는다. 컨텍스트 부족을 "더 나은 모델"로 풀려는 실수를 피한다.
- 도구 사용은 가치와 함께 책임도 키운다. 권한 범위, 승인 규칙, 오류 처리가 권장안에 들어가야 한다.

#### 솔루션 경로와 패턴
- 맞춤형 UX, 제품 통합, 백엔드 자동화가 필요하면 API가 적절하다. 이때 모델은 더 큰 시스템의 일부다.
- 새 맞춤형 API 프로젝트는 **Responses API**를 기본 출발점으로 쓴다.
- "에이전트", "오픈 모델", "하이브리드"는 동등한 인터페이스가 아니라 기능과 배포에 속하는 후속 결정이다.
- 솔루션 패턴은 최종 아키텍처가 아니라 반복 가능한 방식이다. 이름을 붙이는 이유는 설계 전에 함의를 드러내기 위해서다.
- 패턴 조합은 기능 나열이 아니라 워크플로 순서로 설명하고, 단계마다 실패 가능성과 검토 지점을 묻는다.

#### 평가 증거로 권고 검증
- 데모와 한 번의 인상적 답변은 근거가 아니다. 경량 평가로 초기 권고를 뒷받침하거나 수정한다.
- **성공 기준은 2~3개**만 고른다. 예를 들어 조달 접수는 분류 정확도, 형식 준수, 에스컬레이션을 본다.
- 소규모 시드 세트에 일반 사례와 어려운 사례를 모두 넣는다. 대표성 있는 소규모 세트가 모호한 대규모 세트보다 낫다.
- 공정 비교를 위해 같은 사례, 프롬프트, 도구 권한을 쓰고 모델 ID와 설정 차이를 기록한다.
- 결과 해석 기준은 미리 정한다. 쉬운 예제만 잘하고 모호한 사례에서 실패하면 권고를 약화하는 신호다.
- 초기 권고는 "최종 권고가 아니라 검증할 초기 모델 클래스와 패턴"이라고 경계를 밝힌다. 가격 확약처럼 들리게 하지 않는다.

### 기억할 개념·프레임워크

| 범주 | 유용한 경우 |
|---|---|
| 추론 중심 모델 | 다단계 분석, 모호성 처리, 정책 해석 |
| 범용 모델 | 문서 작성, 요약, 분류 등 광범위한 언어 작업 |
| 효율적인 모델 | 속도와 비용이 중요한 안정적 대량 작업 |
| 멀티모달 모델 | 이미지, 문서, 오디오 등 혼합 입출력 |
| 오디오·실시간 모델 | 음성, 전사, 저지연 대화형 경험 |
| 임베딩 모델 | 의미 검색, 유사도 비교, 클러스터링 |

- 콘텐츠 검토, 도구 사용, 검색과 순위 지정은 모델이 아니라 **기능**이다. 오픈 모델은 모델·배포 옵션이다.
- **의사결정 요인:** 추론 깊이, 지연 시간, 비용, 규모, 맥락, 구조화 출력, 도구 사용, 위험, 평가 요구.

| 결정 영역 | 지침 질문 |
|---|---|
| 작업 형태 및 산출물 요구사항 | AI에게 어떤 작업을 요청하나? |
| 모델 클래스 및 의사결정 요인 | 어떤 클래스가 타당한 가설이고, 어떤 상충이 중요한가? |
| 솔루션 경로 및 패턴 | 어디서 운영되고, 무엇을 하며, 어떻게 제어되나? |
| 평가 근거 및 에스컬레이션 | 고객 공개 전에 어떤 증거가 필요한가? |

- **다음 조치 3가지:** 워크플로가 명확하면 경로 제시, 증거가 빠졌으면 검증, 전문가가 필요하면 상급 보고.

### 실무 적용 예시
- "계약 검토용 모델" 요청 → 추출, 조항 비교, 협상 메모 중 무엇인지 먼저 확인한다. 추출은 구조화 출력, 조항 비교는 승인 출처 검색으로 이어진다.
- 짧은 입력을 단순 레이블로 대량 분류 → **효율적 모델**이 출발점이다. 긴급하거나 민감한 사례를 놓치면 클래스나 라우팅을 바꾼다.
- 조달 접수 개선에 시스템 연결과 예외 검토가 필요 → 주 인터페이스는 **API 애플리케이션**이고, 분류, 추출, 검색, 사람 검토를 조합한다.
- 갱신 청구서 조정 → 재무팀 검토용 초안만 작성한다. 기록이 충돌하거나 증거가 없으면 정직한 중단과 검토 이관이 기대 결과다.

### 지식 점검 포인트
- "클레임 검토에 어떤 모델?"에 워크플로 중심을 유지하는 질문 → **"청구 심사에서는 무엇을 수행해야 합니까?"**
- 모호한 정책 해석 → **추론 중심 모델**. 문서 이미지 이해는 멀티모달, 대량 단순 분류는 효율적 모델이다.
- 분류, 필드 추출, 약관 조회, 예외 검토가 필요한 보험 청구 앱 → **분류, 추출, 검색, 사람 검토를 갖춘 API 애플리케이션**.
- 쉬운 예제는 잘하지만 모호하고 고위험인 예외를 놓침 → **실패 사례를 라우팅 근거로 삼아** 증거 수집과 대안 테스트, 상급 보고를 한다.

<div class="lesson-head">
  <div class="lesson-num">04</div>
  <div class="eyebrow">레슨 04 · Platform Capabilities and Developer Tools</div>
  <h1 class="lesson-title">플랫폼 기능 및 개발자 도구</h1>
</div>

> **한 줄 요약:** 기능 목록이 아니라 워크플로우 요구에서 출발해 기능별 역할과 통제를 따지고, 1차 버전의 최소 실행 가능 역량 세트를 고른다.

### 핵심 내용
#### 기능 목록이 아니라 역량에 초점
- 플랫폼 기능은 업무의 한 부분을 수행하는 빌딩 블록이며, 명확한 워크플로우 요구와 연결될 때 유용하다.
- "검색이 필요해요", "에이전트가 필요해요" 같은 기능 이름은 요구를 설명하지 못한다. 기능 우선 제안은 **과잉 구축**을 낳는다.
- 기능 추가 전 질문: 어떤 역할을 하나? 어떤 종속성과 통제를 도입하나? 1차 버전에서 빼면 어떻게 되나?
- **최소 실행 가능 기능 세트**는 가장 작은 데모가 아니라, 요구 충족과 위험 통제를 갖춘 가장 작은 책임 있는 조합이다.

#### 상호작용과 컨텍스트
- 새 사용자 지정 API 프로젝트는 **Responses API**가 기본 시작점이다. 주변 애플리케이션이 호출 방식과 결과 처리를 제어한다.
- 모델이 도구 실행을 요청했다고 실제 실행된 것은 아니다. 실행, 추적, 결과 확인은 애플리케이션 책임이다.
- 모든 워크플로우에 사용자 정의 API가 필요하지는 않다. ChatGPT 환경으로 충분하면 그쪽이 더 나은 출발점이다.
- 후속 시스템에 신뢰할 계약이 필요하면 JSON 스키마 기반 구조화된 출력을 쓴다. 형식이 맞아도 비즈니스 의미는 따로 확인한다.
- 핵심 결정은 "검색을 추가할까?"가 아니라 "어떤 승인된 컨텍스트가 필요하고, 준비됐나?"이다.
- **검색 준비도**는 콘텐츠 준비와 접근 준비를 합친 것이다. 출처 소유자, 최신성, 사용자별 권한을 확인한다.

#### 도구, MCP, 경계
- "답을 돕는" 단계에서 "다른 시스템에 영향을 주는" 단계로 넘어가면 권한, 승인, 로깅 요구가 강해진다.
- 직접 도구 호출은 모델이 도구 선택과 다음 단계를 판단할 때 쓴다. 프로그래밍 방식 호출은 예측 가능한 대량 처리에만 쓴다.
- **MCP 방식 연결**은 여러 도구와 재사용 연결, 도구 접근 거버넌스가 필요할 때 검토한다. CRM 필드 하나 확인은 단순 호출로 충분하다.
- 애플리케이션은 완전하고 검증된 호출만 보내고, 부분 스트리밍된 인수는 실행하지 않는다.
- 조회 실패는 빈 레코드가 아니며, 승인 누락은 진행 허가가 아니다.

#### 필요할 때만 고르는 고급 기능
- 상호작용 형태는 워크플로우를 지원하는 가장 단순한 것을 고른다. 비동기 텍스트로 충분하면 검증과 운영이 쉽다.
- **Agents SDK**는 맞춤 앱에 관리형 오케스트레이션, 인계, 추적이 필요할 때 쓴다. 단일 호출이면 더 단순한 패턴이 낫다.
- 평가와 가시성은 기능을 고를 때 함께 고려한다. 조회 도구 장애나 중간 중단 같은 실패 경로도 테스트한다.
- 모니터링은 테스트와 사람 검토를 대체하지 못한다. 중지해도 이미 완료된 작업은 되돌려지지 않는다.
- **Codex**는 고객 요구가 소프트웨어 전달 과정 안에 있을 때 관련된다. 계정 브리핑 도구 자체에는 불필요하다.
- 결과는 "최종 설계가 아니라 검증해야 할 1차 버전 기능 세트"라고 경계를 밝힌다.

### 기억할 개념·프레임워크

| 기능 역할 | 계정 브리프 예 |
|---|---|
| 상호작용 | 내부 앱에서 브리프 요청 |
| 컨텍스트 | 승인된 계정 메모, 통화 요약, 정책 문서 |
| 조치 | CRM 상태 확인, 승인용 업데이트 준비 |
| 오케스트레이션 | 컨텍스트 수집 → 누락 확인 → 작성 → 검토 요청 |
| 평가 | 완전성, 출처 근거, 형식 |
| 개발자 워크플로우 | Codex로 구현, 테스트 추가, 코드 리뷰 |
| 거버넌스·가시성 | 권한, 승인 단계, 로그, 에스컬레이션 경로 |

| 도구 구분 | 하는 일 | 필요한 통제 |
|---|---|---|
| 읽기 전용 | 조회, 검색, 계산 | 접근 권한, 소스 검증, 로깅 |
| 실행형 | 생성, 업데이트, 전송, 트리거 | 위에 더해 승인 단계, 작업 제한, 명확한 책임 |

- 차이는 시스템이 아니라 **조회만 하나, 변경할 수 있나**에 있다. 경계가 명확해진 뒤에만 조회에서 실행으로 넘어간다.
- **4단계 역량 결정 구조:** 워크플로우 요구와 필수 역할 → 최소 실행 가능 역량 세트 → 종속성·통제·상충 → 검증과 에스컬레이션.

### 실무 적용 예시
- 영업팀 계정 개요 어시스턴트 → 승인 소스 검색, 구조화된 출력, 평가, 고객 사용 전 사람 검토로 구성한다. 실시간이나 MCP는 불필요하다.
- 조달 공급업체 상태 확인 → 읽기 전용 요약은 기본 통제로 충분하다. 티켓 생성이나 기록 업데이트까지 하면 승인 게이트와 로깅이 더 필요하다.
- 여러 시스템에서 컨텍스트를 모으고 CRM 업데이트 전 승인을 요청하는 흐름 → 이때 비로소 **에이전트 툴링**이 타당하다.

### 지식 점검 포인트
- 계정 브리핑 도구 1차 버전의 기능 판단 → **워크플로 역할부터 시작**한다. 모든 기능 선포함이나 CRM write-back부터는 오답이다.
- 일관 형식과 출처 참조가 필요하고 사용자별 권한이 다름 → **구조화된 출력, 승인된 검색, 접근 권한 검증, 검토와 평가**.
- CRM 기회 상태 조회와 예측 필드 업데이트 → **상태 조회는 읽기 전용, write-back 전에는 승인**으로 경계를 나눈다.
- 음성이나 자율 업데이트가 불필요한 1차 도구 → **승인된 컨텍스트, 구조화된 출력, 검토, 평가, 기본 가시성부터** 시작한다.
  - CRM 조회는 별도로 검증한다.

  <div class="eyebrow">레슨 05 · Architecture Patterns & Solution Blueprints</div>
  <h1 class="lesson-title">아키텍처 패턴 및 솔루션 청사진</h1>
</div>

> **한 줄 요약:** 워크플로우에 맞는 패턴을 먼저 고르고, 가정과 검증 사항이 드러나는 간결한 1차 청사진으로 옮기되 최종 설계로 과장하지 않는다.

### 핵심 내용
#### 설계도보다 패턴 먼저
- 도구나 모델로 바로 뛰어들지 말고 "어떤 솔루션 형태인가?"를 먼저 묻는다.
- 패턴 계열은 엄격한 범주가 아니라 자주 겹친다. 암기보다 워크플로우를 가장 잘 설명하는 패턴을 고르는 것이 중요하다.
- 좋은 1차 청사진은 "모호해서 쓸모없는" 상태와 "검증 전에 지나치게 세부적인" 상태를 모두 피한다.

#### RAG와 에이전트 오케스트레이션
- 혼동하기 쉬운 두 패턴은 **검증된 지식 활용(RAG)**과 다단계 작업 오케스트레이션이다.
- RAG는 내부 문서나 정책에 의존하고, 답변이 출처에 근거해야 하며, 근거 없는 답을 피해야 할 때 맞다.
- 검색은 후보 문단을 만들고, 재순위 지정은 가장 유용한 승인 맥락이 먼저 오도록 정렬한다.
- RAG도 판단을 없애지 않는다. 출처가 답을 뒷받침하지 못하면 명확화 요청이나 에스컬레이션 같은 안전한 대응을 정한다.
- 에이전트 오케스트레이션은 다단계 목표, 시스템 간 도구 사용, 사람 승인, 완료 기준이 있을 때 맞다.
- 단일 답변이나 요약, 분류면 더 단순한 패턴이 낫다. 에이전트 용어는 불필요한 복잡성을 더할 수 있다.

#### 검토, 멀티모달, 통합
- "human in the loop"만으론 부족하다. 검토 대상, 검토자, 트리거, 기준, 불합격 시 처리를 명시한다.
  - 좋은 예: "환불이나 법적 문구가 담긴 권고는 발송 전 지원 관리자가 확인하고, 근거가 부족하면 팀장에게 상신한다."
- 검토는 병목 없이 위험을 실질적으로 줄이는 곳에 둔다. 검토자 수정과 반복 실패는 개선 루프로 이어진다.
- 멀티모달과 음성은 모달리티가 가치나 실현 가능성을 바꿀 때만 쓴다. 텍스트로 같은 결과가 나오면 불필요하다.
- 엔터프라이즈 통합은 "고객 시스템에 연결한다"로 끝내지 않는다. 관련 시스템, 데이터 이동, 권한, 승인 단계를 드러낸다.
- 하이브리드에서 핵심이 전 과정 조율이면 주 패턴은 에이전트 오케스트레이션이고, 검색과 추출, 검토가 이를 지원한다.

#### 청사진 구축과 압력 테스트
- **청사진 4개 섹션:** ① 워크플로와 패턴 ② 컨텍스트·데이터·도구 가정 ③ 검토, 평가, 성공 지표 ④ 위험과 다음 기술 단계.
- 간결하게 유지한다. 전체 아키텍처 다이어그램이나 보안 설계 문서가 되면 안 된다.
  - 예: "1차 버전은 승인된 운영 기록 사용, 시스템 write-back 없음, 소스 소유권 검증 필요."
- 미해결 질문이 남아도 논의할 준비는 된 것일 수 있다. 그것을 드러내는 것이 1차 청사진의 핵심이다.

### 기억할 개념·프레임워크

| 수준 | 핵심 질문 | 내용 |
|---|---|---|
| 아키텍처 패턴 | 이 워크플로에 맞는 일반적 해법 형태는? | 재사용 가능한 틀 |
| 1차 청사진 | 여기에 어떻게 적용되며 무엇을 검증하나? | 가정, 위험, 검증 요구 |
| 최종 기술 설계 | 어떻게 구현, 운영, 보안, 확장하나? | 전문가 주도 |

- **패턴 계열 9가지:** 검색 기반 생성, 구조화된 추출, 에이전트 조정, 재순위 지정, 인간 검토, 멀티모달, 음성·실시간, 엔터프라이즈 통합, 하이브리드.

| 워크플로 신호 | 청사진 수정자 |
|---|---|
| 출력이 고객에게 전달 | 사람 검토 |
| 스캔 양식 입력 | 멀티모달 |
| 시스템 레코드 업데이트 | 기업 시스템 연동 |
| 검색, 도구, 승인 결합 | 하이브리드 |
| 실시간 음성 지원 | 음성·실시간 상호작용 |

- 신중한 표현: "타당한 시작 경로로 보이지만, 권장 사항으로 보기 전에 소스, 접근, 도구, 검토 가정을 검증해야 한다."

### 실무 적용 예시
- HR 정책 어시스턴트 → 주 패턴은 RAG와 정책 문구 재순위 지정이다. 티켓 생성은 권한과 승인이 검증될 때까지 1차 버전에서 뺀다.
- 승인 기록으로 월별 예외 보고서 초안을 쓰고 관리자가 검토 → **RAG와 인간 검토**다. AI가 초안을 쓴다고 에이전트형은 아니다.
- 경비 정책 어시스턴트의 답변형 A와 시스템 업데이트형 B 비교 → 1차 버전은 단순한 A를 택하고, 조율된 조치가 실제로 필요할 때 바꾼다.

### 지식 점검 포인트
- "세부 인증, 보존, 로깅, 배포 설계" → **최종 기술 설계**. "검색 기반 생성과 인간 검토"는 아키텍처 패턴이다.
- 승인된 정책 출처, 인용된 답변, 정책 누락 시 이관이 필요 → **검색 기반 생성(RAG)**.
- 검색, 도구 사용, 승인이 결합된 워크플로 → **하이브리드 패턴** 수정자를 쓴다.
- 1차 논의에 가장 효과적인 청사진 노트 → **승인된 인사 정책, 출처 인용, 민감 사안 상급자 보고, 접근 권한 검증**을 담은 노트.
  - 최종 인프라나 인증 설계까지 넣은 노트는 지나치게 세부적이다.

  <h1 class="lesson-title">보안, 거버넌스 및 데이터</h1>
</div>

> **한 줄 요약:** 거버넌스를 신뢰 수단으로 보고, 데이터와 권한, 조치 위험, 통제를 점검해 알려진 것과 검증할 것을 담은 준비도 권고안을 쓴다.

### 핵심 내용
#### 거버넌스는 신뢰 구축 수단
- 거버넌스는 AI 업무가 통제, 검토, 모니터링, 개선되는 방식이다. 소유권, 권한, 승인 규칙, 로그 등을 포함한다.
- 거버넌스는 관료주의가 아니다. 책임자와 경계가 미리 정해지면 모호성 해소 비용이 줄어 **오히려 빨라진다**.
- 이 과정의 역할은 통제를 직접 구성하는 것이 아니라, 언제 중요한지 알아보고 전문가 검증 시점을 파악하는 것이다.
- 솔루션 유형마다 통제는 달라도 습관은 같다. AI가 무엇에 접근하고, 누가 검토하며, 누가 개선을 책임지는지 묻는다.
- Codex는 모든 편집에 승인이 필요하다고 가정하지 않는다. 활성 샌드박스와 정책이 허용 경계를 정한다.

#### 데이터 민감도, 접근, 소유권, 이동
- **사용 가능한 데이터가 곧 승인된 데이터는 아니다.** 접근할 수 있는 것과 고객이 사용을 승인한 것을 구분한다.
- 권고안에 "데이터 사용 가능"이라고만 쓰지 말고 유형, 민감도, 출처, 소유자, 접근 경계를 적는다.
- 접근 경계를 지키지 않으면 볼 권한이 없는 사용자에게 정보가 노출될 수 있다.
- 데이터 흐름은 유입부터 로그 보관까지 끝까지 매핑한다. 보존 설정 하나가 모든 엔드포인트와 로그를 포괄한다고 가정하지 않는다.
- API 워크플로우는 Zero Data Retention 요구가 쓸 수 있는 엔드포인트와 도구를 바꾸는지 확인한다.

#### 권한, 도구 위험, 승인 범위
- 권한과 역할은 누가 조회, 수정, 승인, 실행할 수 있는지 정해 데이터 경계를 운영 규칙으로 바꾼다.
- **조치-위험 단계**는 "AI가 도울 수 있다"에서 "AI가 행동할 수 있다"로 너무 빨리 넘어가는 것을 막는다.
- 승인 설정은 도구 사용 범위를 제한할 뿐, 연결 시스템의 권한을 대체하거나 반환 콘텐츠의 안전을 보장하지 않는다.
- 외부나 검색 콘텐츠에는 숨은 명령이 있을 수 있으므로 신뢰하지 않는다.
- 승인 게이트는 "사람의 개입"처럼 막연히 쓰지 않는다. 검토자, 트리거, 기준, 승인이나 거부 후 조치를 적는다.

#### 통제 수단과 준비도 권고안
- 평가는 동작을 테스트하고, 가드레일은 경계를 정하며, 가시성은 실제 사용을 보여 주고, 감사 가능성은 사후 재구성을 돕는다.
- 구조화된 출력은 모호성을 줄이지만 **정확성을 보장하지 않는다**. 여전히 평가가 필요하다.
- 개선 루프에는 담당자를 명시한다. 책임 소재가 없으면 문제를 찾아도 고칠 수 없다.
- 법률, 개인정보, 데이터 소재지, 보안에 대해 근거 없는 주장을 하지 않는다. 검증 필요성을 아는 것과 답을 주는 것은 다르다.
- 검증 함정이 있다고 작업이 자동으로 멈추지는 않는다. 불확실성을 확신으로 포장하지 말라는 신호다.

### 기억할 개념·프레임워크

| 조치-위험 단계 | 의미 |
|---|---|
| 읽기 전용 | 정보 검색, 요약 |
| 초안 | 사람이 검토할 콘텐츠 생성 |
| 권장 | 직접 조치 없이 다음 단계 제안 |
| 승인 후 실행 | 사람 승인 후에만 조치 수행 |
| 제한 | 자동화 금지 또는 전문가 검증 필요 |

| 통제 | 역할 |
|---|---|
| 평가 | 워크플로우가 예상대로 작동하는지 테스트 |
| 가드레일 | 규칙과 위험에 따라 동작을 안내하고 제한 |
| 모더레이션 | 안전하지 않거나 정책상 민감한 콘텐츠 식별 |
| 구조화된 출력 | 예측 가능한 필드 생성 (정확성 보장 아님) |
| 가시성 | 품질, 오류율, 에스컬레이션 등 모니터링 |
| 감사 가능성 | 요청, 도구 호출, 승인자, 조치를 재구성 |

- **검증 역할:** 워크플로우 소유자, 데이터 담당자, 보안 책임자, 개인정보·법무 검토자, 구현 책임자 등.
- **준비도 권고안 4섹션:** ① 데이터와 접근 ② 권한, 도구 위험, 승인 ③ 평가, 가드레일, 가시성 ④ 검증 필요 사항과 다음 단계.

### 실무 적용 예시
- 고객 대응 초안 어시스턴트 → 단순 초안이라도 고객에게 영향을 준다. 발송 전 검토자와 에스컬레이션 주제(환불, 해지, 법적 민원)를 정한다.
- 지원 플랫폼에 문서, 사례 메모, 내부 코멘트가 섞여 있음 → 승인 여부를 단독 판단하지 않고 출처별 민감도와 소유자, 노출 위험을 적는다.
- 공급업체 위험 정보를 요약하다 결국 시스템까지 업데이트하려 함 → 읽기 전용, 초안, 쓰기 작업을 구분한다. 실제 조치에 가까울수록 통제를 강화한다.
- 초안 전용이지만 고객 데이터를 다루고 향후 자동 업데이트 가능성이 있음 → **시범 운영 전 전문가 검증 필요**로 권고한다.

### 지식 점검 포인트
- 강력한 거버넌스를 가장 잘 반영하는 문장 → **소유자, 범위, 검토 시점, 에스컬레이션을 정해 신뢰를 바탕으로 더 빠르게 움직이게 한다**.
- "데이터가 이용 가능하니 AI에 써도 된다"는 팀 → **먼저 소유권, 사용 승인 여부, 접근 권한을 확인**한다.
- 가장 강력한 승인과 감사 가능성이 필요한 동작 → **고객 기록 자동 업데이트와 고객 메시지 발송**.
- 출시 후 에스컬레이션, 재승인, 오류 패턴 추적 → **가시성**. 사후 재구성은 감사 가능성, 승인 출처 근거 확인은 평가다.
