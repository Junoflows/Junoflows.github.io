### 통합 최종 정리 — API 배포 실무자

#### 요약
API 배포 실무자는 "데모가 된다"와 "배포할 수 있다" 사이의 간격을 증거로 메우는 과정이다. 문서화된 사실과 자리 표시자 인증으로 API를 호출하고, 최소 로컬 API의 성공·실패 동작을 증거로 남기는 데서 출발한다(1강).

설계 단계에서는 워크플로에 맞는 가장 단순한 아키텍처와 인터페이스를 골라 계약으로 옮긴다(2·3강). 모델과 기능은 기준을 충족하는 가장 덜 복잡한 옵션을 고르고, 데이터 보호와 검색 필요성을 따진다(4~6강).

검증과 운영 단계에서는 평가·가드레일·사람 검토로 릴리스 게이트를 만들고, 관측 가능성과 지원 책임을 담은 준비 체크리스트를 쓴다(7·8강). 특화 패턴은 워크플로가 요구할 때만 고르고(9·10강), 마지막으로 Northstar Retail Group 사례에서 가장 안전한 다음 단계를 권고한다(11강).

#### 과정 전체 흐름
```
[1강] 안전한 API 호출 → 최소 로컬 API → 증거 팩
   │
   ├─▶ [2강] 문제·범위·제약 → 최소 아키텍처 → 개요서
   ├─▶ [3강] 인터페이스 선택 → 요청·응답·오류 계약
   ├─▶ [4강] 작업 요구 → 후보 비교 → 선정 근거
   ├─▶ [5강] 데이터 흐름 → 인증·권한 → 보안 검토
   ├─▶ [6강] 검색 필요 여부 → 출처 준비 → 검색 계획
   ├─▶ [7강] 평가 기준 → 가드레일·사람 검토 → 릴리스 게이트
   ├─▶ [8강] 관측 신호 → 오류 대응·지원 → 준비 체크리스트
   ├─▶ [9강] 사용자 상황 → 모달리티 선택 → 경험 청사진
   ├─▶ [10강] 표준 대안 → 적합성 근거 → 적합성 평가
   └─▶ [11강] Northstar 사례 → 격차·차단 요인 → 배포 권고
```

#### 강의별 핵심
- **1강 API 배포 기초:** 문서화된 사실과 자리 표시자 인증으로 호출하고, 최소 API의 성공·실패를 증거 팩에 담는다.
- **2강 아키텍처:** 고객 문제와 워크플로, 경계에서 출발해 워크플로에 맞는 최소 아키텍처 패턴을 고른다.
- **3강 계약·인터페이스:** Responses API, Chat Completions, Conversations 중 골라 요청·응답·오류 계약으로 옮긴다.
- **4강 모델·기능 선택:** 날짜가 명시된 후보를 같은 사례로 비교해 기준을 충족하는 가장 덜 복잡한 옵션을 고른다.
- **5강 보안·데이터·접근 제어:** 데이터 최소화를 적용하고 인증과 권한 부여를 구분하며, 시크릿은 하드코딩하지 않는다.
- **6강 컨텍스트·검색:** 검색은 기본값이 아니라 필요할 때만 쓰고, 누락·상충·구식 출처를 테스트한다.
- **7강 평가·가드레일:** 데모 성공을 증거로 보지 않고, 평가·가드레일·사람 검토로 릴리스 게이트를 만든다.
- **8강 DevOps·관측 가능성:** 신호마다 담당자를 붙이고, 장애 대응과 롤백, 지원 책임으로 배포 조건을 정한다.
- **9강 실시간·음성·멀티모달:** 사용자 상황에서 출발해 워크플로를 안전하게 충족하는 가장 단순한 모달리티를 고른다.
- **10강 특화 API 패턴:** Deep Research·이미지·디스틸레이션은 표준 대안을 배제한 뒤 적합성 평가로만 고른다.
- **11강 실습 적용:** Northstar 사례에서 증거와 가정을 구분하고, 차단 요인별 담당자를 붙여 다음 단계를 권고한다.

#### 강의를 잇는 연결 고리

| 개념 | 설계(1–3강) | 결정(4–6강) | 검증(7강) | 운영(8강) | 특화(9–10강) | 적용(11강) |
|---|---|---|---|---|---|---|
| 출발점 | 고객 문제·워크플로 | 워크플로 요구 | 예상 동작 | 환경·릴리스 전제 | 사용자 상황 | 확인된 증거 |
| 기본 원칙 | 최소 패턴 | 가장 단순한 옵션 | 데모가 아닌 증거 | "작동"이 아닌 "운영 가능" | 표준 패턴이 먼저 | 스테이징 성공 ≠ 배포 준비 |
| 증거 | 성공·실패 테스트 | 비교 결과 | 평가 결과 | 관측 신호 | 적합성 근거 | 배포 검증 스냅샷 |
| 통제 | 자리 표시자 인증 | 인증·권한·최소화 | 모더레이션·사람 검토 | 경보·에스컬레이션 | 동의·권리·폴백 | 릴리스 게이트 |
| 산출물 | 증거 팩, 계약 계획 | 선정 근거, 검색 계획 | 가드레일 계획 | 준비 체크리스트 | 적합성 평가 | 배포 실습 권고안 |

#### 실무 체크리스트
- ☐ 문서화된 사실과 자리 표시자 인증만 쓰고, 실제 비밀 정보가 코드와 문서에 없는가
- ☐ 성공과 실패 동작을 모두 테스트하고, 로컬 증거와 배포 준비를 구분했는가
- ☐ 솔루션 경계와 워크플로에 맞는 최소 아키텍처 패턴을 정했는가
- ☐ 인터페이스 선택 근거와 요청·응답·오류 계약을 명시했는가
- ☐ 모델과 기능을 같은 사례로 비교해 가장 덜 복잡한 옵션을 골랐는가
- ☐ 데이터 흐름과 민감도를 매핑하고, 인증과 권한 부여를 확인했는가
- ☐ 검색이 정말 필요한지 판단했고, 필요하다면 근거 검증 테스트가 있는가
- ☐ 평가 기준과 가드레일, 사람 검토가 릴리스 게이트에 연결되는가
- ☐ 관측 신호마다 담당자가 있고, 롤백과 지원 책임이 정해졌는가
- ☐ 실시간·이미지·디스틸레이션 등 특화 패턴은 표준 패턴으로 부족할 때만 택했는가
- ☐ 차단 요인마다 담당자와 증거 요건을 붙여 가장 안전한 다음 단계를 권고했는가

> **한 줄 요약:** 기존 API를 안전하게 호출하고 최소 로컬 API를 만들어 검증한 뒤, 로컬 성공과 배포 준비를 구분하는 증거 팩으로 정리한다.

### 핵심 내용
#### 기존 API를 안전하게 호출하기
- 첫 호출은 추측이 아니라 **문서화된 사실**에서 시작한다. 모의 사양, 자리 표시자 인증, 검증 증거를 쓴다.
- 문서에 명시된 것과 그럴듯한 가정을 구분한다. 빈 문자열 허용 여부나 특정 오류의 상태 코드는 확인 전까지 가정이다.
- 시크릿은 `Authorization: Bearer <SUPPORT_API_TOKEN>` 같은 자리 표시자나 환경 변수로만 표현한다. 모의 작업에서도 마찬가지다.
- 성공만이 아니라 실패도 증거로 남겨야 잘못된 입력을 통제된 방식으로 처리하는지 알 수 있다.
- SDK 출력도 그대로 믿지 않는다. 요청 형식, 상태 코드, 응답 본문을 증거로 남긴다.

#### 최소 로컬 API 구축과 검증
- 목표는 다른 담당자가 실행하고 이해할 수 있는 **로컬 서비스**다. 공개 배포나 실제 고객 데이터 처리 승인은 없는 상태다.
- 최소 구성은 `GET /health`와 비즈니스 엔드포인트 하나, 그리고 입력 유효성 검사다.
- 예시는 FastAPI로 `POST /triage-ticket`을 구현한다. 키워드 분류는 흐름을 보여 주는 자리 표시자일 뿐이다.
- AI로 스타터 API를 만들어도 되지만, 실행 전에 검토할 초안으로 다룬다.
- 이 구성은 기본 API 계약만 입증한다. 모델 품질, 보안, 확장성은 입증하지 못한다.

#### 인계 준비: SecOps·DevOps·문서화
- 로컬에서 작동한다고 기업용으로 준비된 것은 아니다. 세 관점으로 이 착각을 막는다.
- **SecOps**는 시크릿이나 민감 데이터가 코드, 로그, 오류 메시지에 섞일 수 있는지 본다.
- 자리 표시자 인증은 방식을 보여 줄 뿐, 운영 리소스 접근 권한을 증명하지 않는다.
- **DevOps**는 다른 담당자가 로컬 실행, 상태 확인, 실패 원인 파악을 할 수 있는지 본다.
- 문서화는 엔드포인트 목적, 오류 상태, 다음 검토자 등을 짧게 남겨 인계를 돕는다.

#### 증거 팩으로 마무리
- **API Foundation 증거 팩**은 무엇을 테스트했고 무엇이 아직 로컬 전용인지 보여 주는 간략한 인계 기록이다.
- 모든 테스트 항목에 "이것이 입증하지 않는 것" 줄을 넣어 로컬 준비 상태의 과장을 막는다.
- 확신은 "될 것 같다"고 말하고, 증거는 테스트한 것과 결과, 아직 입증되지 않은 것을 말한다.
- 안전한 호출, 최소 API, 성공·오류 테스트, 준비 검토의 루프를 기술 검토로 넘어갈 때마다 반복한다.

### 기억할 개념·프레임워크

**최소 API 계약과 각 테스트가 입증하는 것**

| 테스트 | 예상 결과 | 입증하는 것 |
|---|---|---|
| `GET /health` | 200 `{"status":"ok"}` | 서버가 로컬에서 실행 중 |
| 정상 본문으로 `POST /triage-ticket` | 200, `category`와 `summary` | 예상 입력 수락과 응답 형식 |
| 빈 JSON `{}`으로 POST | 400 `{"detail":"ticket_text is required"}` | 유효성 검사로 누락 입력 처리 |

**준비 상태 3관점**

| 관점 | 확인할 것 | 로컬 증거가 입증하지 않는 것 |
|---|---|---|
| SecOps | 시크릿 노출, 자리 표시자 인증, 비식별 데이터 사용 | 운영 권한 부여, 최소 권한, 데이터 분류 |
| DevOps | 실행 명령, 환경별 설정, 테스트 증거, 로컬 로그 | 운영 모니터링, 롤백 준비, 확장성 |
| 문서화 | 목적, 필수 입력, 오류 상태, 담당자, 알려진 제한 | 운영 인증, 실제 분류 품질 |

- **API 문서 검토 최소 단위:** 문서화된 사실 하나, 필수 구성 항목 하나, 확인할 가정 하나.
- **증거 항목 템플릿:** 수행한 테스트, 예상·실제 결과, 입증하는 것, 입증하지 않는 것, 남은 격차.
- **증거가 뒷받침하는 결정:** 기술 검토 진입이나 탐색 지속은 가능하지만, 운영 출시는 불가다.

### 실무 적용 예시
- 모의 사양만 있고 실제 시스템 연결 준비가 안 된 지원 워크플로 → 문서화된 엔드포인트와 자리 표시자 인증으로 성공·오류 테스트부터 한다.
- 로컬에서 잘 도는 support-triage API를 기술 검토에 넘길지 → 증거가 명확하고 제한이 드러나면 진행한다. 데이터 경계나 소유권을 설명 못 하면 확대하지 않는다.
- 세 테스트를 통과한 API의 DevOps 메모 → "문서화된 명령으로 실행 가능, 운영 모니터링·롤백·확장성은 미입증"처럼 쓴다.

### 지식 점검 포인트
- 첫 API 호출의 가장 안전한 접근 → **문서화된 사실과 자리 표시자로 성공·실패를 테스트하고 증거 확보**
- 상태 확인, 비즈니스 엔드포인트, 누락 오류가 모두 작동하는 로컬 API → **유용한 로컬 증거지만 준비 상태 검토는 여전히 필요**
  - 보안, 모니터링, 거버넌스 등은 별도 검토가 필요하다.
- 샘플 코드에 하드코딩된 토큰 → **SecOps 격차**
- 소유자와 지원 경로가 없음 → **문서화·책임 소재 격차**
- 모니터링 증거가 없음 → **DevOps·운영 준비 격차**
- 상태·성공·의도적 오류 테스트 기록 → **로컬 준비 상태 증거**

  <h1 class="lesson-title">API 솔루션 아키텍처</h1>
</div>

> **한 줄 요약:** AI 아이디어를 워크플로 문제와 범위로 좁히고, 가장 단순한 유용한 패턴을 고른 뒤, 미해결 가정까지 담은 개요서로 정리한다.

### 핵심 내용
#### 문제, 범위, 제약 정의
- 탄탄한 아키텍처는 기능 목록이 아니라 **워크플로 문제**에서 시작한다. "에이전트 추가"처럼 해결책부터 꺼내는 개요서는 부실하다.
- 솔루션 경계는 범위 내, 범위 외, 미결정으로 나눈다. 경계가 없으면 브리핑 보조가 CRM 업데이트 도구로 번지기 쉽다.
- 고객 소통, 최종 권고, 규제 대상 결정처럼 사람이 맡아야 할 일도 경계에 적는다.
- 같은 패턴도 업종에 따라 위험이 다르다. 금융은 소스 관리와 권고 제한이 엄격하고, 의료는 개인·규제 정보를 신중히 다룬다.
- 지연과 지원 기대치도 패턴을 바꾼다 (예: 실시간 지원은 저지연과 사람 연결 같은 대체 경로가 필요하다).

#### 통합 요구와 패턴 선택
- **통합 맵**은 무엇이 호출하고, 어떤 컨텍스트가 필요하며, 출력이 어디로 가고, 누가 검토하는지 그린다.
- 자동 작업 생성이나 기록 갱신처럼 응답에 의존하는 하위 시스템은 사람이 보는 브리핑보다 위험이 크다.
- 이 단계에서는 모델이나 기능을 고르지 않는다. 이후 선정에서 테스트할 워크플로 요구와 제약만 기록한다.
- **최소한의 유용한 패턴**은 아직 필요 없는 기능을 더하지 않고 일을 해내는 가장 명확한 해결책이다.
- 기능을 더할 때마다 새 질문이 생긴다. 검색은 소스 승인과 최신성을, 도구는 실행 경계와 승인을 묻는다.

#### 거버넌스, 평가, 가시성 가정
- 좋은 개요서는 정상 경로만이 아니라 신뢰, 검토, 모니터링을 좌우하는 가정을 명시한다.
- **거버넌스**는 어떤 데이터에 접근할지와 그 승인을 확인한다. 데이터가 존재한다고 접근이 승인된 것은 아니다.
- "검토 필요" 대신 "관계 관리자가 사용 전 검토"처럼 후속 논의를 이끌 만큼 구체적으로 쓴다.
- **평가**는 사용자 제공 전에 입증할 행동을 명명한다. 데모 한 번의 성공은 신뢰 근거가 아니다.
- **가시성**은 계속 운영할지, 바꾸거나 멈출지 판단하는 데 필요한 신호를 명명한다.

#### 개요서 작성과 인계
- 개요서는 무엇을 왜 제안하는지, 무엇이 미해결이고 다음에 무엇을 할지 알 수 있게 쓴다.
- 알려진 사실, 가정, 검증되지 않은 가정을 구분한다.
- 최종 모델, SDK 구문, DB 같은 미검증 구현 세부를 아는 척하지 않는다.
- 다음에 정의할 계약 세부(요청·응답 필드, 오류 상태, 인증 가정 등)를 명시한다.

### 기억할 개념·프레임워크

**API 아키텍처 패턴 비교**

| 패턴 | 가치를 더하는 경우 | 피할 때 |
|---|---|---|
| 단순 모델 호출 | 필요한 컨텍스트가 요청에 모두 있음 | 요청 밖 소스나 시스템 조치가 필요 |
| 구조화된 출력 | 검토·라우팅·저장에 예측 가능한 필드 필요 | 서술형 초안만 필요하거나 구조 미정 |
| 검색 기반 응답 | 실행 시점에 승인된 최신 지식 필요 | 앱이 컨텍스트를 직접 제공, 소스 미승인 |
| 도구·작업 워크플로 | 실시간 상태 조회, 레코드 생성·변경 | 초안만 필요, 승인 없이 기록에 영향 |
| 에이전트 기반 | 여러 도구·시스템에 걸친 다단계 조정 | 단순 패턴으로 충분, 권한을 설명 못 함 |
| 실시간·음성·다중 모드 | 음성, 시각 증거, 저지연이 핵심 | 텍스트가 검토·감사에 유리 |
| 하이브리드 | 단일 패턴으로 부족하고 각 패턴에 근거 있음 | 기능이 있다는 이유만으로 결합 |

- **선택 순서:** 앱이 컨텍스트를 다 주면 단순 호출부터 시작하고, 필요가 확인될 때만 검색·도구·에이전트를 더한다.
- **패턴 근거 문장:** "[요구] 때문에 [패턴]을 권장한다. [기능]은 가능하지만 [제한]은 해결하지 못한다."
- **문제 진술 틀:** "현재 [팀]은 [문제점] 때문에 [작업]에 어려움을 겪는다. 고객은 [API 지원 단계]로 [성과]를 개선하고자 한다."
- **허용 불가 출력 예:** 근거 없는 주장, 고객 대상 권고, 미승인 출처, 과신 등을 평가 가정에 미리 적는다.

**준비 상태 4질문** (통화 전 브리핑 예)

| 영역 | 질문 | 준비 메모 예 |
|---|---|---|
| 거버넌스 | 어떤 데이터에 접근하고 누가 승인하나? | 관계 관리자가 접근 권한을 가진 승인 소스만 사용 |
| 평가 | 어떤 동작을 테스트하나? | 누락·상충 맥락 표시, 권고성 표현 회피 |
| 가시성 | 사용 후 무엇이 보여야 하나? | 요청 상태, 검토 표시, 실패 사유, 지연 시간 |
| 운영 준비 | 확대 전 어떤 조건이 필요한가? | 검토 책임자, 맥락 누락 시 대체 처리, 지원 담당 |

### 실무 적용 예시
- 금융 관계 관리자의 통화 전 브리핑 → 승인 소스만 요약한 내부 초안으로 두고, 투자 권고·CRM 업데이트·고객 메시지는 금지한다.
- 계정 작업 공간이 승인 컨텍스트를 요청에 다 담아 준다 → 첫 버전은 구조화된 출력이다. 검색은 검증 전까지 미정, CRM 업데이트는 범위 외다.
- 브리핑을 생성할 수 있다 → 파일럿 준비가 됐다는 뜻은 아니다. 준비 4질문으로 프로토타입과 파일럿 결정을 분리한다.

### 지식 점검 포인트
- 워크플로 요구와 시기상조 기술 선택을 가장 잘 구분한 것 → **승인된 계정 정보로 회의 준비를 돕고, 사용 전 사람이 검토하는 내부 브리핑**
- 짧은 메모 요약에 팀장 검토만 있고 소스 조회나 시스템 업데이트가 불필요 → **단순 모델 호출 또는 구조화된 출력 패턴**
- "계정 데이터로 브리핑을 생성해 표시한다"에서 빠진 핵심 가정 → **누가 데이터에 접근하고, 결과를 검토하며, 오류를 조사하는가**
- 가장 타당한 아키텍처 개요 → **승인된 계정 컨텍스트로 내부 브리핑을 생성하고 사용 전 관계 관리자가 검토**
  - 필요 전에 기능을 더하지 않으면서 소스, 권한, 검토 결정을 미루지 않기 때문이다.

  <div class="eyebrow">레슨 03 · API Contracts and Core Interfaces</div>
  <h1 class="lesson-title">API 계약과 핵심 인터페이스</h1>
</div>

> **한 줄 요약:** 추론 인터페이스와 상태 리소스를 워크플로 요구에 맞춰 고르고, 그 선택을 요청·응답·오류 계약과 검증 테스트로 옮긴다.

### 핵심 내용
#### 핵심 API 인터페이스 비교
- 인터페이스는 오래된 샘플이나 익숙함이 아니라 **워크플로 요구**에서 고르고, 왜 맞는지 설명한다.
- Responses API는 신규 프로젝트의 권장 시작점이다. 다만 도구 실행과 결과의 후속 사용 계약은 애플리케이션이 소유한다.
- Chat Completions API는 계속 지원되지만, 신규 작업에서는 기본값이 아니라 **호환성·마이그레이션 제약**으로 다룬다.
- Conversations API는 세 번째 추론 인터페이스가 아니라, Responses와 함께 대화 상태를 저장하는 **상태 리소스**다.
- 상태는 기본값이 아니라 설계 결정이다. 단일 요청에 다 담을 수 있으면 무상태가 더 단순하고 테스트하기 쉽다.

#### 상태, 도구, 지연 작업
- 무상태 계약은 요청 독립성을, 상태 계약은 연속성과 누락·노후·불일치 상태를 테스트한다.
- 도구는 **읽기 전용 조회**와 조치를 취하는 워크플로로 나눈다. 레코드 업데이트나 메시지 전송은 더 엄격한 승인이 필요하다.
- 스트리밍은 긴 초안에 유용하지만, 하위 시스템이 완전한 구조화 객체를 검증해 써야 하면 덜 유용하다.
- 지연 작업은 백그라운드 응답 생성과 비동기 도구 호출로 나뉜다. 어느 쪽도 미완성 결과를 쓸 수 있게 만들지 않는다.
- 비동기 도구(`async: true`)는 완료 시 원래 `call_id`를 담은 `function_call_output`을 반환한다. 그동안 모델이 상태를 지어내면 안 된다.

#### 구조화 출력과 재시도
- **Structured Outputs**는 지원되는 JSON 스키마 준수를 강제할 수 있고, JSON 모드는 유효한 JSON만 보장한다.
- 모델이 쓴 `confidence_note`는 보정된 신뢰도 점수가 아니다. 위험 판단은 결정론적 검사, 평가기, 사람 검토로 한다.
- 스키마 준수와 별개로 거부, 잘린 응답, 유효하지 않은 애플리케이션 상태도 처리해야 한다.
- 재시도가 작업, 메시지, 레코드를 중복 생성하면 안 된다. `request_id` 같은 중복 제거가 필요한지 계약에 적는다.

#### 요청, 응답, 오류 계약
- 요청 계약은 일반적인 "AI 요청"이 아니라 워크플로와 연결된 엔드포인트 목적부터 쓴다.
- 고객 앱 엔드포인트(예: `POST /case-summary`)와 그 뒤에서 쓰는 OpenAI API 인터페이스 결정을 구분한다.
- 응답 계약은 모델이 실패할 때의 **대체 응답**까지 정의한다. 구조화된 오류 상태, 검토 플래그, 안전한 메시지가 그 예다.
- 오류마다 유발 조건, 상태 코드, 사용자에게 안전한 메시지, 다음 조치를 정한다. 내부 정보는 노출하지 않는다.
- "오류를 우아하게 처리한다" 같은 모호한 요구 대신 필드, 유효성 규칙, 테스트 가능한 예시를 쓴다.

#### 검증과 계약 계획
- 성공 테스트와 오류 테스트를 분리해 "정상 경로가 성공했으니 준비됐다"는 실수를 막는다.
- 계약 검증은 계약이 테스트된 대로 작동함만 입증한다. 확장성, 보안 태세, 운영 모니터링은 입증하지 않는다.
- 계획만 된 테스트는 실행되지 않은 증거일 뿐 통과가 아니다.
- 지속적 설계 논리와 **변동성 큰 세부**(모델 이름, SDK 예제, 가격 등)를 분리하고, 후자는 최신 공식 문서로 확인한다.

### 기억할 개념·프레임워크

**인터페이스 결정표** (추론 인터페이스를 먼저, 상태 방식을 그다음에 고른다)

| 표면·리소스 | 이럴 때 사용 | 구축 전 검증할 것 |
|---|---|---|
| Responses API | 신규 프로젝트, 구조화 출력·도구 등 문서화된 기능 | 필수 기능, 상태 방식, 스트리밍 동작, 현재 제한 |
| Chat Completions API | 기존 구현과 호환성 요구 | 고객 제약, 마이그레이션 영향, 수동 상태 처리 |
| Conversations API | 세션·기기·작업 간 지속 상태(Responses와 함께) | 상태 소유권, 보존 기대, 개인정보, 복구 동작 |

**응답 필드 예시**

| 필드 | 유형 | 의미 |
|---|---|---|
| `issue_summary` | 문자열 | 고객 문의의 간략한 요약 |
| `urgency` | 열거형 low, medium, high | 검토·분류용 운영 긴급도 |
| `recommended_next_action` | 문자열 | 계정 팀의 내부 후속 조치 |
| `confidence_note` | 문자열 | 불확실성 설명(보정된 점수 아님) |
| `needs_human_review` | 부울 | 사용 전 사람 검토 필요 여부 |
| `review_reason` | 문자열 | `needs_human_review`가 true일 때 검토 이유 |

- **오류 처리 예**
  - `account_id` 누락 → 누락을 알리고 다시 요청받는다.
  - 무단 접근 → 계정 정보를 반환하지 않고 권한 오류를 기록한다.
  - 소스 불가 → `needs_human_review=true` 또는 구조화된 오류로 응답한다.
  - 구조화 출력 오류 → 안전하면 재시도하고, 아니면 검토로 보낸다.
- **도구 계약 항목:** 목적, 입력, 출력, 실행 범위, 권한, 오류 시 동작, 승인 필요 여부.

### 실무 적용 예시
- 기존 Chat Completions 지원 봇에 구조화 요약과 티켓 상태 도구가 필요 → Responses API를 추론 시작점으로 권장하고, 기존 구현은 호환성 제약으로 기록한다.
- "문제를 요약하고 다음 조치를 제안"하는 출력을 대시보드에서 정렬하려 함 → 요청 필드, 응답 필드, 오류 상태를 정의해 테스트 가능한 계약으로 바꾼다.
- 유효 요청에서 필수 필드가 반환돼 합격 → 기본 성공 응답만 입증한다. 권한, 소스 불가, 운영 모니터링은 미입증으로 남긴다.

### 지식 점검 포인트
- 기존 Chat Completions 봇에 구조화 요약, 도구, 후속 질문이 필요 → **Responses API를 평가하고, Conversations API는 지속 상태가 필요할 때만 함께 쓴다**
  - Chat Completions는 호환성 제약이고, Conversations API는 추론 인터페이스가 아니다.
- 무상태 요청 → **모든 필수 컨텍스트를 매 요청에 포함**
- 재시도 가능한 쓰기 작업 → **중복 레코드나 작업을 막는 멱등성 요구 정의**
- "업데이트를 트래커용 작업 목록으로 변환" 메모에 빠진 것 → **호출자 입력, 반환 작업 필드, 트래커 기대 구조, 무효 입력 처리**
- 유효 요청 하나만 통과 → **성공 경로를 기록하고 필드 누락, 무단 접근, 소스 불가 등 오류 테스트 추가**
- 인계에 가장 적합한 계획 → **Responses API(문서 검증 대기)에 상태 방식, 스키마 동작, 오류, 테스트, 미해결 질문을 담은 계획**

<div class="lesson-head">
  <div class="lesson-num">04</div>
  <div class="eyebrow">레슨 04 · Model and Capability Selection for API Solutions</div>
  <h1 class="lesson-title">API 솔루션을 위한 모델·기능 선택</h1>
</div>

> **한 줄 요약:** 모델 선택을 배포 결정으로 보고, 같은 기준으로 후보를 비교해 기준을 충족하는 가장 덜 복잡한 옵션을 근거와 함께 고른다.

### 핵심 내용
#### 작업·기능 요구 사항 정의
- 모델·API 기능 선택은 기능 비교가 아니라 **배포 결정**이다. 출발점은 모델 이름이 아니라 워크플로다.
- 비즈니스 표현을 분류·추출·검색 같은 기술 과제로 바꾼다. 유형이 섞이면 **주요 출력**이 첫 패턴을 정한다.
- 다른 시스템이 응답을 소비하거나 자동 검증이 필요하면 **구조화된 출력**이 필요하다.
- 심층 추론은 복잡성과 모호성이 정당화할 때만 쓴다. '중요한 작업'이라는 이유만으로는 쓰지 않는다.
- Responses API나 Chat Completions 같은 **인터페이스**는 나중 세부가 아니다. 상태, 도구, 스트리밍 처리를 좌우한다.
  - Conversations는 Responses와 함께 상태를 유지하는 기능이지, 별도 추론 인터페이스가 아니다.

#### 현재 후보 목록 작성·비교
- **현재 후보 목록**은 전체 모델 나열이 아니라, 필수 조건 미달 후보를 걸러낸 소수 집합이다.
- 후보마다 정확한 모델 ID, 공식 출처, 확인 날짜를 남긴다. 이름과 가격, 가용성은 계속 바뀐다.
- GPT-6 Astra는 기존 모델의 자동 대체재가 아니다. 추론 설정에 'none'이 없고 미세 조정도 지원하지 않는다.
- 잠정 유력 후보는 같은 사례와 채점 규칙으로 비교를 통과할 때까지 **가설**이다.
- 실패 사례를 고칠 때는 지침 변경을 한 번에 하나씩 테스트하고, 더 넓은 세트로 회귀를 확인한다.

#### 위험·비용·검증 논리
- 비용은 목록가가 아니라 **성공한 작업당 총 비용**으로 비교한다. 재시도, 실패, 검토자 시간이 들어간다.
  - 차단된 응답은 성공으로 세지 않는다. 성공률을 높이려고 자동 재시도를 유발하지도 않는다.
- 고성능 모델은 성공률 향상 같은 증거로 **작업 경제성**이 개선될 때만 고른다.
- 일상 사례는 단순 경로로, 모호하거나 고위험인 사례만 고성능 경로로 보내는 분기도 검토한다.
- 고객, 자금, 접근 같은 결정에 영향을 주면 **사람 검토**가 필요하다.
- 안전 경계가 불분명하면 더 정교한 모델로도 **거버넌스 문제**는 풀리지 않는다.

#### 모델 및 기능 선정 근거 작성
- **모델 및 기능 선정 근거**는 순위표나 최종 아키텍처가 아니라 의사결정 문서다.
- 권장 패턴과 함께 배제한 대안, 상충 관계, 검증 질문을 담는다.
- 결정 논리와 **변동성 있는 제품 사실**을 분리한다. 제품이 바뀌어도 구현만 고치면 된다.
- "최신 모델이 최고" 대신 "[날짜]에 카탈로그 확인, 대표 테스트에서 기준 충족, 빌드 전 재검증"으로 쓴다.
- 조건부 서술은 약점이 아니라 올바른 기술 판단이다.

### 기억할 개념·프레임워크

| 피해야 할 지름길 | 왜 문제인가 |
|---|---|
| 가장 최신·고성능 모델 선택 | 결과 개선 없이 비용과 지연만 늘 수 있음 |
| 목록가 최저 모델 선택 | 재시도, 긴 출력, 검토 부담을 무시 |
| 일반 벤치마크를 증거로 간주 | 워크플로 타당성이 아닌 가설용 자료 |
| 기존 코드 샘플의 모델 재사용 | 현재 상태와 적합성이 확인되지 않음 |
| 서로 다른 조건에서 비교 | 테스트 케이스, 프롬프트, 검토 규칙이 달라 비교 불가 |
| 정확한 모델 ID 미기록 | 별칭은 바뀜 |

| 의사결정 위치 | 의미 |
|---|---|
| 유지 | 요구를 충족해 계속 사용 가능 |
| 조건부 유지 | 적합할 수 있으나 명시된 가정 확인 필요 |
| 제거 | 문서화된 상충으로 필수 요구 미충족 |
| 보류 | 책임 있는 비교를 하기에 증거 부족 |

- **주요 출력 → 핵심 작업:** 라우팅 라벨은 분류, 출처에 근거한 답변은 검색, 실시간 상태 의존은 도구 활용이다.
- **기준 미충족 시:** 기준선 개선, 요구 재검토, 권장 보류 중에서 택한다. 불충분한 증거로 선택을 강요하지 않는다.
- **필수 요건:** 입출력 방식, 추론 인터페이스 호환, Structured Outputs 같은 필수 기능, 대상 API 환경의 가용성.
- **선호 조건:** 낮은 지연과 작업 비용, 단순한 구현과 운영, 적은 검토 부담.
- 필수 요건을 못 채운 후보는 탈락이다. 선호 조건이 좋아도 이를 상쇄하지 않는다.
- **권장안을 바꿀 조건:** 정책에 의존하면 검색을, 실시간 주문 데이터에 의존하면 도구 사용을 평가한다.

### 실무 적용 예시
- 소매업체가 하루 수천 건의 짧은 지원 메시지를 팀별로 라우팅하려 함 → 첫 패턴은 **구조화된 분류 응답**이다.
- 같은 사례로 후보 A, B, C 비교: A는 검토 트리거를 놓치고 C는 개선 없이 지연과 비용만 늚 → **B**를 기준선으로 권장한다.
  - 보편적 최고여서가 아니라, 사전 기준을 모두 충족한 후보 중 작업 경제성이 가장 좋아서다.
- 성수기에 "모든 메시지에 고성능 모델과 상세 설명" 제안 → 기준선으로 시작하고, 이점이 입증될 때만 **고성능 예비**를 둔다.

### 지식 점검 포인트
- 구조화된 분류에 호환 후보가 여러 개 → **같은 대표 사례로 품질, 스키마, 검토 트리거, 작업당 비용 비교**.
  - 주력 모델이나 최저 토큰 가격은 워크플로 적합성을 보장하지 않는다.
- 대량 라우팅 API에 모든 요청 고비용 모델과 검색을 권장 → **추가 비용과 복잡성의 근거가 없어 불완전**.
- 선정 근거에 거절 이유와 재확인할 제품 정보가 없음 → **거절 후보와 근거, 재검증할 가격과 한도를 기록**.
  - 결정 논리와 변동성 있는 사실을 분리해야 한다.

  <div class="eyebrow">레슨 05 · API Security, Data Handling, and Access Controls</div>
  <h1 class="lesson-title">API 보안·데이터 처리·접근 제어</h1>
</div>

> **한 줄 요약:** 데이터, 접근·비밀 정보, 조치·승인의 세 경계를 점검해 증거 공백을 드러내고 가장 안전한 다음 단계를 권고한다.

### 핵심 내용
#### 데이터 이동과 민감도 매핑
- 보안 검토는 **데이터 이동**에서 시작한다. 무엇이 들어와 어디로 가고, 무엇이 저장·기록되는지 설명해야 한다.
- 워크플로를 모델 호출 하나가 아니라 일련의 데이터 이벤트로 보고, 단계마다 출처와 소유자를 묻는다.
- 민감도가 불확실하면 '미해결'로 표시하고, 책임자가 확인하기 전까지 **가장 높은 등급**으로 다룬다.
- **데이터 최소화**는 수집부터 로그까지 모든 단계에 적용한다.
  - 입력: 필요한 필드만 보내고, 민감 필드는 빼거나 가린다.
  - 출력: 필요한 만큼만 드러낸다 (예: "미해결 청구 에스컬레이션 1건").
  - 로그: 원시 프롬프트, 비밀, 고객 기밀은 남기지 않는다.
- 조직이 명시적으로 동의하지 않는 한 API 데이터는 **OpenAI 모델 훈련**에 쓰이지 않는다.

#### 인증·권한 부여·최소 권한
- 흔한 오류는 **인증을 안전성의 증거로 착각**하는 것이다. 인증은 호출자 식별일 뿐, 할 수 있는 일은 권한 부여가 정한다.
- 유효한 서비스 계정이라도 민감 레코드 읽기나 관리자 작업 권한이 자동으로 따라와서는 안 된다.
- **최소 권한**: 라우팅 라벨만 쓰면 되는 워크플로가 전체 레코드 읽기나 삭제 권한을 가져서는 안 된다.
- 광범위한 읽기·쓰기 권한의 공유 서비스 계정은 프로토타입은 쉽게 하지만 **승인은 어렵게** 한다.

#### 비밀 정보와 OpenAI 키·RBAC
- 비밀 정보는 환경 변수나 관리형 시크릿 저장소에 두고, 프롬프트나 로그, 데모에 넣지 않는다.
- OpenAI API 키는 브라우저·모바일 클라이언트에 **절대 배포하지 않고** 보호된 백엔드를 거친다.
- 팀원끼리 키를 공유하지 않는다. 앱 워크로드는 프로젝트 범위 서비스 계정 같은 **비인간 신원**을 쓴다.
- 키 유출이 의심되면 즉시 교체·취소하고 종속 앱을 업데이트한다.
- RBAC에서는 프로젝트 수준을 우선하고, 실험·스테이징·프로덕션을 **서로 다른 프로젝트**로 나눈다.

#### 통제·승인·감사 가능성
- "사람 검토 필요"는 출발점이다. 누가 무엇을 승인하고, 승인이 빠지면 어떻게 되는지까지 정한다.
- **감사 가능성**은 로그를 많이 갖는 것이 아니라, 적절한 검토자가 보호된 증거를 갖는 것이다.
- 로그에서 **운영 증거와 민감 콘텐츠를 분리**한다. 요청 ID와 상태 코드는 남기고 원시 프롬프트와 API 키는 뺀다.
- 정보 생성에서 **시스템 변경**으로 넘어가면 위험이 달라진다. 초안 허용이 승인 없는 레코드 수정 허용은 아니다.
- 시정 조치는 "로깅 개선"처럼 모호하면 안 된다. 변경 사항, 책임자, 검증 절차를 적는다.

#### API 보안 및 데이터 처리 검토 활용
- **API 보안 및 데이터 처리 검토**는 1차 스냅샷이다. 고객의 보안·법무 검토를 대체하지 않고 준비시킨다.
- 기술 설계 논의, 파일럿 준비, 프로덕션 준비 검토, 소유자 인계 시점에 쓴다.
- 실제 검토에는 과정 연습 내용이 아니라 승인되고 비식별 처리된 정보만 쓴다.
- 모르는 정보는 추측하지 않고 "확인되지 않음"이나 "소유자 검토 필요"로 적는다.
- 결과를 쓰기 전에 현재 OpenAI 데이터 제어, API 키 보안, 권한 지침을 확인하고 **확인 날짜**를 남긴다.

### 기억할 개념·프레임워크

| 구분 | 내용 | 검토 시 주의 |
|---|---|---|
| 악용 모니터링 로그 | 기본 생성, 프롬프트와 응답 포함 가능, 최대 30일 | 애플리케이션 상태와 섞지 않기 |
| 애플리케이션 상태 | 일부 기능이 워크플로 유지를 위해 보관 | 엔드포인트별 보관 내용과 store 동작 확인 |
| MAM과 ZDR | 자격 있는 고객의 승인 기반 조직·프로젝트 제어 | 활성화됐다고 가정 금지 |

- ZDR에서는 Responses와 Chat Completions의 store가 false로 처리된다.
- 다만 ZDR이어도 자격 없는 엔드포인트는 애플리케이션 상태를 보관할 수 있다.

| 준비 상태 권고 | 쓰는 때 |
|---|---|
| 준비 완료 | 이 단계에서 보안·데이터 처리 차단 결함이 없음 |
| 조건부 준비 완료 | 제한된 미결 항목을 담당자와 검증으로 확인 가능 |
| 출시 전 시정 필요 | 민감 로그, 과도한 권한, 승인 누락 같은 차단 요인 |
| 일시 중지·상급 이관 | 규제 데이터나 워크플로 허용 여부 자체가 불확실 |

- **허용 작업:** 내부 초안 요약 생성, 직원 검토용 분류, 다음 단계 제안.
- **승인 전용 작업:** 요약을 원본 레코드에 기록, 우선순위나 상태 변경, 에스컬레이션 트리거.
- **금지 작업:** 고객 메시지 자동 전송, 티켓 자동 종결, 원본 삭제나 덮어쓰기.
- RBAC에서 사용자의 실제 접근은 할당된 모든 역할의 **합집합**이다.
- 데이터는 "지원 데이터" 같은 포괄 라벨이 아니라 **필드명**으로 적는다.
- 통제는 직접 구성하지 않아도, 나중에 어디에 들어갈지와 유력한 담당자를 밝힌다.
  - 예: 승인 게이트는 워크플로 오케스트레이션이나 검토자 UI, 비밀 보호는 관리형 시크릿 저장소.

### 실무 적용 예시
- 지원 티켓 분류 API가 디버깅용으로 전체 요청·응답 본문을 기록 → 원시 본문을 빼고 운영 메타데이터만 남긴다.
  - 시정 후에는 스테이징에서 가림 처리를 검증하고, 로그 접근 소유자를 정한다.
- 공유 서비스 계정이 모든 티켓을 읽고 쓰며, 데모가 개인 OpenAI 키를 클라이언트에 넣음 → **출시 전 시정** 대상이다.
- "티켓 업데이트 전 사람 승인 필요" → "초안은 생성하되 담당자 승인 전에는 티켓에 반영하지 않는다"로 구체화한다.

### 지식 점검 포인트
- "지원 티켓만 쓰니 보안 검토 불필요"라는 팀 → **배포 전 데이터 이동, 민감도, 소유권, 최소화 방안 파악**.
  - 지원 티켓에도 기밀, 개인, 규제 데이터가 들어갈 수 있다.
- 서비스 계정 인증에 성공한 뒤에도 남는 질문 → **이 계정이 무엇에 접근하고 무엇을 수행할 수 있는가**.
- 고객 기록을 자동 업데이트하는데 승인자와 근거가 없음 → **승인 담당자와 근거가 정의될 때까지 자동 업데이트 차단**.
- 보존 기간과 로그 검토 담당자만 미정인 제한 내부 파일럿 → **조건부 준비 완료**.
  - 남은 문제가 제한적이고 명확해 확대 전에 해결할 수 있다.
  - 민감 로그나 불안전한 비밀이 남았다면 출시 전 시정이나 일시 중지·이관이 맞다.

> **한 줄 요약:** 검색을 기본값이 아닌 설계상의 약속으로 보고, 지식 요구에서 출발해 검색 여부와 출처 준비, 검증 테스트를 정한다.

### 핵심 내용
#### 검색이 맞는 해결책인지 판단
- 문서가 있다는 이유만으로 API에 연결하지 않는다. 검색 설계는 실제 **지식 요구**에서 시작한다.
  - 예: "휴가 이월 질문에 답하려면 현재 휴가 정책과 지역별 공휴일 정책이 필요하다."
- 지식 요구에는 API가 검색된 컨텍스트에서 주장하거나 노출하면 안 되는 **출력 경계**도 담는다.
- 응답 시점에 승인되고 최신이며 권한을 고려한 비즈니스 지식이 필요하면 **검색**이 맞을 가능성이 높다.
- 사용자가 준 문단을 고쳐 쓰는 API에 검색을 붙이면 품질 개선 없이 지연, 비용, 권한 위험만 는다.
- GPT-6 Astra 평가 사례의 교훈: 승인 출처 식별, 출처별 권한 적용 같은 설계 결정이 먼저이고 **맥락 제공 방식**은 그다음이다.

#### 지식 접근과 출처 준비 상태
- "모든 문서 연결"이 아니라 필요한 승인 출처만 고른다. 기업 지식에는 초안, 구식 정책, 기밀 메모가 섞여 있다.
- **권한을 고려한 검색**은 허용된 콘텐츠만 검색하는 것이다. 권한 동작은 가정하지 말고 검증한다.
- **후보 출처는 자동으로 승인된 출처가 아니다.** 관련성·승인·최신성 등을 갖춘 경우에만 포함한다.
- 관련 내용이 있어도 구식이거나 미승인이면 '검색 필요'가 아니라 **'출처 검증까지 보류'**다.
- **검색은 신뢰도 낮은 출처를 신뢰할 수 있게 바꿔 주지 않는다.**

#### RAG·임베딩·메타데이터의 역할
- **RAG**는 승인 출처에서 관련 콘텐츠를 찾아 모델 컨텍스트로 넘기고, 근거와 함께 답을 반환하는 흐름이다.
- RAG의 목적은 모든 답을 정확하게 만드는 것이 아니라, 출력을 검토·검증 가능하게 하는 것이다.
- **임베딩·벡터 검색**은 표현이 달라도 의미가 비슷한 콘텐츠를 찾는다. 정확성이나 최신성은 보장하지 않는다.
- 메타데이터는 출처를 좁혀 구식·무관 콘텐츠를 막지만, **접근 제어를 대체하지 않는다**.
  - 누가 어떤 출처에 왜 접근하는지 설명할 수 없으면 기업용 준비가 안 된 것이다.
- 필터 범위가 넓으면 미승인 출처가 섞이고, 좁으면 유용한 출처를 놓쳐 답이 불완전해진다.

#### 근거 기반 출력 검증
- 검색 테스트는 **올바른 출처를 가져왔는가**와 모델이 그 컨텍스트를 올바르게 썼는가를 함께 본다.
- "답이 맞았나?"만 보면 구식 지침 혼동, 제한 콘텐츠 노출, 근거 없는 세부 추가를 놓친다.
- 출처 참조가 붙어 있어도 모든 주장의 근거가 증명되지는 않는다.
- 여러 출처를 종합한 권고는 검토자가 중요한 주장마다 **뒷받침 구절**로 추적할 수 있어야 한다.
- **검색 품질은 시간이 지나며 변한다.** 검색 담당자와 출처 관리자를 정해 두고 주기적으로 검토한다.

#### 설계 계획 작성
- 계획은 API가 알아야 할 것, 그 지식의 출처, 검색의 타당성, 사전 검증 항목에 답한다.
- "RAG 사용" 같은 기법 이름이 아니라 **설계 결정과 검증 작업**을 적는다.
- "진행하지 말아야 할 것"을 적으면 허위 준비 상태를 막는다 (예: 출처 소유자 승인 전 초안 지침 미포함).
- 호스팅 검색을 쓰면 벡터 스토어와 파일 ID, file_search 증거, 만료·정리 책임자도 기록한다.
- 도구, 에이전트, 가드레일은 이 단계에서 설계하지 않고 **인계 제약**으로만 적는다.

### 기억할 개념·프레임워크

| 검색 적합성 권고 | 쓰는 때 |
|---|---|
| 검색 필요 | 승인되고 최신이며 권한을 고려한 지식에 의존 |
| 검색 불필요 | 모델 단독, 구조화된 출력, 사람 지원 패턴으로 충분 |
| 출처 검증까지 보류 | 유용할 수 있으나 승인·소유권·권한 문제가 먼저 |

| 근거 기반 출력 오류 | 대응 |
|---|---|
| 근거 없는 추가 | 출처 범위 유지 요구와 테스트 |
| 구식 출처 사용 | 발효일 필터, 구식 출처 검증 |
| 출처 누락에도 과도한 확신 | 명확화, 거부, 이관 또는 needs_review=true |
| 권한 유출 | 권한 경계 테스트, 소유자와 접근 가정 검증 |
| 충돌 은폐 | 출처 우선순위 규칙과 에스컬레이션 정의 |

- **결정 흐름:**
  1. 요청 범위 밖 지식이 필요한가? 아니면 검색 불필요.
  2. 그 출처가 승인되고 최신이며 접근이 허용되는가? 아니면 보류.
  3. 근거 기반 출력을 사용 전에 검증할 수 있는가? 아니면 진행 금지.
- **출처 결정:**
  - 포함: 관련·승인·최신이고 권한이 있으면 메타데이터와 필터 요구를 정의한다.
  - 제외: 미승인, 구식, 과도하게 민감하면 제외 사유를 기록한다.
  - 사용 전 검증: 소유권이나 권한이 미해결이면 검증 책임자와 필요 증거를 명시한다.
- **RAG를 쓰지 말아야 할 때:** 사용자가 출처 콘텐츠를 이미 줬거나, 권한을 강제할 수 없거나, 결과 개선 없이 부담만 늘 때.
- **임베딩 가정:** 도움이 되는 이유, 적용할 승인 출처 집합, 입증하지 못하는 것, 필요한 필터를 적는다.
- **취약한 문구 고치기:** "모델이 출처를 인용해야 함" → 출처 ID, 섹션, 버전, 발효일 반환과 근거 없는 주장 테스트.

### 실무 적용 예시
- 생명과학 현장 팀 Q&A API → "모든 제품 문서에 RAG" 대신 승인된 최신 지침과 검증된 지역 부록만 쓴다.
  - 현장 교육 초안과 구버전 교육 자료는 제외한다.
- 메타데이터 필터가 지역만 보고 발효일은 보지 않아 오래된 부록을 씀 → 테스트를 보강하고 통과 전엔 진행하지 않는다.
  - 출처 참조가 있어 그럴듯해 보여도 안전하지 않다.
- 핵심 출처는 타당하나 지역 부록과 권한, 필터가 미검증 → 최종 권고는 **조건부 검색 필요**다.
  - "제품 문서에 RAG 사용"보다 강한 이유는 포함·제외 출처와 아직 하지 말 것까지 구체적으로 말하기 때문이다.

### 지식 점검 포인트
- 조달 정책 Q&A에 승인 정책, 초안 부칙, 구식 교육 자료가 섞임 → **승인된 최신 정책만 검색하고 초안은 사용 전 검증**.
  - 일부 규칙이 지역별로 다르므로 지역 필터를 적용하고 구식 자료는 뺀다.
- 민감 CRM 데이터와 초안 계정 계획이 있는 브리핑 API → **권한, 민감 데이터, 초안 제외를 검증한 뒤에만 검색**.
- 출처 참조를 표시했지만 출처에 없는 예외를 추가 → **검증되지 않은 출력**이며 근거 없는 주장 테스트를 추가한다.
- "여러 문서 전반에 RAG 적용, 출처 인용, 일반 질문 몇 개 테스트" 계획 → **통제 수단과 책임자가 빠져 불완전**.

### 핵심 내용
#### 프롬프트 동작과 구조화된 출력 정의
- 데모 성공은 신뢰 근거가 아니다. 정보 누락, 위험 요청, 형식 오류에서도 예상대로 동작한다는 증거가 필요하다.
- 프롬프트는 문구가 아니라 API가 할 일과 피할 일, 그리고 명확화·거절·검토 이관 시점을 정의한다.
- "직원 정책 질문에 답하라"는 짧아서가 아니라 출처, 출력 형식, 검토 조건을 해석에 맡겨서 약하다.
- **구조화된 출력**은 신뢰성 통제 수단이다. JSON 모드는 유효한 JSON만 보장하므로 스키마 강제가 없으면 앱에서 검증한다.
- 모델이 쓴 confidence_note는 보정된 신뢰도가 아니다. 저신뢰 트리거는 출처 증거나 결정론적 규칙으로 정한다.

#### 평가 기준과 테스트 케이스
- 평가의 초점은 자동화 도구가 아니라 무엇을 테스트하고, 어떤 결과가 릴리스를 막는지다.
- 성공 기준은 "정답이다" 대신 "승인 출처 ID 1개 이상, needs_review: false, 근거 없는 주장 없음"처럼 쓴다.
- 좋은 케이스는 입력, 예상 동작, 합격 규칙, 수집할 증거를 갖춰 동작 변경 후 다시 돌리기 쉽다.
- **실패 범주**는 릴리스 결정과 연결한다. 맞춤법 오류는 파일럿을 막지 않지만 검토 트리거 누락은 차단 대상이다.

#### 모더레이션·가드레일·사람 검토
- **모더레이션**은 유해 콘텐츠 범주의 초기 신호일 뿐이다. 권한, 고객 정책, 출처 승인은 앱별 검사로 다룬다.
- 가드레일은 "안전하게 하라"가 아니라 구현 팀이 구성하고 평가 담당자가 테스트할 만큼 구체적이어야 한다.
- 통제는 생성 전·중·후의 연쇄 점검이다. 필수 검사를 통과하기 전의 출력은 최종 결과가 아니다.
- 출력 검사는 필드 간 일관성까지 본다. 정책 주장인데 source_ids가 비어 있으면 필드가 다 있어도 실패다.
- **사람 검토**는 사후에 붙이지 않고 워크플로 통제로 설계한다. 검토가 불가능하면 진행하지 않음을 평가로 입증한다.

#### 릴리스 게이트와 계획
- 정상 작동이 곧 출시 준비는 아니다. "테스트에서 양호했다" 대신 통과·실패 사례와 미해결 위험을 제시한다.
- 게이트는 진행 조건뿐 아니라 롤아웃을 멈출 **일시 중지 조건**도 명시한다.
- 핵심 질문은 "어떤 증거가 권고를 바꾸는가?"다. 프롬프트나 스키마가 바뀌면 이전 증거가 무효가 될 수 있다.
- 통제는 위험을 없애지 않고 줄이고 관리한다. 계획의 목적은 위험이 없음을 증명하는 것이 아니다.

### 기억할 개념·프레임워크

| 응답 경로 | 언제 쓰나 |
|---|---|
| 응답 | 범위 내이고 근거가 있으며 형식을 충족할 수 있음 |
| 명확화 | 범위 내지만 세부가 누락되거나 모호함 |
| 거부·안전한 완료 | 안전하지 않거나 범위 밖인 요청 |
| 에스컬레이션 | 민감·고위험이라 책임 있는 검토가 필요 |
| 구조화된 실패 반환 | 증거, 권한, 형식 문제로 유효한 결과 불가 |

| 검증 권고 | 사용 조건 |
|---|---|
| 준비 완료 | 동작 증거가 있고 게이트 충족, 차단 결함 없음 |
| 조건부 준비 완료 | 남은 이슈가 제한적이고 담당자가 있으며 통제됨 |
| 출시 전 시정 | 근거 없는 주장, 검토 트리거 누락 등 차단 요인 잔존 |
| 일시 중지 | 필요한 증거, 승인, 검토 책임 미충족 |
| 에스컬레이션 | 보안·법률·정책 등의 문제라 구현 팀 단독 결정 불가 |

- **테스트 케이스 4범주:** 정상, 경계, 실패, 검토 유발.
- **가드레일 6필드:** 경계, 트리거, 점검 위치, 예상 동작, 캡처할 증거, 책임자.
- **통제 매핑:** 위험 → 실패 범주 → 통제와 점검 위치 → 트리거 → 예상 동작 → 책임자와 릴리스 영향.

### 실무 적용 예시
- 접근 정책 API에 "지금 바로 관리자 권한을 달라" → 거부하거나 승인된 접근 요청 절차로 이관한다.
- 계약업체가 제한 데이터 세트 사용을 물음 → needs_review를 켜고 사유와 담당자를 붙여 수동 검토로 보낸다.
- 일반 질문은 통과했지만 저신뢰 답변 1건과 잦은 검토자 재정의 → **내부 시범만 허용**하고 근거 없는 주장이 반복되면 멈춘다.

### 지식 점검 포인트
- 검증 근거가 가장 강한 프롬프트 요구 → **출처 범위, 반환 필드, 명확화 절차를 정의한 요구**.
- 출시 검증에 가장 강한 평가 세트 → **정상, 경계, 검토 유발 사례 등을 섞은 혼합 세트**. 한 위험 영역만 다루면 부족하다.
- 출처 ID 없이 "그럴 가능성이 높다"며 검토도 안 켠 답변 → **차단하거나 검토로 전달**. 형식이 맞아도 동작이 안전하지 않다.
- 민감 사례 2건이 검토 트리거를 놓쳤고 검토 담당자도 미정 → **수정 또는 일시 중지**. 내부 시범이라도 진행할 수 없다.
- 인계에 적합한 계획 → **동작, 평가, 통제에 담당자와 재테스트 트리거까지 담은 계획**.

  <div class="eyebrow">레슨 08 · DevOps, Observability, and Production Readiness for APIs</div>
  <h1 class="lesson-title">API의 DevOps·관측 가능성·프로덕션 준비</h1>
</div>

> **한 줄 요약:** 로컬에서 작동하는 API를 준비 완료로 보지 않고, 환경과 관측 신호, 오류 대응, 책임을 정해 출시 조건을 판단한다.

### 핵심 내용
#### 환경·구성·릴리스 전제 조건
- 로컬 테스트는 요청이 닿고 응답이 온다는 것만 보여준다. 프로덕션은 관찰, 지원, 복구가 가능해야 한다.
- 흔한 함정은 정제된 데이터와 적은 트래픽을 쓰는 스테이징을 "프로덕션과 같다"고 가정하는 것이다.
- 스테이징과 프로덕션은 **별도 OpenAI 프로젝트**로 나누고, 프로젝트별 사용량과 지출 한도를 건다.
- 시크릿은 승인된 절차로 관리하고 코드, 프롬프트, 스크린샷에 넣지 않는다.
- 릴리스 경로는 낙관이 아니라 증거로 정한다. 대상 환경, 승인 담당자, 롤백 담당자, 미해결 차단 요인을 적는다.

#### 비동기 작업과 스티어링 검증
- 비동기 도구 호출을 쓰면 앱 작업 ID와 원본 call_id를 매핑해 지연된 결과가 올바른 호출에 닿게 한다.
- response.steer.accepted는 '적용'이 아니라 '대기열 추가'다. 결과와 후속 처리는 따로 확인한다.
- 스티어링이나 중지는 완료된 작업을 되돌리거나 이미 시작된 앱 도구를 취소하지 않는다.

#### 관측 가능성
- 관측 가능성은 "로그가 있다"가 아니라 출시 후 판단에 쓰는 운영 증거다. 결정으로 이어지는 신호만 고른다.
- **추적**은 한 요청이 거친 모델 호출, 검색, 도구 단계를 이어 실패나 지연 지점을 찾게 한다.
- x-ratelimit-* 응답 헤더로 한도와 잔여 용량을 본다. 정확한 헤더 세트는 구현 전 현행 문서로 확인한다.
- 서버의 x-request-id와 앱의 X-Client-Request-Id를 함께 남기면 응답 헤더가 없는 타임아웃도 추적된다.
- 로그는 많을수록 좋은 게 아니다. 프롬프트 전문, 고객 기록, 자격 증명 없이도 문제 해결이 되게 남긴다.
- **경보**는 즉각 조치가 필요하고 대응 책임자가 있을 때만 쓴다. 저가치 경보가 많으면 중요한 신호를 놓친다.

#### 오류 처리와 지원 책임
- 대응은 오류 무시와 과잉 반응을 모두 피한다. 전면 롤백이 맞을 때도 있지만 유일한 대응은 아니다.
- **재시도**는 재시도 가능 오류에만, 지터를 넣은 유한 지수 백오프로 한다. 실패한 요청도 분당 제한에 포함된다.
- error.code가 misalignment_policy_violation이면 그 대화의 추가 작업을 멈추고, 자동 재시도 없이 담당자에게 넘긴다.
- 검색 소스를 못 쓰면 근거 없는 답을 강행하지 않는다. 한계를 알리고 차선책을 안내한다(점진적 성능 저하).
- 지원 책임이 없으면 문제는 발견만 되고 해결되지 않는다. 주요 신호마다 누가 결정하는지 정한다.

### 기억할 개념·프레임워크

| 환경 | 입증하는 것 | 단독으로 입증 못 하는 것 |
|---|---|---|
| 로컬 | 통제된 환경에서 실행 가능 | 공유 접근, 모니터링, 안전한 배포 |
| 개발 | 팀 공유 환경에서 실행 가능 | 데이터 경계, 릴리스 통제, 운영 소유권 |
| 스테이징 | 프로덕션 유사 환경에서 검증 가능 | 프로덕션 승인, 지원과 롤백 준비 |
| 프로덕션 | 대상 사용자에게 공개 | 여전히 지속 모니터링과 지원이 필요 |

| 체크리스트 질문 | 기록할 핵심 |
|---|---|
| 1. 무엇을 어디서 실행하나? | 환경, 노출 범위, 구성과 시크릿, 사용량 한도 |
| 2. 릴리스 준비 증거는? | 스모크 테스트, 버전 식별자, 승인·롤백 담당자 |
| 3. 릴리스 후 어떻게 파악하나? | 주요 지표, 요청 ID, 경보 트리거, 로깅 금지 데이터 |
| 4. 실패하면 어떻게 되나? | 오류 모드, 제한된 재시도, 롤백·일시 중지 기준 |
| 5. 릴리스 권고는? | 권고, 근거, 차단 요인, 결정을 바꿀 증거 |

- **신호 → 결정 예**
  - 지연 증가 → 원인 조사, 점진적 성능 저하, 롤백
  - 예상치 못한 비용 증가 → 사용 제한, 모델과 기능 재검토
  - 릴리스 후 오류 급증 → 롤백, 확장 중지
- **릴리스 권고 5종:** 준비 완료, 조건부 준비 완료, 출시 전 수정, 일시 중지 또는 이관, 롤백 또는 확장 일시 중지.

### 실무 적용 예시
- 계정 지원 API가 스테이징을 통과했지만 롤백 검증과 비용 가시성이 없음 → "스테이징 통과 = 파일럿 준비"로 보지 않고 차단 요인을 명시한다.
- "API를 모니터링하겠다"는 계획 → 무엇을 보고 누가 대응할지 없어 부실하다. 신호마다 1차 대응과 결정권자를 정한다.
- 현장 서비스 API에 지연, 조회 실패, 할당량 근접이 겹침 → 점진적 성능 저하와 확장 일시 중지를 먼저 하고, 릴리스가 원인으로 확인되면 롤백한다.

### 지식 점검 포인트
- 스테이징은 잘 되지만 릴리스 식별자, 데이터 경계, 승인자가 없음 → **파일럿 노출 전에 누락된 증거를 보완**한다.
- 접속은 되지만 검색이 간헐적으로 실패해 출처 없는 답을 냄 → **점진적 성능 저하, 확장 일시 중지, 검색 오류 해결**.
- 스모크 테스트만 통과하고 롤백 경로 없이 200명 출시 예정 → **출시 전 시정 필요**. 아직 출시 전이라 롤백은 답이 아니다.
- 릴리스·버전 식별자의 역할 → **관찰된 현상이 어느 배포 버전과 구성에서 났는지 알려준다**.

  <h1 class="lesson-title">실시간·음성·멀티모달 API 경험</h1>

> **한 줄 요약:** 음성과 이미지, 실시간을 "진보돼 보여서" 고르지 않고, 워크플로를 안전하게 충족하는 가장 단순한 모달리티를 고른다.

### 핵심 내용
#### 다중 모달이 필요한 시점
- 모달리티 선택은 워크플로 요구에서 출발한다. "음성을 넣자"부터 시작하는 것이 흔한 실수다.
- 비텍스트는 입력이 어렵거나, 핸즈프리가 필요하거나, 시각 증거에 의존할 때 유용하다.
- 검토와 감사 가능성이 중요하거나 미디어 동의가 미해결이면 텍스트가 더 안전한 기본값이다.
- 결정 기준은 **워크플로 요구를 안전하게 충족하는 가장 단순한 모달리티**다.

#### 패턴별 판단 기준
- 실시간은 "빨리 답한다"가 아니라 끼어들기, 수정, 도구 지연 중 안내까지 설계한 패턴이다.
- **STT** 전사본은 검토 가능하지만 자동으로 정확하지 않다. 이름, 날짜, 수량에는 확인 절차를 둔다.
- TTS로 전한 약관, 가격, 확인 번호 같은 중요 세부는 텍스트로도 제공한다.
- 이미지 입력은 증거로 쓰되 고위험 결정의 유일한 근거로 삼지 않는다.
- 이미지 출력은 기본 보강 수단이 아니다. 구조화 텍스트가 더 안전한 첫 버전일 수 있다.

#### 상호작용 흐름과 사용자 제어
- 흐름은 다른 팀이 테스트할 만큼 구체적으로 쓴다. "사용자가 도움을 요청한다"는 너무 모호하다.
- 사용자는 일시 정지, 사진 교체, 잘못 들은 내용 수정, 텍스트 전환을 할 수 있어야 한다.
- 예약 변경, 청구 접수 같은 **중대한 조치**는 승인된 워크플로와 필요한 확인이 있을 때만 한다.
- 폴백은 "[조건]이면 [안전한 조치]를 하고 사용자는 [다음 조치]를 할 수 있다" 문형으로 쓴다.
- 폴백과 이관은 실패 후 즉흥 처리하지 않고 상호작용 로직에 미리 넣는다.

#### 안전·개인정보·접근성·관측 가능성
- 비텍스트는 입력이 불완전해도 설득력 있게 느껴져 위험을 키운다. 프로토타입과 파일럿 전에 점검한다.
- 안전 확인은 모든 단계가 아니라 위험과 비즈니스 영향이 커지는 지점에 둔다.
- 사진 배경이나 녹음 속 타인처럼 다중 모달은 요청 이상의 정보를 담는다. 캡처 전 동의와 보존 규칙을 정한다.
- 접근성은 특정 모달리티를 강요하지 않는 것이다. 음성에는 텍스트 대안, 이미지에는 비시각적 대안을 준다.
- API에 접속돼도 오인식이나 과도한 폴백으로 경험은 실패할 수 있다. 모달리티별 신호를 따로 본다.

### 기억할 개념·프레임워크

| 구분 | 선택지 | 맞는 경우 |
|---|---|---|
| 아키텍처 | 실시간 음성-음성 | 저지연 대화, 끼어들기, 실시간 도구 사용 |
| 아키텍처 | 연쇄 파이프라인 (STT→텍스트 에이전트→TTS) | 중간 텍스트, 영구 대본, 결정론적 확인이 필요 |
| 연결 | WebRTC | 브라우저나 모바일이 오디오를 직접 캡처·재생 |
| 연결 | WebSocket | 서버가 미디어 파이프라인의 원시 오디오를 받음 |
| 연결 | SIP | 전화 음성 에이전트 (번역·전사는 모델 지원 확인) |

연결 방식과 지원 동작은 바뀔 수 있으니 구현 직전 최신 OpenAI 문서를 확인한다.

| 상황 | 더 안전한 대응 |
|---|---|
| 명확하고 저위험인 범위 내 요청 | 승인된 워크플로로 정상 대응 |
| 불완전하거나 저신뢰인 입력 | 계속하기 전에 명확화 질문 |
| 고객, 기록, 비즈니스 결정에 영향 | 확인이나 사람 검토, 또는 둘 다 |
| 승인 워크플로 밖이거나 안전하지 않음 | 거절하거나 허용 정보만 제공 |
| 여전히 민감하거나 미해결 | 승인된 담당자에게 에스컬레이션 |

- **음성 상호작용 3패턴**
  - 음성-동작: 말한 요청을 도구로 처리한다. 민감하거나 되돌릴 수 없는 작업 전에는 확인한다.
  - 시스템-음성: 시스템 맥락을 음성 알림으로 전한다. 도움과 방해를 구분한다.
  - 음성-음성: 실시간 번역처럼 음성 상호작용이 이어진다.
- **공통 안전장치:** TTS 음성은 사람이 아닌 AI 생성임을 명확히 알린다.
- **청사진 6질문:** 사용자 상황, 적합한 모달리티, 상호작용 진행, 통제와 안전장치, 검증과 모니터링, 권고.

### 실무 적용 예시
- 여행 차질 앱에 "음성이 자연스러우니 음성 비서를" → 긴급 알림은 음성, 최종 여정과 예약 번호는 텍스트인 혼합형을 권한다.
- 항공사 재예약 어시스턴트 → 옵션 비교는 돕되, 선택안을 텍스트로 요약해 확인받기 전에는 예약을 바꾸지 않는다.
- 사진과 음성으로 보험 청구 접수 → 타당한 사례지만 동의·보존 규칙 등이 정해지기 전에는 합성 데이터로 제한적 프로토타입만 한다.

### 지식 점검 포인트
- 음성·이미지를 원하지만 텍스트 양식으로 충분하고 동의·보존 규칙이 미승인 → **첫 시범은 텍스트, 다중 모달은 보류**.
- 현장 지원 흐름에 중단, 수정, 텍스트 전환 방법이 없음 → **사용자 제어와 에스컬레이션 지점 누락**이 문제다.
- 청구 조정이 가능한 음성 비서에 확인 절차, 상담원 연결, 전사 오류 추적이 없음 → **이것들이 정의될 때까지 시범을 제한**한다.
- 바쁜 카운터의 손상품 반품 도우미 → **음성, 이미지, 서면 확인에 폴백과 상급자 보고를 더한다**.
- 음성 통화를 편집 가능한 텍스트로 남기려 함 → **STT**가 맞는 패턴이다.

> **한 줄 요약:** Deep Research·이미지·디스틸레이션 같은 특화 패턴은 표준 패턴으로 부족하다는 근거가 있을 때만 고르고, 적합성 평가로 권고한다.

### 핵심 내용
#### 특화 패턴을 대하는 태도
- 특화 API 패턴은 워크플로가 정말 필요로 할 때만 가치가 있다.
- 특화 패턴에는 검증 부담과 운영 복잡성, 데이터·권리 문제가 함께 따라온다.
- **표준 패턴**은 '기본적'이라는 뜻이 아니라 특화 기능 없이 구현할 수 있다는 뜻이다.
  - 예: 구조화 출력, 검색 기반 응답, 에이전트형 워크플로
- 이 레슨이 다루는 특화 패턴은 Deep Research, 이미지 이해, 이미지 생성·편집, 디스틸레이션, 최적화다.

#### Deep Research 워크플로
- Deep Research는 단순 모델 호출이 아니라 Responses API로 구축하는 **통제된 워크플로**다.
- 요청에는 승인된 데이터 소스가 최소 하나 있어야 한다.
  - 소스: 웹 검색, 벡터 스토어 파일 검색, search와 fetch를 구현한 원격 MCP 서버
  - 분석용 코드 인터프리터는 더할 수 있지만, 함수 호출 등 기타 도구는 지원되지 않는다.
- 작업이 수십 분 걸릴 수 있어 백그라운드 모드, 완료 감지, 도구 호출 한도를 정한다.
- 백그라운드 모드는 응답 데이터를 약 10분 보관해 Zero Data Retention(ZDR)과 호환되지 않는다.
- ZDR이 필요하면 백그라운드 모드를 끄고 더 긴 요청 타임아웃을 쓴다.
- 승인된 정책 출처 하나로 답할 수 있는 문의라면 검색 기반 응답으로 충분하다.
- Deep Research는 여러 출처를 종합하고 증거를 비교하며 불확실성을 표시해야 할 때 관련성이 커진다.
- 더 큰 위험은 모델 오류보다 **불확실성을 숨긴 확신에 찬 종합**이다.
- 출처가 상충하면 하나를 골라 사실처럼 쓰지 않고, 상충을 표시해 검토자에게 넘긴다.
- 안전한 실패를 정의한다. 예: "출처 간 상충이 있어 사람 검토가 필요합니다."

#### 이미지 이해·생성·편집
- 질문은 "이미지를 쓸 수 있나?"가 아니라 "이미지가 워크플로에서 어떤 역할을 하나?"다.
- 체크리스트나 텍스트 요약으로 더 낮은 위험에 같은 결과를 낸다면 시각 워크플로는 타당하지 않다.
- **표면 선택**은 목적에 따라 나눈다.
  - 이미지 이해·분석: 이미지 입력이 포함된 Responses API 흐름
  - 직접 생성·편집: Images API
  - 대화형·다단계 생성: Responses API 이미지 생성 도구
- 이해와 생성이 모두 필요하면 단계를 나누고, 단계 사이의 인계와 검토 통제를 정한다.
- 권리와 승인된 사용이 특히 중요하고, 접근성(대체 텍스트 등)은 처음부터 설계에 넣는다.
- 앱이 **생성 전과 후 모두** 경계를 강제한다. 전에는 요청 허용 여부, 후에는 저장·게시 가능 여부다.
- 검증은 "괜찮아 보인다"가 아니라 구체적인 기준이어야 한다.

#### 디스틸레이션·최적화
- 디스틸레이션과 최적화는 품질·비용·지연 문제의 첫 해결책이 아니다.
- 많은 '맞춤화 문제'는 실은 불명확한 프롬프트나 느슨한 출력 계약 같은 설계 문제다.
- 결정 규칙: 현재 패턴이 정의·테스트되고 더 단순한 통제로 개선될 때까지 하지 않는다.
- **디스틸레이션**은 강한 '교사'의 동작으로 작고 빠른 '학생'을 지원해 비용과 지연을 바꾼다.
- 원래 워크플로가 불안정하면 취약한 솔루션의 더 싼 버전만 생긴다.
- 학생이 더 빠르고 싸도 품질 임계값을 넘지 못하면 수용하지 않는다.
- **최적화**는 모델, 프롬프트, 검색 전략 등 워크플로 전반의 설계를 조정하는 더 넓은 개념이다.
- "더 빠르게" 대신 "라우팅 정확도를 유지하며 평균 지연을 줄인다"처럼 검증 가능한 목표를 쓴다.
- 최적화는 관측 가능성에 달려 있다. 릴리스 버전, 지연, 품질 상태 등을 기록해 버전을 비교한다.
- 파인튜닝은 새 워크플로의 기본 최적화 경로가 아니며, 논의 전 자격과 최신 공식 지침을 확인한다.
- 운영 루프 책임자가 없는 최적화 패턴은 고객 배포 준비가 안 된 것이다.

#### 적합성 평가로 종합
- 평가는 기능 소개가 아니라 의사결정 자료다.
- 권고는 **적합성과 준비 상태를 구분**한다. 타당한 패턴도 아직 준비가 안 됐을 수 있다.
- "아직은 아니오"라는 권고에도 결정을 바꿀 근거를 적어 논의가 이어지게 한다.
- 고객이 고급 기능을 요청하면 워크플로부터 시작해 더 간단한 대안을 배제한 뒤 결정한다.

### 기억할 개념·프레임워크

**최적화 경로 선택 (가장 낮은 복잡도부터)**

| 문제 | 먼저 고려 | 디스틸레이션·심층 최적화는 이때만 |
|---|---|---|
| 출력 불일치 | 프롬프트, 출력 계약, 구조화 출력 | 단순 통제로 부족하고 평가 기준이 있을 때 |
| 검색 성능 저조 | 소스 품질, 메타데이터, 검색 필터 | 검색은 검증됐으나 비용·지연이 걸림돌일 때 |
| 지연 과다 | 모델 재검토, 불필요한 단계 축소 | 품질이 허용 수준이고 지연 목표가 있을 때 |
| 비용 과다 | 컨텍스트 크기, 도구 호출, 중복 작업 | 동작이 정상이고 품질을 유지해야 할 때 |

**권고 범주 5**

| 범주 | 사용 시점 |
|---|---|
| 표준 패턴으로 충분 | 표준 패턴이 더 낮은 위험으로 요구 충족 |
| 조건부 특화 | 근거는 있으나 검증·거버넌스 조건 필요 |
| 근거 확보까지 보류 | 유용할 수 있으나 핵심 근거 부족 |
| 일시 중지·상급 이관 | 보안·법무 등 전문가 검토가 필요한 위험 |
| 불필요한 특화 거부 | 실제 요구를 못 풀거나 복잡성만 추가 |

- 디스틸레이션 전에 명시할 것: 유지할 동작, 성공 측정, 허용 품질 저하, 유지보수 책임자

### 실무 적용 예시
- **금융 주간 리스크 브리핑:** 규제와 내부 정책을 종합해야 한다 → 승인 출처와 분석가 검토를 갖춘 제한 프로토타입으로 시작한다.
- **소매 이미지 워크플로:** 제품 시각 초안과 사진 품질 분석을 원한다 → 내부 초안과 시각 QA에만 쓰고 자동 게시는 금지한다.
- **티켓 분류 비용 압박:** 일부 범주 오류와 비용 증가가 있다 → 범주와 구조화 출력부터 고치고, 품질이 안정된 뒤 디스틸레이션을 평가한다.

### 지식 점검 포인트
- 경영진 브리핑용 연구 워크플로에 승인 출처와 검토자가 미정 → **출처·검토 책임자가 정해질 때까지 보류**
  - 통제 없는 종합은 권위 있어 보여도 증거 공백을 숨긴다.
- 고객용 제품 이미지 자동 생성인데 권리·브랜드 검토가 미확인 → **승인 절차가 정해질 때까지 내부 초안만 사용**
- 범주가 겹치고 평가 기준이 없는데 즉시 최적화를 원함 → **범주와 출력 계약을 고치고, 평가 기준과 비용·지연 기준선을 갖춘 뒤 재검토**
  - 지금 디스틸레이션하면 취약한 동작까지 복제한다.
- 연구, 시각 초안, 지역 요약을 묶은 '고급 API 솔루션' → **워크플로별로 나눠 가장 간단하고 안전한 패턴 적용**

> **한 줄 요약:** "스테이징에서 잘 되니 릴리스해도 될까요?"라는 Northstar Retail Group 사례에서 격차를 진단하고 '출시 전 수정'을 권고한다.

### 핵심 내용
#### 사례와 현재 증거 검토
- 이 실습의 핵심은 코드 작성이 아니라 **배포 판단**이다.
- 사례를 읽을 때 확인된 증거, 합리적 가정, 미해결 질문을 구분한다.
- 피할 실수는 두 가지다. 작동하는 스테이징 API를 배포 준비로 보는 것, 누락마다 전면 재설계를 주장하는 것이다.
- Northstar는 가상의 글로벌 소매업체로, 승인 문서로 사내 정책 질문에 답하는 내부 '직원 정책 API'를 시범 운영하려 한다.
- 바쁜 인사·복리후생 기간 전에 시범을 열라는 경영진 압박이 있다.
- 올바른 질문은 "통제가 확인되면 제한된 파일럿 그룹에 안전하게 공개할 수 있나?"다.

#### 아키텍처·계약·선정 격차
- 요청은 question, user_id, user_role, region, channel이고, 응답은 answer, 출처 제목, confidence_label, 다음 단계다.
- confidence_label은 보정된 신뢰도 점수가 아니다. 누가 어떤 근거로 붙이고 어떤 조치가 따르는지 정해야 한다.
- 첫 릴리스에는 HR 티켓 생성이나 기록 업데이트 같은 실제 조치 기능이 없다.
- 검색 기반 정책 응답 패턴 자체는 일상 셀프 서비스에 맞다.
- 문제는 정책 콘텐츠가 누락·구식·제한일 때의 동작이 정의되지 않았다는 점이다.
- **계약**은 정상 응답과 정책별 오류 사례의 기대 동작이 정의될 때까지 완성된 것이 아니다.
- 실시간 음성, 시각, 연구형 같은 특화 패턴은 현재 증거로 정당화되지 않는다.
- 향후 티켓 생성은 별도 도구 워크플로로 다루고 첫 출시 권고에서 뺀다.

#### 보안·데이터·거버넌스 격차
- 질문은 "응답할 수 있나?"가 아니라 "올바른 소스로, 올바른 사용자에게, 안전하게 응답하나?"다.
- API는 호출 앱이 준 user_role과 region을 그대로 신뢰한다.
- 로그에 요청 본문, 사용자 ID, 검색 스니펫, 생성 답변이 남지만 마스킹과 보존 기간이 확인되지 않았다.
- 배포 승인, 보안 승인, 지원 책임의 주체가 모두 명시되지는 않았다.
- **내부 API라고 저위험이 아니다.** 직원 신원과 제한된 인사 콘텐츠를 다룰 수 있다.
- 인증만으로는 권한 부여나 권한을 고려한 검색이 증명되지 않는다.
- 소스 거버넌스는 릴리스 통제 수단이다. "문서가 있으니 써도 된다"고 가정하지 않는다.

#### 검증·관측 가능성·운영 준비 격차
- 42개 테스트 중 일반 일상 질문 35개는 통과했다.
- 모호한 질문 4개는 대체 동작이 일관되지 않았다.
- 제한·지역별 사례 3개는 대체 처리나 상급 보고를 해야 할 상황에 답을 냈다.
- 관리자 전용 정책, 노사 관계 콘텐츠, 누락·구식·상충 소스에 대한 테스트는 없다.
- 관측 신호는 상태 점검, 요청 수, 지연뿐이다. 폴백이나 검색 실패율 신호가 없다.
- 정책 API는 **눈에 띄지 않게 오작동**할 수 있다. 상태 점검은 답이 정확한지 알려주지 않는다.
- 지원 담당자가 없으면 공개 결과에 책임질 사람이 없다. 인계 공백도 기술 공백만큼 중요하다.

#### 배포 준비 권고
- 권고는 야망이 아니라 증거에 기반한다. 특화 패턴 추가는 장애를 풀지 못하고 복잡성만 늘린다.
- 이 API는 실패한 것도, 출시 준비된 것도 아니다.
- **권고는 '출시 전 수정'이다.** 차단 요인이 해결될 때까지 파일럿 사용자에게 노출하지 않는다.
- 확신, 긴급성, 성공적인 데모만으로는 진행하지 않는다.
- 차단 요인이 책임자와 함께 해결되면 '조건부 진행'으로 바뀔 수 있다.
- 제한 소스나 로깅 문제를 실무 팀이 풀 수 없으면 '검토를 위한 이관'으로 바뀐다.

### 기억할 개념·프레임워크

**계약 격차와 개선 방안 (발췌)**

| 정책 사례 | 위험 | 가능한 계약 개선 |
|---|---|---|
| 출처 없음 | 추측으로 응답 | missing_source 오류 사유와 대체 경로 |
| 오래된 출처 | 구식 정책 기반 답변 | source_status, source_version |
| 지역별 정책 | 잘못된 지역 지침 | region_scope와 누락 시 동작 |
| 제한 콘텐츠 | 민감 인사 내용 노출 | restricted_content, escalation_required |
| 지원되지 않는 질문 | 승인 워크플로 밖 응답 | unsupported_request와 안전한 설명 |

**의사결정 기준 5 (Northstar 적용)**

| 결정 | 언제 | Northstar |
|---|---|---|
| 진행 | 필요한 증거가 있고 차단 요인 없음 | 아님 |
| 조건부 진행 | 남은 격차가 제한적이고 책임이 명확 | 아직 아님 |
| 출시 전 수정 | 사용자 노출 전에 차단 문제 해결 필요 | 현재 가장 강한 방향 |
| 일시 중지·재설계 | 설계가 워크플로에 맞지 않음 | 해당 없음 |
| 검토를 위한 이관 | 위험이 팀 권한을 넘음 | 실무 팀이 풀 수 없을 때 |

- 릴리스 게이트 9개(평가 범위, 로그 통제, 지원 경로 등)는 모두 미완료이거나 일부만 충족됐다.

### 실무 적용 예시
- **HR 직원 핸드북 v4.1:** 승인된 현행 소스다 → 시범 범위에 포함한다.
- **2026년 복리후생 가입 안내서:** 미국만 승인, 캐나다는 검토 중, 영국은 불분명하다 → 승인 지역 버전만 쓰고 나머지는 답하지 않는다.
- **직원 관계 조사 절차:** 제한 소스다 → 검색에서 제외하거나 권한을 제한하고, 인사 법무 경로로 이관한다.

### 지식 점검 포인트
- 사례에서 확인된 증거 → **스테이징 상태 점검과 일반 질문용 정책 응답 엔드포인트가 있다**
  - 최종 운영 승인이나 로깅 통제는 사례에 없는 주장이다.
- 파일럿 공개에 가장 직접 영향을 주는 설계 문제 → **누락·구식·제한 콘텐츠 등의 동작이 계약에 없음**
- 무조건적 파일럿을 가장 강하게 막는 기업 차원 장애 → **직원 데이터에 대한 로깅 통제 미확인**
- 일반 질문은 되지만 위험 사례 검증과 지원 담당자가 없음 → **출시 전 수정**
  - 핵심 워크플로는 유용해 재설계는 과하다.
- 최종 권고 → **차단 요인별 책임자를 지정하고 출시 전에 수정**
