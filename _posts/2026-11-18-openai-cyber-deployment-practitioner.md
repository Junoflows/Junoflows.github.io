### 통합 최종 정리 — OpenAI 사이버 배포 실무자

#### 요약
OpenAI 사이버 배포 실무자는 "보안 경보를 더 많이"가 아니라 "검토 가능한 결정을 더 정확하게"로 대화를 바꾸는 과정이다. Codex Security를 보안 신호를 검증된 증거와 검토 가능한 수정으로 바꾸는 워크플로 계층으로 보고, 가장 좁은 패턴을 고르는 데서 시작한다(1강).

고객의 관심은 "전부 테스트해 보자"가 아니라, 승인된 대상 하나와 검토자, 품질 스코어카드를 갖춘 범위 지정 평가로 바꾼다(2강). 거버넌스는 장애물이 아니라 운영 모델 자체이며, 6가지 질문으로 승인부터 다음 단계까지 점검한다(3강).

결과는 활동량이 아니라 범위와 증거에 묶인 가치 신호로 정리해 CISO가 받아들일 경영진 보고로 만든다(4강). 마지막으로 Harborline Bank 사례와 Northstar Financial 랩에서 넓은 요청을 증거 기반 다음 조치로 바꾸는 과정을 연습한다(5·6강).

#### 과정 전체 흐름
```
[1강] 보안 신호 → 증거 경계 → 가장 좁은 패턴 → 워크플로 요약
   │
   ├─▶ [2강] 첫 대상 → 평가 헌장 → 품질 스코어카드 → 고객 권고안
   ├─▶ [3강] 6가지 질문 → 접근·작업 경계 → 증거와 기록 → 다음 단계
   ├─▶ [4강] 가치 신호 → 가치 스토리 → 8요소 경영진 보고
   ├─▶ [5강] Harborline: 신호 → 진단 → 패턴 → 평가 → 증거 보정 → 권고안
   └─▶ [6강] Northstar 랩: 넓은 요청 → 인증 PR 1건 검토 → 한 페이지 권고안
```

#### 강의별 핵심
- **1강 Codex 보안 워크플로 패턴:** 승인 범위와 증거 상한선, 검토자를 먼저 확인하고 네 가지 패턴 중 가장 좁은 것을 고른다.
- **2강 범위 지정 평가와 시범 운영 설계:** 안전한 첫 대상 하나를 고르고, 발견 건수가 아닌 결정 품질로 다음 단계를 권고한다.
- **3강 사이버 거버넌스와 운영 모델:** 6가지 운영 모델 질문으로 준비 상태를 점검하고 진행, 일시 중지, 에스컬레이션, 확장을 정한다.
- **4강 사이버 가치 스토리와 경영진 보고:** 활동량과 가치 증명을 구분하고, 증거가 뒷받침하는 가치 신호로 8요소 경영진 보고를 쓴다.
- **5강 사이버 응용 실습:** Harborline의 넓은 요청을 권한 관련 PR의 코드 변경 검토로 좁히고, 발견 사항을 후보로 보정해 권고한다.
- **6강 사이버 랩 노스스타 파이낸셜:** "모든 리포지토리 자동 수정" 요청을 인증 PR 1건의 읽기 전용 검토로 좁혀 한 페이지 권고안을 쓴다.

#### 강의를 잇는 연결 고리

| 개념 | 패턴·평가(1–2강) | 거버넌스(3강) | 가치(4강) | 적용(5–6강) |
|---|---|---|---|---|
| 출발점 | 보안 신호와 고객 작업 | 6가지 운영 모델 질문 | 기술적 워크플로 결과 | 고객의 넓은 요청 |
| 기본 원칙 | 가장 좁은 패턴, 대상 하나 | 거버넌스가 곧 운영 모델 | 활동량이 아닌 결정 품질 | 요청은 결론이 아닌 신호 |
| 증거 | 증거 수준과 발견 상태 | 증거 보존과 기록 시스템 | 가치 신호와 증명 공백 | 근거, 추론, 미입증 구분 |
| 통제 | 승인 범위, 증거 상한선 | 접근·작업 경계, 데이터 처리 | 과장 없는 표현 | 읽기 전용, 사람의 승인 |
| 산출물 | 워크플로 요약, 평가 헌장 | 준비 상태 판단 | 가치 스토리, 경영진 보고 | 파트너 안전 권고안 |

#### 실무 체크리스트
- ☐ 넓은 요청을 결론이 아니라 신호로 받고, 병목과 결정권자를 먼저 확인했는가
- ☐ 승인된 범위, 고객 소유 자산, 승인 환경을 확인하고 범위 밖 항목을 명시했는가
- ☐ 고객 작업에 맞는 가장 좁은 Codex Security 워크플로 패턴을 골랐는가
- ☐ 첫 평가 대상을 하나로 좁히고, 검토자와 증거 경계를 평가 헌장에 적었는가
- ☐ 성공 지표가 발견 건수가 아니라 결정 품질과 검토 부담을 재는가
- ☐ 접근 권한과 작업 경계, 데이터 처리 규칙이 정해졌는가
- ☐ 증거를 출처 사실, 뒷받침되는 추론, 런타임 증명, 증명 공백으로 나눠 표현했는가
- ☐ 발견 사항을 후보와 검증됨으로 구분하고, 확정 판단은 고객 검토자에게 남겼는가
- ☐ 결정과 근거가 고객의 기록 시스템에 남는가
- ☐ 가치 신호가 범위와 증거에 묶여 있고, 증명 공백을 함께 밝혔는가
- ☐ 다음 조치마다 담당자가 있고, 자동화나 보안 결과를 약속하지 않았는가

> **한 줄 요약:** Codex Security를 보안 신호를 검증된 증거와 검토 가능한 수정으로 바꾸는 워크플로 계층으로 설명하고, 범위와 검토자를 먼저 정해 가장 좁은 패턴을 고른다.

### 핵심 내용
#### 방어적 워크플로에서 Codex Security의 역할
- Codex Security는 **Daybreak**의 일부로, 승인된 팀이 지정 범위의 코드를 분석하고 발견 사항을 검증하도록 돕는다.
- 인터페이스는 로컬 Codex 태스크의 플러그인과, Codex 클라우드에 연결된 GitHub 저장소를 스캔하는 클라우드 두 가지다.
- "스캔해 주나", "백로그를 해결해 주나"는 결정이 아니라 신호다. 승인된 방어 워크플로를 먼저 정하고 패턴을 고른다.
- 가치는 경보의 양이 아니라 **결정 품질**에 있다. 경고는 업무를 만들고 증거는 결정을 뒷받침한다.
- "더 많은 취약점을 찾는다"는 약한 포지셔닝이다. 증거로 뒷받침되는 발견을 가려 검토자의 다음 단계를 돕는다고 말한다.
- 위험도 판단, PR 승인, 릴리스 결정, 기록 시스템 업데이트는 여전히 고객 팀 책임이다.
- 고객에게는 증거 준비와 수정 지원은 돕지만, 무엇을 수용하고 병합할지는 귀사 팀이 결정한다고 말한다.
- 스캐너나 AppSec 팀의 대체, 모든 취약점 발견 보증, 자동 병합·배포·종결 시스템이 아니다.

#### 리포지토리 컨텍스트와 증거 경계
- **증거 경계**는 승인된 범위와 허용 활동에 따라 조사하고 주장할 수 있는 범위다.
- **증거 상한선**은 정직하게 주장할 수 있는 최고 증명 수준이다. 런타임 테스트가 미승인이면 런타임 증명은 주장하지 않는다.
- 컨텍스트는 무제한 접근이 아니라 승인된 작업에 필요한 자료다. PR 검토라면 변경 파일, 관련 헬퍼, 테스트면 된다.
- 컨텍스트, 에이전트 기반 런타임, 가시성의 세 계층에서 실행 위치와 증거, 검토자를 묻는다. 답이 불명확하면 아직 준비 전이다.
- 모델 성능이 좋아져도 승인 범위가 넓어지거나 승인 요건이 사라지지 않는다.
- "고객 포털을 스캔해 달라"로는 부족하다. 저장소, 브랜치, 모듈, 검토자, 제외 대상까지 정해야 패턴을 고를 수 있다.
- 후보 단계에서 "취약점을 발견했다"고 말하지 않는다. 확인, 추론, 미입증을 구분하는 **증거 보정**이 핵심 습관이다.

#### Codex Security 평가 라이프사이클
- "도구가 찾았다"에서 "해결됐다"로 건너뛰지 않게 하는 6단계 경로다. 모든 단계를 한 번에 거치지는 않는다.
- **위협 모델**은 신뢰할 수 없는 입력, 인증 적용 위치, 민감 데이터를 밝혀 위험이 큰 곳에 검토를 집중시킨다.
- 검증은 실제 존재, 도달 가능성, 기존 통제의 완화 여부, 증거의 강도를 묻는다.
- 공격 경로 분석은 시작점과 전제 조건을 설명해 실제 위험을 잡음, 오탐, 추가 증거 필요 항목과 구분한다.
- 보고서는 자동 티켓 대기열이 아니라 범위, 결과, 증거, 미비 사항, 다음 조치를 담은 **증거 패키지**다.
- "권한 부여 취약점 발견, 즉시 수정"보다 소스 증거와 의심 근거, 권장 검토를 함께 적은 보고가 훨씬 유용하다.
- "패치가 제안됐다"는 "해결됐다"가 아니다. 고객의 검토, 테스트, 승인, 기록이 뒷받침해야 종결이다.

#### 적합한 워크플로 패턴 선택
- 가장 안전한 패턴은 대개 작업에 딱 맞는 **가장 좁은 패턴**이다. 패턴 선택은 곧 범위 결정이다.
- 보안 스캔 실행은 범위 지정 저장소의 첫 체계적 검토에 맞고, 후보 발견과 우선순위, 증거 미비를 낸다.
- 심층 보안 스캔을 기본 대응으로 쓰면 검토 부담만 늘어난다. 검토자 처리 용량을 먼저 확인한다.
  - 중요·민감 시스템에 쓰되, 지정 검토자와 검토 시간, '충분한 증거'의 기준을 먼저 합의한다.
- 보안 민감 PR에는 보안 측면의 코드 변경 사항 검토가 가장 좁고 책임 있는 패턴인 경우가 많다.
- 발견 사항 수정 및 검증은 검토자가 시정을 수락한 뒤에만 쓴다. 막연한 우려나 검토 안 된 스캐너 출력은 시작점이 아니다.
- **회귀 테스트 증거는 보안 증명이 아니다.** 원래 문제가 더 이상 재현되지 않는다는 증거가 따로 필요하다.
- 패턴은 이유와 함께 말한다(예: 저장소 전체가 아니라 특정 권한 변경의 병합 전 검토라서).
- 플러그인은 이 밖에 기존 발견 사항의 백로그 분류와, 발견 사항 내보내기 또는 추적도 제공한다.

#### 검토 가능한 시정과 고객 안전 인계
- **범위가 제한된 수정**은 리팩토링이나 무관한 변경 없이 특정 발견 사항만 해결하는 표적 변경이다.
- 현대화 프로젝트, 다중 저장소 자동 수정, 보호 브랜치 무검토 커밋이 되어서는 안 된다.
- 재검증은 근본 원인 해결, 원래 공격 경로의 잔존, 정상 동작 유지, 미입증 가정을 확인한다.
- "Codex에 의해 수정됨"이 아니라 무엇이 바뀌고 누가 결정했으며 무엇이 미검증인지 밝힌다.
  - 예: 엔지니어링이 최소 패치를 승인했고 하위 환경 권한 테스트는 통과, 프로덕션 동작은 미테스트.
- Codex Security는 변경 파일, 추가 테스트, 잔여 위험을 요약해 PR 준비를 돕는다. 병합과 릴리스는 인간 검토자가 정한다.
- "취약점을 수정했다", "병합해도 안전" 대신 "검토 가능한 패치 제안서를 작성했다"처럼 말한다.
- 좋은 인계는 승인 범위, 선택 패턴, 책임 검토자, 증거 기준, 다음 단계를 과장 없이 밝힌다.
- 대상, 검토자, 허용 런타임 활동, 증거 상한선 중 하나라도 불분명하면 멈추고 명확히 한다.
- 실제 대상 테스트, 익스플로잇 위주 작업, 특수 모델 접근, 가격 약정은 지원 요청이나 이관 대상이다.

### 기억할 개념·프레임워크

| 증거 수준 | 의미 |
|---|---|
| 출처 사실 | 코드, 구성, 로그, 스캐너 결과에서 직접 확인 |
| 뒷받침되는 추론 | 출처 사실에서 도출한 합리적 결론 |
| 런타임 증명 | 명시 승인된 런타임 테스트에서 관찰 |
| 지원되지 않는 주장 | 가용 증거 범위를 벗어난 진술 |
| 증명 공백 | 아직 미입증, 추가 증거와 검토 필요 |

| 패턴 | 사용 시점 | 주요 제한 |
|---|---|---|
| 보안 스캔 실행 | 승인된 저장소나 폴더의 초기·정기 검토 | 범위를 명확히 제한, 검토자 주도 |
| 심층 보안 스캔 실행 | 표준 스캔 후 같은 범위의 더 철저한 검토 | 검토자 처리 능력과 실질 위험 확인 |
| 보안 측면의 코드 변경 사항 검토 | PR, 브랜치, 커밋의 병합 전 회귀 검토 | 승인된 테스트 없이 런타임 검증 주장 금지 |
| 발견 사항 수정 및 검증 | 검토자가 범위 내 시정을 수락한 뒤 | 제안된 수정을 승인된 시정으로 간주 금지 |

- **고객 대화용 4가지 업무:** 코드 컨텍스트 이해, 증거가 발견을 뒷받침하는지 테스트, 검토용 결정 정리, 준비된 발견의 수정 지원.
- **발견 사항 상태:** 후보, 검증됨, 오탐, 억제됨, 미해결 증명 격차를 섞지 않는다.
- **라이프사이클 6단계:** 위협 모델 → 취약점 발견 → 검증과 공격 경로 분석 → 증거 패키지 보고 → 시정 지원 → 재검증과 처리.
- **처리 결과 7종:** 확인 및 수정 완료, 확인되었으나 미수정, 오탐, 기존 통제로 완화, 증거 부족으로 차단, 보류, 상급 이관.
- **패턴 선택 4질문:** 대상은 무엇인가, 시기는 언제인가, 어떤 증거가 필요한가, 시정 준비가 됐는가.
- **워크플로 요약 5질문:** 무엇을 검토하나, 어떤 패턴이 맞나, 책임 주체는, 무엇을 입증할 수 있나, 다음 단계는.

### 실무 적용 예시
- 지역 금융사가 스캐너 발견의 악용 가능성을 몰라 개발자가 티켓을 미룸 → 스캐너 교체가 아니라 의사 결정 병목을 다룬다.
  - 기존 스캐너 출력과 리포지토리 컨텍스트로 원시 신호를 검토 가능한 결정으로 바꾼다.
- 런타임 테스트가 제외된 핀테크 인증 PR 검토 → requireExportRole() 호출 제거는 출처 사실로 적는다.
  - 내보내기 권한이 세션 검증에만 의존할 수 있다는 것은 추론이다.
  - 상위 미들웨어가 런타임에 막는지는 증명 공백으로 남긴다.
- "모든 중대 발견을 자동 수정·병합·종결해 달라" → 후보와 검증된 발견을 나누고, AppSec이 수락한 건만 수정 및 검증으로 돌린다.
  - 승인, 병합, 티켓 종결은 고객 팀이 맡고, 미검증 건은 검증과 증거 확보부터 시작한다.

### 지식 점검 포인트
- 스캐너는 있지만 검증이 느리고 엔지니어링이 티켓을 불신 → **검증과 증거, 수정을 지원하되 인간 검토 책임 유지**.
- 로그인 변경 PR, 런타임 테스트 미승인 → **소스 근거 분석과 추론까지만 제공하고 런타임 증명은 주장하지 않음**.
- 업로드가 내부 파서에 닿는지 보는 검토 순서 → **위협 모델, 발견, 증거 검증, 정리, 제한적 수정, 재검증**.
- 관리자 권한 확인을 바꾸는 PR의 병합 전 검토 → **보안 측면의 코드 변경 사항 검토**. 시정을 수락한 발견이 아직 없다.
- 패치가 기능 회귀 테스트만 통과 → **수정 지원 자료가 준비됐을 뿐**. 엔지니어링 검토, 재검증, AppSec 승인이 남았다.
- 백로그 전체를 수정하고 티켓 자동 종결 요청 → **범위 정의, 후보와 시정 대상 구분, 검토자 지정부터**.

> **한 줄 요약:** Daybreak에 대한 관심을 승인된 하나의 워크플로와 대상, 검토 경로, 성공 지표로 묶은 범위 지정 평가로 바꿔 다음 결정을 증거로 내린다.

### 핵심 내용
#### 왜 범위 지정 평가가 중요한가
- Daybreak와 Codex Security에 대한 관심은 유용하지만 아직 **평가 계획**이 아니다.
- 범위 지정 평가는 고객의 범위 과잉 확장과 파트너의 과잉 약속을 막고, OpenAI 팀에 지원 판단 근거를 준다.
- 준비 점검 질문은 "무엇을 누가 검토하고, 어떤 증거가 유효하며, 끝에 무엇을 결정하는가?"다.
- 광범위한 평가는 야심차 보이지만, 저장소가 많으면 검토 시간이 모자라고 소유권이 불분명하면 증거 신뢰도가 떨어진다.
- 범위 지정 평가는 본격 출시, 전문 모델 접근 약속, 승인 없는 프로덕션 테스트 권한, 리포지토리 전반 자동 수정이 아니다.
- 대화가 특별 접근이나 자동 패치 같은 '접근 우선'이나 '자동화 우선'으로 흐르면 승인 워크플로와 증거 정의로 되돌린다.
- 질문은 "몇 건 찾았나"가 아니라 "**더 나은 보안 결정**을 내리게 도왔나"다. 증거를 갖춘 적은 발견이 더 가치 있다.

#### 첫 번째 평가 대상 선정
- 첫 평가는 저장소, 서비스, 백로그 세그먼트, 취약점 분류 같은 대상 하나에 집중한다.
- 강한 첫 대상은 소유권 명확, 승인됨, 범위 제한, 관련성, 검토 가능, 측정 가능, 맥락 풍부, 안전의 8기준을 갖춘다.
- 하나라도 빠지면 불가능하지는 않지만, 시작 전에 범위를 더 명확히 해야 한다.
- 대상은 병목에 맞춘다. 스캐너 노이즈가 문제면 백로그 슬라이스, 릴리스 위험이면 민감한 PR·diff 패턴이 낫다.
- 모든 저장소, 타사 인프라, 익스플로잇 위주 테스트, 중요 인프라는 부적절한 첫 대상이자 에스컬레이션 신호다.
- 이런 신호가 보이면 속도를 늦추고, 보안 담당자를 참여시키거나 OpenAI 전문가와 상의한다.

#### 평가 헌장 수립
- **평가 헌장**은 검증 질문, 범위 내·외, 검토자, 증거 기준, 성공 지표, 중단 조건을 담은 운영 합의서다.
- "보안 수준을 높일까?"는 약하다. "상위 50개 스캐너 발견을 더 적은 오탐으로 검증하게 돕는가?"가 강한 질문이다.
- 가설에는 기대 결과를 적는다(예: 검토자가 유효 발견과 잡음을 구분하고 개발자 인계를 더 명확히 준비한다).
- 범위 외 예로는 운영 환경 테스트, 타사 시스템, 익스플로잇 위주 검증, 자동 병합, 헌장에 없는 리포지토리가 있다.
- 범위 외 항목은 행정 세부가 아니라 평가를 보호한다. 범위 안에서는 빠르게, 밖으로 나가면 늦추게 한다.
- 도구가 아니라 **사람**을 지정한다. 흔한 실패는 도구와 대상만 정하고 인간 검토 경로를 빼는 것이다.
- 위험 결정, 시정 승인, 릴리스 결정 책임은 고객 보안·엔지니어링 팀에 있다.
- 증거는 파일, 스캐너 출력, 테스트, 검토자 메모 같은 구체적 산출물로 추적돼야 한다.
- 보존 산출물로 검토 기록, 증거 요약, 스코어카드, 시정 인계, 증거 미비 목록을 정한다.
- 승인과 관찰이 없는 런타임 증명, 패치 제안만으로 한 수정 완료 주장은 하지 않는다.
- Rokt CTO Clay Schubiner는 GPT-6 Astra가 버그 5개를 찾으면 5개 모두 실제 버그라고 보고했다.
  - 고객의 엔지니어링 관찰일 뿐 독립 평가가 아니다. 표본과 방법론이 없어 100% 정확도는 입증하지 않는다.
  - 공개 역량 증거는 참고일 뿐 고객 환경 결과를 입증하거나 테스트를 승인하지 않는다.

#### 성공 지표 정의
- 활동량이 아니라 더 나은 보안 결정을 측정하고, 지표를 고객 병목에 연결한다.
- "엔지니어링이 티켓을 불신"한다면 발견 건수 대신 증거 유용성, 인계 품질, 수정안 승인률을 본다.
- **발견 품질 지표**에는 타당성, 증거 유용성, 오탐 감소, 중복 감소, 검토자 신뢰도 등이 있다.
- 결과 전에 표본을 고정하고, 각 발견을 확인됨, 기각됨, 미해결로 같은 기준에 따라 기록한다.
- 새 모델을 현 설정과 비교할 때는 같은 조건에서 동등한 작업을 돌리고 차이를 기록한다.
- 검토되지 않은 발견을 '확인됨'으로 채점하지 않는다.
- 시정 지표는 수정 지원이 승인 범위에 있을 때만 쓴다. 제안된 수정은 승인된 시정이 아니다.
- 운영·거버넌스 지표는 한 번 잘 된 워크플로가 반복 가능하고 기존 업무에 맞아 확장할 만한지 판단하게 한다.
- 비용과 토큰 사용량 같은 효율 측정은 품질 지표를 보조할 뿐 대체하지 않는다.

#### 평가 주기와 고객 권고안
- 사전 점검의 핵심 질문은 "어떤 상황에서 평가를 중단해야 하나?"다.
- 보고서를 증거로 검토해 후보, 검증, 오탐, 증거 부족 등으로 분류한다. 심각도와 후속 조치는 사람이 정한다.
- 시정 검토는 헌장이 승인한 경우에만 확인된 발견에 좁게 잇는다. 제안된 수정은 자동 병합 결정이 아니다.
- 점검 지점은 계획, 초기 검토, 시정, 최종 검토 네 번이다.
- 최종 검토는 활동 요약이 아니라 **결정**이다. 미입증 사항, 다음 조치, 담당자, 다음 결정 시점을 담는다.
- 확장 기준은 결과 수집 전에 합의한다. 유망한 결과는 또 하나의 제한된 평가를 정당화할 뿐이다.
- 조정 후 합의된 사례를 반복하고 미해결 격차를 검토한 뒤에 확장을 고려한다.
- 확장은 범위를 느슨하게 하거나 검토를 생략하는 시점이 아니다.
- 권고안은 가치가 입증됐다고 주장하지 않고, 결정별 조건을 미리 정해 확장이 체계적 절차임을 보인다.
  - 예: 증거 품질이 높으면 인접 슬라이스로 확장, 신뢰도가 낮으면 조정, 프로덕션 테스트가 필요하면 일시 중지나 이관.
- 준비 항목이 빠졌다면 "거의 다 왔지만 검토자와 증거 상한선을 먼저 다듬자"고 말한다.

### 기억할 개념·프레임워크
- **범위 지정 학습 루프:** 대상 하나 선택 → 질문 정의 → 검토자와 증거 범위 확인 → 실행 → 증거 검토 → 결정.

| 역할 | 책임 |
|---|---|
| 비즈니스·보안 후원자 | 평가가 보안 목표를 어떻게 뒷받침하는지 확인 |
| AppSec·보안 검토자 | 발견 사항, 증거 품질, 심각도 근거 검토 |
| 엔지니어링 담당자 | 실현 가능성, 테스트 기대치, 시정 준비 평가 |
| 의사결정 책임자 | 계속, 조정, 확대 등 최종 결정 |
| 파트너·OpenAI 지원 | 고객 책임자를 대체하지 않고 범위 설정과 이관 지원 |

| 증거가 보여주는 것 | 책임 있는 다음 단계 |
|---|---|
| 결과 타당, 증거 품질 높음, 부담 감당 가능 | 인접 저장소나 백로그 슬라이스 하나로 확장 고려 |
| 검토자가 신뢰, 산출물이 기록 시스템에 부합 | 같은 검토 기준으로 평가 패턴 반복 |
| 다음 범위를 명확히 정의할 수 없음 | 확장 전 멈추고 범위를 다듬기 |
| 프로덕션 테스트, 전문 접근, 익스플로잇 위주 작업 요구 | 권고 전에 멈추고 상급 보고 |

- **첫 대상 패턴 6종:** 단일 소유 저장소, 단일 앱이나 서비스, 백로그 일부, 단일 취약점 분류, 단일 PR·diff 패턴, 승인된 하위 환경.
- **지표 영역:** 발견 품질, 개발자 인계, 수정 진행, 검토자 업무 부담, 운영 통제.
- **평가 후 결정 6종:** 계속, 조정, 확장, 일시 중지, 중단, 상급 이관.
- **강한 중단 조건:** 승인 대상 밖 접근, 미승인 런타임 테스트, 프로덕션 관련, 불분명한 데이터 처리.

### 실무 적용 예시
- "모든 저장소에 Daybreak를 돌려 보자" → 우선순위 저장소나 백로그 영역 하나로 시작한다.
  - 병목이 AppSec 적용 범위면 결제 서비스 저장소, 스캐너 노이즈면 지난주 SAST 상위 40개 항목 검증이 낫다.
  - 범위 지정 평가가 확장 가치를 입증하는 가장 빠르고 책임 있는 방법이라고 전한다.
- 파일럿 A는 저신뢰·중복 후보가 많고, B는 적지만 증거와 검토자 지침을 갖춤 → 결정 품질을 높인 **B**가 더 유용하다.
- 첫 평가 후 "모든 저장소에 적용할 수 있나?" → 같은 검토 모델로 인접 저장소 하나만 확대하고, 넓은 통합은 재현성 입증 뒤로 둔다.

### 지식 점검 포인트
- "모든 저장소에 먼저 적용하고 검토자와 지표는 나중에" → **승인된 단일 대상, 지정 검토자, 품질 기반 지표로 시작**.
- 복잡한 스캐너 백로그, AppSec과 엔지니어링 검토 가능 → **정의된 백로그 일부를 지정 담당자가 증거 품질로 검토**.
- 저장소 이름과 "Codex Security가 결과 검토"만 있는 계획 → **시작 전에 범위 외, 검토자, 증거 상한선, 지표로 헌장 완성**.
- 발견 건수를 지표로 제안하지만 병목은 유효성 판단 → **결함 타당성, 증거 유용성, 오탐 감소, 인계 품질, 검토 부담**.
- 첫 평가 성공 후 다음 주 전 저장소 CI/CD 통합 요청 → **CI/CD는 후속 단계로 두고 인접 저장소나 백로그 슬라이스 하나 추가**.
- 파일럿을 건너뛰고 광범위 배포를 묻는 고객 → **소유 저장소나 백로그 일부의 범위 지정 1차 평가를 먼저 권장**.

> **한 줄 요약:** 거버넌스를 Daybreak의 운영 모델 자체로 보고, 6가지 질문으로 준비 상태를 점검해 진행, 일시 중지, 에스컬레이션, 확장 중 다음 단계를 정한다.

### 핵심 내용
#### 거버넌스가 Daybreak의 운영 모델인 이유
- 사이버 워크플로는 소스 코드, 취약점 발견 사항, 수정 결정과 얽힌다. 그래서 거버넌스는 사후 고려가 아니라 **가치를 만드는 방식**의 일부다.
- "모든 것을 스캔해 달라", "모든 수정을 자동화해 달라"는 실제 긴급성을 반영하지만, 책임과 승인, 검토 단계가 없어 아직 안전하지 않다.
- **운영 모델**은 누가 무엇을 하고, 어떤 자산과 환경이 승인됐고, 누가 검토하며, 결정을 어디에 기록하는지 정하는 업무 패턴이다.
- 6가지 운영 모델 질문은 고객이 모델 접근, 프로덕션 테스트, 수정 자동화를 한꺼번에 꺼낼 때 속도를 늦추고 준비 상태를 확인하는 장치다.
- 컨텍스트, 에이전트 기반 런타임, 가시성의 세 계층은 영업과 기술 팀이 같은 언어로 말하게 하고, 초점을 접근이 아니라 워크플로에 둔다.

#### 승인된 범위, 고객 소유 자산, 방어 환경
- 첫 질문은 "이 작업을 해도 되는가?"다. 무엇을, 어떤 방어적 목적으로, 누구의 권한으로 조사하는지 묻는다.
- **승인됨**은 고객이 승인된 환경에서 지정 자산에 작업할 명시적 권한이 있다는 뜻이다. 방어적은 고객 자체 시스템을 보호하는 작업이다.
- 대상 시스템, 소유자, 검토자를 답하지 못하면 아직 준비 전이다. 기회가 나쁘다는 뜻이 아니라 권한과 범위를 먼저 밝히라는 뜻이다.
- 첫 워크플로는 **4요소 범위 명세서**로 요약하고, 이를 들고 자산 소유자와 검토자에게 승인 범위를 확인한다.
- 좋은 첫 대상은 관리할 만큼 좁고 증거를 낼 만큼 의미 있다(예: 고객 소유 저장소, 백로그 일부, 승인된 하위 환경).
- 프로덕션이나 라이브 테스트는 명시적 승인이 필요하며 기본 시작점이 아니다.

#### 접근 제어, 도구 권한, 데이터 처리
- 다음 질문은 "워크플로가 무엇에 접근하고 무엇을 할 수 있나?"다. 같은 작업도 권한에 따라 위험이 달라진다.
  - 예: 리포지토리 슬라이스 하나의 읽기 전용 검토는 좁지만, 브랜치 생성이나 티켓 업데이트까지 되면 위험이 바뀐다.
- 흩어진 접근 논의는 **사람, 시스템, 작업** 세 범주로 정리한다. 권한이 승인 범위에 비례하는지 보는 실용적 방법이다.
- 핵심 점검은 "도구가 할 수 있나?"가 아니라 "고객이 승인한 운영 모델에서 이 워크플로가 이 작업을 해도 되나?"다.
- 첫 워크플로는 **최소 권한 경계**에서 시작한다. 검증 품질 개선 여부만 알면 되면 읽기 전용으로 충분할 수 있다.
- 데이터 처리는 작업 전에 정한다. 최종 보고서가 안전해도 클론, 테스트 출력, 로그 같은 **임시 아티팩트**에 민감 정보가 남을 수 있다.
- 특별 보존 조건, ZDR, 접근 예외는 적절한 OpenAI나 고객 채널로 확인되기 전에는 약속하지 않는다.

#### 증거, 기록 시스템, 인적 검토
- 모든 결과물은 자동 티켓 대기열이나 종결 결정이 아니라 **사람이 검토할 증거**로 다룬다.
- 확실한 증거는 확정, 보류, 시정 같은 결정을 돕고, 약한 증거는 엔지니어링 반발과 과도한 주장을 낳는다.
- **의사결정 등급 증거 기록**은 검토자가 어떤 저장소와 환경을 썼고 결정이 어디 기록됐는지 추측하지 않게 한다.
  - 초기 워크플로에서 전 요소를 채울 필요는 없다. 민감해지거나 반복, 확장될 때 완전성 점검으로 쓴다.
- 모니터링과 감사가 불가능하면 확장 권고 전에 일시 중지, 범위 축소, 에스컬레이션을 고려한다.
- **기록 시스템은 고객 소유다.** Daybreak는 고객의 스캐너, 티켓 시스템, 위험 등록부를 대체하지 않고 보완한다.
- Codex 지원 실행은 증거 정리와 시정 제안을 돕는다. 위험 판단, 시정 승인, 기록 업데이트는 **고객 책임**이다.
- 이 책임 분담은 가치 제안의 약점이 아니라, 고객 책임성을 지키며 통제된 워크플로로 더 빨리 움직이게 하는 요소다.
- 검토 단계는 결과가 나오기 전에 정한다. 결과가 티켓이나 코드 변경에 영향을 주기 전에 누가 검토할지 확인한다.

#### 진행, 일시 중지, 에스컬레이션, 확장
- **진행**은 "모든 것을 자동화"가 아니라, 범위가 정해진 다음 단계를 뒷받침할 만큼 워크플로가 명확하다는 뜻이다.
- **일시 중지**는 조건이 불분명하거나 고객이 수동 검토 생략, 자동 종결을 원할 때 한다. 누락 조건과 해결 담당자를 명시한다.
- **에스컬레이션**은 접근, 통합, 자동화를 권하기 전에 더 깊은 검토가 필요하다는 뜻이다. 위험을 명확히 이름 붙여 전문가를 부른다.
- **확장**은 제한된 워크플로가 꾸준히 유용한 증거를 내고 검토자가 결과를 신뢰할 때만 한다. 결과가 나왔다는 것만으로는 부족하다.
- 핵심 변화는 "사이버 보안에 AI를 쓸 수 있나?"에서 "어떤 승인된 방어 워크플로를 관리하고 입증할 수 있나?"로 질문을 바꾸는 것이다.

### 기억할 개념·프레임워크

| 운영 모델 질문 | 명확히 하는 내용 |
|---|---|
| 1. 이 작업을 해도 되는가? | 승인, 방어적 목적, 고객 허가와 범위 |
| 2. 자산은 고객 소유이고 환경은 승인됐나? | 대상과 환경이 워크플로에 적합한지 |
| 3. 무엇에 접근하고 무엇을 할 수 있나? | 사람과 시스템의 권한, 허용 작업 |
| 4. 어떤 증거를 생성하고 보존, 기록하나? | 감사 가능성, 증거 품질, 기록 시스템 |
| 5. 어떤 결정이 고객 몫으로 남나? | 위험, 시정, 종결의 인적 책임 |
| 6. 다음 단계는 무엇인가? | 준비 상태에 따른 책임 있는 다음 단계 |

| 다음 단계 | 사용 시점 |
|---|---|
| 진행 | 승인, 범위, 검토, 근거가 갖춰진 고객 주도 상태 |
| 일시 중지 | 운영 모델 조건 중 하나가 불분명 |
| 에스컬레이션 | 요청이 민감하거나 고급이어서 OpenAI 확인 필요 |
| 확장 | 증거 품질, 검토 가능성, 거버넌스 통제를 입증 |

- **운영 모델 3계층**
  - 컨텍스트: 무엇이 승인됐고 무엇을 제외하나.
  - 에이전트 기반 런타임: 어디서 실행되고 어떤 도구와 작업이 허용되나.
  - 가시성: 무슨 일이 있었는지 추적하고 사람 검토 준비를 판단할 수 있나.
- **4요소 범위 명세서:** 고객 소유 자산, 승인된 환경과 접근 경로, 지정된 소유자와 검토자, 증거 요건과 중단 조건.
- **작업 경계 7종:** 읽기 전용, 승인된 테스트, 변경 제안 준비, 검토 가능한 PR 준비, 증거 내보내기, 반복 실행, 하류 작업.
  - 경계를 넓히기 전에 승인자, 실행 신원, 보존할 로그, 영향 전 검토자를 확인한다.
- **진행 조건 9가지:** 자체 보유 자산, 승인된 환경, 접근 경로, 허용 데이터, 도구 권한, 검토자 소유권, 증거 요건, 중지 조건, 기록 경로.
- **에스컬레이션 트리거 예:** 불분명한 권한이나 제3자 대상, 프로덕션 테스트, 익스플로잇 위주 작업, CI/CD 자동화, 가격과 ZDR 등.
- **안전한 성숙도 경로:** 수동 관리되는 제한된 워크플로 → 리포지토리 범위 반복 → 기록 시스템 통합 → 통제된 CI/CD 검토.
- **피할 표현:** "사이버 모델을 제공해 드릴 수 있다", "거절 사례가 없어진다", "Codex Security가 자동으로 수정하고 배포한다".

### 실무 적용 예시
- 스캐너 백로그에 묻힌 고객 → 첫 질문은 "어떤 모델을 쓸까?"가 아니라 "이 워크플로를 관리할 수 있나?"다.
  - 백로그 구간 하나, 저장소 하나, 승인 환경 하나, 지정 AppSec 검토자, 중지 조건부터 정한다.
- 그럴듯한 발견 사항 요약 → 검토와 제외 범위, 출처 사실과 추론, 미검증 사항, 기록 위치를 담은 증거 기록으로 바꾼다.
- 파일럿 성공 후 더 많은 앱으로 확장 요청 → 오탐 처리, 증거 보존, 결정 기록, 민감 사례 에스컬레이션이 되는지 먼저 확인한다.
  - 명확하면 확장할 수 있고, 아니면 확장을 멈추거나 범위를 좁힌다.

### 지식 점검 포인트
- 전체 백로그 자동 검증을 원하는 고객에게 운영 모델을 먼저 쓰는 이유 → **작업 전에 승인 자산, 실행 범위, 증거 경로, 고객 결정을 확인하게 해서**.
- 다음 단계로 논의할 준비가 된 첫 워크플로 → **승인된 하위 환경의 고객 소유 리포지토리, 지정 검토자, 합의된 증거 기대치, 중단 조건**.
- 접근 결정을 세 범주로 연결 → **사람, 시스템, 작업**.
  - 누가 승인, 실행, 검토하나는 사람, 범위 내 리포지토리와 티켓은 시스템, 읽기나 시정 제안 가능 여부는 작업이다.
- 작업별 소유자 구분 → 결과 요약과 승인된 표적 점검은 Codex 지원 실행, 중대성 판단과 병합 승인, 공식 종결 기록은 **고객 결정**.
- 수동 워크플로 1회 성공 후 같은 리포지토리에 같은 검토 게이트로 반복 요청 → **확장이 적절할 수 있다**.
  - 증거 품질과 공식 기록 경로가 입증됐으니, 검토 게이트와 고객 결정을 유지한 채 넓힌다.

> **한 줄 요약:** 제한된 워크플로의 증거를 범위에 묶인 가치 신호로 바꾸고, CISO가 수용할 가치 스토리와 8요소 경영진 보고로 과장 없이 다음 단계를 제안한다.

### 핵심 내용
#### 제한된 기술적 워크플로에서 입증된 가치로
- **범위가 제한된 워크플로**는 리포지토리 슬라이스 하나, 발견 유형 하나처럼 의도적으로 좁힌 승인된 방어 작업이다. 경계가 증거의 한계를 알려 준다.
- 제한된 워크플로가 증거를 만들고, 가치 스토리가 그 증거가 왜 중요한지 설명하며, 경영진 보고가 리더십 결정을 위해 메시지를 정리한다.
- 발견 사항, 수정 제안, 테스트 결과 같은 산출물은 그 자체로 가치를 입증하지 않는다. CISO는 노출 감소와 검토자 결정 개선을 알고 싶어 한다.
- **가치 증명은 활동 기록이 아니다.** "100개의 문제를 발견했다"는 활동이다.
  - "슬라이스 하나에서 검토자가 5건을 검증하고 오탐 추정 항목을 배제하며 시정 1건을 승인했다"가 가치 증명에 가깝다.
- 후보와 검증된 발견, 제안된 수정과 승인된 시정, 증명 공백과 실패를 구분해 말해야 신뢰를 지킨다.

#### 올바른 가치 신호 선택
- **가치 신호**는 증거가 뒷받침하는 구체적 고객 가치다. 경고가 넘치는 고객에게 "더 많은 발견"은 검토 부담만 늘린다.
- 가장 강한 보고는 대개 위험 신호 하나, 워크플로 신호 하나, 거버넌스 또는 확장 신호 하나를 묶는다.
- **지표는 범위와 연결될 때만 의미가 있다.** "12건 제외"보다 "검토된 백로그 구간에서 증거 기준 미달 12건을 제외했다"가 명확하다.
- 평가하지 않은 범위로 일반화하지 않는다. 벤치마크, 오탐률, 시간 절감 주장은 외부 공개 전에 승인된 출처로 검증한다.
- **개발자 인계**는 보안 가치가 가속되거나 정체되는 지점이다. 근거, 수정 지침, 테스트 기대, 책임 소재가 함께 가야 한다.
- 고객이 변경을 적용하고 재검증해 수락하기 전에는 "Daybreak가 수정했다"고 하지 않고 '위험 감소 진행'으로 쓴다.

#### CISO가 수용할 수 있는 가치 스토리 구축
- 기능이 아니라 고객 문제와 근거를 먼저 말하게 하는 커뮤니케이션 구조다.
  - 템플릿: [병목] → [범위] 안의 [증거] → 검토자 [결정] → [가치 신호] → [증명 공백] → [다음 조치·담당자·시기]
- **강한 가치 표현**은 구체적이고 범위가 명확하며 고객 결정과 직결된다. 가치를 더 분명히 하되 과장하지 않는다.
- **증명 공백**은 중립적으로 쓴다. "프로덕션 런타임 동작은 테스트하지 않았다"가 "운영에서 작동할지 알 수 없다"보다 명확하다.
- "도구가 이슈를 해결했다"보다 "워크플로가 검토자 승인을 뒷받침하는 증거를 냈다"가 더 강하다.
- Daybreak가 실행을 지원한 지점과 고객이 결정한 지점을 구분해, 검토 가능한 결과를 승인된 결과처럼 말하지 않는다.

#### 경영진 보고서 작성
- 경영진 보고는 기술 보고서도, 홍보 자료도, 발견 사항 목록도 아닌 **간결한 의사 결정 브리핑**이다.
- 신뢰를 얻을 만큼만 기술 세부를 넣는다. 평가 범위, 검토자 결정, 시정 상태, 미해결 공백은 넣는다.
- 악용 방법, 민감한 취약점 세부, 미승인 저장소 콘텐츠, 원시 로그는 넣지 않는다.
- 기술 증거는 비즈니스 문장으로 번역한다.
  - "스캐너 결과 40건 중 12건 도달 불가" → "조치 필요 항목과 오탐 추정 항목을 구분해 검토자 혼란을 줄였다".
- 공식 결정이 남는 **기록 시스템**을 밝히면, 일회성 보고서가 아니라 통제된 결정을 낳았다는 확신을 준다.

#### 결과 보고와 다음 조치 제안
- 대화 순서는 고객 워크플로 문제 → 명확한 범위 → 결정을 뒷받침하는 증거 → 미입증 사항 → 다음 조치다.
- "시범 운영이 성공적이었다"로 끝내지 않는다. 구체적인 다음 조치와 담당자, 일정으로 마무리한다.
- "확장 전에 어떤 증거 공백을 메워야 하나?"처럼 고객이 가치를 직접 검증하게 질문한다.
- **확장 준비 상태**는 더 넓은 배포가 아니라, 또 다른 범위 제한 평가를 제안할 근거가 생겼다는 뜻이다.
- 경영진이 더 큰 주장을 요구하면 입증된 것, 방향성이 유망한 것, 추가 검증이 필요한 것을 나눠 답한다.

### 기억할 개념·프레임워크

| 가치 신호 범주 | 보여 주는 것 | 신호 예시 |
|---|---|---|
| 위험 감소 | 고객이 변경을 적용하고 재검증 후 수락 | 수정 적용, 재검증 완료, 범위 내 노출 감소 |
| 워크플로 효율성 | 마찰이 줄어든 업무 진행 | 오탐 감소, 검토자 시간 절약, 명확한 개발자 인계 |
| 거버넌스 신뢰도 | 고객 통제 유지와 의사 결정 이력 | 더 강한 증거, 감사 가능성, 문서화된 증명 공백 |
| 확장 준비도 | 다음 단계를 정당화할 근거 | 반복 가능한 워크플로, 명확한 성공 기준 |

| 경영진 보고 8요소 | 답하는 질문 |
|---|---|
| 범위 | 무엇을 검토했나 |
| 증거 | 어떤 사실과 검증 결과가 결론을 뒷받침하나 |
| 결정 | 고객은 무엇을 승인, 거부, 보류했나 |
| 가치 신호 | 왜 중요한가 |
| 다음 조치 | 증거에 비춰 어떤 조치가 타당한가 |
| 책임자 | 누가 맡나 |
| 시기 | 다음 검토 시점은 언제인가 |
| 증명 공백 | 어떤 미입증 조건이 다음 조치나 주장을 제한하나 |

- **첫 가치 메시지 구조:** "승인된 [범위]에서 [작업]을 했고 검토자는 [결정]했다. [가치 신호]를 뒷받침하지만 [공백]은 검증이 필요하다."
- **개발자 인계 5요소:** 구체적 문제, 발견 근거, 시정 맥락, 예상 테스트와 검토 항목, 담당자와 다음 조치.
- **책임 있는 다음 단계 5종:** 같은 워크플로 내 계속, 다른 제한된 워크플로로 확장, 증거 기준 개선, 거버넌스 강화, 에스컬레이션.
- **흔한 증명 공백:** 미테스트 런타임 동작, 제한된 리포지토리 범위, 미해결 심각도 판단, 회귀 테스트 증거 누락 등.
- **피할 표현:** "Daybreak가 모든 것을 찾았다", "이제 검토자가 필요 없다", "수동 검토를 건너뛸 수 있다".

### 실무 적용 예시
- 40건 검토 결과 5건 검증, 12건 제외, 1건 수정 제안이 엔지니어링 검토로 감 → "40건을 찾아 1건을 고쳤다"는 과장이다.
  - "5건 검증, 12건 제외, 1건 시정 단계 진행, 프로덕션 런타임은 미테스트"가 신뢰할 수 있는 메시지다.
- "이 시범 운영으로 모든 앱의 위험 감소가 입증됐나?" → 위험 감소의 진전이지 입증은 아니라고 답한다.
  - 입증하려면 고객이 변경을 적용하고 재검증해 수락해야 하며, 다른 앱에서도 재현되는지 테스트해야 한다.
- "시범 운영은 성공적이었다"로 마무리하려 함 → 결과와 가장 강한 신호, 미입증 사항을 말한 뒤 두 번째 제한된 평가를 제안한다.

### 지식 점검 포인트
- 검토자가 3건 검증, 수정 경로 1건 검토용 수락, 런타임 미테스트 → **"승인된 슬라이스에서 검증 3건, 검토용 수정 경로 1건, 런타임 검증 공백 1건"**.
  - 범위 안으로 한정하고, 결정과 산출물을 구분하며, 공백을 밝혔다.
- 적용하고 재검증한 시정 1건을 고객이 승인 → **위험 감소** 신호다.
  - 증거 기준 미달 12건 제외는 워크플로 효율성, 결정과 누락을 티켓 시스템에 기록한 것은 거버넌스 신뢰도다.
- CISO가 가장 안심할 가치 스토리 → **승인된 부분이 검토자 수용 증거를 냈지만, 더 넓은 적용엔 별도의 제한된 검증이 필요하다**.
- 결정이 공식 기록에 없고 다음 검토 단계도 불분명한데 CI/CD로 바로 가자는 후원자 → **두 번째 평가의 기록, 검토 게이트, 승인 절차부터 확인**.

> **한 줄 요약:** 가상의 Harborline Bank 사례에서 넓은 요청을 신호로 받아 첫 패턴과 제한된 평가를 고르고, 증거를 보정해 6섹션 파트너 안전 권고안으로 정리한다.

### 핵심 내용
#### 고객 배경과 사례 설정
- Daybreak는 방어적 사이버 워크플로 절차이지, 모델 접근 제안도 자동 문제 해결 약속도 아니다.
- **Harborline Bank**는 디지털 고객 포털을 현대화 중인 가상의 지역 금융사다. 혼잡한 AppSec 백로그와 검토자 부족, 릴리스 압박을 안고 있다.
- 당면 결정은 customer-account-service의 권한 부여 로직을 바꾸는 PR이다. 이해관계자마다 우선순위가 다르다.
- 사례 파일은 알려진 사실, 합리적 가정, 미해결 질문을 구분해 읽는다.
- 과제는 취약점 입증이나 전체 배포 계획이 아니다. AppSec과 엔지니어링이 결정권을 유지하는 **책임 있는 첫 단계**를 제시하는 것이다.
- 모듈마다 산출물을 쌓는다: 신호 요약 → 진단 → 경로와 패턴 → 평가 계획 → 증거 검토 메모 → 권고안.

#### 페르소나, 병목, 사용 사례 파악
- **사이버 페르소나**는 직함이 아니라 의사 결정 관점이다. 무엇을 책임지고 어떤 증거를 신뢰하는지로 정의한다.
- "CISO는 위험을 중시한다"로는 부족하다. 첫 평가가 소유 리포지토리에 한정되고 기록 가능한 증거를 낸다는 확신이 필요하다고 쓴다.
- 병목은 신호 부재가 아니라, 신호가 검증과 검토 가능한 조치로 이어지기 전에 막히는 데 있다.
- "모든 AppSec 작업이 느리다"는 너무 넓다. "권한 관련 PR에 릴리스 전 추가 보안 작업이 필요한지 증거로 판단할 방법"이 구체적이다.
- 첫 사용 사례는 **권한 부여 관련 PR의 코드 변경 검토**다. 백로그 검증은 첫 검토가 명확한 결정을 낸 뒤의 확장 경로다.

#### 경로 지정과 워크플로 패턴 선택
- "모든 리포지토리에서 Daybreak를 쓸 수 있나?"는 출발점이 아니다. 고객 소유이고 지정 검토자가 있는 권한 관련 PR부터 시작하자고 재구성한다.
- 결정 기준은 가능한 가장 큰 목표가 아니라 **첫 고객 결정에 패턴을 맞추는 것**이다.
- 첫 패턴은 Codex Security의 코드 변경 사항 검토다. 인증, 권한 부여, 고객 데이터 같은 민감 로직의 제한된 변경에 맞다.
- 사이버 보안 전용 접근, ZDR, 가격, 프로덕션 테스트, 자동 수정, 취약점 탐지 보장은 약속하지 않고 SME에게 에스컬레이션한다.

#### 범위 지정 평가와 증거 검토
- 대상은 customer-account-service의 권한 부여 관련 PR과, 이를 검토하는 데 필요한 권한 부여 파일과 테스트다.
- **범위 외 항목**은 승인 범위 밖으로 번지는 것을 막는다. 프로덕션 테스트, 실제 환경 재현, 타사 인프라, 고객 데이터, 자동 병합을 뺀다.
- 의사 결정 책임자는 AppSec 검토자, 엔지니어링 담당자, PR 진행 여부를 정하는 의사결정권자다.
- 평가는 이 diff가 권한 문제를 만드는지에는 답할 수 있지만, 런타임 악용 가능성과 전사적 위험은 입증할 수 없다.
- 성공은 발견 건수가 아니라 결정 품질로 잰다. 검토자가 증거 기록으로 후보를 수용, 거부하거나 추가 증거를 요청할 수 있으면 강한 지표다.
- 가상 출력 "권한 검사가 우회될 수 있다"는 액면 그대로 받지 않고 증거 라벨로 검증한다.
- 처리는 **후보 발견 사항, 추가 검토 필요**다. 런타임 증명과 검토자 결정이 없어 검증된 결과가 아니고, 출처 사실이 있어 오탐도 아니다.

#### 파트너 안전 권고안 마련
- 6섹션 구조는 실행하기엔 너무 모호한 권고와, 결정을 돕기엔 너무 기술적인 권고라는 두 실수를 막는다.
- **파트너 안전 언어**는 조심스러워 보이려는 게 아니라 신뢰를 지키기 위한 것이다. 방어적이고 워크플로 중심이며 사람 검토를 분명히 한다.
- 좋은 권고안은 다음 자가 점검을 통과한다.
  - 즉각적 의사 결정 시점을 짚고, 범위가 명확한 첫 단계를 제시했다.
  - 의사 결정 책임자를 명시하고, 근거와 증명 공백을 구분했다.
  - 사이버 보안 전문 접근, 운영 환경 테스트, 자동 수정, 취약점 발견 보장을 약속하지 않았다.

### 기억할 개념·프레임워크

| 페르소나 | 의사 결정 관점 | 권고안이 다룰 것 |
|---|---|---|
| CISO | 위험, 거버넌스, 경영진 신뢰 | 범위가 명확하고 인적 책임과 연결된 작업 |
| AppSec 책임자 | 발견 타당성, 증거 품질 | 후보, 증거 공백, 검토자 결정의 구분 |
| DevSecOps 관리자 | 재현성, 도구 적합성 | 기록 시스템 우회와 성급한 CI/CD 통합 회피 |
| 엔지니어링 이사 | 릴리스 준비, 개발자 인계 | 자동 승인을 전제하지 않는 PR 검토 지원 |

| 권고안 섹션 | 포함할 내용 |
|---|---|
| 고객 상황 | 고객 신호, 주요 페르소나, 병목, 사용 사례 |
| 권장 경로 | 기회 경로와 선택한 Codex Security 패턴 |
| 범위 지정 평가 | 승인 대상, 검토자와 검토 절차, 범위 외 항목 |
| 성공 기준과 안전장치 | 성공 지표, 예상 산출물, 에스컬레이션 조건 |
| 증거 현황 | 후보 상태, 출처 사실과 추론, 증명 공백 |
| 다음 조치 | 고객, 파트너, OpenAI SME 조치와 담당자, 시기 |

- **증거 라벨(이 사례)**
  - 출처 사실: 이 diff가 계정 업데이트 경로를 변경한다.
  - 뒷받침되는 추론: 변경된 경로는 AppSec 검토가 필요할 수 있다.
  - 런타임 증명: 이번 사례에는 없다.
  - 지원되지 않는 주장: "무단 접근이 입증됐다".
  - 증명 공백: 경로 수준 통제가 이미 권한 부여를 강제하는지 알 수 없다.
- **첫 패턴 적합성**
  - 코드 변경 사항 검토: 첫 선택이다. 권한 관련 PR이라는 즉각적 결정에 맞다.
  - 백로그 분류: 주요 문제가 백로그 검증으로 바뀔 때의 확장 패턴이다.
  - 심층 보안 스캔: 첫 검토 루프가 효과를 입증하기 전에는 검토 부담만 키운다.
  - 발견 사항 수정 및 검증: 발견이 승인되고 시정이 범위에 들기 전에는 시기상조다.
- **증거 검토 4질문:** 증거는 무엇인가, 한계는 무엇인가, 결론을 어떻게 기술할까, 다음에 누가 검토하나.

### 실무 적용 예시
- "모든 리포지토리에 Daybreak를 쓸 수 있나, 전문 접근이 도움이 되나?" → 요청은 결론이 아니라 신호다. 워크플로와 검토자, 범위부터 정한다.
- 증거 해석 메모 → "런타임 검증이 승인되지도 수행되지도 않아 검증된 취약점으로 제시하지 않는다"고 쓴다.
  - 이어서 AppSec과 엔지니어링이 변경 경로와 다른 곳의 권한 적용을 확인할 다음 조치를 적는다.
- "모든 저장소를 스캔하고 권한 문제를 해결하며 전용 접근도 돕는다"는 권고 → 범위, 결과, 접근을 과잉 약속한다.
  - 강한 권고는 권한 관련 PR부터 검토하고, 넓은 범위와 CI/CD, 접근 경로는 첫 검토 주기 뒤에 다룬다.

### 지식 점검 포인트
- Harborline의 초기 신호 → **넓은 요청이지만 첫 단계에서 승인된 워크플로, 검토자, 범위, 검증 지점을 명확히 해야 한다**.
- "이 권한 관련 PR이 릴리스 위험 없이 진행될 수 있나"라는 엔지니어링 이사 → **민감 PR의 코드 변경 사항 검토가 첫 사용 사례**.
- 모든 리포지토리와 전문 접근을 묻는 고객의 첫 접근 → **권한 관련 PR부터 시작하고, 범위가 확정될 때까지 접근 논의를 미룬다**.
- 첫 평가 계획 → **소유 저장소의 권한 관련 PR 검토, 프로덕션 테스트와 자동 수정 제외, 증거 기록으로 다음 조치 결정**.
- "우회될 수 있다"는 출력에 런타임 검증도 AppSec 결정도 없음 → **AppSec과 엔지니어링 검토가 필요한 후보 발견 사항**.
  - 미입증은 오탐이 아니고, 출력이 구체적이라고 검증된 발견이 되지도 않는다.

### 핵심 내용
#### 과제와 고객 상황
- 가상 고객 상황을 읽고 250~400단어, 1페이지 권고안을 쓴다. 약 20분이 걸리고 사람이 검토한다.
- Northstar Financial은 3일 뒤 `customer-account-service`의 **계정 업데이트 승인 로직**을 바꾸는 PR을 낸다.
- AppSec 팀에는 저신뢰가 많은 미해결 발견 62건이 있고, 팀장은 이번 주에 1건만 검토할 수 있다.
- 엔지니어링 이사는 명확한 출시 결정과, 쓸모 있는 증거를 담은 개발자 전달을 원한다.

#### 승인 범위와 주어진 증거
- **승인됨:** 인증 PR과 직접 관련된 파일, 테스트의 읽기 전용 검토.
- **승인 안 됨:** 다른 리포지토리, 프로덕션 테스트, 취약점 재현, 타사 시스템, 자동 수정과 병합, 자동 릴리스 결정.
- 변경된 경로에서는 이전에 있던 역할 확인 헬퍼가 더 이상 호출되지 않는다.
- 기존 테스트는 다른 고객 계정 업데이트 가능 여부를 보여 주지 않고, 런타임 검증도 하지 않았다.

#### 권고안 필수 섹션 6개
1. **고객 현황:** 지금 내릴 결정, 결정권자, 막힌 지점
2. **권장 첫 단계:** 가장 먼저 할 제한된 검토와 그 이유
3. **범위와 검토자:** 범위 내·밖, 책임질 고객 측 검토자
4. **증거 현황:** 직접 근거, 합리적 추론, 우려 분류, 미입증 사항
5. **성공 지표와 안전 장치:** 유용한 검토의 조건과 지킬 경계
6. **다음 조치와 담당자:** 다음 단계, 책임자, 그로써 내릴 결정

### 기억할 개념·프레임워크

| 앞선 강의 개념 | 이 랩에서 쓰는 곳 |
|---|---|
| 가장 좁은 패턴 선택(1강) | 전 리포지토리 스캔 대신 코드 변경 검토 1회 |
| 근거, 추론, 증거 공백(3·4강) | 증거 현황 섹션의 구분 |

- 헬퍼 누락은 직접 근거, 타 계정 수정 가능성은 추론이다. 그래서 **검증 전 후보**로 분류한다.

### 실무 적용 예시 — 제출한 권고안 요약
- 결정은 릴리스, 수정 후 릴리스, 보류 중 하나다. 릴리스는 엔지니어링 이사, 우려 판정은 AppSec 팀장이 맡는다.
- 첫 단계는 인증 PR 읽기 전용 변경 검토 1회다. 백로그 정리는 그 뒤에 범위를 따로 합의한다.
- 증거는 직접 근거, 추론, 검증 전 후보, 미입증(악용 가능성, 런타임 동작)으로 나눴다.
- 개발자가 타 계정 업데이트를 거부하는 부정 테스트를 넣고, AppSec 팀장이 후보를 확정하거나 기각한다.

### 지식 점검 포인트
- 객관식 없이 사람이 검토한다. 좋은 제출물의 조건:
  - 넓은 요청을 승인 범위 안의 가장 작은 검토로 바꾸고, 범위 밖 항목을 명시한다.
  - 근거와 추론을 섞지 않고 우려를 후보로 분류한다.
  - 다음 조치마다 담당자와 내릴 결정을 붙이고, 자동화나 보안 결과를 약속하지 않는다.
